= Diagram Preview with a Local Kroki
:toc: left
:toclevels: 3

This guide captures how AsciiDoc diagrams (Mermaid, PlantUML) are rendered in the VSCode
preview for this repository, and why the rendering runs against a *local* Kroki server rather
than the public one.

It exists so diagram previews do not silently break and so the setup survives a machine change
or a reboot without re-discovery.

== Purpose

The docs in `docs/architecture/` rely on Mermaid diagrams (see the project standard: Mermaid, not
PlantUML). The VSCode `asciidoctor.asciidoctor-vscode` extension renders those `[mermaid]` blocks
through *Kroki*. This guide makes that rendering reproducible:

* explain why a local Kroki is required (the public one is not enough here)
* record the container project and the Docker context that runs it
* record the single VSCode setting that points the preview at it

== Why a local Kroki (the failure we hit)

The public `kroki.io` endpoint, from this network, only *serves diagrams it already has cached*
and cannot perform a *fresh* render. The symptom is precise and misleading: a diagram that already
existed (e.g. an unchanged block copied from another doc) renders fine, but any *new or edited*
diagram shows an empty frame — "Diagram / Last updated <timestamp>", no figure. Changing a single
character in a working block is enough to make it vanish.

A local Kroki renders fresh content reliably, so every new diagram displays. Mermaid specifically
needs a *companion* container (`kroki-mermaid`) alongside the Kroki core; PlantUML and Graphviz are
handled by the core itself.

== Where it runs: the `nerd-nixos` Docker context

The Docker engine is not local to the Mac — it is the *podman* engine on `bioskop-nixos`, reached
over SSH. A Docker context wraps that endpoint:

[source,console]
----
$ docker context create nerd-nixos \
    --docker "host=ssh://nxmatic@bioskop-nixos.local/run/podman/podman.sock"

$ docker context use nerd-nixos
$ docker context ls
NAME          URI                                                       DEFAULT
nerd-nixos    ssh://nxmatic@bioskop-nixos.local/run/podman/podman.sock  true
----

NOTE: The server reports version `5.7.0` — that is *podman* behind the `docker` CLI, not Docker
Engine. The `docker compose` plugin drives it the same way.

`DOCKER_HOST` works too, but the URL form needs the double slash:

[source,console]
----
export DOCKER_HOST=ssh://bioskop-nixos        # correct
# DOCKER_HOST=ssh:bioskop-nixos                # WRONG: not a URL, fails
----

Two prerequisites the `ssh://` transport needs (both satisfied on `bioskop-nixos`): non-interactive
SSH (key-based, `BatchMode=yes` succeeds) and `docker` on the *non-login* PATH (here
`/etc/profiles/per-user/nxmatic/bin/docker`, provided by the nix profile).

== The container project: `.dev/kroki`

The compose project lives at `.dev/kroki/compose.yaml`. Both services use
`restart: unless-stopped` so they come back after a reboot of `bioskop-nixos`.

[source,console]
----
# from the repo root, against the nerd-nixos context
$ docker --context nerd-nixos compose -f .dev/kroki/compose.yaml up -d
$ docker --context nerd-nixos compose -f .dev/kroki/compose.yaml ps
----

The Kroki core delegates Mermaid to the companion via `KROKI_MERMAID_HOST=mermaid` /
`KROKI_MERMAID_PORT=8002`, and publishes the core on port `8000`.

== Wiring the VSCode preview to it

The extension reads the Kroki URL *only* from the AsciiDoc attribute `kroki-server-url` (verified in
the extension source: `document.getAttribute('kroki-server-url') || 'https://kroki.io'`). A
`.vscode/settings.json` entry is *not* consulted for this — setting it there silently leaves the
preview pointed at the public `https://kroki.io`, which only serves cache and yields empty frames.

To set the URL *once* for the whole repo without editing every document header, use a
`.asciidoctorconfig` file at the repository root. The extension picks it up automatically and
prefixes its content to every `.adoc` it renders:

[source]
----
# .asciidoctorconfig (repo root)
# :kroki-server-url: http://bioskop-nixos.local:8000
----

`bioskop-nixos.local` is the *mDNS* name of the host running the Kroki container. seed-outcluster is always
operated from `bioskop` (reached by screen-sharing the RDP host → VSCode), and `bioskop-nixos` sits on
the same LAN, so both this shell and the VSCode webview resolve `bioskop-nixos.local` directly — no
tailscale route involved. (An earlier revision pinned the *tailscale* IP `100.64.0.15` as "stable
across networks"; that was a mix-up with a different machine on a guest network — it is not routable
from `bioskop` and gave empty frames. The mDNS name is the reliable channel for this work environment.)
Individual `.adoc` files stay clean: no per-machine URL inside them, and the one place to change (or
drop, to fall back to a public Kroki) is this root file. Only `asciidoc.extensions.enableKroki: true`
stays in `.vscode/settings.json`.

== Allow the http:// image in the webview (the last, non-obvious step)

Even with the server rendering correctly and the URL wired, the figure can still show an empty frame.
The webview's Content-Security-Policy allows `img-src https:` but *not* `http:` at the default
security level — and the local Kroki is served over *http*. So the rendered image is fetched and then
*blocked by the CSP*.

Fix it once per workspace via the VSCode command palette:

. *AsciiDoc: Manage Preview Security Settings*
. choose *Allow insecure content*
. reload the window

CAUTION: On some builds (seen on VSCode Insiders) the quick-pick shows the raw l10n
*identifiers* instead of resolved labels. The entry to pick is then literally
`security.insecureContent.title` — it maps to security level `1`
(`AllowInsecureContent`). Do *not* pick `security.insecureLocalContent.title` (level `3`):
"local" means `localhost`, and the Kroki host here is a *LAN* name
(`bioskop-nixos.local`), which that level does not cover.

*Why "insecure content" relates to https:* in CSP terms, "insecure content" means *content loaded
over http* (non-TLS). The default policy permits `img-src https:` but not `http:`; our local Kroki is
served over http, so its image is refused. "Allow insecure content" simply adds `http:` to the
allowed sources. The two ways out are therefore the same coin: *allow http* (this option), or *serve
Kroki over https* (a TLS reverse-proxy), which the default CSP already accepts without any change.

*Where the setting lives (and why it must be re-done per worktree).* It is *not* in any
`settings.json` (user, workspace, or folder). The extension stores it in its own *globalState*
Memento — on macOS:

[source]
----
~/Library/Application Support/Code - Insiders/User/globalStorage/state.vscdb
  -> ItemTable, key "asciidoctor.asciidoctor-vscode"
     { "preview_security_level:file://<workspace-root>": 1, ... }
----

The map is keyed by the *workspace-root URI*. So the choice is bound to the exact root path, not to
the repo: it survives a reboot and a re-open of the same path, but a *fresh path* starts back at
Strict (`0`) and the figures go blank again. Under the external-worktree model — where every branch
is checked out at its own `<repo>.d/<namespace>/<branch>` path — this means *each new worktree needs
its own "Allow insecure content" toggle* the first time its preview is opened. Same reason it must be
re-done on another machine (a different globalState DB).

Inspect the current state directly:

[source,console]
----
$ sqlite3 "$HOME/Library/Application Support/Code - Insiders/User/globalStorage/state.vscdb" \
    'SELECT value FROM ItemTable WHERE key = "asciidoctor.asciidoctor-vscode";'
{"preview_security_level:file:///private/var/lib/git/nxmatic/rke2lab.d/feature/cluster-seed-scenario":1}
----

NOTE: How we proved this was the cause: enable Kroki DEBUG logging
(`JAVA_OPTS: "-Dlog.level=DEBUG"` on the `kroki` service) and watch its logs while reloading the
preview. The server logged `Request received /mermaid/svg` + `Convert took NNms` — so the request
*did* reach the server and rendered; the empty frame was therefore the webview refusing to display
the http image, i.e. the CSP.

== Verifying the render

A direct POST proves a *fresh* render (not a cache hit):

[source,console]
----
$ printf 'graph TB\n subgraph G[x]\n A[ping]-->B[pong]\n end\n' \
    | curl -s -X POST http://bioskop-nixos.local:8000/mermaid/svg --data-binary @- \
      -o /dev/null -w "HTTP %{http_code}\n"
HTTP 200
----

== Troubleshooting

[cols="1,2",options="header"]
|===
|Symptom |Cause / fix
|A diagram shows an empty "Diagram / Last updated …" frame, and the Kroki log shows NO request on reload |The URL is not reaching the extension. Confirm the repo-root `.asciidoctorconfig` carries `:kroki-server-url:` (a `.vscode` setting is *not* read for this) and the container is up.
|Empty frame, but the Kroki log DOES show a rendered request |The webview CSP is blocking the http image. Run *AsciiDoc: Manage Preview Security Settings* → *Allow insecure content* (see the section above).
|Only previously-seen diagrams render; brand-new/edited ones are empty |You are on the public `kroki.io`, which only serves cache. Point at the local Kroki.
|Preview shows a stale figure after editing the file outside VSCode |The preview can cache; reload the window (Developer: Reload Window) to force a re-read.
|`docker` cannot connect / context not found |Ensure the `nerd-nixos` context exists and `bioskop-nixos` is reachable over SSH; `docker --context nerd-nixos ps` should list the kroki containers.
|===
