= Cluster Seeding Controller — seed-incluster
:toc: left
:toclevels: 3

The in-cluster twin of `seed-master`. Where `seed-master` seeds a cluster from
the *host* (Pulumi/nix, out-of-band), `seed-incluster` is the *in-cluster*
reconciler that brings CAPI's view of the fleet into being and keeps it true —
**by adopting the clusters that are already running, not by re-provisioning
them**. It realises the adoption handoff that
link:management-workload-topology.adoc[Management / Workload Topology] describes
as a direction (its
link:management-workload-topology.adoc#mgmt-adoption[Adoption — the Pulumi→CAPI
handoff] section) and closes its open *workload follow-up*.

== Overview — what, why, the problem it solves

CAPI/CAPRKE2/CAPN natively *provision* clusters: they launch instances and
bootstrap a fresh control plane. They do **not** natively *adopt* an
RKE2-on-Incus control plane that is already running — the exact situation this
project lives in, for two structural reasons:

. *Cold-start survivability.* The management cluster is nix-seeded and
  reconstructible from git; a cold-start (`pulumi destroy` + recreate) **wipes
  its etcd**, so every CAPI object describing the fleet vanishes. But the
  *workload* clusters are independent Incus infra with their own etcd — they
  **survive**. Re-provisioning them from a fresh management plane would destroy
  live clusters. They must be **re-adopted**, idempotently, from the surviving
  reality.
. *Single-owner (Flux ↔ CAPI/CAPN).* If Flux renders the full CAPI CR-set and
  CAPI/CAPN then mutates those same objects during reconcile, two reconcilers
  fight over one object → SSA flap. One object = one owner.

`seed-incluster` resolves both. It reconciles a rich *intention*
(`ClusterIntention`, Flux-owned) into a CAPI CR-set it **owns** (so those
objects leave the Flux set), and its reconcile is **adopt-first**: it always
tries to describe the running reality before it ever provisions. A wiped
management etcd is re-derived, not lost.

[TIP]
====
The controller code exists today as the `rke2-adoption-controller`
(`ClusterAdoption` CRD, per-step status conditions, owned `Machine` +
concrete `LXCMachine(providerID)`). This document is the design of its
*evolution*: add the `ClusterIntention` + `PoolIntention` intention resources (and
the `PoolAdoption` mirror — the <<resource-model,2×2>>), the adopt-first state
machine, and generalise from a single control-plane node to the full *all-pets*,
per-**pool** node model (see <<all-pets>>). The renames it implies
(`rke2-adoption-controller` → `seed-incluster`, group
`adoption.seedmatic.io` → `cluster.seedmatic.io`,
`ExecutionEnclosure.OPERATOR` → `STANDALONE`) are tracked in <<naming>>.
====

== The core primitive — adopt = reconcile with an already-running cluster

This is the central capability, and the one thing CAPI cannot do for us:

[IMPORTANT]
====
**Adopting a cluster = reconciling CAPI's description with a control plane that
is ALREADY running, idempotently.**

* *Match* the running instance by its **deterministic providerID**
  (`lxc:///<cluster>-<node>`) — no fuzzy discovery: the node name is SSOT
  (`ClusterNetworkBlueprint.CANONICAL_NODE_NAMES`).
* *Materialise* the CAPI CR-set in **adopt mode**: `providerID` pre-set +
  **bootstrap SKIPPED**, so CAPRKE2 does not re-bootstrap and CAPN does not
  re-launch — CAPI merely **describes** the existing node.
* *Idempotent*: re-runnable on every reconcile (cold-start, requeue) — it
  re-attaches without churn. The adopt-first state machine guarantees it.
====

Proven today for the management cluster (self-adoption: `RemoteConnectionProbe=True`).
The design generalises it to the workload and makes it cold-start-idempotent.

[[resource-model]]
== The resource model — a 2×2 (intention × grain)

Extending `ClusterAdoption` with "how to create a cluster" mixes two roles; and a
single monolithic `ClusterIntention` carrying the whole cluster (all pools, all
pets) fights CAPI's OWN grain, which is already decomposed cluster / pool / node.
So the model is a **2×2**: two ROLES (intention vs mirror) across two GRAINS
(cluster vs pool), in group `cluster.seedmatic.io`.

[cols="1,1,1",options="header"]
|===
| | cluster (parent / aggregate) | pool (child, N uniform)

| **intention** (Flux-rendered) | `ClusterIntention` | `PoolIntention`
| **mirror** (controller-owned) | `ClusterAdoption` | `PoolAdoption`
|===

* **`ClusterIntention`** (1/cluster) — the cluster-level intention: kind, remote
  (endpoint + per-remote CAPN identity), image, versions, VIP, CIDRs. Materialises
  `Cluster` + `LXCCluster`.
* **`PoolIntention`** (N/cluster, ownerRef → `ClusterIntention`) — one per **pool**
  (`control-node`, `gpu-node`, …): the pool's TEMPLATE (its CAPI stamp) + the named
  pet roster. Materialises `RKE2ControlPlane` (pool `control-node`) /
  `MachineDeployment` (a worker pool) + `LXCMachineTemplate` + the per-pet `Machine`
  + `LXCMachine`. Pools are UNIFORM — `control-node` is a pool like any other; its
  control-plane-ness is DERIVED (its `RKE2ControlPlane` is what the `Cluster`
  references), not a special resource. A pet stays a roster entry (the `Machine` is
  CAPI's node CR — there is no "NodeProvision").
* **`ClusterAdoption`** (1/cluster) — the cluster mirror: EXISTENCE (does any node
  of any pool exist? see <<existence>>) + REACHABILITY (`Cluster.RemoteConnectionProbe`
  — is the intention realised?). Cold-start-safe: re-derived from reality.
* **`PoolAdoption`** (N/cluster) — the pool mirror: its pets' PRESENCE (by
  `providerID` / the `LXCMachine` status) and per-pool adoption.

.The FloxCatalog / FloxEnv shape
[TIP]
====
The intention decomposition mirrors the flox-controller: `ClusterIntention` ~
`FloxCatalog` (the parent — reconciles the source, aggregates its children's
readiness + propagates to them) and `PoolIntention` ~ `FloxEnv` (N uniform
children). We ADD the mirror layer (`ClusterAdoption` / `PoolAdoption`) that
flux-controller has no equivalent for, because we do adopt-first over SURVIVING
state — the mirror is re-derived at cold-start, never a persistent flag.
====

Two roles, two grains: **Provision** (bring into existence) ↔ **Adoption**
(describe the existing), each at the **cluster** and **pool** grain.

[[all-pets]]
=== All nodes are named pets — no cattle

Every node (control plane *and* workers) is a **named pet** from the blueprint
(`<cluster>-<node>`, `CANONICAL_NODE_NAMES`), bootstrapped once by CAPN then
adopted by `providerID`. **CAPI is a full mirror**; a cold-start re-adopts
*everything* uniformly (same per-node reconcile). No node is ever discarded.

This is the resolution of the *workload follow-up* the topology anchor left
open: `MachineDeployment` workers carry CAPI-minted **random** names, whose
`Machine`↔instance linkage lives only in the management etcd — a cold-start
loses the linkage and the fresh CAPI cannot recognise the survivors (different
names) → it leaks orphans and re-provisions. Deterministic pet names make every
node re-matchable by `providerID` after any cold-start. So
`ClusterIntention.spec` carries the **blueprint node list**, not a
cattle pool + replica count.

== Reconcile — adopt-first, guarded by cluster-level existence

[[existence]]
=== Existence is a cluster-level fact — the anti-greenfield guard

Before any pet is ever provisioned greenfield, the controller asks ONE cluster-level
question: **does the cluster EXIST?** — `∃ at least one node, of ANY pool, present by
its providerID` (`lxc:///<cluster>-<node>`). The `providerID` is the SSOT for BOTH
existence and matching. `ClusterAdoption` carries existence as the OR of every
`PoolAdoption`'s pet presence — it spans all pools, not one.

* **Exists (≥1 node, any pool)** → adopt-first everywhere; an absent pet PROVISIONS as
  a JOIN (the control plane is up or coming — never a fresh etcd). NEVER greenfield a
  rival.
* **Zero nodes anywhere** → a true day-0: greenfield — the first `control-node` pet
  does `cluster-init`, the rest join.
* **Broken (e.g. a worker present but 0 control-node)** → `DEGRADED` — never greenfield
  a rival control plane beside an orphan.

Greenfield is therefore **operator-armed, never controller-decided**: the controller
never abandons a surviving cluster. `DEGRADED` is a HOLD (surface + retry adopt), not
auto-repair-by-reprovision. The ONLY way to arm a fresh day-0 is the OPERATOR
DROPPING the Incus node(s) on an unrecoverable incident → existence falls to 0 → the
controller `cluster-init`s. Human-in-the-loop; recovery-by-recreate is deliberate.

=== The funnel — per pool, aggregated at the cluster

[source,text]
----
reconcile:                                    # INVARIANT: adopt-first
  exists = ∃ pet (ANY pool) present by providerID           # cluster-level guard
  for each pool (PoolIntention → PoolAdoption):
    for each pet in the pool roster:
      present            → ADOPT      (describe it; providerID pre-set, bootstrap skipped)
      absent  & exists   → PROVISION  as JOIN       (CAPN launches; CP up/coming)
      absent  & !exists  → PROVISION  as GREENFIELD (control-node first → cluster-init)
  reachable = Cluster.RemoteConnectionProbe                 # cluster-level (the CAPI Cluster)
  ClusterAdoption = aggregate(exists, ALL pools adopted, reachable)
----

The funnel lives at the **pool** grain (`PoolIntention` → `PoolAdoption` runs it over
its pets); the **cluster** aggregates (`ClusterAdoption` Adopted ⟺ reachable AND every
`PoolAdoption` Adopted — the "waiting for FloxEnvs Ready" shape). Worker pools GATE on
cluster reachability (a worker joins only once the control plane answers). A provision
**always begins by attempting an adoption**; there is no up-front "mode" — the
adopt-first invariant + the existence guard collapse day-0 / cold-start / recovery into
ONE idempotent path.

=== State machine — `ClusterIntention.status.phase`

Level-triggered, never "kill/restart" — it manages a *state*. The management
cold-start wipes the etcd → the `ClusterAdoption` (which lived there)
disappears; what survives is the `ClusterIntention` (Flux re-renders it from
git) + the running workload. So the controller **re-derives reality every
reconcile**; the `ClusterAdoption` is the *result* of a successful adopt
(re-created), not a persistent flag.

[mermaid,cluster-seeding-state-machine,svg]
----
flowchart TD
  start(["reconcile"]) --> adopting
  adopting{{"ADOPTING<br/>adopt-first, ALWAYS<br/>reads providerID + RemoteConnectionProbe (watch, no probe)"}}:::hot
  adopting -->|"nodes present + CP healthy"| adopted["ADOPTED<br/>create/refresh ClusterAdoption + CAPI mirror"]:::ok
  adopting -->|"nodes ABSENT"| provisioning["PROVISIONING<br/>CAPN launches the missing nodes"]:::work
  adopting -->|"present + CP SICK"| degraded["DEGRADED<br/>NEVER re-provision (= data loss)<br/>surface + retry"]:::bad
  provisioning -->|"nodes up — reloop"| adopting
  adopted -->|"re-reconcile / cold-start (mgmt etcd wiped)"| adopting
  degraded -->|"retry (backoff)"| adopting

  classDef hot fill:#ffe6cc,stroke:#d79b00
  classDef ok fill:#d5e8d4,stroke:#82b366
  classDef work fill:#dae8fc,stroke:#6c8ebf
  classDef bad fill:#f8cecc,stroke:#b85450
----

Every state **passes back through `Adopting`** — the adopt-first invariant made
concrete. `Provisioning` is reached ONLY via "nodes absent", never from
`Degraded` (present-sick). Destroying a present node = data loss, so
`present-sick` never provisions.

The SAME funnel runs at TWO grains (the 2×2 resource model): each `PoolIntention` →
`PoolAdoption` runs it over its pets; `ClusterAdoption` AGGREGATES — the cluster is
`Adopted` only when it is reachable AND every pool is `Adopted` (the "waiting for
FloxEnvs Ready" shape). Existence (the anti-greenfield guard) and reachability live on
`ClusterAdoption` (cluster-level); pet presence lives on `PoolAdoption` (per pool).

=== Watch model — thin controller, derived from CAPI/CAPN

The controller `Owns` the CAPI CRs it creates (`Cluster`, `RKE2ControlPlane`,
`LXCCluster`, `Machine`, `LXCMachine`) → their events requeue its reconcile → it
**derives** `phase` from the conditions CAPI/CAPN *already maintain* — it does
NOT run its own probe:

[cols="1,2",options="header"]
|===
| question | signal it reads (never re-measures)

| CP healthy? | `Cluster.RemoteConnectionProbe` / `ControlPlaneInitialized` —
CAPI probes the workload apiserver for us.
| node present? | `LXCMachine`/`Machine` status — CAPN reflects the Incus
instance.
|===

This is the "thin controller / rich intention" principle: `seed-master` (SSOT
`ClusterNetworkBlueprint`) fills the `ClusterIntention` with concrete values;
the controller only *materialises* (templates) the CR-set and owns it — **zero
addressing logic in Go** (that would duplicate the Java blueprint → drift).

== Config ownership — the blueprint SSOT, pools, and the node

The thin-controller principle generalises to ALL of a cluster's config, not just
the CR-set addressing: there is ONE source of truth — the `ClusterNetworkBlueprint`
(the netplan domain) — and everything else is a *projection* of it, never a
re-computation.

=== The blueprint is the SSOT; three projections

`ClusterNetworkBlueprint` derives every addressing fact of a cluster from its
`clusterName`, deterministically (CIDRs, the kube-vip VIP, each node's address, the
vmnet bridge, the gateway). That one SSOT projects into three places — the same
values, never recomputed:

[mermaid,cluster-seeding-config-projections,svg]
----
graph TB
  bp["ClusterNetworkBlueprint<br/>SSOT · f(clusterName)"]:::src
  bp -->|"GrowNetworkResolver"| dhcp[("vmnet DHCP reservations<br/>→ the node gets ITS ip at boot")]:::proj
  bp -->|"ClusterApiWorkloadManifestsUnit"| cp["ClusterIntention (CAPI intent)<br/>VIP · CIDRs · roster {name,pool}"]:::proj
  bp -->|"RuntimeRke2ConfigManifestsUnit"| br["manifests/&lt;cluster&gt; branch<br/>cluster-common + per-pool profiles"]:::proj
  classDef src fill:#e1d5e7,stroke:#9673a6
  classDef proj fill:#dae8fc,stroke:#6c8ebf
----

`ClusterIntention` is thus the blueprint's *CAPI-intent projection*: the network
facts (VIP, CIDRs, the pet roster) plus the non-network facts a cluster needs
(image fingerprint, RKE2 / kube-vip versions, the per-remote CAPN identity, the
remote endpoint). The controller templates it; it computes nothing.

=== Pools, pets, profiles — the config vocabulary

[cols="1,2,2",options="header"]
|===
| term | values | what it is

| *cluster* | `bioskop-wrkld` | the unit; its branch is `manifests/<cluster>`
| *cluster-role* | `mgmt` / `wrkld` (`ClusterRole`) | which manifest domains the cluster renders
| *pool* | `control-node`, `gpu-node`, `storage-node`, … | a GROUP of pets sharing ONE profile + ONE template
| *pet* | `<cluster>-master`, `-peer1`, `-gpu1` | a named member of a pool
|===

A *profile* (the RKE2 config content) and a *template* (the CAPI stamp:
`RKE2ControlPlane` / a worker `RKE2ConfigTemplate` + `LXCMachineTemplate`) are both
*per pool* — and BOTH are management concerns, so both live on the **managing mgmt
cluster's branch** (`manifests/<mgmt>`), never the workload's own. The **template is an
INTENTION** (it DEFINES + launches the node in CAPI/CAPN) → the pool's `PoolIntention`;
the **profile is config CONTENT** the node installs at boot. A workload does not know how
it was configured — its own branch carries only what RUNS in it (the app stack). Each
`PoolIntention` carries ONE pool's template + its named pet roster `{name}`. CAPI
treatment DERIVES from the pool: pool `control-node` ⇒ control-plane (`RKE2ControlPlane`,
an etcd member — NOT a `MachineDeployment`); any other pool ⇒ worker. A pet name
(`master`) is a NAME, never a pool.

=== Config is a management concern — VISIBLE in the mgmt cluster

The config is a MANAGEMENT concern, so it lives where management lives — and since the mgmt IS
a running cluster, it lives there as **visible k8s resources**, not hidden git-only artifacts.
The **mgmt render** synthesises, per `(cluster × pool)`, each managed cluster's RKE2 config as
`ConfigMap`/`Secret`s — for the mgmt itself AND every cluster it holds an intention for —
rendered on `manifests/<mgmt>` and **applied by Flux** into the mgmt cluster (no `LOCAL_CONFIG`).
So `kubectl get configmap,secret` on the mgmt is the single pane over every managed cluster's
config: nothing hidden.

[source]
----
manifests/<mgmt>/   →  rendered on the branch AND Flux-applied into the mgmt cluster
  …/rke2-config/<mgmt>/control-node/…        # the mgmt's own config
  …/rke2-config/<host>-wrkld/control-node/…  # a managed workload's config (per pool)
  …/rke2-config/<host>-wrkld/gpu-node/…      # (future pool)
  ClusterIntention + PoolIntention*          # the intentions
  … the mgmt's own app stack …
----

The workload's OWN branch `manifests/<host>-wrkld` carries ONLY its app stack (its own Flux,
its own `contents:read` token). Its config lives in the MGMT, visible.

=== Delivery follows the management relationship — the pre-join wall

A k8s `ConfigMap` in the mgmt is NOT readable by a node at boot: a workload node is in a
DIFFERENT cluster, and even a mgmt node is still JOINING (no k8s API yet). So the config is
DELIVERED, per the relationship:

[cols="1,1,2",options="header"]
|===
| node | relationship | delivery

| **mgmt / root** | self-managed | **git-fetch** — `install-rke2-config` from its OWN branch (the pre-join wall forces git; `seed-master` poses the read token). The root is the fixpoint.
| **workload** | managed (CAPRKE2) | **bootstrap-inject** — `seed-incluster` (in the mgmt) READS the visible k8s config + stuffs it into the CAPRKE2 `RKE2Config` (cloud-init). No git-fetch, NO read token on the workload node.
|===

So `install-rke2-config` is the **self path**; a managed workload gets the config the mgmt
already holds (visible) via the **bootstrap-inject path** — no branch fetch of its own.

=== cluster-common vs per-pool vs per-node

For each managed cluster, its config splits three ways:

* *cluster-common* (every node of that cluster): CIDRs, the VIP (`advertise-address`),
  `disable`, `tls-san` as an ALL-NODES superset (VIP + every pet's `.local` FQDN +
  gateway/lan/localhost). The RKE2 join token is CAPRKE2's own (it bootstraps the
  cluster), not a delivered fragment.
* *per-pool profile*: that pool's RKE2 config (control-node: etcd/server; a worker pool:
  its `agentConfig`, labels, taints).
* *per-node*: NOT rendered — LOCAL facts each node resolves from its own identity by an
  on-node oneshot (the pattern `node-labels` + `provider-id` already use; `node-ip` joins
  them): `node-ip` from its vmnet interface (DHCP-reserved from the blueprint),
  `node-name` from its hostname (= the pet name CAPN stamped), `provider-id` =
  `lxc:///<hostname>`. So no branch carries N nodes' per-node config, and the old render
  `node=<name>` param DISSOLVES.

=== Two layers — L1 boot vs L2 app

[cols="1,1,2",options="header"]
|===
| layer | when | source

| L1 — RKE2 *boot* config | at `rke2` start, PRE-Flux | the MANAGER — git-fetch (self) / bootstrap-inject (managed workload)
| L2 — the app stack | after the cluster is up | the cluster's OWN Flux, pulling `manifests/<cluster>` with its own self-minted `contents:read` token (`GithubAppSecretManifestsUnit`)
|===

L1 is pre-Flux by necessity (Flux runs as pods *inside* the rke2 it configures) — it can never
come from the workload's own Flux; the manager delivers it, above.

=== The read token — self-path only

Only the **git-fetch** (self) path needs a `contents:read` token in cloud-init: the root/mgmt
node fetches its OWN branch, and `seed-master` poses the token via the cellar→devlxd seam
(`fileNodeGithubToken`, which fires ONLY for the STANDALONE root — a workload render skips it).
A **managed workload** node needs NO read token — it never git-fetches; `seed-incluster` reads
the config in-cluster and injects it into the bootstrap. Any token is ephemeral, least-privilege,
minted at use, never baked.

=== Cleanup — Flux-prune + ownerRef cascade, uniform

Because the config is Flux-applied (not git-only `LOCAL_CONFIG`), removing a pool/cluster from
the source makes the mgmt render drop it → **Flux prunes** its config `ConfigMap`/`Secret`s AND
its `PoolIntention`/`ClusterIntention` CRs; the CAPI CR-set (`Cluster` / `RKE2ControlPlane` /
`Machine`) is **ownerRef-GC'd** under the pruned intention. One uniform, Flux-driven lifecycle —
no render-only special case. (Dropping the Incus node is the separate, operator-armed act that
arms a greenfield — see <<existence>>.)

=== The boot config needs NO day-0 render of the workload's own branch

Because a node's L1 config lives on the **managing mgmt branch** (`manifests/<mgmt>`,
synthesised by the mgmt render — which already runs), `ClusterIntention(bioskop-wrkld)`
can provision straight away: it only needs the mgmt branch to carry the workload's config,
which it does once `bioskop-wrkld` is one of the mgmt render's cluster intentions. **The
day-0 chicken-and-egg for CONFIG dissolves** — nothing waits on `manifests/bioskop-wrkld`.

The workload's OWN branch carries only its **app stack** (L2), needed AFTER the cluster is
up (its own Flux) — NOT a boot dependency. Its first render is still bootstrapped from the
parent (the workload cannot render its own branch before it exists): a one-off Tekton
`PipelineRun` (`render-manifests cluster=bioskop-wrkld`) in the mgmt plane, whose `prepare`
seeds the branch null-base. Steady-state, the workload's OWN PaC `Repository` re-renders it
on a source push (`.tekton/render.yaml` lives on the SOURCE branch — push-triggered +
source-scoped, cutting the render→render loop; the `Repository` CR binds the repo and
selects the rendered branch via `spec.params.cluster`). Day-0 app-branch = parent-driven
`PipelineRun`; steady-state = self-driven PaC. See
link:manifests-rendered-branches.adoc[Manifests Rendered Branches].

== Where seed-incluster runs — the single-adopter topology invariant

[IMPORTANT]
====
**A cluster is adopted by EXACTLY ONE management plane.** Two `seed-incluster`
instances adopting the same cluster ⇒ two owners of the same
`ClusterAdoption` + CAPI CR-set ⇒ SSA flap. This is *one object = one owner*
raised to the **cluster** grain. Corollary: seed-incluster runs *where the
management plane lives*, not "in every cluster so it manages itself".
====

* **seed-incluster runs in every management plane** — today (single host in
  play) that is **the management cluster alone**; under the cross-host
  federation (<<cross-host,tier B below>>) each mgmt tier runs one (`bioskop-mgmt`
  + `nikopol-mgmt`). A plane's etcd carries the CRs (`ClusterIntention` /
  `ClusterAdoption`) for itself *and* its children (rendered on
  `manifests/<host>-mgmt`; the plane's Flux applies them).
* **The workload is a MANAGED cluster, not a plane.** It is adopted *from* its
  parent mgmt; it does **not** run seed-incluster (that would be a second adopter
  of the same cluster).
* **Only the ROOT self-adopts — because it is the ONLY out-of-band boot.** The
  root (`bioskop-mgmt`) is the single cluster `seed-master` seeds STANDALONE;
  nothing above it can adopt it, so it self-adopts in-cluster. Every non-root
  cluster (workload OR sub-plane) is **born in-cluster** by its parent's
  seed-incluster and adopted by that parent → never self-adopts. See
  <<cross-host>> for the federated recursion.
* **"Can a cluster already managed by CAPI/CAPN be adopted in-cluster?" → No.**
  It already has its single adopter (the parent plane); adoption happens **once,
  from the management plane**. Re-adopting from inside = double-owner.

[[cross-host]]
=== Cross-host — the two-tier direction (preferred over direct remote-Incus)

Reaching a second bare-metal (`nikopol-nixos`, over the tailnet) is the next
step. Two candidate topologies:

[cols="1,3",options="header"]
|===
| topology | shape

| **B — two-tier management (PREFERRED)** | `bioskop-mgmt` manages
`nikopol-mgmt`; `nikopol-mgmt` manages `nikopol-wrkld` **locally** (local Incus,
same host). Only the rare *mgmt-of-mgmt* hop crosses the tailnet; the frequent
workload machine-lifecycle stays host-local. Matches the anchor's operating-model
preference — a host-local management "removes the cross-host and tailnet
dependencies entirely (a fresh local management + git is all it needs)". Each
host is autonomous.
| A — single plane, remote Incus | `bioskop-mgmt` drives CAPN across TWO Incus
remotes (`bioskop-nixos` local + `nikopol-nixos` over the tailnet) and manages
`nikopol-wrkld` directly. Fewer clusters, but it couples the frequent workload
machine-lifecycle to the fragile cross-host reach (CGNAT, roaming host).
|===

.One CAPN, many Incus remotes — the remote is a CLUSTER-level target
[NOTE]
====
A single CAPN in a management plane drives **multiple Incus remotes** — this is
CAPN's native model (verified against `cluster-api-provider-incus` in the anchor):
each `LXCCluster.spec.secretRef` names ONE remote's identity Secret (`server` /
`server-crt` + client cert/key), and all that cluster's `LXCMachine`s provision
into it. So `IncusIdentitySecretManifestsUnit` becomes **per-remote** (it renders
one `<cluster>-incus-identity` today).

The remote is therefore a **cluster-level** target, NOT per-node:
`ClusterIntention.spec.remote` names it (endpoint + per-remote CAPN identity
Secret), and every node of the cluster lands on that one remote. A cluster never
spans two remotes — the anchor's shared-fabric model (BGP/clustermesh,
`features.networks=false`) requires a cluster's nodes to be L2/L3 peers on one
host's bridge. Cross-host is BETWEEN clusters (the mgmt-of-mgmt hop), never within
one. Under tier B, each plane targets at most ONE non-local remote at a time:
`bioskop-mgmt` uses `nikopol-nixos`'s remote only to birth `nikopol-mgmt-master`;
`nikopol-wrkld` is local to its own plane.
====

[IMPORTANT]
.Real federation — a sub-plane is BORN in-cluster, not standalone-seeded
====
The federation crux: **`nikopol-mgmt` is NOT bootstrapped by `seed-master`
(the STANDALONE, out-of-band boot). It is PROVISIONED in-cluster by
`bioskop-mgmt`'s seed-incluster** — the same provision-then-adopt funnel, its
single mgmt node born via CAPN on `nikopol-nixos`'s remote Incus, then adopted.
Once up, `nikopol-mgmt` provisions `nikopol-wrkld` **locally**.

This resolves the anchor's chicken-and-egg per tier. "CAPI cannot create the
cluster that runs CAPI" bites the **root only** — where the creator would be the
created. A non-root plane has a CAPI *above* it (its parent), so the creator
(`bioskop-mgmt`'s CAPI) differs from the created (`nikopol-mgmt`'s CAPI); no
paradox. Hence the exact mapping onto the <<naming,enclosure axis>>:

* **`STANDALONE` = the ROOT, and it alone** — `seed-master` seeds `bioskop-mgmt`
  out-of-band. The one irreducible nix floor; it births exactly ONE cluster, ever.
* **`IN_CLUSTER` = everything else, recursively** — `seed-incluster` births +
  adopts every descendant: workloads (leaves) AND sub-management-planes. The
  fleet is CAPI-native turtles-all-the-way-down on a single nix floor.

Single-adopter composes cleanly across the tiers:

* `bioskop-mgmt` = **root** — self-adopts (nothing above it; the sole STANDALONE
  boot). Its seed-incluster births+adopts: itself, `bioskop-wrkld`, `nikopol-mgmt`.
* `nikopol-mgmt` = **mid tier** — PROVISIONED + adopted in-cluster by
  `bioskop-mgmt` (does NOT self-adopt), YET RUNS its own seed-incluster to
  birth+manage its child `nikopol-wrkld`. "Being a plane" (manages children) and
  "who births/adopts me" (the parent) are orthogonal roles.
* `nikopol-wrkld` = **leaf** — provisioned+adopted by `nikopol-mgmt`, runs no
  seed-incluster.

So each cluster has EXACTLY ONE adopter (its parent plane; the root adopts
itself). The cross-host Incus remote shrinks to birthing ONE node
(`nikopol-mgmt-master`), never the whole workload fleet. B is clean because it is
the same adopt-first controller *composed*, not a new mechanism — real federation.
====

[[federation-now]]
== Federation is first-class — design for it now, not later

The model is **inherently recursive**: a management plane births + adopts its
children with the same adopt-first controller, and a child that is *itself a
management plane* then does the same for ITS children. Retrofitting the tier /
cluster-kind / remote dimensions later would reshape both `ClusterIntention` and
the render — so they are baked in from the start. Federation is not a distant
mode; it is the single mechanism *composed*.

.The self-similar reconcile
[TIP]
====
There is ONE controller and ONE reconcile (adopt-first), run in every plane. A
plane does not know or care whether a child is a leaf workload or a sub-plane at
the level of *provisioning* it — it births the child's nodes and adopts them
identically. The only difference is the child's **render flavor** (what manifests
land inside it), carried by the cluster KIND in the spec. So "federation" adds no
new control path — it is the leaf case applied to a child that happens to run its
own seed-incluster.
====

Four concrete requirements this places on the design NOW:

. *Cluster KIND in `ClusterIntention.spec`* — `workload` (leaf) vs `management`
  (sub-plane). It selects the **render flavor** of the child: a `management`
  child gets the CAPI operator + `seed-incluster` + its OWN `ClusterIntention`s
  for its children rendered into it; a `workload` child gets only the app stack.
  This is the per-cluster/role synthesis the anchor already foresaw
  (`manifests.publish.{domain}` becoming per-cluster).
. *CR placement follows the tier boundary* — a plane owns the `ClusterIntention`s
  of ITS children, in its own rendered branch (`manifests/<host>-mgmt`).
  `bioskop-mgmt`'s branch carries provisions for `{bioskop-wrkld, nikopol-mgmt}`
  (+ its self-`ClusterAdoption`); `nikopol-mgmt`'s branch carries the provision
  for `{nikopol-wrkld}`. The tier boundary = the branch/etcd boundary.
. *Level-triggered tier ordering* — `nikopol-wrkld`'s `ClusterIntention` lives in
  `nikopol-mgmt`'s etcd, which does not exist until `bioskop-mgmt` has
  provisioned+adopted `nikopol-mgmt`. No explicit orchestration: each plane's
  adopt-first reconcile converges once its own control plane is up. The tiers
  bootstrap outside-in, purely by level-triggered convergence.
. *The remote is cluster-level* (see the NOTE above) — `spec.remote` targets one
  Incus engine; the cross-host reach is used only to birth a sub-plane's single
  node, not a whole fleet.

.The addressing foundation already exists — one SSOT, two provisioning layers
[NOTE]
====
Federation does not need new addressing: the `ClusterNetworkBlueprint` **already
defines both hosts** — `hostOf(clusterName)` derives the host from the cluster
name, and `hostId()` enumerates them (`bioskop` = 0, `nikopol` = 1; TEST = 2),
with every span a pure `f(clusterId = (hostId << 1) | roleId)`. So `bioskop-mgmt`
can already carry BOTH host identities.

That one SSOT feeds **two** provisioning layers, and the split is the point:

* **ndh provisions the HYPERVISOR** — the NixOS host `nikopol-nixos` + its Incus
  engine + fabric. ndh consumes the netplan/dataplan (the anchor's per-host disko
  → `catalog.datasets`), so it stands up the remote engine with the right network
  identity.
* **seed-incluster provisions the CLUSTER NODE** — `nikopol-mgmt-master` *on* that
  remote engine, from the same blueprint.

So the remaining work is not to DEFINE the cross-host identities (they exist) but
to PROJECT them: derive `ClusterIntention.spec.remote` + the per-remote CAPN
identity Secret from the blueprint's host dimension — the "rich intention / thin
controller" principle applied to the remote.
====

.The cross-host trust is a WIRING gap, not a missing channel — the secure channel already exists
[NOTE]
====
rke2lab and ndh **already share the sops age key** (encrypt/decrypt) **and the git
smudge/clean filters** (ndh's `git-sops-filter` SSOT). They are therefore in ONE
sops trust domain: anything one encrypts to the shared age key, the other
decrypts. So the cross-host trust does NOT need a new secure channel — that framing
was overstated. Two consequences:

* *The transport exists.* The material rides the already-shared sops-encrypted git
  + the existing rke2lab → ndh flow (the dataplan seed-master owns, pulled into
  ndh's `catalog.datasets`). The remaining work is **placement + wiring**, not
  building a channel.
* *Most of the material is PUBLIC.* Incus trust is by **cert fingerprint**: ndh
  needs only the CAPN client cert's PUBLIC part to add to `nikopol-nixos`'s trust
  store; the returned `server-crt` is public too. The PRIVATE keys stay put (the
  CAPN client key in the cluster-side identity Secret; the server key on the
  hypervisor). So the shared age key only ever guards the little that is truly
  secret — the bulk of the handshake is public certs.

The LOCAL case (`bioskop`, its own Incus) is already covered
(`IncusIdentitySecretManifestsUnit` + a locally-trusted engine).
====

.We OWN the Incus PKI — cross-host trust is a build-time derivation, not a runtime exchange
[IMPORTANT]
====
The Incus server certs are OURS: we mint them (from the ndh `mammoth-skate-tls`
root — the same PKI behind "deterministic cluster access" and the BYO-CA cellar
material), and so is the CAPN client cert. When you own the authority, mutual TLS
trust is **CA-based**, not a per-cert exchange:

* ndh configures each Incus engine to **trust our CA** when it provisions the
  hypervisor (the engine's own `server-crt` is minted from the same root).
* Any client cert minted from that root is then accepted by **every** engine
  automatically — by CA membership. No `incus trust add` per remote, no per-cert
  handshake.

So `bioskop` / `nikopol` (and their CAPN) are authorized to reach **all Incus
remotes in their network** at generation time — which is exactly what the anchor
means by "the CAPN identity can be shared, trusted by both hypervisors": the share
works BECAUSE both trust our CA.

The residue is therefore purely **build-time**: derive the server certs + the
client cert from our root, coherent with the blueprint's host identities, and seed
the CA trust into each engine at provision (ndh). Nothing is exchanged at runtime;
the shared age key only ever carries the PRIVATE keys — which do not move anyway.
See <<open-items>>.
====

== Ownership & operator view

Two **ownerRef cascades**, one per grain — the mirror owns the CAPI objects it
builds. The intents (`ClusterIntention` + the N `PoolIntention`) are git/Flux and
survive a cold-start → they re-seed both chains; the mirrors + CAPI CR-set are
re-derived. Cleanup is uniform: **Flux-prunes the intents** (removing them from the
branch) ⇒ the ownerRef cascades GC the mirrors and the whole CAPI CR-set. The
`ClusterIntention` does NOT own the `PoolIntention` (both ride the branch, both
Flux-pruned); the cluster↔pool link is the aggregate (below) + the deterministic
`Cluster.controlPlaneRef` name, not an ownerRef.

== Root-resource asymmetry (self vs managed — same CR shape)

Both clusters render the **same intent** (`ClusterIntention` + a control-node
`PoolIntention`) — the render is uniform (mgmt and workload delegate to the same
`ClusterApiCrRenderer`); they differ only by `kind`, pet count, and a local vs
remote endpoint. The residual asymmetry is *self vs managed*, not the CR shape:

* **mgmt (self)** — seed-master bootstraps the mgmt intent out-of-band, and
  seed-incluster runs *inside* the cluster it describes, so its control plane is
  necessarily up when the controller reconciles → it always ADOPTS, never
  greenfields (existence holds by construction). Its `ClusterAdoption` carries the
  self-guard finalizer (deleting it would suicide the plane).
* **workload (managed)** — the mgmt renders + Flux-applies the workload's intent;
  seed-incluster can greenfield it (existence = 0) or re-adopt the survivor.

At a mgmt cold-start every cluster converges back to `Adopted` — the mgmt
self-adopts, the survived workload is re-adopted — nothing is re-provisioned.

== Anti-patterns

[cols="1,1",options="header"]
|===
| ❌ Don't | ✅ Do instead

| Run seed-incluster inside the workload so it "manages itself".
| Run it only in the management plane; the workload is adopted *from* the mgmt
(single-adopter invariant). A second adopter = double-owner flap.
| Re-provision a node that is present but its CP is sick.
| `Degraded` — surface + retry adopt. Re-provision ONLY when the node is truly
absent (`providerID` not found). Destroying a present node loses its etcd.
| Model workers as a `MachineDeployment` cattle pool (random names + replicas).
| All nodes are named pets from the blueprint, adopted by `providerID` — the
only shape that survives a cold-start (random names leak, see <<all-pets>>).
| Compute addressing (CIDRs, VIP, providerID) in the Go controller.
| `seed-master` fills the `ClusterIntention` from the `ClusterNetworkBlueprint`
SSOT; the controller only templates + owns. Go-side addressing duplicates the
blueprint → drift.
| Run a home-grown health probe in the controller.
| Derive `phase` from `Cluster.RemoteConnectionProbe` /
`LXCMachine` status via `Owns`/watch — CAPI/CAPN already maintain them.
| Extend `ClusterAdoption` with "how to create a cluster".
| Two resources, two roles: `ClusterIntention` (create) + `ClusterAdoption`
(describe). Merging mixes roles.

| Bake per-node config (`node-ip`/`node-name`) onto the per-cluster branch (a render
`node=<name>` param).
| Per-node values are LOCAL facts — resolved on-node by oneshots (`node-labels` +
`provider-id` already are; `node-ip` joins them). The per-cluster branch carries
per-POOL profiles + cluster-common; it cannot hold N nodes' per-node config.
|===

[[naming]]
== Naming & rename mechanics (tracked, not yet done)

[cols="1,1,2",options="header"]
|===
| from | to | why

| `ExecutionEnclosure.OPERATOR` | `STANDALONE` | The enum's own doc says
"a *standalone* process". `OPERATOR` mixed the *who* with the *nature*;
`STANDALONE` names the nature (a process outside a cluster: `.secrets` + ndh
files) opposite `IN_CLUSTER`. `HOST` rejected (collides with the Incus/nixos
host everywhere: `/srv/host`, `HostPathCatalog`, the `host/` module).
| `rke2-adoption-controller` | `seed-incluster` | It no longer only "adopts" —
it provisions + adopts + re-adopts. Named by *locality* (the axis that
distinguishes it from `seed-master`); `seed-cluster` rejected (collides with
`ClusterSeedScenario`).
| group `adoption.seedmatic.io` | `cluster.seedmatic.io` | Named by the *domain*
(cluster lifecycle: `ClusterIntention` + `ClusterAdoption` + future cluster
CRs), not the producer → decoupled from the controller name (a CRD group is
near-immutable), no `seed…seedmatic` stutter, and a direct parallel of CAPI's
own `cluster.x-k8s.io` (fitting our mirror role).
|===

`seed-master` is **kept** — the flagship module, huge blast radius; "master"
carries its primacy as the primary out-of-band seeder.

== Open items

. **CRD shapes (federation-native, DECOMPOSED — see <<resource-model>>)** —
  `ClusterIntention.spec` is **cluster-level only**: `{ kind, remote (target Incus
  endpoint + per-remote CAPN identity Secret; local or over the tailnet), Incus
  project, image, versions, VIP, CIDRs }` — NO node list. `PoolIntention.spec` is
  **per pool** (ownerRef → its `ClusterIntention`): `{ pool (control-node /
  gpu-node / …), the pool's template, the named pet roster {name} }`. The *pool*
  selects the template + (on the workload branch) the profile; CAPI treatment
  derives from it (`control-node` ⇒ control-plane, others ⇒ worker). The
  cluster-level **KIND** (`workload` leaf vs `management` sub-plane) selects the
  child's render flavor — so the parent knows to expect a seed-incluster inside it
  — see <<federation-now>>. Mirror side symmetric: `ClusterAdoption` +
  `PoolAdoption`. (Immediate scope: `bioskop-wrkld`, one `PoolIntention(control-node)`,
  three pets.)
. **Cross-host Incus trust (federation)** — a build-time PKI derivation, NOT a
  runtime exchange: we own the Incus PKI (`mammoth-skate-tls` root), so mint the
  server certs + the CAPN client cert from it and seed CA-trust into each engine
  at provision (ndh). CA membership authorizes bioskop/nikopol to reach every
  remote in-network — no per-cert `trust add`. Residue: derive the certs coherent
  with the blueprint host identities + author the per-remote identity Secret.
. **Rename mechanics** — order + CRD-group migration for the three renames
  above.
