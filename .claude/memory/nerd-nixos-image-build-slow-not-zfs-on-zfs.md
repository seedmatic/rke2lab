Chantier (2026-09-17) : le build de l'image disque nerd-nixos **sur bioskop-nixos** (VM Tart vz) est lent ; il passait « beaucoup plus vite » sur le linux-builder vz. Investigation live (je drive par `ssh root@bioskop-nixos.local`).

**→ MODE OPÉRATOIRE (relancer + mesurer un build) : `.claude/nested-image-build-force-rebuild-and-measure.md`** dans rke2lab (worktree feature/nixos-node-substrate). Contient : comment forcer un vrai rebuild (`--option substituters https://cache.nixos.org` — sinon nix SUBSTITUE l'image raw 14 GiB depuis nxmatic.cachix.org et aucun qemu ne démarre ; `--no-substitute` est trop agressif → deps échouent), la suppression des sorties (référent yaml d'abord, sinon "still alive"), le mirror `xchg/install.log` (la console guest ne remonte PAS au log nix), et **le baseline chiffré à battre : 3645 s (~61 min)** à 4 vCPU.

**Faits établis (mesurés, pas supposés) :**
- **KVM ACTIF** dans le QEMU nested : `/proc/$(pgrep -n qemu-system)/fd` montre `/dev/kvm` (fd 17) + `kvm-vm` + 4 `kvm-vcpu` + vgic ARM. `accel=kvm:tcg` a bien pris kvm. dmesg : `kvm: nv:… nested… Hyp nVHE initialized`. **Donc PAS TCG, pas un souci d'accélération CPU.** `/dev/kvm` = `crw-rw-rw-` (0666, accessible nixbld). `sandbox = false` sur les nixos (modules/nixos/nix-settings.nix).
- **`/nix/var/nix/builds` = ZFS** (`tank/nerd/nix/builds`) → structurellement ZFS-sur-ZFS (les disques `boot.raw`/`tank*`/`recover` sont des fichiers raw sur le ZFS hôte, la VM crée un pool ZFS dedans).
- **A/B host (zpool sur ZFS vs sur tmpfs, même payload) : ZFS-sur-ZFS N'EST PAS le goulot.** Séquentiel : 1046 vs 1222 MB/s (**1.17×**). Sync-IOPS (8k O_DSYNC ×20000) : 4728 vs 4803 (**1.02×**). Débit hôte sain (>1 GB/s), 31 GiB RAM. **Hypothèse ZFS-sur-ZFS RÉFUTÉE.**

**RÉSOLU par mesure live (2026-09-17, build réel `nerd-nixos-bringup-zfs-systemd-disk` sur bioskop-nixos) — goulot = chemin de LECTURE du store via virtiofs, PAS le disque :**
- Store monté `type virtiofs` dans le guest (2 vhost-user-fs : `store` + `xchg`). virtiofsd lit le store à **~1-2 MB/s seulement** (`kB_rd/s` pidstat) = **latence/métadonnées, pas bande passante**.
- **CPU-bound en temps SYSTÈME** : guest `%system` 44-74 %, qemu hôte `%CPU` 136-358 % (`%guest` + `%system` hôte 41-77 %). **virtiofsd lui-même ~0 % CPU.**
- **Disque oisif** (re-confirme A/B) : hôte vdb/vdc `await` 0.1-0.6 ms `%util` <2 % ; guest bloc `await` 1.6-4 ms `%util` <5 % ; `iowait` ~1 %. Pool hôte écrit à 8 MB/s = bridé par l'amont virtiofs, pas par ZFS.
- virtiofsd invoqué **SANS `--cache`** (→ défaut `auto` = revalidation fréquente → round-trips) et **file-handles désactivés** sur **`EPERM`** (`Failed to open file handle for the root node: Operation not permitted`) = **capability manquante** (`CAP_DAC_READ_SEARCH`, virtiofsd en uid 1000 `--sandbox none`), PAS un `EOPNOTSUPP` ZFS. Cmdline : `virtiofsd --xattr --sandbox none --seccomp none --shared-dir /nix/store`.

**★ FIX VALIDÉ LIVE + POUSSÉ (2026-09-17) — `--cache=always` sur le virtiofsd du store :** wrapper virtiofsd dans `bringup-zfs-disk-image.nix` (`virtiofsdStoreCached` = writeShellScriptBin qui injecte `--cache=always` UNIQUEMENT sur la share `virtio-store.sock` — xchg garde `auto`), passé via `pkgs.vmTools.override { virtiofsd = …; }`. **A/B mesuré : débit write phase chaude 3→10 MB/s (~3.3×), guest %system 44-74%→17-19%.** MAIS la traîne (copie closure) retombe à ~2.7 MB/s (premiers accès = round-trips FUSE, non aidés par le cache) → build complet toujours ~50 min. Commit `67029777` (poussé). + mirror install.log → xchg, commit `4cdf9422` (poussé, voir bug empty-logs).

**✗ DAX virtio-fs : CUL-DE-SAC (QEMU).** Kernel guest ✅ `CONFIG_FUSE_DAX`, virtiofsd ✅, MAIS `vhost-user-fs-pci` de QEMU n'a **AUCUNE propriété `cache-size`/dax** — vérifié dans la source **10.2.4, 11.1.0 ET master** (`vuf_properties` = chardev/tag/num-request-queues/queue-size only). La fenêtre DAX virtio-fs n'a **jamais été mergée mainline** (fork Red Hat `virtio-fs-dev` seulement — c'est ce que les LLM hallucinent). Pas un pb de version. Tout le code DAX (wrapper cache-size, vmTools vendoré `-o dax`, app revendor) **reverté** → retour baseline cache=always.

**✗ Store read-only pré-bâti (squashfs, Forme D) — IMPLÉMENTÉ, TESTÉ, ABANDONNÉ + REVERTÉ (2026-09-17).** Idée : livrer la closure comme cache binaire nix (`mkBinaryCache`) dans un squashfs, attaché virtio-blk read-only, monté dans le guest, `ensure_toplevel_in_target_store` copie via `nix copy --from file:///mnt/srccache` (au lieu du store virtiofs). Additive (ne démonte pas le virtiofs). Codé : dériv° cache+squashfs, drive `if=virtio,readonly=on`, mount par probe squashfs sur `/dev/vd*`, `--from` conditionnel via `NDH_SRC_CACHE_URL`, + module kernel `squashfs`. **Résultat live :** round-trips virtiofs BIEN éliminés (virtiofsd read=0, guest idle 54%→~5%) — MAIS **la copie devient CPU-bound** (%system 86-92% : unpack NAR + hash sha256 + write ZFS checksum/compression) et le **temps total ≈ baseline** (~50min). Le squashfs rend les LECTURES gratuites, mais le **plancher CPU côté ÉCRITURE** (produire l'image) reste, même ordre de grandeur. En prime la **phase query-narinfo** (`nix copy` walk la closure) est lente aussi (latence par-op nested, transport-agnostique). **Le vrai mur = latence/CPU par-opération de la VM nested**, pas le transport → aucun read-side fix ne gagne. Gotchas notés : (a) `-device vhost-user-fs-pci` explicite CASSE le boot (utiliser `if=virtio`) ; (b) squashfs zstd = pénalité décompression → non compressé (`-noD -noF -noI -noX`) ; (c) **nested-KVM Apple thrashe >6 vCPUs** (8 → guest load 21, D-state, stall ; le commentaire `vmCpuCores ? 4` "max safe" avait raison ; nikopol=6 ok) ; (d) guest "unresponsive" = CPU-saturé (pas hung). **Tout revert vers baseline cache=always.** Ne PAS re-tenter le read-side. Piste éventuelle NON explorée = réduire le CPU côté write (compression ZFS off pendant l'install, ré-activée au 1er boot).

**★★ RÉSOLU + SHIPPÉ (2026-09-18, ndh `acc0a094` sur `develop`) — store de sortie en EROFS+overlay packé SUR L'HÔTE. Mesuré : VM imbriquée ~6 min (contre ~50).** Arithmétique décisive d'abord : closure = 9,3 GiB mais **260 121 fichiers** → ~11 ms/fichier ≈ 87 fichiers/s ; le travail « octets » (sha256 HW-accéléré, zstd, écriture brute) ne pèse que 1-3 min sur 50. Le build est borné par les **opérations**, pas les octets — ce qui explique enfin pourquoi Forme D échouait. Tous les leviers ZFS bon marché étaient déjà appliqués (`atime=off`, `xattr=sa`, `recordsize=16K`, `sync=disabled` pendant le bringup). **Argument qui rend l'EROFS non-contournable : `mkfs.erofs` ne requiert PAS root (donc dérivation nix pure, cacheable, dédupable fleet-wide), alors que `zpool create` le requiert — c'est la raison d'être de la VM imbriquée, qui reste mais n'écrit plus le store.** Implémentation : `modules/nixos/erofs-store-{image,layout,mount}.nix` (SSOT des labels/mountpoints), dataset `nerd/nix/store` REMPLACÉ par `nerd/nix/rwstore` (upper), image = **son propre disque** porté dans le bundle en **symlink** (zéro copie de 9 GiB) avec `role: prebuilt` au manifeste → côté darwin copie verbatim, PAS de resize à `vmDataDiskSizeGiB`, PAS de sonde de labels ZFS, attaché `:ro`. Recette = celle de `qemu-vm.nix` (`tar --files-from <closureInfo>/store-paths | mkfs.erofs --force-uid/gid=0 -T 0 -U <fixe> --tar=f`), **non compressée** (le CPU guest est la ressource rare, pas l'octet). **Vérifié** : déterminisme par `nix-store --realise --check` (le 1er test « mismatch » était faussé — tar/mkfs.erofs de versions différentes) ; image montée = 1656 store paths, 361 559 inodes ; **bootée en QEMU nu** (`snapshot=on` partout + store `readonly=on`, donc VM vivante intacte) → shell root, `/nix/store`=overlay, `/nix/.ro-store`=erofs sur vdf, **tank+recover ONLINE**, 144K dans l'upper. `/nix/store` monté 2× = normal (initrd + bind ro NixOS stage 2). **2 BUGS PRÉ-EXISTANTS corrigés au passage** (silencieux depuis toujours, tous les bundles avaient `images: []` et `zpools: []`) : (a) `cp` depuis le store donnait mode 0444 à `manifest.yaml` → chaque `yq -i` échouait en EACCES, **et yq sort 0 malgré l'échec d'écriture** donc `set -e` ne voyait rien → le darwin vivait sur sa liste codée en dur, qui n'a pas de disque store ; (b) garde zpools = `yq -e … /dev/null` (document vide) + test `!!seq` alors que la charge est un map. **★ CHEMIN DARWIN VALIDÉ LIVE (2026-09-18) via une VM Tart jetable.** Recette (rejouable) : édition TEMPORAIRE de `hosts/bioskop/darwin.nix` → `vmName = "nerd-nixos-erofs"` + `vmMacAddress` distinct (sinon **collision MAC** avec la vivante sur le bridge) + `vmCpuCount = 4` / `vmMemoryMiB = 8192` (sinon les deux VM prennent toute la machine : la vivante tient 10 cœurs et 48 GiB). Tout dérive de `vmName` (répertoire des disques, gcroot, wrapper) donc `~/.tart/vms/nerd-nixos/` n'est JAMAIS touché — **impératif : `nerd-nixos` EST bioskop-nixos, notre builder**. **Contexte historique — la piste telle qu'énoncée avant de la coder (2026-09-18) :** Toutes les tentatives read-side échouent parce que le coût dominant est la **production du store de sortie DANS la VM nested** (unpack NAR + sha256 + checksum/compression ZFS). Corollaire : le seul levier est de **sortir la production du store de la VM nested**. Si le store de l'image produite est un **EROFS read-only + overlay writable** (au lieu d'un store matérialisé sur dataset ZFS), l'EROFS se packe **sur l'hôte** (`tar | mkfs.erofs`, débit hôte >1 GB/s mesuré) et la VM nested n'a plus à écrire le store du tout. Précédent in-tree : `nixos/lib/erofs-store-image.nix` + le montage `/nix/store` de `qemu-vm.nix`/`vz-vm.nix` (lower `/nix/.ro-store` fsType=erofs + overlay upper) — **boot-prouvé, y compris sur le backend Apple Virtualization**, et déjà reproductible (`-T 0`, `--force-uid/gid=0`, UUID fixe). PRIX : le store ne vit plus sur ZFS (perte compression/snapshots ZFS *du store*), retouche de `zfs-disko-config.nix`, VM nested toujours requise pour bootloader/zpool ; upper à placer sur disque (pas tmpfs — `builderMemSizeMiB` 8-16 GiB). Convergence : c'est le même mécanisme que la vision « store compact pour node mobile » (voir `.claude/gachix-nix-store-vision.md` dans rke2lab). **NB : ne PAS confondre avec le read-side (Forme D) qui est réfuté — ici on change la SORTIE, pas l'entrée.**

**Levier restant :** **robustesse fd** — file-handles désactivés sur `EPERM` (virtiofsd uid 1000 `--sandbox none` → pas de `CAP_DAC_READ_SEARCH`) → un O_PATH fd par inode : **153k fd ouverts mesurés / plafond 524288** → closure plus grosse pourrait faire EMFILE → build qui cale. Fix = capability/root pour virtiofsd (dur dans vmTools). Non fait. NB : gap « rapide sur linux-builder » pas isolé quantitativement (mécanisme virtiofs-latency cohérent, écart FS/ARC exact non prouvé).

**★ À QUOI SERT LE DISQUE EROFS APRÈS LE SWITCH ? (mesuré sur bioskop-nixos, 2026-09-19).**
Question légitime : l'EROFS porte la closure *bringup* (2,6 GiB) ; après `nixos-rebuild switch`
la closure *runtime* part dans l'upper ZFS. Le lower devient-il un vestige ? **Non — il porte un
tiers du système qui tourne.** Closure de `/run/current-system` = 1658 chemins, dont **554 (33 %)
servis par le lower EROFS seul**, 1104 par l'upper seul, **0 dans les deux** et 0 dans aucun.
Conséquences : (1) détacher `vdf` casse le boot (554 chemins perdus) — c'est la couche de base ;
(2) **zéro duplication** → le switch n'a écrit que le delta (1104 chemins, 5,3 GiB dans l'upper au
lieu des 1658), donc le lower a épargné ~2,6 GiB d'écritures du type coûteux (par fichier) ;
(3) immuable, `ro=1` au niveau bloc, ni corruptible ni GC-able.
**Réserve : le ratio DÉCROÎT.** Chaque switch alimente l'upper et, nixpkgs avançant, de moins en
moins de chemins runtime recoupent la closure bringup gelée ; à terme le lower ne couvre plus que
l'invariant. Pour le remonter il faudrait que l'EROFS porte la closure RUNTIME, c'est-à-dire
renseigner `runtimeSystemPath` (laissé `null` à dessein) — mais y mettre la closure d'un hôte
précis tague l'image par hôte et casse la dédup fleet-wide. **Arbitrage assumé : image identique
pour toute la flotte CONTRE couverture maximale du lower.** À rouvrir explicitement si le coût des
switches devient gênant.
