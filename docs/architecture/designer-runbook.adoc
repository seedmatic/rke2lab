= The designer's runbook — a live render of the design state
:toc: left
:toclevels: 3

[NOTE]
====
*Status:* DESIGN (2026-06-21). A re-entrance materialization (hub `reentrance-northstar`): the runbook
is a LIVE render of the doctor DSL for the OPERATOR; the designer's runbook is the same service one
layer up — a live render of the design state for US. It answers "where are we / what is next" without
re-reading memory and grepping the code by hand each session. This doc states what it is, why it is
owed, and how it is built.
====

== The picture in one image — two poles, two links

The whole of our work resolves to one image. There are two poles:

* the *documentation materializes the design* — the atlas, the specs, the scenario maps: the
  what and the why;
* the *codebase materializes the system* — the reactor that compiles and runs: the how.

And there are two *runbooks*, the links between the poles — one in each direction, the same service
("render the live state, do not let it drift") on two different subjects:

* the *operator's runbook* links the codebase to its RUNTIME state — it renders the live state of
  the running system, replayed from Pulumi. Subject: the system as it runs.
* the *designer's runbook* (this document) links the codebase BACK to the design — it replays the
  design scenarios from the code and proves the documentation has not drifted. Subject: the system
  as it is designed.

bottom layer (system → runtime). One re-entrance discipline, seen once as two poles plus two links,
once as four layers.

== Why it is owed — the re-entrance debt

The operator runbook obeys a rule: render the state LIVE from the real substrate (Pulumi), never
hand-written, never stale. We impose that rule on the operator's view but exempt our OWN view: the
`integration-atlas.adoc` and the capability map are HAND-WRITTEN, free to drift. They did drift — the
unitrepo spec carried a stale "mechanism C" until it was caught by hand this session. That exemption is
a re-entrance debt: a system that rules its domain but does not submit itself to the same rule has a
blind spot on itself. The designer runbook pays the debt — the design view rendered by the same
live-from-real-state rule we give the operator.

design scenario. We already play these; the runbook is what renders them.

== How we use it — the compass, not just the mirror

The runbook is not only a mirror of state ("where are we"); it is a *compass* ("which path, for which
benefit, in how many steps"). This is the need it was built to answer. The mechanism is the GATE (see
the integration atlas ritual): a narrated scenario is moored to named boxes whose gates are shut, so a
shut gate is not a vague "not yet" — it is a *countable distance*. Scenario "resolve" is at 0 gates
(already blue, a benefit in hand); the handler-load scenario is at 2 named gates (a concrete
`UnitHandler` + load-from-store); a federation scenario is at 4-5 (amber). The runbook therefore answers
three questions from one document:

* *where are we* — the LIVE mode (the scenarios green against the reactor today);
* *where are we going* — the DRY-RUN mode (every scenario we have written, the full intent);
* *which path, at what cost* — the gap between them read as a graph of gates: each benefit is "N
  flips green→blue away", and a green box that opens several scenarios at once (a shared gate) is a
  point of LEVERAGE, visible because scenarios name their boxes.

The intended query, the one that answers the real need: *"I want THIS scenario realized — what does it
cost me, and in how many increments?"* The runbook reads the scenario's shut gates, names the boxes
behind them, and counts: the cost is the boxes to ship, the increments are the green→blue flips on the
path. This is exactly the answer one gets TODAY by asking the question in conversation (decomposing
scenario 3's gates by hand gives "R4 blue, two green boxes, two increments"). The runbook merely
*crystallizes* that gesture — makes permanent and self-derived what the dialogue already produces. That
is why the USE can be graved now while the evaluation machine is deliberately NOT built yet: the gesture
already exists between us; the runbook is its durable form.

This compass reading is also the *plan* layer of the answerability cascade (design → spec → plan →
codebase): descending to implementation IS choosing which gates to open first, and "the order in which
we open the gates" is what a plan is. Ranking benefits by distance-in-gates and surfacing shared-gate
leverage is a capability of the runbook v0 — the information is present today (each scenario names its
boxes and their colour), it is simply not yet ranked or rendered as a graph.

=== Two scenarios this runbook itself is gated behind

The runbook is subject to its own DSL: these two design scenarios describe the runbook's own
end-state, both narrated, both behind the same shared leverage gate (the orchestration-OSGi inversion
— see the integration atlas runtime view). Naming them here repays the completeness clause: the
"orchestration purity" increment is not a stray, it realizes these.

. *The designer runbook is a pure bundle* — `[narrated]` green +
.. GIVEN the scenario engine (JGiven) compile-scope on the host, so every scenario adheres to the host
.. WHEN the scenario engine is made pure (the scenario MODEL separated from the report ENGINE, which
   stays host)
.. THEN the designer runbook is a pure OSGi bundle — the instrument that measures the system's purity
   is itself pure (the re-entrance loop closes) — AND the report rendering stays host, the model
   describes, the host actualises, nothing forced.

. *The compass is resolved by Felix, not hand-counted* — `[narrated]` green +
.. GIVEN gates counted by hand when answering "how many increments to realize this scenario"
.. WHEN scenarios resolve as units (their gates expressed as resolution edges — see the unitrepo view)
.. THEN the compass's distance-in-gates is computed by the Felix resolver, not by us — AND this is the
   same gesture we do by hand today, crystallized; additive over the shipped resolver.

== What it is built from — the hybrid substrate

The operator runbook has one hard substrate (Pulumi state) so it is fully replayed. The design state is
mixed, so the designer runbook is HYBRID: a playable half and a narrated half.

* *The playable half* is replayed from the CODE — the hard substrate (grep/jdeps over the reactor,
  surefire counts, the shipped `-port` modules and capabilities). It is where the value is: it CANNOT
  lie, because it is re-derived from what actually compiles and ships. It catches the drift a
  hand-written atlas hides.
* *The narrated half* renders the reasoning that has no executable substrate yet — additivity of a
  not-yet-built model, the design horizon. It is rendered, not executed; it must live where it does not
  rot (regenerated alongside the atlas, not free-typed).

== How it is constructed

The engine question is already settled by the parked DSL-unification decision: ONE engine (JGiven),
two layers — the fluent grammar is the authoring surface, JGiven is the narration + report substrate.
The designer runbook follows the same mapping, with the codebase as the system under scenario:

* *design scenarios are JGiven scenarios over the reactor.* A scenario reads GIVEN the design baseline,
  WHEN a model/term, THEN the capability — and its steps PROBE the code for the playable assertions
  (the module exists, the capability is exported, the walker is gone, the unit count). The same
  living-documentation principle as the BDD suite: the generated report IS the deliverable.
* *the generated report IS the designer runbook* — JGiven's HTML/AsciiDoc output, the way the operator
  runbook is the rendered doctor narrative. Read one document, have the live design state.
* *it renders against the capability-anchoring device* (see rke2lab
  `unit-repository/unitrepo-design-unification-state` in memory and the atlas capability maps): the
  playable assertions flip a capability blue/green; the narrated ones stay amber.

== The v0 — feasible today, the infrastructure already exists

A first implementation needs NO new engine. JGiven is already wired (`jgiven-core` + `jgiven-junit5`
in the BOM and in `exec/seed-outcluster`), the report directory is already configured
(`jgiven.report.dir`), and seed-outcluster already holds ~18 scenario classes under `controlplane/bdd/`
in the established style (`Given/When/Then extends Stage`, fluent steps, `@As` prose). The doctor
scenarios prove the shape: the production vocabulary IS the scenario DSL.

=== A capability sentence IS a scenario — the mapping

The capability sentences are not a metaphor for scenarios; they are scenarios not yet written in
JGiven. The three clauses map one-to-one:

* GIVEN — the constellation before (the reactor as shipped).
* WHEN — the term or model that lands.
* THEN — the capability we can now say, AND additivity (nothing erased).

Worked example, the sentence "a unit is a star the resolver sees; the universe holds 46 units on
bioskop" becomes a scenario reading:

* `given().the_reactor_as_shipped()`
* `when().the_unitrepo_resolution_is_in_production()`
* `then().any_unit_set_resolves_in_one_felix_resolve().and().the_universe_holds_units(46)`

=== The playable steps probe the code — the half that cannot lie

The v0's value is the PLAYABLE half: steps whose assertions are re-derived from the reactor, the same
checks done by hand at the start of every session. They live in a design-probe `Stage`:

* `the_module_exists("osgi/unitrepo/unitrepo-core")` — assert the module directory and its pom.
* `the_walker_is_retired()` — assert `ManifestsUnitDependencyApplier` is absent from the tree.
* `the_capability_is_exported("unitrepo.handler")` — read the generated bundle manifest.
* `the_universe_holds_units(46)` — count via the resolver universe, the bioskop figure.

A green probe flips its capability blue/green in the rendered report; a probe that no longer holds
turns the line red — that is the drift a hand-written atlas hides, caught at render. The narrated
clauses (additivity of a not-yet-built model) are attached as plain narration steps, rendered not
asserted.

=== The deliverable is the generated report

Nothing more is built: a new `DesignStateScenarioTest` under `controlplane/bdd/`, a `DesignProbe`
stage holding the code-probing steps, and the already-configured JGiven report renders them. That
report IS the designer runbook v0 — read one document, have the live design state. Scope of the first
cut: a handful of playable scenarios over the shipped unitrepo + doctor state; the narrated half and
the atlas regeneration come after.

== What it is not (scope honesty)

It is not a replacement for the atlas — it is the atlas's missing live half. The atlas stays the map of
models and their additivity (the reasoning, the figures); the designer runbook is the part of that map
that is re-derived from the code so it cannot drift. Nor is it built yet — this is the design; the
first concrete step is to express a handful of playable design scenarios as JGiven scenarios that probe
the reactor, and render their report.
