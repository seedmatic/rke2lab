Chantier ouvert 2026-09-09 (design tranché avec l'user, code PAS commencé). Deux problèmes LIÉS dans `host/pulumi/incus-ingress/.../InstanceGrow.java`.

**Le leak :** `ensureImage` déclare `seed-image-<fingerprint>` (content-addressed) avec **`retainOnDelete(true)`** — au renew, l'ancienne image quitte le programme mais Pulumi la retire de l'état SANS supprimer l'image daemon (« pour ne pas casser l'instance qui tourne encore dessus »). → les vieilles images node-base **s'accumulent** dans le projet incus. Live sur bioskop-nixos : `pipelines-webhook-funnel-cert`… non, ça c'est un dataset ; les IMAGES leakent.

**L'alias abandonné (raison retrouvée, commentaire InstanceGrow:190) :** un alias stable sur l'Image collisionne sur l'**unicité per-projet du daemon quand ancienne+nouvelle coexistent au replace** — et elles coexistent PRÉCISÉMENT à cause du `retainOnDelete`. « Alias = concern CAPN futur, réintroduit comme sa propre resource. »

**Contraintes trouvées :** (1) le provider incus (`com.pulumi.incus`) n'a **PAS de resource alias séparée** — seulement l'attribut `ImageArgs.aliases` (collisionne en create-before-delete) ; (2) `IncusImportLookup` n'a que des **invokes read-only** (`getXxxPlain`) — **aucune écriture impérative** (delete-image/add-alias) via le provider ; (3) le GC + l'alias doivent être **POST-instance** car le renew d'instance est non-atomique (delete-puis-create, cf [[incus-master-renew-delete-without-recreate]]) → délai avant que l'ancienne image soit supprimable.

**DÉCISIONS (user) :** rétention = **courante SEULEMENT** (pas de rollback) ; mécanisme = **shape B — `com.pulumi.command` local.Command post-instance** (dependsOn l'instance) qui : (a) liste les images du projet et supprime toutes sauf le fingerprint courant, (b) pose l'alias **`node-base`** (PAS de préfixe `rke2lab-`, on est déjà dans le projet rke2lab) sur le fingerprint courant. Découplé du graphe de replace → évite le piège deleteBeforeReplace↔renew.

**Faisabilité vérifiée :** `com.pulumi.command` 1.2.1 est dans le BOM ✅ ; `incus-client` (darwin) existe dans le flake (`pkgs.incus.passthru.client`, `.#incus-client`, dans le devShell) ✅ ; le provider joint le daemon via un **remote** (`ProviderRemoteArgs`, `IncusProviderContext`). **QUESTION OUVERTE À RÉSOUDRE EN CODANT :** comment le CLI `incus` du local.Command s'authentifie au remote (le provider a endpoint+cert via config ; le CLI a besoin d'un `incus remote add` équivalent ou d'un remote déjà configuré sur l'hôte qui run pulumi). Fingerprint courant = un `Output<String>` de `ensureImage` → à passer au Command via `.apply`/interpolation. Supprimer aussi le `retainOnDelete(true)` (ou le garder + laisser le Command GC — à décider en codant). Alias `node-base`.

**INVESTIGATION FAITE (2026-09-09, post-reboot).** Résultats : (1) **PAS de `sdks/incus`** ni de client incus/lxd impératif dans la codebase (la réf CLAUDE.md est périmée) — le seul incus Java = le SDK Pulumi généré (`host/pulumi/pulumi-generated-sdks/incus`, resources déclaratives + invokes READ-ONLY via `IncusImportLookup`) + l'`incus-edge` OSGi (`CultivatingNixosImageBuilder`, BUILD-ONLY nix, « No incus dependency »). (2) **Shape A (déclaratif deleteBeforeReplace) IMPOSSIBLE** : l'instance est un **clone ZFS de l'image** → incus refuse de supprimer l'image tant que le clone (l'instance) existe → c'est pourquoi le code a `retainOnDelete(true)` ; le GC DOIT être post-teardown-instance (le « délai » de l'user). (3) REST API incus (dérivée LXD) confirmée : `GET/DELETE /1.0/images/<fp>?project=P`, aliases `POST /1.0/images/aliases {name,target}` + `DELETE /1.0/images/aliases/<name>` + `PATCH .../<name> {target}`, auth = **cert client mTLS**.

**DÉCISION user = client REST incus Java (combler le gap edge impératif).** Auth résolue : le provider utilise `IncusProviderContext` avec `configDir=config.incusConfigDir()` + `generateClientCertificates(false)` → les **certs client mTLS + le remote sont déjà dans ce configDir** ; le client REST charge cert/key/cacert de là + tape `https://<config.incusRemoteAddress()>/1.0/...?project=<config.incusProject()>`.

**PIVOT VÉHICULE (2026-09-09) : le client REST + « step post-up dans le driver » ÉTAIT UNE FAUSSE PISTE — il n'y a AUCUN hook post-up.** Investigation du driver : `exec/seed-master/.../Main.java:75` = TOUT seed-master tourne DANS `Pulumi.run(ctx -> {…})` (le corps DÉCLARE le graphe puis rend la main ; le moteur applique APRÈS le retour → zéro code Java ne s'exécute après le `up` de la stack principale ; le grow = `pulumi up seed-master` lancé de l'extérieur). Le `StackHandle.up()`/`stack.up()` que la mémoire citait comme « automation API du grow » = le CELLIER (`PulumiCellar:290`, side-stacks de stockage), PAS le grow. Donc le seul point d'exécution impératif post-instance = une **resource résidente du graphe** qui `dependsOn` l'instance. **DEUX faits neufs tranchent pour `local.Command` (pas REST) :** (1) `flake.nix:542` — le runtime du grow bundle DÉJÀ le CLI incus (« the incus client the provider shells out to ») → CLI garanti + auth = le même `configDir` que le provider (la « question ouverte » d'auth CLI s'évapore : le provider fait déjà exactement ce shell-out) ; (2) sans hook post-up, REST devrait vivre dans un apply-side-effect (anti-pattern Pulumi, timing subtil) alors que `local.Command` est natif, exécution garantie post-création, gate preview natif, colle au rôle declare-only d'`InstanceGrow`. User a confirmé `local.Command`.
