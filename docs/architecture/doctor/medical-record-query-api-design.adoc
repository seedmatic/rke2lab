= Medical Record — a query API reconstructed from Pulumi (WIP design)
:toc: left
:toclevels: 3

*Status:* ✅ Implemented, then migrated into the OSGi world. This is the settled design and its
rationale; where a design-time name and a shipped name differ, the mapping is called out inline
(see _As-built mapping_ below). The model was grounded on a working proof before implementation (the
throwaway `wip/sandbox` program; not retained on `main`).

[NOTE]
.OSGi re-baseline (as-built) — read this before the design body
====
The design below was written when the doctor reconstructed the record *directly* from Pulumi
in-process. That premise is preserved as *vision* (reconstruct on demand from a single source, never
a stored blob, the four clinical questions, the additive schema, the layered error contract), but the
as-built code moved:

* The Pulumi self-introspection capability shipped *host-side* as the module
  **`host/pulumi/pulumi-edge`** (package `io.seedmatic.rke2lab.pulumi.edge`), NOT a top-level
  `pulumi-automation-ext` module under `io.seedmatic.rke2lab.pulumi.automation`. Its as-built types
  (`SnapshotSource`, `StackHandle`, `StackHistory`, `StackSnapshot`, `StackCheckpoint`,
  `StackHandleSnapshotSource`, `PulumiBackendLayout`, the `Stack*`/`Snapshot*` exception hierarchies)
  live there.
* The doctor no longer imports a `SnapshotSource` and reconstructs Pulumi state itself. The host
  reads the snapshots into a *neutral host journal* — the seed-broker `Cellar`, a `List<SeedEnvelope>`
  of opaque `visit` blobs — and **`doctor-core`'s `MedicalRecordReader`** folds that journal into the
  `MedicalRecord`, decoding each blob codec-based (`SeedCodec.fromMap`) inside the bundle realm. No
  Pulumi type crosses the seam.
* `MedicalRecord` and `ConsultationReport` are `doctor-contract` records; the four questions
  (`chiefComplaint` / `historyOf` / `efficacyOf` / `comorbiditiesWith`) shipped verbatim on
  `MedicalRecord` (with `efficacyOf(Symptom, InterventionLedger)` taking the ledger).
* `ConsultationReportReader` and the offline `MedicalRecordDump` no longer exist — read-back is the
  codec path via `MedicalRecordReader`. The named integration tests below (`SeededMedicalHistoryTest`,
  `RealGraphInjectionTest`) migrated with the module.

Read the module/type names in the body through this note.
====

*Scope:* the longitudinal medical record — what a practitioner can learn about a patient over time.
This is the _préalable_ before `treats()` / the referral round-trip. It does NOT cover the
point-of-view inversion, which is a separate later brainstorm that consumes this API.

== Summary (what changed, and why)

An earlier draft proposed an *accumulator*: a top-level `medicalRecord` output, rebuilt and
re-exported every run via a self-`StackReference`, carrying a sliding window of visits. That design
is *abandoned*. It duplicated, by hand, history that Pulumi already keeps — the very thing that made
it feel wrong.

The replacement: the medical record is **reconstructed on demand from Pulumi, the single source**.
Nothing extra is exported. A query API answers the practitioner's questions by reading the current
state and the historical checkpoints Pulumi already persists.

This rests on facts *proven* during the brainstorm, not assumed:

* A Pulumi program *never reads stack state itself* — the engine does. The runtime `Context` exposes
  only name/config/log/export. (Verified against the 1.28.0 jar.)
* The stack *lock is about concurrency only* (one operation at a time); it has nothing to do with
  history visibility. (Verified in `pkg/backend/diy/lock.go`.)
* The Automation API reads (`getHistory`, `exportStack`) are *lock-free* and work *in-process,
  mid-up*. (Verified in `pkg/backend/diy/backend.go` and *proven end-to-end* by `wip/sandbox`:
  a program reads its own history+state during its own `up`; history grows 0,1,2 across runs; a
  per-node `consultationReport` written by one run is read back from `exportStack()` the next run,
  by the right key and content.)

== The patient and the practitioner

* *Patient* = the Pulumi stack (`org/project/stack`) — a persistent identity with a history of
  deployments.
* *Practitioner* = the `Generalist` / `Specialist`. It diagnoses, and to diagnose well it *asks the
  record* about the patient's past.
* *The record is not a stored blob* — it is *answers to questions*, reconstructed when asked. The
  doctor drives the shape, not the storage.

== The four clinical questions

These are the questions a practitioner actually asks about a patient. They are the API.

[cols="1,2,2",options="header"]
|===
|Clinical question |API (practitioner-facing) |What it needs
|*Present complaint* — what hurts now |`chiefComplaint(patient)` |the latest deployment only
|*History of a symptom* — had it before, how often, acute vs chronic |`historyOf(patient, symptom)` |scan the diagnosis across past deployments
|*Treatment efficacy* — what we prescribed, and whether it worked |`efficacyOf(patient, symptom)` |pair the symptom with the prescription and the next visit
|*Correlations* — which symptoms co-occur or cascade |`comorbiditiesWith(patient, symptom)` |symptoms grouped per visit + walked along `dependsOn`
|===

=== They reduce to one primitive

All four are expressed over a single primitive: *the diagnostic layer of one deployment*.

The historical questions are *aggregations* of the diagnosis-at-one-deployment primitive over the
timeline that `StackHistory` enumerates. A past deployment is *immutable*, so a fetched diagnosis
caches, keyed on `(patient, deployment-instant)`; only the latest moves.

[IMPORTANT]
====
*The ordering key is the deployment instant, not a version number.* The design originally assumed an
"ordered version sequence". Reading the real dev backend (283 deployments) disproved it: the file
backend leaves the history `version` field at *0 for every deployment in a stack* — it is not the
update sequence number it looks like. The strictly-monotonic key is the *nanosecond stamp in the
checkpoint file name* (`<stack>-<nanos>.checkpoint.json`), which `StackHistory` parses into the
deployment `Instant` and sorts on. `StackHistory.Entry` keeps the raw `version` only as an opaque
field; nothing orders by it. This is the single most load-bearing correction between design and
as-built — and the reason the on-disk coupling is documented so explicitly below.
====

== Placement: a reusable top-level module, a neutral doctor interface, wired in seed-outcluster

Other modules will be Pulumi-based too (`seed-outcluster` today, future `seed-*`). The capability to
*read a stack's own state and history in-process* — and to *re-provide the missing versioned export*
over checkpoints — is generic and has *no doctor notion*. It must be a *shared module*, not buried in
seed-outcluster, so every seed-* reuses it.

*It is NOT under `sdks/`.* In this repo (and in Pulumi's own vocabulary) an `sdks/*` module is a
*generated provider SDK* — `sdks/incus` is package `com.pulumi.incus` with resource classes
(`StorageBucket`, `NetworkLb`, …) a program instantiates to *create* resources. This module creates
nothing; it *observes* a stack from outside the resource graph via the Automation API. It is *not* a
provider and *not* a runtime extension — its capability is client-side. *As-built (OSGi):* it shipped
*host-side* as **`host/pulumi/pulumi-edge`** (package `io.seedmatic.rke2lab.pulumi.edge`), where the
whole Pulumi seam lives — not the design-time top-level `pulumi-automation-ext`
(`io.seedmatic.rke2lab.pulumi.automation`). It stays generic and reusable by any host-side seed-*.

So there are *three* layers, each in its place:

* *`host/pulumi/pulumi-edge` (the host Pulumi module)* — Pulumi self-introspection: read own state
  (`exportStack`) and history in-process, and materialize the snapshot of *any* past deployment
  (addressed by its deployment instant) over the checkpoint JSON. Knows Pulumi, knows nothing about
  the doctor. Coordinates: package `io.seedmatic.rke2lab.pulumi.edge`. As-built types: `StackHandle`
  (the workspace anchor), `StackHistory` + `StackHistory.Entry` (the deployment timeline, ordered by
  instant), `StackSnapshot` / `StackCheckpoint` (one deployment's state), `SnapshotSource` /
  `StackHandleSnapshotSource` (the snapshot seam), `PulumiBackendLayout` (the single source of truth
  for the on-disk layout), and the `StackException` / `StackAccessException` / `StackContentException`
  plus `SnapshotException` / `SnapshotAccessException` / `SnapshotContentException` hierarchies.
* *the doctor (`doctor-core`, OSGi)* — the *neutral* clinical model: the `MedicalRecord` (the four
  questions, a `doctor-contract` record), reconstructed for one `Patient` by `MedicalRecordReader`,
  which folds the host `Cellar`'s neutral `visit` journal and decodes each blob codec-based
  (`SeedCodec.fromMap`) — there is no `ConsultationReportReader`. The doctor imports no Pulumi type;
  only opaque `SeedEnvelope` blobs cross the seam.
* *the host / `pulumi-edge`* — reads the snapshots through `StackHandleSnapshotSource` and files them
  into the `Cellar` as neutral `visit` blobs; the OSGi side folds them. The patient is bound once, at
  `MedicalRecordReader.read(patient, journal)`; the resulting `MedicalRecord` answers the four
  questions without re-taking a patient argument.

The `Generalist` receives a `MedicalRecord` and cannot tell whether it is Pulumi-backed, file-backed,

point.

=== Where the module attaches in the Pulumi model: nowhere in the resource graph

A natural question: as a "Pulumi module", what does it hook into — a provider, a plugin? *Nothing in
the resource/provider model.* A provider *creates and manages resources* (the incus provider makes
instances) and participates in the graph. Our module *creates nothing*: it reads state and history
from *outside* the graph, like an ops script. Its one anchor is
`LocalWorkspace.createOrSelectStack(stack, workDir)` — a *workspace handle* to an already-deployed
stack (proven by `wip/sandbox`), reached through the Automation API, not through the runtime. This is
the same line the project already drew: the doctor is not a Pulumi resource. (As-built, the
per-node `consultationReport` is filed into the host `Cellar`/journal as a neutral blob, not carried
by a design-time `registerOutputs` output on the stack.) The module is application code that *drives*
Pulumi, not an extension of the Pulumi runtime.

== Realizing the per-deployment diagnosis: one primitive, two backings

Reading the diagnosis at a *past* deployment is *exactly* the capability the file backend lacks and
the cloud has — Pulumi's optional `SpecificDeploymentExporter.ExportDeploymentForVersion`. The CLI
flag `pulumi stack export --version N` exists but the *file backend refuses it*
("the current backend does not provide the ability to export previous deployments"); the
Automation API Java surface has *no* versioned export at all. So we re-provide the capability over
the checkpoints Pulumi already writes to disk — addressing each one by its *deployment instant*, not
by a version number (see the ordering correction above).

Only the *fetch* step differs between backings; the *navigate + map* step is shared. Swapping
file to cloud later replaces "parse a checkpoint file" with "call the native capability", and nothing
else in the adapter moves. The file backing is *coupled to the file-backend on-disk layout*
(`.pulumi/history/<project>/<stack>/<stack>-<nanos>.checkpoint.json`) — an accepted, documented
coupling, *owned in exactly one place*: `PulumiBackendLayout` is the single source of truth for that
path (no other class re-encodes `.pulumi/history/...`), and the `<nanos>` stamp is the deployment
ordering key. The coupling is isolated behind that layout type and the `StackHistory`/`StackHandle`
pair.

NOTE: The per-node `consultationReport` (shipped, filed into the host `Cellar`/journal as a neutral
blob) is the *substrate this all reads*. It is OUR diagnostic data — Pulumi cannot recompute it. It
stays. What the abandoned accumulator added on top (a top-level duplicate) is what goes away.

* *During a run (the main use).* While diagnosing, the doctor enriches the current diagnosis with the
  patient's past — "has this symptom happened before? did the last prescription work?". In-process,
  lock-free (proven).
* *Offline, transient (the dogfooding loop).* Not a dashboard. When a symptom no specialist treats
  produces a *recruitment prescription*, the system calls us back: operator + Claude consult the
  patient record offline (`historyOf`, `efficacyOf` for that frontier symptom) to brainstorm and
  design the new specialist, then codify it into the roster. The offline entry point stays light —
  it just instantiates the same adapter against a stack for the duration of that design session.

== Error handling: a layered contract, never errors-as-logs

The earlier draft of this section said "skip the bad version, log it, keep going". That is
*errors-as-logs* — it deports the decision (is a missing diagnosis acceptable here?) onto a human
reading output later. The shipped contract refuses that. Two return channels, with disjoint meaning:

* *`Optional` / empty list = nothing-here.* A genuine absence the caller can act on: no history yet,
  a healthy run with no symptom, an empty `latest`. Never an error.
* *A checked exception = something-went-wrong.* A present thing that could not be read. The reader
  does *not* swallow it, does *not* substitute empty, does *not* log-and-continue. It throws, and the
  *caller* decides the policy.

The exceptions are *typed on the retryable axis*, so the caller can branch without parsing messages:

[cols="1,1,2",options="header"]
|===
|Exception |Meaning |Caller policy
|`StackAccessException` |an *I/O / access* failure — the file vanished between listing and read, the workspace call failed |*retryable* — transient, may succeed on retry
|`StackContentException` |the bytes are present but *malformed / wrong shape* — corrupt checkpoint, unparseable filename stamp |*never-retry* — retrying reads the same bad bytes; carries the offending `path()`
|===

Three roles, each with one job (the same discipline as instance-passing — each layer owns its decision):

[cols="1,2",options="header"]
|===
|Layer |Contract
|*Leaf* (`StackHistory`, `StackHandle`, `StackHandleSnapshotSource`) |throws the *precise* typed exception; never catches-to-empty, never logs. A genuine absence is `Optional.empty()` / empty list, *not* an exception.
|*Aggregator* (`MedicalRecordReader`) |*fail-at-end*: walks the whole timeline, accumulates entries that read cleanly, and if any entry failed throws *one* `MedicalRecordReconstructionException` carrying the partial result plus every per-entry failure via `addSuppressed` (each enriched with its identity — which patient, which entry). It does not abort on the first bad entry, and it does not hide that one was bad.
|*Caller* (the in-run doctor / host-journal fold) |*decides the policy* with full information. An offline consumer may be lenient — surface the partial record and report the suppressed failures because a human is in the loop; an in-run consultation may choose to be strict. (The design-time offline `MedicalRecordDump` entry point was not carried into the OSGi build — the codec fold via `MedicalRecordReader` is the read-back path.)
|===

[cols="1,2",options="header"]
|===
|Situation |Behaviour
|Healthy run, no symptom raised |`chiefComplaint` returns _nothing-to-report_ (empty) — not an error
|First run / empty history |`latest` is `Optional.empty()`, `timeline()` is an empty list — nothing-here
|A present checkpoint cannot be read (deleted mid-read, I/O error) |`StackAccessException` propagates — retryable, never degraded to empty
|Checkpoint corrupt or unexpected shape |`StackContentException` (with the offending `path()`) — never-retry
|Several entries fail across the timeline |the aggregator throws *one* `MedicalRecordReconstructionException` with the partial record + all failures as suppressed; the caller decides
|Cold cache |a past deployment is immutable, so a clean read is cached, keyed on `(patient, deployment-instant)`; only the latest moves
|===

NOTE: One catch-all remains, documented as deferred backlog: `StackCheckpoint.snapshot` still wraps a
broad `catch(Exception)` into `StackContentException`. Narrowing it to the precise parse exceptions is
tracked, not yet done — called out here so the contract's one rough edge is on the record.

== Schema evolution: presence-based versioning, the version number deferred losslessly

The diagnostic data the record reads — `ConsultationReport.toOutputMap()` — is an *open key-bag*:
a flat map with no schema-version field. The record's "version" is carried by *which keys are
present*, never by a number. This is a deliberate choice, and the reasoning matters because the
obvious alternative (stamp every report with a `schemaVersion` integer now) looks like cheap
insurance and is in fact the wrong tool here.

=== What a version number actually buys

A schema-version integer earns its keep in exactly one regime: a *breaking* change — when the
*meaning* of an existing key changes, or keys are removed or reshaped, so the reader must branch
("if v1 interpret this way, if v2 that way"). The number is a *global* discriminator that selects an
interpretation.

It buys *nothing* for purely *additive* evolution — only ever adding new keys, never changing old
ones. There a *tolerant reader* (read-by-key, ignore-unknown-keys, absent-key-means-empty) reads
every generation uniformly with no version check. The discriminator still exists, but it is *local*
(per-key presence) instead of *global* (one number).

=== Our regime is additive by domain nature

A medical record is *append-only*: you never rewrite a patient's past, you accrete to it. New
features add information (the inter-practitioner courrier `ReferralReply` is the next known example —
it will attach to `ConsultationReport` when `treats()` produces it); they never remove or reshape
what an older report already wrote. In a purely additive regime a version number would be
*written but never read* — no code path would branch on it. That is write-only dead data, which the
project's conventions explicitly reject (no speculative abstractions, no dead code kept for "a later
pass").

=== Deferring the number is lossless — this is the crux

The version field can itself be introduced *additively*, the day a genuine breaking change finally
arrives. By the tolerant-reader rule, a report *without* a `schemaVersion` key reads as absent =
unambiguously "the pre-versioning schema" (version 0); reports *with* it carry their explicit number.
So at the exact moment versioning is needed, the entire past is still cleanly interpretable. There is
no future "I wish I had stamped it sooner" — *additive schemas are always distinguishable by
key-presence*, by construction. We lose nothing by waiting.

=== Why stamping it now would be actively worse

* It is dead, write-only data until a breaking change that may never come.
* It tempts the *wrong* reader pattern: a present version number invites a future reader to branch on
  it and *reject unknown versions* — which breaks the forward-compatibility the presence-based
  approach gives for free (an old reader silently ignores a new key; a new reader handles both old and
  new). The number would erode the very property we want.
* It adds a *third* "version" meaning next to the two the system already juggles (the deployment
  schema version `3` = DeploymentV3, and the update sequence number) — more identifier-mismatch
  surface, the same class of silent bug as `clusterApi` vs `cluster-api`.

=== What must exist now (and does)

The real insurance is *not* the number — it is the *tolerant-reader discipline itself*:
read-by-key, ignore unknown keys, treat absent keys as empty. That is the load-bearing half, and it
must be correct *today*: it is the contract the diagnosis-reading step (the navigate+map of
`diagnosisAt`) is built to. A report written before the courrier existed and one written after must
*both* reconstruct. The version *number* is the half that does not pull its weight yet — deferred,
losslessly, until a breaking change asks for it.

== Test strategy

* *Unit, no Pulumi (where the risk is).* Feed a neutral `visit` journal (opaque blobs) to the fold
  and assert the `ConsultationReport`s are codec-decoded; run the aggregations
  (`historyOf`/`efficacyOf`/`comorbiditiesWith`) over synthetic multi-visit timelines; cover the error
  cases (healthy run, empty journal, malformed blob). As-built, this is `doctor-core`'s
  `MedicalRecordReaderTest` / `MedicalRecordReaderExpectationTest` + the codec round-trip
  `ConsultationReportCodecTest`.
* *Integration, real Pulumi (the seam).* Proven by a throwaway sandbox program before implementation:
  in-process lock-free read of the program's own history+state, and per-node read-back across runs.
  The host-side snapshot→journal seam lives in `host/pulumi/pulumi-edge` and is exercised by its own
  tests (checkpoint fixtures under `pulumi-edge`). FLAG: the design-time `SeededMedicalHistoryTest` /
  `RealGraphInjectionTest` names did not survive the OSGi split verbatim — the reader-side coverage is
  the `doctor-core` reader tests above; the host-side coverage is `pulumi-edge`'s snapshot tests.

== Non-goals

* A top-level accumulator / self-`StackReference` rebuild (abandoned — it duplicated Pulumi).
* A wrapper process or a faked cloud service backend (self-hosted Pulumi Cloud is commercial;
  rejected).
* Forking the DIY Go backend to implement versioned export (disproportionate; the checkpoints are
  plain JSON we parse in Java).
* The `treats()` / referral inversion (separate later brainstorm; it consumes this API).
