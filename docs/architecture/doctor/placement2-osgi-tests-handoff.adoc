== What this closes

Placement 2 moved doctor's cross-boundary value types into `doctor-port` and sealed the actors
(`final class`, package-private) in `doctor-core`. But the *tests* were left incoherent with that
map:

* 5 value-type tests (`MedicalRecordTest`, `ConsultationReportSerializationTest`,
  `ConsultationReportExpectationTest`, `DoctorRecordsTest`, `MedicalRecordEfficacyConfoundedTest`)
  were *parked in `exec/seed-outcluster` HOST* — they belong to `doctor-port`, but the flat classpath
  could not give a model test a home in the OSGi module.
* The shared fixtures (`ReferralReplies`, `FakeSpecialist`) lived in a separate `doctor-testkit`
  module — created *only* to dodge the flat classpath — which produced a `doctor-port ↔
  doctor-testkit` Maven cycle.
* doctor-core's 10 actor tests sat in `doctor-core/src/test`, reaching the sealed package-private
  actors only by the *accident* of the flat classpath (a black-box bundle could never).

All three are now dissolved by the test-fragment model: the test *is* its host (shared classloader),
so it sees the host white-box with no reverse module edge — no cycle, no parking, real coherence.

The naming rule this settles: *`-testkit`* = shared public fixtures you depend on (a library/bundle);
*`-test`* = a white-box fragment attached to the one subject it tests. They never overlap.

== The model: two halves, two worlds

A host `-test` fragment is split across the classloader membrane on purpose.

* `src/main` → compiled into the *fragment*, loaded by the *host* bundle → runs white-box,
  in-container. This is where the test classes + a tiny host-package entry point (`DoctorPortTests` /
  `DoctorCoreTests`) live.
* `src/test` → a plain-JVM JUnit5 `@TestFactory` harness (VSCode-clickable, loaded by surefire). It
  boots Felix, installs the host + the fragment + the JUnit/jGiven bundle worlds, resolves the host
  (attaching the fragment, OSGi Core §3.14), then invokes the entry point reflectively *through the
  host classloader*. Each in-container test result comes back as a plain `String` → one
  `DynamicTest`, so VSCode shows a node per test and a single failure fails alone.

== The three OSGi crossings (the hard-won part)

Running a real JUnit Platform Launcher *inside* Felix hits three classloader boundaries. Each is
handled in `InContainerJUnitRunner`; all three were found empirically and are the reusable payoff.

[cols="1,3",options="header"]
|===
| Crossing | Resolution

| *Thread context classloader.* The launcher's `ServiceLoader` and Jupiter's discovery read the
  TCCL; surefire leaves it on the flat app classpath, so the launcher would find the flat-classpath
  engine whose `TestEngine` supertype differs from the launcher's (`"JupiterTestEngine not a
  subtype"`).
| The whole launch runs on a *dedicated thread* whose context classloader is the host bundle loader.
  The thread is the membrane between the OSGi world and the bare-JVM world.

| *Engine discovery.* `ServiceLoader` cannot cross the OSGi boundary — the
  `META-INF/services/…TestEngine` resource lives in the engine bundle, and package wiring does not
  expose another bundle's resources (`"Cannot create Launcher without at least one TestEngine"`).
| The engine is registered *explicitly* (`LauncherConfig`, auto-registration off). The fragment
  passes the engine *`Class`* (`JupiterTestEngine.class`) to a strongly-typed runner
  (`InContainerJUnitRunner<T extends TestEngine>`). Two wins at once: the engine is instantiated via
  the host loader (matching supertype), AND naming the class in the fragment's bytecode makes bnd
  compute `Import-Package: org.junit.jupiter.engine`, wiring the engine bundle into the host. This is
  the in-container form of *declare what you import*.

| *Class discovery.* `selectPackage(…)` uses Jupiter's `ClasspathScanner`, which walks
  `getResources(pkg)` as a file directory — it cannot list Felix `bundle://` URLs, so it finds zero
  tests.
| Test classes are enumerated via `BundleWiring.listResources(pkgPath, "*Test.class", LOCAL)` — the
  OSGi-native enumeration — then `selectClass(…)` each. Sees the attached fragment's classes.
|===

== How a future host adopts the model

Three files, mechanical (copy `doctor-port-test`):

. *`bnd.bnd`* — `Bundle-SymbolicName`, `Fragment-Host: <the-host-bsn>`, `Export-Package` for any
  fixtures the fragment shares, and (only if it runs jGiven) `-include` the shared
  `jgiven-fragment.bnd`. No manual `Import-Package`: naming `JupiterTestEngine.class` in the entry
  point lets bnd compute it.
. *the entry point* (`<Host>Tests` in the host's package):
+
[source,java]
----
public static List<String> run() throws InterruptedException {
  return new InContainerJUnitRunner<>(
          <Host>Tests.class.getClassLoader(), JupiterTestEngine.class,
          <Host>Tests.class.getPackageName())
      .run();
}
----
. *the harness* (`src/test`, `@Osgi @TestFactory`): boot via `OutOfContainerFrameworkExtension.builder()` (or
  `JGivenTestkit.felix()` for jGiven), `installFromClasspath` the JUnit bundles + `junit-testkit`,
  install host + fragment, `resolve`, invoke `run()` through the host loader, map each line to a
  `DynamicTest`.

== Anti-patterns

❌ *`Export-Package` a host's internal package to let a fixture see it.* That un-seals the package for
the whole world. A fixture that needs a host internal belongs in *that host's* `-test` fragment,
where it reads it white-box (shared package) and may publish its own public API over it — without
ever re-exporting the host's package. Visibility of the host is never violated in tests.

❌ *Put the in-container runner in a plain jar / in each fragment.* It must be a *bundle* (imported by
fragments) and it must be *generic* (one copy). It is `junit-testkit`'s `…container` package.

❌ *`x-friends` / `x-internal` / `osgi.support.multipleHosts`.* Equinox/PDE extensions; inert under
Felix. The cycle dissolves by *module structure* (the fragment depends on the fixtures, not the
reverse), not by access directives. A fragment names exactly one `Fragment-Host`.

❌ *Default the engine inside the runner.* Then the fragment's bytecode never names it and bnd cannot
wire the engine bundle. Pass `JupiterTestEngine.class` from the fragment — strong typing AND import
inference in one move.
