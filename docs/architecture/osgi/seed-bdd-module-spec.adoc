= seed-bdd — the common gardening spine every seed exec rebuilds on
:toc: left
:toclevels: 3

[NOTE]
====
*Status:* being implemented (2026-07-12). `seed-bdd` is the FOUNDATION module holding the gardening spine
common to every seed exec — the host runbook stages spoken in the gardening register (`Cellar`
fetch/store, the sow-and-graft caller) plus the open `Gardening` the GIVEN carries. An exec
(`seed-outcluster`, and the seed execs after it) adds only its OWN root composition: which scions, in what
order. It realises the host half of link:../bdd/bdd.adoc#clusterseed-scenario-map[the ClusterSeed scenario
map] atop link:gardening-model-spec.adoc[the gardening model]. Opening the gardening is NOT a WHEN — the
map's GIVEN is "I have access to the open gardening", so the driver opens the `Gardening` instance and
hands it to the scenario's Given; the WHENs are the worktree survey → cellar fetch → the sow-and-graft
crossings → cellar store, with the clean-worktree entry gate now enforced inside the worktree crossing.
====

== Why a module — common spine vs per-exec composition

The target host runbook is uniform: every root step is EITHER pure-host gardening (`Cellar` fetch/store)
OR a *sow-and-graft caller* (sow a domain scenario toward the gardening, graft its scion). The
STAGES that speak these gestures are the same for every seed exec; only the COMPOSITION — the phase order,
which scion each step sows — is exec-specific. So the stages are common (`seed-bdd`), the composition is
the exec's (`seed-outcluster` writes its `ClusterSeedScenario`, a later exec writes its own).

[cols="1,2",options="header"]
|===
| layer | contents · home
| *common* | the gardening stages (`Cellar` fetch/store, the sow-and-graft caller, the world
opening + the seeding harness) — **`osgi/foundation/seed-bdd`**
| *per-exec* | `Main` + the concrete root scenario (the phase chain: worktree survey → … → outputs) — the exec
module (**`seed-outcluster`**, …)
|===

== Placement and consumption — under osgi/, consumed FLAT by the host

`seed-bdd` lives in `osgi/foundation/` (beside `seed-broker-port`, whose BDD counterpart it is), yet the
host consumes it as a *flat jar*. Location and realm are independent axes — the precedent is
`scenario-engine` (`osgi/runtime/`): *a bundle is a superset of a plain jar*, and the split is by PACKAGE,
not by module.

* *One artifact, one BSN* (`io.seedmatic.rke2lab.osgi.foundation.seed.bdd`), both a bundle and a plain jar.
* *The SOW half IS exported* (`seed.bdd.sow` — `Gardening`). The open gardening is an INSTANCE holding
  the live connection + the gardener (the `SeedBroker`), and it knows how to sow: `gardening.sow(soil)`
  grows that soil's scenario through the gardener and reaps the runbook. Sowing is REALM-AGNOSTIC: the
  driver holds the open gardening host-side today (embedded), but a scion-peer could hold one in-container
  tomorrow (remote — the same door, the same gesture, § REST embedded-today / remote-tomorrow). So the
  reusable half travels; the package is exported for that future in-realm reuse.
* *The GRAFT COMPOSITION + the rest of the spine are NOT exported* — the base package `seed.bdd`
  (`SowAndGraftStage`, the `CellarStage`). `SowAndGraftStage`
  composes `ScenarioGraft` for the HOST ROOT's crossings and runs on the flat host classpath, never
  wired in-container — exporting a host stage would let a bundle load a second copy of a seam class
  (the `DUPLICATE_REALM_CLASS` collision the engine's bnd guards against). `ScenarioGraft` ITSELF,
  though, is NOT host-only: the graft is local to whoever owns a runbook tree, and a scion can own a
  sub-runbook (the incus provisioning scion grafts the manifests scion under its own step,
  in-container), so `ScenarioGraft` lives in the engine's EXPORTED `.container` package — stateless,
  only flat JSON crosses the realm, so no live jGiven object is ever shared between loaders.
* *Host-only imports are `resolution:=optional`* (framework-launch, jGiven, `org.osgi.framework`) — exactly
  as `scenario-engine`, so the bundle still RESOLVES when installed in-container to provide `seed.bdd.sow`.

This is the `scenario-engine` split, applied to the sow/graft asymmetry you surface for the remote mode:
*export by PACKAGE, not by module*. The reusable SOW travels in-realm; the tree-local GRAFT stays home.
It is NOT the codec's dual-realm (two copies) — one jar whose exported `sow` package a bundle *may* install
and whose non-exported base package the host uses flat, superset not duplication. When the remote mode
lands (a scion sowing a peer's sub-scenario), `seed.bdd.sow` is already the in-realm half it needs; any
further stage a scion wants is exported then, per package, reversibly, never by inflating the seam.

== Dependencies — leans on seed-port + engine, never inflates seed-port

`seed-bdd` DEPENDS on `seed-broker-port` (it consumes `Cellar`, `SeedEnvelope`, `Parcel`, `SeedBroker`,
`RunGate`) and on the neutral half of `scenario-engine` (the sow-and-graft mechanics). The arrow runs
FROM `seed-bdd` TO `seed-port` — depending on the seam is not entering it. `seed-port` stays the minimal
membrane; the gardening stages are a consumer, not a seam inhabitant.

== Who speaks gardening — the stages, not the engine

The engine stays at the FLIRT level: `ScenarioGraft` names the horticultural gesture (*graft*) but its
signatures are mechanical (`rebuild(String)`, `graftUnder(ReportModel, …)`). `seed-bdd`'s stages SPEAK
gardening in their step titles ("I go to the cellar for the parcel's state", "I sow X and graft its
scion", "I store the harvest") and COMPOSE the neutral mechanics underneath. The engine gains no
gardening type; the vocabulary lives in `seed-bdd`'s stages, which call the engine's neutral mechanics.

The sow-and-graft caller composes the two halves of the crossing (link:seed-broker-spec.adoc#playing-a-scenario-is-a-sow[the
runbook handler]): the SOW half is `broker.sow(new RunbookCoordinate(soil), trigger)` — the host holds
only a soil NAME (a `String`) and reaps the runbook as JSON, never naming a `*Coordinate` enum nor
reaching a scenario front-door (the play lives INSIDE the domain's `*RunbookHandler`, delegated to the
shared `ScenarioPlayer`, on its own loader). `RunbookCoordinate` is a neutral value-coordinate in `seed-broker-port` (the twin of
`SplitCoordinate`), so the seam names nothing a domain owns. The GRAFT half is
`ScenarioGraft.rebuild(payload)` + `graftUnder(hostTree, step)`, on the runbook owner's side (host-side
for the root; a scion owning a sub-runbook grafts in-world — incus grafts manifests). One gesture — one
door out, one graft home — nine times in the root scenario. `seed-bdd` therefore depends on
`seed-broker-port` (the `SeedBroker` door + `RunbookCoordinate`) and the neutral `ScenarioGraft` (in the
engine's exported `.container`), never on a domain's `*RunbookHandler` or `*Coordinate`.

== The root scenario — a per-exec composition on the common stages

`seed-outcluster`'s `ClusterSeedScenario` is the concrete instance: pure-host `Cellar.fetch` opening (read the
parcel's state — where we start from), nine sow-and-graft crossings (worktree · bbox · cluster-pki · ghapp ·
replicator-secrets · ghapp-webhook · incus-provision · systemd · cluster — the dependency chain whose
terminal fruit is *the cluster answers ready*) interleaved with the host-flat beats (the GROW, the operator
kubeconfig, the readiness-budget tuning), pure-host `Cellar.store` closing (the harvest filed to its parcel). The cellar at both ends — `fetch` opens, `store` closes; between them
everything is cultivated fresh (no scion reads the cellar; the manifests graft is grown fresh, not cached).

[[the-amorce]]
== The amorce — Pulumi wraps, the GIVEN bootstraps, the store carries the one irreducible fact

Bootstrapping is the hardest seam: the world does not exist yet, and it must be born in the right order.
There are TWO layers, and the frontier between them is precise.

*Layer 1 — the Pulumi envelope (the exec's `Main`, host-side, irreducible).* The whole program runs
*inside* `Pulumi.run(context -> …)`: the `com.pulumi` provisioning graph cannot enter Felix (it stays
host, per the migration spec), and the run-mode fact — is this a live run or a preview? — is only knowable
there (`Deployment.getInstance().isDryRun()`, projected to `RunMode`). So `Main` is and stays the Pulumi
entry point; it captures the run's facts into a `SeedRun` and plays the root scenario on the launcher
(`JUnitLauncherCore`, flat host loader, `selectClass(ClusterSeedScenario)`). This layer is NOT a jGiven
step — it *precedes* the jGiven world.

[NOTE]
.One `pulumi up` = one `SeedRun` = one transaction — no concurrent root scenarios
====
A `pulumi up`/`preview` is ONE `Main` process, ONE `Pulumi.run`, ONE `new SeedRun(...)` — so ONE root
scenario, played once (`selectClass` of a single class, sequential). Two `pulumi up` on the SAME stack are
refused by Pulumi's state lock; on DIFFERENT stacks they are SEPARATE processes (separate JVMs, disjoint
worlds). There is never a second live root in one process. This is why the run's `txId` (below) needs no
map: within a run it is the one id every fragment inherits, between runs the process is the isolation. The
in-process concurrency is only the scions under one root, and the `sow` is synchronous — they share the
one `txId` by design (that IS the correlation).
====

*The `SeedRun` carries the run's facts, `txId` included.* `Main` builds a `SeedRun(runMode, parcel, config,
cleanWorktreeRequired, txId)` where `txId = UUID.randomUUID()` — the root-minted transaction id. It is NOT
the drain discriminant (the `RunRole` is, § seed-broker-spec cellar-transactional); it is the AUDIT
correlation thread, carried on every `sow` so a launched scion inherits it and its work ties back to the
run that sowed it. A scion posts it as a narrative tag on its runbook (visible in the graft), never into a
map.

*Layer 2 — the GIVEN bootstraps the gardening (narrated).* Everything else the run needs is built in the
scenario's GIVEN, read as narration: take the `Gardening` OVER the world extension's connection
(`Gardening.over(connection)` — the connection `BaseWorldExtension`/`@SeedRuntime` opened and owns at the
class scope; the GIVEN does NOT boot a second framework), publish the `RunGate` into the registry so the
scions resolve it (`registerService`, not a handler — the ambient run-condition the map's GIVEN names),
build the `Cellar` realisation (`PulumiCellar.fromEnvironment`), name the `Parcel`, publish the `txId`. The
map's GIVEN — "I have access to the open gardening, and a RunGate" — IS this bootstrap; opening the
gardening is a precondition, never a WHEN. (The clean-worktree entry gate is no longer built here: it is
contributed as a FACET amendment and enforced OSGi-side inside the worktree crossing.)

*What crosses layer 1 → layer 2, all through the session store.* The launcher's inbound channel
(`JUnitLauncherCore.run(…, seedSessionStore)`) carries what only `Main` can know: the `SeedRun` (bearing
the `RunMode` + `txId`) via `SessionSeed`, and the `RunRole` (=ROOT for the host root) via `RunRoleSeed` —
seeded together (`SEED.into(run).andThen(RunRoleSeed.into(ROOT))`). A jGiven-ordered
`TestInstancePostProcessor` reads the `SeedRun` and sets it before the GIVEN; `ScenarioCellarExtension`
reads the `RunRole` to decide the drain. JUnit bridges the two store realms — a Jupiter extension's
`ExtensionContext.getStore(ns)` walks the parent chain up to the session-level store the driver seeded
(same namespace parts on both sides), so no bridge code is written. A sown scion opens its OWN launcher
session (a fresh store), so `RunRoleSeed.read` finds nothing there ⇒ defaults to FRAGMENT — correct: a
scion no one declared root does not drain, its tags ride the graft up to the root.

*Why the store, not a static field or the global flag:* the store is the launcher's designed inbound
channel (typed, namespaced, cross-thread-safe), and the amorce is where other execs will carry their own
one-or-two irreducible facts — a generic `seed-bdd` mechanism (a typed key + the seeding consumer + the
post-processor) earns its place, where a static field would be a per-exec one-off and re-reading the
global `isDryRun()` in the GIVEN would couple the scenario to the `com.pulumi` global. This is NOT the
former `HostSeeder`: it carries ONE value and sets it — no executor swap, no model injection, no report
toggle, no probe fan-out. The channel, minus the machinery.

=== The scion twin — `ScenarioInputSeed`, the same channel one realm deeper (2026-07-18)

`SessionSeed` bootstraps the HOST ROOT, host-flat, from `Main`. Two scions — manifests and
incus-provision — need the same shape one realm deeper: their `*RunbookHandler` (in-container) must
hand the played scenario an ACTIVATION INPUT decoded off the trigger (the operator's `ManifestsRunbookInput`
facet, the `IncusRunbookInput` carrying the `@Amendment(SOIL)`). The other four scions ignore their
trigger, so they take no input.

*Why not `SessionSeed` itself.* `SessionSeed` lives in `seed-bdd`'s base package, which is NOT
exported (§ placement — the graft half stays host-flat, never wired in-container); a scion bundle
cannot import it. So the scion twin lives in the exported `scenario-engine` `.container` package the
scions already depend on: `ScenarioInputSeed<T>` (a generic `TestInstancePostProcessor`, keyed +
typed like `SessionSeed`) + `InputReceiver<T>` (the receiver the scenario implements). The front-door
seeds `INPUT.into(input)` onto the launcher session store; the post-processor reads it and sets the
field before the GIVEN — the exact `SessionSeed` mechanism, one realm deeper.

*What it replaced.* The two input-bearing scenarios used a `static AtomicReference INPUT` + a
`seedInput(...)` setter the front-door called before `selectClass` — the inbound counterpart of the
`LAST_RUNBOOK` static (§ seed-broker-spec, the ScenarioOutcome channel). Same cross-membrane-static
fragility, same fix: a typed session-store channel. The value is carried as a LIVE object (no codec) —
the hop is in-realm (front-door and scenario share the bundle loader, the very property the former
"same-loader static" relied on), so nothing crosses the dual-realm membrane.

The three receivers a scion may wear are now uniform siblings, each a field set before the GIVEN by
its own extension: `InputReceiver` (the activation input, this §), `CellarReceiver` (the transactional
cellar, § seed-broker cellar-transactional), and the `@OsgiService` fields (the registry
collaborators, § seed-broker the OSGi-service bridge) — plus `ConsultationSource`, the one PULL twin,
read OUT after the body.
