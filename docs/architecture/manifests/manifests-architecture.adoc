= Manifests Architecture
:toc: left
:toclevels: 3

This is the **canonical reference** for the `manifests` module: how rke2lab synthesizes
Kubernetes manifests from context-aware domain definitions using CDK8s.

It absorbs and supersedes four older documents (nomenclature, system-architecture,
synthesis-architecture, chart-vs-construct). For runtime and policy concerns it links out to
focused companions; see <<related-documentation>>.

[NOTE]
====
**Java packages**: the code referenced here lives under the OSGi manifests domain, split across two
bundles both rooted at `io.seedmatic.rke2lab.manifests`:

* `osgi/domains/manifests/manifests-contract/` — the SPIs and value types (the `…manifests.contract`
  package: `ManifestDomainCatalog`, `ManifestDomainPolicy`, `ManifestAnnotation`, `ManifestLayer`,
  the explode/document/flox SPIs, `profiles/BootstrapIdentity`, `node/NodeEnvContext`).
* `osgi/domains/manifests/manifests-core/` — the implementations and the units (the plain
  `…manifests` package: `AbstractManifestsUnit`, `DefaultManifestSynthesisService`, the `Default*`
  SPI impls, `domain/` registrars, `node/DefaultNodeEnvContext`, `profiles/`, and `units/<domain>/`).

The BDD narration (`ManifestSynthesisScenario`) lives in `osgi/domains/manifests/manifests-bdd/`.
====

== Overview

The manifests module transforms high-level, context-aware domain definitions (networking,
storage, gitops, cluster-api, …) into the **Kubernetes manifests** (`manifests.k8s.yaml`)
installed into the cluster — synthesized from `ManifestsUnit` definitions in a single pass.

[NOTE]
====
The module once emitted a SECOND output tree — systemd unit files + `/srv/host` scripts, the
bootstrap machinery that installed those manifests. That systemd synthesis was *dissolved* when
the node moved to a declarative NixOS substrate (see
link:../nixos-substrate/substrate-model.adoc[target vision]); node unit ordering now lives in the
`nixos/` modules. What remains is the single K8s-manifest synthesis described here.
====

The system uses:

* **CDK8s** for type-safe K8s object creation (the upstream `Construct`/`Chart`/`ApiObject` model)
* a **ThreadLocal `ManifestSynthesisContext`** for injecting runtime configuration into units
* the **Construct tree pattern** for object collection and serialization

== Nomenclature

The word "layer" used to be overloaded across the project. The manifest level now uses a clear,
distinct vocabulary.

[cols="1,2,3",options="header"]
|===
|Term |Lives at |Purpose

|**ManifestsUnit**
|`units/<domain>/<Name>ManifestsUnit.java`
|The atomic build block. A plain object holding metadata whose `doSynthesize(scope, context)` hook
 synthesizes one logical group of K8s resources into a CDK8s scope it is *given* (it no longer *is* a
 `Construct` — see <<manifestsunit>>). Plural because one unit typically emits several `ApiObject`
 resources.

|**ManifestsDomain**
|`ManifestsDomain.java`
|Groups related `ManifestsUnit`s that share a concern (networking, gitops, …) and declares
 cross-domain dependencies. Corresponds to one installer service
 (e.g. `cluster-api` → `rke2lab-cluster-api-manifests.service`).

|**ManifestDomainCatalog**
|`ManifestDomainCatalog.java`
|Single source of truth for domain ID strings (kebab-case). Always use its accessor methods,
 never string literals — see link:manifest-domain-catalog-pattern.adoc[the catalog pattern].

|**Chart**
|created in `DefaultManifestSynthesisService`
|The single synthesis boundary. `Chart` emits the consolidated K8s YAML. See <<chart-vs-construct>>.

|**NodeEnvContext**
|`node/DefaultNodeEnvContext.java`
|The read-only node context (cluster/node identity + network topology) threaded to units at
 synthesis time.
|===

[IMPORTANT]
====
There is **no** separate `Component` class and **no** singular `ManifestUnit`. An earlier design
split each unit into a `Component` (CDK8s Construct) plus a `ManifestUnit` wrapper. Those were
merged: today a single `*ManifestsUnit` class carries the metadata and dependencies and synthesizes
its resources into a `Construct` scope handed to `doSynthesize` (it no longer extends `Construct`
itself). If you find a doc or comment mentioning `Component`,
`ManifestUnit` (singular), `LayerDomain`, or `manifests/layers/`, it is stale.
====

== Core Concepts

[[manifestsunit]]
=== ManifestsUnit

`ManifestsUnit` is the interface every unit implements; `AbstractManifestsUnit` is the base class
that owns the CDK8s coupling via a template method (see
link:manifests-unit-lifecycle.adoc[the unit lifecycle]).

[source,java]
----
public interface ManifestsUnit {
  String manifestUnitId();
  List<String> dependsOnManifestsUnitIds();
  default String outputDir() { /* last segment of manifestUnitId() */ }

  // Template method (final in AbstractManifestsUnit): creates a scope Construct,
  // calls doSynthesize, then emits the group marker.
  void apply(ManifestsUnitContext context);
}
----

A unit's single responsibility is **K8s synthesis**: create `ApiObject` instances in the CDK8s
`scope` it is *handed*, which CDK8s walks into the consolidated `manifests.k8s.yaml`.

==== The pure constructor + doSynthesize hook

A unit no longer *is* a `Construct`. `AbstractManifestsUnit implements ManifestsUnit`; its
constructor is pure metadata initialization (id + dependency ids), and all domain logic lives in the
`doSynthesize(Construct scope, ManifestsUnitContext context)` hook:

[source,java]
----
public final class CiliumConfigManifestsUnit extends AbstractManifestsUnit {

  public static final String MANIFEST_UNIT_ID =
      ManifestDomainCatalog.NETWORKING + "/cilium-config";

  private final PackageMetadataProfile packageProfile =
      new PackageMetadataProfile("networking", "cilium-config");

  public CiliumConfigManifestsUnit() {
    super(MANIFEST_UNIT_ID, List.of());   // pure init — no scope, no I/O
  }

  @Override
  protected void doSynthesize(final Construct scope, final ManifestsUnitContext context) {
    createHelmChartConfig(scope);                  // 'scope' is the parent Construct
    createClustermeshRemoteUsersConfigMap(scope);
  }
}
----

The base `apply(context)` template method creates a fresh `Construct` under
`context.chart()` (named after the unit id), calls `doSynthesize(scope, context)`, then emits a
group marker into the same scope — so CDK8s walks `App → Chart → <per-unit Construct> → ApiObject`
during synthesis. Registrars instantiate units directly with `new XxxManifestsUnit()`; there is no
scope to defer, so the former `ManifestsUnit.lazy(...)` factory and the null-scope legacy
constructor are both gone.

=== ManifestsDomain

`ManifestsDomain` groups related units and declares dependency ordering between domains:

[source,java]
----
public class ManifestsDomain {
  private final String domainId;                       // e.g. "cluster-api" (from catalog)
  private final List<String> dependsOnDomainIds;
  private final List<? extends ManifestsUnit> units;   // field name is "units"
}
----

A domain must define at least one unit (the constructor enforces this) and obtains its `domainId`
from `ManifestDomainCatalog`, never a literal.

[[chart-vs-construct]]
== CDK8s Pattern: Chart vs Construct

CDK8s provides two base classes, and choosing wrong silently breaks the pipeline.

* **`Chart`** is a *synthesis boundary*: each Chart produces its own `*.k8s.yaml` output file.
* **`Construct`** is a *composition node*: it adds resources to its parent Chart's single output.

[IMPORTANT]
====
**Any CDK8s node a unit creates (its per-unit scope, any helper `Construct`) MUST be a `Construct`,
never a `Chart`.** The base creates the per-unit scope with `new Construct(context.chart(), …)`; a
helper that reaches for `Chart` instead breaks the single-output model below.

The only `Chart` in the codebase is the one created in `DefaultManifestSynthesisService`:

* `new Chart(app, "manifests")` — K8s resources
====

=== Why a single Chart

rke2lab uses a **single-Chart model**: all domains feed one consolidated `manifests.k8s.yaml`,
which an exploder then splits by annotation into per-domain directories.

[cols="1,3,3",options="header"]
|===
|Aspect |Single-Chart (current) |Chart-per-domain (rejected)

|Cross-domain deps |Natural — all in one construct tree |Needs CDK8s export/import
|Ordering |Unit dependency graph orders application |Needs explicit Chart ordering
|Output |One file — easy to checksum and version |N files need consolidation
|Routing |Annotations create any directory layout |One Chart = one file = one dir
|===

=== What goes wrong if a unit extends Chart

If a unit (or helper) extends `Chart` instead of `Construct`:

. CDK8s emits a *separate* `N-<id>.k8s.yaml` file with a numeric prefix.
. The exploder only matches `*-manifests.k8s.yaml` / `manifests.k8s.yaml`, so that file is ignored.
. The domain directory under `rke2-manifests.d/` is never created.
. The installer service skips via `ConditionPathExists=/srv/host/rke2-manifests.d/<domain>`.
. The manifests never reach the cluster.

The lesson (learned from the cert-manager incident, commits 18f31fbb5 → 795bc4cf): for
synthesis features, verify the actual output directory, not just that the code compiles.

=== C4 L3: Construct tree at runtime

After synthesis, each unit's `apply()` has created a per-unit `Construct` scope (named after the
unit id with `/` → `-`) owning its K8s `ApiObject`s plus the group-marker `ConfigMap`.

[source,text]
----
App
└─ Chart ("manifests")
   ├─ Construct ("networking-cilium-config")        <- created by CiliumConfigManifestsUnit.apply()
   │  ├─ ApiObject ("helmchartconfig-rke2-cilium")
   │  ├─ ApiObject ("configmap-clustermesh-remote-users")
   │  └─ ApiObject ("group-marker")                 <- local-config ConfigMap, base-emitted
   └─ Construct ("gitops-flux-operator")            <- created by FluxOperatorManifestsUnit.apply()
      ├─ ApiObject ("helmchart-flux-operator")
      └─ ApiObject ("group-marker")
----

CDK8s tracks everything via parent-child registration, so units never store references — they
just `new ApiObject(scope, …)` into the handed-in scope and let `app.synth()` walk the tree.

=== C4 L2b: The manifests-world port (host↔OSGi seam)

The construct tree above is the synthesis _internals_. What the flat host actually calls across the
OSGi frontier is a set of Service-Provider Interfaces published by the `manifests-contract` bundle and
implemented OSGi-side (see xref:#manifests-core-impl[the implementation inventory]). Each SPI owns a
manifests-world guarantee the host must NOT re-implement: the host asks for the operation and
consumes the result, never serialising YAML nor reaching into the synthesis internals itself.

|===
| Port type | Contract

| `ManifestExplodeService`
| SPI splitting one consolidated multi-document YAML into per-resource files under
  `<domain>/<package>/<order>-<kind>-<name>.yml`. The seam the host crosses after synthesis.

| `ManifestExplodeRequest`
| Request record (`consolidatedManifestFile`, `explodedTargetDir`). The domain/package come from the
  `io.seedmatic.rke2lab/domain` + `/package` annotations stamped on each resource; the order prefix is
  kind-derived (`00-` CRDs, `01-` other cluster-scoped, `02-` namespace-scoped).

| `ManifestExplodeResult`
| Result record for `explode(...)`: the `explodedTargetDir` and the `List<Path>` of files written.

| `ManifestAnnotation` + `ManifestLayer`
| The metadata annotation vocabulary, typed as enums (was loose `String` constants on a
  `ManifestAnnotations` record). `ManifestAnnotation` is the annotation KEYS
  (`io.seedmatic.rke2lab/domain`, `/package`, `/layer`, … + `key()` / `packageAnnotations(...)`);
  `ManifestLayer` is the closed, ordered set of reconcile-layer VALUES
  (`CRDS`/`FOUNDATION`/`OPERATORS`/`WORKLOADS`, `value()`) written under `MANIFEST_LAYER`. Typing
  them makes a mistyped key/layer a compile error instead of a silent misroute. Every emitted
  resource carries the domain/package/layer stamp so the explode step can bucket + order it.

| `ManifestDocumentService`
| SPI reading manifest YAML through the manifests world's deterministic parser (sorted keys, literal
  block scalars, the 64 MiB code-point limit, empty-document coercion). Even a READ crosses this
  seam rather than a host-side `ObjectMapper` — the byte-deterministic format is a manifests-world
  guarantee, so the host actualises the parsed structure but never owns the parser.

| `FloxRuntimeAssetService`
| SPI materialising the Flox runtime installer assets the manifests world owns — installer scripts,
  per-environment `.flox` trees, NRI plugin sources, debug tooling. The host asks for the tree to be
  written and reads which environments were discovered; laying out the assets is description, so it
  lives here.

| `ManifestDomainPolicyAware`
| Marker contract for models that explicitly carry manifest-domain policy.
|===

== Synthesis Flow

`DefaultManifestSynthesisService.synthesize(request)` is the orchestrator. The real sequence:

[mermaid]
----
sequenceDiagram

    participant Svc as DefaultManifestSynthesisService
    participant Ctx as ManifestSynthesisContext
    participant App as cdk8s App

    Note over Svc,App: Write files

=== Runtime configuration: ManifestSynthesisContext

Units never receive runtime config through constructors (their constructor is pure metadata init).
Instead the service publishes a `ManifestSynthesisContext` to a ThreadLocal for the duration of one
`synthesize` call, and units read it inside `doSynthesize` via
`ManifestSynthesisContext.current()`:

[cols="1,3",options="header"]
|===
|Slice |Description
|`FloxDebugPolicy` |Per-domain debug toggle for the flox NRI plugin
|`BootstrapIdentity` |Cluster + node identity (clusterName, clusterId, clusterToken, …)
|`NetworkTopology` |CIDRs, interface names, gateway addresses
|`ComponentVersions` |Version pins (cilium, flux, cluster-api operators, …)
|`ImageState` |Stage A → Stage B control-node image identity (alias, fingerprint, checksum, remote)
|===

[source,java]
----
// Inside doSynthesize(...) or a private create*(scope, ...) helper:
final ManifestSynthesisContext ctx = ManifestSynthesisContext.current();
final String version = ctx.componentVersions().clusterApiOperator();
final String cluster = ctx.bootstrapIdentity().clusterName();
----

This is the documented context-access pattern; see
link:../bootstrap/bootstrap-identity-provider.adoc[Bootstrap Identity Provider].

[[ordering-and-coherence]]
=== Visit order and coherence: the resolver-driven type-state

The unit *visit order* — the sequence in which `manifestUnitVisitor.visit(unit, …)` runs during
K8s synthesis — is load-bearing: `Cdk8sApiObjectResolver` lets a consuming unit look up an
`ApiObject` produced by a unit it depends on, and that contract assumes the producer ran first.
So the order must be *producer-before-consumer* — a topological order over the real dependency
edges (`dependsOnManifestsUnitIds` between units, `dependsOnDomainIds` between domains).

That order, and the coherence checks that guard it, are computed by the standalone Apache Felix
`UnitResolver` (in `unitrepo-core`) — **not** a hand-rolled walker. The old depth-first ordering
trio and the constructor validation it relied on have been retired. The design is a *type-state*:

[mermaid]
----
flowchart LR
  ASM["ManifestsDomainRegistry\n(assembled — build-only, never throws\non a malformed graph; only structural\ninvariants: no dup id, no multi-domain\nunit, no empty domain)"]
  RES["resolve()\nthe single coherence gate"]
  COH["CoherentManifestsDomainRegistry\n(the ONLY type exposing visitOrder())"]
  ASM -->|resolve| RES --> COH
----

* **`ManifestsDomainRegistry` (assembled).** Construction only builds indices; it does **not**
  check dependency coherence and never throws on a malformed graph. It exposes `domains()`,
  `manifestUnits()`, `requireDomainIdForManifestsUnit(…)`, and `resolve()` — but **no** visit
  order.
* **`resolve()` is the single coherence-rule coordinator.** It builds a fine-layer `UnitResource`
  universe (`ManifestsUniverse`, domains + units in the resolver's Provide/Require vocabulary),
  resolves it with `UnitResolver` from a synthesis root that `requireAll`s every domain, derives
  the visit order by topologically sorting the *real-dependency* (`require`) edges while excluding
  the `requireAll` containment edges, and runs the cross-domain policy check. It returns a
  `CoherentManifestsDomainRegistry`.
* **`CoherentManifestsDomainRegistry` (coherent)** is the only type that carries `visitOrder()`.
  A caller therefore *cannot* synthesize from an unresolved registry — it does not compile. The
  old build-time fail-fast is replaced by a stronger compile-time guarantee plus one runtime gate.

==== The three coherence checks `resolve()` coordinates

A *coherence rule* is a pure function of the assembled registry (the context every rule reads).
Today three checks run at the gate, with three owners:

[cols="1,2,2",options="header"]
|===
|Check |Owner |How a violation surfaces
|Satisfiability (unknown domain/unit reference) |`UnitResolver` |an unsatisfiable `require` → `ResolutionException` (wrapped as `IllegalStateException`)
|Acyclicity (no dependency cycle) |`ManifestsVisitOrder` topo-sort |no valid linearization → `IllegalStateException` naming the units
|Cross-domain policy |`CrossDomainRule` |an illegal cross-domain dependency → `IllegalStateException` naming the units + domains
|===

The **cross-domain rule** — *a unit in domain A may depend on a unit in domain B only if A
transitively `dependsOn` B* — is enforced by an explicit pure check, **not** by encoding it into
the resolver's filters. Encoding it there was tried and rejected: because each unit enters the
closure via its domain's `requireAll` containment (`cardinality:=multiple`), an offending unit
whose own `require` cannot be satisfied is **silently pruned** from the closure rather than
failing — a misconfigured unit would vanish from synthesis with no error. The governing principle
is that the system must *report* a misconfiguration for a human to fix, never silently
auto-resolve it. The dependency target genuinely exists, so the violation is invisible to
resolution itself: it is a *policy above resolution*, hence an explicit rule that throws.

`CrossDomainRule` is the exemplar of the "pure function of the assembled registry" shape; the
other two checks have different owners and shapes, so a shared `CoherenceRule` abstraction is
deliberately deferred until a third same-shaped policy rule appears (rule-of-three). The visitor
seam (`ManifestsUnitVisitor` / `ManifestsUnitContext` / `Cdk8sApiObjectResolver`) is unchanged by
all of this — only the *source* of the order moved, from a DFS walker to the resolver wiring plus
a topological sort.

== Delivery to the node

The synthesised, exploded per-resource tree is delivered to the node's
`server/manifests` directory (via the scion → `manifestsRoot` → jsync promotion), where RKE2
auto-applies it. A unit no longer emits systemd installer services: the former
`synthesizeSystemdUnits` / `SystemdService` `/srv/host` installers were dissolved when the node
moved to a declarative NixOS substrate (see
link:../nixos-substrate/substrate-model.adoc[the NixOS node-substrate target vision]). The full
runtime journey is covered in link:manifest-apply-flow.adoc[Manifest Apply Flow].

=== Flox runtime unit

[cols="2,3",options="header"]
|===
| Type | Role

| `FloxControllerManifestsUnit`
| The `AbstractManifestsUnit` deploying the flox-controller node-agent (the companion that
  _provisions_ what the NRI plugin injects — see `github:seedmatic/flox-controller`): the `FloxEnv`
  CRD plus the controller DaemonSet + cluster RBAC (ServiceAccount / ClusterRole / ClusterRoleBinding).
  The DaemonSet + RBAC sit on the `operators` layer (the controller healthy before workload
  `FloxEnv` CRs); the `CustomResourceDefinition` is forced to the `crds` layer by kind. Its
  namespace (`rke2lab-system`) is created in the `foundation` layer
  (`ClusterRuntimeNamespaceManifestsUnit`) so it exists before this operators-layer SA/DaemonSet —
  a namespace that later layers depend on belongs early (else operators↔workloads deadlock). The CRD is single-sourced from the flox-controller flake (its `controller-gen`
  output, exposed as `flox-controller-crds` and staged onto the synthesis classpath under `/crds/` by
  `seedMasterJar` / `nix run .#stage-flox-controller-crd`) and emitted verbatim via
  `UpstreamYamlInclusion` — never re-modelled or vendored. The DaemonSet runs the baked
  `io.seedmatic.flox-controller` image (`FloxDebugPolicy#floxControllerImage`, `IfNotPresent`) on
  nodes labelled `flox.seedmatic.io/enabled` (`ManifestAnnotation#NODE_FLOX_RUNTIME_LABEL`), mounting
  the host `/nix` + containerd socket so it realises closures + GC-roots and imports carrier images.

| `FloxCatalogManifestsUnit`
| The `AbstractManifestsUnit` binding the flox-controller's nix-flake catalog to a Flux source. The
  workload flox packages (kdns, headscale, …) live in a nix flake maintained directly at the ROOT of a
  dedicated `flox-catalogue` branch (NOT the per-cluster rendered `manifests/<slug>` branch). It emits a
  `GitRepository` tracking that branch
  (same repo + GitHub App auth) so Flux exposes the flake as an in-cluster tarball artifact, and a
  `FloxCatalog` (`catalogue`) whose `sourceRef` points at it — the controller resolves
  `floxcatalog:rke2lab-system/catalogue#<output>` install refs against it. On the `operators` layer
  (Ready before workload `FloxEnv`s resolve their flake refs).

| `FloxEnvManifestsUnit`
| The `AbstractManifestsUnit` emitting the workload `FloxEnv` CRs the flox-controller realises on
  each node (kdns for networking, plus the headscale/tailscale/headplane mesh family).
  Each env installs its package from the `FloxCatalogManifestsUnit` catalog via a
  `floxcatalog:catalogue#<output>` ref (same namespace, `rke2lab-system`); its `folder` is the GC-root
  category the NRI plugin keys on (`<base>/networking/kdns`). Flavor is a single logical env switched
  by the networking debug toggle (`FloxDebugPolicy.networkingEnabled`): prod ships stripped `#kdns`,
  debug ships delve-wrapped `#kdns-debug`. On the `workloads` layer (after the catalog on
  `operators`).

| `FloxWebhookManifestsUnit`
| The `AbstractManifestsUnit` serving the flox-controller's pod-mutating webhook: a
  `kubernetes.io/tls` Secret (`flox-controller-webhook-tls`), the `flox-controller-webhook` Service
  fronting the DaemonSet pods (the mutation is stateless → any pod serves, so no separate
  Deployment), and the `MutatingWebhookConfiguration` routing pod `CREATE` to it. The serving cert is
  minted by the cluster-pki `server-ca` and revealed onto the synthesis as `WebhookServingMaterial`
  (see xref:../cluster-api/deterministic-cluster-access.adoc[deterministic cluster access]); the
  Service name/namespace must match the cert's SAN. `failurePolicy: Ignore` + system-namespace
  exclusion bound the blast radius; the unit renders only when the serving material is present (a
  real seal), matching `FloxControllerManifestsUnit`'s `--enable-webhook` guard. On the `operators`
  layer.
|===

== Anti-Patterns

❌ **Create `ApiObject`s with a parent other than the handed-in scope.** Passing `chart` (or a
helper's arbitrary scope) instead of the `Construct scope` given to `doSynthesize` drops the unit's
resources out of its grouping node. Create them on that `scope`.

❌ **Do domain logic in the constructor.** The constructor is pure metadata init (`super(id, deps)`);
create `ApiObject`s in `doSynthesize`, never at construction time.

❌ **Extend `Chart` from a unit helper.** See <<chart-vs-construct>> — it produces an orphaned output
file the exploder ignores.

❌ **Hardcode domain ID strings.** Use `ManifestDomainCatalog` accessors. See
link:manifest-domain-catalog-pattern.adoc[the catalog pattern].

== Adding a New ManifestsUnit

. Create `units/<domain>/<Name>ManifestsUnit.java` extending `AbstractManifestsUnit` with a no-arg
  constructor that calls `super(MANIFEST_UNIT_ID, deps)`. Derive `MANIFEST_UNIT_ID` from a
  `ManifestDomainCatalog` accessor (e.g. `ManifestDomainCatalog.STORAGE + "/minio"`).
. Override `doSynthesize(Construct scope, ManifestsUnitContext context)` and create K8s `ApiObject`s
  on `scope`, stamping `PackageMetadataProfile.packageAnnotations(...)` on each so the exploder routes
  them.
. Register the unit in its domain (via the domain's `ManifestsDomainRegistrar`), instantiating it
  directly with `new <Name>ManifestsUnit()`. If it depends on
  another unit, declare that in `dependsOnManifestsUnitIds`; if the dependency lives in another
  domain, that domain must be reachable through `dependsOnDomainIds` (the cross-domain rule — see
  <<ordering-and-coherence>>), or `resolve()` will reject it.

== Troubleshooting

=== Domain directory missing in rke2-manifests.d/

. Confirm no unit/helper `extends Chart` (must be `Construct`) — see <<chart-vs-construct>>.
. Confirm `PackageMetadataProfile` annotations are stamped on every `ApiObject`; without them the
  exploder routes to `default/unknown/`.
. Confirm the domain is enabled in policy — see
  link:manifest-conditional-inclusion.adoc[Manifest Conditional Inclusion].

=== Multiple `*.k8s.yaml` files in the synth outdir

Numeric-prefixed files (`2-…k8s.yaml`) mean some Construct accidentally extends `Chart`. Fix the
base class; only the single top-level `Chart ("manifests")` may exist.

=== Systemd service skipped (ConditionPathExists)

The manifests were not exploded to the expected directory — almost always the Chart-vs-Construct
bug above. Verify the directory exists before debugging the unit file.

=== Synthesis fails with "manifest closure is incoherent: …"

`resolve()` could not resolve the unit/domain graph — an `dependsOn…` references a unit or domain
that no enabled domain provides. The wrapped cause is the resolver's `ResolutionException`. Fix the
offending `dependsOnManifestsUnitIds` / `dependsOnDomainIds`, or enable the domain that provides the
missing dependency. See <<ordering-and-coherence>>.

=== Synthesis fails with "Cyclic manifest unit dependency detected: …"

Two or more units depend on each other (directly or transitively), so no producer-before-consumer
order exists. The message names the units on the cycle. Break the cycle by removing one
`dependsOnManifestsUnitIds` edge.

=== Synthesis fails with "… crosses domains without a matching domain dependency …"

A unit in domain A declares a `dependsOn` on a unit in domain B, but A does not (transitively)
`dependsOn` B. This is the cross-domain rule (<<ordering-and-coherence>>). Either add the missing
`dependsOnDomainIds` edge from A to B, or move the unit so the dependency stays within reachable
domains. The error names both units and both domains.
