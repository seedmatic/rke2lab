= Systemd D-Bus Adapter Architecture
:toc: left
:toclevels: 3

== Overview

The systemd adapter is how the bootstrap gate learns the master node's systemd
state. It is an *OSGi edge* that runs *seed-outcluster-side* (in the OSGi world inside
`seed-outcluster` and the CLIs) and opens a *dbus-over-TCP* connection TO the node. It
is NOT a service that runs on the node.

* `DbusSystemdProbe` (bundle `dbus-systemd-edge`) is the single door toward
  systemd: it opens an anonymous-SASL DBus connection to `tcp:host=…,port=…`, reads
  live state through `de.thjom.java.systemd`, and translates it into the pure
  `SystemdStatusSnapshot`. It implements the domain seam `SystemdRuntimeProbe` and
  is published by SCR; the host resolves it from the registry.
* On the node, the only systemd-side surface is a plain dbus-over-TCP *system bus*
  (`rke2lab-dbus-tcp-system-bus.service`) that exposes `org.freedesktop.systemd1`
  over TCP. There is no adapter process on the node — the edge is the client.
* `DbusTcpSpecialist` (bundle `systemd-core`) is the doctor domain's systemd
  diagnostician: it reads the captured snapshot and, on a connection-refused
  symptom, prescribes restarting the adapter unit.
* `SystemdAdapterScenario` / `SystemdRunbookHandler` (bundle `systemd-bdd`) are the
  in-container scion the host grafts (the "the systemd adapter is launched" step).

[NOTE]
====
*History (dissolved).* An earlier design placed a *node-side Spring Boot HTTP
service* here — `SystemdAdapterApplication` + `SystemdStatusController` exposing
`/status/systemd` + `/healthz/systemd`, backed by a
`DbusSystemdStatusSnapshotProvider`, that Pulumi polled over HTTP. That HTTP surface
and its Spring Boot module are gone: dbus-over-TCP is plain sockets (playable in
OSGi), so the contact migrated INTO the OSGi world as `DbusSystemdProbe`, reached
through the `SystemdRuntimeProbe` seam — no HTTP, no controller, no node-side
service. The full before/after of that move is
link:../osgi/dbus-systemd-edge-spec.adoc[the dbus-systemd-edge spec].
====

== Runtime placement and ownership

* *The edge is seed-outcluster-side, OSGi.* `DbusSystemdProbe` lives in the OSGi world
  (`dbus-systemd-edge`), embedding the dbus-java stack as nested jars on its own
  `Bundle-ClassPath` so the transport `ServiceLoader` discovers `TcpTransportProvider`
  inside one classloader. Only Pulumi stays irreducibly host; this was the first
  edge extracted and migrated into OSGi.
* *systemd introspection is local to the node.* The node runs the dbus-TCP system
  bus; the edge reaches it over TCP. Knowledge runs downward: the systemd domain
  does not know a doctor auscultates it, nor that it belongs to a control-node.
* *The control-node (`seed-outcluster`) mediates by PORTS.* It is the one place that
  knows BOTH `systemd` and `doctor`, so it makes the systemd domain speak (edge →
  `systemd-contract`) and — on a symptom — the domain itself consults the doctor
  through the neutral port; the host reaps only a coarse verdict.

== Port contract — the contract types

Review question: what crosses the host↔OSGi frontier, and does it stay free of host
types?

The adapter's normalized surface is declared as `systemd-contract` types (an
installed bundle wired bundle-to-bundle inside the OSGi world, so neither side leaks
its own config type across):

[cols="2,3",options="header"]
|===
| Port type | Contract

| `SystemdProbeRequest`
| The pure input crossing the readiness seam — `dbusHost`, `dbusPort`, `nodeName`,
  `imageBuilderHost` — a record with a normalizing canonical constructor
  (blank/absent fields fall back to `localhost` / `0` / `unknown`). It is COMPOSED
  OSGi-side by `SystemdAdapterScenario`, not filled by the flat host: the node's
  mDNS FQDN (`<cluster>-<node>.local`) and the `<cluster>-nixos` host DERIVE from
  the netplan `ClusterNetworkBlueprint` (a pure identity→topology function, the
  single source of network names), while `dbusPort` is a fixed systemd SERVICE
  constant — a port is not identity-derived, so it stays with the service, never in
  the blueprint. So no host config type crosses and no network host is hard-coded.
  The former fixed `localhost:0` marker survives only for an offline play.

| `SystemdRunbookInput`
| The systemd runbook trigger's input — one `@Amendment(FACET)` role, the stable
  cluster/node `Identity` the host contributes AMBIENT (mirroring the incus FACET).
  The scenario derives the network blueprint from that identity to compose the
  `SystemdProbeRequest` above, so the host names only the neutral identity (JSON on
  the FACET role), never a systemd or netplan type. `Optional` / EMPTY is the honest
  model of an unamended (offline) play — the scenario then falls to the marker.

| `SystemdRuntimeProbe` / `SystemdStatusSnapshot`
| The readiness seam itself (`awaitReady(request, budget)` → snapshot) and the pure
  fact it produces. `DbusSystemdProbe` is the sole producer; the port owns the type.
  A `SystemdUnitController` egress face is a latent, future extension (the same
  `systemd1.Manager` already exposes `RestartUnit`).
|===

== Readiness — awaiting convergence, not a one-shot probe (2026-08)

`SystemdRuntimeProbe.awaitReady(request, budget)` is the systemd twin of the
cluster's `ClusterReadinessContact.awaitReady` (§
link:../osgi/cluster-edge-spec.adoc[cluster-edge-spec], readiness-await). It does
NOT snapshot the adapter once; it AWAITS convergence over the shared `ReadinessAwait`
driver (`osgi/runtime/readiness-await`): a two-tier `ReadinessBudget` — a CONNECT
deadline to reach the dbus-over-TCP endpoint (absorbing a cold boot), then a READY
deadline to converge once reachable. The edge opens ONE dbus connection, subscribes
the manager's `JobRemoved` signal, and wakes on each job completion to re-check the
target's state rather than polling blind — falling back to a bounded poll if no
signal arrives. On the connect deadline it throws, surfaced as an adapter-not-ready
snapshot. This is what fixed the regression where a checkpoint probed DURING the grow
failed the instant the node was not yet up.

The budget is CONDITIONED by the grow's cold/warm `Growth` (§
link:../atlas/seed.adoc[atlas/seed], the readiness beat): a WARM master gets a short
fail-fast budget, a COLD bring-up the patient one. The deadline VALUE lives in code
(`@ReadinessDeadlines` on the scenario `@Test`, the visible default) and is tuned per
checkpoint from `rke2lab:readiness:` under the `systemd-adapter` checkpoint slug (§
link:../osgi/seed-broker-spec.adoc[seed-broker-spec], `ReadinessOverrides`).

== Usage patterns

✅ *DO reach systemd through the `SystemdRuntimeProbe` seam.* The host
`awaitService(SystemdRuntimeProbe.class)` and calls `awaitReady`; it never imports
`DbusSystemdProbe` or any dbus-java type.

✅ *DO name the adapter unit through `SystemdUnitId`.* The manifests producer, the
`DbusTcpSpecialist`, and the tests all import the one typed id
(`SystemdUnitId.DBUS_TCP_SYSTEM_BUS`) — importing it draws the relationship in the
graph; a duplicated string literal hides it.

❌ *DON'T add an HTTP status endpoint or a node-side adapter service.* That was the
dissolved Spring Boot model. The edge is the dbus-over-TCP client; the only node
surface is the dbus-TCP system bus itself.

❌ *DON'T make the doctor open the dbus door.* The specialist reads the captured
`SystemdStatusSnapshot` (a fact off the stack) and reasons; only the edge contacts
systemd.

== Troubleshooting

[cols="1,2",options="header"]
|===
| Symptom | Cause / fix

| `awaitReady` throws on the connect deadline
| The dbus-over-TCP endpoint was unreachable for the whole CONNECT budget — the node
  is not up, or `rke2lab-dbus-tcp-system-bus.service` is not running / not listening
  on the expected port. Confirm the unit is active on the node and the
  `SystemdProbeRequest` host/port match.

| The probe connects but never reads ready
| The mandatory target (`rke2lab.target`) has not converged, or units keep failing.
  Inspect the snapshot's failed-unit count; on a connection-refused symptom the
  `DbusTcpSpecialist` prescribes restarting the adapter unit.

| `TcpTransportProvider` not found
| The dbus-java transport `ServiceLoader` did not resolve — the nested jars must be
  on `dbus-systemd-edge`'s own `Bundle-ClassPath` so discovery happens inside the
  one bundle classloader (never system-exported).
|===
