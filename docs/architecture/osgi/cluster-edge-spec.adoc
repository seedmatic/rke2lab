= cluster-edge — the readiness contact, put in its place
:toc: left
:toclevels: 3

[NOTE]
====
*Status:* IMPLEMENTED (2026-06-26). The fourth external edge of the
link:../patterns/frontier-playability-model.adoc[frontier-playability model], after
link:pulumi-edge-handoff.adoc[pulumi-edge], link:ssh-to-age-edge-handoff.adoc[ssh-to-age-edge] and
link:dbus-systemd-edge-spec.adoc[dbus-systemd-edge]. It mirrors the dbus-systemd-edge shape: a single
class shells the external tool; everything else consumes a port.

Built in four green steps (Option B): `cluster-contract` (`ClusterReadinessPhase` rapatriated from
doctor-contract, `ClusterSchemaRef`, `ControllerRef`, the `ClusterReadinessContact` contract);
`cluster-core` swaps loose literals for `ClusterSchemaRef`; `cluster-edge`; `cluster-bdd`.

*As shipped (re-baselined) — the edge is fabric8-typed and the host orchestration dissolved into a
scion.* The Option-B exploration below reasoned about a `KubectlClusterContact` shelling `kubectl` over
`ProcessBuilder` and a host `ProductionClusterReadinessProbe` orchestrating the phases. Neither
survives verbatim. The shipped edge is `Fabric8ClusterContact` — a `@Component(service =
ClusterReadinessContact.class)` in `cluster-edge` that reaches the API through a typed fabric8
`KubernetesClient` built from the published kubeconfig (NO `kubectl` shell, no embedded jars). The two
point-in-time booleans collapsed into one awaiting verb — `ClusterReadinessContact.awaitReady(kubeconfig,
List<ControllerRef>, ReadinessBudget) → ClusterReadinessSnapshot` (see the readiness-await note below).
And the host readiness orchestration MOVED WHOLE into the `cluster-bdd` scion: `ClusterReadinessScenario`
(the jGiven metier, `@OsgiService`-injecting the contact) grown by `ClusterRunbookHandler` behind the
broker door. The former host types — `ClusterBootstrapReadinessVerifier`, `ProductionClusterReadinessProbe`,
`ClusterReadinessStage`, `SeedNodeBootstrapWatcher` — are DELETED, not thinned. The before/after below is
kept as the design rationale that motivated the extraction; the shipped shape is the scion, not a
host-side probe.

The cluster domain already has its *core* — `ClusterSpecialist`, a `Specialist` `@Component` in
`osgi/cluster/cluster-core`, contributed to the doctor's DS-collected roster (the specialist
distribution, commit `b2a65de0`). What was still missing when this was written was the *port* and the
*edge*: the cluster readiness contract, and the live contact that satisfies it. They lived in
`seed-outcluster` then, folded into the host orchestration. This document extracts them.

This is a *before / after* document. Each section states one problem, shows it, and shows the
resolution. The "before" is the host-trapped state of the 2026-06-26 surface inventory (design
rationale); the as-built end-state is the fabric8 edge + the `cluster-bdd` scion summarised above and in
§ <<the-cluster-scion-scenario>>.
====

Four problems, each a section below:

* *No cluster port.* The `ClusterReadinessProbe` contract lives in `exec/seed-outcluster/.../controlplane/bdd/`
  — a contract stranded in the host, not a domain membrane.
* *The phase enum squats the doctor.* `ClusterReadinessPhase` lives in `doctor-contract`, coupling the
  doctor domain to cluster readiness vocabulary it has no business owning.
* *The kubectl contact is trapped in the host.* `ClusterBootstrapReadinessVerifier` shells kubectl
  inline in `seed-outcluster`, mixed with host orchestration that genuinely belongs there.
* *SchemaRef literals are loose strings.* `"cluster/api/v1"`, `"cluster/kubeconfig/v1"` … are spelled
  inline in `ClusterSpecialist`, the same name-mismatch hazard `SystemdUnitId` cured for systemd.

== Problem 1 + 2 — the port does not exist, and its phase enum squats the doctor

`ClusterReadinessProbe` (the contract) sits in `seed-outcluster/controlplane/bdd/`; `ClusterReadinessPhase`
(its vocabulary) sits in `doctor-contract`. Neither is where a domain's contract belongs — and the
doctor should not carry another domain's phase enum (it is latent debt: the doctor depends on cluster
readiness vocabulary, the wrong direction).

*Resolution — a real `cluster-contract` (`type=contract`), mirroring `systemd-contract`.* It carries:

* `ClusterReadinessProbe` — the contract interface (moved from the host `bdd/` package).
* `ClusterReadinessPhase` — moved out of `doctor-contract` into its owning domain. Blast radius: 5
  `seed-outcluster` files re-import (no `osgi/` file outside doctor-contract references it — the sealing
  holds); the doctor stops depending on cluster vocabulary.
* `ClusterSchemaRef` — a phase↔`SchemaRef` mapping enum (the `SystemdUnitId` move): the four
  `"cluster/*/v1"` literals become typed constants, single-sourced, no name drift.
* `ControllerRef` — one required controller (kind/name/namespace), the projected unit the readiness
  reasoning checks; the host projects the policy into a `List<ControllerRef>`, the reasoning never
  sees the policy.
* `ReadinessInput` — the minimal input a readiness run reasons over ({`kubeconfigPath`, `timeout`}).
  The host derives it from its fat bootstrap config; the cluster reasoning depends on this port
  alone, no host type — so the verifier's per-phase checks take a `ReadinessInput`, not a
  `BootstrapConfig`.

`cluster-contract` depends only on `domain-annotations` + `doctor-contract` (for `Observation`/`Symptom`/
`SchemaRef`, the doctor's value vocabulary the probe speaks). It is `type=contract`: an installed bundle,
wired bundle-to-bundle inside the OSGi world, like every domain `-contract`.

== Problem 3 — the kubectl contact, trapped in the host

`ClusterBootstrapReadinessVerifier` (seed-outcluster) is 556 lines that mix three different concerns:

* *the external contact* — `runCommand` (ProcessBuilder) shelling `kubectl get --raw=/readyz`
  (API_READY) and `kubectl wait --for=create` + `kubectl rollout status` (CONTROLLERS_EFFECTIVE);
* *host orchestration that cannot move* — `SeedNodeBootstrapWatcher.waitForBootstrapPreconditions()`
  (the systemd/bootstrap gates), `policy.manifestLink()` → required controller refs, the
  `VerificationResult` output projection, the NIO kubeconfig file poll (KUBECONFIG_PUBLISHED — the
  file is written by host bootstrap, not by kubectl);
* *the projection into doctor facts* — mapping a phase failure to a `Symptom`/`Observation`.

Only the first concern is an edge. The cluster contact is `kubectl` over `ProcessBuilder` — pure JDK,
*zero embedded jars* (simpler than dbus-systemd-edge, which embedded three for ServiceLoader
transport discovery).

*Resolution — a `cluster-edge` bundle (`type=edge`), a `@Component` that makes the kubectl contact and
nothing else.* The host keeps the bootstrap gates, the policy projection, the kubeconfig poll, the
`VerificationResult` — it *composes* the edge in for the two kubectl phases.

The one design choice this extraction forces is *the grain of the contract the edge implements*. Two
shapes, figured below.

[IMPORTANT]
====
*Decided (2026-06-26): Option B* — the edge is a low-level kubectl contact; the host projects into
`Observation`. Option A is kept below only as the rejected alternative and the reasoning.
====

=== Option A — edge implements the phase-probe contract (coarse, minimal refactor)

`cluster-edge` implements the existing `ClusterReadinessProbe` (`probe(config, phase) → Observation`),
but only answers the two kubectl phases; the host composes KUBECONFIG_PUBLISHED (NIO poll + systemd
gate) itself and delegates the other two to the injected edge.

honours 2 of the 3 phases, an asymmetry a reader must learn.

=== Option B — edge is a low-level kubectl contact (fine, purer)

`cluster-edge` exposes a fine contact — `boolean isApiReady(kubeconfig)` /
`boolean areControllersEffective(kubeconfig, List<ControllerRef>)` — that knows kubectl and nothing
about phases or `Observation`. The host's `ProductionClusterReadinessProbe` orchestrates all three
phases, calling the edge for the two kubectl ones and projecting the results into `Observation` itself.

[IMPORTANT]
====
*Contract shape: the edge receives already-projected `ControllerRef`s — it never
sees the host policy.* A `verifyRequiredControllers(kubeconfig, policy,
timeout)` shape would mix two concerns: deriving the required controllers from the policy facet
(`requiredControllers(policy)` reads HA/networking/storage/… enabled flags) AND shelling
`kubectl wait`/`rollout`. Only the second is the contact. So the *host* keeps the policy→refs
projection and passes the resulting `List<ControllerRef>` to the edge; the edge does pure kubectl over
refs it is given. `ControllerRef` (kind/name/namespace) becomes a neutral record of `cluster-contract` —
the contact vocabulary, free of any policy type. `isApiReady` needs only the kubeconfig path. This is
the clean single-door edge: it imports one port, contacts one target, and carries no host type.
====

[NOTE]
.Update (readiness-await, 2026-08): the contact AWAITS, and the wait moved into the edge
====
The two point-in-time booleans (`isApiReady` / `areControllersEffective`) collapsed into ONE
awaiting call — `ClusterReadinessSnapshot awaitReady(kubeconfig, List<ControllerRef>,
ReadinessBudget)`. The reason: the BDD migration had left the checkpoint one-shot (the host's retry
loop was cut), so a gate probed during `grow` failed the instant the cluster was not yet up. The
patience now lives in the edge, bounded by a two-tier `ReadinessBudget` (a pure-JDK value from
`osgi/runtime/readiness-await`): the reach retries `/readyz` until the *connect* deadline (a cold
boot / fresh image re-seed lives here), then — once the API answers — fabric8
`waitUntilCondition` awaits every required controller rolling out until the *ready* deadline. The
shared `ReadinessAwait` skeleton owns the connect-retry + two-deadline control flow (the systemd
edge uses it too, over dbus `JobRemoved`); the edge injects only its connect + convergence.

`awaitReady` returns a `ClusterReadinessSnapshot` (`apiReady`, `controllersEffective`) rather than
throwing for a not-ready cluster — the twin of `SystemdStatusSnapshot`: the checkpoint's phase steps
READ the snapshot's facts (fail-fast on the api phase, then the controllers phase) instead of each
making a contact. The deadlines are declared where they read, on the `@Test`
(`@ReadinessDeadlines(connect, ready)`), and are overridable from the stack config; the
`ReadinessBudgetExtension` resolves the effective budget and injects it before the body.
====

*For:* the edge is purely "make the contact" — it never touches a doctor fact, the cleanest single-door
edge (matches the coupling signature: an edge sees ONE port + contacts ONE external target); the
phase→`Observation` projection stays whole, in one host place. *Against:* a wider contract surface
(two-plus contact methods vs one `probe`); the existing `ClusterReadinessProbe` contract is reshaped, more
call-site churn.

[NOTE]
====
*Recommendation: Option B.* It is the same discipline dbus-systemd-edge settled on — the edge makes the
contact and returns a raw fact; the *translation into a doctor fact* is the host's job, not the edge's
("doctors do not open doors", and edges do not diagnose). The asymmetry of Option A (edge honours 2 of
3 phases, edge knows the `Observation` projection) is the smell B removes. The cost (a slightly wider
contract) is the honest shape.
====

== Problem 4 — SchemaRef literals are loose strings

`ClusterSpecialist` spells `SchemaRef.of("cluster/kubeconfig/v1")`, `"cluster/api/v1"`,
`"cluster/controller/v1"`, `"cluster/other/v1"` inline — the exact loose-literal hazard
`ManifestDomainCatalog` and `SystemdUnitId` exist to prevent. *Resolution:* the `ClusterSchemaRef` enum
in `cluster-contract` single-sources them; `ClusterSpecialist` references the typed constant. cluster-core
gains a dependency on cluster-contract (its own domain's port — the natural direction).

== The whole, after (as shipped)

The as-built shape differs from the four-step plan in one load-bearing way: the readiness orchestration
is NOT a host `ProductionClusterReadinessProbe` composing the edge — it is the `cluster-bdd` scion
(`ClusterReadinessScenario`), which `@OsgiService`-injects `ClusterReadinessContact`, calls `awaitReady`,
and consults the doctor ITSELF on a failing phase (Fork B). The host only sows the scion and reaps a
coarse verdict.

== Build order (each step green before the next)

1. *cluster-contract* — create the contract module; move `ClusterReadinessPhase` from doctor-contract (re-import
   the 5 seed-outcluster files); add `ClusterSchemaRef`; move the probe/contact interface from `bdd/`. Build green.
2. *cluster-core* — swap the loose literals for `ClusterSchemaRef`; add the cluster-contract dep. Green.
3. *cluster-edge* — create the `@Component` edge, extract the kubectl contact from the verifier (the
   chosen grain). Mirror `dbus-systemd-edge` (pom + bnd `type=edge`, no embedded jars). Green.
4. *cluster-bdd + seed-outcluster* — the readiness orchestration became the `cluster-bdd` scion
   (`ClusterReadinessScenario`, `@OsgiService`-injecting `ClusterReadinessContact`), grown by
   `ClusterRunbookHandler`; the host `ProductionClusterReadinessProbe`/`ClusterBootstrapReadinessVerifier`
   were deleted (not thinned), and `seed-outcluster` now sows the scion through the broker. An in-container
   boot test proves the `Fabric8ClusterContact` `@Component` resolves and the contact works.

== The cluster SCION scenario (the metier definition — SHIPS today)

In the ClusterSeed vision (link:../bdd/bdd.adoc#clusterseed-scenario-map[the scenario map]) cluster is a
graft-caller: the host step "the cluster becomes ready" (nested under resources) sows THIS scenario
in-container and grafts its scion. This one SHIPS — `ClusterReadinessScenario` in the `cluster-bdd`
bundle, grown by `ClusterRunbookHandler` behind the broker's host→scion door. The host speaks gardening; this scenario speaks the cluster
metier (readiness · phase · observation).

[listing]
----
SCENARIO: the cluster's control plane is ready
  GIVEN the ClusterReadinessContact (edge) — resolved from the registry, inert if the RunGate is closed
  WHEN each ClusterReadinessPhase is probed (api reachable, controllers effective)
  THEN the cluster is ready — every phase observed healthy
    AND on a failing phase the domain CONSULTS the doctor ITSELF (not the host), transversally
----

The contact is resolved by `context.getServiceReference(ClusterReadinessContact.class)` — the live
`Fabric8ClusterContact` bundle when the `RunGate` is open, inert when closed (the real kubectl edge stays
home, the scion renders PENDING via E9 — NOT a host-side fake; see
link:seed-broker-spec.adoc#live-preview-rungate[the RunGate section]). Fork B holds: the checkpoint OWNS
its consult — the domain consults the doctor itself on a failing phase, the host never does. The host reaps
only a coarse verdict + the grafted scion (the `VerificationResult` it derives is from the scion's coarse
SUCCESS/FAILED, never from a domain phase internal).
