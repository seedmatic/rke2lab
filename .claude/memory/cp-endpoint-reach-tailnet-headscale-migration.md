**CAPI reach le VIP workload PAR LE TAILNET.** Deux reaches (gravé `docs/architecture/cluster-api/management-workload-topology.adoc#cp-endpoint-reach`) : self-adoption = `kubernetes.default.svc` in-cluster ; workload reach = pod CAPI mgmt → VIP `10.80.<w>.10` via l'operator tailscale (Connector subnetRouter annonce le supernet vmnet /18 + egress ProxyGroup L4 pass-through, TLS end-to-end, client-cert préservé = plan A, PAS apiServerProxy/impersonation). Deux verrous déclaratifs ndh `manage-tailnet` dérivés du segment blueprint `"vmnet"` : autoApprovers.routes (tag:k8s) + ACL accept dst. **Prouvé live 2026-09-12** (bioskop → 10.80.7.10:6443, DERP puis direct). Décisif : nikopol itinérant/CGNAT ⇒ le tailnet est le SEUL transport cross-host (shared-L2 et OVN uplink morts).

**Migration souveraine SaaS→Headscale = DIFFÉRÉE, tranchée (2026-09-12)** — gravé `#sovereign-headscale-reach`. Clusters internal-only ⇒ end-state = control-server self-hosted. Blocage : la boucle de réconciliation de l'operator est couplée à l'**API admin Tailscale `/api/v2` + OAuth** (client Go `tailscale.com/client/tailscale/v2`), qu'AUCUNE release Headscale (≤ v0.29.3) n'implémente (son API = v1 HTTP, forme différente ; gRPC en retrait). **Headscale 0.30.0 (non publiée au 2026-09-12) ferme le gap PAR DESIGN** : porte `/api/v2`+OAuth "reusing Tailscale wire shapes" pour que l'operator+Terraform pilotent Headscale sans patch (PR #3334) ; CI PR #3337 prouve le VRAI operator en k3s contre Headscale : self-register + egress Connector + ingress + ProxyGroup (= nos 2 primitives). Retarget = **une** var `OPERATOR_LOGIN_SERVER` (pointe le control-plane tsnet ET le base-URL /api/v2) + OAuth client minté par Headscale (scopes `devices:core`+`auth_keys`, `tag:k8s-operator` owns `tag:k8s`). **Conséquence design : rendre le login-server PARAMÉTRABLE dans les manifests egress → flip de config, pas réécriture.** apiServerProxy non testé contre Headscale mais on ne l'utilise pas. **Fork controller sur `hibare/headscale-client-go` REJETÉ** (duplique 0.30.0, cible l'API v1 que HS remodèle) — dernier recours seulement si sovereign exigé sur release stable avant 0.30.0.

**Plan A = 3 pièces à coder** (SaaS d'abord) : (1) egress `ManifestsUnit` = `ProxyGroup type: egress` (ns tailscale-system) + Service `<w>-apiserver` annoté `tailscale.com/tailnet-target-ip: 10.80.<w>.10`, modelé sur `units/tailscale/TailscaleManifestsUnit.java`, VIP dérivé du blueprint ; (2) `tls-san += <w>-apiserver.tailscale-system.svc.cluster.local` dans `ClusterApiCrRenderer.rke2ControlPlane` (controlPlaneEndpoint reste le VIP) ; (3) override `<cluster>-kubeconfig.server = https://<FQDN egress>:6443` dans le `rke2-adoption-controller`.

**SESSION 2026-09-12 progress** : (a) drift reach fixé & poussé `8dcfe8642` — Connector tailscale + 3 pools LB cilium (`cluster`=lbCidr, `vip`=vipCidr, `lan`=lanLbCidr) dérivent tous du blueprint (étaient figés clusterId 0 ; le pool `lan` `192.168.1.192/27` collisionnait même sur le LAN partagé). (b) Egress (pièce 1) DESIGN CLOUÉ, pas codé : forme operator confirmée (sources tailscale main) = **`ProxyGroup type:egress`** (`tailscale.com/v1alpha1`, replicas défaut 2, tags défaut `[tag:k8s]`) + par-workload un Service **`ExternalName`** (ports 6443 + annotations `tailscale.com/proxy-group` + `tailscale.com/tailnet-target-ip: <VIP>`) ; l'operator POSSÈDE `spec.externalName` (le pointe vers son ClusterIP généré) + crée les EndpointSlices. Placement tranché = **domaine cluster-api** (itère `workloadTargets` + dérive blueprint comme `ClusterApiWorkloadManifestsUnit` ; l'operator tailscale est structural sur les 2 rôles donc présent sur mgmt). Service en ns `tailscale-system`, FQDN `<cluster>-apiserver.tailscale-system.svc.cluster.local`. **SONDE LIVE tranchée (2026-09-12, bioskop-mgmt operator v1.102.3, ns dédié `egress-probe` appliqué+nettoyé)** : le ProxyGroup-egress est câblé par le `service-pg-reconciler` via des objets SÉPARÉS operator-owned (ClusterIP Service + EndpointSlice + ConfigMap `<pg>-egress-config` lu par les pods proxy via `/etc/proxies`) ET l'operator **mute `spec.externalName`** du Service utilisateur (le repointe vers son ClusterIP). ProxyGroup = cluster-scoped ; operator watch tous les ns (`OPERATOR_NAMESPACE=` vide). Service utilisateur = `ExternalName` + ports + annotations `tailscale.com/proxy-group` + `tailscale.com/tailnet-target-ip`. **DÉCISION ownership (user) : l'egress N'est PAS un ManifestsUnit rendu par Flux** (la mutation d'`externalName` flapperait sous Flux SSA force-apply) → **le `rke2-adoption-controller` POSSÈDE l'egress** : il crée/réconcilie ProxyGroup + Service egress idempotemment (touche `externalName` seulement si vide) EN MÊME TEMPS qu'il patche la kubeconfig. Reach = facette de l'adoption, un seul owner, zéro course. Donc pièces reventilées : **rendues** = (1) controlPlaneEndpoint=VIP + (2) tls-san += `<w>-apiserver.tailscale-system.svc.cluster.local` (dans `ClusterApiCrRenderer`) ; **controller** = (3) override kubeconfig.server→FQDN egress + (4) l'egress ProxyGroup+Service.
