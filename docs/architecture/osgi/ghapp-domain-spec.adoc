== Overview

The `ghapp` domain owns *one thing*: the identity of the single org-owned GitHub App
`seedmatic-rke2lab`. It does two jobs:

. *Mint* short-lived, scoped installation tokens from the App's private key — the writer's
  `contents:write` push token host-side, and (via Kubernetes operators) the readers' tokens
  in-cluster.
. *Rehydrate* the sealed credentials into each run so the mint has a key to work from.

*Declaration* — creating the App on GitHub, generating its key, installing it, and seeding
`.secrets` — is NOT a domain job in the grow: it is an out-of-band operator ceremony driven by the
standalone `ghapp` CLI (see <<The ghapp CLI>>). It is kept out of the grow deliberately: `seed-master`
runs under `pulumi up`, whose gRPC engine captures the console and makes a mid-run browser/prompt
unusable, so the human ceremony runs on a real console instead.

Everything the system does with GitHub — `seed-master` pushing a rendered branch, each cluster's Flux
pulling it — is authenticated by a token minted from this one App. No personal PAT, no `gh auth token`,
no deploy key. The *why* (escaping the corporate governance of personal tokens) lives in the
link:../cluster-api/github-credential-model.adoc[credential-model vision]; this doc is the *how*.

The domain follows the standard `contract` / `edge` / `bdd` layout (like `auth`, `bbox`, `incus`):

* *ghapp-contract* (`type=contract`) — the vocabulary: `GithubAppCredentials` (the sealed cellar case),
  `GhAppCoordinate`, the `GithubAppMinter` verb (mint a scoped token), `TokenScope`, `MintedToken`, and
  the webhook-reconcile trio — the `GithubAppWebhookConfigurer` verb, its `WebhookConfig` (`url` +
  `secret`), and the `WebhookReconcileInput` amendment wire-record (see <<The webhook reconcile>>).
* *ghapp-edge* (`type=edge`, two `@Component`s) — the GitHub-API contact: `GithubAppTokenMinter` signs
  the App JWT and mints scoped installation tokens; `GithubAppWebhookConfigurerEdge` PATCHes the App's
  webhook config. Both `cultivating`-gated.
* *ghapp-bdd* (`@SeedScenario`) — `GithubAppScenario`, a *pure rehydrate*: seal the credentials into
  the run from the cellar or from the `.secrets` `githubApp` block (via the read-only
  `SecretsGateway`). No browser, no registration. And `GithubAppWebhookScenario` (+ its
  `GithubAppWebhookRunbookHandler` / `GithubAppWebhookAmendReflector`) — the grow-sown reconcile of the
  App's webhook to the current funnel.
* *GithubAppCli* — the host-side `ghapp` operator command (a `seed-master` subcommand), driving the
  declaration ceremony (`create` / `install` / `seed`) out-of-band. See <<The ghapp CLI>>.

== Why declaration cannot be a loopback POST — GitHub's SameSite hardening

GitHub's original App-*manifest* flow POSTs a JSON manifest from a page you host to
`github.com/…/settings/apps/new`; GitHub stores it in your web session, you confirm, and it redirects
with a short-lived `code` you exchange for the PEM. A tempting automation is to host that
auto-submitting form on a loopback endpoint (`127.0.0.1`) the operator opens. *It cannot work.*

GitHub protects App creation behind two session cookies — `user_session` (`SameSite=Lax`) and
`__Host-user_session_same_site` (`SameSite=Strict`). A form served from `127.0.0.1` POSTing to
`github.com` is a *cross-site POST*, and the browser strips *both* (Lax is withheld on cross-site
POST; Strict is withheld on any cross-site request). GitHub receives an *anonymous* request, cannot
tie the manifest to a session, and answers `"url" wasn't supplied` — even though the manifest is
perfect and the operator is logged in. Proven from a HAR of the real POST: zero session cookies on
the request. There is no self-install or key-generation API either, so *nothing* lets code create the
App from a loopback.

The escape is a *top-level GET navigation*, which DOES carry the Lax session: GitHub's *pre-filled*
"New GitHub App" form (`settings/apps/new?<params>`). The operator lands *authenticated* on GitHub's
own page with the App's shape pre-selected, and the final "Create" click is *same-site* on github.com
(carrying the Strict cookie). That is what the `ghapp create` subcommand opens.

== The ghapp CLI — declaration, out of the grow

`GithubAppCli` runs as the `ghapp` subcommand of `seed-master`'s `Main`, *before* the Pulumi envelope
(so it needs no engine and prints to the real console). It drives the three-click ceremony and
finishes it:

[cols="1,3",options="header"]
|===
|Subcommand |What it does

|`ghapp create`
|Opens GitHub's PRE-FILLED New-App form (the top-level GET below) via `java.awt.Desktop`. The
operator clicks *Create GitHub App* and *Generate a private key* (PEM → `~/Downloads`).

|`ghapp install`
|Opens the App's install page; the operator installs it on the `seedmatic` org (selecting
`seedmatic/rke2lab` or all repos).

|`ghapp seed <appId> [pemPath]`
|Forges the App JWT from the PEM (JDK-only: PKCS#1→PKCS#8 wrap + `SHA256withRSA`), resolves the
installation id via `GET /app/installations`, and writes the `githubApp` block into `.secrets`
(`appId` / `installationId` in the clear, `privateKeyPem` marked `# sops:encrypted`). `pemPath`
defaults to the newest `*.pem` in `~/Downloads`.
|===

The pre-filled form URL (permissions use the permission slug as the parameter name; see
link:https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-using-url-parameters[GitHub's
URL-parameters doc]):

----
https://github.com/organizations/seedmatic/settings/apps/new
  ?name=seedmatic-rke2lab
  &url=https://github.com/seedmatic/rke2lab
  &webhook_active=false
  &contents=write&statuses=write&pull_requests=write&checks=write&metadata=read
----

The permissions are the *union* of what every usage needs; each minted token is *scoped down* to a
`TokenScope` subset (writer → `contents:write`, reader → `contents:read`, CI →
`statuses`/`pull_requests`/`checks`). One App, many least-privilege tokens.

[NOTE]
====
*The three clicks are irreducible.* Creating the App, generating the key, and installing it are
GitHub-UI-only — there is no API for an App to install itself or mint its own first key. `ghapp seed`
automates *only* what has an API: installation-id resolution and the `.secrets` write. It turns the
manual URL-reading + YAML edit into one command; it does not remove the clicks.
====

== The grow rehydrates — GithubAppScenario

The grow sows `GithubAppScenario`. It is a *pure rehydrate* — it never declares the App, never opens a
browser, never hard-fails:

. *cellar hit* — the `GithubAppCredentials` were already sealed this run → no-op (idempotent-keep).
. *`.secrets` hit* — the `githubApp` block is present (via the read-only `SecretsGateway`) →
  rehydrate: seal to the cellar. This is the steady state once the operator has run `ghapp seed`.
. *miss* — neither present → seals nothing. That is the honest local skip: a required-credential
  absence is a HARD fail at the CONSUMPTION site (the writer mint / the Flux-Secret render), never
  here. If the operator has not run the `ghapp` CLI, the downstream mint/render fails loudly.

The credentials thus live in *two* homes for two lifetimes: `.secrets` (sops-governed, committed
encrypted, operator-owned — the durable source of truth, written by `ghapp seed`) and the *cellar*
case `GithubAppCredentials` at `GhAppCoordinate.GITHUB_APP`, `Sensitivity.SEALED` (the in-run working
copy the writer mint and the reader-Secret render fetch). The PEM is never re-derivable: if lost, a
*new* key must be generated in the GitHub UI (also human-gated).

== Flow — using it in the cluster via Flux

The management cluster's Flux pulls the rendered branch as the App. `seed-master` renders a *githubapp
Secret* — the Flux Operator's native GitHub App auth shape — into the *local-only bootstrap seed* (the
node's RKE2 auto-deploy dir), alongside the `FluxInstance` that references it via `pullSecret`. The
chicken-and-egg is solved: the credentials arrive in the local-only seed, not in the branch they are
used to fetch.

*Read it*: `ghapp` does NOT run in the cluster for the reader — the *Flux Operator* does the minting
(https://fluxcd.io/blog/2025/04/flux-operator-github-app-bootstrap/[native GitHub App auth]): given the
`githubapp` Secret (App id + installation id + PEM), Flux signs the JWT, mints a short-lived
`contents:read` token, and self-refreshes. This replaces deploy keys and PATs for the pull. Other
in-cluster actors (Tekton) get their scoped tokens from a `github-app-operator`-style controller — the
same pattern, a different consumer. The `ghapp` domain's own minting is *host-side only* (the writer,
below).

== The writer — the spine

The whole point of the reader is to have something to read: `seed-master` must *push* the rendered
manifests so the cluster can pull them. That push is the spine, and it is where `GithubAppMinter` runs.

*The mint is in-container, at the point of use — never sealed.* `GithubAppMinter` and
`GithubAppCredentials` are bundle-wired `type=contract` types — a flat-host
`awaitService(GithubAppMinter.class)` resolves the host's own class copy, which never matches the
bundle's, so the host *cannot* call the minter directly (the seam law in
link:../../CLAUDE.md[CLAUDE.md]). So the mint runs *in the scenario that pushes*
(`ManifestSynthesisScenario`, and the version-bump `VersionBumpScenario`): at the moment of the push
it reveals the sealed `GithubAppCredentials` from its own cellar case and mints a FRESH `WRITER` token
through the `auth` domain's `GithubWriterTokenMint` verb (its `cultivating` edge
`GithubWriterTokenMintEdge` `@References` `GithubAppMinter`). The token is *ephemeral* (≈1 h) and
*never sealed* — minting it seconds before the push and discarding it is what keeps it from going
stale, the trap a durable seal fell into (an installation token filed in the cellar before
provisioning, revealed for the push after the whole cluster came up, long past its 1 h life). The
push itself is in-container too, so the token never crosses the host↔OSGi membrane.

This *replaced* the former `gh auth token` → sealed-token → host-side `JgitCheckout` path (whose
auth-seal vocabulary — `AuthSealScenario`, `GithubToken`, the `auth` sow — is deleted): the credential
source is now the org-owned App, the mint is on-demand, and both mint and push live in the scenario.
`GithubAppMinter` is fail-fast: it returns a token or throws, never a silent fallback.

== The webhook reconcile — pointing the App at the funnel

The App does not only mint tokens; it also carries a *webhook* GitHub POSTs its events to, so
Pipelines-as-Code can start a render PipelineRun on a push. Two of that webhook's fields drift after
creation and would otherwise be hand-edited in the GitHub UI: the *URL* (it changes whenever the
Tailscale funnel is renamed — the way we win a fresh Let's Encrypt cert budget) and the *secret* (the
shared HMAC value PaC validates against, which GitHub forbids as a registration URL parameter). The
`ghapp` domain reconciles both AS the App, on every grow — so the operator never opens the webhook
page.

The verb is `GithubAppWebhookConfigurer.configure(GithubAppCredentials, WebhookConfig)`: it signs the
App JWT and calls `PATCH /app/hook/config` with the desired `WebhookConfig` (a `url` + `secret`
record; content-type and `insecure_ssl` are edge constants). The one *edge* that satisfies it,
`GithubAppWebhookConfigurerEdge`, carries `rke2lab.gardening=cultivating` — filtered out under a
survey/preview frontier, so the reconcile PENDS rather than touching GitHub. This is the exact
posture of `GithubAppMinter`/`GithubAppTokenMinter`, one door further.

The scion `GithubAppWebhookScenario` is grow-sown at coordinate `ghapp-webhook`. It reads the App
`GithubAppCredentials` from the cellar (sealed by `GithubAppScenario`) and the shared
`github.webhook.secret` from `.secrets` in-container, and takes the *one host-held fact* — the funnel
URL — through its `WebhookReconcileInput` (a `@SeedContract("runbook")` wire-record whose single
`@Amendment(Amendment.FUNNEL)` component the host fills). Only the host holds the URL: the MagicDNS
leaf is the shared `PacWebhookFunnel.LEAF` constant, but the tailnet suffix is host-config appended by
Tailscale at runtime — never on the in-container synthesis context — so `seed-master` builds
`PacWebhookFunnel(tailnet).url()` and sows it as the `FUNNEL` amendment. The amend door
(`GithubAppWebhookAmendReflector`) binds that neutral role onto the input field; the runbook handler
(`GithubAppWebhookRunbookHandler`) decodes the reconciled trigger and plays the scenario. Absence of
any input (no cellar credentials, no secret, no cultivating edge) is the honest local skip — the
reconcile is a best-effort convenience, never a hard gate on the grow.

=== Per-cluster repository webhooks — beyond the App's single webhook

A GitHub App has exactly ONE webhook URL, so the App webhook above can drive only ONE cluster's
Pipelines-as-Code receiver. A *repository* accepts MANY webhooks, so each cluster's PaC/Tekton funnel
can be driven independently. The `GithubRepoWebhookConfigurer` verb reconciles ONE repo webhook via
`POST/PATCH /repos/{repo}/hooks` — its `RepoWebhookConfig` (`repoFullName`, `url`, `secret`,
`events`, keyed by `url` so the reconcile is idempotent: patch the matching hook or create it). It
needs a `TokenScope.REPO_ADMIN` installation token (`administration:write` — repo webhooks are not
manageable with the App-level JWT), minted through the existing `GithubAppMinter`. Its edge
`GithubRepoWebhookConfigurerEdge` is `cultivating`-gated like the rest. This is the capability half of
the per-cluster webhook rewire; the grow wiring (a per-cluster funnel leaf + reconciling flux and pac
repo webhooks, retiring the App webhook) is the pending step.

human ceremony is host-side, out of the pulumi-driven grow.

== Predictability & caveats

* *Three human clicks, once.* Create the App, generate the key, install it — GitHub-UI-only, no API.
  Every run after `.secrets` is seeded is fully automatic (rehydrate).
* *Existence ≠ authority.* Only *holding the PEM* authenticates as the App. The scenario branches on
  "is the PEM sealed / anchored", not "does the App exist".
* *No loopback, by GitHub's design.* App creation is gated behind `SameSite` session cookies a
  cross-site loopback POST cannot carry; the pre-filled top-level-GET form is the only working path.
* *Declaration out of the grow.* Because `seed-master` runs under `pulumi up` (console captured by the
  gRPC engine), the browser ceremony lives in the standalone `ghapp` CLI on the real console — the
  grow only rehydrates.
* *One key, scoped short tokens.* No per-cluster keys (generating App keys is UI-only). Isolation is
  by *token scope* (a reader never mints write) and short lifetime (≈1 h); revocation is
  suspend-the-App or rotate-the-key.
* *Read-only secrets seam.* The in-container `SecretsGateway` only READS `.secrets`; the one write
  (the `githubApp` block) is the host-side `ghapp seed` command, not a scion.
