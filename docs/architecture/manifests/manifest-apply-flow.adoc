= Manifest Apply Flow
:toc:
:toc-placement: preamble

== Overview

RKE2Lab manifests flow from CDK8s synthesis to live Kubernetes resources through a
*GitOps rendered-branch* pipeline. The `manifests` domain synthesises a cluster's
resources, explodes them into a per-resource tree, and *pushes* that tree to the
cluster's own `manifests/<cluster>` git branch. *Flux* — not RKE2's on-node
auto-deploy, not `kubectl apply` — reconciles the branch into the cluster, one
`Kustomization` per `(layer, domain, package)` service cell.

The pipeline has three lanes, one operation. The render+push OPERATION lives in
OSGi (the `ghapp`→`auth`→`manifests` scion graph, driven through the
`seed.broker.port` membrane); the executables are thin HOSTS that sow the SAME
coordinates:

* *Grow* (`seed-outcluster`) — the FIRST render+push, host-side, inside the Pulumi
  envelope. It must be host-side: at bootstrap there is no cluster, no Flux, no
  branch to pull.
* *Operator publish* (`manifests publish` CLI) — a standalone render+push, minus
  the Pulumi envelope.
* *In-cluster* (Tekton Pipelines-as-Code) — re-render+push when the manifests
  SOURCE changes, no grow needed.

Downstream of all three, Flux reconciles the pushed branch.

[NOTE]
====
*History (superseded).* Earlier, the exploded tree was pushed onto the *node's*
`/srv/host/rke2-manifests.d/` over `incus file push`, then a per-layer systemd
oneshot (`rke2lab-<layer>-manifests.service`) ran `rke2lab-manifests-install.sh`
to symlink-stow the tree into `/var/lib/rancher/rke2/server/manifests/` where
RKE2's built-in auto-deploy applied it. That whole on-node flow — the install
script, the `RKE2LAB_MANIFESTS_PUBLISH_*` publish-flag gating, the symlink stow,
the per-layer `.service` units, and the `lazy()` unit factory — was *dissolved*.
Delivery is now the git branch + Flux; layer enable/disable is a Flux
`Kustomization` armed/absent, not an env flag read on the node. See
link:../nixos-substrate/concern-ownership.adoc[concern ownership] (the "manifests
install" row moves to Flux GitOps) and
link:../cluster-api/manifests-rendered-branches.adoc[the rendered-branch model].
====

*Key insight*: no `kubectl apply` and no on-node install script. The branch IS the
desired state; Flux is the only actor that applies it, and it does so per-service
with observable, independently-retryable `Kustomization`s.

== Stage 1: Synthesis

Each domain contributes `ManifestsUnit` implementations that construct Kubernetes
resources type-safely via CDK8s `Chart`. Units are plain objects with a canonical
`(Construct scope, String id)` constructor; scope binding is deferred to
`apply(ManifestsUnitContext)` and group-markers are emitted uniformly from the
`doSynthesize(Construct, ManifestsUnitContext)` base hook (the `lazy()` factory is
gone — see link:manifests-unit-lifecycle.adoc[the unit lifecycle]).

Synthesis is orchestrated by `ManifestSynthesisScenario` (the synthesis FLUX in
`manifests-bdd`), which resolves the `ManifestDomainPolicy` from the run's facet,
drives the `CoherentManifestsDomainRegistry` visit-order, and produces one
consolidated YAML stream. Identity (cluster/node, network topology, component
versions) reaches units by `ManifestSynthesisContext` (ThreadLocal), never
constructor params — see
link:../bootstrap/bootstrap-identity-provider.adoc[Bootstrap Identity Provider].

*Code*: `osgi/domains/manifests/manifests-core/src/main/java/io/seedmatic/rke2lab/manifests/units/<domain>/`

Every `ApiObject` is stamped with a package annotation that routes it during the
explode:

[source,java]
----
public KdnsManifestsUnit(final Construct scope, final String id) {
  super(scope, id, MANIFEST_UNIT_ID, List.of());
  new ApiObject(this, "deployment-kdns", ApiObjectProps.builder()
      .metadata(ApiObjectMetadata.builder()
          // io.seedmatic.rke2lab/package: "networking/kdns" (+ the layer routing)
          .annotations(packageProfile.packageAnnotations("|Deployment|rke2lab-system|kdns"))
          .build())
      .build());
}
----

== Stage 2: Explode + plan

`DefaultManifestExplodeService` parses the consolidated stream and writes each
document to `<layer>/<domain>/<package>/NN-kind-name.yml`, keyed off the package
annotation. Layer assignment is annotation-driven: the default is `workloads`; a
`CustomResourceDefinition` is routed to `crds` by kind; a unit that installs an
operator/CRD-registrar carries a `layer=operators` mark (`PackageMetadataProfile`).

[source]
----
manifests/<cluster>/          # branch root (materialised tree)
├── manifest.yaml             # render facet record (source + facet) — root, not a resource
├── crds/
│   └── runtime/flox-controller/…
├── operators/
│   └── clusterapi/cluster-api-operator/…
└── workloads/
    ├── networking/kdns/
    │   ├── 01-clusterrole-kdns-ingress-reader.yml
    │   ├── 02-serviceaccount-kdns.yml
    │   └── 02-deployment-kdns.yml
    └── mesh/headscale/…
----

`FluxServiceKustomizationPlanner` then reads the written cells plus the in-memory
dependency graph and emits one child `Kustomization` per service cell under
`./flux`, wiring each child's `dependsOn` from two sources — the *layer barrier*
(crds → foundation → operators → workloads) and *intra-layer service→service*
edges from a unit's `dependsOnManifestsUnitIds`. See
link:flux-kustomization-planner.adoc[The Flux Kustomization Planner] for the full
mechanics.

`local-config` resources (`config.kubernetes.io/local-config: "true"`) are carried
in the tree but sit outside every `Kustomization` path, so Flux applies nothing for
them — they are inputs to other resources (Helm values, Kustomize bases), not
standalone objects.

== Stage 3: Deliver (git)

The render materialises into a *transient git worktree* of `manifests/<cluster>`
(under the gitignored `.local.d/`), signs the commit as the rke2lab bot, and
*fast-forwards* the branch. Delivery is armed by the facet's `delivery.push`; an
unarmed render renders-but-does-not-push (the signed commit still lands locally).

* The push is history-preserving — the branch keeps a full, auditable GitOps trail,
  never a force-push.
* An unchanged source+facet re-renders byte-identically, so the empty-commit guard
  (`JgitCheckout.setAllowEmpty(false)`) makes the push a fast-forward no-op — a
  *fixpoint*.
* The branch is secret-blind: real-data secrets ride the `NODE_BOOTSTRAP` lane the
  exploder writes OUTSIDE the git tree, never staged or committed.

Which identity signs and pushes, and where the push token comes from, is resolved
by the *execution enclosure* (OPERATOR vs IN_CLUSTER) — see
link:../cluster-api/pac-in-cluster-render-spec.adoc#auth[the auth section].

== Stage 4: Reconcile (Flux)

A push to `manifests/<cluster>` triggers a Flux reconcile at once (the Flux webhook
over the Tailscale funnel, degrading to the 1m poll if the webhook is down). Flux
reconciles the branch in *layers, not one atomic apply*:

* a single root `Kustomization` `flux` over `./flux` owns the per-service children;
* each child reconciles its own `./<layer>/<domain>/<package>` path;
* the children's `dependsOn` graph carries the layer order (a CR's CRD — rendered,
  or registered at runtime by a foundation/operators provider — is established
  before the CR), and the root's `wait: true` makes it Ready only once every child
  is.

An operator sees per-service progress in `flux get kustomizations`
(`mesh-headscale`, `runtime-flox-controller-crds`, …); a failure stays local to one
service; retries are independent. This is the durable answer to the recurring
CRD↔CR ordering problem, with per-service observability. Full detail:
link:../cluster-api/manifests-rendered-branches.adoc#layers[the branch reconciles in layers].

== The render facet follows the grow

The render is parameterised by a *facet* — which layers publish (`gitops`,
`networking`, `mesh`, `cicd`, …), the `debug` toggles, and whether `delivery.push`
is armed. It has one authoring source: the *Pulumi stack* (`rke2lab:manifests`),
read at the grow and contributed as the `Amendment.FACET` through the broker.

Every render writes the resolved facet back as a native-YAML `manifest.yaml`
document at the ROOT of the tree (carrying `source:{sha,dirty}` provenance +
`facet:`). It is NOT a Kubernetes resource — it sits outside every `Kustomization`
path — but a human-legible git artefact written by `ManifestSynthesisScenario`
(the flow, not a `ManifestsUnit`: at synthesis only the resolved
`ManifestDomainPolicy` survives). The in-cluster render reads it at branch HEAD
(`git show manifests/<cluster>:manifest.yaml | yq .facet`), so it renders exactly
what the last grow decided. See
link:../cluster-api/pac-in-cluster-render-spec.adoc#render-config[the facet-follows-the-grow section].

== Adding a new ManifestsUnit

*Step 1*: Create the unit in
`osgi/domains/manifests/manifests-core/src/main/java/io/seedmatic/rke2lab/manifests/units/<domain>/`,
using the canonical `(Construct scope, String id)` constructor and stamping package
annotations on every resource.

[source,java]
----
public final class MyManifestsUnit extends AbstractManifestsUnit {

  public static final String MANIFEST_UNIT_ID = ManifestDomainCatalog.MY_DOMAIN + "/my-thing";

  private final PackageMetadataProfile packageProfile =
      new PackageMetadataProfile("my-domain", "my-thing");

  public MyManifestsUnit(final Construct scope, final String id) {
    super(scope, id, MANIFEST_UNIT_ID, List.of());
    // Create ApiObjects on 'this', annotating with
    // packageProfile.packageAnnotations("|Kind|namespace|name")
  }
}
----

*Step 2*: Reference it from its domain registrar in
`.../manifests/domain/`, adding it to the domain's `ManifestsDomain`. The assembled
`CoherentManifestsDomainRegistry` `resolve()` then orders the units and checks
coherence — see
link:manifests-architecture.adoc#ordering-and-coherence[Manifests Architecture → visit order and coherence].

*Step 3*: If the unit installs an operator or registers CRDs, mark it
`layer=operators` (via `PackageMetadataProfile`) so `FluxServiceKustomizationPlanner`
places its child on the right barrier rung. A plain workload needs no mark (default
`workloads`). There is NO systemd unit and NO install-script step to add — that
world is dissolved.

*Step 4*: Build and render.

[source,bash]
----
flox activate -- ./mvnw -pl :manifests-core -am clean package
# render into a plot (no push):
flox activate -- ./exec/manifests-cli/... synthesize -Drke2lab.manifests.outdir=…
----

== Staged (post-cluster) resources

Some resources need data only available AFTER Pulumi provider resources exist
(e.g. the Cluster API `NodeImage` needs the built image's fingerprint — see
link:../cluster-api/node-image-lifecycle.adoc[Node image lifecycle], where it now arrives as the
`IMAGE_STATE` amendment rather than a provider round trip), while synthesis runs
before those Outputs resolve. Such units defer
their synthesis to the provider stage via `Output.applyValue`, then flow through
the SAME explode→deliver→reconcile pipeline — there is no separate on-node
`staged/` install path any more; a deferred unit's resources land in the tree and
are reconciled by Flux like any other. See
link:../atlas/manifests.adoc[Atlas — Manifests] (the "staged synthesis" capability).

== Troubleshooting

[cols="1,2",options="header"]
|===
| Symptom | Cause / fix

| A resource never appears in the cluster
| Check the exploded tree carries it (`git show manifests/<cluster>:<layer>/<domain>/<package>/…`),
  then `flux get kustomizations` for its service cell (`<domain>-<package>`) and
  `flux logs`. A `dependsOn` barrier may be holding it (its layer waits on an
  earlier layer that is not Ready).

| A CR fails with `no matches for kind … (CRD not registered)`
| The CR's CRD is registered at runtime by an operator, but the CR's child did not
  wait for it. Confirm the operator's unit carries `layer=operators` so the barrier
  applies + health-gates it before the `workloads` layer.

| The reconciled branch churns with empty commits
| A structural re-render on an unchanged source must be a no-op fast-forward. If it
  is not, the render is non-deterministic — check the `NODE_BOOTSTRAP` secrets stay
  off the branch and the facet is stable.

| `manifests publish` renders but the push is skipped
| The facet's `delivery.push` is not armed, or (in-cluster) the push token was not
  revealed. See link:../cluster-api/pac-in-cluster-render-spec.adoc#auth[auth].

| The in-cluster render renders the wrong layer set (e.g. no `mesh`)
| It fell back to the CLI's hardcoded posture instead of the recorded facet. Confirm
  the root `manifest.yaml` exists on `manifests/<cluster>` at HEAD and the render
  reads it. A branch grown before the facet-record landed has none → one re-grow
  writes it.
|===

== Anti-patterns

❌ *A per-layer systemd unit + install script on the node.* That was the dissolved
model; there is no `/srv/host/rke2-manifests.d/`, no `rke2lab-manifests-install.sh`,
no symlink stow. ✅ Render → push the branch; Flux reconciles.

❌ *`kubectl apply -f` in a unit or a Job.* It bypasses the GitOps trail, needs a
kubeconfig, and there is no drift reconciliation. ✅ Let the resource ride the
branch; Flux applies and reconciles it.

❌ *Gate a layer with an env flag (`RKE2LAB_MANIFESTS_PUBLISH_*`).* Dissolved. ✅
The facet decides which layers synthesise; a disabled layer produces no tree, so
its `Kustomization` is simply absent from the branch.

== Design rationale

*Why a rendered branch + Flux, not on-node auto-deploy?*

1. *Auditable history* — the branch keeps every rendered commit; rollback is
   `git revert` or a re-render from an earlier source `@sha`.
2. *Per-cluster isolation is structural* — one branch per cluster mirrors the
   physical cluster boundary; a mis-scoped resource cannot land in the wrong
   cluster because it cannot even exist on the wrong branch.
3. *Layered, observable reconcile* — per-service `Kustomization`s give
   independent progress/failure/retry, and solve the CRD↔CR ordering problem by
   construction.
4. *Drift reconciliation* — Flux continuously reconciles git-vs-cluster; a manual
   change is corrected, unlike a one-shot apply.
5. *Uniform delivery* — grow, operator publish, and in-cluster PaC all sow the
   same OSGi operation and push the same branch shape; only the host differs.
