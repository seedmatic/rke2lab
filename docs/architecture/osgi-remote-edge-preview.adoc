= Separer le monde Host du monde OSGi via les Remote Services (2026-06-27)
:toc: left

Whiteboard de design *annexe* (hors conf, hors contexte de la branche cluster-edge en cours).
Question : peut-on rendre le monde OSGi *live* et autonome, l'embed exec devenant *juste une interface*
vers un monde OSGi *distant* ? Reponse : oui -- ton seam world-gateway est deja concu transport-neutre
(*tout passe en `Document`/JSON sur des verbes, schema = OpenAPI ; "embedded today, remote later, same
contract"*). Les Remote Services OSGi (RSA, chapitre 122) sont le mecanisme qui rend ce seam physique
SANS toucher les consommateurs.

== Figure 3 -- TA question : comment l'interface est realisee cote client

C'est le coeur. L'interface cote edge n'est PAS du code que tu ecris : c'est un *proxy genere
dynamiquement* par le distribution provider, et POSE dans le registre local du host par le RSA d'import.
Ton `awaitService(HealthSystem)` actuel ne change pas d'un caractere -- il recupere ce proxy au lieu d'un
`@Component` local. Le corps de chaque methode du proxy serialise le `Document`, l'envoie sur le fil,
attend, deserialise la reponse.

== Lecture

* *Pourquoi RSA et pas un simple HttpClient* : ta vision n'est pas "host = client HTTP nu", c'est
  "host = framework OSGi reduit a l'edge". RSA ne te vend pas la transparence des TYPES (inutile, tu
  passes du `Document`) mais la transparence du MODELE DE CONSOMMATION : tes consommateurs gardent
  `@Reference` / `awaitService`, aucun ne devient un site d'appel HTTP. Le HTTP/Document reste SOUS le
  proxy, parle par le DP -- ton schema JSON devient la serialisation du fil, tu ne le perds pas.

* *Ce qui change dans ton code* : presque rien cote consommateur. Ce qui change, c'est ce que le
  framework host CONTIENT -- plus les domaines lourds, seulement `-port` + RSA + DP + discovery. Le
  raisonnement demenage dans le daemon.

* *L'effet sur les gates* : REALM_BOUNDARY (Plan 1, en cours) devient redondant avec une frontiere
  PHYSIQUE -- les types bundle-only ne sont plus dans la JVM host, donc la loi ASM garde la valeur
  pendant la phase embedded et documente l'invariant que le split materialisera ensuite.

* *Cout honnete* : un DP a choisir et a embarquer dans l'edge (ECF JAX-RS, ou Aries Remote Services,
  ou CXF-DOSGi) ; le cycle de vie du daemon a gerer (qui le demarre, le supervise) ; la version-skew
  redevient possible -- d'ou le runtime-validation du schema que le spec parquait en YAGNI et qui
  devient pertinent des que les deux mondes sont deployes separement.

== Lecture des faits verifies

* *ECF Remote Services 3.16.8 (avril 2026)* : la SEULE option vivante (impl de reference du TCK OSGi
  R8, travail de feature en cours). Framework-agnostique, prouvee sur Karaf-sur-Felix, build Maven/bnd
  sans PDE. Couts : (a) pas de phrase doc quotable "tourne sur Felix" -> un smoke-test sur Felix 7.0.5
  s'impose ; (b) ~4 bundles utilitaires Equinox transitifs ; (c) CONFIRMER qu'un provider JAX-RS/JSON
  existe bien au 3.16.x avant de s'engager.

* *Apache Aries RSA 1.16.1 (sept 2021)* : coeur RSA propre, Felix-friendly, zero Equinox, pur Maven --
  MAIS maintenance-only (commits 2026 = bumps de bot) et surtout son UNIQUE transport JAX-RS est
  `cxf-dosgi-provider-rs`, release 2017, repo archive 2022. Route REST = artefact mort.

* *Apache CXF-DOSGi 2.3.0* : archive 2022, release 2017. Elimine pour du neuf -- il ne compte que parce
  qu'il EST la route REST dont depend Aries.

* *L'angle qui rend "Aries + provider maison" credible* : ton contrat est DEJA Document JSON sur des
  verbes. Un provider de distribution qui serialise un JsonNode sur HTTP et regenere le proxy, c'est
  precisement ce que tu maitrises -- RSA te garde la generation transparente du proxy, tu ne fournis que
  le transport. Pas trivial, mais loin de la stack web-services complete.

== DECISION ROUVERTE -- la verif inverse la base du choix ECF

On avait choisi ECF parce que "le maintenu". La verif (juin 2026) montre que ce qui est maintenu n'est
PAS la partie utile : le coeur ECF est vivant (3.16.8) mais le provider JAX-RS vit dans un depot
SEPARE, dormant depuis fevrier 2022, ABSENT de Maven Central. Sur l'hygiene : les 3-4 bundles
utilitaires Equinox sont des deps DURES du coeur RSA (non excluables) MAIS zero machinerie p2/repository
n'est tiree -- le "repository OSGi" que tu voulais dehors reste dehors.

== CORRECTION -- "REST" n'etait PAS une exigence (sur-cadrage de ma part)

J'avais erige REST en exigence a cause du "REST, but in our embedded model" du spec -- mais c'est un
MODELE MENTAL (coordinate=path, Document=body), PAS un protocole de fil impose. Un provider RSA = un
transport sur un fil ; il y a DEUX familles : les transports applicatifs (REST/HTTP, ceux qui sont
morts) et les transports generiques (binaire/socket, qui EXISTENT et sont disponibles). L'utilisateur
n'a aucun besoin REST -> la mort des providers REST devient SANS OBJET.

== Le contrat survit sans REST

Le seam reste l'interface Java consult Document ; le transport generique marshalle l'appel, RSA
regenere le proxy, awaitService ne voit rien. Le schema-par-document valide toujours le Document qui
traverse -- il n'est juste plus expose en endpoint HTTP OpenAPI. Seul detail : le tcp d'Aries utilise la
serialisation Java, donc Document doit etre serialisable (trivial si on porte le JSON comme String dans
le record) ; fastbin a son propre protocole.

== Pourquoi je penche Aries + tcp

. *L'hygiene que TU as posee est le critere explicite* -- Aries la satisfait totalement, ECF non.
. *"Fige" fait moins peur ici* : la RSA SPI est gelee par la spec OSGi, le transport ne TRANSPORTE
  qu'il n'evolue pas, et Felix 7.0.5 est stable. Inverse d'une lib applicative.
. *tcp colle au contrat* avec un seul detail trivial (Document Serializable via JSON-as-String).
  fastbin = async binaire, surdimensionne pour un consult synchrone.

Seul contrepoids pro-ECF : vouloir un projet vivant sous soi quitte a avaler 3 jars Eclipse -- ce qui
va contre ta reticence repetee a Eclipse.

=== La tension specifique a rke2lab + l'echappatoire

* *Le provisioning Karaf EST la machinerie repository que tu voulais dehors* : features + mvn URL +
  resolveur runtime, l'inverse de ton staging extension qui DERIVE l'ensemble par cloture Import-Package
  et le fige au build. Adopter Karaf naivement INVERSE ta philosophie de boot.

* *L'echappatoire = assembly statique* : le karaf-maven-plugin cuit TES features au build, sans
  resolution ni mvn URL au runtime. Tu gardes le modele "bundles figes au build" ET tu obtiens daemon +
  shell + JMX. C'est l'usage qui reconcilie Karaf avec ta discipline. Si Karaf, alors statique.

* *La vraie valeur pour toi* n'est PAS le provisioning (ton staging extension fait mieux) -- c'est le
  cycle de vie supervise + le shell/JMX d'introspection d'un daemon de raisonnement vivant.

* *Le risque qui peut tout trancher = JDK 25* : rke2lab est sur JDK 25 ; Karaf 4.4.x vise plutot JDK
  11/17. Si Karaf ne tourne pas sur JDK 25, question close. A VERIFIER, pas supposer. Idem la version
  Karaf courante debut 2026.

* *Le risque de sunk-cost* : on a passe la session a instruire ECF RSA. Mais la decision seed-outcluster =
  embedded peut signifier que RSA n'est PAS necessaire du tout -- la separation Host OSGi que tu
  cherchais serait obtenue par la frontiere du POD (deploiement), pas par les remote services dans un
  host. Il faut le verifier, pas le presumer.
* *RSA ECF garde sa valeur SEULEMENT si* le consommateur in-cluster est lui-meme OSGi (il heberge le

* *Mon intuition a confirmer* : les consommateurs in-cluster typiques (operators, controleurs) sont
  rarement OSGi -> l'option HTTP simple, ou l'option pod-autonome, est plus probable que RSA. Mais c'est

== DENOUEMENT -- recrutement de specialiste = la federation OSGi (RSA a pleine valeur)

Decision utilisateur : le monde OSGi in-cluster expose ses services et peut RECRUTER dynamiquement un

monde OSGi -> option A confirmee, RSA ECF a sa pleine valeur. C'est le cas qui paie enfin le dividende
OSGi : la dynamique (service qui apparait au runtime, registre qui survit) jamais exercee en embedded.

== Stratégie de confinement (idiome du projet : bannedDependencies + inventaire verifie)

* *Le mecanisme* : meme rituel que la coupe osgi.cmpn -- exclusion BOM + `bannedDependencies` dans le
  build-parent sur `org.eclipse.equinox.*`, `org.eclipse.core.*` et toute machinerie repository/p2 ;
  puis une assertion d'INVENTAIRE des bundles reellement embarques sous META-INF/bundles (un compte
  verifie, pas une promesse). Jumeau de l'invariant `grep -ri pulumi osgi == 0` et du system-exports
  seam gate.

* *Le caveat honnete* : la feature Karaf d'ECF DECLARE comme requis 4 bundles utilitaires Equinox
  (common, jobs, concurrent, supplement). "Les bannir" n'est atteignable QUE si le coeur RSA d'ECF n'en
  a pas besoin au runtime -- a verifier. S'ils sont obligatoires, le choix devient : les ACCEPTER (4
  bundles plain-OSGi, pas le framework) ou ecrire un provider maison sur Aries. La banderole reste le
  but ; sa faisabilite est un fait a etablir AVANT de graver.
