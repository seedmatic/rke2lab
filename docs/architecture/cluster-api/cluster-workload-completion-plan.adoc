= Cluster Workload Completion Plan
:toc: left
:toclevels: 3

The remaining work to finish cluster bring-up under the management/workload separation. `seed-mgmt`'s
validation was paused mid-way to rework its provisioning logic (the BDD-as-engine pipelines), so this
is a live FUTURE worklist, not a closed plan — it resumes with that rework. It captures what is still
to do, in a recommended (but reorderable) sequence.

[IMPORTANT]
====
Rewritten for the *management/workload separation*. Read
link:management-workload-topology.adoc[Management / Workload Topology] (the anchor) first. The biggest
change from the old plan: there are *no control-plane peers on the management cluster*. The management
cluster is single-node by design (resilience comes from <<function-of-git,function-of-git>>, not from
etcd HA). The `master + peer1 + peer2` HA control planes belong to the *workload* clusters, which the
management cluster greenfield-creates. The old "round out HA on the management cluster itself" phase is
gone.
====

== What today's seed becomes

The single cluster `seed-mgmt` currently seeds (`nikopol-mgmt`, node `master`) *is* the management
cluster. Completing it means two distinct tracks, no longer one:

* *Management track* — configure CAPI/CAPN/CAPRKE2 on that single node so it can greenfield-create the
  workload clusters (Phase 2 below). No peers are ever added to it.
* *Workload track* — the operator/add-on stack (Porch, Flux, apps) that used to be applied to the seed
  now belongs to the *workload* clusters, delivered by each workload's own GitOps (Tier 1). Phase 1
  below is re-scoped to the workload clusters.

== Management track — DONE (validated live 2026-08-25)

The management track (Phase 2.A below) is COMPLETE and proven on the running cluster: `bioskop-mgmt`
comes up single-node Ready, the CAPI operator + all four providers (core, rke2 bootstrap, rke2
control-plane, incus infrastructure) install as *manifest units* rendered into `manifests/bioskop-mgmt`
and applied by the cluster's own Flux, and reconcile to Ready. `kubectl get providers -A` shows them
Ready; `kubectl get clusters` is empty (no workload declared yet — the workload track below).

[NOTE]
====
The old blocker — `rke2lab-cluster-api-install.service` / `rke2lab-capn-provider-install.service`
`inactive`, a `clusterctl.yaml`-lacks-incus + systemd-ordering bug — is *gone*, not fixed:
the whole `/srv/host` + `clusterctl` + host-systemd install mechanism was DISSOLVED by the NixOS
substrate refactor. The CAPI operator installs the providers declaratively (`ClusterApiOperatorManifestsUnit`
renders the operator release YAML + the `CoreProvider`/`InfrastructureProvider incus`/`ControlPlaneProvider
rke2`/`BootstrapProvider rke2` CRs), delivered by GitOps like every other add-on. §2.A below is kept only
as the record of that superseded approach.
====

NOTE: The gitops/add-on surface is *already built* as manifest units — Flux is shipped by
`FluxOperatorManifestsUnit` (a `helm.cattle.io/v1` HelmChart, `installCRDs: true`) alongside
`FluxInstanceManifestsUnit` / `FluxRootManifestsUnit` / `SopsAgeSecretManifestsUnit`; Tekton and
cert-manager ship the same way. So there is *no operator-install backlog* left. *Porch is descoped* —
there is no `PorchResourcesManifestsUnit` and no `gitops/porch-resources/*` on disk; the only surviving
Porch mentions are dormant/illustrative comments (`gitops/package-info.java`, `ComponentVersions.java`).
The remaining architectural work for these add-ons is *where they publish* (Phase 1 below).

Known hygiene items to revisit once the workload set is stable: pods log `DNSConfigForming`
(>3 nameservers in `/etc/resolv.conf`, kubelet trims silently); several `rke2lab-*-manifests.service`
units run after `rke2.target` has settled — unit ordering to revisit.

== Phase 2 — configure the management cluster's CAPN (the resume point)

Stage B (CAPI + CAPN + CAPRKE2 greenfield-creating the workloads) cannot start until the *management*
cluster has the CAPN infrastructure provider configured. Today `rke2lab-capn-provider-install.service`
fails because `clusterctl config repositories` does not list `incus` (no `~/.cluster-api/clusterctl.yaml`).

=== 2.A — Foundation: install services + clusterctl.yaml [SUPERSEDED]

WARNING: SUPERSEDED — kept only as a record. The `clusterctl.yaml` + host-systemd install described
here belonged to the `/srv/host` era the NixOS substrate dissolved. The CAPI operator + all four
providers now install as GitOps manifest units (see the management-track NOTE above) and are Ready on
the live cluster. Do not implement this section.

Two prerequisite work items before any workload `Machine` reconciles:

. *Materialize `clusterctl.yaml` at provisioning time.* Pulumi config (`rke2lab:capn.provider.url`,
  `rke2lab:capn.provider.version`) → templated by a host-side init script writing
  `/root/.cluster-api/clusterctl.yaml`. Drives `rke2lab-capn-provider-install.service` precondition
  green. Add CAPRKE2 in the same pass so `clusterctl init -i incus -c rke2 -b rke2` is one call.
  *Both incus remotes* must be registered here (bioskop + nikopol) — CAPN drives two bare-metals.
. *Fix the systemd ordering bug.* `rke2lab-cluster-api-install.service` and
  `rke2lab-capn-provider-install.service` both `Requires=` a prerequisite that becomes active after
  `rke2lab.target`, so they get queued and dropped. Either propagate `WantedBy=` from the prerequisite,
  or restructure so both services are pulled in by their actual unblocker rather than by the target.

Validation: `pulumi up` with these fixes should land the `seed-mgmt` output's `pendingDependencies`
empty (currently shows the two services as `inactive`).

=== 2.B — Greenfield the first workload cluster (bioskop-wrkld)

[IMPORTANT]
====
MECHANISM SETTLED (2026-09-07). The workload grow is **GitOps-in-mgmt**: a synthesis run renders the
workload CAPI CR set onto `manifests/<host>-mgmt` — the branch the *management* cluster's own Flux
tracks — so Flux applies the CRs to the management API and CAPI/CAPN reconcile them into a *different*
cluster `<host>-wrkld`. The CRs live where CAPI runs (the management cluster); the `-wrkld` branch
carries only that workload's app stack, reconciled by its own Flux once it is up. There is no
imperative `kubectl apply`. The delivery model is specified in
link:manifests-rendered-branches.adoc[Manifests Rendered Branches]; the Stage A boundary in
link:../bootstrap/stagea-stageb-handoff-contract.adoc[the handoff contract]. The work items below are
the CR artifacts to author as manifest units under the `cluster-api` domain, rendered onto the `-mgmt`
branch (CAPN per-remote identity is a separate work item, still valid). The granular foundations
backlog + dependency DAG for this phase (the workload-targets carrier, the single-cluster render
baseline, kube-vip, dataplan, Incus project) lives in
link:workload-grow-foundations.adoc[Workload Grow — Foundations Roadmap].
====

Once 2.A lands, the *first* CAPN-managed cluster is `bioskop-wrkld` — a *separate*, greenfield HA
control plane, *not* peers of the management cluster.

Work items:

. *Define a `Cluster` + `LXCCluster` for `bioskop-wrkld`* targeting the `bioskop` incus remote. `seed-mgmt`
  publishes the handoff identity (management kubeconfig, `apiEndpoint`, per-remote CAPN identity secret)
  — Stage B reads these to install into the management cluster and populate the workload's Cluster spec.
. *Define `RKE2ControlPlane` + `LXCMachineTemplate`* (note: the CAPN CRD is `LXCMachine`/
  `LXCMachineTemplate`, not "IncusMachine") for the workload's `master + peer1 + peer2`. CAPRKE2
  *initialises* the first replica (`cluster-init`) and *scales up* the two peers that join it — this is
  greenfield, not a join against a pre-existing endpoint. kube-vip fronts the workload's own
  control-plane endpoint (`LXCCluster.spec.loadBalancer`).
. *Validate end-to-end*: `kubectl --context bioskop-wrkld get machines` shows three control-plane
  Machines reconciling; the workload's own `etcd` grows to three members; its `kube-apiserver` is
  reachable through the workload VIP throughout.

NOTE: `peer3` is dropped — a workload control plane is `master + peer1 + peer2` (three etcd members).

=== 2.C — Greenfield nikopol-wrkld + workers

After `bioskop-wrkld` is HA, greenfield `nikopol-wrkld` the same way over the node mesh plane
(`mammoth-skate`), then add workers to both via `MachineDeployment` shapes with the worker bootstrap
profile (`RKE2ConfigTemplate`, `agentConfig`). Workers are always a later sub-phase than a workload's
own control-plane HA.

== Phase 1 — publish the gitops domain to the workloads

There is *no operator-install backlog left*. The add-on surface is already built as manifest units:
Flux via `FluxOperatorManifestsUnit` (a `helm.cattle.io/v1` HelmChart, `installCRDs: true`) +
`FluxInstanceManifestsUnit` / `FluxRootManifestsUnit` / `SopsAgeSecretManifestsUnit`; Tekton and
cert-manager via `UpstreamYamlInclusion` / HelmChart the same way.

The GitOps model needs *no Porch*. The three GitOps layers are covered without it: *authoring +
variance* by CDK8s at build time (the `manifests` module → `gitops/`, with the `manifests.publish`
toggles), and *sync + reconcile* by Flux in each workload (Tier 1). Porch is the intermediate
*package-orchestration* layer (KRM `PackageVariant` fan-out) that only earns its place at
Nephio-scale (hundreds of targets, runtime package mutation); at this scale it would also be redundant
with CDK8s, which already occupies the authoring/variance niche. *Porch is descoped* — no
`PorchResourcesManifestsUnit`, no `gitops/porch-resources/*` on disk.

So the remaining architectural work is not "install operators" but *where the gitops domain publishes*.
Under the separation, Flux runs in *each workload* (Tier 1, autonomous), not in the management cluster.
The `manifests.publish.{domain}` toggles become the split: the `gitops` domain (Flux + its instance +
sops-age) publishes to the *workload* clusters; `cluster-api` publishes to the *management* cluster.
This is the domain-split by role — see the anchor, § _Materialization consequences_.

== Phase 3 — automation: tracking and bumping upstream artifacts

Once Phase 1 lands we will have ≥4 `release-vX.Y.Z.yaml` files committed under
`manifests/src/main/resources/upstream/`. Treat this as a versioned manifest of cluster components and
automate the bump cycle.

Goals:

* Single source of truth for "what version of upstream operator X is a cluster running."
* Mechanical upgrade: replace the file, bump the Java string, review the YAML diff, ship.
* Visibility: PR review sees what changed in the upstream artifact alongside our integration changes.

Concrete workstream:

. *Inventory.* Author a `docs/upstream-tracked-components.adoc` listing every tracked upstream (Tekton
  operator, Flux operator, cert-manager, CAPI operator, snapshot-controller-CRDs, …) with its current
  pinned version, source URL, and the layer that owns it. (Porch is *not* tracked — descoped.)
. *Bumper script.* Small flake script (`bin/bump-upstream-component.sh <component>`): re-fetches the
  latest release artifact, writes the new YAML to a new versioned filename, prints the diff against the
  old one, leaves the Java string update to the human (one place, easy to grep).
. *CI guard.* Build asserts that every `release-*.yaml` referenced by Java code actually exists in
  `src/main/resources/upstream/`. Catches typos and orphaned files.
. *Renovate-style automation* (later): periodic check, opens a PR per component when a new upstream
  release exists.

== Phase 4 — build cluster-required binaries via nix

The flox-env catalog flake (a nix flake at the root of the `flox-catalogue` branch) already builds
`kdns` + the headplane stack from source, and the `flox-nri-plugin` fork flake
(`github:seedmatic/flox-nri-plugin`) builds the plugin. Same path applies to the rest of the operator
binaries we currently consume as upstream container images.

Why bother: same reason flox-injected workloads beat per-image baking — single nix store across host
and pods, byte-for-byte reproducibility through `flake.lock`, no registry dependency, fast iteration.

Candidates, ordered by leverage:

. *clusterctl* — currently shipped via `curl` from `rke2lab-cluster-api-install.service`. Move it to a
  flox env so version pinning matches the same flake.lock as everything else. Pairs naturally with
  Phase 2.A.
. *kube-vip* — single Go binary, easy to flake-build. Replace the upstream container with a
  flox-managed version. Lower priority now that the daemonset is healthy, but the leverage argument
  still holds.
. *Tekton operator* — Go-built, but more involved (multi-binary, embedded assets). Phase 4.B candidate
  after the simpler ones land.
. *Flux operator* — evaluate after Phase 4.A pieces land (shipped today as an OCI HelmChart, so the
  "build from nix" question is a later, lower-leverage one).

Open question for each candidate: do we replace the **operator container image** referenced in the
upstream release.yaml (transform hook in `UpstreamYamlInclusion` to swap the image tag), or do we build
a **separate workload that calls the same controller code** (more work, more control)? For phase 4.A
(clusterctl, kube-vip) the answer is "image swap." For Tekton it's likely "image swap" too, but the
diff is bigger.

== Order of operations summary

Recommended execution order — respects what unblocks what, leaves room to skip:

. *Phase 2.A CAPN materialization + systemd ordering fix* — unblocks Stage B; the resume point. Both
  incus remotes registered.
. *Phase 2.B greenfield `bioskop-wrkld` (master + peer1 + peer2)* — the first workload HA control plane.
. *Phase 1 publish the gitops domain to the workload* — the add-on surface is already built; this is
  the `manifests.publish` split, once 2.B has a cluster to host its Flux.
. *Phase 2.C greenfield `nikopol-wrkld` + workers* — the second workload, then worker scale-out on both.
. *Phase 3 tracking + bumper script* — once the upstream inventory is non-trivial.
. *Phase 4 nix builds for clusterctl, then operator binaries* — opt-in, per-component.

== Notes that don't fit a phase but should not be lost

* `RuntimeRke2ConfigLayer` adds `rke2-snapshot-{controller,controller-crd,validation-webhook}` and
  `rke2-ingress-nginx` to RKE2's `disable:` list. The original intent was likely "openebs-zfs ships its
  own snapshot stack" — but openebs-zfs only ships the *controller container*, not the CRDs. Reconcile
  this when wiring the workload gitops/add-on surface.
* `rke2lab-cluster-api-install.service` and `rke2lab-capn-provider-install.service` were observed as
  `inactive (dead)` after a fresh boot because their `Requires=` prerequisite
  (`rke2lab-networking-manifests.service`) became active *after* `rke2lab.target` had already settled.
  The services are queued + dropped. `systemd show -p WantedBy/Wants` lists them; `Result=success` is
  misleading. Phase 2.A covers this.
* The CSI snapshot CRDs `volumesnapshots.snapshot.storage.k8s.io` etc. genuinely don't exist on the
  cluster despite RKE2 attempting to install them — confirmed by `kubectl get crd | grep snapshot`
  returning only the openebs-zfs internal types. RKE2's logs show "Extracting …
  rke2-snapshot-controller-crd.yaml" followed 27 seconds later by "Deleting manifest …
  rke2-snapshot-controller-crd.yaml" because of the project's `disable:` list.
* The deprecated branch `deprecated/rke2lab-pre-pulumi-main` shipped Tekton via raw kpt-rendered
  upstream YAML in `rke2.d/bioskop/master/catalog/cicd/tekton-pipelines/release-operator-v0.78.1.yaml`.
  Same approach now lives in `UpstreamYamlInclusion`; `release-v0.79.1.yaml` is its current pinned
  successor.
* `BootstrapIdentity` / `NetworkTopology` / `ComponentVersions` records are in place under
  `layers/common/profiles/`. `ComponentVersions` is currently empty — fill it as Phase 3 introduces
  version tracking, and graduate per-layer literals (`kube-vip-version`, `tailscale-version`, etc.)
  into it.
