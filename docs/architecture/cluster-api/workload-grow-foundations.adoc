= Workload Grow — Foundations Roadmap
:toc: left
:toclevels: 3

The engineering backlog and sequence to lay *all* the foundations before the first workload cluster
(`bioskop-wrkld`) is greenfield-created. The management track is live (CAPI operator + the four
providers Ready on `bioskop-mgmt`, validated 2026-08-25); the *apply mechanism* is now settled
(model B — see <<premise>>). What remains is a set of code foundations, several of them
single-cluster today and net-new for a second cluster. This doc is the resume point: it records the
verified current-state baseline, the dependency DAG, and the design intent of the first foundation
(the workload-targets carrier).

====
Read the anchor first: link:management-workload-topology.adoc[Management / Workload Topology]. The

[[premise]]
== Premise — the settled model (B)

The workload CAPI CR set (`Cluster` / `LXCCluster` / `RKE2ControlPlane` / `RKE2ConfigTemplate` /
`LXCMachineTemplate` / `MachineDeployment`) lives on `manifests/<host>-mgmt` — the branch the
*management* cluster's own Flux tracks. Flux applies the CRs to the management API; CAPI/CAPN
reconcile them into the workload nodes. There is no imperative `kubectl apply`. **The CRs live where
CAPI runs** (the management cluster); a `-wrkld` branch carries only that workload's app stack,
reconciled by the workload's *own* Flux once it is up. This was reconciled across the three delivery
docs on 2026-09-07.

[[carrier]]
== Foundation 2a — the workload-targets carrier (design intent)

The render must stop meaning "the one current cluster" and start distinguishing *the cluster being
seeded* (the management cluster — `bootstrapIdentity()`) from *the target clusters it must create*
(the workloads, whose CRs it renders onto its own branch). That is the whole of 2a: carry a set of
*target* cluster identities into the management synthesis, and let a `cluster-api` unit derive each
target's blueprint on demand.

[mermaid,workload-grow-foundations-carrier,svg]
----
flowchart TB
  CFG["Pulumi config<br/>workload targets<br/>{ host, role=wrkld, topology }"]
  RIN["ManifestsRunbookInput<br/>+ workloadTargets amendment"]
  CTX["ManifestSynthesisContext<br/>bootstrapIdentity() = the MGMT cluster<br/>workloadTargets() = the CR subjects"]
  UNIT["cluster-api CR units<br/>(new)"]
  BP["ClusterNetworkBlueprint.builder()<br/>.cluster(target).node(n).build()"]
  CRS["Cluster / LXCCluster / RKE2ControlPlane<br/>/ LXCMachineTemplate / MachineDeployment<br/>on manifests/&lt;host&gt;-mgmt (paused)"]

  CFG --> RIN --> CTX --> UNIT
  UNIT -->|"per target"| BP --> CRS
----

Design points:

* **Two distinct identities, never conflated.** `bootstrapIdentity().clusterName()` stays the
  *management* cluster (the branch owner, the render subject). The workload targets are a *separate*
  set. A CR unit renders, for each target, resources named after the *target* — not after the
  management cluster.
* **Each target's addressing is derived, not carried.** A target identity is just
  `{ host, role=wrkld, topology }`; every span comes from
  `ClusterNetworkBlueprint.builder().cluster("<host>-wrkld").node(n).deriveRecipeModel().build()` —
  the addressing SSOT already handles the `wrkld` role, so the carrier holds identity atoms, not
  addresses.
* **Insertion points.** The target set enters as a new amendment on `ManifestsRunbookInput` (the
  membrane door), is exposed on `ManifestSynthesisContext`, and is consumed only by the `cluster-api`
  domain units. `BootstrapIdentity`'s own comment already anticipates a "peer cluster set".

[NOTE]
====
Anti-pattern to avoid: ❌ overloading `bootstrapIdentity().clusterName()` (or spinning a second full
`BootstrapIdentity`) to *be* the target — that erases the "which cluster does this render belong to"
invariant the branch model rests on. ✅ Keep the management identity singular and add a *targets* set
beside it; a CR unit reads the targets, everything else keeps reading the one identity.
====

== The remaining foundations (intent + target)

Each is detailed when tackled; here is the target artifact and the starting state.

* **1 — CR-set units.** New `cluster-api` manifest units rendering the CAPI CR set for each target
  onto `-mgmt`, `spec.paused` until that bare-metal is up. Depends on 2a (needs the target + its
  blueprint). Values: blueprint (VIP/CIDRs/topology) + facet + CAPN identity ref.
* **6 — domain split by role.** The `manifests.publish.{domain}` toggles become per-role domain sets:
  management = `cluster-api` + base + Tailscale client (+ the target CRs); workload = the app stack
  (`gitops`/`storage`/`mesh`/`cicd`/`high-availability`), no `cluster-api`. Today all seven publish
  to `bioskop-mgmt`.
* **2b — second render run for `-wrkld`.** The workload's app-stack branch is just another
  single-cluster render keyed by `role=wrkld` (config already frames "two clusters = two runs"). No
  multi-cluster plumbing beyond a second descriptor/run.
* **3 — dataplan cluster dimension.** `DataplanLayout` gains `<cluster>` so `bioskop-nixos` carries
  both the mgmt node's datasets and `bioskop-wrkld`'s (`tank/rke2lab/<cluster>/<node>/containerd`),
  plus the ndh side (`catalog.datasets`, `zfs-disko-config`, `zpool-init`). Parallel to 2a. Open
  sub-questions: producer emit mechanism, openebs-zfs adoption of a pre-existing dataset, ephemeral
  wipe owner.
* **4 — Incus project per cluster.** Project-per-cluster (`bioskop-mgmt` / `bioskop-wrkld`) with
  `features.images=false` / `features.networks=false`; the workload's `LXCCluster` remote scoped to
  its own project. Parallel to 2a.
* **5 — CAPN identity scoped to workload.** At least the workload's identity secret in `capn-system`
  (remote `bioskop-nixos`, `project=bioskop-wrkld`), referenced by `LXCCluster.spec.secretRef`; full
  per-remote generalisation (bioskop + nikopol) is a Phase 2.C concern.
* **kube-vip — per-workload VIP.** Derive the VIP from the blueprint
  (`vip().vipHostInetaddr()` → `10.80.15.10` for `bioskop-wrkld`) instead of the hardcoded
  `10.80.7.10`; and settle whether the workload's control-plane VIP is fronted by this
  `high-availability` unit or by `LXCCluster.spec.loadBalancer` (avoid two kube-vips).

== Deferred (does NOT block the first workload)

* Cluster PKI in git (sops) — required for the function-of-git *reproducibility* invariant, but
  CAPRKE2 generates fresh CAs on the first greenfield (`LookupOrGenerate`). Seal before relying on
  re-seed.
* Full per-remote CAPN identity (nikopol) — Phase 2.C only.
* Hygiene: `DNSConfigForming` (>3 nameservers), `rke2lab-*-manifests.service` ordering after
  `rke2.target`, the snapshot-CRD `disable:` reconcile.

== Sequence

. **2a** — the workload-targets carrier (the foundation the render chain roots on).
. **1** — the CR-set units (once 2a carries the target + its blueprint).
. **6** — the domain split by role, then **2b** — the second render run for `-wrkld`.
. **3 / 4 / 5** — dataplan, Incus project, CAPN identity — *in parallel* with 1 (independent of 2a).
. **kube-vip** per-workload VIP.
. Live checks (providers Ready, CRDs present, `node-base` image shared, projects created), then
  greenfield `bioskop-wrkld`.
