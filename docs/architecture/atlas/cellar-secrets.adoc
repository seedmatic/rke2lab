== Overview — one channel in, one filter out

rke2lab feeds on two kinds of operator input — the Pulumi *stack config* and the *secrets* provided
in the worktree — which, once inside rke2lab, are **the same kind of information**: a decrypted
string. The git sops smudge already reveals the secrets when the worktree is materialised, so by the
time the seed reads them a secret is indistinguishable from config. This document settles how the
root scenario **unifies** them onto the one existing amendment channel, and how the *only* real
difference between config and a secret — that a secret must not be written in clear when it reaches
the **cellar** — is honoured by a **clean/smudge filter** modelled on git and refined by sops.

The model is not invented. It is git's `clean`/`smudge` idea (a declarative attribute + a filter at
one boundary, never a trace of derivations), applied to the cellar as a **second store at rest**,
and refined by what sops adds over plain git: field-level marking by declaration, and encryption
**for recipients** rather than under a single local passphrase.

== The vocabulary — three axes that never mix

The design blocked for a while on "what is the role of a secret versus config?". The resolution is
that the question conflates three orthogonal axes. Keep them apart and the block dissolves:

[cols="1,3",options="header"]
|===
| Axis | What it is

| *Coordinate* = the consuming domain
| `AmendCoordinate(domain)` names *who consumes* the input — `bbox`, `incus`, `manifests`. Not a
config-vs-secret axis. Constrained by the seed-broker BETA guard: a contributor's coordinate MUST
match a served `SeedHandler`, or the assembler throws.

| *Role* = the kind of provisioning input
| The neutral `Amendment` vocabulary — `FACET`, `SOIL`, `WORKTREE`, `IMAGE`. `FACET` is the
operator policy the host read once. A secret is **not a new kind**: it is part of the same `FACET`
subtree. There is deliberately **no `SECRET` role** — inventing one would confuse *sensitivity* (an
attribute) with *kind of input* (the role).

| *Sensitivity* = a per-value attribute
| On *input*, a mark on an individual value, set **once by sops** (the sole authority — Pulumi's own
`secure:` provider is retired, see <<source>>). On *output*, sensitivity is re-declared by the scion
as a `Sensitivity` at `store` (a harvest is produced dynamically — no stable path to hang an input
attribute on), and honoured OSGi-side by the `CellarCipher`. Same axis, two boundaries: sops marks
what enters, the scion declares what is sealed. Not a role, not a section.
|===

**Config and secrets are the same kind (`FACET`); they diverge only at the cellar filter.** That is
why the block felt intractable — it was a search for an *input* difference that does not exist; the
only difference is on *output*.

== Store & fetch — clean / smudge

The seal is applied **OSGi-side** by `CodecCellar` via the `CellarCipher`, *before* the payload
crosses; the scion declares `Sensitivity` at `store`, so the mark rides with the harvest — no side
registry, no coordinate lookup at the host. `PulumiCellar` persists the opaque result without any
crypto (the `OpaqueCellar` contract, honoured literally — it never sees clear nor holds a key).
Reveal needs no flag: the sealed wrapper **self-identifies**.

== git ↔ sops ↔ cellar

[cols="1,1,1,1",options="header"]
|===
| Concern | git | sops | cellar (this design)

| store at rest | object store | file with `ENC[…]` values | Pulumi state → git
| into store | `clean` | encrypt | `CodecCellar` seal via `CellarCipher` (OSGi)
| out of store | `smudge` | decrypt | `CodecCellar` reveal via `CellarCipher`
| what's marked | `.gitattributes` (path→filter) | `encrypted_regex` / `sops:encrypted` | `Cellar.store(…, Sensitivity)` — the scion declares
| granularity | whole blob / file | field (regex) | envelope (≈ blob)
| recipients | — (local) | age keys — operator + cluster | *passphrase → age via `jagged`* — the **cellar's own**, not `.sops.yaml`'s
| self-describing | — | `sops:` metadata block | the sealed wrapper self-identifies
|===

NOTE: The cellar's recipients are NOT the git repo's. `.sops.yaml` / `.gitattributes` govern who can
decrypt the *repository*; the *cellar* is a second store with its **own** recipients — who may reveal
a harvest (the seeding-cluster → seeded-cluster relation). The cellar cipher takes its recipient /
identity config from a cellar-owned home (a passphrase in the degenerate mono case), never by reading
`.sops.yaml`. Conflating the two policies would be a genuine error; the `CellarCipher` seam keeps them
apart. The cluster's age identity (minted by `ssh-to-age`) *may be reused*, but the policy home is the
cellar's, not the repo's.

== What is feasible, and what is not

[cols="1,3"]
|===
| ✅ *Declarative marking*
| Name what is secret *by declaration*, the way `.gitattributes` and `encrypted_regex` do. For the
cellar this is the `Sensitivity` the scion states at `store` — a declaration at the point the harvest
is born, not an attribute hung on a stable path (a harvest has none). The filter acts at one boundary.

| ❌ *Tracing derivatives*
| Java has no native taint, and any mark is lost the moment a value flattens to a JSON string
crossing the OSGi seam. A leaky taint is *worse than none* — false confidence. A derivative that
must stay secret is *re-declared* where it is born, exactly as git needs a second `.gitattributes`
line for a rendered file.
|===

== The source model — two homes, one authority, one channel

Operator input has two tracked, sops-governed homes, under **one encryption authority** (sops) and
merged into **one amendment channel**:

* *Stack config* — `Pulumi.dev.yaml`, tracked and `filter=sops-yaml` in `.gitattributes` like
  `.secrets`. Pulumi's native secret provider (`encryptionsalt` / `secure:` / `pulumi config set
  --secret`) is **retired**: the git smudge means Pulumi only ever reads plaintext in the worktree,
  and sensitivity is marked by sops alone. This avoids two encryption authorities fighting over one
  file.
* *Shared secrets* — the sops YAML (`.secrets`) that also serves non-seed tooling (nix, flox, shell:
  cachix, tailscale, docker, github). Those consumers do not speak Pulumi, so this file cannot fold
  into the stack config; it stays a separate git-sops home.

Two rules keep the tracked config free of per-worktree noise:

* `worktree.dir` is **removed from config and derived at runtime** — the root already knows its own
  worktree; storing it would collide across worktrees. The derivation is now the `Worktree` OSGi
  component (`osgi/domains/worktree`): a jgit-free service that self-locates its root by walking up
  to the enclosing `.git`, so a launch from any subdirectory still resolves the real root, with jgit
  sealed behind the implementation. OSGi consumers reference the service directly (the incus scion,
  for the root it anchors paths on and the HEAD provenance the staging entry freezes); the flat host
  reads the same facts across the broker (the GROW beat its root, the entry gate its clean/dirty
  state) — no jgit type crosses the seam. (The component's own contract spec is the master's to
  write — tracked as SPEC_COVERAGE debt on the `worktree-contract` package; see the
  cluster-seed-scenario handoff.)
* Per-worktree preferences (e.g. `logging.level`) live in an **untracked local overlay**, merged by
  the root at read time; the tracked file carries only the shareable.

NOTE: `ssh-to-age` stays a *domain transform*, not part of this unification. It feeds sops for Flux
(the in-cluster gitops decryption key derived from the cluster SSH key). A pure-Java age codec
(`jagged`) exists, but it is *age only* — it does not implement sops, nor the SSH→X25519 conversion
`ssh-to-age` performs — so the `ProcessBuilderSshToAgeConverter` edge remains the single door to the
CLI.

== The recipient gap and the `bench-cellar` thesis

The one thing sops has that the cellar lacks is **recipients**. The `CellarCipher` seals under a
single local passphrase today (`PassphraseCellarCipher` — an AES-GCM seal keyed by PBKDF2 over a
dummy passphrase, the degenerate case that "holds no secrets") — which
works only while the writer and the reader are the same party (the single live management node, today
— host-indifferent, currently on nikopol). The moment the cellar travels (the "git-backed cellar
tomorrow" the `OpaqueCellar` contract anticipates — which is exactly the *function-of-git* invariant:
the cellar PKI moves out of Pulumi state into sops-in-git so the management cluster is reconstructible
from git; see the anchor, link:../cluster-api/management-workload-topology.adoc[Management / Workload
Topology] § _Function of git_), a passphrase breaks: it would have to be shipped. sops solves exactly this by encrypting **for a set of recipients**; the `CellarCipher`
generalises to the same, with `jagged` (pure-Java age) doing the multi-recipient key-slot. rke2lab
already mints a cluster age identity (`ssh-to-age` on the cluster SSH key) that the cellar's recipient
config *may reuse* — but the config home is the **cellar's own**, never `.sops.yaml` (which is the
repo's recipient policy, a different set). The passphrase is just the degenerate single-local-recipient
case of the same `CellarCipher` seam.

NOTE: The concrete first traveller is the next rke2lab step, already scoped by the management/workload
separation: the *management* cluster (host-indifferent, seeded by `seed-mgmt`) greenfield-creates the
*workload* clusters. The management cluster's cellar/secrets (CAs, tokens, CAPN identities) must be
readable by the *seeded* workloads — i.e. sealed *for their recipients* — which is precisely the
multi-recipient case this thesis proves, and precisely what function-of-git needs (a git-backed cellar
sealed for management + workload recipients). Today's single-node setup (seed + cellar on the same host)
is the degenerate one-recipient prelude to it.

A disposable `bench-cellar` proof (mirroring `bench-startlevel` / `bench-scr` — real bnd bundles in
embedded Felix, plain `@OsgiWorld` JUnit) proves the *seam* holds as recipients grow. *BUILT and
green* at `osgi/runtime/bench/bench-cellar` (`CellarSeamTest` + `CellarAdditivityTest`):

. *Roster* — a `clean` component's `@Reference(MULTIPLE)` over `Recipient` addresses the blob to
  every bound recipient, at boot and at runtime.
. *Independent smudge* — a `smudge` bound to one identity recovers the payload from a blob addressed
  to a *set* including it — no shared passphrase.
. *Additivity* — adding a recipient at runtime does not break the existing ones (the thesis).
. *Anti-cheat* — a smudge whose identity is not a recipient stays unsatisfied (`null awaitService`).

The crypto is a *faithful stand-in* (a data key wrapped once per recipient — the sops key-slot
shape), not real age: the bench proves the OSGi seam and the multi-recipient property, not the
cipher.

NOTE: A fifth thesis, `CellarResolutionModeTest`, was added to engrave a lesson the roster mechanism
depends on: the `MULTIPLE`/`DYNAMIC` reference binds runtime recipients live, where a `STATIC` one
snapshots at activation and misses them — and `policyOption` (GREEDY) is a *no-op* on a dynamic
multiple. The full model lives in
link:../patterns/service-contributors-views-adapters.adoc[the contributors pattern §
"Contributor resolution"].

== Implementation sequence

Ordered *foundation → live wiring → bench* — the working single-recipient case ships live first; the
multi-recipient generalisation is proven at the bench afterwards, when the cellar actually travels.

. *Foundation* — this document (the vocabulary lock + the model). ✅ committed.
. *Live wiring (single-recipient)* — on the live master: (a) the `CellarCipher` seam +
  `Cellar.store(…, Sensitivity)` + the `CodecCellar` clean/smudge branch that honours it OSGi-side
  (`PulumiCellar` reduced to an opaque byte store), with the **passphrase — the degenerate
  single-local-recipient case** and its own cellar-owned recipient config home; (b) the unified
  two-file input + per-coordinate contributors + `worktree.dir` derived at runtime + the untracked
  local overlay. Ships working value now, covered by its own tests. Wire the first real consumer
  (bbox transport) independently — it needs no cellar mark (its password never reaches the cellar).
. *`bench-cellar` proof (multi-recipient)* — the recipient seam on the disposable bench (clean-for-N
  / smudge-per-identity / additivity / anti-cheat / resolution-mode). ✅ *BUILT and green*.
. *age/`jagged` cipher* — ✅ *SHIPPED* as `AgeCellarCipher` (`cellar-cipher-age`): the passphrase
  generalised to age over `jagged`, sealing to the `rke2-cluster` ssh key (the *management-seeds-workload*
  generalisation). The recipient config is the ndh key inventory (`NdhKeystoreReader`), the cellar's own
  home, never `.sops.yaml`. Multi-recipient key-slots (management + workload) remain the next widening.
