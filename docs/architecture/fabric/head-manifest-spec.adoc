= Spec — The seedmatic head manifest
:toc: macro
:toclevels: 3

toc::[]

**Status:** 📐 spec — the vision, decided by the operator on 2026-10-08 and 2026-10-09 after a
brainstorm, a post-mortem and three reviews by the integration session. The last review replaced a
design that made a cyclic graph safe with a graph that is acyclic by construction. How today's code
moves to it (before and after) is in link:../atlas/flake-chain.adoc[the flake-chain atlas]. Nothing here
is built except one tool per pass (nix-flake-commons `fd6f361`). The first increment is the relock in the
nix provisioning layer (§ <<first-increment>>); everything in the cluster comes after it.

== Overview

Every seedmatic flake is reached from other flakes: it is pinned as an input, its outputs are read
(the netplan contributions, the CRDs staged into the synthesis), and its relock is requested. Today what
a flake *is*, and how it relates to the others, is scattered across `flake.nix`, `flake-registry.json`,
the arguments each repo passes to `lib.mkRelockApp` (including `consumers`, a list a repo writes about
repos that pin *it*, and the catalog hop), and committed JSON at the root of rke2lab. Two of the pin
relations are cycles (rke2lab ↔ ndh, ndh ↔ nnh), which the chain cuts with `follows = ""` and bounds with
a visited list.

The vision has three parts:

. **A head owns its manifest.** The unit is the *head* of a branch, `(repo, branch)`, that is a flake
  or a data branch. Each head describes itself in `.seedmatic/`, as each repo describes itself to GitHub
  in `.github/`. Nobody writes another head's description.
. **The pin graph is acyclic by construction.** A contribution, a datum one head publishes for another to
  aggregate, lives on its own **orphan data head**, published by development and never by a relock. The
  only edge left is the pin of a lock, and the pins form a DAG without anything being declared or proved.
. **One local rule, two modes.** Every head applies the same rule with the same tool. While the fabric
  is bootstrapped, heads are inert and the rule runs as an *execution plan played as a call tree*. Once
  the clusters live, heads are peers and the rule runs *peer to peer*.

== Decisions

[cols="1,5",options="header"]
|===
| # | Decision

| V1
| **A head is the unit.** Every branch carries its manifest. A session branch inherits `develop`'s and
may change it. A reader reads the head it resolves: `develop` by default (the registry is branchless),
or the branch a local overlay aims at. The key of a head is `slug[:branch]` everywhere.

| V2
| **`.seedmatic/` is the extension point, one file per facet.** `.seedmatic/git-head.json` holds the
core; a logic that needs to say something adds its own file. Relock's only facet is its trace,
`.seedmatic/relock.json`, rewritten in the commit of a change. Git merges per file, so one owner per
file is one owner per facet.

| V3
| **One edge type: the pin of a lock.** A root input of `flake.lock` that is a string, matched to a head
by `original.id`, is an edge; a list is a `follows`, not an edge. Nobody declares an edge.

| V4
| **A contribution lives on an orphan data head.** rke2lab's (`network-blueprint.json`,
`dataplan.json`) on `rke2lab:fabric-plan`; nnh's (its fabric segments, today a literal) on
`nnh:contribution`. The aggregator pins them as data (`flake = false`), and so does the contributor
itself, which keeps **one copy**: the files leave rke2lab's root, and `lib.networkBlueprint` becomes
`fromJSON` of the pinned file, with rke2lab's own helpers (`vmnetSupernet`, `deriveMacs`) computed over
it in rke2lab. ndh reads only the data.

| V5
| **A contribution changes by development, never by a relock.** It is a function of its head's sources
only, so a relock pass never has to regenerate it. `nix run .#publish-plan` regenerates it, commits it
on the orphan, pushes the orphan, and bumps the contributor's own pin of it, in the developer's change.
A relock never writes an orphan: that would be a hop under another name.

| V6
| **A mandatory pre-push hook fails hard, with what is needed to fix it.** rke2lab's `.githooks/pre-push`,
chained by the global `core.hooksPath` dispatcher, refuses the push while the published contribution is
not what the pushed sources produce, or while rke2lab's lock does not pin the orphan's head. The same
checks are flake checks (`blueprint-fresh`, `dataplan-fresh`), for CI and for the plan.

| V7
| **The regeneration does not depend on ndh.** It is the one cycle the locks cannot show: ndh pins
`fabric-plan`, produced by code built from rke2lab's flake, which pins ndh. A check proves it, cheaply:
the `drvPath` of the regeneration is the same with the `ndh` input overridden by an empty flake.
`publish-plan` runs it before publishing, and it is a flake check.

| V8
| **The impact guard measures `packages`, `apps`, and the configurations.** The `drvPath` of each
`nixosConfigurations` and `darwinConfigurations` top level, evaluated with `system.configurationRevision`
neutralised (ndh sets it to `self.rev or self.dirtyRev`, `flake.nix:395`, which moves 9 of its 12
configurations on every commit). A contribution reaches the hosts only through the configurations; a
moved `fabric-plan` pin is therefore carried like any other bump. Measured stable on 2 of the 12
configurations; 1a sweeps the 12.

| V9
| **The list of heads is the seat's flake registry**, orphans included: `seed-incluster`,
`flox-catalog`, `fabric-plan`, `nnh-contribution` each map to their repository and branch, as
`seed-incluster -> rke2lab:seed-incluster` already does.

| V10
| **flox-catalog is an ordinary head.** It pins rke2lab, so the plan reaches it as a dependent of
rke2lab. Its own `#relock` re-locks its envs **after** its inputs, through an "after inputs" artifact of
the tool. There is no hop: no head's relock carries another.

| V11
| **One tool per pass.** The tool is known by its code (`lib.relockToolId`); every head's relock in a
pass is built on it, and a relock of other code refuses. ✅ Built, nix-flake-commons `fd6f361`.

| V12
| **Fail hard, with the context going up.** A pin cycle, a stale contribution, or a failed relock is an
error that names the head, the edge or the file, and the command that fixes it.

| V13
| **Bootstrap first.** The first increment is the relock in the nix provisioning layer, in call-tree
mode. The cluster mode comes after, and waits on two other chantiers (§ <<dependencies>>).

| V14
| **In the cluster, Tekton runs, Flux applies.** A relock is a pipeline. Flux applies the rendered
manifests and never runs one.

| V15
| **seed-incluster is the fabric's delegate in the cluster.** It adopts the heads (the change of mode
is an adoption), and plays the integration of work sessions.
|===

=== The files

[source]
----
.seedmatic/
  git-head.json   the core: schema, id
  relock.json     the relock facet: the trace of the last change (wave, tool, bumped, dropped)
----

[source,json]
----
// .seedmatic/git-head.json
{ "schema": "seedmatic.git-head/v1", "id": "rke2lab" }

// .seedmatic/relock.json, on rke2lab
{
  "schema": "seedmatic.relock/v1",
  "status": { "wave": "…", "tool": "98003774…",
              "bumped": { "flake-commons": [ "83c2364", "5d1a9b5" ] }, "dropped": [ "nixpkgs" ] }
}
----

The rules of the envelope:

. The core holds only the identity (`schema`, `id`; `id` only when it is not the name). Everything
  else is a facet, one per file.
. A facet has **one owner**, the logic that writes it, and its own versioned schema.
. A trace is written only by its logic, in the commit of a change, never in a commit of its own.
. A reader **ignores** a facet it does not know; a version of a facet it knows badly is an error.
. What the lock says is never copied.
. A manifest is **data, never a command**: no field makes an automation run something.

An orphan data head carries no manifest of its own: it is a head of its repository's registry entry,
and its repository's develop describes it.

=== The hook's message

A hook that only says « stale » sends the developer looking. The refusal carries the contribution, its
file and its orphan; **both fingerprints, each with what it measures (`of`: head, revision, file) and how
(`method`: the command that produces it)**; the keys that differ, not only that the files differ; and
the exact command that fixes it.

[source]
----
REFUSING push: the contribution `network-blueprint.json` on rke2lab:fabric-plan is stale.

  published : sha256-3f2a…  of rke2lab:fabric-plan @ 8c41d02 — network-blueprint.json
  expected  : sha256-91bc…  of rke2lab:develop @ 5e32b50 — nix build .#networkBlueprintJson
  changed   : segments[vmnet].cidr, clusters.bioskop-wrkld

  Your change to rke2lab's model alters what ndh will read.
  Fix:   nix run .#publish-plan      # regenerates, commits on rke2lab:fabric-plan, pushes it
  then:  git push                    # again
----

[source]
----
REFUSING push: rke2lab pins rke2lab:fabric-plan @ 8c41d02, but its head is 1e77a90.

  rke2lab would read one contribution and ndh another.
  Fix:   nix flake update fabric-plan && git commit --amend --no-edit flake.lock
  then:  git push                    # again
----

The hook needs the network: it reads the orphan's head on GitHub, with `--refresh`, and treats a
fallback to nix's cache as a failure (§ <<no-cache>>).

== One local rule, two modes

The rule, the same in every head and in both modes:

[quote]
____
When an input I depend on changes, I relock myself with the pass's tool: I bump, the impact guard drops
what moves nothing I export, I commit my change with its trace in `.seedmatic/relock.json`, I push, and
the heads that pin me are reached next.
____

A data head has no relock: it moves only by `publish-plan`. Its dependents see it move as an ordinary
pin, and the guard carries the bump when a configuration moves.

=== Bootstrap — an execution plan played as a call tree

While the fabric is bootstrapped, no head can react. The head that starts computes the plan: the heads
from the registry, the edges from their locks, read on GitHub with `--refresh`. The edges must form a
DAG, else the plan fails with the cycle, naming each edge and its head. The order is the topological
order of the DAG; the starting head plays it, which may run its own relock after others. After a
`publish-plan`, the start is the contributor, and the plan covers the dependents of the contributor
**and of its orphans**: after rke2lab's, ndh runs first (it pins `fabric-plan`), then nnh and nch, then
rke2lab (it pins ndh), then flox-catalog.

Each head's relock calls the next: the call tree is also the path an error travels back up, with its
context, to whoever knows. Each head runs at most once per plan.

==== A dry run of the wave

A wave can be started dry, to see where it goes before anything is pushed. Each head is relocked in a
local clone with no push remote. A downstream head sees the upstream head's unpushed result through
`--override-input <id> path:<clone>`, on **every** path where that head appears in its lock, transitive
ones included. The output is the predicted wave: the heads that would commit, their bumps, and the
noise of derivations with `src = ./.` marked as such. Before any real push, a lock that contains a
`path:` or `git+file:` entry is refused.

=== Cluster — peer to peer

Once the clusters live, every head is a peer that reacts to its inputs moving. **Tekton runs, Flux
applies**: a relock is a pipeline, run through Tekton's own entry point (PaC), and the rendered
manifests reach the cluster through Flux. « Relock → render → Flux applies » is an order of pipelines. A
publication stays a development act: in the cluster it is made from a workspace, with the same hook.

== The levels, and what each can do today

The same platform reads differently depending on where you stand. Three machines are stacked under the
clusters: **the Mac** (bioskop, nikopol), under nix-darwin from ndh, hosting the operator's seats; **the
NixOS guest** `<host>-nixos`, a Tart VM that boots from the generic image `nerd-nixos` and then takes its
host's name, and that is the Incus host; **the Incus instances**, NixOS `lxc-container` images built by
rke2lab, which are the RKE2 nodes.

[cols="2,2,3,3",options="header"]
|===
| Level | nix | GitHub credential, push | Role

| Mac seat
| yes, flox seat
| `gh auth token`, read and write
| publishes contributions and starts the bootstrap mode — **the only writer today**

| NixOS guest
| yes
| only `nixos-rebuild-gh`, interactive
| consumes `develop`

| Incus node
| store and cache
| `contents:read` only, by design
| consumes `develop`, through the guest's build

| Cluster
| in pods, through the flox NRI plugin
| PaC's per-run App token, or gtm's `github-token-write`
| runs the peer-to-peer mode (later)

| Workspace
| through the flox NRI plugin (planned)
| not designed
| a work session, with its agent (later)
|===

The guest and the nodes never start anything: they build the head of `develop`. That is why the trace
lives in git, in the commit of each change.

== What any writer must provide

[cols="2,4",options="header"]
|===
| Need | Why

| `nix`, with network to GitHub
| what it builds is fetched from GitHub; the hook reads the orphan's head there

| a GitHub token with `contents:write` on **every** repo it writes
| a token that reaches only some repos stops the work halfway

| a canonical `TMPDIR`
| nix refuses a `git+file` flake that crosses a symlink once it is dirty (measured: `/tmp` on macOS)

| a nix cache it can **isolate** for proofs
| nix caches `revCount` by revision: a warm cache can hide a failure (measured 2026-10-08)

| a git identity, and signing where a branch requires it
| the commits are the trace
|===

[[no-cache]]
== Reading the heads without the cache

A lock or an orphan read from a stale cache makes every reader lie, silently. A reader therefore reads
with `--refresh`, and treats nix's fallback messages (`using cached version`, `unable to download`) as a
failure, the rule relock already applies to a bump. It is proved, not asserted: a bats case in which the
fake `nix` emits the fallback warning, with the mutation that drops the check; and a real read with
`XDG_CACHE_HOME` pointed at an empty directory, then again through a warm cache with `--refresh` after a
push. Both reads must return the pushed value.

[[first-increment]]
== The first increment — relock in the provisioning layer

**1a**:

* the orphan data heads `rke2lab:fabric-plan` and `nnh:contribution`, their registry entries, ndh's
  pins of them (`flake = false`) in place of its pins of rke2lab and nnh, and rke2lab's and nnh's own
  pins (V4, V9);
* `publish-plan` in rke2lab (and its twin in nnh), the regeneration check against ndh (V5, V7);
* rke2lab's `.githooks/pre-push` and its message; the `*-fresh` checks compare the orphan (V6);
* rke2lab's relock no longer regenerates its contributions: `ownedArtifacts` goes (V5);
* the impact guard over packages, apps and the 12 configurations with their revision neutralised (V8);
* flox-catalog's own `#relock` (its call site exists, flox-catalog `flake.nix:269`) re-locks its envs
  as an "after inputs" step; the catalog hop leaves the tool (V10);
* `.seedmatic/git-head.json` and the trace `.seedmatic/relock.json` (V2);
* the plan: heads from the registry, edges from the locks, a DAG or fail; the call tree, failing hard
  with its context, once per head per plan (V3, V12).

**1b**: the dry run of the wave.

**Out of the increment**: everything in the cluster.

**Tests that bite**, each with its mutation: a pin cycle → an error naming each edge and its head; a
changed contribution → the guard carries ndh's bump (fails today: the guard projects only `packages` and
`apps`); a stale orphan or an unpinned orphan head → the hook refuses with its message; a regeneration
that reads ndh → `publish-plan` refuses; a relock of rke2lab → no contribution file written.

**Migration.** The ten `mkRelockApp` call sites move by ordinary commits, one per head, pushed in stack
order: nix-flake-commons first, then each consumer locked on it. The orphans are pushed before ndh's pins
of them. In nnh and nch, the bump of `ndh` past `050c8188` goes in the same commit, which removes the
transitive `claude-hub` node. No relock pass runs until all ten are pushed.

== Usage patterns

=== ✅ A contribution is published with the change that alters it

[source,bash]
----
nix run .#publish-plan    # regenerate, commit on rke2lab:fabric-plan, push it, bump the pin
git push                  # the hook checks the orphan and the pin
----

=== ❌ Writing another head's relations

[source,nix]
----
consumers = [ "github:seedmatic/ndh" ];   # ❌ rke2lab saying who pins it
----

A head knows what it pins, and its lock says it. What pins *it* is somebody else's fact.

=== ❌ An aggregator pinning a contributor's code

[source,nix]
----
rke2lab.url = "rke2lab";       # ❌ in ndh: a pin of rke2lab's code, back to the cycle
fabric-plan = { url = "fabric-plan"; flake = false; };   # ✅ the data only
----

=== ❌ Reading a `follows` as a pin

[source,json]
----
"inputs": { "rke2lab": "rke2lab", "ndh": [ "rke2lab", "ndh" ] }
----

`rke2lab` is a pin (a string). `ndh` is a `follows` (a list): it moves with `rke2lab`, and is not an
edge of its own.

=== ❌ A manifest that commands

A field that makes an automation run something turns a branch into an attack surface: with V1, every
session branch carries a manifest. A manifest states facts; the tool decides what to do with them.

== Troubleshooting

[cols="2,3,3",options="header"]
|===
| Symptom | Cause | Fix

| the plan names a pin cycle, with its edges
| a head pins the code of a head that pins it
| move the datum it reads onto an orphan data head, and pin that

| `REFUSING push: the contribution … is stale`
| the model changed, the orphan was not republished
| `nix run .#publish-plan`, then push again

| `REFUSING push: rke2lab pins rke2lab:fabric-plan @ …`
| the orphan moved, rke2lab's pin did not
| `nix flake update fabric-plan`, amend, push again

| `publish-plan` says the regeneration depends on ndh
| the `plan` jar's build reads something of ndh
| remove that read: it would close a value cycle the locks cannot show

| a blueprint change does not reach the hosts
| the guard does not measure the configurations (before V8)
| V8

| `using cached version` while reading a lock or an orphan
| nix served a cached answer
| retry with the network; never accept a cached plan

| a lock that contains `path:` before a push
| a dry run's override leaked
| redo the relock without the override
|===

== Open questions

. **Who starts a relock's PipelineRun** in the cluster: the PaC door on a push (one App, one webhook,
  so one entry through the root), or seed-incluster through the Kubernetes API?
. **Where `GitHead` objects come from**: rendered by rke2lab's synthesis (but nch and seat-roster are
  outside rke2lab's input closure), or discovered by the delegate on GitHub?
. **The heads list in the cluster**: the seat's registry exists only on the Mac.
. **Adoption**: where the fact that a head is adopted lives (a facet written by seed-incluster alone?),
  so that the Mac never relocks an adopted head at the same time.
. **seed-incluster's load**: separate the deterministic mechanics from the agent's host; keep its own
  head out of the reactive relock, since it redeploys itself only through rke2lab's render.
. **Security**: a session head carries a manifest; the boundary « reactive only on provisioned heads »
  must be a rule of the delegate.
. **Token reach, cost and pace of a wave**: whether the App and gtm tokens cover every repo; the time
  and API cost of a wave over ten heads that evaluate their configurations.
. **Other peer-to-peer logics**, each with its facet.
