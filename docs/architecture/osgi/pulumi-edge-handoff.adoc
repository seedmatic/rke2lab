= pulumi-edge — the first realised external edge (the `<target>-edge` template)
:toc: left
:toclevels: 3

[NOTE]
====
*Status:* SHIPPED on `feature/pulumi-edge` (2026-06-21), integrable into `design/pre-integration`.
The first concrete realisation of an *external edge* per the
link:../patterns/frontier-playability-model.adoc[frontier-playability model]. Build GREEN on the
full reactor (`./mvnw -pl :seed-outcluster -am clean package -Dmaven.build.cache.skipCache=true
-DskipTests=false`): `pulumi-edge` 29 tests, `pulumi-edge-testkit` 10, `seed-outcluster` 68 (1 skipped =
`@Tag` excluded `*LiveTest`), `doctor-contract-test` 34 — 0 failures, 0 errors.

This doc is the *reference template* the five remaining edges (dbus-systemd, incus, cluster,
host-filesystem, ssh-to-age) replicate. Read it as "how to extract a `<target>-edge`", not just "what
happened to Pulumi".
====

== What this is

`host/pulumi-edge` is the *single host-side home for every contact with Pulumi* — the state backend
(`com.pulumi.automation` reads) and the Automation API (`LocalWorkspace.up()` writes), mutualised
across all domains. Before this work the Pulumi contact existed "in spirit, scattered": the read face
lived in `host/pulumi-automation-ext`, while the write face (`PulumiInterventionLedgerWriter`) was
*stranded* in `exec/seed-outcluster/.../controlplane/bdd/` — an impl of a doctor port living inside a
consumer module. This consolidates both faces into one named edge.

The name follows the model's reserved vocabulary: an external edge is named `<target>-edge`, never by
direction (`ingress`/`egress` stay in prose and method names to avoid the k8s `Ingress` collision)
and never per-consumer (no `doctor-pulumi` private adapter). One target → one edge → every domain
that touches it goes through the same door.

== Why it stays in the host world (and why that does not weaken the port)

Pulumi is *non-playable*: `com.pulumi.*` carries native deps, `ServiceLoader` lookups, and
classloader assumptions that cannot resolve inside a Felix bundle. So the edge's impl lives in
`host/`, by the playability axis.

Playability is *orthogonal* to the port, though. Reading the state in pure JDK would still *reach* the
state backend — it is still an edge, and the port still protects the domain from the backend's file
format, location, and CLI flags. So `pulumi-edge` keeps its ports even though it could never migrate
to OSGi. For a *playable* target (incus, cluster, host-filesystem, ssh-to-age) the same extraction
applies, with one difference: the edge impl *can later migrate host→osgi* with no change to callers,
because they were already crossing the port. The extraction recipe is identical; only the
world-of-residence differs.

== The shape (the template)

[cols="1,3",options="header"]
|===
| Layer | For pulumi-edge

| The domain (`-core`, osgi-world)
| `doctor-core` — the pure diagnostic model. Never imports the edge; never imports `com.pulumi`.

| The port (`-port`, the membrane)
| `doctor-contract` — `SnapshotSource` (the read seam) + `InterventionLedgerWriter` (the write seam) plus
  the pure gateway records (`SnapshotEntry`, `SnapshotView`, `Intervention`, `StackCoordinate`, …).
  Reached *identically* from the OSGi world and the host world. Pure: zero `com.pulumi` imports — the
  only Pulumi mention is a `{@link}` in Javadoc.

| The edge (`<target>-edge`, host-world here)
| `host/pulumi-edge` — the realised impl of *both* port faces over the file backend, plus the
  low-level contact types.
|===

What lives in `host/pulumi-edge` (package `io.seedmatic.rke2lab.pulumi.edge`):

* *Low-level contact* — `StackHandle`, `StackHistory`, `StackSnapshot`, `StackCheckpoint`,
  `PulumiBackendLayout`, and the `Stack*Exception` family. The single place that knows the on-disk
  `.pulumi/history/<project>/<stack>` convention and the `com.pulumi.automation` API.
* *Ingress impl* — `StackHandleSnapshotSource implements SnapshotSource`: reads the timeline,
  translates `StackHistory.Entry`/`StackSnapshot` into the pure `SnapshotEntry`/`SnapshotView`.
* *Egress impl* — `PulumiInterventionLedgerWriter implements InterventionLedgerWriter`: an out-of-run
  `up()` that registers one `InterventionResource` per append (the *rapatriated* stray).
* *Ingress impl (ledger read)* — `InterventionLedgerSource`: folds the stack timeline into the
  `InterventionLedger` the drift review consults.
* *Registry impl* — `LiveMedicalRecordRegistry implements MedicalRecordRegistry`: reconstructs a
  patient's `MedicalRecord` from live Pulumi state via `StackHandleSnapshotSource`.
* *Layout + resource* — `InterventionLedgerLayout` (the ledger's `StackCoordinate` + backend dir) and
  the package-private `InterventionResource` (the `ComponentResource` the writer emits).

== What stays OUT of the edge (the discipline that keeps it an edge)

The cut is "does this type *touch the Pulumi target*, or merely *consume the port*?":

* `DoctorAssembly` *stays in seed-outcluster* — it is the host-side *wiring* that picks impls
  (`new PulumiInterventionLedgerWriter(...)` vs a no-op) and reads the current `Patient` from
  `Deployment.getInstance()`. It touches `com.pulumi.deployment` but its job is assembly, not the
  edge contact. Wiring belongs to the executable, not the edge.
* `MedicalRecordDump` *stays in seed-outcluster* — a `main()` CLI tool that *consumes* the edge
  (`StackHandleSnapshotSource`) to dump a record as YAML. A consumer of the edge, not part of it.
* The `controlplane.bdd` doctor types (`ClusterReadinessProbe`, `DbusTcpSpecialist`, the scenarios)
  never reach Pulumi — they stay.

Consumers depend on `doctor-contract` only; *nothing in seed-outcluster imports `pulumi-edge` types except as
explicit wiring in `DoctorAssembly`/`RecordInterventionCommand`/`MedicalRecordDump`*. The membrane held:
no caller changed behaviour, only its `import` line moved from `controlplane.bdd.*` to
`pulumi.edge.*`.

== The testkit and the cycle constraint (a template gotcha)

`host/pulumi-edge-testkit` carries shared, main-scope test fixtures (`StackHistoryFixture`,
`GrpcChannelNoiseCapture`) so consumers register them *without a test-jar* (m2e does not resolve
test-jar classpaths — a main artifact resolves cleanly in the IDE).

The load-bearing constraint: *the testkit depends on the edge* (`testkit → edge`, for
`PulumiBackendLayout`). So the *edge cannot depend on the testkit*. Any edge test that needs a testkit
fixture must therefore live *in the testkit's own `src/test`*, not the edge's. This is why:

* the edge's `src/test` holds only the *self-contained mechanic* tests (`StackHandleTest`,
  `StackSnapshotTest`, `StackCheckpointTest`, `StackHistoryTest`, `InterventionLedgerLayoutTest`,
  `InterventionLedgerSourceTest`);
* the testkit's `src/test` holds the tests that *use a fixture or drive a real `up()`*:
  `StackHandleSnapshotSourceTest`, `PulumiInterventionLedgerWriterLiveTest` (egress live), and
  `LiveMedicalRecordRegistryTest` (white-boxes the package-private `backendDirFromUrl`, so it must
  share the package — same-package access, no visibility widening).

`GrpcChannelNoiseCapture` is a JUnit `Extension`, so the testkit declares `junit-jupiter-api` in
*compile* scope (not test) — the same rationale as `StackHistoryFixture` being main-scope. For the
doctor reconstruction fixtures it adds `doctor-contract-test` in test scope (`ReferralReplies`).

[TIP]
====
*Template rule:* if a `<target>-edge` ships a testkit that depends back on the edge, route every
edge test that needs a fixture through the testkit's `src/test`. Keep the edge's own `src/test` to
pure mechanic tests that need nothing but the edge + its port.
====

== The extraction recipe (replicate per target)

. *Find the scatter.* Grep the reactor for the target's library imports (here `com.pulumi`) and for
  impls of the target's ports. The edge is wherever those two coincide — often spread across `host/`
  and stranded inside `exec/`.
. *Name the module `<target>-edge`* under the world the playability axis dictates (host if
  non-playable; host-for-now if playable-but-not-yet-migrated). Rename the Java package to
  `…​.<target>.edge` so the module name and package agree.
. *Rapatriate the strays.* `git mv` every impl-of-a-port and target-contact type into the edge,
  preserving history. Move their unit tests with them; move fixture-dependent tests into the
  edge's testkit (cycle rule above).
. *Leave the ports untouched.* The domain keeps crossing `-port`; only the `import` lines of the
  edge's *own* types move. If a port's `.java` shows in `git status`, it should be a Javadoc `{@link}`
  only — never a real new dependency.
. *Keep wiring and CLI tools in the executable.* Assembly (`DoctorAssembly`) and consumer tools
  (`MedicalRecordDump`) are not the edge.
. *Verify by reactor, never by install.* `./mvnw -pl :<consumer> -am clean package
  -Dmaven.build.cache.skipCache=true -DskipTests=false`, then *count the surefire reports* — a
  `BUILD SUCCESS` with no `Tests run:` line means they were skipped.
