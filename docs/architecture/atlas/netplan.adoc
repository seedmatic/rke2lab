= Atlas L1 — Netplan address-plane view (where a node's addresses come from)
:toc: left
:toclevels: 3

_Level-1 (per-subsystem) view of the link:../integration-atlas.adoc[integration atlas] (L0)._
_L0 shows how this subsystem integrates with the others and the value that emerges; this file is the detail._

The address plane, host-side — the process that moves a node's externally-reachable address off the
*family's home LAN* and into its bare-metal's *own* segment. The contract this plane travels on lives
in link:../patterns/netplan-blueprint-single-source.adoc[the netplan blueprint SSOT pattern]; this view
carries the codebase↔vision delta as before/after figures.

== The thesis — a node's address stops depending on an authority we do not run

Each figure carries its own before/after in one frame (atlas convention). The red `BEFORE` block is
the *external addressing authority* the transition deletes — the residential router, its static DHCP
reservations, its `.lan` zone, and the shared L2 that mDNS rode on. The green `AFTER` block is the
self-contained per-bare-metal segment: an Incus `bare-br` bridge whose dnsmasq the host itself runs,
reachable from elsewhere over a tailnet subnet route.

The motive is not tidiness. `nikopol` is a laptop that connects through mobile hotspots, so *there is
no bbox to serve it*: every address and every name in the red block is unavailable the moment the
machine leaves the house. The green block has no such dependency — the authority is the host.

=== Diagram A — System context: BEFORE vs AFTER

Reads: the BEFORE has two authorities per node and rke2lab owns neither — the bbox serves the node's
`lan0` lease from a MAC-keyed reservation that ndh reconciles into it, and the same router serves the
`.lan` zone that is the only suffix an in-cluster pod can resolve. The AFTER has one authority, and it
is the bare-metal's own NixOS guest: `bare-br`'s dnsmasq serves both the lease and the `.<host>` zone,
and the tailnet carries reachability instead of a shared L2. The dashed edge `the external authority is
removed` is the whole point.

=== Diagram B — Container: the three layers and where the hinge sits

Reads: the stack is three machines deep, and naming them settles who can route. The *bare-metal* is
the physical Mac (the vz-host); the *Incus host* is a NixOS **vz guest** running on it; the nodes are
Incus instances inside that guest. In the BEFORE the Mac is transparent (the guest is bridged straight
onto the home L2) and every layer holds a home-LAN address. In the AFTER the **hinge is the NixOS
guest**, dual-homed by necessity: it holds the segment gateway `.1` *and* a LAN address, because
`baremetal-nat` masquerades the segment's public egress out of that LAN address.

The hinge cannot move up to the Mac. Tart falls back to vz NAT when no bridge interface is given
(`modules/darwin/tart-config.d/run.sh:419-423`), which would make the Mac the router for free — but vz
NAT hands out `192.168.64.0/24`, *identical on every Mac*, so it cannot be a per-host segment advertised
into the tailnet. The layer whose numbering we control is the guest, so that is where the gateway lives.

=== Diagram C — The four address tiers, and the one this migration repairs

Reads: the lab's addressing is four RFC-scoped spaces, each with a distinct *nature* — and the BEFORE
violates the first one. `bioskop-mgmt-lan` is a rke2lab-owned span (`192.168.1.128/29`, ASN 65010)

holds only by most-specific-prefix luck, not by structure. The AFTER gives each tier one nature:
rke2lab leaves the home tier entirely, and the fabric tier becomes the single plane on which anything
is reachable *across* bare-metals.

[[derived-carve]]
=== Diagram D — The carve becomes DERIVED: BEFORE vs AFTER

Reads: the BEFORE carves every cluster of every host out of ONE `/24` — the high half of the home LAN —
so `hostId` has to be a term *inside* the address (`128 + hostId*48 + roleId*16`,
`ClusterNetworkBlueprint.java:186`), and a single-node management cluster is squeezed into a `/29`. The
AFTER stops carving and starts *deriving*: the fabric slice is a pure function of the cluster name,
through the composition the blueprint already uses for everything else —
`clusterId = (hostId << 1) | roleId` (`ClusterNetworkBlueprint.java:163`), the same source that
generates the vmnet plane (`10.80.<clusterId*8>.0/21`), the ULA mirror
(`fd96:6924:3693:<clusterId><role>::/64`) and the MACs (`10:66:6a:4c:<clusterId>:<nodeId>`). The
`172.16` plane is the last one still outside that rule.

Two consequences worth stating separately. First, `derive()` needs *no new input*: `hostOf(clusterName)`
and `ClusterRole.of(clusterName)` are already computed a few lines above. Second, the design principle
*inverts* — in the home `/24` space was scarce (a `/29` for a cluster, a `/27` pool, a `/30` island
outside its own subnet); in a `/12` it is not, so the carve optimises for **legibility over density**. A
`/26` for six nodes is not waste, it is an octet you can read.

Third octet reads as `hostId*16 + slot`, mirroring the vmnet plane's multiple-of-8 aesthetic:

[cols="1,1,1,1",options="header"]
|===
| | host infra (slot 0) | mgmt (slot 1) | wrkld (slot 2)

| *bioskop* (`hostId 0`) | `172.16.0.0/24` | `172.16.1.0/24` | `172.16.2.0/24`
| *nikopol* (`hostId 1`) | `172.16.16.0/24` | `172.16.17.0/24` | `172.16.18.0/24`
| *test* (`hostId 2`) | `172.16.32.0/24` | `172.16.33.0/24` | `172.16.34.0/24`
|===

*One bridge per host, not per cluster.* `bare-br` takes `172.16.<hostId*16>.1/20`, so the per-cluster
`/24`s are an *addressing* convention, not separate broadcast domains. The ndh module changes only its
prefix, and the single `.<host>` DNS zone survives — which is the choice that keeps this cheap.

*Why `/20` per bare-metal and not the more legible `/16`.* `172.<16+hostId>.0.0/16` would give each
machine a whole octet, unbeatable to read. It is rejected for a reason that targets exactly the machine
this migration is for: `nikopol-vzhost` is a *corporate* Mac on a company-governed network, and
enterprise networks consume `172.16.0.0/12` heavily. A `/16` advertised into the tailnet is 512× more
exposed to an overlap with that network than a `/25`, and when it collides the tailnet route is what
loses — on the roaming machine, i.e. at the worst possible place. The `/20` keeps the derivation
identical, fits the *whole fleet* inside `172.16.0.0/16` (15 `/16`s of the `/12` stay untouched), and
cuts the exposure by 16.

=== Diagram E — The consequence chain: what the move forces

Reads: moving the address is the easy half. The BEFORE bakes that address and its names into artefacts
that outlive a reboot — the apiserver's serving certificate carries both the LAN host address and every
canonical node's mDNS FQDN (`RuntimeRke2ConfigManifestsUnit:189` and `:193`). So the AFTER is not a renumber,
it is a renumber *plus a cert reissue plus a name-form collapse*, and those three must ship together —
the same rule as the EROFS stack's "the ESP and the layers move as one unit".

[[fleet-ceiling]]
== The fleet ceiling — three planes, three different answers

Deriving every plane from one composition exposes a disagreement that hand-carving hid: *the three
planes do not agree on how many bare-metals the fleet may have.*

[cols="2,1,2",options="header"]
|===
| Plane | Ceiling | Why

| *pod / service CIDRs* — `podCidr = 10.<44+clusterId>.0.0/16`,
  `serviceCidr = 10.<48+clusterId>.0.0/16`
| *2 bare-metals*
| The two bases are only *4 apart*. `clusterId = 4` yields pod `10.48.0.0/16`, which **is**
  `bioskop-mgmt`'s service CIDR. Same defect in the v6 mirror (`fd00:44` / `fd00:48`).

| vmnet — `superNetworkCidr = 10.80.0.0/18`, clusters at stride 8 in the third octet
  (`clusterCidr = 10.80.<clusterId*8>.0/21`)
| *4 bare-metals*
| 64 ÷ 8 = 8 clusters, and `clusterId = hostId<<1\|roleId`, so `hostId` 0..3

| the fabric `/20` per bare-metal inside `172.16.0.0/16`
| *16 bare-metals*
| 16 `/20`s in a `/16` — the most generous plane, and the only one needing no change

| ULA — `clusterCidr6 = fd96:…:<clusterId>00::/56`, `clusterId` formatted `%02x`
| *128 bare-metals*
| 255 clusters — already a full byte
|===

[WARNING]
====
*The pod/service ceiling is not theoretical — it is reachable today.* `hostId()` already declares
`test = 2`, and `ClusterRole.of("test")` falls back to `MGMT` (ordinal 0), so the reserved `test`
identity derives `clusterId = (2<<1)|0 = 4` and therefore `podCidr = 10.48.0.0/16` — byte-identical to
the live `bioskop-mgmt` service CIDR. (A *blank* name does not get that far: `hostOf("")` yields `""`
and `hostId()` throws, which is the fail-fast working as intended — `test` is the identity that slips
through, precisely because it is declared.) Nothing has collided
yet only because no such cluster has been materialised; the *derivation* is already unsound, and the
next real bare-metal walks into it. Widening the plan must therefore **re-base** these two spans, not
merely stretch them.
====

=== The fix: make `clusterId` an explicit bit-field, then size every plane from it

The disagreement exists because `clusterId = (hostId << 1) | roleId` packs the two coordinates as
tightly as today's counts allow — one bit for the role, because there are exactly two roles. That is the
thing to loosen, and the ULA plane already tells us the target width: it formats `clusterId` as `%02x`,
i.e. it has *always* treated the cluster coordinate as **a full byte**. Making v4 agree with what v6
already declares is the coherent move:

[source,java]
----
// 6 bits host · 2 bits role — one byte, the width the ULA plane already assumes
final int clusterId = (hostId << 2) | roleId;
----

Sizing the planes for *32 clusters* (8 bare-metals × 4 roles) then makes every level land on a natural
boundary:

[cols="2,3",options="header"]
|===
| Plane | Sized for 32 clusters

| vmnet
| `superNetworkCidr` `10.80.0.0/18` → `10.80.0.0/16`. The stride is unchanged
  (`10.80.<clusterId*8>.0/21`) and 32 × 8 = 256 **fills the `/16` exactly**.

| pod / service
| re-based and spaced *by the ceiling* rather than by 4:
  `podCidr = 10.<POD_BASE + clusterId>.0.0/16` and
  `serviceCidr = 10.<POD_BASE + CEILING + clusterId>.0.0/16` with `POD_BASE = 128` → pods `10.128`-
  `10.159`, services `10.160`-`10.191`. Spacing by `CEILING` rather than by a hand-picked gap is what
  makes the disjointness *structural*: it stays correct when the ceiling changes. `POD_BASE = 128`
  (not a smaller multiple) because the pod block must also clear the vmnet supernet at `10.80` — the
  trap in the obvious choice: `POD_BASE = 64` puts `clusterId = 16`'s pod CIDR exactly on
  `10.80.0.0/16`.

| ULA
| unchanged — `%02x` already holds a byte, and each role `/64` sits inside its cluster's `/56` by
  construction. The v6 pod/service mirror re-bases with its v4 twin to keep the "digits match" property
  (`10.128` ↔ `fd00:128`). That pun is *visual* — a decimal integer printed into hex notation — so the
  bases must be checked in both readings: pods land in `[0x128, 0x159]`, services in `[0x160, 0x191]`,
  disjoint (sparsely filled, which is harmless).

| the fabric
| unchanged. `/20` per bare-metal at `hostId*16` holds 16 hosts, and each `/20` has 16 `/24` slots —
  one for host infra, four for roles, eleven spare. It was already the plane with headroom.
|===

`8 × 4` rather than `16 × 2` because the role axis is the one with no slack today: `ClusterRole` has
exactly two values and a third (a dedicated storage or edge cluster) is a plausible architectural
addition, whereas a 9th bare-metal in a home lab is not. If the fleet ever does exceed 8 hosts, what
changes is the *stride*, not the structure — which is the point of making the field explicit.

[IMPORTANT]
====
*Why the plan may be ideal rather than incremental.* Every plane except the home LAN is a *virtualised*
network, defined and driven from nix — the vmnet bridges, the fabric segment, the pod/service spans, the
ULA mirror. None of them is negotiated with hardware or with an authority outside the repos. So an
address choice here is a **design decision, not a migration constraint**, and that is what licenses
re-basing pod/service to `128`/`160` instead of contorting around the historical `44`/`48`. The one fixed
input is `192.168.1.0/24`, frozen above.

*What renumbers, stated plainly.* Widening `roleId` to two bits changes `clusterId` for every cluster
with `hostId > 0`: `nikopol-mgmt` 2 → 4, `nikopol-wrkld` 3 → 5, so their vmnet `/21`, VIP, LB pool, ULA
`/56` and MACs all move. bioskop's two clusters keep `clusterId` 0 and 1 — untouched, which is fortunate
since they are the live ones. The pod/service re-basing moves every cluster's two `/16`s regardless of
host.

*Free to express, not free to apply.* Because it is all derived, the renumbering **is** the edit of two
constants — nothing is hand-maintained, which is the whole return on the solved plan. What is not free
is what must travel with it, and none of it may be deferred:

* a *re-render* of every synthesised artefact carrying a CIDR (cilium's pod-CIDR list and BGP config,
  the rke2 `cluster-cidr`/`service-cidr` drop-ins) — mechanical, but it must reach the rendered branch
  before a node boots on the new plan;
* a *`tls-san` reissue* + rolling `rke2-server` restart, since the certificate names the addresses;
* a *re-grow* of the affected clusters. Cheap by design: etcd is already wiped on every cold start (the
  motivation for the dataplan's `persist` split), so cluster state does not pin an address.

What survives untouched: the ZFS `persist` datasets and their bound PVCs (content, not addresses), and
the funnel/tailscale certificates (tailnet identity, not addresses).

One deliberate side effect to note rather than discover: `nixos/network.nix` routes the sibling-cluster
supernet via `Destination = netplan.vmnetSupernet`, so widening it widens that route to `10.80.0.0/16`.
Nothing else lives there, and the route's stated intent is exactly this — _"this catches every sibling,
present and future, with no per-cluster variant of the image"_. Widening strengthens it.
====

[[solved-plan]]
== The solved plan — every span, derived from two declarations

The plan is *solid* when it rests on two declarations and everything else is arithmetic. The
declarations:

[source,java]
----
// (1) the only name→number table — refuses the unknown, survives renames
hostId: bioskop = 0 · nikopol = 1 · test = 2            // 3 bits → 8 bare-metals
// (2) the one ceiling every plane is sized from
ROLE_BITS = 2                                            // 4 roles (MGMT 0, WRKLD 1, two spare)
CEILING   = 32                                           // = 8 × 4 clusters
clusterId = (hostId << ROLE_BITS) | roleId               // 5 bits, 0..31
----

[CAUTION]
.Frozen input — the home LAN
====
*`192.168.1.0/24` does not change. Nothing in this plan renumbers it.* It is a given, not a variable:
the bbox stays at `.254`, and every physical device — the `media` entries, `wifi-iface`, the two
`darwin-host` Macs (`.129`, `.65`), the two `nixos` hinges (`.130`, …) — keeps the address it has.

The plan touches the LAN in *deletions only*, and both are reversible:

* rke2lab stops *claiming* `192.168.1.128/25` (its `-lan`/`-lb` spans). No device moves; the range simply
  becomes free again.
* the ~12 `kind = "rke2"` static reservations leave the bbox. That shortens the router's reservation
  list; no live address changes.

This is the checkable form of the constraint: *a diff of the plan must contain no new or altered address
inside `192.168.1.0/24`* — only removals. It is also why the tier-purity invariant below is stated as
"rke2lab emits no span here" rather than as a renumbering.
====

Everything below is a function of `(hostId, roleId, nodeId)`. Ranges shown at `CEILING = 32`:

| *v6 mirror*
| ULA
| `fd96:6924:3693::/48` ⊃ `<clusterId>00::/56` per cluster ⊃ `<clusterId><role>::/64` per role —
  containment by construction, unchanged

|
| pods · services
| `fd00:<128+clusterId>::/56` · `fd00:<160+clusterId>::/112`, re-based with their v4 twins
|===

=== The four invariants, and why they now hold by construction

. *Tier purity* — no rke2lab span intersects `192.168.0.0/16`.
. *Containment* — node/LB `/26` ⊂ cluster `/24` ⊂ host `/20` ⊂ fleet `/17`; vmnet cluster `/21` ⊂
  `10.80.0.0/16`; role `/64` ⊂ cluster `/56`.
. *Pairwise disjointness* — across all 32 clusters for every family (fabric `/24`s, vmnet `/21`s, pod
  and service `/16`s, ULA `/56`s), and between the three blocks inside `10.0.0.0/8`. Spacing pod and
  service bases *by `CEILING`* rather than by a hand-picked gap is what makes this survive a change of
  ceiling.
. *Boundedness* — every node address lies inside its own node CIDR for every legal `nodeId` (0..11):
  `host(3+nodeId)` reaches `.14` in a `/26`, `host(10+nodeId)` reaches `.21` in a `/23`. The full
  12-name `nodeId()` table fits, not just the 6 canonical names — so the roster/carve disagreement that
  produced addresses *outside* a slice cannot recur arithmetically.

=== Two mechanical guards — the part that makes it solid

Choosing good numbers is not what makes a plan solid; being unable to violate it is.

*Guard 1 — bound `Cidr.host()`.* Verified: its body is `networkAddress.increment(offset)` and it never
reads `prefixLength` at all. So `Cidr.parse("192.168.1.128/29").host(9)` cheerfully returns
`192.168.1.137` — an address in the *neighbouring* network — which is exactly how the `/29` overflow
produced plausible addresses instead of failing. The fix is one comparison: reject an `offset` beyond
`2^(32 - prefixLength) - 1`. This converts invariant 4 from a property someone must remember into one the
type enforces, and it is the single highest-value line of code in this plan.

*Guard 2 — assert the plan exhaustively.* The legal input space is *finite and tiny*: 8 hosts × 4 roles
× 12 nodes = 384 coordinates. The blueprint is a pure function that reads no input file, so a test needs
no infrastructure at all — enumerate the whole space, collect every emitted span, and assert invariants
1-4 plus `hostId()` throwing for an undeclared host. An arithmetic drift then fails a test instead of
reaching a live cluster.

That test is the real deliverable of this section. Both defects found while writing it — the pod/service
bases only 4 apart, and the trap that `POD_BASE = 64` lands `clusterId = 16` on the vmnet supernet —
are exactly what such an enumeration catches instantly and a reading does not.

=== Where the wall is

At `CEILING = 64` (16 bare-metals × 4 roles) the plan still holds: pods `10.128`-`10.191`, services
`10.192`-`10.255`, together filling `10.128.0.0/9` exactly. **Past 64 it breaks** — the pod/service
scheme runs out of `10.0.0.0/8` and would have to drop to a `/17` per cluster. Recorded here so the next
widening knows the cost in advance rather than discovering it.

== What the transition deletes

The simplification, stated as removals — each is a red box above with no successor:

[cols="2,1",options="header"]
|===
| Deleted apparatus | Replaced by

| the bbox as an addressing authority for cluster nodes (a static reservation per node on a residential
  router, reconciled from the blueprint)
| *nothing* — `bare-br`'s dnsmasq hands out a DYNAMIC address. The static requirement is not moved to
  another authority, it is dropped: see <<mac-scheme-dies>>

| `LAN_DOMAIN = "lan"` — the router-served zone, the only suffix an in-cluster pod could resolve
| the `.<host>` zone `bare-br`'s dnsmasq serves; a pod's resolver *is* that dnsmasq, via its lease

| `nodeMdnsFqdn` (`<cluster>-<node>.local`) and the shared-L2 adjacency it needed
| a CLUSTER-scoped name for the VIP, published as a `host-record` on `bare-br` — see
  <<deterministic-vip-name>>. Not a deletion: a substitution at equal value, and a strictly better
  one, because the name stops naming a node

| the `hostId*48` term in the LAN carve — `hostId` as a coordinate *inside* one `/24`
| `hostId` lifted into the third octet: one segment per bare-metal

| `lanSliceBase` squeezing a single-node management cluster into a `/29`
| `.32-.123` free inside the low half. The `/29` is what made a management cluster that enumerated the
  full canonical roster place `worker1` on its broadcast address and `worker2` on the neighbouring `lb`
  network — the disagreement `ClusterTopology.of()` was introduced to settle. With room in the slice,

[[deterministic-vip-name]]
=== The deterministic name moves from the node to the CLUSTER

Dropping the static-address requirement (above) leaves one thing unreplaced: a *name*. `nodeMdnsFqdn`
was the only deterministic handle on the API, and it was keyed on a node — which is why it never
described a workload cluster, whose nodes are CAPI cattle named `<cluster>-control-plane-<random>`.

The substitution: *one name per cluster, resolving to that cluster's kube-vip VIP.* The VIP is already
a pure function of `clusterId`, already the endpoint CAPI's clustercache dials, and already survives
the node being replaced — so a name pointing at it inherits all three properties and depends on no
node identity at all. That is strictly more than the old name gave, not less.

==== Why the transport cannot be mDNS

Worth stating, because "publish it over mDNS" is the obvious first answer and it is *blocked at both
ends*:

* *mDNS is link-local multicast.* Today `<cluster>-<node>.local` resolves from the operator's Mac only
  because the node sits on the home LAN, sharing L2 with it. Once the node moves behind `bare-br` that
  adjacency is gone — which this view already records as the thing `nodeMdnsFqdn` "needed".
* *The hinge cannot publish an alias.* rke2lab's nodes run **avahi** (`nixos/host-access.nix`), but the
  NixOS guest runs **systemd-resolved** and ndh disables avahi deliberately
  (`ndh/modules/nixos/avahi.nix`, `mkForce false`, after a split-brain between the two responders).
  resolved's mDNS responder publishes the machine's *own* hostname and addresses; it has no notion of
  an alias for a third party. Publishing from the hinge would mean re-opening a wound ndh closed.

==== The mechanism, which already exists at both ends

A dnsmasq **`host-record`** on `bare-br`: a name bound to an arbitrary address, with no MAC and no
reservation — the one form that fits an address nothing holds a lease on. `SegmentHost(name, mac?,
ip)` models the MAC-less variant *explicitly*, for exactly this shape; §<<eval-cycle>> notes both ends
of that contract exist and have never been joined. This is the first consumer that genuinely needs it.

Two properties fall out, and both are worth more than the name itself:

. *One declaration, two audiences.* `bare-br`'s dnsmasq is not only the operator's resolver via
  split-DNS — it is **every pod's first resolver**, because the kubelet hands pods
  `/run/systemd/resolve/resolv.conf` whose first upstream is the bridge, and CoreDNS forwards to
  `/etc/resolv.conf`. Measured 2026-09-23 while chasing a pod that resolved `bioskop-nixos` to its own
  loopback. So the same `host-record` serves in-cluster consumers and the operator — replacing the
  `.lan` FQDN workaround that case needed with the normal form.
. *Naming becomes tailnet-independent.* The resolver is the hinge, which stays on the home LAN
  (`192.168.1.130`), so `/etc/resolver/<host>` on macOS reaches it directly. Resolution therefore works
  when the tailnet does not — recovering half of what the LAN context gave (401 in 6.5 ms, answering
  straight *through* a cold start, where the VIP was mute for minutes). The other half, a *route* to
  the VIP, still needs either a static route via the hinge or the tailnet Connector.

==== What it simplifies downstream

`tlsSanSuperset` collapses from six mDNS FQDNs enumerated out of `CANONICAL_NODE_NAMES` to **one**
cluster name, plus the VIP and the loopbacks. The certificate becomes a pure function of the cluster:
no roster, no node name, so *replacing a node stops touching it at all*. `NamePlan` loses
`nodeMdnsFqdn` and gains the cluster name.

The operator kubeconfig consolidates the same way — one deterministic name per cluster, with the
by-address VIP context kept as the fallback that needs no resolver at all.

[NOTE]
.The bootstrap path, stated rather than rediscovered
====
After the move, both remaining in-band paths — the VIP and the split-DNS name — depend on machinery
that a half-born cluster may not be running yet. The out-of-band path is the hinge itself: it keeps its
home-LAN address, so `ssh bioskop-nixos` then `incus exec` reaches a node that answers nothing else.
That is acceptable, but it should be the *declared* recovery path, because "how do I get in when it is
broken" is precisely the property the measurements above showed matters most.
====

What *survives* in role — though `vmnet0` loses its per-node reservations too
(<<mac-scheme-dies>>): `vmnet0` and the whole per-cluster `10.80.x` plane (isolated,
internal, `dns.mode=none`), the VIP, the pod/service CIDRs, and the `lib.networkBlueprint` flake edge.
This transition does not touch the cluster-internal plane at all — it replaces only the plane that
made a node reachable from *outside* its own fabric.

[[eval-cycle]]
== The invariant the move must not break — and how it constrains the design

This is the finding that should be read before any code is written.

link:../patterns/netplan-blueprint-single-source.adoc#non-cycle-invariant[The non-cycle invariant]
holds that `ndh -> rke2lab` is a *build/eval* edge (ndh imports the blueprint) while
`rke2lab -> ndh` is *runtime only*. A guard comment on rke2lab's `inputs` block exists so a future
edit cannot close the loop. The blueprint is also a **pure output**: the jar reads no input file, which
is precisely why the IFD story has no chicken-and-egg.

The obvious design — "the segment is a property of the bare-metal, so ndh owns it and rke2lab receives
the CIDR" — **violates both**. It would make `ClusterNetworkBlueprint.derive()` a function of ndh's
catalog, so ndh's catalog would feed the jar that generates ndh's catalog: a real eval cycle, and the
end of the pure-output property.

*The derived carve of <<derived-carve,Diagram D>> dissolves the problem rather than resolving it.* If the
slice is a pure function of the cluster name through `clusterId`, then both repos compute the same value
from names they already hold: rke2lab derives it in `derive()`, ndh reads it off the export it already
imports. Nothing new crosses the seam, in either direction.

What this removes is not *a* declaration but the *second* one. Today the number would have to be
declared twice and made to agree: ndh's catalog has nikopol `= 6` and bioskop `= 7`, while rke2lab's
`hostId()` has bioskop `= 0` and nikopol `= 1` — *inverted*, so no arithmetic relates them. After the
change there is one table, `hostId()`, which was already load-bearing for three other planes, and
`baremetal.<host>.netCidr` becomes a projection of it exactly as the `kind=rke2` reservation rows are
today. The catalog's "source of truth: rke2lab" comment becomes true for the segment too.

=== Why not a hash of the host name

The tempting next step — derive the slice from `sha256("nikopol")` and delete `hostId()` entirely — is
*rejected*, and the counter-example is already in the file. `ClusterNetworkBlueprint.java:351` reads:

[source,java]
----
case "nikopol" -> 1; // renamed from alcide, keeping same host id
----

A rename has already happened, and the number was *deliberately decoupled from the name* so that nothing
renumbered. Under a hash, `alcide → nikopol` would have moved the whole slice: addresses, dnsmasq
reservations, the advertised route, the ACL, and every apiserver's `tls-san` — a certificate reissue for
a cosmetic rename. The property actually needed is not determinism (sha256 has that) but *stability
under rename*, which a hash by construction does not have.

Two further properties the table provides and a hash cannot:

* *Uniqueness by construction.* Hashing into the 4 bits a `/20`-per-host carve leaves gives ≈6 %
  collision probability at two hosts and ≈18 % at three — and a collision here is two bare-metals
  sharing a slice: silent overlap, not an error.
* *Refusal of the unknown.* `hostId()` throws with a usable message (_"no LAN slice allocated; add it to
  `hostId()` + the addressing plan"_). A hash returns a *plausible* slice for a typo like `"bioskpo"` —
  precisely the failure class that has bitten this project three times (`clusterApi` vs `cluster-api`,
  `manifests.d` vs the path constant, the systemd unit name), where a wrong identifier yields a
  plausible wrong answer instead of failing. A declared table is valuable *because it refuses input*.

The arithmetic also refuses: a hash is only collision-safe in a *wide* space, `172.16.0.0/12` leaves
only 20 bits with the low ones reserved for nodes, and hashing wide enough to be safe makes the address
unreadable — losing exactly the legibility <<derived-carve,Diagram D>> optimises for. Narrow needs a
collision table; wide forfeits the benefit. There is no window between them in IPv4.

*Where hashing is right, it is already used.* `ULA_PREFIX` takes the first 40 bits of
`sha256("mammoth-skate")` for the `/48` global ID (`ClusterNetworkBlueprint.java:42-49`), and it works
there because all three conditions hold: 40 bits of space (negligible collision), a *fleet* name that
will never be renamed, and RFC 4193 explicitly asking for pseudo-random global IDs. Note the shape of
that design — the hash at the top, a legible derivation underneath, each host re-encoding its IPv4
verbatim in the low 32 bits (`fd96:6924:3693:<CC><RR>::a.b.c.d`) so you can *read the v4 out of the v6*.
Collision resistance and legibility at once, because each is applied at the layer that can carry it.

== Verdict — does it hold?

*Nothing here is implemented.* This view is vision, with one exception: the ndh half of the substrate is
already live and generic, which is why the migration is credible at all.

Verified live on 2026-09-23:

* `bare-br` exists on `bioskop-nixos` — `ipv4.address: 172.16.7.1/25`, `dns.domain: bioskop`,
  `status: Created` — and is **empty**: `used_by: []`, link `DOWN` (a Linux bridge with no member).
  The per-host logic needed no extension; it has no tenant.
* the reconcile path is a *oneshot*, added because the nixpkgs incus preseed is create-only — so a
  renumbering re-applies on a plain `nixos-rebuild switch`, with no cold start on the ndh side.
* public egress from the segment *already works*: `baremetal-nat` masquerades only public-bound traffic,
  preserving source addresses toward the tailnet, the LAN and sibling instances (deliberate — nnh's flow
  attribution needs them). `ipv4.nat = false` is therefore not the blocker it looks like. What remains
  unreachable is instance → *home-LAN service*, which no rke2lab consumer needs once `nixosLanFqdn` is
  gone.

Two gates are open, both found in live state rather than in docs:

. *`bare-br` has `ipv6.address: none`* — no IPv6 at all, while the LAN plane carries a full ULA mirror
  (`ROLE_LAN_NODE` `/64`, `lanHost6`). Like `lanLbCidr`, that v6 half appears *declared but not
  consumed* (the dual-stack `--node-ip` is built on `vmnet0`, not on the LAN plane), so this is
  probably not blocking — but it must be decided explicitly: either the segment gains an
  `ipv6.address` plus the v6 reservations, or the LAN plane's ULA mirror is deleted rather than left
  to lie. A silent mismatch here has already cost one cluster-wide outage (the DHCPv6 DUID that did not
  match, so the kubelet set *no* node addresses — see `nixos/network.nix:63-73`).
. *bioskop's catalog entry has no `dhcpRange`/`dynamicCidr`*, so its dnsmasq auto-ranges the whole
  `/25`. A `bare-br` recreate could then hand a *pinned* address to a DHCP client — the exact failure
  that stalled the nnh pipeline (`catalog/default.nix:70-79`).
+
NOTE: Dropping the static-address requirement *inverts* this gate rather than closing it. It was "a
dynamic pool may collide with our pinned addresses"; it is now "the dynamic pool **is** how a node gets
its address", so the range is no longer a hazard to bound but a span to declare — and the cluster `/24`
needs one carved inside it, which the table above does not yet show.

One more is open in the CODE, and it must be settled before the carve is frozen:

. *`roleId` is `ClusterRole.of(clusterName).ordinal()`* (`ClusterNetworkBlueprint.java:162`). Widening to
  `ROLE_BITS = 2` reserves two role slots, but with `ordinal()` the numbers are a function of *position
  in the enum*: inserting a role before `WRKLD` renumbers every workload cluster's vmnet `/21`, VIP, LB
  pool, ULA `/56` and MACs. That is the very failure `hostId()` is built to prevent — §<<eval-cycle>>
  rejects a hash because the property needed is *stability under rename*, and `ordinal()` fails the same
  test for *edits*. `roleId` needs an explicitly declared number, exactly like `hostId()`; until it has
  one, the "two spare roles" are a trap rather than headroom.

[[mac-scheme-dies]]
=== Settled: the MAC scheme dies entirely

The vmnet plane does *not* keep its per-node reservations either, so the decision is not "which plane
pins addresses" but "nothing does". `GrowNetworkResolver` writes one `dhcp-host=` line per node into
`raw.dnsmasq`, keyed on the WAN MAC — that goes with the rest, and `rawDnsmasq` reduces to its
`no-hosts` line alone (which stays: it is what stopped the bridge serving the *host's* `/etc/hosts` to
every pod).

Nothing was depending on the prediction, which is why this is a deletion and not a redesign:

* the `node-<cluster>` incus profile is *already* documented as "dynamic MAC/IP" for CAPN nodes — the
  cattle case had quietly opted out long ago;
* `rke2lab-node-ip` reads `vmnet0`'s address **live** rather than from `node.env`, precisely so the
  kubelet does not register `cilium_host`;
* the ULA mirror re-encodes whatever v4 the node actually got (`fd96:…:<CC><RR>::a.b.c.d`).

What dies with it, verified by grep rather than assumed:

[cols="2,3",options="header"]
|===
| Dies | Note

| the three MAC derivations — `10:66:6a:4c:<clusterId>:<nodeId>` (LAN),
  `52:54:00:<clusterId>:<nodeType>:<nodeId>` (WAN), `02:00:00:bb:…` (bridge)
| their only consumers were the `dhcp-host` lines and the projection

| `nodeNetwork().nodeHostInetaddr()` + its v6 twin — the *predicted* vmnet address
| its readers are the dying `dhcp-host` line, the projection's per-node entries, and
  `NetworkTopology.nodeHostInetAddr`/`nodeHostInet6Addr`, which have **no reader at all**

| the projection's `macs` and `leases` sections
| and with them ndh's `kind = "rke2"` catalog entries, which read `macs.lan` + `ips.lanHost` — this is
  what actually removes the reservations, since ndh *derives* them (they outlived rke2lab's own
  enumerator being cut to 2 rows)

| `BlueprintRowEnumerator`, including `RKE2_LAN_MAC_PREFIX`
| the MAC-prefix ownership check existed to keep non-RKE2 reservations out of scope; with no
  reservations there is no scope to defend. `DESIRED_COUNT` in the bbox in-container proof goes 2 → 0

| `host(10 + nodeId)` as a vmnet coordinate
| `nodeId` stops being an *addressing* coordinate anywhere. It survives as **identity** —
  `RKE2LAB_NODE_{ID,NAME,KIND,HOSTNAME}`, the only node.env values any nixos unit actually reads
|===

What survives and *gains* weight: `wan().dhcpRange()`, which was the range sitting beside the
reservations and becomes the mechanism; the VIP, the LB pools and the gateways, which are *service*
addresses and stay declared; and `SegmentHost`'s MAC-less form, now rke2lab's only shape — and the
carrier of the cluster VIP name in <<deterministic-vip-name>>.

Ordering, safest first — steps 1 and 2 have no consumer and are reversible; the point of no return is 3:

. *ndh only*: bioskop gains `dynamicCidr`/`dhcpRange` and a `/30` link; both hosts' `/30` moves into the
  high half. Clusters are untouched — the nodes are still on `lan-br`.
. *the catalog joint*: `raw.dnsmasq` derives from the merged `segments[].hosts` instead of a
  hand-written `staticHosts`. Both ends of that contract already exist — `SegmentHost(name, mac?, ip)`
  models the MAC-less `host-record` form *explicitly* to match ndh — but they have never been joined.
  Its client is no longer a node reservation (there are none) but the *cluster VIP name* of
  <<deterministic-vip-name>>: one `host-record` per cluster, serving pods and the operator alike.
. *rke2lab*: the carve, `lanBridgeParent`, and the `tls-san` + `NamePlan` change, in ONE commit. The
  certificate and the address it certifies cannot ship apart.
. *re-grow*, management first: single-node, and on-demand by design.

A note on blast radius, since the guests are often called ephemeral: their *system* is (EROFS + overlay,
rebuilt from the flake), but they carry `tank`, and on bioskop `tank` holds the live clusters' rootfs
(`tank/nerd/incus/containers/rke2lab_bioskop-mgmt-master`, 10.7 GiB). Cold-starting a guest is safe —
the pools re-import. Recreating the pool disks is not. This migration requires neither.
