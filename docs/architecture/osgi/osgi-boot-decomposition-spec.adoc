= OSGi boot decomposition — plan vs launch, one launch operation, no twin runtimes
:toc: left
:toclevels: 3

[NOTE]
====
*Status:* SHIPPED (2026-06-23), on `refactor/osgi-boot-alignment`. Decomposes the embedded-OSGi
boot so the pure *decision* (what to install, at what start-level, with what `system.packages.extra`) is
told apart from the effectful *act* (boot Felix and make it so). The boot is a plain launch operation —
`FrameworkLaunch.embedded().launch()`, plan+launch in one step, invoked as a scenario's first jGiven
step (never a fluent-pipeline verb) — so that `OsgiRuntime` and `SeedRuntime` — a blurry pair with no
principled split — dissolve into the discovery/planner/launcher/booted-framework roles that each answer
one question: *what is your one job?*

A follow-on pax/JCL volet then made the seam law declarative: the third-party boot stack (pax,
felix.scr/resolver, the DS-API trio) is `optional` in `osgi/runtime`, so Maven keeps it off every
consumer's flat host classpath (JCL) by native rule — a bundle on the JCL is a wrong classpath, full
stop — while the build-time staging extension re-resolves it by coordinate to stage it into the
framework. The felix.scr import closure that the prod planner and the test executor each mirrored is
now one shared `BundleIndex.closeOverImports` frame with the per-jar action contributed as a handler.
Detail in memory `bundle-on-jcl-is-wrong-classpath` and `boot-decomposition-state`.

Collects the debt in memory `osgi-runtime-decomposition-debt` ("osgi runtime commence vraiment à être
touffu") and `boot-pipeline-unification-backlog` (prod + test executors duplicate the boot sequence).
Keeps the seam law of link:../patterns/port-edge-domain-ownership.adoc#the-boot-face[the boot face]
unchanged; builds on the model of link:osgi-boot-single-source-handoff.adoc[the boot single-source handoff].

== The defect this closes

`OsgiRuntime.boot()` answers two unrelated questions in one ~140-line body:

. *What should be installed, at what level, with what system-exports?* — a **pure decision**. No framework
  need exist to answer it: `closeOverImports`, `deriveSystemExports`, the seam guard, `startLevelOf`, the
  topology assembly. ~60% of the body, and the cryptic 60%.
. *Boot Felix and make it so.* — the **effectful act**: framework factory, the config map, `init`/`start`,
  the `STARTED` latch, the install loop, `assertScrActive`, `close`.

`OutOfContainerFrameworkExtension` (the test executor) answers the *same two questions a second time*, slightly
differently — its `startScr()` carries the comment *"the runtime mirror of `OsgiRuntime.closeOverImports`"*.
Two copies of one resolution thesis, free to drift.

And the two runtime classes have **no principled axis between them**. `SeedRuntime.boot()` is literally
`OsgiRuntime.embeddedBootStack().build().boot()` wrapped in the fluent topic runner — so a reviewer asking
"what tells these two apart?" gets only "seed wraps osgi", an accidental seam. A blurry boundary reads as
crypticness; that is the symptom this spec removes.

== The provisioning delta (why the executors must unify, not just dedupe)

[cols="2,2,2",options="header"]
|===
| Provisioning step | `OsgiRuntime` (prod) | `OutOfContainerFrameworkExtension` (test)

| factory + temp storage + `bootdelegation.implicit=false` | ✓ | ✓ (identical)
| `system.packages.extra` | ✓ | ✓ (identical)
| *activation model* | *start-levels + raise + `STARTED` latch* | *hand loop: install→start in declared order, no levels*
| import-closure for the boot stack | `closeOverImports` | `startScr()` — "the runtime mirror of `closeOverImports`"
| pax-logging config | ✓ | —
| `bootDelegation` (`sun.misc` for byte-buddy) | — | ✓
| `@FrameworkLog` → `felix.log.level` | — | ✓
|===

The emphasised row is a latent bug, not mere duplication: *the test boots with a different activation
order than prod*, so a green test proves *a* boot, not *the* boot. Unifying the executors onto one
provisioning makes the test exercise what prod ships. Everything else is identical (fold it) or a narrow
honest knob (`bootDelegation`, `felix.log.level`) carried on a launch-config value.

== The launch operation — FrameworkLaunch, plan+launch in one step

The boot has two real, non-reorderable acts, plan then launch; `FrameworkLaunch` folds them into one
`launch()` — no caller inspects a `BootPlan` without booting, so a separate `PlanDone` state would be a
speculative abstraction with no reader. The plan/launch split lives INSIDE `bootEmbedded()`
(`BootPlanner.plan(...)` then `FrameworkLauncher.launch(plan, true)`), and `launch()` hands the live
framework out for the caller to own.

[mermaid]
----
flowchart TB
  Embedded["FrameworkLaunch.embedded()"]
  Plan["BootPlanner.plan(...) — pure BootPlan"]
  Launch["FrameworkLauncher.launch(plan, true)"]
  Booted["BootedFramework — caller owns close"]
  Embedded -->|launch| Plan
  Plan --> Launch
  Launch --> Booted
  style Embedded fill:#e1f5ff,stroke:#0066cc
  style Plan fill:#cce5ff,stroke:#0066cc,stroke-width:3px
  style Launch fill:#ffe0b2,stroke:#ff9900,stroke-width:3px
  style Booted fill:#ffe0b2,stroke:#ff9900,stroke-width:3px
----

The boot is NOT expressed as a fluent grammar. It is a plain launch operation: `FrameworkLaunch`
does plan+launch in one step (no caller inspects a `BootPlan` without booting), and a scenario that
needs a live world invokes it as its first jGiven step — the boot is a scenario step, not a pipeline
verb. The pieces:

* *Plan+launch* — `FrameworkLaunch.Embedded.bootEmbedded()` calls `BootPlanner.plan(...)` then
  `FrameworkLauncher.launch(plan, true)`; there is no separate discovery/plan/launch state chain (a
  `PlanDone` state would be a speculative abstraction with no reader).
* *Hand-out* — `FrameworkLaunch.embedded().launch()` returns the live `BootedFramework`; the caller
  owns the lifecycle and closes it (`try (var f = FrameworkLaunch.embedded().launch()) { … }`, and
  the Jupiter `afterAll` in the socle's `OsgiConnection.embedded()`).

=== Call sites

[source,java]
----
// exec app / socle: boot the fixed prod topology, hand the world out, caller owns the lifecycle
try (BootedFramework framework = FrameworkLaunch.embedded().launch()) {
  // read services off framework.awaitService(...) / play the scenario against the live world
}

// the socle's connection is exactly this — OsgiConnection.embedded() wraps launch() and closes it
OsgiConnection connection = OsgiConnection.embedded();  // boot as the scenario's first step
----

Test worlds do NOT go through `FrameworkLaunch`: `OutOfContainerFrameworkExtension` /
`JGivenTestkit.felix()` boot Felix directly with their own knobs (classpath source, `systemPackages`,
`bootDelegation`, `withScr`), because a test needs to shape discovery and the system-package surface
per fixture — the prod preset deliberately fixes those.

== Module placement (owners verified on the reactor)

[cols="1,2,2",options="header"]
|===
| Module | Footprint today | Gains

| `osgi/boot/boot-discovery`
| `bnd-read` only (JDK + osgi.core `Filter`) — *pure*
| `BootPlanner`, `BootPlan`. The pure 60% retires here, the next layer over the `BundleIndex` /
  `DiscoveryPolicy` it already owns. (Decision: planner lives *inside* boot-discovery, not a sibling — the
  footprint is identical, so a separate module buys only a boundary.)

| `osgi/runtime`
| felix + pax + osgi.core, already depends on `boot-discovery`
| `FrameworkLauncher`, `BootedFramework`, `FrameworkLaunch` + its embedded preset. `OsgiRuntime` +
  `SeedRuntime` *deleted*. No fluent-grammar dependency — the boot is a plain launch operation, not a
  pipeline (the former `pipeline-port` engine dissolved into `manifests-core`'s internal synthesis).
|===

`BootPlanner` runs host-side *before any framework exists* (it computes the plan Felix is launched with),
so it is plain host-world compute reachable on the flat classpath — `osgi/runtime` already depends on
`boot-discovery` as a normal jar. No seam concern.

== BootPlan — a pure, inspectable value

`BootPlanner.plan(index, policy, explicitPackages)` returns a `BootPlan` carrying: the ordered
`Installable` list (location + start-level), the derived `system.packages.extra`, and the per-package owner
attribution. The planner *throws* on a real leak (the seam guard, fail-fast, unchanged) **and** the plan
*holds* the verdict, so a test asserts "this plan would export X" or "installs the DS-API trio at the
passive level" without booting Felix. *pax-presence stops being a flag:* the launcher derives the pax
config from whether the plan contains pax bundles, deleting the `paxLoggingPresent` special case in both
classes today.

== Runtime nature enters only as data, never as a branch in shared logic

The two use cases boot from different sources — the test harness from the **test classpath**, the embedded
exec-jar from **`META-INF/bundles/`** — yet the planner is shared whole. The reason this holds, and does not
crack under a third source later, is that *runtime nature is an input the planner consumes blind, not a fork
in its body*. It is absorbed at the two edges, leaving the middle source-independent:

[cols="1,2,2,1",options="header"]
|===
| Axis of difference | Test (classpath) | Embedded exec (`META-INF/bundles`) | Absorbed by

| where the bytes live + how to read them
| `BundleIndex.ofClasspath()` → `BundleLocation.OnClasspath(Path)`
| `BundleIndex.ofStagedBundles(loader)` → `BundleLocation.Staged(loader, name)`
| `BundleIndex` factory + the `BundleLocation` sealed type (bottom edge)

| which bundles to install
| a pinned subset (the anti-cheat installs the consumer *alone*)
| `DiscoveryPolicy.all()` — everything staged is meant to boot
| `DiscoveryPolicy` (top edge)
|===

`DiscoveryPolicy.select()` is defined over a `BundleIndex`, not over a source: `all()` means "the staged
set" against a staged index and "everything on the path" against a classpath index — *same policy, different
index* (its own javadoc states this). So the three layers stack with **only the bottom one branching**:

[mermaid]
----
flowchart TB
  Policy["DiscoveryPolicy<br/>source-agnostic by construction<br/>all = staged set OR classpath set<br/>per which index, no branch"]
  Planner["BootPlanner<br/>PURE, blind to nature<br/>levels, exports, closure, seam-guard<br/>identical for both"]
  Launcher["FrameworkLauncher<br/>the ONLY place nature shows<br/>install sealed switch<br/>Staged.open stream OR OnClasspath URL"]
  Policy --> Planner
  Planner --> Launcher
  style Policy fill:#e1f5ff,stroke:#0066cc
  style Planner fill:#cce5ff,stroke:#0066cc,stroke-width:3px
  style Launcher fill:#ffe0b2,stroke:#ff9900,stroke-width:3px
----

The only code that asks "classpath or staged" is the install mechanism — two arms of one sealed switch that
already exists in today's `OsgiRuntime.installAtLevel`:

[source,java]
----
case BundleLocation.Staged staged  -> installBundle(id, staged.open());  // stream the bytes
case BundleLocation.OnClasspath cp -> installBundle(cp.locationId());    // install by URL
----

[IMPORTANT]
====
*The mark of the abstraction being right: runtime nature is data, not control flow.* The classpath vs
`META-INF/bundles` distinction lives entirely in which factory the caller picks (`ofClasspath()` vs
`ofStagedBundles(loader)`) and which `DiscoveryPolicy` it passes — exactly the `embedded()` preset vs the
test builder difference at the call sites. The planner never learns which world it is in, so a future third
source (a remote OBR, an exploded dir) is a new `BundleLocation` arm + a `BundleIndex` factory, with *zero*
change to `BootPlanner`.
====

== Aligning the testkit — provisioning shared, proof kept apart

`OutOfContainerFrameworkExtension.beforeAll` builds a plan from the classpath index and launches it through the same
`FrameworkLauncher` — gaining prod's start-level activation model by construction. Its *proof affordances*
stay test-only, operating on the launched `BootedFramework`, and are explicitly **not** a second way to
provision:

[cols="1,3",options="header"]
|===
| Affordance | Why it is proof, not provisioning
| `installMatching(filter)` | installs *without* starting — to drive resolution by hand
| `installFixtureWithHost(filter)` | host + `-test` fragment, neither started, then resolve by hand (OSGi §3.14)
| `resolve(bundles)` + `unsatisfiedRequirements` | the anti-cheat: install the consumer alone, assert it stays unsatisfied
| in-container runner `loadClass(runner).invoke()` | the jGiven white-box run — a workload over the framework, beside `awaitService`
|===

`JGivenTestkit.felix()` stays a *preset* over the shared planner+launcher (it contributes a
`DiscoveryPolicy` adding the jGiven bundles + the `bootDelegation("sun.misc")` knob) — never a branch in
the generic extension, per link:jgiven-osgi-testkit-handoff.adoc[the jGiven testkit handoff]'s first
anti-pattern.

[IMPORTANT]
====
*One true provisioning.* The launcher always uses prod's activation model (start-levels + `STARTED` latch).
The hand-resolution proofs are explicitly not provisioning — they install bare bundles and drive
`resolve()` themselves, beside the launcher, never through it. A "no start-levels" launcher strategy would
re-introduce the very fork this spec deletes.
====

== Anti-patterns retired

❌ *Two hand-aligned boot sequences* (`startScr` mirroring `closeOverImports`). ✅ One `BootPlanner` closure
both executors call.

❌ *Plan fused into launch* — cannot test "would this export leak a domain package?" without Felix. ✅ The
seam-guard verdict is a property of the pure `BootPlan`.

❌ *Twin runtimes with an accidental axis* (`SeedRuntime` wraps `OsgiRuntime`). ✅ Four phase-roles, each
with one job; neither old class survives.

❌ *Provisioning as flag soup* (`paxLoggingPresent`, `embedsBootStack`, `startScr` booleans). ✅ The plan is
the topology; the launcher derives effects from it.

== Implementation order

. **Extract `BootPlan` + `BootPlanner` into `boot-discovery`** (pure move of `closeOverImports` /
  `deriveSystemExports` / seam-guard / start-levels / topology). Add pure-plan unit tests. `OsgiRuntime`
  still launches, now calling the planner. Reactor GREEN.
. **Extract `FrameworkLauncher` + `BootedFramework` in `osgi/runtime`.** `OsgiRuntime.boot()` becomes
  *plan, launch, expose seam*. GREEN.
. **Introduce `FrameworkLaunch`** (plan+launch in one `launch()`) + the `embedded()` preset; route exec
  apps through it; delete `SeedRuntime`. GREEN, `pulumi preview`.
. **Route `OutOfContainerFrameworkExtension` through the shared planner+launcher**; delete the `startScr` mirror;
  keep the proof affordances. Delete `OsgiRuntime`. Full reactor GREEN with tests.
+
*Watch here:* today the testkit installs some bundles *outside* any policy — `installFromClasspath(bsn)`
for the boot stack, `installBundles(bsn)` for a named host. Each must land on a defined channel with
nothing falling through: boot-stack jars are `BootStackJar` entries (the launcher's concern, not the
policy), and named/anti-cheat selections become `DiscoveryPolicy.only(...)` / `onlyMatching(...)` (a closed
set, already supported by `OnlyNames` / `OnlyFilter`). The pinned-subset anti-cheat (install the consumer
without its provider) is `onlyMatching("(role=consumer)")`. Audit every current install site maps to either
a `BootStackJar` entry or a policy — a leftover bare `installBundle` is the smell that nature leaked back
into control flow.

Each step is a GREEN commit; squash-merge into `design/pre-integration`, never `main` (memory
`rke2lab-solo-no-pr-merge-direct`, `merge-from-target-worktree`).

== Verification

* *Pure-plan unit tests (no Felix):* assert the staged-topology `BootPlan` installs the DS-API trio at the
  passive level, derives the expected `system.packages.extra`, and that a synthetic domain-package leak
  makes `BootPlanner.plan(...)` throw naming the package + owning bundle.
* *Both executors green through the shared launcher:* `HostSeamEmbeddedFelixTest`, `EmbeddedBundlesBootTest`,
  and the testkit SCR / extender / doctor / jGiven proofs, via

  *count* surefire reports (memory `build-verification-gotchas` — a green build with no `Tests run:` line
  means skipped).

  callback, SCR publishes, the host seam consumes, preview completes with no master mutation.
