= Cluster API Bootstrap Requirements & Cleanup
:toc: left
:toclevels: 3

Plan for Phase 1 cleanup and flox environment architecture for cluster workloads.

== Overview

Declarative CAPI/CAPN/CAPRKE2 installation runs via manifest layers: the Cluster API Operator with
provider CRs, the Incus identity secret, the `NodeImage` describing the realised node-base
(link:node-image-lifecycle.adoc[Node image lifecycle] — it replaced a write-only `image-state`
ConfigMap), the Flux GitRepository + root Kustomization, and the SOPS age Secret are all in place as
manifest units.

This document covers what remains: (1) remove the old imperative clusterctl-based installation, (2)
the flox-environment architecture for pod-level executable injection, (3) validating bootstrap with no
clusterctl dependency.

[IMPORTANT]
====
Read against the management/workload separation (see the anchor,
link:management-workload-topology.adoc[Management / Workload Topology]). Under the separation the
`cluster-api` domain (operator + provider CRs + Incus identity + the `NodeImage`) publishes to
the *management* cluster *only* — that is where CAPI/CAPN/CAPRKE2 live. The `gitops` domain (Flux + the
vCluster operator) publishes to the *workload* clusters. Two consequences for the units below: the
`IncusIdentitySecretManifestsUnit` becomes *per-remote* (one identity secret per bare-metal — bioskop +
nikopol — since CAPN drives two remotes), and the flox pod-injection architecture applies to *any*
cluster, not one named host. Porch is *descoped* (see
link:cluster-workload-completion-plan.adoc[Cluster Workload Completion Plan]).
====

== Current State

The old imperative `clusterctl`-based install (systemd units + scripts under the retired
`manifests/src/main/resources/systemd/…`) is *gone* — there is no `clusterctl` in any flox
environment and no imperative cluster-api systemd unit; the Cluster API Operator replaces it.

The declarative installation lives as manifest units in the `cluster-api` domain (all `…ManifestsUnit`,
wired by `ClusterApiDomainRegistrar`):

- `ClusterApiOperatorManifestsUnit` — operator + the Core/Infrastructure(CAPN)/ControlPlane+Bootstrap(CAPRKE2) provider CRs
- `IncusIdentitySecretManifestsUnit` — CAPN identity Secret (becoming *per-remote*, see the IMPORTANT above)
- the `NodeImage` rendered by the management/workload units — the realised node-base's identity AND
  the runtime contract an instance needs to run it (link:node-image-lifecycle.adoc[Node image
  lifecycle]). It superseded `ImageStateConfigMapManifestsUnit`, whose ConfigMap had no reader.
- `ClusterKubeconfigManifestsUnit` — the cluster's kubeconfig Secret

These render into the management cluster's rendered branch and reach it via Flux, not an imperative
apply (see link:manifests-rendered-branches.adoc[Manifests Rendered Branches]).

See link:bootstrap-identity-provider.adoc[Bootstrap Identity Provider] for the identity pattern.

== Architecture: Flox Environment Injection for Pods

=== Three-Tier Environment Model

**Goal**: Pods in any rke2lab cluster use flox-provided executables from nix store via annotation-based injection.

=== Tier 1: Operator Environment (Dev Machine)

Current: `.flox/env/manifest.toml`

[source,toml]
----

pulumi.pkg-path = "pulumi-bin"
cdk8s-cli.pkg-path = "cdk8s-cli"
incus-client.flake = "github:nxmatic/rke2lab#incus-client"

[include]
  environments = [
    { dir = "../fleet/flox/git" },
    { dir = "../fleet/flox/jdk" },
    { dir = "../fleet/flox/k8s" },
    { dir = "../fleet/flox/pulumi" },
    { dir = "../fleet/flox/shell" },
  ]
----

=== Tier 2: Bootstrap Node (Master Host)

**Components**:

- RKE2 server binary (installed by RKE2 install script)
- Nix store with flox environments
- Flox NRI plugin DaemonSet (existing pattern)

**DaemonSet responsibilities**:

- Materialize flox environments to `/srv/host/k8s-daemonset.d/runtime/flox/environment.d/`
- Update nix store on nodes
- Publish environment metadata via ConfigMap (nix store paths)

**Pattern**: Reuses existing flox NRI plugin architecture.

=== Tier 3: Cluster Workloads (Pods)

Pods opt into flox-provided executables with a per-container annotation
`flox.seedmatic.io/environment.<container>: fleet/k8s` (or `fleet/keyhole`). Injection is done by the
*flox NRI plugin*, not a mutating admission webhook: the plugin intercepts container creation on the
node, reads that annotation, and mounts the nix store + sets `PATH`/`FLOX_ENV` from the materialised
environment. The plugin is baked as a systemd service (`rke2lab-flox-nri-plugin`) from the
`flox-runtime` flake input; the workload envs are delivered as `FloxEnv` CRs (`FloxEnvManifestsUnit`)
that the flox-controller realises onto each node. See `FloxShellSidecarProfile` (debug/exec injection)
in `manifests-core`.

NOTE: An earlier design proposed a cert-managed mutating webhook in a `flox-system` namespace for this
tier. It was never built and is superseded by the NRI plugin above — the plugin needs no admission
webhook, no per-pod cert, and keys on the per-container annotation rather than a bare pod annotation.

== Required Flox Environments for Cluster Workloads

=== Fleet K8s Environment

**Location**: `fleet/flox/k8s/.flox/env/manifest.toml`

**Contents**:

- kubectl, helm, helmfile
- cilium-cli, fluxcd
- kpt, etcdctl
- kubectl plugins: doctor, tree, view-secret, graph, etc.

**Use cases**:

- Flux controllers (GitRepository, Kustomization reconciliation)
- Tekton tasks (kubectl apply, helm upgrade)
- Debug pods (kubectl exec into cluster)

=== Fleet Keyhole Environment

**Location**: `fleet/flox/keyhole/.flox/env/manifest.toml`

**Contents**:

- age, sops
- gnupg, openssh, openssl
- pass, ssh-to-age, keychain

**Use cases**:

- Flux SOPS controller (decrypt encrypted Secrets)
- Tekton tasks (encrypt cloud-init Secrets in Phase 2)
- Secret management workloads

=== Environment Availability

**How environments reach nodes**:

1. Flox NRI plugin DaemonSet materializes environments to the host nix store
2. The plugin intercepts container creation and mounts the store + sets `PATH`/`FLOX_ENV`
3. Keying is the per-container `flox.seedmatic.io/environment.<container>` annotation

**Phase 1 scope**: Verify these environments exist and are suitable.

== Remaining work

The near-term surface is the environment definition (include fleet/keyhole in the operator
environment; decide the mesh/cicd domain toggles) — the old imperative clusterctl install is already
gone. Then the future track:

* *Environment availability* — materialize `fleet/k8s` + `fleet/keyhole` on nodes via the DaemonSet
  trampoline and let the flox NRI plugin mount them by the existing volume pattern (no admission
  webhook — see Tier 3 above).

== Benefits of Flox Injection Architecture

**Single source of truth**:

- Tool versions defined in flox environments
- No version drift between dev and cluster
- Update once, applies cluster-wide

**Minimal container images**:

- Base images (alpine, busybox) sufficient
- No need for kubectl/helm/etc in every image
- Smaller image sizes, faster pulls

**Consistent with existing patterns**:

- Reuses flox NRI plugin DaemonSet pattern
- Same nix store maintenance
- Unified environment management

**Easy updates**:

- Update flox environment
- Refresh DaemonSet
- All pods get new tool versions

**Developer experience**:

- Same tools locally and in-cluster
- Annotate pod, get tools
- No Dockerfile changes for new tools

== Open Questions

   - Tailscale provides cluster networking
   - **Answer**: Keep enabled, may be required

2. **CICD domain at bootstrap?**
   - Tekton needed for Phase 3
   - **Answer**: Keep enabled, lightweight operator

   - Manual vs automated in seed-master
   - **Answer**: Keep manual (one-time setup, documented)

== Success Criteria

The cleanup is done when no clusterctl remains in any flox environment and no imperative
cluster-api systemd units remain; fleet/keyhole is included in the operator environment; the manifests
module builds; the Cluster API operator installs declaratively with all provider CRs (Core,
Infrastructure, ControlPlane); and bootstrap completes with no clusterctl dependency.
