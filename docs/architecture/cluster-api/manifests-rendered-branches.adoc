= Manifests Rendered Branches — the `manifests/*` GitOps delivery model
:toc: left
:toclevels: 3

This document specifies HOW the manifests the `manifests` module synthesises reach the clusters
that consume them. It is the missing companion to
link:management-workload-topology.adoc[Management / Workload Topology] (the *what* — which clusters
exist) and to link:vcluster-gitops-architecture.adoc[the vCluster GitOps Architecture] (the
*per-cluster* Flux/vCluster pattern): this doc is the *delivery seam* between them.

It supersedes the earlier assumptions that (a) the rendered manifests live under a `gitops/` *path*
on `main`, (b) the management cluster runs no Flux, and (c) `seed-mgmt` imperatively `kubectl
apply`s the workload CAPI CRs at a "Stage B". All three are revised here.

== Overview

`manifests` (the CDK8s Java module) is the *single source of truth* for manifest generation. But a
source of truth is not a delivery mechanism: something has to carry the RENDERED YAML to each
cluster and keep it reconciled. This doc defines that carrier.

The shape is a *rendered-branch* GitOps model:

* **`main`** holds the *source* — the CDK8s Java + the input config. Humans edit `main`; nothing
  applies from it.
* **`manifests/<host>-<role>`** branches hold the *rendered* YAML — one branch per cluster. The
  `manifests` module regenerates a cluster's tree and **pushes** its branch as ordinary,
  history-preserving commits. These branches keep the *full change history* — an auditable GitOps
  trail, never a force-push that discards it.
* **Every cluster runs Flux** (in a `gitops` vCluster — see <<uniform>>) whose `FluxRoot` tracks
  *its own* branch `manifests/<host>-<role>` and reconciles it.

So the split is not "which domains the master publishes into its `server-manifests`". It is: **what
`manifests` renders into `manifests/<host>-<role>`, per cluster** — and Flux, uniformly, applies it.

== The branch model

[cols="1,2,3",options="header"]
|===
|Branch |Carries |Reconciled by

|`main`
|Source: CDK8s Java + input config
|Nobody applies it — it is the build input

|`manifests/nikopol-mgmt`
|The management cluster's definition: the `seed-master` *sow* (single-node RKE2 bootstrap + the `FluxRoot` seed) + CAPI operator + the four providers + base + Tailscale client, AND the **workload CAPI CRs** (`Cluster` / `LXCCluster` / `RKE2ControlPlane` / `LXCMachineTemplate` / `MachineDeployment`) for every workload — paused until that workload's bare-metal is up
|**`seed-master`** sows the node (local-only seed); the management cluster's **own Flux** then applies the rest of the branch — including the workload CRs, which **CAPI / CAPN** reconcile into the workload nodes

|`manifests/nikopol-wrkld`
|The workload's **app stack**: `gitops` · `storage` · `mesh` · `cicd` · `high-availability` — **no `cluster-api`**
|the workload's **own Flux**, once the workload cluster is up

|`manifests/bioskop-wrkld`
|idem — the workload's app stack
|the workload's own Flux — dormant until the bioskop bare-metal is up
|===

The consumer is per-branch and drives the branch's shape (§ <<render-inputs,output shape>>): a
`-mgmt` branch carries the management-plane shape — the `seed-master` sow + the CAPI operator and
providers + the *workload CAPI CRs* — because CAPI runs *in the management cluster* and reconciles
those CRs there; a `-wrkld` branch carries the workload's own **app stack** (gitops · storage · mesh ·
cicd · high-availability), reconciled by the workload's own Flux once the cluster is up. The
cluster-*creation* content therefore lives entirely on the `-mgmt` branch (read by `seed-master` for
the node seed, then reconciled by the management cluster's own Flux — the operator, the providers, and
the workload CRs); a `-wrkld` branch has content to reconcile only after its cluster exists to host a
Flux. **Flux everywhere** (the management cluster running its own Flux against `manifests/<host>-mgmt`
— see <<function-of-git>>) is the uniform model, not a deferred layer.

The namespace names the *producer* (`manifests`), not the consumer (`gitops`): the branch holds
rendered manifests, and Flux is only their reader. Per-cluster isolation is a *branch* concern, not
a directory concern — a render pushes ONE branch, so one cluster's regeneration never moves
the `GitRepository` revision the other clusters' consumers watch.

The deeper win is *correctness*: the branch boundary **mirrors the physical cluster boundary**. Each
consumer reads only its own branch — there is no shared tree in which a mis-scoped resource could
land in the wrong cluster. A directory layout (`clusters/<host>-<role>/` on one branch) leaves that
failure mode open (a wrong path, a stray file, a `prune` that spans siblings); a branch per cluster
closes it structurally. The physical separation of the clusters is replicated in the git model, so
"which cluster does this resource belong to?" is answered by *where it can even exist*, not by a
path convention a render could get wrong.

[[uniform]]
== One architecture for every cluster

Every cluster — management included — runs Flux inside a `gitops` vCluster (the Option-D pattern
from link:vcluster-gitops-architecture.adoc[the vCluster GitOps Architecture], now applied
uniformly). There is no "management is special, it has no Flux" exception: the management cluster is
*just another cluster* whose `gitops` vCluster's Flux tracks `manifests/nikopol-mgmt`.

Running Flux in a vCluster (rather than directly in the core's `flux-system`) buys the same
Option-D benefits everywhere: isolation (a Flux failure is contained), reentrancy (a `gitops-next`
vCluster can test a Flux upgrade against a copy), and uniformity (the management plane is managed
"like just another vCluster"). The vCluster provisions *pods*, never machines, so it never
re-introduces CAPI into a cluster that should not run it.

[mermaid,manifests-rendered-branches-fluxroot,svg]
----
flowchart TB
  subgraph C["any cluster &lt;host&gt;-&lt;role&gt;"]
    subgraph GV["gitops vCluster"]
      FLUX["Flux"]
      FR["FluxRoot:<br/>GitRepository(ref.branch=manifests/&lt;host&gt;-&lt;role&gt;, path=./)<br/>+ root Kustomization (prune, decryption: sops)"]
      PK["parent-cluster-kubeconfig<br/>→ this cluster's core"]
    end
    CORE["cluster core"]
  end
  BR[("manifests/&lt;host&gt;-&lt;role&gt;")]
  BR -->|tracks| FR
  FR --> FLUX
  FLUX -->|"applies via parent-cluster-kubeconfig"| CORE
  FLUX -.->|holds| PK
----

`FluxRoot` is the chicken-and-egg solver: it is the single bootstrap object (a `GitRepository`
pointing at the cluster's rendered branch + a root `Kustomization` with `prune` and SOPS
decryption) that, once seeded, lets Flux self-manage everything else from the branch.

[[layers]]
== The branch reconciles in layers, not one atomic apply

A single `Kustomization` over `path: ./` applies the WHOLE branch atomically with an up-front
server-side dry-run — and that dry-run *hard-fails on any CR whose CRD is not yet registered*
(`no matches for kind "GatewayClass" in gateway.networking.k8s.io/v1`). Because the apply is
atomic, one such resource blocks the entire branch. This is structural, not incidental: the branch
mixes CRDs, the operators/installers that register *more* CRDs at runtime, and the CRs that need
those CRDs — an ordering the flat model cannot express.

So `FluxRoot` seeds a single **root `Kustomization` `flux`** over `./flux` — plus one child
`Kustomization` per **service** `(layer, domain, package)` cell, generated post-explode by
`FluxServiceKustomizationPlanner` and written under `./flux`. The root applies (owns) the children;
each child reconciles its own `./<layer>/<domain>/<package>` path. An operator sees per-service
progress in `flux get kustomizations` (`mesh-headscale`, `runtime-flox-controller-crds`, …), a
failure stays local to one service, and retries are independent — where the old flat per-layer
stack lumped every domain's resources into four opaque `Kustomization`s. The reconcile ORDER still
comes from the layers, now carried by the children's `dependsOn` (the planner's full mechanics, the
two gaps a live cold-start exposed, and the planned domain-scoped v2 are in
link:../manifests/flux-kustomization-planner.adoc[The Flux Kustomization Planner]):

----

  ko2 -.->|barrier| kw1

A child's `dependsOn` combines two sources:

. the **layer barrier** — a cell depends on every cell of the immediately-previous NON-EMPTY layer
  (crds → foundation → operators → workloads), so a CR's CRD (rendered, or registered by a
  foundation/operators provider) is applied first *transitively*, without enumerating each CR→CRD
  edge; and
. **intra-layer service→service edges** from a unit's `dependsOnManifestsUnitIds`
  (`mesh-headplane` after `mesh-headscale`, both `workloads`). Only SAME-layer edges are emitted: a
  cross-layer unit dep is either already covered by the barrier (dep in an earlier layer) or would
  invert it (dep in a later layer — the layer assignment wins). Barrier edges only ever point to a
  lower layer and intra-layer edges stay within one layer (the unit graph is a DAG), so the combined
  `dependsOn` graph is acyclic by construction; the root's `wait: true` makes it Ready only once
  every child is.

The four layers keep their meaning as the barrier's rungs:

. *crds* — every rendered `CustomResourceDefinition`. Applied first; Flux's own CRD-first ordering
  plus this explicit layer means a CR's *rendered* CRD is always established before the CR.
. *foundation* — the cluster-wide providers later operators depend on. Today that is *cert-manager*
  (a `HelmChart` that registers the `cert-manager.io` CRDs and runs the issuer). It is distinct from
  `operators` because an operator's install bundles a `Certificate` whose CRD must be registered —
  and whose issuer must be running — before that operator layer can even dry-run. `wait: true` holds
  the chain until cert-manager is healthy.
. *operators* — the installs that register CRDs / bring controllers *at runtime* (the Cluster API
  operator + provider CRs, the envoy-gateway installer `Job`). `wait: true` blocks until they are
  healthy — e.g. the envoy-gateway installer `Job` has completed, so the Gateway API CRDs it applies
  exist. This is the layer that covers CRDs NOT carried as rendered manifests but registered by an
  in-cluster actor. (flux-operator itself is in the node-side bootstrap lane, not this branch.)
. *workloads* — everything else: the CRs that depend on an operator-registered CRD (`GatewayClass`,
  the CAPI `Cluster`/`RKE2ControlPlane`/`LXCCluster` set, `HelmRelease`s, plain app YAML). By the
  time this layer applies, both rendered CRDs (layer 1) and runtime-registered CRDs (layer 2, waited
  on) exist, so the dry-run passes.

*Layer assignment* is annotation-driven, mirroring the node-bootstrap lane
(link:../nixos-substrate/node-bootstrap-delivery.adoc[node-bootstrap delivery]): the default is
`workloads`; a `CustomResourceDefinition` is routed to `crds` by kind; a unit that installs an
operator/CRD-registrar carries a `layer=operators` annotation (`PackageMetadataProfile`). The
exploder writes each resource under `&lt;layer&gt;/&lt;domain&gt;/&lt;package&gt;/…` (unchanged);
`FluxServiceKustomizationPlanner` then reads those written cells plus the in-memory dependency graph
(`CoherentManifestsDomainRegistry`) and emits the per-service children. Child names are the bare
`&lt;domain&gt;-&lt;package&gt;` (a `-&lt;layer&gt;` suffix only for a service whose resources span
layers, e.g. `runtime-flox-controller-crds`/`-operators`); the cluster slug is dropped — the branch
+ `flux-system` namespace are already per-cluster (a single, self-managing management cluster, not
hub-and-spoke).

This is the durable answer to the recurring CRD↔CR ordering problem — not a per-resource patch, now
with per-service observability on top. A new operator only needs its `layer=operators` mark; its CRs
stay in `workloads` and wait for the barrier.

== The management cluster is function-of-git too

Because the management cluster now runs Flux against `manifests/nikopol-mgmt`, the workload CAPI CRs
are *GitOps-reconciled by the management cluster's Flux* — not imperatively pushed. This revives, in
its correct form, the "GitOps source" role the CAPI CRs were always documented to have: a controller
finally pulls them, and that controller is Flux.

Consequences:

* **The imperative "Stage B `kubectl apply`" dissolves into Flux.** The old
  `stagea-stageb-handoff-contract` sequence (`seed-mgmt` pushing the workload CRs into the live
  management cluster) is replaced by: the CRs live in `manifests/nikopol-mgmt`, Flux applies them,
  CAPI reconciles them.
* **`seed-mgmt` Stage A shrinks to two acts**: nix-seed the single management node, and bootstrap
  `FluxRoot` (the `GitRepository` + root `Kustomization` pointing at `manifests/nikopol-mgmt`). From
  there Flux installs the CAPI operator + providers AND applies the workload CRs — all from the
  branch. The management cluster is reconstructible from its branch exactly like a workload.
* **The absent bare-metal's workload is optional.** `bioskop-wrkld`'s `Cluster` CR is either carried
  with `spec.paused: true` in `manifests/nikopol-mgmt` (defined but not reconciled) or simply
  omitted until bioskop is up. CAPI's `paused` is the mechanism; the choice is an implementation
  detail of the render.

== The staging evolves

The DARWIN-local staging (`.local.d`, see link:../osgi/host-cellar-realisation-spec.adoc[host
Cellar realisation] and `BootstrapPaths`) currently materialises the rendered manifests into a local
`rke2-manifests.d` (with a rotation slot / drift / `host.live.d` promotion) that a single RKE2 server
auto-applies. Under this model that whole materialisation *leaves* `.local.d`: the synthesis renders
the per-cluster tree and **pushes it to `manifests/<host>-<role>`** (into a transient git
worktree of the branch) as history-preserving commits, not into a `server-manifests` drop-in. The
rotation / promotion machinery is replaced by the render-then-push of a branch. `.local.d` is **no
longer the delivery
channel**.

What stays in `.local.d` is then only what legitimately does *not* belong in git — the artefacts of
a local run, never desired state:

* the **incus image** (`rootfs.squashfs`, `incus.tar.xz`, `.image.checksum.sha256`) — the canonical
  case: a large binary build output that must never enter git;
* the **kubeconfig** (a credential);
* run **logs** and the rendered **runbook**.

So the separation is clean: *desired state* (the rendered manifests) lives in the `manifests/*` git
branches; *local run artefacts* (image, kubeconfig, logs) stay in the gitignored `.local.d`. The flat
`.local.d` layout (link:management-workload-topology.adoc[one management node]) is unchanged — it
simply sheds the manifest-materialisation trees it used to carry.

=== What the host staging becomes

The elaborate host-folder staging — the rotating slots (`host.N.staging.d`), the drift files
(`host.N.drift.*`), the promotion to `host.live.d`, the retention count — existed for the old
"materialise into `rke2-manifests.d`, rsync to the remote, keep N slots" delivery. Git subsumes it,
because the render is a *pure function* of `(main, config, descriptor)` and therefore reproducible:

[cols="1,1",options="header"]
|===
|Host staging (today) |Rendered-branch (new)

|`host.N.staging.d` rotating slot |a transient git *worktree* of `manifests/<host>-<role>` to render into
|`host.N.drift.*` (staged vs live) |`git diff` (render worktree vs branch HEAD) before push
|promotion rsync → `host.live.d` |`git push` (history-preserving, atomic ref update)
|N-slot retention (rollback) |the branch history — `git revert` to a prior rendered commit (or re-render from `main@<sha>`)
|remote reads `host.live.d` over the automount |Flux / `seed-master` read the branch — no manifests rsync
|===

The render worktree lives at **`.local.d/render/<host>-<role>/`** — a linked git worktree of the
branch, *inside* gitignored `.local.d`. That nesting is deliberate and clean: the `.local.d` ignore
makes the main worktree never look inside it (no untracked noise, no "embedded repo" gitlink), while
`.gitignore` being per-checkout means the parent's ignore never leaks into the rendered branch's own
tracking. Cleanup is `git worktree remove`.

Two consequences fall out:

* **The automount becomes image-only.** With manifests delivered through git, the remote NixOS host
  no longer reads a manifests tree over the automount — the bi-machine rsync of manifests dissolves,
  and `asAutomountView` / `netPrefix` rebase *only the incus image artefacts* (§ the `.local.d`
  split). That is what keeps the automount machinery earning its place.
* **Drift doubles and improves.** The single local "staged vs live" diff becomes two: `git diff`
  (pre-push, to review the change) and Flux reconciliation (post-push, git-vs-cluster — the *actual*
  drift). Neither is a local rotation file.

So increment 1 *removes* the host-staging machinery (`HostSlotSelector` rotation,
`BootstrapPaths.asStagingView` / `liveRoot`, the drift files, the retention count) and replaces the
render target with the git worktree above. The only local materialisation left is the `local-only`
bootstrap seed.

== Naming

Branches follow the cluster naming convention `<host>-<role>` (see
link:management-workload-topology.adoc#naming[the topology's naming convention]), namespaced under
`manifests/`:

* `manifests/bioskop-mgmt` / `manifests/nikopol-mgmt` — the management cluster, on whichever
  bare-metal currently hosts it.
* `manifests/bioskop-wrkld` — the workload on bioskop.
* `manifests/nikopol-wrkld` — the workload on nikopol.

`git branch --list 'manifests/*'` enumerates the rendered clusters — the branch-per-cluster analogue
of "see the clusters materialised".

== The cluster descriptor is generic — growth ≠ function

A cluster is `{ name=<host>-<role>, host, role, topology }`. The **topology** — single vs multi
node, the control-plane count (the etcd quorum), the workers and their roles — is a *generic*
descriptor that applies to every cluster. It is independent of *how* the cluster is grown:

* the *management* cluster's topology is single-node (one control-plane, no workers, never scales —
  it is nix-seeded and reconstructible from its branch);
* a *workload* topology is HA (master + peer1 + peer2 = three etcd members, plus workers).

`manifests` renders each cluster from `{ role, topology }`. The **growth mechanism is the consumer**
of that render, and it is the only thing that differs per cluster: `seed-mgmt` nix-seeds the single
management node from its rendered RKE2 config; CAPRKE2/CAPN greenfield-create a workload's nodes from
`RKE2ControlPlane.replicas` + `MachineDeployment`. **Growing a cluster does not change how it
functions** — the functional topology is the same descriptor whichever mechanism materialises it.
This is why the render stays uniform across clusters even though only workloads go through CAPI.

== The render's inputs beyond the descriptor

Beyond the descriptor `{ host, role, topology }` (the *what*), the synthesis is parameterised by two
further facets of *how* it renders.

=== Output shape — which consumer's language

A `manifests/*` branch has *no single canonical shape*: **its shape is a function of who consumes
it.** `manifests` (the SSOT) projects the same rendered intent into the form each consumer expects,
and a new consumer is just a new projection off the one source:

* **`seed-master`** → a **sow**: the management node's RKE2 bootstrap (single-node config + the
  `FluxRoot` seed), applied `local-only` to bring the node up. NOT CAPI CRs — the management cluster
  is self-seeded, never a CAPI product.
* **Flux** → **reconcilable manifests**: Kustomizations / HelmReleases / plain YAML it applies to a
  cluster core (the app stack, the CAPI operator + providers).
* **CAPI/CAPN** → **CRs**: `Cluster` / `LXCCluster` / `RKE2ControlPlane` / `LXCMachineTemplate` /
  `MachineDeployment` — carried as plain manifests Flux applies, then reconciled by CAPI into nodes.

Where a shape is a projection of the generic *topology* (the `seed-master` sow and the CAPI CRs), it
is the *one* topology expressed in that consumer's language: `topology.controlPlanes=3` →
`RKE2ControlPlane.replicas=3` for CAPI; `=1` → a single-node RKE2 config for `seed-master`. Growth ≠
function — the same topology, one rendered form per consumer.

=== Delivery target — where it lands

* **`branch`** (steady state) — push `manifests/<host>-<role>` (history-preserving); Flux reconciles.
* **`local-only`** (bootstrap) — the node's local `server-manifests`, applied by RKE2 with no git:
  the minimal `FluxRoot` + Flux seed that breaks the chicken-and-egg. It is the *only* output applied
  outside git; everything after is GitOps.

So `manifests` renders `{ descriptor } × { output format } × { delivery }`. In practice the format
follows the role and `local-only` is only the bootstrap seed, so the free knob is small — but naming
the three facets keeps the synthesis honest about exactly what it is asked to produce, and it is what
lets the *flow* be exercised (branch + either format) independently of the CAPI content maturing.

== The output contract of `manifests`

The `manifests` module's delivery contract is one sentence per cluster:

> render the cluster `<host>-<role>` (its role-selected domain set) and push
> `manifests/<host>-<role>` (keeping history).

The role selects the domain set (management: `cluster-api` + base + Tailscale client + the workload
CAPI CRs; workload: the app stack, no `cluster-api`). This is the per-cluster generalisation of the
`manifests.publish.{domain}` toggles, which move from a single global posture to a per-cluster one.

== The flow stands up before CAPI

The delivery seam is *decoupled from CAPI/CAPN*. Because delivery is nothing but "Flux reconciles a
rendered branch", the WHOLE flow — `manifests` render → push `manifests/<host>-<role>` →
`FluxRoot` in a `gitops` vCluster → reconcile — can be stood up and validated with ANY content,
before a single CAPI provider exists. A management cluster's Flux reconciling `manifests/nikopol-mgmt`
and a workload's Flux reconciling its app stack are the *same mechanism* whether or not the CAPI
operator and workload CRs are present yet.

So the rollout is two independent layers:

. **The flow** — establish rendered-branch + `FluxRoot` + `gitops` vCluster delivery, testable with
  base / app-stack content alone. This is the foundation and can be proven first.
. **CAPI as content** — layer the CAPI operator + the four providers + the workload CRs onto
  `manifests/<host>-<role>` as manifests the flow *carries*. CAPI is not a change to the seam; it is
  cargo that rides it.

This is why the split is worth doing now, ahead of the CAPI/CAPN work: it gives us a working,
observable GitOps pipeline (render → branch → Flux → cluster) that the harder CAPI step then plugs
into, rather than co-developing both at once.
