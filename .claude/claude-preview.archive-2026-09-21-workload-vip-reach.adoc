= Scratchpad — l'@VIP d'un cluster workload : exister, puis être joignable
:toc: left
:toclevels: 3

État live mesuré le 2026-09-21 sur `bioskop-mgmt` / `bioskop-wrkld`, après la naissance du premier
nœud workload. Ne rouvre RIEN : l'architecture est tranchée dans
link:../docs/architecture/cluster-api/management-workload-topology.adoc#cp-endpoint-reach[management-workload-topology.adoc#cp-endpoint-reach].
Ce scratchpad ne fait que montrer *où en est le code* contre cette cible.

== L'idée en une phrase

L'@VIP est **deux problèmes distincts** :

. **Exister** — quelque chose doit *porter* `10.80.15.10` sur le nœud control-plane du workload.
. **Être joignable** — le cluster de gestion doit pouvoir *atteindre* cette adresse.

Les deux sont **déjà codés**, chacun comme une unité de manifeste. Il n'en manque qu'**une seule
chose**, et elle produit les deux symptômes : le cluster workload n'a ni branche rendue ni Flux,
donc il ne reçoit aucune des deux unités.

CAUTION: La prémisse de cette figure — « le manque = pas de branche + pas de Flux » — est

carve pas le bundle de bootstrap de ses cibles**. Les deux invariants ci-dessous restent vrais.

Deux invariants que la figure encode :

* `controlPlaneEndpoint` **reste le VIP** — c'est ce que consomment les nodes workload et kube-vip
  lui-même. Pas de FQDN de substitution, pas de réécriture du `server` du kubeconfig : le Connector
  rend l'adresse *réellement routable*, donc CAPI la compose telle quelle.
* Le reach passe par le **node-plane** (`mammoth-skate`), jamais par le workload-plane
  (Headscale, pods↔pods) — le VIP est une adresse de *node*. Sinon on couplerait le reach de gestion
  au réseau applicatif.

== Ordre d'exécution qui découle de la figure

. **`external`** — FAIT le 2026-09-21 (`90e790a0f`). C'était un *prérequis* : sans elle, dès que Flux
  arrive dans le workload, l'Addon RKE2 et Flux se disputent `system:kube-vip-role`/`-binding`
  (figure 2). Inerte sur les deux `LXCCluster` déjà créés (`ensure` = create-if-absent).
. **Rendu multi-cluster + branche `-wrkld` + Flux amorcé là-bas.** C'est le chantier
  `workload-grow-foundations`. Au moment où Flux tourne dans le workload, les DEUX unités atterrissent
  ensemble — la VIP apparaît *et* devient routable dans le même mouvement.
. **Rien d'autre à coder** pour l'@VIP.

= Brainstorm — amorcer un cluster né de CAPI/CAPN : le poseur manquant

Suite du 2026-09-21. Le nœud de `bioskop-wrkld` est né mais `NotReady`, et rien ne tourne dessus.
Ce qui suit confronte le modèle tranché

Quatre propriétés qui font pencher pour cette forme :

* **le secret n'entre jamais dans un spec** — `contentFrom` est une *référence*, ce qui la rend
  compatible avec le modèle B (le CR-set du workload est rendu sur la branche du manager) ;
* **le propriétaire unique est préservé sans rien ajouter** — la règle de la figure 4 s'applique telle
  quelle ;
* **l'ordonnancement est inhérent** — `write_files` précède rke2, la même garantie que le oneshot ;
* **aucun concept nouveau** — pas d'annotation supplémentaire, pas de ConfigMap par objet.

== Le seul point encore ouvert : QUI carve le bundle du workload

Le carve se fait par **passe de synthèse**, donc par cluster rendu — et `bioskop-wrkld` n'a pas de
passe. Deux lectures :

[cols="1,2,1",options="header"]
|===
| Lecture | Conséquence | Verdict

| le render du MANAGER carve un bundle par cible
| exactement la forme que `RuntimeRke2ConfigManifestsUnit` a déjà (« the manager's branch, not its own » + chaque `workloadTarget`)
| cohérent avec le modèle B

| chaque cluster carve le SIEN
| suppose qu'il tourne déjà, donc inapplicable au premier amorçage
| circulaire
|===

Le modèle B tranche de fait : les CR CAPI du workload vivent déjà sur la branche du manager, le bundle
de bootstrap suit la même règle.

== Ce que ça reformule

Le blocage n'est pas « il manque Flux dans le cluster de charge ». C'est **« le manager ne carve pas
encore le bundle de ses cibles »** — une seule cause, dans un endroit connu, et qui explique d'un coup
cilium, kube-vip, Flux et le Connector.
