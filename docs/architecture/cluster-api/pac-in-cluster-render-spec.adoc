= In-cluster manifests render via Pipelines-as-Code — the upstream GitOps loop
:toc: left
:toclevels: 3

== Overview

The GitOps delivery loop has two halves. The *downstream* half is shipped
(link:manifests-rendered-branches.adoc[the rendered-branch model] + the Flux push webhook):
a push to the rendered branch `manifests/<cluster>` triggers a Flux reconcile at once. This
document specifies the *upstream* half: when the manifests **source code** changes, re-render and
push `manifests/<cluster>` **in-cluster**, without a grow.

Three lanes, one operation:

* *Grow* (seed-master) — the FIRST render+push, host-side. It MUST be host-side: at bootstrap there
  is no cluster, no Tekton, no webhook, and Flux needs the branch to pull.
* *Downstream* (Flux webhook) — the rendered branch changes → reconcile.
* *Upstream* (THIS doc) — the source changes → re-render → push the rendered branch → downstream fires.

The render+push OPERATION is not owned by any executable — it lives in OSGi (the
`ghapp`→`auth`→`manifests` scion graph, driven through the `seed.broker.port` membrane). seed-master
and the `manifests publish` CLI are thin HOSTS that sow the SAME coordinates, differing only by
envelope (Pulumi grow vs standalone CLI). The upstream lane runs `manifests publish` inside a
Tekton PipelineRun — no standing renderer workload (staleness-free: it builds from the source it
renders; the first render stays seed-master's, Tekton maintains).

*Why Pipelines-as-Code (PaC), not raw Triggers or a bespoke renderer Deployment:* PaC is Tekton's
GitHub-App-native CI — it handles the webhook, matches PipelineRuns from the repo's `.tekton/`, and
authenticates as a GitHub App. We already baked a GitHub App for this automation and PaC is already
installed (Tekton profile `all`). Reusing it dissolves the webhook plumbing AND the in-cluster push
credential (see <<auth>>). Don't reinvent the wheel.

[#namespaces]
== Namespaces — rke2lab owns its runs, Tekton owns its controllers

The render loop is split across two namespaces by OWNERSHIP, not lumped in `tekton-pipelines`:

[cols="1,2",options="header"]
|===
| Namespace | What lives there

| `rke2lab-system` (the runtime-system namespace, already home to flox-controller)
| rke2lab's OWN render artifacts — the `Repository` CR (which binds the source repo to THIS
  execution namespace), the `render-manifests` `Pipeline` + its `git-fetch`/`render-publish` Tasks,
  the Maven-cache PVC, the `manifests-render-signing` Secret, and the PipelineRuns PaC creates. PaC
  runs a matched PipelineRun in the `Repository`'s namespace — so this is where the runs execute.

| `tekton-pipelines`
| The Tekton + Pipelines-as-Code CONTROLLERS (their system), the global `pipelines-as-code-secret`
  the PaC controller reads to act as the App, and the Tailscale funnel `Ingress` (its backend is the
  `pipelines-as-code-controller` Service, which must be co-located).
|===

The PaC controller (in `tekton-pipelines`) watches `Repository` CRs cluster-wide and creates the
PipelineRun in the CR's namespace, so its RBAC must reach `rke2lab-system` (verified at grow).

[#funnel-durability]
=== Durable funnel identity — no Let's Encrypt re-issuance across grows

The funnel's LE cert was re-issued every cold-start because the Tailscale proxy returned as a NEW
device (fresh node key): the operator stores the proxy's tailscaled state (node key + cert) in a
Secret named after the pod (`TS_KUBE_SECRET=$(POD_NAME)`), etcd-ephemeral, lost on re-grow → enough
re-grows in 168h hit the per-FQDN 5-cert limit → `getCertPEM: 429` → no TLS → dead webhooks.
Persisting etcd would make a cold-start inconsistent (it carries the old cluster forward), so the fix
is SURGICAL — persist ONLY the funnel identity: a `ProxyClass` pins `TS_KUBE_SECRET` to a stable name;
a static PV + `ZFSVolume` adopt the dataplan's `tank/rke2lab/<role>/persist/funnel-cert` dataset
(`Retain`) — per-cluster, and placed by the in-cluster volume controller rather than named in the
render (<<funnel-node-affinity,why>>); a *restore* Job seeds the saved state into the stable Secret,
and a *backup* Job mirrors it back out.
The proxy then returns as the SAME device → Tailscale serves the existing cert → no re-issuance. The
proxy cannot mount the PVC itself (ProxyClass exposes no volume), so the helper Jobs do. See
link:../patterns/dataplan-single-source.adoc[Dataplan SSOT] (the persist tier).

EVERY funnel is persisted, not just PaC. The canonical set is the `FunnelLeaf` registry (a dual-realm
enum in `manifests.ingress`: `pipelines-webhook` + `flux-webhook`), each carrying its stable state
Secret (`ts-<leaf>-state`) and per-funnel `ProxyClass`. The restore/backup Jobs LOOP `FunnelLeaf`, one
per leaf, over `/persist/<leaf>/state.yaml` on the shared PV; `FluxReceiverManifestsUnit` opts
flux-webhook into its `ProxyClass` (it was previously un-persisted and re-registered every grow).

The purge and the persistence must not fight: `TailnetPurgeManifestsUnit` runs `manage-tailnet
--prune-stale-devices` which would DELETE the very (offline, stale) device whose identity the restore
brings back — so the restored node key would point at a deleted device and the proxy re-registers
(new device, cert re-issued) instead of re-attaching. The purge therefore passes `--keep-host <leaf>`
to SPARE a persisted device — but CONDITIONALLY: only for a leaf whose `/persist/<leaf>/state.yaml`
exists (there is state to re-attach to). A leaf with no backup yet is NOT spared, so its stale device
is pruned and the fresh proxy claims a clean name; the first backup then establishes its state and the
next grow re-attaches. A drifted duplicate (`<leaf>-1`) never matches the bare `--keep-host` name, so
it is always pruned — the reclaim we want. Needs the ndh `manage-tailnet --keep-host` flag.

Until 2026-09-27 the per-cluster `Connector` device was the one un-persisted orphan this pruning had
to sweep on every grow. It is gone: the bare-metal advertises its own `vmnet` segments now (ndh
`cluster-vmnet.nix`), and a host device is PERSISTED — so no tailnet route churns with a cold start
any more, and none needs re-approving. See
link:management-workload-topology.adoc#cp-endpoint-reach[the reach mechanism].

[#funnel-per-cluster]
==== A funnel's identity is PER-CLUSTER — the leaf alone is not it

Everything above was written when there was one cluster, so the leaf *was* the identity. A workload
cluster needs its own funnels (its Flux receives, its PaC acts), and the moment it does, the flat
shape is not untidy — it *defeats the mechanism for both clusters at once*.

A funnel's identity is the triple **(FQDN, tailnet device, cert)**, and the budget this whole section
protects is per *exact FQDN*. So two clusters on one leaf name means: both proxies overwrite the same
`/persist/<leaf>/state.yaml`, both return as new devices, both re-issue, both walk into the `429`.

And worse, deterministically: the second cluster cannot even claim the bare name. The tailnet suffixes
it (`flux-webhook-1`), and per the purge rule above a drifted duplicate *never matches the bare
`--keep-host` name, so it is always pruned* — so the manager's purge Job would delete the workload's
funnel device on every run, forever.

The cluster dimension is therefore missing in four places that are all the same fact:

*The dataset*:: `tank/rke2lab/persist/<cluster>/funnel-cert`. The `persist` tier stays ONE sibling of
`control-nodes`, so the "the ephemeral wipe never reaches it" invariant is still expressed at a single
level. The `<leaf>/state.yaml` subdirectories live inside it, unchanged.

*The FQDN*:: `FunnelLeaf`'s hostname gains the cluster — `FluxReceiverManifestsUnit`'s
`FUNNEL_HOSTNAME` is a bare constant today.

*The leaf-derived names*:: the stable state Secret `ts-<leaf>-state` and the per-funnel `ProxyClass`.

*The purge*:: `--keep-host` must name the cluster's FQDN, or one cluster's purge prunes another's
device.

So the contract change is `FunnelLeaf` — a dual-realm enum whose leaf was the whole identity —
becoming **(cluster, leaf)**. That, not the PV, is the shape that moves. The enum keeps only the leaf
vocabulary; a `Funnel` record carries the pair and derives everything named after the funnel:

[source]
----
hostname     = <cluster>-<leaf>        bioskop-mgmt-flux-webhook
stateSecret  = ts-<hostname>-state    ts-bioskop-mgmt-flux-webhook-state
proxyClass   = <hostname>
persistSubdir= <leaf>                 the volume is already per-cluster
----

Cluster FIRST, like every other composite name here (`bioskop-mgmt-master`,
`<cluster>-server-manifests`), so a fleet's funnels group by cluster in `tailscale status` rather than
interleaving. The persist SUBDIRECTORY keeps the bare leaf: the dataset is per-cluster already, so
qualifying the path inside it would say the same thing twice.

This also removed a duplicate: `PacWebhookFunnel` (the host-side face that builds the GitHub App's
webhook URL) re-declared `"pipelines-webhook"` as its own `LEAF` constant — the same string in two
places. It now carries the cluster and derives the leaf from the enum.

[WARNING]
====
*A GitHub App has ONE webhook URL, and every cluster now exposes its own PaC funnel.* The App can
point at exactly one of them, so *which cluster receives PaC events is a decision, not a derivation*.
Today it is the management cluster's funnel (`ghapp create` pre-fills that one). The workload
cluster's PaC funnel exists and is persisted, but nothing delivers events to it until that decision is
made — a second App, or a router in front.

Note this is NOT the same question as Flux's per-cluster tokens: those are many mints from the *same
one* App key (see <<_auth_two_distinct_secret_properties_resolved_by_the_execution_enclosure,Auth>>).
The App is fleet-wide; only its webhook is singular.
====

ONE PV per CLUSTER, not per leaf. The <<funnel-ordering,dependency graph>> already serialises the
restore and backup Jobs so they never contend for the single RWO claim; a PV per leaf would discard
that argument and force it to be re-made. Per cluster it is kept verbatim, and the controller has one
volume per `ClusterIntention` to own.

A happy side effect: the spec's own escape hatch is that renaming an FQDN opens a *fresh* 5-cert
budget. Migrating to per-cluster names IS that rename, so it is also the way out if `flux-webhook`'s
budget is already spent. It costs updating the GitHub App's webhook URL, as the WARNING below notes.

NOTE: the maven cache has LANDED on that same tier, and the shape is settled:
`tank/rke2lab/<role>/persist/maven-cache` — keyed by `ClusterRole`, not by cluster name, for the
reason `DataplanLayout` gives (the projection ndh consumes is one checked-in list materialised on
every host, so it cannot name hosts). It is adopted by a `VolumeIntention` the render pipeline
renders, exactly as the funnel cert is, so the dataset is no longer the unadopted orphan that made
declaring it litter. What forced the move was not tidiness: as a Tekton *workspace* the cache was
co-mounted by the affinity assistant, which required the `shared: yes` bind-mount class, which lives
on the ephemeral tier — where a dynamic `pvc-<uuid>` leaked one dataset per cold start (measured
2026-09-24: eight datasets for one live claim) and a node-pinned PV stranded the cache on the first
control-plane roll. See `RenderPipelineManifestsUnit` § workspaces-vs-caches.

[#funnel-node-affinity]
==== The volume belongs to the CONTROLLER — a managed node's name is not render-time knowledge

The static-adopt pattern is load-bearing: it is the only thing that survives an etcd wipe. Dynamic
provisioning cannot replace it — a cold start wipes the PVC object, so openebs provisions a *fresh*
`pvc-<uuid>`, the old dataset leaks and the cert is lost. That is precisely why the PV is pre-declared
and adopts a dataset by stable name.

But a pre-declared PV needs a node: `spec.nodeAffinity` (matched on the `openebs.io/nodename` label)
and the `ZFSVolume`'s `ownerNodeID`. On a CAPI-provisioned cluster the node's name is RANDOM
(`bioskop-wrkld-control-plane-v9fhz`), so no render-time literal can ever match — and the literal in
`FunnelCertRestoreManifestsUnit` (`bioskop-mgmt-master`) is not a bug to parameterise so much as an
admission that the unit was only ever meant to run on a host-grown cluster.

A node LABEL does not free us either: `ownerNodeID` must equal the `ZFSNode` object's name, and
openebs names that after the node. The label is standard for the scheduling half only.

So the render declares the INTENT and names no node — a `VolumeIntention`
(`dataplan.seedmatic.io/v1alpha1`) carrying this cluster's persist pool, the dataset, the size, the
claim to satisfy and the KIND of node eligible to serve it. A controller owns the volume: it elects a
node, then creates the `ZFSVolume` (stamping `ownerNodeID`) and the static PV (stamping
`nodeAffinity`). Keeping openebs in the path is what *enforces* single access — exactly one `ZFSNode`
serves the volume — rather than leaving `ReadWriteOnce` as a contract nobody polices.

*Which controller — NOT `seed-incluster`.* The first instinct was to give this to the existing adopter,
but it cannot: `seed-incluster` speaks only to the MANAGEMENT cluster. It never opens a client to a
workload cluster — it learns reachability by reading CAPI's `RemoteConnectionProbe` condition on the
`Cluster`. The volume, meanwhile, lives *in the target cluster*. Giving `seed-incluster` a remote client
would be a new capability (RBAC, caching, error paths) and would make every object it wrote there a
second poser facing Flux.

So the volume controller is a *separate binary running in the cluster it serves* — a second `cmd/` in
the same Go module as `seed-incluster`, sharing its internal packages but declaring *its own CRDs and
its own ClusterRole*. That separation is the point, not an accident of packaging: a single binary
switched by a `--role` flag would ship one controller-gen `role.yaml` carrying CAPI rights into a
managed cluster, and would leave
link:cluster-seeding-controller.adoc#single-adopter[the single-adopter invariant] resting on the value of
a flag. Its RBAC is small and local: `nodes`
get/list/watch, `persistentvolumes` and `zfsvolumes.zfs.openebs.io` get/create/patch, and nothing under
`cluster.x-k8s.io`.

It also runs in the MANAGEMENT cluster, for the same reason: mgmt has the identical need and only
appeared to work because the literal happened to match its one node's name. One owner for persist
volumes, fleet-wide.

NOTE: this is unrelated to the workload cluster hosting CAPI for its vclusters (which it will — the
vcluster CAPI provider hosts vclusters only in the cluster where it runs). A vcluster has no machines,
no pool, no pet and no etcd quorum, so `seed-incluster`'s adopt-first primitive has no referent there;
that is why it still does not run in a workload cluster, and why the CAPI CRDs being present there makes
the flag-switched variant *more* dangerous, not less.

IMPORTANT: this is the FOURTH place "a CAPI node's name is random" has cost something, after the
infraRef naming divergence, the missing ZFS dataset GC, and the declared `CONTROL_NODES` list. Read it
as an invariant rather than a series of bugs: *nothing the render produces may be keyed on a managed
node's name.*

[#pet-label]
==== Giving a managed node its PET identity back — a Machine label CAPI propagates

The invariant above says what may not be keyed on a node's name; it does not give the render anything
to key on INSTEAD. A pet label does: the node carries `master` / `peer1` / `peer2` as a first-class
fact, so a `nodeSelector` (the funnel pod), a PV `nodeAffinity` and a legible election ("the persist
volume belongs to the pet `master`") stop needing the opaque `…-v9fhz`.

Two routes were considered and one is a trap.

*NOT by taking over Machine creation.* Pre-creating the greenfield Machines with pet names would give
deterministic instance names and dissolve the root cause — but `RKE2ControlPlane` names its Machines
because it OWNS their lifecycle: the init-vs-join decision, etcd membership and quorum, scale, rollouts
on a version change, remediation. Taking the naming takes an unbounded slice of that. The adoption path
proves CAPRKE2 counts a pre-created Machine as its replica, but explicitly *without* bootstrapping it
(`dataSecretName` with no `configRef` — the sentinel), so it is no evidence for the greenfield case.

*NOT via cloud config either, on the managed path.* Each Machine does get its own `RKE2Config`
(measured: `Machine …-rmz8z` → `configRef: RKE2Config/…-566v4`), so a per-machine channel EXISTS — but
CAPRKE2 authors it from the one `RKE2ControlPlane` spec, and would regenerate anything we patched in.
`spec.files` is likewise one set for every replica, which is exactly why the RKE2 config fragments are
node-invariant. (On the HOST-grown path the opposite holds: `InstanceGrow` writes cloud-init per
instance, so `node-label=` would be trivial there. `NodeRestriction` is not the obstacle — it protects
the `kubernetes.io/` and `k8s.io/` namespaces, and a third-party domain is permitted from a kubelet.)

*The supported route: assign, don't name.* The controller sorts the control-plane Machines by
`creationTimestamp` — deterministic, monotonic, CAPI-owned — and assigns `master`, `peer1`, `peer2` in
order, skipping any Machine that already carries a pet. Sticky and idempotent by construction, and it
creates nothing: `RKE2ControlPlane` keeps its whole lifecycle.

The assignment is written as a MACHINE label whose domain CAPI propagates to the Node. Verified against
`util/labels/helpers.go` (`GetManagedLabels`), the sync set is:

* `node-role.kubernetes.io`
* `node-restriction.kubernetes.io` and any `*.node-restriction.kubernetes.io`
* `node.cluster.x-k8s.io` and any `*.node.cluster.x-k8s.io`
* anything matching an operator-supplied `--additional-sync-machine-labels` regex

So `rke2lab.io.node.cluster.x-k8s.io/pet: master` lands on the Node with no further wiring — set by the
CONTROL PLANE, which is what that mechanism is for.

WARNING: the pet label does NOT remove the need for the controller to resolve a node NAME.
`ZFSVolume.ownerNodeID` must equal the `ZFSNode` object's name, which openebs names after the node
(measured: `ZFSNode/bioskop-wrkld-control-plane-v9fhz`, with `openebs.io/nodename` and
`openebs.io/nodeid` both valued at the node name). A label serves the scheduling half only — a PV's
`spec.nodeAffinity` is a standard `NodeSelector`. Nor does it fix the dataset leak; that needs the
per-cluster pools (link:../patterns/dataplan-single-source.adoc#per-cluster-pools[dataplan]).

===== What the pet may and may not name

The label makes a stable role available, which invites using it wherever a random node name hurts. It
has exactly one legitimate use here, and one tempting illegitimate one.

✅ *Electing the owner of a PERSIST volume.* The pet is a better key than sorting the control-plane
Machines by `creationTimestamp`: when the role moves — a remediated `master` — the label moves with it,
so the controller re-stamps `ownerNodeID` and the affinity toward the node that now HOLDS the role. A
date sort would keep designating the oldest survivor instead.

❌ *Naming an EPHEMERAL dataset path.* Two independent reasons, both in
link:../patterns/dataplan-single-source.adoc#pet-not-in-the-path[the dataplan's rule] with a sequence
figure: the label does not exist yet when the path is needed (the containerd dataset is mounted
`before=rke2-server.service`, so before the node joins and before any `Node` object exists), and a pet
is RECYCLED — a replacement machine inherits it, so a pet-named dataset would hand the new node the
previous one's snapshotter state.

****
*The rule.* The pet names what must SURVIVE. The node name names what must NOT.
****

[#funnel-ordering]
==== The ordering is STRUCTURAL — restore before the operator, not timing

The invariant: when the tailscale proxy starts, its state Secret must ALREADY hold the persisted cert,
so it reuses it (zero ACME). The operator is the SINGLE actor that creates the proxy (and the Secret,
if absent) when it reconciles the funnel Ingress — so the restore must land the Secret *before the
operator runs*. Leaning on Flux LAYER timing (operators-before-workloads) is not enough: the layers
race, and a cold-start observed the proxy issue a fresh cert while the restore Job was still starved.
The fix makes the order a DEPENDENCY GRAPH, not timing:

* *`FunnelCertRestoreManifestsUnit`* (its own service) renders the restore Job + the `VolumeIntention`
  + the PVC + its RBAC — it renders NO `tailscale.com` CR, so it depends only on openebs (the derived
  `zfs.openebs.io` CRD edge), NOT on the tailscale operator. The `ZFSVolume` and the static PV are NOT
  rendered: <<funnel-node-affinity,the volume controller>> creates them, so the PVC stays Pending until
  a node has been elected.
* *`TailscaleManifestsUnit`* (the operator) `dependsOn` `FunnelCertRestoreManifestsUnit` — so Flux
  applies + health-gates the restore Job to completion BEFORE the operator is up to provision any
  proxy. The operator then adopts the pre-seeded Secret (its `sts.go` `Get`+`MergeFrom`, no new
  authkey).
* *`FunnelStatePersistenceManifestsUnit`* keeps the `ProxyClass` + the backup Job; it `dependsOn` the
  operator (the derived `tailscale.com` CRD edge for the `ProxyClass`). Splitting restore OUT breaks
  the cycle (operator → restore, ProxyClass → operator) that one combined unit would form.

The chain — `openebs → funnel-cert-restore → tailscale operator → ProxyClass/Ingress → proxy (adopts
the seeded Secret) → backup` — is acyclic and gives the invariant by construction. It also SERIALISES
the two Jobs (restore completes far up-chain; backup runs far down-chain), so they never contend for
the one RWO persist PVC — no shared-mount storage class needed. The backup waits for the cert to be
present in the Secret before mirroring (`kubectl wait --for=jsonpath` on the `<fqdn>.crt` key), which
needs `list`+`watch` on its own Secret in the funnel-state Role.

WARNING: the per-FQDN LE budget is REAL — 5 certs / exact FQDN / 168h. A grow that re-issues (the
ordering broken) burns one. If the budget is exhausted before the fix holds, the escape hatch is to
RENAME the funnel FQDN to a fresh one (a fresh 5-cert budget) — which requires updating the GitHub
App's webhook URL to the new funnel host. Prefer getting the ordering right so the seeded cert is
reused (0 issuance) and the treadmill stops.

[NOTE]
====
*Validate with LE STAGING.* While proving the persistence/reuse mechanism, the tailscale operator runs
`useLetsEncryptStagingEnvironment: true` (`TailscaleManifestsUnit`) — staging has effectively unlimited
rate limits, so each re-grow in the loop costs nothing, where production would spend one of 5 certs /
exact FQDN / 168h per attempt.

A staging cert is UNTRUSTED, so GitHub's webhook TLS handshake fails while this is on — which is why
*SSL verification is disabled on the GitHub App's webhook for the duration*. That is not merely to keep
PaC events flowing: the in-cluster render is TRIGGERED by that webhook, so losing delivery stalls the
whole GitOps loop for as long as the validation window lasts, not just the PaC feature.

So these are a PAIR, and they must be flipped back TOGETHER:

* `useLetsEncryptStagingEnvironment` → `false` (a trusted production cert), and
* the GitHub App webhook's *SSL verification* → back ON.

Do NOT leave one without the other: staging LE + verify-on ⇒ no delivery, so no render; production LE +
verify-off ⇒ a working-but-unverified webhook that silently accepts a MITM.

The cert already on disk is handled, and it had to be: tailscaled renews on DATES alone — ARI, else 2/3
of the cert's lifetime — and never compares the issuer, since the ACME directory URL is only logged
(`feature/acme`, `shouldStartDomainRenewal`). A persisted staging cert would therefore be served for the
rest of its ~90 days with the posture already back on `PRODUCTION`. So the *backup* Job records the
posture beside the state (`/persist/<leaf>/issuance`) and the *restore* Job drops any cert that does not
match the posture in force.

The same rule covers a funnel RENAME: a cert whose key does not start with this funnel's hostname is
dropped too, so the old `<fqdn>.crt` cannot linger. Only the cert keys (`*.crt` / `*.key`) go — the node
key stays, so the proxy returns as the SAME tailnet device and the purge has nothing to reclaim. The
flip costs exactly one issuance and no identity churn.

The two halves now have ONE owner: `FunnelCertIssuance.current()`, in the dual-realm
`manifests.ingress` face. The tailscale render projects it into `useLetsEncryptStagingEnvironment`; the
ghapp webhook reconcile projects it into `insecure_ssl` (which used to be a hardcoded `0` in the edge).
So the pair cannot be half-flipped, and returning to `PRODUCTION` turns verification back on by
construction.

That coupling was forced by a measured failure, not chosen for tidiness: as a constant, `insecure_ssl`
was re-asserted on EVERY grow, so a grow silently undid an operator's manual "verification off" and
stalled the render loop mid-validation. The objection to making it state — "a render could decide to
stop verifying" — is answered by tying it to the posture rather than exposing it: nothing can set
verification off except declaring staging, and declaring production sets it back on.

WARNING: the REPOSITORY webhooks (the per-cluster Flux receivers) are NOT covered by this. Nothing
reconciles them — `GithubRepoWebhookConfigurer` exists but has no caller — so their `insecure_ssl` is
whatever an operator last set by hand, on each one.
====

== Operator setup — extend the existing App, do not create a new one

There is no Tekton/PaC webhook yet (`pipelines-as-code-secret` is unconfigured). What exists is the
baked GitHub App, whose SINGLE webhook currently drives Flux (pointed at the `flux-webhook` funnel,
HMAC `github.webhook.secret`) — there is no repo-level webhook. Configuring PaC EXTENDS the one App
(the single automation identity) — a new App would fragment the identity and double the rotation.
Out-of-band operator ceremony:

* the App has ONE webhook and PaC (in GitHub-App mode) needs it, so *repoint* the App's webhook URL
  at the PaC funnel AND give Flux its trigger back via a *repo-level* webhook (same URL — the
  `flux-webhook` funnel `/hook/<receiver-id>`, content-type `application/json`, secret
  `github.webhook.secret`, `push` event). Flux's webhook is only an accelerant over its 1m poll, so
  the brief move degrades to polling, never breaks;
* add the `push` event to the App + subscribe `Check run` for statuses;
* extend App permissions with `checks:write` (PaC statuses) + `metadata:read`, on top of the
  `contents` read (Flux pull) + write (render push) the App already carries.

[[auth]]
== Auth — two distinct secret properties, resolved by the execution enclosure

Draw the line precisely, because an early draft blurred it: the render *OUTPUT* is secret-blind, but
the render *PROCESS* is not.

* *The output branch is secret-blind.* The reconciled `manifests/<cluster>` branch Flux tracks
  carries ZERO secret bytes — every real-data secret rides the `NODE_BOOTSTRAP` lane, which the
  exploder writes OUTSIDE the git worktree (`NodeBootstrapArtifact`, a sibling above the tree; never
  staged/committed/pushed). This is unchanged and permanent.
* *The render process handles two secrets.* It ALWAYS signs the rendered commit (as the rke2lab bot),
  and — when `delivery.push` is armed — it pushes. So the process needs a *signing key* and a *push
  token*. Neither ever touches the output branch; both are process inputs.

Both are container-dependent, and the seam that resolves them is the *execution enclosure* — TWO
distinct-but-dependent concepts:

* `link:../../../host/host-runtime[ExecutionEnclosure]` — the runtime FACT (OPERATOR vs IN_CLUSTER).
  It is the *deterministic gate*: it decides WHICH branch of the missing logic runs (read the ndh
  keystore, or not; re-emit `sops-age`, or not). It crosses the `seed.broker.port` membrane so OSGi
  branches on it explicitly — a named gate, never inferred from an empty projection.
* `link:../../../host/host-runtime[ExecutionEnvironment]` — the RESOLVER instance that owns the
  process env, derives the enclosure from it, and projects it: the named `EnclosureGate` (a
  `seed.broker.port` seam interface, `inCluster()` + a `through(operator, inCluster)` combinator)
  that crosses the membrane, mirroring how `RunMode` crosses as its `RunGate`/`LiveGate` projection —
  the fact (`ExecutionEnclosure`) stays host-side, the `EnclosureGate` projection carries the query.
  Plus `secretsGateway()` (the `.secrets` door the `ghapp` scion reads). Both are host-seeded seam
  services, derived from the same fact so they are always coherent.

The two *process* secrets (push token, signing key) are NOT `ExecutionEnvironment` projections —
they are container-aware *scenario-side reveals*, twins of each other: `revealGithubToken()` (exists)
and `revealSigningKey()` (new), each gated on the seeded enclosure and reading OPERATOR-side
(cellar/keystore) or IN_CLUSTER-side (env, from a mounted Secret). The `secretsGateway()` projection
is a different concern — the `.secrets` DOOR — not a process secret.

[[secret-delivery]]
== The two doors for a delivered secret — manifests never carries secret material onto the branch

The output-branch-is-secret-blind rule (above) has a corollary that governs EVERY Secret the
synthesis emits, not just the render-process secrets: *manifests never carries secret MATERIAL into a
resource Flux reconciles.* A secret-blind in-cluster render holds no cellar material, so any Secret
that depended on a reveal would render EMPTY and — pushed to the branch — Flux would prune the grow's
populated one. The material reaches the cluster by exactly two doors, chosen by whether it is
IMMUTABLE or ROTATING:

* *Door 1 — the durable NODE_BOOTSTRAP lane (grow-only).* The exploder diverts the Secret OUT of the
  branch tree into `.bootstrap/rke2lab-bootstrap.yaml` (`NodeBootstrapArtifact`), sealed under
  `SERVER_MANIFESTS`, posed on the instance's devlxd key at the grow, applied by RKE2's
  server-manifests oneshot at master bootstrap — once, off-branch. It NEVER participates in an
  in-cluster reconciliation: Flux's prune is inventory-scoped and these resources carry no Flux
  inventory label (RKE2 applied them, not Flux), so Flux is blind to them in apply AND prune. Fits
  *immutable* material — a cluster CA + endpoint, an app credential: `<cluster>-kubeconfig` (CAPI),
  `githubapp`, `sops-age`, the replicator SOURCE secrets, the `manifests-render-signing` key. The
  opt-in is a per-resource marker annotation (`ManifestAnnotation.NODE_BOOTSTRAP`), stamped
  whole-unit via `new PackageMetadataProfile(domain, pkg, true)`, or per-resource for a MIXED unit
  (the `ReplicatorManifestsUnit` / `ClusterKubeconfigManifestsUnit` shape: only the credential + its
  namespace ride the lane, the rest stays on the branch).
* *Door 2 — an in-cluster controller mints it from a durable seed.* manifests emits a CR, NOT a
  Secret; a controller reconciles the Secret in-cluster, so a secret-blind re-render only re-emits
  the CR (no material) and nothing is stripped. Fits *rotating / derived* material — cert-manager (a
  `Certificate` → the controller mints + renews the TLS Secret, `ca-injector` fills a webhook
  `caBundle`), the mittwald replicator (the durable SOURCE fans out into target namespaces), and the
  Tailscale operator (provisions the funnel `*.ts.net` cert in-cluster from the tailnet). The
  `flox-controller` webhook TLS follows this door (shipped 2026-09-06): a self-signed cert-manager
  `Issuer` + leaf `Certificate` for its internal `*.svc` SAN, `ca-injector` filling the
  `MutatingWebhookConfiguration` `caBundle` — no grow-sealed secret, no reveal-gate.

The doors are complementary, not alternatives: a rotating secret typically uses BOTH — Door 1 for its
durable seed (the CA, the source), Door 2 for the in-cluster reconciliation that derives the live
Secret. What is forbidden is the third path — a reveal-populated Secret rendered straight onto the
reconciled branch, which the in-cluster render silently strips.

[[tekton-in-source]]
== The Tekton resources are rendered manifests; only a minimal PipelineRun stub is source

The Tekton objects — the `Pipeline` `render-manifests` + its `Task`(s), the PaC `Repository` CR, the
`pipelines-as-code-secret`, the funnel `Ingress` — are *ordinary K8S resources*, so they are RENDERED
by `cicd` `ManifestsUnit`s and reconciled by Flux like everything else. They split by ownership (see
<<namespaces>>): the pipeline, Repository, Tasks and signing Secret in `rke2lab-system`; the global
`pipelines-as-code-secret` and the funnel `Ingress` in `tekton-pipelines`.
There is no dedicated `tekton/<cluster>` branch, no remote pipeline resolution, no second rendered
branch — earlier drafts explored those; they were a design detour. The Tekton pipeline is not special;
it is a manifest.

The ONE thing that must be source is the *trigger*: PaC matches a `PipelineRun` in `.tekton/` on the
code/default branch (`pipelinerun_provenance` is only `source` or `default_branch`). That stub is
minimal and stable — it `pipelineRef`s the IN-CLUSTER `render-manifests` Pipeline by name, sets
`on-event: [push]` + `on-target-branch`, and reads the per-cluster values (the cluster identity) from
the `Repository` CR's `spec.params`. It is glue (which in-cluster Pipeline to run, on what event), not
the pipeline logic — the logic is the rendered, Flux-reconciled Pipeline.

=== The render self-reference + the `manifests → tekton → manifests` cycle are benign

The `render-manifests` Pipeline is a rendered manifest, and the render it runs produces (among
everything) that same Pipeline — a self-reference. It is benign, and the deep reason is that *the
trigger is source-scoped*: PaC only runs a PipelineRun whose `on-target-branch` matches the pushed
branch (the SOURCE branch, e.g. `main`). The render's effects — a push to `manifests/<cluster>` (the
OUTPUT branch) and Flux reconciling it — never match `on-target-branch`, so they never re-trigger PaC.
The feedback loop is cut at the trigger; a render, even when it touches the Pipeline, cannot cause
another render. What remains is the ordinary GitOps self-management loop (Flux-manages-Flux):

* *The grow bootstraps it.* seed-master renders EVERYTHING host-side at bootstrap (the Pipeline, the
  PaC config, the manifests) and pushes; Flux applies it; PaC + the in-cluster Pipeline exist. The
  first turn needs no Tekton.
* *It converges with a one-run lag.* A change to the Pipeline (or the PaC config) is rendered →
  pushed → Flux applies it in-cluster; the CURRENT run used the previous in-cluster Pipeline, the
  NEXT run uses the new one. No fatal chicken-and-egg — exactly how any self-managing manifest
  behaves. (Earlier drafts over-weighted this into a "the pipeline must be source" rule; it is only a
  one-run lag.)

The residual fragility is the price of self-management: a render that pushes a BROKEN Pipeline or PaC
config breaks the next trigger and needs a re-grow to recover — the grow is the escape hatch, as for
any self-managing GitOps cluster.

=== No dedicated branch, no separate repo

Because the Tekton objects are manifests, the isolation question dissolves: they live in
`manifests/<cluster>` like the rest, reconciled by Flux; the only source footprint is the tiny
`.tekton/` PipelineRun stub. A separate repo would be doubly wrong — the flox comparison holds
(`flox-nri-plugin`/`flox-controller` earned repos by being independent software with their own
language/lifecycle/domain; the render pipeline is thin glue over rke2lab's own build, intrinsically
rke2lab knowledge), and a rendered K8S resource has no reason to leave the manifests it lives among.

[[render-config]]
== Render configuration — the facet follows the grow, recorded in the branch

The render is parameterised by a *facet* — which layers publish (`gitops`, `networking`, `mesh`,
`cicd`, …), the `debug` toggles, and whether `delivery.push` is armed. The facet is the operator's
authoring concern with ONE authoring source: the *Pulumi stack* (`rke2lab:manifests` in
`Pulumi.<stack>.yaml`), read at the grow. It is not a Pulumi-runtime concept the domain sees — the
grow's host edge reads it and contributes it verbatim as the `Amendment.FACET` through the
`seed.broker.port` membrane (`FacetContributor`); the synthesis is source-agnostic, consuming only the
JSON facet, resolved into a `ManifestDomainPolicy` (which domains/layers synthesise).

The in-cluster render has no Pulumi. The rule: *the in-cluster render renders exactly what the last
grow decided.* The grow is the authority; the steady-state render is its faithful continuation. So the
facet must reach the in-cluster render WITHOUT re-authoring and WITHOUT the render touching Pulumi —
and the branch should RECORD how it was rendered, inspectable in git.

*The branch records its own render facet, as a native-YAML `manifest.yaml` document at the root.* Every
render writes a plain YAML doc (`RENDER_FACET_FILE = "manifest.yaml"`) at the ROOT of the materialised
tree (which becomes the root of `manifests/<cluster>`), carrying two top-level keys — `source:` (the
render's `sha` + `dirty` provenance) and `facet:` (the resolved facet). It is NOT a Kubernetes resource
— no `local-config` ConfigMap, no `config.kubernetes.io/local-config` annotation — but a human-legible
git artefact, written by the synthesis FLOW — `ManifestSynthesisScenario`, which holds the raw
`Amendment.FACET` and the materialisation root — NOT a CDK8s `ManifestsUnit`: at synthesis time only the
*resolved* `ManifestDomainPolicy` survives (the raw facet is not retained), so a unit could not echo the
original facet, and the exploder nests every rendered resource under `<layer>/<domain>/<package>/` with
no root path. The scenario writes it directly at the tree root — the legitimate root-write location
where the exploder already lands `.gitattributes` — through a deterministic YAML mapper (stable key
order, no doc-start marker) so an unchanged render is byte-identical. Being plain YAML at the root it is
applied by nothing and sits outside every Flux `Kustomization` path. The branch becomes self-describing:
`git show manifests/<cluster>:manifest.yaml | yq .facet` shows the facet that produced it.

*Transmission — the synthesis reads that manifest from the branch HEAD.* The render prepares its
linked worktree on `manifests/<cluster>` (`RenderedBranch.prepare`, which first fast-forwards the
LOCAL branch to origin's tip so a fresh clone — the in-cluster Tekton `--depth 1` checkout — reuses
the pushed history instead of orphaning it), then the synthesis (`ManifestSynthesisScenario`) reads
the recorded facet at HEAD THROUGH the worktree edge (`Worktree.readAtHead("manifest.yaml")`) — jgit
is already in the boat, so there is no wrapper `git show` plumbing and no `-D` facet file. The read is
robust to the delivery EMPTYING the working tree (it reads the COMMITTED blob, not the checkout). No
per-cluster value is baked into the Pipeline, which stays generic. The grow WRITES the manifest (from
its Pulumi facet, bootstrapping the branch); every in-cluster render READS it, renders (reproducing
the same manifest), and pushes — a *fixpoint*. Only the grow (or a deliberate `edit`) CHANGES the
facet. The manifest records the render's `source` provenance (`sha` + `dirty`) alongside the facet,
and the commit subject echoes it as `render <cluster> manifests @ <short-sha>[-dirty]`; an unchanged
source+facet re-renders byte-identically, so the empty-commit guard
(`JgitCheckout.setAllowEmpty(false)`) makes the push a fast-forward no-op, while a new source revision
updates the recorded `source` and lands a real commit recording how the branch moved.

[[render-verbs]]
=== The render verbs — `RenderMode` (who wins: the grow, the CLI args, or the branch HEAD)

WHETHER the seeded facet or the recorded HEAD facet is authoritative is the sower's intent, carried
as `RenderMode` (the `render-mode` amendment on `ManifestsRunbookInput`). Its default is `GROW`,
UNAMENDED — seed-master's grow keeps applying its Pulumi facet unchanged, so the contract addition is
invisible to the grow; only the `manifests-cli` delivery verbs opt into following HEAD.

[cols="1,3,2",options="header"]
|===
| Verb | Facet resolution | Guard

| `GROW`   | the SEEDED facet wins (the grow's Pulumi SSOT) | none — the grow writes or overwrites
| `INIT`   | the SEEDED facet wins (the CLI args) | the branch MUST be new (no recorded HEAD facet)
| `UPDATE` | the recorded HEAD facet wins (seeded publish/debug ignored) | the branch MUST exist
| `EDIT`   | the recorded HEAD facet OVERLAID with sparse operator overrides | the branch MUST exist
|===

The `manifests-cli` verbs map onto these: `synthesize` surveys (GROW, no branch, a temp dir — it
does not know jgit); `init`/`update`/`edit` deliver (signed commit + ff-push). The in-cluster PaC
step and the operator's steady-state re-render both run `update` — the faithful continuation of the
grow. `edit` carries a SPARSE set of overrides (dotted JSON paths into the facet, e.g.
`debug.mesh.enabled` → `true`) that overlay HEAD and are re-recorded in ONE shot, so the branch's tree
always matches its recorded facet. The seeded `delivery` (the push intent) is always kept — only
`debug` and `workloadTargets` follow HEAD. No path reaches the domain set: it is a function of the
cluster role (`ClusterRole`), so it replays from the identity and is never recorded (`f51ba1d10`).

*Drift is an explicit, git-native override.* Two branch-native ways to render against a DIFFERENT
facet without a grow: run `manifests-cli edit publish.<layer>=…` (overlays the toggle on HEAD,
re-renders, re-records — one shot, tree matches facet), or hand-edit the recorded manifest on the
branch (`manifests/<cluster>:manifest.yaml`) and let the next `update` reproduce it. Either way the
next grow RESETS the facet from the Pulumi SSOT (the grow is the authority). No Pipeline param and no
hidden knob: the branch manifest IS the render config, so changing it is the whole override surface.

*Why this shape, not the alternatives:*

* ❌ *Hardcode the facet in the `publish` CLI* (the state that shipped: `mesh` defaulted `false`
  in-cluster while the grow ran `mesh: "true"`). The in-cluster render then rendered a DIFFERENT layer
  set than the grow — a mesh-layer change (e.g. the funnel-state Job) never reached the branch, and a
  source push touching only mesh produced no diff and no push. The facet MUST come from the grow.
* ❌ *A neutral facet file in the SOURCE repo both edges read.* It splits authoring (Pulumi for the
  rest of the cluster, a file for the facet) and lets the render diverge from what was provisioned.
* ❌ *Bake the facet into the Pipeline as a param default.* It transmits, but buries the config as
  base64 in a `workloads/cicd` manifest (opaque to git introspection) and makes the Pipeline
  per-cluster. Recording it as a root manifest keeps the Pipeline generic and the branch legible.
* ✅ *A root `manifest.yaml` doc (native YAML: `source` + `facet`), read at branch HEAD.* Single
  authoring locus (the stack), the render stays Pulumi-blind, the branch is self-describing, the
  Pipeline is generic, and the flow writes it directly at the tree root (no `ManifestsUnit`, no
  `local-config` resource). The param is a deliberate drift override.

`delivery.push` rides the SAME facet: the in-cluster render pushes iff the recorded facet armed it, so
a grow that disabled delivery yields an in-cluster render that renders-but-does-not-push, coherently.

== Build — verify before publish

The pipeline runs `mvn -pl :manifests-cli -am clean verify` (not `package`): `verify` runs the tests
+ staging gates (realm-wiring-integrity, spec-coverage) so a broken manifests change can NEVER be
pushed. `verify` sits before `install` in the lifecycle → the reactor discipline holds (siblings
resolve from `target/`, nothing is installed to `~/.m2`). Speed:

* A *RWO PVC* mounted at `~/.m2` carries the dependency repo + the maven-build-cache. `clean` wipes
  the module `target/` dirs but NOT the PVC build-cache, so unchanged modules restore from cache.
* The pipeline is *serialised* (concurrency 1) — a Maven local repo + build-cache are not
  multi-writer safe, and two renders racing to push the branch is undesirable anyway.

*Runtime = the flox NRI plugin (dogfooding).* The PipelineRun pod is flox-annotated → the NRI plugin
injects a FloxEnv build-toolchain (JDK 25 / maven). No bespoke toolchain image; its lifecycle is a
FloxEnv CR. The NRI plugin is baked into the node base (a systemd service) → present before Tekton,
so no circular bootstrap. Ownership: the toolchain FloxEnv, the `Repository` CR, and the PaC secret
all belong to the `cicd` domain (where `TektonPipelinesManifestsUnit` owns the Tekton config); the
FloxEnv flavor is `FloxEnvFolder=cicd`.

== Which revision, which branch

PaC fetches the *pushed commit* (`@R`) and matches `on-target-branch` — the branch the cluster was
grown from (the source-of-truth branch: `feature/viewpoint-separation` today, `main` at term). The
`.tekton/` PipelineRun must exist on that branch. The rendered revision is thus the triggering push's
commit — determinism + consistency with what an operator would render.

⚠️ *The trigger is single-valued, and a stale value fails silently.* Exactly one source branch may
win, because every render publishes to the shared `manifests/<cluster>` branches. So the branch name
is a literal that must be maintained — and on 2026-09-28 it was found still naming
`feature/nixos-node-substrate`, weeks after that branch was retired: pushes matched nothing, *no*
`PipelineRun` was created, and there was no error to notice. The symptom surfaced elsewhere entirely
(a newly rendered `tls-san` that never reached any cluster), which is the shape to watch for. The
same fact is encoded a second time as ndh's `rke2lab` flake input URL and had rotted identically;
when this branch is superseded, both move together.

[[webhook-delivery]]
== Fleet render delivery — the ROOT is the fleet's event source (📐 2026-09-30)

A sub-plane on an ITINERANT host cannot be a webhook destination. This section records the
measurement that proved it, and what follows from it.

[IMPORTANT]
.Read the ORDER of this section — its middle is superseded by its end
====
Three things are settled and stable:

. the root is the fleet's **single event source** — a GitHub App has one webhook URL, and the root is
  the only position GitHub can be sure to reach;
. the fan-out target list is a **derivation** of `ClusterFleet`, never fleet topology stored in
  GitHub's settings;
. the returning plane must not **catch up** (<<return-to-service>>).

What is SUPERSEDED is the *mechanism* below — a reconciler that POKES each sub-plane's PaC. (3) turned
out to condemn it: the poke orders the returning plane to render, which is the destructive act, at its
most fragile moment. The successor is a fleet-SCOPED render, at the end of this section. ⚠️ Do not
build the poke; the measurement and the asymmetry that motivated it are what remain worth reading.
====

=== The measurement

`nikopol-mgmt` had no `PipelineRun` at all, while GitHub reported a successful delivery — and every
component on the cluster was healthy, which is what made it confusing:

[cols="2,3",options="header"]
|===
| Checked | Found

| the successful delivery
| it targeted `nikopol-mgmt-flux-webhook`, the **Flux** receiver. A Flux receiver reconciles a
  `GitRepository`; it never creates a `PipelineRun`. Right door for Flux, wrong door for a render.

| PaC on the sub-plane
| controller + watcher + webhook all `Running`

| its `Repository` CR
| correct — `cluster=nikopol-mgmt`, `pipelinerun_provenance: source`

| its funnel `nikopol-mgmt-pipelines-webhook`
| **up and public** — HTTP 200, TLS verified

| its PaC controller log
| **silent since start** — no event had EVER reached it
|===

The cause is structural: **a GitHub App has exactly ONE webhook URL**, and `GithubAppCli` builds it
as `PacWebhookFunnel(DEFAULT_CLUSTER, DEFAULT_TAILNET)` — the ROOT's funnel, by construction. The
four repository-level webhooks that did exist all targeted `*-flux-webhook`, one per cluster, and
were provisioned BY HAND. The sub-plane's PaC funnel was built, certificated, and wired to nothing.

=== The asymmetry between the two doors

This sets how much each door is worth defending, and it is the fact to remember:

[cols="1,2,2",options="header"]
|===
| Door | What the webhook is for | If an event is lost

| Flux receiver
| the steady-state trigger — and `spec.interval` (relaxed 1m → `10m` *because* the receiver landed;
  `FluxReceiverManifestsUnit` states this itself) is its FALLBACK
| ≤ one interval of latency. **Nothing is lost** — the interval converges.

| PaC
| the **only** trigger. No interval, no poll, nothing to catch up
| the render **never happens**, permanently.
|===

★ The asymmetry is about LOSS, not about which mechanism drives. Both doors are event-driven in
steady state; only one has a floor underneath it. That is the whole design brief for the fan-out
below — give PaC the floor Flux already has, and the event stops being load-bearing.

⚠️ And GitHub does **not** retry a failed webhook delivery — it is fire-and-forget (hence the manual
*Redeliver* button). Repeated failures also risk GitHub disabling the hook. So pointing a webhook
straight at a host that is offline part of the time silently loses renders, and that is why the
obvious wiring — one repo webhook per cluster — is REJECTED here rather than adopted.

=== The decided shape — the PARENT reconciles its sub-planes' render freshness

Not a proxy, and in the end not a relay either: a reconciler of the same shape as every other
controller here — desired state, observed state, an action that closes the gap.

[cols="1,3",options="header"]
|===
| | 

| DESIRED
| every sub-plane's branch is rendered at the source branch HEAD

| OBSERVED
| each `manifests/<cluster>` branch records the facet that produced it, including `source.sha` and
  `dirty` (<<render-config>>). Verified 2026-09-30: both branches at `9ccd89923`, `dirty: false`,
  equal to the source head — an in-sync fleet makes the loop do nothing.

| ACTION
| trigger that plane's render — a POST to its PaC funnel

| WAKE-UP
| the event the ROOT ALREADY RECEIVED. The App's one webhook lands on the root, PaC creates the
  root's own render `PipelineRun` in `rke2lab-system`, and that object CARRIES the source sha — so
  the fleet's event source is an in-cluster watch, not a network hop.

| FLOOR
| an interval. Bounds the LOSS (the wake-up bounds the latency), which is what gives PaC the
  guarantee Flux already had.
|===

★ Those last two rows are the correction of 2026-09-30, and they are the reason this section is
about the ROOT and not about polling: *the cluster the GitHub App points at forwards the events to
the fleet*. That was the decision all along; an earlier draft of this table collapsed it into "the
source head changed" and lost the word EVENT, which made the design look like a poller.

What stays rejected is only the TRANSPORT that phrase invites — a verbatim HTTP relay, which needs a
server, a second public funnel door, signature re-emission and a durable retry queue. None of that is
needed, because the event does not have to arrive at the child in the shape it arrived at the root:

[cols="1,3",options="header"]
|===
| |

| what is FORWARDED
| the *fact* that the source moved, re-derived. The child is poked; it reads git itself.

| what is NOT forwarded
| the payload, its signature, its headers. Nothing of GitHub's wire format crosses the root.
|===

And the two rows compose rather than compete — the same pairing the <<_the_asymmetry_between_the_two_doors,asymmetry table>> describes one level down:

* the WAKE-UP makes a push reach the whole fleet at once, so latency is a hop and not an interval;
* the FLOOR makes a LOST wake-up cost latency instead of a render. GitHub does not retry, and an
  itinerant host may be away exactly when the push lands — so without the floor the fan-out inherits
  the very defect that made one-webhook-per-cluster unacceptable.

⚠️ So the floor is not a fallback to drop once the watch works. It is the half of the design that
makes an itinerant sub-plane safe, and the watch is the half that makes it fast.

★ Read the figure for what does NOT cross a network: the App's event enters ONCE, and its trip to the

because it is the only plane GitHub can be sure to reach.

=== The SCOPE is the hierarchy — `ownedBy` filtered to the planes

A parent reconciles exactly the children that RENDER, which is the children that are planes:

[source,text]
----
ownedBy(bioskop-mgmt) = [bioskop-wrkld (WRKLD), nikopol-mgmt (MGMT)]  -> filter MGMT -> [nikopol-mgmt]
ownedBy(nikopol-mgmt) = [nikopol-wrkld (WRKLD)]                       -> filter MGMT -> []
----

A workload child drops out by ROLE, needing no special case: it runs no PaC and owns no branch of
intentions. The recursion terminates on its own and generalises to N tiers — each plane pokes only
the sub-planes it birthed, the same hierarchy as adoption.

=== Where it lives — `seed-incluster`, because it already IS this relation

[cols="1,3",options="header"]
|===
| Reason | 

| the responsibility is ALREADY there
| `PoolReflection` is the parent writing into its CHILD's branch what it observes of that child.
  Render freshness is the parent ensuring its child's branch is CURRENT. Same responsibility, other
  artifact — not a CI/CD concern bolted onto a CAPI controller.

| the plumbing is already there
| `reflector_git.go` drives go-git at BOTH ends (clone + commit) against these very branches, with
  the `contents:write` App token already mounted.

| the loop is already there
| a controller-runtime reconciler, with the parent/child relation as its subject.

| the fan-out needs no config
| every door is `https://<cluster>-<leaf>.<tailnet>` — `Funnel.hostname()` is `<cluster>-<leaf>` and
  `FunnelLeaf` holds exactly `pipelines-webhook` and `flux-webhook`. Crossed with the declared fleet
  (`ClusterFleet`, see `cluster-seeding-controller.adoc` § `cluster-set-derives-from-hosts`), the
  target list is a pure derivation. ★ A dividend of the fleet becoming declared.
|===

Stateless by construction: a failed POST is retried by the next pass, so the loop IS the durability
and git stays the only state. And the loop terminates because a successful render always rewrites
`manifest.yaml` — the recorded `source.sha` is IN it — so the observed state always advances and a
no-change render cannot leave a plane looking permanently behind. (The sha is redundantly in the
branch's HEAD commit message, `render <cluster> manifests @ <sha>`, the cheaper read.)

⚠️ `dirty: true` must NOT count as in sync, or a local render from an uncommitted tree would suppress
the real one.

=== What this DELETES

Worth more for what it removes than for what it adds:

* **The four hand-provisioned Flux webhooks.** Reached by derivation instead, and Flux's own
  `interval` already made them accelerators rather than requirements.
* **`RepoWebhookConfig`, `GithubRepoWebhookConfigurer`, `GithubRepoWebhookConfigurerEdge`** —
  written, never called, and now never to be. They exist for the per-cluster repo webhook this design
  rejects; keeping them would be dead code preserved for an abandoned plan.
* **`administration=write`** in the App's requested permissions (`GithubAppCli`), whose only purpose
  is managing repo webhooks.

So GitHub keeps exactly ONE webhook — the App's, on the root — and the repo carries no fleet topology
in its settings.

=== Rejected

❌ **One repository webhook per cluster.** The obvious wiring. GitHub does not retry, so a push
landing while an itinerant host is away is a render lost for good, with auto-disable as a further
risk. It also puts fleet topology into GitHub settings where nothing in this repo can see it drift —
the four hand-made hooks being the proof.

❌ **Replicating the webhook PAYLOAD** (an HTTP relay forwarding it verbatim, with its signature).
Needs a server, a second public funnel door and a durable queue — to deliver bytes the child does not
need, since it reads git itself. ⚠️ Not to be confused with forwarding the EVENT, which is the
decided design: what is rejected is the TRANSPORT, never the topology — see the WAKE-UP row above.

❌ **A catch-up poller inside each plane.** Splits detection from emission across two hosts and puts
the fleet view where the fleet is not declared. Detection needs the fleet and a git read; both are
the parent's.

📐 **The render's SCOPE becomes the fleet** — the root renders the transitive closure of `ownedBy`,
so a sub-plane needs no PaC at all. Recorded here as the successor to everything above, because the
reason this was deferred no longer holds. See <<return-to-service>>.

The cost is small and already half-paid: `prepareWorkloadPasses` goes ONE level
(`ownedChildren(self)`), so `ownedBy(nikopol-mgmt) = [nikopol-wrkld]` is never reached and its
bootstrap bundle never carved — which is exactly why that pool waits today. The closure terminates on
its own (a workload owns nothing).

[[rendered-by]]
==== The closure is `ClusterFleet.renderedBy` — landed, and NOT yet switched on

The contract is in place and tested (`ClusterFleetTest`): breadth-first from the renderer, itself
excluded, each level host-local first. Two questions that look alike are kept apart —

[cols="1,2",options="header"]
|===
| Method | Question it answers

| `ownedBy`
| whose machines do I DRIVE? ONE level, because a plane's CAPI reaches only its own children's Incus
  engine. Unchanged, and still what the CR-emitting units ask.

| `renderedBy`
| whose branch do I WRITE? The CLOSURE, because writing a branch needs no reachability — it is a git
  push.
|===

⚠️ The call site still walks ONE level, deliberately. Switching it alone would MISPLACE material:
every carved bootstrap bundle is handed to the MANAGING pass, so a grandchild's bundle would render
`<grandchild>-server-manifests` onto the ROOT's branch instead of its adopter's — a CA private key on
a cluster with no use for it. Two pieces must land together with the switch:

. passes ordered DEEPEST-FIRST, so a child's bundle exists before its adopter's pass runs;
. each bundle routed to the pass of the cluster that ADOPTS it, which is "material follows the
  adopter" restated correctly — the material's PLACEMENT follows the adopter, whoever renders it.

★ And one property is recorded as a test because asserting its opposite is the tempting mistake, made
here first: the closures OVERLAP. `nikopol-wrkld` is in the root's and in `nikopol-mgmt`'s, and
`manifests/nikopol-mgmt` already has two writers today (the root as a child pass, nikopol as its own
managing pass). That is not a collision to remove — it is the uniform view, and DETERMINISM is what
makes it safe, not exclusivity. ✅ Verified 2026-09-30 that no host-local state blocks it: the
child pass already receives the PARENT's `ImageState` (`facet.image()`), and `recordedImage` replays
the one the last grow graved at HEAD — and `ImageState` is a CONTENT identity (`imageFingerprint`,
`rke2Version`), the same on every Incus member, not a location.

The deferral said it "re-centralises rendering in the root". Under a uniform federation view that
reading is wrong: the root is not a centre, it is the **position that is always up**. The code already
asserts the invariant that makes this safe —

[quote,ManifestSynthesisScenario, the child facet]
whoever renders, the result must be IDENTICAL, which is what makes the two copies of a sub-plane's
intention agree by construction instead of by coincidence.

[[return-to-service]]
=== ★ The hazard is RETURN-TO-SERVICE, not the outage

The decisive argument, and it is not availability — it is that **a plane coming back online must not
catch up**. This is the greenfield defect one layer up: a `pet` pool may never greenfield from an
inconclusive read, because *absent* and *I cannot tell yet* look alike on return
(`pooladoption_controller.go` § `resolveRoster`). A plane that returns, reads "not rendered", and
concludes "I render" commits the same error.

⚠️ And be precise about WHY re-rendering is destructive, because the obvious answer is wrong. The
render IS deterministic — `ClusterSeal.sealWorkloadCas` is additive and idempotent, and a cluster
already in the seal *keeps* its CA, "never re-minted — a re-mint would rotate every workload cert".
The random mint happens ONCE, the first time a cluster appears in the declared fleet. What makes the
render deterministic is therefore the PERSISTED SEAL, and that seal is **host-side**
(`ClusterPkiCoordinate`: "sealed host-side once per cluster"). So a second renderer does not mint
*differently* — it mints because it has no `existing` to keep. The constraint is the seal's
LOCALITY, not the render's nature.

[cols="1,2,1",options="header"]
|===
| Shape | What the returning plane does | Verdict

| a POKE from the parent
| it is TOLD it is behind, so it renders — the heaviest, most fragile act (clone, reactor build, cold
  nix store) ordered at the worst moment
| ❌ the poke IS the hazard

| fleet-scoped render, ONE renderer
| nothing. Its branch is already current, rendered in its absence; it only APPLIES
| ✅ safe by construction — it holds no declarative authority to misuse

| fleet-scoped render, ANY renderer
| it renders too, minting FRESH CAs over the valid ones. Not latency — corruption
| ⚠️ needs both guards below
|===

So return-to-service is a pure apply, and the expensive half of the work was done by a plane that was
up all along. ⏸️ Making the render REDUNDANT (any plane may render, which is what a uniform view
naturally wants) needs TWO conditions, not one:

. the SEAL must be reachable from the rendering position — it is host-side today, so a second plane
  has nothing to keep. This is a question about where the seal STORE lives, not about the render;
. the push must be guarded by IMPACT — identical tree ⟹ no commit. The same drv comparison
  `relock` uses (link:../patterns/flake-lock-propagation.adoc[flake-lock-propagation] §
  `termination`). Without it a returning renderer REWRITES instead of converging.

★ Condition 2 is needed for CONVERGENCE between two renderers. It is tempting to also call it a
determinism detector — "a deterministic render commits nothing on a re-run" — and that was WRONG on
this branch for a reason worth knowing, now fixed one layer down. See <<render-determinism>>.

[[render-determinism]]
=== The render was deterministic; its CARRIER was not (audited + fixed 2026-09-30)

Audited because "every render rewrites every Secret" looks like a non-deterministic renderer. It was
not the renderer. The law worth holding is narrower than byte-stability:

[IMPORTANT]
====
**The render must be deterministic in WHAT THE CLUSTER APPLIES** — on the projection, not on the
bytes. The producer already complied. The DELIVERY did not, and that was a real defect.
====

What was measured, on `manifests/bioskop-mgmt` (183 commits):

[cols="2,3",options="header"]
|===
| Checked | Found

| the render logic
| ✅ clean — no clock, no randomness anywhere under `osgi/domains/manifests/`

| the workload CAs
| ✅ deterministic by PERSISTENCE — `sealWorkloadCas` is additive and a known cluster keeps its CA,
  "never re-minted — a re-mint would rotate every workload cert"

| `NodeImage.spec.buildChecksum`
| moves when `fingerprint` does not — but it is a digest of INPUTS (revision-sensitive by design, so
  stable for a given source) and the field's own doc states "no controller compares it today"

| every rendered Secret
| ⚠️ churned on EVERY render — sampled renders read `369 insertions(+), 369 deletions(-)` with nothing
  changed. **Root-caused and fixed**, below
|===

==== The root cause was ONE line, and the guard already existed

The git-sops **clean filter** already refuses to re-encrypt unchanged content: it decrypts `HEAD`,
compares, and re-emits the OLD ciphertext on a match. It never fired.

Its two sides were in two SPELLINGS of the same document — `git::sops decrypt` pipes through
`yq eval .`, so the HEAD side was yq output while the input side was whatever the producer wrote. The
whole difference was a leading `---` the renderer emits and sops's own output does not. **26 of 29**
encrypted manifests differed by nothing else.

That miss is never cheap: sops takes a fresh AES-GCM IV, a fresh ephemeral age key per recipient and a
`lastmodified` stamp on every encryption, so each re-encryption is unconditionally a new blob — ~370
lines of incompressible ciphertext per render, which git cannot delta-compress.

Fixed in ndh (`04b778d5`) by projecting BOTH sides through one canonical form — the discipline
`lock-envs` already applies with `jq -S`:

[cols="1,2",options="header"]
|===
| Step | Why

| `--no-doc`
| drops the document separator — the actual difference

| `sort_keys(..)`
| makes key order irrelevant, so no producer's emission style can decide "changed"

| project for the COMPARISON only
| what gets encrypted is still the caller's input verbatim; no formatting is rewritten behind a
  producer's back

| an input that does not project compares UNEQUAL
| staging the OLD blob for NEW content is the one outcome worse than churn — a silent loss
|===

⚠️ `yq eval .` is NOT a canonicaliser — it faithfully preserves whether the input carried a separator,
so normalising one side through it fixes nothing (verified: 0 of 29 matched). The first attempt did
exactly that and was measured wrong before being believed.

Verified three ways against the store's own layout: an identical re-render keeps the SAME blob; the
same content with reordered keys keeps the SAME blob; a changed value still produces a NEW blob.

==== Why it was worth fixing — and why the reason is NOT runtime

Stated plainly because two tempting justifications are false:

* ❌ *runtime consequence* — there is none. Flux applies the DECRYPTED content, so an identical
  plaintext yields no apiserver update, hence no watch event, hence nothing downstream restarts.
* ❌ *the render pipeline pays for the history* — it should not: the SOURCE fetch is already
  `--depth 1` (`RenderPipelineManifestsUnit`), and the RENDERED BRANCH fetch is not
  (`GitCli` — `git fetch origin +<ref>:<ref>`). History is never read to render, so shallow-fetching
  the branch is correct independently of this fix.
* ✅ what it really buys: **diff legibility** (a human can see what a render changed), a branch that
  stops growing ~28 incompressible blobs per render, and — decisively — condition 2 above
  ARRIVING FOR FREE. Blob-level idempotence is exactly what a second renderer needs in order to
  converge instead of rewrite.

⚠️ Open, found during the audit and NOT fixed: the git-sops **textconv is dead code**. The dispatcher's
`textconv` arm redirects stdin from the file and then falls through to `exit 1`, where every other arm
re-execs. So it returns nothing, with no diagnostic, for every format — and git silently falls back to
the raw blob. Consequence: `git diff` never shows plaintext for a sops file anywhere in the fleet,
which is why nobody noticed. The `diff.sops-yaml.textconv` driver IS registered in git config; the
generated `.gitattributes` also sets only `filter=`, leaving `diff:` unspecified.

★ The lesson is the one this document keeps re-learning, now in the carrier rather than the producer:
**a comparison must project BOTH sides, or it is not a comparison.** The guard was written, correct in
intent, and inert for the want of one `yq` invocation on the other side.

What a sub-plane keeps either way is worth naming: **autonomy of reconciliation** — offline it cannot
receive a new declaration (it cannot reach git either), but it keeps enforcing the last artifact its
source-controller fetched, so it does not regress. Only **autonomy of declaration** moves, and the
argument that it never belonged to a sub-plane is strong: declaring needs the source, which needs the
network.

⚠️ Until the redundant form lands, a root that is down means nothing is declared anywhere. Acceptable
only while the root is the non-itinerant position — which is a property of today's fleet, not of the
model.

=== Open

* The reconcile interval — a latency-versus-churn trade, not a correctness question: the loop
  converges at any interval. Bounded below by the shared nix/maven cache PVC each render warms.
* How the parent AUTHENTICATES its poke to the child's PaC: sign a synthetic push with the shared
  `webhook.secret` (identical across clusters — measured 2026-09-30, same sha256, and both hold the
  same App id + private key), or use PaC's `/incoming` endpoint, which exists for external triggers.

== Anti-patterns

* ❌ *Render the PipelineRun via the synthesis.* PaC only matches `.tekton/` in the repo; a rendered
  PipelineRun would never fire. ✅ Commit the PipelineRun in source `.tekton/`; render only the PaC
  App secret + `Repository` CR.
* ❌ *Mint or mirror a push credential in-cluster* (a `KubeSecretsGateway` over `.secrets`, or an
  in-cluster `ghapp`→`auth`). ✅ Consume PaC's `git_auth_secret` — it is already an App token.
* ❌ *A standing renderer Deployment* watching for changes. ✅ Event-driven build-and-run — the
  renderer is a per-run build artifact, staleness-free (built from the source it renders).
* ❌ *`mvn install`* to make siblings resolve. ✅ `-am clean verify` (reactor from `target/`).

== Troubleshooting

[cols="1,2",options="header"]
|===
| Symptom | Cause / fix
| PaC never fires on a push
| The App webhook isn't pointing at the PaC funnel, or the App lacks *webhook events (push)* /
  *checks* permissions (ours was scoped for Flux contents:read + push contents:write). Extend the
  App's permissions+events; confirm the App webhook URL = the PaC funnel host.
| `manifests publish` renders but the push is skipped
| The `git_auth_secret` wasn't wired into `publish` — in-cluster the delivery's `revealGithubToken()`
  reads PaC's mounted token (`RKE2LAB_PUSH_TOKEN`), else it reveals an empty token and skips the push
  (the signed commit still lands locally).
| `render: SOPS_AGE_KEY not set` (the render step aborts before building)
| The git-sops `spec.inject` did not deliver the age key. Either the container is not annotated
  `environment.step-render=toolchains/git-sops`, or the replicated `sops-age` Secret is absent from
  `rke2lab-system` (the mittwald replicator lane). The inject is `optional:true`, so a missing Secret
  leaves the env unset — this check turns that into a clear error instead of a decode failure.
| `render: sops-yaml git filter not registered` (the render step aborts)
| git-sops's `[hook.on-activate]` did not wire the include — the `git-sops-filter` package shipped no
  `$FLOX_ENV/sops` file, or the env did not activate on the container. Confirm the container carries
  the `environment.<c>=toolchains/git-sops` annotation and the env realised on the node.
| A `JsonParseException` on `ENC[…]` (the render reads a still-ENCRYPTED file)
| The clone landed the sops file un-smudged: the sops-yaml filter was not wired at CLONE time. The
  clone step (`step-clone`) must ALSO carry `environment.step-clone=toolchains/git-sops`, so its `git
  checkout` smudges `.secrets` (and the cellar asset) in the shared `source` workspace. This was the
  root cause the git-sops on-activate wiring fixed — installing the filter package is not enough, the
  `git config --global include.path` must register it.
| `keys.yaml appears sops-encrypted at rest` during an in-cluster render (legacy, pre-git-sops)
| The render tried to read the ndh keystore in-cluster before the git-sops chantier wired the smudge
  filter. The enclosure gate is missing/misresolved: `SopsAgeMaterialResolver` + `deliveryPlan` must
  branch on the seeded `ExecutionEnclosure` and, in IN_CLUSTER, skip the keystore and take the signing
  key from `revealSigningKey()` (the `RKE2LAB_SIGNING_KEY` env) instead.
| The reconciled branch churns with empty commits
| A structural re-render on an unchanged source is a no-op fast-forward; if it is not, check the
  render is deterministic (input hashing) — the NODE_BOOTSTRAP secrets must stay off the branch.
| The in-cluster render renders the wrong layer set (e.g. no `mesh`), or a source change to a
  non-default layer produces no push
| The render did not read the recorded facet — it fell back to the `publish` CLI's hardcoded default
  (which differs from the grow's stack facet). Confirm the root `manifest.yaml` exists on
  `manifests/<cluster>` at HEAD (`git show manifests/<cluster>:manifest.yaml \| yq .facet`) and that the
  render reads it (no drift-override param forcing a different source). A branch grown before this landed
  has no recorded manifest → one re-grow writes it. See <<render-config>>.
| The `publish` step's render narration is invisible in the PipelineRun logs (only the Felix boot
  warnings show)
| The framework's logging drains to a file (`LogFileSeed` → pax-logging), not stdout, once the OSGi
  framework boots — so the container logs show nothing after boot. The `render-publish` step `cat`s
  `.local.d/manifests-publish.log` on exit (a `trap`, so failures surface too), lifting the render
  narration into the container logs.
