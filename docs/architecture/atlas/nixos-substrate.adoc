= Atlas L1 — NixOS node substrate view (the node OS, image-side)
:toc: left
:toclevels: 3

_Level-1 (per-subsystem) view of the link:../integration-atlas.adoc[integration atlas] (L0)._
_L0 shows how this subsystem integrates with the others and the value that emerges; this file is the detail._

The node substrate, image-side — the process that turns "what a node is" from an imperative
materialisation apparatus into a declarative NixOS closure. The vision it renders lives in
link:../nixos-substrate/substrate-model.adoc[the substrate model]; this view carries the
codebase↔vision delta as before/after figures.

== The thesis — the closure is the config; the materialisation apparatus is deleted

Each figure carries its own before/after in one frame (atlas convention). The red `BEFORE` block is
the imperative materialisation apparatus the transition *deletes*; the green `AFTER` block is the
declarative substrate that replaces it. The simplification of rke2lab is the red block collapsing
into the green one: no synthesis-of-a-tree, no `/srv/host` staging, no stow-then-activate — the image
IS the tree, and the small per-node + bootstrap residue reaches the node over *devlxd*.

=== Diagram A — System context: BEFORE vs AFTER

Reads: the BEFORE choreographs three engines per node (Pulumi+OSGi materialisation → distrobuilder
image+cloud-init → an `/srv/host` tree stowed then rke2); the AFTER builds one image, references it,
and splits the rest by realm (Pulumi-thin for master, CAPN greenfield for the fleet, Flux + a
controller post-join). The dashed edge `the layer underneath is removed` is the whole point — the
survivors (Pulumi graph, CAPN, Flux) stay; the layer under them goes.

=== Diagram B — Container: BEFORE vs AFTER

Reads: the BEFORE is a long materialisation pipe (OSGi synthesis → 28-script materializer into
`/srv/host` → jsync promotion into `host.live.d` + checksum → on-node stow then rke2); the AFTER is
`the closure IS the config` — the flake's node-base/control/worker modules build via the
`lxc-container` profile (`config.system.build.{squashfs,metadata}`) into the image store, the node applies its baked config at boot, and the two
residues arrive on their own channels: the *per-node seed* (hostname·role·token·dataset) and the
*node-side bootstrap set* (CNI + Flux) both over devlxd, then Flux Kustomizations + a controller
post-join. The dashed edge `no tree, no stow, no promotion` names the erased apparatus.

=== Diagram D — Flox env delivery: BEFORE vs AFTER

Reads: the BEFORE bakes each flox env (subtree + activation + closure) into the node-base
`/nix/store` via `nixos/flox-runtime.nix` and folds `environment.d` into the image digest — so a
package bump changes the image and COLD-STARTS the control node. The AFTER keeps only the *shim*
baked (foundation) + the *flox controller*, and makes each env a first-class `FloxEnv` CR: the
controller (node-agent) realises the closures onto the host `/nix/store` and the NRI plugin overlays
it, resolving the pod annotation as a FloxEnv reference — no PVC. The image is unchanged on a bump, so
no cold-start. The dashed edge `envs leave the image` names the shift.

=== What the transition deletes

The simplification, stated as removals — each is a red box above with no successor:

[cols="2,1",options="header"]
|===
| Deleted apparatus | Replaced by

| `distrobuilder` Debian image + its post-unpack/post-files actions
| `lxc-container` image build

| `cloud-init` NoCloud seed (user-data + network-config)
| baked NixOS config + per-node devlxd seed

| the 28 host systemd scripts + the 4 synthesis phases
| `systemd.services.*` + the `nixos/` modules

| `rke2lab-systemd-link` + `rke2lab-activate` (materialise → stow → activate)
| the closure *is* the config; nothing to stow

| `/srv/host` staging tree + `host.live.d` promotion (jsync)
| no materialised tree — the image is the tree; the node-side residue rides devlxd

| checksum → `replaceOnChanges` glue (nocloud drift → instance replace)
| image digest *is* the identity; a new image is a new instance by construction

| the runtime `nix flake build` of the flox shim on the host (DaemonSet trampoline)
| the shim baked into the base image at build time

| flox *envs* baked into the node-base `/nix/store` (`environment.d` folded into the image digest → cold-start on every package bump)
| envs are first-class `FloxEnv` CRs reconciled by our flox controller onto the host store (no PVC); the image is unchanged on a bump
|===

What *survives*, unchanged in role: the Pulumi Incus graph for the management node (thin, host-side),
and CAPN + CAPRKE2 + Flux for the fleet. The substrate does not rebuild these — it *removes the layer
underneath them*.

== Verdict — does it hold?

Shipped, on the codebase today (the green blocks are not all vision):

* the `nixos/` per-concern modules build the node-base image via nix (`CultivatingNixosImageBuilder`);
  it boots in Incus with rke2-server + containerd up (iteration 1, proven).
* per-node identity + cluster PKI arrive over devlxd (`nixos/identity.nix`, `nixos/sops.nix`) — the
  `/srv/host` mount and cloud-init are gone from `InstanceGrow`.
* the *node-side bootstrap seam* of Diagram B/C is now real in code: the exploder carves the
  `NODE_BOOTSTRAP` lane, the synthesis scion files it (SEALED) through the cellar, the host GROW poses
  `user.rke2lab.server-manifests`, and `nixos/bootstrap-manifests.nix` writes it into
  `server/manifests` before rke2-server (`cni="cilium"`). See
  link:../nixos-substrate/node-bootstrap-delivery.adoc[node-bootstrap delivery].

*The seam has ONE poser, and that is now the live gap.* Its last two steps name `InstanceGrow` and a
devlxd key, so they only cover a node the HOST grows. A control node CAPRKE2 provisions gets no bundle
at all — proven on `bioskop-wrkld`'s first node (2026-09-21): cilium fell back to RKE2's bundled chart,
dialled the apiserver at the in-cluster ClusterIP before any CNI existed, and the node stayed
`NotReady: cni plugin not initialized`, so nothing ran there — Flux included. The second poser
(`RKE2ControlPlane.spec.files[].contentFrom.secret`) is designed, verified against the live CRD, and
NOT coded; and it depends on the manager's render making a
link:../cluster-api/manifests-rendered-branches.adoc#per-target-pass[pass per workload target], since
a cluster cannot carve its own first bundle. See
link:../nixos-substrate/node-bootstrap-delivery.adoc#second-poser[the second poser].

Still vision (the red block has not fully collapsed): CAPN growing peers/workers from the published
images (the management cluster is not yet wired to grow the fleet), and the Go controller for
post-join host mutation (still the DaemonSet stage). The e2e LIVE proof — grow a real node to Ready —
is the open gate. Flox-*env* delivery is now runtime `FloxEnv` CRs realised onto the host store by
the flox controller (Diagram D's AFTER), not baked into the image; its live proof rides that same
grow-a-node-to-Ready gate — see link:../patterns/flox-store-resolved-runtime-and-builder.adoc[Flox
Store-Resolved Runtime] §Runtime env delivery.

Consequence for this atlas: activating a node's target configuration no longer transfers anything, because its closure is already mounted and already valid in the guest's Nix DB — the remote `nixos-rebuild --target-host` in the runbook is now a rescue path, not the normal one. Carries the ownership boundary (instance owns data, `ndh` owns layout) and the two invariants that bind a layer to a booted node: appending a layer is safe, replacing one is not, and the ESP and the layers must move together.
