= Conditional Manifest Unit Inclusion
:toc: left
:toclevels: 3
:icons: font

== Overview

The manifest synthesis system supports **conditional inclusion of manifest units** and **bootstrap context access** within domains. This enables:

1. **Policy-driven conditional inclusion** - Optional manifest units based on policy flags (e.g., an optional unit within GitOps)
2. **Bootstrap identity access** - Infrastructure configuration (e.g., Incus remote name) passed through BootstrapIdentity
3. **Graceful ephemeral synthesis** - Units can skip when context is unavailable (smoke tests, unit tests)

**Key principle**: A single domain can contain both mandatory and optional manifest units. Optional units are controlled by policy flags, and all units have access to bootstrap context for configuration.

[CAUTION]
====
**Status (2026-06-03): this mechanism is dormant.**

The `ManifestsDomainRegistrar.domain(ManifestDomainPolicy)` hook exists as a default interface
method, but:

* No registrar in the `domain/` package currently overrides it — they all use the plain `domain()`
  form with a fixed unit list (see `GitopsDomainRegistrar`).
* So while the registry itself is live (it assembles the domains and `resolve()` orders them — see
  link:manifests-architecture.adoc#ordering-and-coherence[Manifests Architecture → visit order and coherence]),
  the *policy-driven conditional* hook that would vary a domain's unit list is not yet exercised.

The example used throughout this document is *illustrative only* — it uses a generic *optional
unit* placeholder. The component that once filled this role was evaluated and removed from the
project, so a neutral placeholder replaces it. Read this as the intended design for conditional
inclusion, to be restored alongside the domain registry; substitute a real optional unit when you
implement the mechanism.
====

== Implementation Details

=== ManifestsDomainRegistrar Interface

The link:../../../osgi/domains/manifests/manifests-core/src/main/java/io/seedmatic/rke2lab/manifests/ManifestsDomainRegistrar.java[ManifestsDomainRegistrar] interface provides two methods — the shape is the teaching point:

[source,java]
----
public interface ManifestsDomainRegistrar {
  // Fixed unit list — most registrars implement only this
  ManifestsDomain domain();

  // Policy-aware — override for conditional inclusion; default delegates
  default ManifestsDomain domain(ManifestDomainPolicy policy) {
    return domain();
  }
}
----

A registrar that needs no conditional logic implements only the no-arg `domain()`; the default `domain(policy)` delegates to it. Each registrar is an SCR `@Component(service = ManifestsDomainRegistrar.class)`, collected by `DefaultManifestSynthesisService` (a `@Reference(MULTIPLE)`) which calls `domain(policy)` on each — see the interface JavaDoc for the component diagram.

=== Registrar Implementation Pattern

The choice is between a **separate domain per optional feature** (❌ — domain
proliferation, cross-domain dependency edges for tightly-coupled units) and
**conditional inclusion of a unit within its owning domain** (✅). The Component
and Sequence figures above show the ✅ shape: the registrar receives the run
`policy` and folds the optional unit into the domain's unit list only when the
flag is set. The one line that IS the pattern:

[source,java]
----
if (policy.isEnabled(/* an optional-unit flag */)) {
  units.add(/* the optional unit */);   // else the domain omits it
}
----

**Real implementation**: link:../../../osgi/domains/manifests/manifests-core/src/main/java/io/seedmatic/rke2lab/manifests/domain/GitopsDomainRegistrar.java[GitopsDomainRegistrar] contributes a fixed unit list (Flux operator/instance/root, SOPS-age and GitHub-app secrets) via the plain `domain()` — it does *not* override `domain(policy)` today, so the conditional branch above is the intended design, not current code. See link:../../../osgi/domains/manifests/manifests-core/src/main/java/io/seedmatic/rke2lab/manifests/units/gitops/package-info.java[units/gitops/package-info.java] for the domain overview.

**Why this is better**:

* **Single source of truth**: One domain owns the feature, not scattered across multiple domains
* **Logical grouping**: the optional unit is part of GitOps, not a separate concern
* **No dependency complexity**: No need to declare cross-domain dependencies for tightly related features
* **Policy granularity**: Domain-level enable/disable + unit-level enable/disable

=== Policy Configuration

The policy is defined in two layers:

**1. ManifestDomainCatalog** (single source of truth for identifiers): the real
link:../../../osgi/domains/manifests/manifests-contract/src/main/java/io/seedmatic/rke2lab/manifests/contract/ManifestDomainCatalog.java[ManifestDomainCatalog]
exposes accessors that return *domain* IDs (`gitops()`, `mesh()`, `clusterApi()`, …),
each backed by a `public static final String` constant. A per-*unit* flag such as the
one below is a **placeholder** — there is no such accessor today:

[source,java]
----
// PLACEHOLDER — not a real catalog method; a per-unit flag would look like this
public String optionalUnit() {
  return "optional-unit";
}
----

**2. ClusterRole** (the domain set is a FUNCTION of the cluster's identity, not a toggle — see
link:../../../osgi/domains/manifests/manifests-contract/src/main/java/io/seedmatic/rke2lab/manifests/contract/ClusterRole.java[ClusterRole]):

[source,java]
----
// ClusterRole — parsed from the `<host>-<role>` clusterName
public ManifestDomainPolicy domainPolicy(final ManifestDomainCatalog catalog) {
  return ManifestDomainPolicy.builder()
      .domainCatalog(catalog)
      .enableOnly(enabledDomainIds(catalog))   // membership is structural to the role
      .build();
}
----

`ManifestSynthesisScenario` then derives the policy with `ClusterRole.of(clusterName).domainPolicy(CATALOG)`.

IMPORTANT: there is no `PublishFacet` and no `rke2lab:manifests:publish:` config block — both were
removed in `f51ba1d10` ("domain set follows the cluster role, not a publish facet"). The reasoning is
worth keeping: membership is *structural* (a management cluster runs Cluster API, a workload cluster
does not), so it replays deterministically from the identity on every render — grow or in-cluster —
with nothing recorded and nothing to drift. Making it configurable would give a *derived* fact a
second owner, which is exactly what the single-source-of-truth rule forbids.

NOTE: a *pause* is not the same thing as structure, and the tree currently collapses the two: `mesh`
(Headscale/Headplane) is hibernated by simply not being listed in `enabledDomainIds`, with the
rationale written as a comment there. Deliberate, and re-adding the one term wakes the domain — and
since the flox envs now follow the domain policy (`FloxEnvManifestsUnit`), its envs wake with it.

**3. Unit-level filters** stay inside their domain: the optional unit is a UNIT *within* gitops, not a
domain flag, so its inclusion is decided by the gitops registrar's `domain(policy)` hook (below).
There never was a `publish.optional-unit` key, and there is no domain-level key at all any more.

=== Accessing Bootstrap Identity for Infrastructure Configuration

A manifest unit reads infrastructure identity off the synthesis context — the
per-run coordinate sown across the host↔OSGi membrane — not off the unit itself.
Units extend `AbstractManifestsUnit` and override `doSynthesize(Construct, ManifestsUnitContext)`;
they reach the identity through `ManifestSynthesisContext.current()`. The teaching
point is the accessor path and the ephemeral guard:

[source,java]
----
final String clusterName =
    ManifestSynthesisContext.current().bootstrapIdentity().clusterName();

// Skip in ephemeral/test mode: no real cluster (or no material supplied)
if (BootstrapIdentity.UNKNOWN.equals(clusterName)) {
  return;
}
----

link:../../../osgi/domains/manifests/manifests-core/src/main/java/io/seedmatic/rke2lab/manifests/units/clusterapi/IncusIdentitySecretManifestsUnit.java[IncusIdentitySecretManifestsUnit]
renders the `<cluster>-incus-identity` Secret in `capn-system` from the
`IncusIdentityMaterial` seed-master assembled host-side and handed across on the
request — the unit never reads a host file or classpath resource itself. It guards
on `BootstrapIdentity.UNKNOWN` **and** on the material being absent. See
link:../../../osgi/domains/manifests/manifests-core/src/main/java/io/seedmatic/rke2lab/manifests/units/clusterapi/package-info.java[units/clusterapi/package-info.java] for the domain overview.

**Why this pattern**:

* **Separation of concerns**: Infrastructure identity arrives on the synthesis context, not hardcoded in the unit
* **Testable**: Units can run in ephemeral mode (smoke tests) by checking for `UNKNOWN`
* **Frontier-clean**: the host assembles the material; the unit only renders — no host I/O in the OSGi world
* **Fail-fast**: A missing coordinate is caught at synthesis time, not runtime

**BootstrapIdentity fields** (see link:../../../osgi/domains/manifests/manifests-contract/src/main/java/io/seedmatic/rke2lab/manifests/contract/profiles/BootstrapIdentity.java[BootstrapIdentity]):

* `clusterName` - Logical cluster name ("bioskop")
* `incusRemoteName` - Incus remote name from config ("bioskop-nixos")
* `clusterToken`, `clusterDomain`, `nodeName`, `nodeId`, `nodeKind` - See BootstrapIdentity

== Usage Patterns

=== Adding Conditional Units to Existing Domains

To add a new optional feature to an existing domain:

1. **Add policy flag** to `ManifestDomainCatalog` and `ManifestDomainPolicy`
2. **Override `domain(policy)`** in the domain registrar
3. **Check policy flag** before adding the unit to the list
4. **Map the facet key** in the scion's policy derivation (`ManifestSynthesisScenario`)

Example: making the mesh **headplane** unit optional. The
link:../../../osgi/domains/manifests/manifests-core/src/main/java/io/seedmatic/rke2lab/manifests/domain/MeshDomainRegistrar.java[MeshDomainRegistrar]
today contributes all its mesh units (namespace, Headscale, Headplane, Tailscale, the funnel
cert-restore / state-persistence and tailnet-purge units) unconditionally via the plain
`domain()`. To stage the headplane, it would override
`domain(policy)` and gate only that unit — the same one-line branch as the ✅ pattern
above, applied to `HeadplaneManifestsUnit`:

[source,java]
----
if (policy.isEnabled(/* a headplane flag */)) {
  units.add(new HeadplaneManifestsUnit());   // else mesh ships without it
}
----

=== When to Use Conditional Inclusion vs Separate Domains

**Use conditional inclusion when**:

* Feature is logically part of a larger concern (the optional unit ⊂ GitOps)
* Feature shares dependencies with sibling units
* Feature is optional/experimental/staged rollout
* You want fine-grained control without domain-level dependencies

**Use separate domains when**:

* Feature is independently valuable (storage, networking, mesh are distinct)
* Feature has complex cross-domain dependencies
* Feature represents a distinct architectural layer
* Domain-level enable/disable is the right granularity

== Policy Evaluation Flow

=== Two-Phase Filtering

The system applies policy in two phases:

**Phase 1: Unit-level conditional inclusion** (this document's focus)

* Happens during `domain(policy)` call
* Registrar queries policy flags
* Manifest units conditionally added to domain

**Phase 2: Domain-level filtering**

* Happens in `applyManifestDomainPolicy()`
* Entire domains enabled/disabled based on policy
* Domain dependency resolution (if A depends on B, enable B)

[mermaid]
----

    BUILD[buildDomainRegistry policy]

    subgraph "Phase 1: Unit Filtering"
        REG1[Register Domain 1]
        REG2[Register Domain 2]
        REGN[Register Domain N]
        UNIT1{Policy Check}
        UNIT2{Policy Check}
    end

    subgraph "Phase 2: Domain Filtering"
        FILTER[applyManifestDomainPolicy]
        DEPS[Resolve Dependencies]
        ENABLED{Domain Enabled?}
    end

    SYNTH[Synthesize Units to YAML]

    START --> BUILD

    BUILD --> REG2
    BUILD --> REGN

    REG1 --> UNIT1
    UNIT1 -->|enabled| FILTER
    UNIT1 -->|disabled| FILTER

    REG2 --> UNIT2
    UNIT2 --> FILTER

    FILTER --> DEPS
    DEPS --> ENABLED

The two examples below use `cluster-api`, the one genuinely role-exclusive domain (CAPI reconciles
clusters *from* the management cluster), because the domain-level filter now answers to the cluster's
ROLE rather than to a config key — so what flips between them is the clusterName, not a toggle.

**Example**: clusterName `bioskop-mgmt` — `cluster-api` is in the role's set

* **Phase 1**: ClusterApiDomainRegistrar creates the domain with its units
* **Phase 2**: cluster-api passes the domain-level filter, units synthesized

**Example**: clusterName `bioskop-wrkld` — `cluster-api` is absent from the role's set

* **Phase 1**: the registrar creates the domain identically — registration does NOT consult the policy
* **Phase 2**: cluster-api is filtered out entirely, nothing synthesized

That asymmetry between the phases is the point: a registrar always registers, and only the
domain-level filter decides. A unit-level filter is a separate mechanism — the illustrative optional
unit is a UNIT within gitops, included or not by the gitops registrar's `domain(policy)` hook, and it
never had a domain-level key of its own.

== Troubleshooting

=== Optional Unit Always Included

**Symptom**: Manifest unit appears in synthesized YAML even when policy flag is disabled.

**Causes**:

1. Registrar not overriding `domain(ManifestDomainPolicy)`
2. Registrar checking wrong policy flag name
3. Policy not passed through from Pulumi config

**Fix**:

[source,bash]
----
# There is no config key for the domain set — it follows the cluster ROLE, so the
# question "is this domain enabled?" is answered by the clusterName, not by pulumi:
pulumi config get rke2lab:cluster.name    # <host>-<role> — the role IS the answer

# The optional unit has no domain-level flag either: it is filtered within the gitops
# registrar's domain(policy) hook.

# Check synthesis logs
grep "Applying manifest-domain policy" /tmp/rke2lab.log

# Verify registrar override
grep -A 10 "domain(ManifestDomainPolicy" \
  osgi/domains/manifests/manifests-core/src/main/java/io/seedmatic/rke2lab/manifests/domain/GitopsDomainRegistrar.java
----

=== Optional Unit Never Included

**Symptom**: Manifest unit missing from synthesized YAML when policy flag is enabled.

**Causes**:

1. Parent domain disabled at domain level
2. Policy flag name mismatch between catalog and registrar
3. Unit constructor throws exception

**Fix**:

[source,bash]
----
# Check domain-level policy — it follows the cluster ROLE, there is no config key.
# The role is the second term of the clusterName, and ClusterRole.enabledDomainIds
# lists what that role publishes.
pulumi config get rke2lab:cluster.name    # <host>-<role>

# Check the flag name matches the catalog's single source of truth
# (real accessors return domain IDs — gitops(), mesh(), …; a per-unit flag is a placeholder)
grep 'public String' \
  osgi/domains/manifests/manifests-contract/src/main/java/io/seedmatic/rke2lab/manifests/contract/ManifestDomainCatalog.java

# Check for synthesis exceptions (substitute the real optional unit's class name)
grep "ManifestsUnit" /tmp/maven.log
----

=== Policy Changes Not Reflected

**Symptom**: Changing Pulumi config doesn't affect synthesized manifests.

**Causes**:

1. Stale Pulumi state
2. Policy cached from previous run
3. Wrong stack active

**Fix**:

[source,bash]
----
# Verify active stack
pulumi stack ls

# Force policy refresh
pulumi config refresh

# Re-run with clean state
pulumi up --refresh
----

=== Remote 'X' Not Found in Incus Config

**Symptom**: Error during synthesis: `Remote 'bioskop' not found in /Users/nxmatic/.config/incus/config.yml`

**Causes**:

1. Manifest unit using `clusterName` instead of `incusRemoteName` to lookup Incus remote
2. Incus remote name doesn't match cluster name (e.g., cluster "bioskop" → remote "bioskop-nixos")
3. `BootstrapIdentity.incusRemoteName` not properly passed through from config

**Fix**:

[source,bash]
----
# Check Pulumi config for remote name
pulumi config get rke2lab:incus.defaultRemote

# Check what's in Incus config
grep -A 3 "^remotes:" ~/.config/incus/config.yml

# Verify BootstrapConfig loads the remote name
grep "incusDefaultRemote" \
  exec/seed-master/src/main/java/io/seedmatic/rke2lab/controlplane/config/BootstrapConfig.java
----

**In manifest units**, resolve identity off the synthesis context and use `incusRemoteName()` not `clusterName()`:

[source,java]
----
final BootstrapIdentity identity = ManifestSynthesisContext.current().bootstrapIdentity();

// ❌ Wrong - assumes cluster name = remote name
final String remoteName = identity.clusterName();

// ✅ Correct - uses configured remote name
final String remoteName = identity.incusRemoteName();
----
