= Management / Workload Topology
:toc: left
:toclevels: 3

This is the anchor document for rke2lab's cluster topology. It defines the separation
between the *management cluster* (which runs Cluster API) and the *workload clusters*
(which run the actual applications), the naming convention that binds clusters to the
bare-metal hosts they live on, and the reasoning that led here.

It supersedes the earlier *self-managed / dual-role* model (a single `bioskop` cluster that
was both the management plane and the workload, scaled in place by in-cluster CAPI). Every
Stage A/B contract and in-cluster-ownership note that still encodes that older model is being
reframed to point at this document.

== Overview

We run *three* Kubernetes clusters across *two* bare-metal hosts:

* one *management cluster* — nix-seeded, single node, *reconstructible from git* (see
  <<function-of-git>>), that runs CAPI + CAPN (the Incus infrastructure provider) + CAPRKE2 (the RKE2
  control-plane and bootstrap providers). Its job is to *reconcile* the workload clusters — and only
  for machine-lifecycle changes; day-to-day app/config is GitOps-pull inside each workload (see
  <<operating-model>>).
* two *workload clusters* — one per bare-metal host — each a full HA control plane
  (master + peer1 + peer2 = three etcd members) plus workers, running the application stack.

The management cluster **greenfield-creates** the workload clusters. It never scales itself,
never adopts an externally-bootstrapped node, and holds no application workloads. This is the
textbook Cluster API management/workload split, and it is what makes the whole design tractable
(see <<why-separation>>).

== Naming convention

A cluster is named `<bare-metal-host>-<role>`, with `role ∈ { mgmt, wrkld }`:

[cols="1,2,3",options="header"]
|===
|Cluster |Role |Runs on

|`bioskop-mgmt` / `nikopol-mgmt`
|Management (CAPI/CAPN/CAPRKE2)
|The bare-metal host it is currently placed on — it *travels*
|`bioskop-wrkld`
|Workload
|The `bioskop` bare-metal host
|`nikopol-wrkld`
|Workload
|The `nikopol` bare-metal host
|===

The management cluster carries the name of *its current host* because it can move between
bare-metals (the cellar travels with it — see the cellar-secrets atlas). A node's full identity
is `<cluster>-<node>`, e.g. `nikopol-mgmt-master`, `bioskop-wrkld-peer1`.

* *Target placement*: `bioskop-mgmt` · `bioskop-wrkld` · `nikopol-wrkld` (management on `bioskop`).
* *Current placement*: `nikopol-mgmt` · `bioskop-wrkld` · `nikopol-wrkld` (management on `nikopol`,
  which is what `Pulumi.dev.yaml` currently seeds — `cluster=nikopol`, `node=master`).

NOTE: `nikopol` was formerly `alcide`; `alcide` is retired (`ClusterNetworkBlueprint` keeps the
cluster id, renamed the name). Use `nikopol`.

== Logical topology (C4 L2 — containers)

CAPI/CAPN/CAPRKE2 live **only** in the management cluster. The workloads do not run them.

Each workload is created from scratch: CAPRKE2's `RKE2ControlPlane` initialises its own first
replica (`cluster-init`) and scales up the peers that join it; CAPN provisions the Incus
instances from the shared `node-base` image. No node of a workload is ever the management
cluster's node, so there is no adoption and no "mixed management mode".

== Physical placement (C4 L3 — deployment)

The two bare-metal hosts each run a NixOS hypervisor (`<host>-nixos`) that hosts Incus; the
clusters are Incus instances on those hypervisors. The management cluster co-locates with a
workload on whichever host it is placed, and reaches the *other* host over the mesh.

The <<mesh,virtual network (the mesh)>> is the *transport* that lets the management cluster reach a
workload on a different bare-metal. The relevant plane here is the *node* plane — `Tailscale`'s
`mammoth-skate` tailnet, on which every node is a permanent member — so this hop works at bootstrap and
in steady state alike, independent of whether any Headscale workload plane exists yet. Without it, a
management cluster on one host cannot reach a workload's API or the Incus host on another.

[[incus-tenancy]]
== Incus tenancy — a project per cluster, engines not nested (C4 L3 — deployment)

Each host runs *one* Incus engine, and the clusters that share it are isolated by an
*Incus project per cluster* — not by nested Incus engines. The project is a logical
tenant boundary on a shared engine: it cloisons what must be isolated (instances,
storage volumes / quotas) while *mutualising* the two invariants this document already
relies on — the homogeneous `node-base` image and the shared node fabric.

The C4 deployment diagram nests the deployment nodes — `bioskop` bare-metal → the
`bioskop-nixos` hypervisor's single Incus engine → the projects — and places the instances
as «container» elements inside the per-cluster projects. The shared `default` project holds
the `node-base` image («artifact») and the fabric («network»); each per-cluster project
(`bioskop-mgmt`, `bioskop-wrkld`) reaches *back* to `default` — `resolves` the image and
`attaches` the fabric — while its own «container» instances and «volume» storage stay
project-local.

The feature split is what makes the boundary a *tenant* boundary and not a *silo*:

[cols="2,1,3",options="header"]
|===
|Incus project feature |Setting |Effect

|`features.images`
|`false`
|The project has no image store of its own → it resolves images from `default` → the *one*
`node-base` image is published once and shared read-only by every cluster (the homogeneous-image
invariant, not duplicated per tenant).
|`features.networks`
|`false`
|The project has no network of its own → instances attach `default`'s fabric → nodes of
*different* clusters stay L2/L3 peers on one bridge, so cilium BGP / clustermesh / per-node ASN
work across clusters.
|instances
|(native)
|Each cluster sees only its own instances — the isolation the operator wants.
|`features.storage.volumes`
|`true`
|Volumes and quotas are project-local → per-cluster resource isolation.
|===

CAPN consumes this directly: a workload's `LXCCluster` remote is scoped to *its* project on the
target host's engine (see the CAPN materialization consequence below), so CAPN provisions into
`bioskop-wrkld` without ever seeing the management project's instances.

.Anti-pattern — do NOT nest the Incus engines
[WARNING]
====
It is tempting to have the management node run its *own* Incus and grow the workload *inside*
itself (nested engines), since the node is itself NixOS. Do **not**. Nesting makes the management
node a *single point of failure for the whole workload*: stopping it, rebooting it, rebuilding its
image, or an OOM on its root cgroup takes every workload node with it — the exact opposite of the
<<operating-model,on-demand management>> invariant (workloads must *survive* management churn, the
management cluster is stopped when idle). Nesting also buries the workers behind the management
node's internal bridge, breaking the shared-fabric peering (BGP/clustermesh) this topology depends
on; and because the outer NixOS runs under vz on Apple Silicon (no nested virtualization), nested
instances could only ever be containers — a permanent ceiling. The correct isolation primitive is
the *Incus project* above: a logical tenant on a shared engine, with independent lifecycles.
====

[[mesh]]
== The mesh — a virtual network (detail deferred)

The clusters reach each other over a *virtual network* that abstracts the physical one — the
node/cluster-reachability counterpart of what kube-vip does for the control-plane endpoint (kube-vip
stabilises the apiserver address; the mesh stabilises reachability across bare-metals, independent of
the physical network).

It is *not* one mesh but *two planes that stack*, at two different levels — this is the key
distinction, and it is not a migration where one replaces the other:

* *Node plane — `Tailscale`, tailnet `mammoth-skate`.* Every *node* is a member: the bare-metal NixOS
  hosts, the management control node, every workload control node. This plane is *always* present,
  independent of any running cluster, so it is the *bootstrap-time* transport (the management cluster's
  first cross-host reconciliation rides it) and the path for external access. It is the machine-level
  address plane.
* *Workload plane — `Headscale` (self-hosted control-server + DERP).* The *workloads inside* the
  clusters (pods / services) are members of a *distinct* tailnet defined by Headscale. Headscale is
  itself deployed *as a workload-cluster service*, so this plane exists only *after* a workload cluster
  is up — today, with no workload running yet, there is no Headscale at all. It is hosted on the
  *always-live* `bioskop-wrkld` (never on the on-demand management cluster).

The two coexist by design, each at its own level: nodes stay on `mammoth-skate` permanently; the
Headscale tailnet is layered on top for workload-to-workload reachability once the workloads exist.

This also dissolves the obvious chicken-and-egg: the management cluster's first cross-host
reconciliation is node-level, so it rides the `mammoth-skate` node plane (or the LAN) and cannot need
Headscale (nothing hosts it yet). And because Headscale lives on a *workload*, it is never on the
on-demand management cluster — stopping that cluster cannot take the workload plane with it.

.Deferred — do not over-specify here
[NOTE]
====
The two-plane split (nodes on `mammoth-skate` / workloads on Headscale) and Headscale's host (the
always-live `bioskop-wrkld`) are decided. What remains a separate concern is the internal/LAN vs
external split (self-hosted Headscale for internal, Tailscale for outside) and whether a given
bare-metal is LAN-local or remote. Its first concrete instance is the corp bare-metal Mac (`vzhost.nikopol`)
that hosts `nikopol-nixos`: JAMF-managed, it cannot be a `mammoth-skate` member. Instead it lives on
`nikopol-nixos`'s *baremetal instance segment* (`172.16.6.0/24`), which `nikopol-nixos` advertises into
the tailnet with a split-DNS `.nikopol` zone — so peers resolve and reach `vzhost.nikopol` (and the segment's
instances) by name, over the advertised route, without the Mac being a tailnet member. That transport is
specified in `nix-darwin-home`'s `docs/network-topology-c4.adoc`. This does not touch the *property* this
document relies on: every *node* (the bare-metal hypervisors and every cluster node) is a `mammoth-skate`
member, so the management cluster reaches each workload node regardless of host — the off-mesh case is
the bare-metal Mac, never a node.
====

[[why-separation]]
== Why separation, not self-management

The earlier model tried to bootstrap `bioskop` with nix, then install CAPI *inside it* and have
`RKE2ControlPlane` add control-plane peers to that same cluster. That does not work, and the
reason is structural, verified against CAPRKE2 `v0.24.4`:

* `RKE2ControlPlane` **owns** the whole control plane. Its `initializeControlPlane` counts only
  the machines it owns; a nix-seeded master is invisible to it, so it would `cluster-init` a
  *second*, separate cluster with a fresh CA.
* There is no adopt/join-existing field — `reconcileNormal` has no `adoptMachines` (unlike
  KubeadmControlPlane) and outright *refuses* to operate in "mixed management mode" if any
  control-plane machine is not owned by it. `RegistrationMethod` only selects which address the
  replicas use; it is not a way to join a foreign cluster.
* The standalone `RKE2Config` bootstrap carries `agentConfig` only (no `serverConfig`), so a bare
  `Machine` bootstraps an *agent*, never an etcd-member server.

.Anti-pattern — do NOT
[WARNING]
====
Do not point an `RKE2ControlPlane` at a cluster whose first node was bootstrapped outside CAPI
expecting it to "add peers". It will either refuse (mixed-mode) or initialise a rival control
plane. Adopting an external master is manual surgery (hand-built owned `Machine` + `LXCMachine`
with a matching `providerID`, a satisfied bootstrap, and pre-seeded cert Secrets) with no
turnkey path.
====

Greenfield creation from a *separate* management cluster sidesteps all of this: `RKE2ControlPlane`
is on its clean init path, and the management cluster's own single node is never something CAPI
has to manage.

[[mgmt-declarative-mirror]]
== The management cluster's own declarative mirror (planned)

The workload clusters exist on the branch as *applied* CAPI CRs (Flux applies them, CAPI reconciles
them). The management cluster does not — it is nix-seeded (<<seeding-management>>), so it has no CAPI
representation anywhere, and reading the branch does not show the whole fleet.

The mirror closes that gap WITHOUT contradicting <<why-separation>>: render the management cluster's own
CAPI CR set (`Cluster`, `LXCCluster`, `RKE2ControlPlane`, `LXCMachineTemplate`, …) onto the branch, marked
`config.kubernetes.io/local-config: "true"` — the same "local only" annotation the render already uses for
the facet ConfigMap (see the render-facet mechanism). Kustomize/Flux keep these resources in the tree but
NEVER apply them, so there is no adopt / mixed-mode hazard (they are descriptive, not actuated). The branch
becomes a complete, uniform, self-describing record of the fleet — one model (CAPI CRs), one marker
(`local-config`) separating "Flux applies" from "recorded, actuated node-side".

Preferred over a bespoke ConfigMap: CAPI CRs are typed, schema-validated, tool-readable
(kubectl/clusterctl), and uniform with the workload CRs. (The facet ConfigMap stays a SEPARATE concern —
it carries the `ManifestDomainPolicy` synthesis facet, which is not a CAPI topology concept.)

.No drift — derive, never author
[IMPORTANT]
====
A descriptive mirror can LIE if it diverges from the real (nix/operator) bootstrap. The mirror CRs MUST be
DERIVED from the same SSOT as the real grow — the management cluster's `ClusterNetworkBlueprint` /
identity — exactly as the workload CRs are already derived, never hand-authored. Derivation makes the drift
structurally impossible.
====

[[mgmt-self-hosted-hypothesis]]
== Hypothetical direction — a CAPI-native cold-start (self-hosted via bootstrap → pivot)

WARNING: This is an EXPLORATORY direction, NOT a plan and NOT shipped. It is recorded so the option is not
re-discovered from scratch. It revisits <<seeding-management>> and must clear the caveats below before it
could be considered.

The mirror above is descriptive; the ambitious end-state makes it REAL. Instead of seed-master nix-seeding
the management cluster forever, an *ephemeral* CAPI bootstrap cluster (kind-like) would GREENFIELD-create the
management cluster — the clean `RKE2ControlPlane` init path <<why-separation>> says "sidesteps all of this" —
then `clusterctl move` (pivot) would transfer the management cluster's own CRs INTO it, and the management
cluster would self-host (manage itself + all workloads). The bootstrap cluster's sole role is to birth the
management cluster, then it is discarded. This is the canonical CAPI answer to the chicken-and-egg that
<<seeding-management>> currently resolves by keeping the seed-master nix-seed load-bearing.

Caveats that gate it:

* *The self-management paradox.* A self-hosted management cluster reconciles the control plane it RUNS ON.
  Control-plane-replacing operations (RKE2 upgrade, machine replacement, etcd rotation) can self-destruct.
  Standard mitigation: pivot OUT to a temporary bootstrap cluster for those operations (then re-pivot), or
  pause the self-`Cluster`. Must be designed explicitly.
* *The nix floor remains.* The incus host (`bioskop-nixos`) is nix/operator-provisioned, not CAPI. "Self
  managed" covers the k8s/LXC layer only; there is always an operator base under it.
* *Grow-then-pivot, not grow-eliminated.* Cold start still needs the management cluster to EXIST before it
  can self-manage; the ephemeral bootstrap does the initial greenfield, then hands over. It relocates the
  seed-master role (to running the ephemeral bootstrap + provisioning the incus host), it does not remove it.

[[operating-model]]
== Operating model — GitOps pull, management on demand

Changes to a workload split into two tiers, with very different reliability:

*Tier 1 — application / config changes (the common case): GitOps pull, in the workload.* Each
workload runs Flux, which *pulls* its desired state from git and applies it to itself (Deployments,
ConfigMaps, HelmReleases, CRs, …). This needs no management cluster, no tailnet, and no other host —
the workload depends only on git. For everything Flux can reconcile, each workload is fully
autonomous.

*Tier 2 — machine-lifecycle changes (rare: scale / replace / add a node → needs CAPI/CAPN).* Only
here is a management cluster required. It is single node (see <<seeding-management>>), *on-demand*
(stopped when idle; its state persists on its zfs dataset — stop, not destroy), and because it is a
<<function-of-git,function of git>> it can be run either as:

* a *fixed* `bioskop-mgmt` that reconciles both workloads remotely over the tailnet, or
* a *transient, host-local* management — seeded on the host that owns the workload, fed from git,
  reconciling the local workload, then discarded.

The transient host-local shape is the more reliable way to make a host independent: it removes the
cross-host and tailnet dependencies entirely (a fresh local management + git is all it needs).

*Reliability consequence.* The common case (Tier 1) depends only on git — not on the other host, the
management cluster, or the mesh. The rare case (Tier 2) is either local or a short remote reconcile.
The tailnet is therefore never a single point of fragility for a workload's own operations.

*Mesh placement.* `Headscale` is a *workload-cluster service* (see <<mesh>>), so it is naturally
never on the management cluster, and not a bootstrap dependency — bootstrap rides `Tailscale`.
Stopping the on-demand management cluster therefore cannot take the mesh with it.

[[function-of-git]]
== The management cluster is a function of git

Single-node management is safe *only* if the management cluster can be thrown away and re-seeded —
anywhere — into the same state, from git alone. That invariant dictates what must be persisted:

* *Desired state (GitOps source).* The CAPI/CAPN/CAPRKE2 resource set per workload (`Cluster`,
  `RKE2ControlPlane`, `RKE2ConfigTemplate`, `LXCCluster`, `LXCMachineTemplate`, `MachineDeployment`).
* *Deterministic secrets (sops-in-git) — the inputs that make the GENERATED Secrets reproducible.*
  Per-workload cluster CAs (so `certificates.LookupOrGenerate` reuses them → same trust domain), join
  tokens, the CAPN→incus identity, the management cluster's own CA/token, and the sops age key that
  decrypts them.
* *Deterministic identities (code-in-git).* `ClusterNetworkBlueprint` (cluster/node names,
  addressing) and the `node-base` image reference — which also let CAPN adopt instances by name.

The one piece of state that is *not* naturally git-persistable — the runtime link between a CAPI
`Machine.providerID` and the running Incus instance — is *re-derivable* from deterministic instance
names **iff** CAPN adopts an existing instance by name (to verify in the `LXCMachine` controller).

.Required, not optional
[IMPORTANT]
====
This forces where the durable secrets live: they must be in *git (sops-encrypted)*, not only in the
cellar's Pulumi state. A transient, host-local management fed from git must obtain the CAs and tokens
*from git* — it cannot reach a cellar hosted on the other host's Pulumi state. Host-level secrets
already live in `.secrets` sops; the cluster PKI from the cellar must join them in git.

The MECHANISM that carries the cellar's sealed materials into git is the `reach = IN_CLUSTER` extraction
(the seal declares `reach`, the render extracts the marked entries into a sops-encrypted branch asset, and
an in-cluster read-only cellar reads them back): see
link:../osgi/seed-broker-spec.adoc#in-cluster-cellar-asset[seed-broker-spec — the in-cluster cellar asset].
====

[[seeding-management]]
== Seeding the management cluster

The management cluster's single control node is always *nix-seeded* by seed-master — CAPI cannot
create the cluster that runs CAPI (a chicken-and-egg), so the management tier is the one place the
seed-master path stays load-bearing. In this model seed-master *is* the management-cluster seeder:
`seed-master` becomes `seed-mgmt` in effect — it seeds the cluster that holds the *global vision*
(the CAPI resources for every workload), not "the master node of a cluster" (a leftover of the
dual-role model).

* *Today*: a single control node, currently placed on `nikopol` (this is what `Pulumi.dev.yaml`
  seeds — `cluster=nikopol`, `node=master`). It `cluster-init`s and is the whole management cluster.
* *Single node — not per-host.* A node per bare-metal was considered and rejected: two etcd members
  is an *even* quorum (tolerates zero failures, needs both hosts up) — *less* available than one node
  — and two bare-metals cannot give etcd fault-tolerance regardless. Resilience comes instead from
  the <<function-of-git,function-of-git invariant>>: re-seed a fresh single node, on any available
  host, and it converges to the prior state from git.
* *Naming*: the single node is `<host>-mgmt`, named by the host it currently sits on (`bioskop-mgmt`
  when fixed on `bioskop`, or the host it is transiently seeded on). Workloads always stay
  `<host>-wrkld`.

== Operator experience — host-indifferent

From the operator's side, one `pulumi up` of the `seed-mgmt` stack provisions the management cluster
and — through its CAPI — the workload's master control node (greenfield), then the peers. The same
command runs *indifferently on `bioskop` or `nikopol`*, with identical expected behavior.

  participant PU as pulumi seed-mgmt (on bioskop OR nikopol)
  participant MG as management cluster (CAPI)
  participant GH as git
  participant WL as workload
  OP->>PU: pulumi up
  PU->>MG: nix-seed / update the single management node
  MG->>GH: read desired state (CRs) + secrets (CAs / tokens)
  MG->>WL: CAPI greenfield-creates the workload MASTER (cluster-init), then peers
  Note over OP,WL: host-indifferent — same expected behavior on either bare-metal
----

Host-indifference is not luck; it rests on three invariants from above: the *homogeneous*
`node-base` image (every node boots the same substrate), the *deterministic* `ClusterNetworkBlueprint`
(names/addressing are a pure function of cluster + node), and the <<function-of-git,function-of-git>>
invariant (all desired state and secrets come from git, so no host carries hidden state). And because
the workload master is *CAPI-created* — not nix-seeded on the host — nothing about a workload is
pinned to the bare-metal the operator happened to run `pulumi up` on.

== Materialization consequences

NOTE: The concrete *delivery* of these materialized sets — per-cluster rendered branches
`manifests/<host>-<role>` (history-preserving fast-forward push), consumed by `seed-master` (`-mgmt`) and CAPI/CAPN
(`-wrkld`) — is specified in link:manifests-rendered-branches.adoc[Manifests Rendered Branches]. The
`gitops/workloads/…` path model described elsewhere is superseded by that branch-per-cluster model.

This topology changes three materialization surfaces:

. *Manifests — three sets, synthesized together.* Synthesis moves from one `clusterName` to
  per-cluster/role: the management cluster gets `cluster-api` (operator + CAPN + CAPRKE2) + a
  minimal base + a Tailscale client; each workload gets the application stack (gitops · storage ·
  mesh · cicd · cilium) but **not** `cluster-api`. The `manifests.publish.{domain}` toggles become
  per-cluster. The CAPI/CAPN/CAPRKE2 resource set for a workload is a CDK8s `ManifestsUnit` applied
  *in the management cluster*, its values (`${cluster}`, VIP, CIDRs, token, tls-san) drawn from the
  synthesis context / scenario states.
. *Disko — per-host, across two bare-metals.* `nix-darwin-home`'s `zfs-disko-config.nix` is
  currently a single-cluster, hand-listed tree (`rke2/control-nodes/{master,peer1,peer2,peer3}/containerd`,
  `mountpoint=legacy`; the guest *mounts* it, it does not create it). It stops being a static
  literal: the layout becomes a *dataplan* owned by rke2lab `seed-master` and pulled into ndh's
  `catalog.datasets`, materialised per host (see
  link:../patterns/dataplan-single-source.adoc[Dataplan SSOT]). The root renames `rke2` -> `rke2lab`
  (owner, not the distro); the tree gains a cluster dimension (`rke2lab/<cluster>/<node>/containerd`)
  and splits per host — `bioskop-nixos` carries the management node's dataset + the `bioskop-wrkld`
  datasets; `nikopol-nixos` carries the `nikopol-wrkld` datasets. The dataplan is a *storage* artifact
  (its own `lib.dataplan`), NOT a field of `ClusterNetworkBlueprint` — a dataset is not a network fact
  (decompose by nature). `peer3` is dropped (three etcd members, odd quorum).
. *CAPN — two incus remotes (one per host), scoped per project.* CAPN in the management cluster
  provisions instances on *both* hypervisors — `bioskop-nixos`'s incus and `nikopol-nixos`'s incus —
  each remote scoped to the workload's own <<incus-tenancy,Incus project>>, so each workload's
  `LXCCluster.secretRef` points at its own incus-identity Secret (`server`/`server-crt` per remote;
  the `client-crt`/`client-key` CAPN identity can be shared, trusted by both hypervisors). The
  cross-host remote (`nikopol-nixos`) is reached over the tailnet at a stable address. Today's
  `IncusIdentitySecretManifestsUnit` renders a single `<cluster>-incus-identity`; it must become
  per-workload / per-remote. (`bootstrap-identity-provider.adoc` already models this — separate
  clusters, each its own remote, one shared CAPN identity.)
. *Scenarios.* The seed scenario changes from "seed the master" to "seed the management cluster,
  which then greenfield-creates the workload clusters" — the management cluster on its host, one
  workload beside it, and the other workload across the mesh.
