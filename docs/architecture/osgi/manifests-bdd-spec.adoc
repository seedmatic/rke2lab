= The manifests scion — synthesis played through the broker
:toc:
:toclevels: 3

== Overview

The manifests domain synthesizes the node's material — the K8s manifests, the
systemd units, the rke2 config, the env-config overlay — from CDK8s units and node
contributors. That synthesis (`ManifestSynthesisService`) lives OSGi-side; the host
cannot resolve it by type across the realm boundary, and doing so would be the
realm-boundary anti-pattern (see
link:../bootstrap/provisioning-slice-architecture.adoc[the incus-bootstrap constat]
§ corroboration). This spec describes **`manifests-bdd`, the manifests scion**
(SHIPPED), played in-container through the broker like bbox/incus/systemd/
cluster — the "graft cultivated fresh" the ClusterSeed map names.

It is the fifth scion, on the exact trio pattern the four sibling shipped scions share
(`*Scenario` + `*RunbookHandler` + `*AmendReflector`, the in-container play delegated
to the shared `ScenarioPlayer` behind `GenericRunbookHandler`), with three differences its
nature forces — spelled out below so the implementation does not blindly copy bbox.

== What makes the manifests scion different from the four others

[cols="1,2,2",options="header"]
|===
| Concern | The four contact scions (bbox/incus/systemd/cluster) | The manifests scion

| The gesture
| *probe/reconcile* an external system (router, incus, dbus, kube-API) — read or
  converge live state
| *synthesize + materialize* files — pure generation into an output tree, touching
  no live system

| The input
| enumerated from a static blueprint (bbox rows) or fixed markers; the scion holds
  its own desired state
| the operator's per-domain *activation choice* (`mesh` on/off, `cluster-api` on/off)
  — which must arrive from the host, in the trigger

| The doctor
| consults on trouble (a refused row, an unreachable instance) — runtime symptoms
| *no consult* — a synthesis failure is a build defect (a missing unit, a bad
  template), surfaced as a failed step, not a medical symptom
|===

== The one config path — the sow trigger (general, manifests is the first consumer)

This is the crux, and it is bigger than manifests: it is THE single path by which
any policy reaches any scion. The rule (user decision): **one config path, and every
policy reachable through it.**

=== What exists today (the audit)

* The four shipped scions (bbox/incus/systemd/cluster) have **no policy config path
  at all**. They resolve only the ambient `RunGate` (the whole-run live/preview
  fact) and their contacts + the doctor, all from the registry. Every `handle(trigger)`
  **ignores its trigger** — the sow trigger is empty (`"{}"`) today.
* Manifests has ONE policy path: the activation facet. Both the seed flow AND
  `manifests-cli` sow the `manifests` coordinate through the broker; the scion derives
  `ManifestDomainPolicy` from the `publish` facet of
  `ManifestsRunbookInput` (the host contributes it, or it falls to `defaults()`). The
  former system-properties path (`ManifestSynthesisRequest.fromSystemProperties()`,
  `-Drke2lab.manifests.policy.enabledDomains=…`) is gone — no second vocabulary to drift.
* The host policies that WOULD target other scions (`ReadinessPolicy`,
  `PreviewPolicy` → cluster/systemd) are wired to NOTHING — neither the old nor the
  new path carries them.

So there is no unified path; there is one duplicated path (manifests) and several
dead-ends. The scion work installs the single path.

=== The single path — one file, the shape carves each soil's facet

The one source of truth is a PHYSICAL file: `Pulumi.dev.yaml`. It is already read by
ONE reader, `ConfigLoader`, abstracted from its source through a `SectionReader`
seam — the seed reads it live (`ConfigLoader.of(com.pulumi.Config)`, inside
`Pulumi.run`), and any off-Pulumi caller reads the SAME file parsed to a map
(`ConfigLoader.ofNestedRoot(yaml)`). So "one config path" is not an invented
in-memory policy threaded through `SeedRun`; it is the file both realms' callers
already point at, through the one reader.

The config is organised **by concern**, not by soil. The manifests concerns live under
`rke2lab:manifests` — `publish`, `debug`; the remaining policy concerns (`network`,
`readiness`, `preview`) stay under `rke2lab:policy`. The concern grouping is the operator's
natural vocabulary, and the seed reads each verbatim into typed DTO records (plain
`Optional<Boolean>` keyed by camelCase — NO manifests type named). The soil→facet mapping
does NOT live in the file; it is carried by the *shape* (below), so the file never needs a
by-soil reshuffle.

. **One source of truth — the file, one reader.** `Pulumi.dev.yaml`, read through
  `ConfigLoader`. The seed binds it live via Pulumi; the CLI parses the same file to
  a map and feeds `ofNestedRoot`. Neither caller invents a policy shape; both read
  the operator's file.
. **The shape carves the facet — no host names a domain vocabulary.** A soil's facet
  is NOT a sub-map the caller knows a priori; it is DISCOVERED:
  `sow(ShapeCoordinate(S), {})` reaps S's runbook-input schema, whose top-level
  properties ARE the concern keys S owns (`manifests` → `publish`, `debug`). The caller
  plucks exactly those concern sub-maps from the yaml `manifests` section and assembles
  the trigger. Generic — the sower names NO domain vocabulary; the schema dictates
  which concerns to pluck. This is why the concern grouping needs no by-soil sealing
  in the file: the sealing lives in each soil's wire-record (which concerns it
  declares), reviewed in one place, not in the yaml's shape.
. **One channel — the sow trigger.** The plucked concerns become the trigger
  `SeedEnvelope` payload (today `"{}"`). A soil whose schema names no concern gets
  `{}` — exactly today's behavior, so the four shipped scions are unaffected until
  they grow a wire-record. This is a `seed-bdd` change (`Gardening.sow` /
  `SowAndGraftStage` stop sending empty), not manifests-only.
. **One translator per domain — the scion.** Each scion reads its own facet in
  `handle(trigger)` and translates it in its OWN vocabulary. The manifests scion
  owns `ManifestDomainCatalog`, so it derives `ManifestDomainPolicy` + `FloxDebugPolicy` from the
  `publish`/`debug` concerns. A scion sees ONLY its facet, never another soil's config.

**Consequences.** `fromSystemProperties()` dissolves — the CLI reads the same file
as the seed, through the same reader. Both host policy classes are GONE (deleted at
`1f7c1ee54`): `ManifestLinkPolicy` (whose sole job was translating the raw booleans
into `ManifestDomainPolicy` + `toEnvMap()`) AND `ControlplanePolicy` (the aggregate
that held it) were orphaned live logic with no production caller, and the translation
now lives OSGi-side in the scion. The scion derives `ManifestDomainPolicy` (the synth-time
filter) from its own `publish`/`debug` facet — it owns `ManifestDomainCatalog`, so no host type
names `manifests.contract` (the gate is clear, and LOCKED at ERROR). The scion's facet is defaulted today
(`ManifestsRunbookInput.defaults()`); the host does not pilot it (a decision, not a
gap — the policy is a manifests concern, not a host one). `readiness` / `preview`
were always separate concerns (they lived on the now-deleted host policy); they stay
raw in the config (the residual `rke2lab:policy` section / `ReadinessConfig`) and belong
to a cluster/doctor scion the day it grows a wire-record, not to the host.

*Design constraint this puts on piece 2 (the wire-record).* For the pluck to stay
generic, the runbook-input wire-record's top-level component names MUST equal the
yaml concern keys (`publish`, `debug`) — the schema's top-level properties ARE those
component names, and the caller plucks `manifests.<name>` for each. So the wire-record
nests (`record …(PublishFacet publish, DebugFacet debug)`), mirroring the yaml's concern
nesting exactly, rather than flattening into one bag.

*The workload-targets sub-facet.* Alongside `publish`/`debug`/`delivery`, the `Facets`
wire-record carries a fourth concern — `workloadTargets`, a `List<WorkloadTarget>` sourced
verbatim from `rke2lab:manifests:workloadTargets`. A `WorkloadTarget(host, role)` names a
*different* cluster the MANAGEMENT render must create: under the management/workload separation
(model B — see link:../cluster-api/manifests-rendered-branches.adoc[Manifests Rendered Branches]),
the workload CAPI CR set is rendered onto the management cluster's own `manifests/<host>-mgmt`
branch, because CAPI runs there. So the synthesis needs the workload identities *beside* its own
`bootstrapIdentity()` (which stays the management cluster): the `cluster-api` units read
`ManifestSynthesisContext.workloadTargets()` and derive each target's `ClusterNetworkBlueprint`
from its `WorkloadTarget.clusterName()` (`<host>-<role>`; the topology is the CANONICAL HA shape,
not carried). The compact constructor coalesces an absent list to empty — a management cluster
with no declared workloads.

=== The policy has TWO ends — the scion must cover both

The activation choice does not stop at "which domains synthesize". It drives a path
with two distinct ends, and the scion owns BOTH:

[cols="1,2,2",options="header"]
|===
| End | What it decides | Where it lives today

| *synth-time* | which domains are *synthesized* — `ManifestDomainPolicy` filters
  the domain registry (`applyManifestDomainPolicy`), resolves inter-domain deps,
  rejects an all-disabled set
| in-container (manifests-core) — correct already

|===

From its facet (the `manifests` sub-map of the one policy, § the single path), the scion derives
the `ManifestDomainPolicy` and, at synth-time, filters the domain registry — which layers
synthesise. This is why the scion is the natural home: it is the single point that already knows
the catalog, and it satisfies synthesis from one payload without any host type naming a domain
vocabulary.

==== The policy IS the synthesis input

The activation choice drives synthesis structurally, not by promise:
`ManifestSynthesisRequest` carries `manifestDomainPolicy` + `floxDebugPolicy` as
FIELDS — synthesis does not run without them. The scion derives both from its facet
(the `publish`/`debug` concerns) and calls `synthesize(request)`, so the policy IS the
synthesis input, not something computed beside it. It owns `ManifestDomainCatalog`, so no host
type names `manifests.contract`.

At synth-time the `ManifestDomainPolicy` filters which domains synthesise; the enabled layers'
manifests land in the per-resource tree RKE2 auto-applies from `server/manifests`. The former
host-side projection of this (the deleted `ManifestLinkPolicy` / `ControlplanePolicy`, and the
`RKE2LAB_MANIFESTS_PUBLISH_*` env-var overlay the node once read) is gone; the operator's choice
is made live by what is synthesised, not by a separate publish section.

=== Scope — which of the host policies this scion absorbs

The operator's policy has several concerns; not all route to manifests. This scion
owns the two that are manifests' business; the rest live elsewhere:

[cols="1,2,1",options="header"]
|===
| Policy concern | What it decides | Destination

| *publish* (the publish concern) | which domains synthesize + which layers publish live (the two-ended
  path above) | *this scion* (activation payload)
| `DebugPolicy` → `FloxDebugPolicy` | per-layer debug (flox NRI / mesh / networking
  image-command-env swap) — already a `manifests.contract` input of
  `ManifestSynthesisRequest` (`floxDebugPolicyFromSystemProperties`) | *this scion*
  (debug facet of the payload)
| `NetworkPolicy` (lanBinding) | host-side Incus provisioning (the Pulumi graph) | stays host
| `ReadinessPolicy` (raw severity overrides) | readiness verdict — cluster/doctor
  vocabulary; the host already carries it raw ("hands the raw value to the OSGi-side
  handler") | a *cluster/doctor* scion, not this one
| `PreviewPolicy` (raw fault simulation) | preview-only fault injection —
  cluster/doctor vocabulary, raw | a *cluster/doctor* scion, not this one
|===

So the manifests activation payload has TWO facets — *activation* (which domains,
from the *publish* facet) and *debug* (per-layer, from `DebugPolicy`→`FloxDebugPolicy`).
Both are already `manifests.contract` concepts; the scion assembles them from the
sown payload. `ReadinessPolicy`/`PreviewPolicy` are a separate transposition (a
cluster/doctor scion), out of scope here — noted so their host records are not
mistaken for dead when the manifests policies dissolve.

== The scion trio

Mirrors bbox's trio (link:bbox-edge-spec.adoc[bbox-edge-spec]), adapted:

=== `ManifestSynthesisScenario` (the `*Scenario`)

A production jGiven scenario in the MANIFESTS domain's vocabulary. Resolves its
collaborators from THIS bundle's registry (`FrameworkUtil`): the
`ManifestSynthesisService` (the SCR-published synthesis). MODE-BLIND — it injects no
`RunGate`: manifests is a pure FS materializer with no live touch (no
`Cultivating`/`Surveying` pair), so it runs identically in both modes. The
materialization target is carried by the SOIL amendment alone (the real staging tree
when the host amended a plot, a temp dir for a bare survey); rendering the run PENDING
under a surveying gate is the frontier's business (the engine's survey executor), not
the scenario's — the preview inertness the map requires, lifted out of the scenario.

[listing]
----
GIVEN the activation facet (which domains the operator enabled)
  AND the synthesis service, resolved from this bundle's registry
WHEN the policy is derived from the facet            [the scion builds the ManifestDomainPolicy — the synth-time domain filter]
  AND the manifests are synthesized                  [service.synthesize(request) → the K8s manifest tree (+ rke2-config), filtered synth-time]
THEN every enabled domain produced its units         [domainCount matches the enabled set]
  AND the manifests file is written                   [the consolidated manifestFile exists, hit count > 0]
----

No doctor consult. A synthesis `IOException` or an empty domain set fails the step —
jGiven marks it, the runbook shows the failure. The output tree location is the
run's `outdir`, chosen by the SOIL amendment alone (blank SOIL — a bare survey: a temp
dir; an amended SOIL: the staging slot incus PREPARE chose, later promoted to
`host.live.d` and mounted); the only surviving replace-trigger is the
nocloud→`replaceOnChanges` wire, NOT the removed `TargetChecksumPipeline` — see
host-cellar § the-grow-anatomy). The two synthesis
beats (units tree + controlplane overlay) are the two policy ends above: the scion
drives both, so a single sow produces the complete master material.

=== `ManifestsRunbookHandler` (the `*RunbookHandler`)

Identical shape to `BboxRunbookHandler`: `@Component(service = SeedHandler.class)` extending
the shared `GenericRunbookHandler`, supplying `coordinate()` (`ManifestsCoordinate.RUNBOOK`) and
`scenarioClass()` (`ManifestSynthesisScenario`) — the shared `ScenarioPlayer` does the in-container
play. It overrides `seedFrom(trigger)` to decode the activation facet (`ManifestsRunbookInput` —
which layers link, which debug) off `trigger.payload()` and route it through the scenario's
`ManifestSynthesisScenario.INPUT` channel (bbox does the same for its `BboxRunbookInput`), so the
operator's choice drives the synthesis.

=== `ManifestsAmendReflector` (the `*AmendReflector`) + the shared front-door

The per-domain front-door class is gone: the in-container play is the SHARED
`ScenarioPlayer` (a `JUnitLauncherCore` with an explicit `selectClass(scenarioClass())`,
returning a `RunbookEnvelope` — runbook JSON + empty consultations, the manifests scion
consults no one — as one serialized String across the realm boundary), invoked by
`GenericRunbookHandler`; the five per-domain `*BddScenarios` copies were dissolved into it.
What stays manifests-specific is `ManifestsAmendReflector` (`@Component service=SeedHandler`,
serving `ManifestsCoordinate.AMEND`, the reconciling twin of `ManifestsShapeReflector`): it
binds the host's NEUTRAL roles (the mandatory `FACET`, the optional `SOIL`/`IDENTITY`/`WORKTREE`)
onto the `ManifestsRunbookInput` subtree via the foundation `AmendmentBinder`, returning it under
the runbook coordinate — so vocabulary reconciliation lives at the amend door, not in the handler.

== The gardening boundary — the scion gardens, the units are cultivated

A load-bearing separation of concern, worth stating so it is not eroded: **the manifests units do
NOT know the gardening.** The gardening lexicon — broker, coordinates, `Cellar`, sow/reap, scions —
belongs to the *gardener*: the scion trio (`ManifestSynthesisScenario` + `ManifestsRunbookHandler` +
`ManifestsAmendReflector`, on the shared `ScenarioPlayer`), the composition root. Below it, the `ManifestSynthesisService` and its CDK8s
units are **gardening-ignorant** — pure domain synthesis, with no reference to the broker, a
coordinate, or a cellar. In the gardening metaphor the units are the *cultivated*, not the
*cultivators*: they receive their soil (the unit context) and grow (synthesise); the gardener did the
sowing.

This is not an inconsistency to "fix" by making units injectable/broker-aware. It is the layering, and
it buys two properties:

* *Portability.* `ManifestSynthesisService` runs under the scion (gardened) AND under a plain
  in-process call with no broker and no engine at all (a unit test, a direct `synthesize(request)`).
  If a unit knew the gardening, that plain path would break. Their ignorance IS their portability —
  and `manifests-core` depends on nothing from the scenario-engine, keeping the core→engine direction
  one-way. (The `manifests-cli` verb no longer calls the service directly — it sows through the
  broker like the seed flow — but the SERVICE stays callable without a broker, which is the point.)
* *No sideways reach.* A unit that sowed a coordinate to fetch what it needs would be the
  hidden-global-reached-sideways anti-pattern in broker clothing. Units declare their dependency at the
  injection point (the context) instead — the reviewer's win.

*The boundary is a value cascade, crossed once.* A cross-frontier view (cluster/node identity) is
reaped ONCE at the gardener — the `RunbookCoordinate("manifests")` crossing delivers the `WORKTREE`
amendment, from which `ManifestSynthesisScenario` sets `ManifestSynthesisRequest.bootstrapIdentity`.
From there it is pure in-process narrowing: the synthesis root builds one `NodeEnvContext` from that
identity and threads it to every unit through `ManifestsUnitContext` — the units consume their narrow
view, never the broker. This is exactly the two-tier navigability of
link:../patterns/service-contributors-views-adapters.adoc[the service/contributors/views/adapters
pattern] (§ Navigability): coordinate-via-broker across the frontier, in-memory reference within the
realm. It is also what killed the `bioskop` compile-time literal — the cluster name now flows from the
run's identity, reaped at the gardener and cascaded to the ignorant units.

== Why this closes several deltas at once

* **The synthesis runs again** — driven as a scion, in-container, where SCR
  activation is normal (the `awaitService`-from-flat-host puzzle disappears).
* **`manifests-cli` becomes a sower** — it sows `RunbookCoordinate("manifests")`
  and names no contract type, so its `NoClassDefFoundError` (host→contract-flat)
  is gone by construction.
* **The five materialization targets get their trigger** (constat deltas #2–6) —
  the scion IS the trigger the demolition removed; the synthesis machinery it drives
  is intact.
* **The realm-boundary gate on the manifests policies falls** — the host stops
  naming `manifests.contract`; the choice travels as a sown payload.

Two couplings dissolve here, and they are the SAME move. A sower that KNOWS the
payload shape a priori is coupled to the wire-record; a sower that reads config from
its OWN vocabulary (system properties) is coupled to a second source of truth. The
shape closes both: the CLI reads the operator's `Pulumi.dev.yaml` (one file, § the
single path) and asks the broker "what config do you want for the manifests runbook?"
(`sow(ShapeCoordinate("manifests"), {})`). The reaped schema's top-level properties
name the concerns to pluck (`publish`, `debug`); the CLI plucks exactly those from the
yaml `manifests` section and sows the runbook — naming no manifests vocabulary, holding
no contract class.

For this the `shape` meta-coordinate must be realized (foundation piece 1 — SHIPPED,
`ShapeCoordinate` + `RecordSchemaProjector`, see
link:seed-broker-spec.adoc#shape-realization[seed-broker-spec § realization status]).
Piece 2 (a `@SeedContract("runbook")` input wire-record + a `ManifestsShapeReflector`
projecting it) gives the runbook input its typed home — its top-level components ARE
the yaml concern keys (design constraint above), so the pluck stays generic. Until
piece 2 ships the shape is known a priori (a temporary coupling, not the end state).

== The version-bump scion — a second plant on the manifests domain

The `manifests-cli versions` verb is a SECOND scion of this domain, on its OWN coordinate
`ManifestsCoordinate.VERSIONS` (slug `manifests-versions`) — deliberately NOT a fork of the
synthesis runbook. Where the synthesis materialises into a soil, the bump READS the version pins,
queries the upstream GitHub releases, and — on `apply` — rewrites the source pin literals, refreshes
the vendored `release-<version>.yaml` manifests, and COMMITS the change to the worktree as the
rke2lab bot. It exists as a scion for the same structural reason the synthesis does: its
collaborators (`Worktree`, `GithubWriterTokenMint`, `NdhKeystoreReader`) register with their `type=contract`
bundle's class copy, so a flat host `awaitService` never matches — sowing through the broker grows
the work in-container where the `@OsgiService` injections resolve bundle-side.

=== The `Component` SSOT enum (dual-realm ingress)

A component's whole identity lives in ONE place: the `Component` enum (`manifests-ingress-contract`,
`type=dual-realm`), one constant per bootstrap component, carrying its wire `slug()`, its baseline
`defaultVersion()` pin, and its `Optional<ComponentSource>` provenance. It is a `WireEnum`, so the
codec maps it ↔ slug and the bump facet carries a typed `Optional<Component>` filter that crosses the
host↔OSGi membrane by slug — typed in BOTH realms because ingress is dual-realm. `ComponentSource`
(the GitHub `owner/repo` + optional release-asset + optional vendored-dir) is the provenance the
bumper reads to query GitHub and refresh the vendored asset; a component with an empty source (an
openebs chart, a container tag) is reported `manual`. `ComponentVersions` is now a thin resolved
holder over the enum (`of(Component)`), its baseline `defaults()` built from each
`Component.defaultVersion()` — the literal the bumper rewrites. `BumpLevel` (a `WireEnum`:
major/minor/micro) is the bump CEILING the operator authorises; the highest release the level admits
is taken, so `major` degrades to a minor/micro when that is all that is newer. The enum is passive —
it holds identity, provenance and the default pin and does NO network I/O; discovery is computed
OSGi-side by the bumper (a `VersionReport` keyed by `Component`).

=== The crossing and the scion trio

The host fills the operator's policy onto the neutral `FACET` role — the wire contract is
`ManifestVersionsBumpInput` (`@SeedContract("runbook")`, its `@Amendment(FACET)` `BumpFacet` carrying
`BumpLevel` + `apply` + `Optional<Component>`). `VersionsAmendReflector` binds that subtree at the
`AmendCoordinate("manifests-versions")` door (the twin of `WorktreeAmendReflector`);
`VersionsRunbookHandler` serves `ManifestsCoordinate.VERSIONS` and grows `VersionBumpScenario`
in-container. The scenario `@OsgiService`-injects `Worktree` (jgit stage/commit), the optional
`GithubWriterTokenMint` (the `auth` edge that mints a fresh writer token on demand from the App
credentials revealed at `GhAppCase`, not a long-lived env token), and `NdhKeystoreReader` (the
tailnet `authorityDomain` the bot email is minted from). On `apply` it rewrites `Component.java`,
stages the changed paths (including the deleted old `release-<oldPin>.yaml`) through `Worktree`, and
commits as the identity `GitBotIdentities` mints — `rke2lab:manifests-bumper` /
`manifests-bumper@<domain>`, the domain single-sourced from the PKI keystore. The report IS the
runbook: each component is a nested step (`@NestedSteps`), so the host renders the diff — and, on
apply, the bumps + the bot commit — straight from the reaped runbook (`VersionsCliScenario` sows the
coordinate and grafts the scion under its step; `Main` prints it).
