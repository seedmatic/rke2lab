= OSGi boot single-source — the embedded-bundle capability scan
:toc: left
:toclevels: 3

[NOTE]
====
*Status:* SHIPPED on `refactor/osgi-boot-single-source`, integrable into `design/pre-integration`.
Removes the hand-list of embedded model bundles — the "boot trap" flagged in
link:../patterns/port-edge-domain-ownership.adoc[Port, edge, domain — told apart]. The embedded model
bundles are now DISCOVERED at boot by scanning `META-INF/bundles/` for a self-declared OSGi
capability, not named in Java at ~8 scattered sites. Build GREEN on the reactor
(`./mvnw -pl :seed-outcluster,:manifests-cli,:netplan-cli -am clean package
-Dmaven.build.cache.skipCache=true -DskipTests=false`).

This is the prerequisite for `ssh-to-age-edge` (the first NEW embedded bundle): with the trap still in
place, adding it would have doubled the hand-list. Now it is one pom `artifactItem` + one capability
line in the bundle's `bnd.bnd` — zero Java.
====

== The defect this closes

The `META-INF/bundles/` embed topology had *no single source*. The boot stack
(pax-logging, felix.scr, felix.resolver) was already single-sourced via the `*_JAR` constants in
`OsgiRuntime` — those are fixed and identical across entrypoints, so naming them by constant is
correct. The *model bundles* (`manifests-core.jar`, `netplan-core.jar`) were the problem: each was
copied as a literal at four kinds of site, times three exec entrypoints:

[cols="1,3"]
|===
| Site | What it said

| pom staging (`destFileName`)
| `maven-dependency-plugin` `stage-embedded-bundles` — copies the reactor jar into
  `generated-resources/META-INF/bundles/<name>.jar`.

| pom shade (`<exclude>`)
| `maven-shade-plugin` `artifactSet/excludes` — keeps the model bundle OUT of the flat uber-jar so it
  stays the single exporter of its packages (the R1 split scar).

| Java boot (`bootingEmbedded("…jar")`)
| `SeedRuntime.bootingEmbedded("manifests-core.jar")` in `BootstrapStage` / `Main` /
  `SynthesisCommand` — named which staged jar to install as a model bundle.

| Test (`embeddedBundle("…jar")`)
| `OsgiRuntime.embeddedBootStack().embeddedBundle("…jar")` in each `EmbeddedBundlesBootTest`.
|===

`OsgiRuntime` admitted it in its own Javadoc: _"poms cannot call Java, so this is the authoritative
registry during review."_ A registry maintained by review discipline is exactly the parallel
hand-list `model-substrate-alignment` warns against — it drifts at the first rename.

== The decision — filter on a CAPABILITY, not on names

Filtering the scan by jar *name* would have been a hand-list in disguise: a renamed jar silently drops
out of the model-bundle set with no compile error. Instead each embeddable bundle carries an
*objective, self-declared marker* in its manifest, and the boot reads the real artifact.

=== The marker

Each model bundle declares, in its `bnd.bnd`:

[source]
----
Provide-Capability: io.seedmatic.rke2lab.embed; type=model
----

* The namespace `io.seedmatic.rke2lab.embed` is *ours* — reverse-DNS, the vendor convention for custom
  capability namespaces. It deliberately does NOT start with `osgi.`, the prefix the OSGi Alliance
  reserves for the standard namespaces (`osgi.wiring.package`, `osgi.identity`, `osgi.extender`,
  `osgi.service`, …). No collision, present or future.
* There is *no matching* `Require-Capability`, so the OSGi resolver never considers it for wiring — it
  is a pure out-of-band marker, read by `OsgiRuntime` from the jar manifest, never by Felix. It does
  not touch `system.packages.extra` or any `osgi.wiring.*` resolution.
* It lives *per-bundle*, next to `Export-Package`. Being EMBEDDABLE is a narrower per-module property
  than being a bundle: ports, `cdk8s-systemd`, `unitrepo-core` are bundles but are served flat, never
  embedded. A shared parent would over-broadcast the marker to non-embeddable bundles, so it stays
  local to the two (soon three) model bundles that actually carry it.

=== The scan

`OsgiRuntime.boot()` discovers the model bundles instead of receiving their names:

. `listEmbeddedJarNames()` enumerates the `*.jar` directly under `META-INF/bundles/`, handling both
  deployment shapes — a `jar:` URL when the root is inside the running exec-jar, and a `file:`
  directory when `generated-resources/META-INF/bundles` is an exploded resource root (the reactor
  test classpath). A missing root yields an empty list.
. `scanEmbeddedModelBundles()` reads each jar's manifest and keeps those whose `Provide-Capability`
  contains `EMBED_CAPABILITY_NAMESPACE`. The boot-stack jars are in the same directory but carry no
  such header, so they are excluded *objectively* — they are still installed, by the `*_JAR`-named
  path, as before. Result is sorted by file name for a reproducible boot log.

Adding a model bundle is now: **one `artifactItem` in the exec pom's `stage-embedded-bundles` + one
`Provide-Capability` line in the bundle's `bnd.bnd`.** No Java touched.

== What stays on the pom side (and why)

The staging `artifactItem` and the shade `<exclude>` are the *two pom faces of one declaration* and
cannot be collapsed into the scan:

* The shade runs at `package`, *before* the process ever boots — there is no running framework to
  scan, so the exclude cannot be derived from a runtime capability read.
* Maven's `maven-dependency-plugin` and `maven-shade-plugin` filter by GAV coordinate, not by manifest
  capability; deriving the exclude from the capability would need a bespoke mojo — more machinery than
  the duplication costs.

So the irreducible pom side is: stage the jar under `META-INF/bundles/` AND exclude it from the flat
shade. That pair is inherent to "embed intact + keep single exporter", and it applies to the boot
stack too. What this change eliminates is the *Java* hand-list — the four-site × three-exec scatter is
now zero Java literals.

== The one trap during implementation — scan vs the classpath boot topology

`OsgiRuntime` serves two boot topologies:

* *embedded* — `embeddedBootStack()`, used by the three exec entrypoints and their
  `EmbeddedBundlesBootTest`: every jar comes from `META-INF/bundles/`.
* *classpath* — `HostSeamEmbeddedFelixTest` in seed-outcluster: the model bundle is located on the reactor
  classpath (an exploded `target/classes`) via `OsgiRuntime.locateOnClasspath(...)` +
  `bundle(Path)`, NOT from `META-INF/bundles/`.

In a reactor build the staged `META-INF/bundles/` is *also* on the test classpath. An unconditional
scan would therefore install manifests-core twice in the classpath test — once via `bundle(Path)`,
once via the scan — and Felix fails with `Bundle symbolic name and version are not unique`.

The scan is gated to the embedded topology: it runs only when `embeddedRuntimeNames` is non-empty
(which only `embeddedBootStack()` fills). The classpath topology installs solely what `bundle(Path)`
named; the embedded topology installs solely what the scan discovered. The two never mix.

== Determinism, degradation, resolver-neutrality (the points checked before coding)

* *Order* — model bundles share `START_LEVEL_BUNDLES` (=3); within a level Felix wires by capability,
  not by install order, so there is no required order between them. The scan still sorts by file name
  so the boot log is reproducible.
* *Off-exec-jar* — `hasEmbeddedBundles()` is false on a bare reactor/test classpath with no staged
  root; `listEmbeddedJarNames()` then returns an empty list, no exception. The degraded case is the
  classpath topology above, which never relies on the scan anyway.
* *Resolver neutrality* — the custom capability has no matching `Require-Capability`, so it never
  enters Felix's resolution; it is read only by the manifest scan in the host world.

== Files touched

* `osgi/manifests/manifests-core/bnd.bnd`, `osgi/netplan/netplan-core/bnd.bnd` — added the
  `Provide-Capability` marker.
* `osgi/runtime/.../OsgiRuntime.java` — `EMBED_CAPABILITY_NAMESPACE` + `scanEmbeddedModelBundles()` +
  `listEmbeddedJarNames()`; the scan gated to the embedded topology in `boot()`; removed the
  `embeddedBundle(String)` builder verb and the `embeddedBundleNames` field; refreshed Javadoc.
* `osgi/runtime/.../SeedRuntime.java` — `bootingEmbedded()` is now no-arg; dropped `modelBundleJars`.
* `exec/{seed-outcluster,manifests-cli,netplan-cli}` — the three `bootingEmbedded()` call sites and the
  three `EmbeddedBundlesBootTest` boots dropped their model-bundle literal.
