= The engine lifecycles — framework, launcher, runbook, on the JUnit substrate
:toc: left
:toclevels: 3

[NOTE]
====
*Status:* BUILT (increment 1 landed 2026-07-05, `feature/engine-lifecycle-socle`, all tests +
6 staging gates green). This is the SOCLE (foundation) of the BDD-as-engine migration — it lands
before the ClusterSeed vertical (link:../bdd/bdd.adoc[BDD-as-engine]) consumes it. The realised
module is `osgi/runtime/scenario-engine` (the boot module was renamed `osgi/runtime/framework-launcher`
alongside); `OsgiConnection` shipped as a `context()`-based contract (not `world()`), and the machinery
sits behind a realm/seam package split (in-realm exported, seam unexported). See the
`engine-lifecycle-socle-state` memory for the as-built decisions.

One spec for one subject: *how the stacked engine lifecycles are held at runtime* — the OSGi
framework, the embedded JUnit Platform launcher, and the jGiven runbook — and how the SAME model
serves both a real test and a live seed run, differing only by scope, never by branch.

*Why this exists:* the BDD-as-engine turn makes the seeding a tree of jGiven scenarios played by an
embedded JUnit launcher inside Felix. That launcher, that framework, and that runbook each have a
lifecycle — and today all three are held *lexically / per-scenario* (a fresh framework per launch, a
throwaway launcher per run, a new runbook per scenario). That is fine for a test that may fall after
each case; it is WRONG for a live seed, where the world must survive across the scenarios that
compose the run. This spec fixes the ownership and the scoping.
====

.TL;DR — read the figures, this confirms them
====
* *Substrate (Figure 2):* JUnit is the single lifecycle substrate. It already discovers and creates
  the OSGi framework; it also carries scope demarcation (session root > class > method) via nested
  `Store`s + callbacks. Nothing home-grown doubles it.
* *Framework lifecycle (Figure 3):* held by a JUnit scope's `Store`; undone when THAT scope closes.
  Test vs runtime = *where the root lives* (test run / seed run), same code. The connection is an
  abstraction: embedded is realised (owns the close, stops the world), remote is a named extension
  point (detaches — the world survives).
* *The lever (Figure 4):* the OSGi *start level*, a SINGLE global cursor, driven by the depth of the
  JUnit scope. Descent stops bundles transiently (async → wait for the level-changed event);
  re-ascent re-lights them from the persistent autostart. The `BootPlanner` stays the sole
  role→level source.
* *Two composable dimensions* a scope declares: *depth* (start level) × *domain* (`DiscoveryPolicy`
  — which bundles are installed).
* *Discipline by role (Figures 5 & 6), declared by an rke2lab annotation:* *isolation* (a real test —
  the method scope descends/re-ascends, each case starts clean) vs *stationary* (a runtime pipeline —
  climbs once, NEVER descends between pipelines, the world survives). Extensible: a 3rd discipline =
  a 3rd annotation.
* *The runbook is the DELIVERABLE (Figure 7).* Owned by the launcher / the seed OPERATION (bounded by
  `pulumi up`), NOT by the framework — the framework only CONTRIBUTES scenario models to it.
* *YAGNI:* no per-bundle activation model (the test case does that in plain JUnit), no scenario-level
  start-level (a scenario activates no bundle of its own — fixtures are fragments), no transaction
  engine (the "lease" is a lifetime analogy, not ACID), no framework-serves-N-operations (there is
  no client version of the framework yet).

== The subject — three stacked lifecycles, held lexically today

The BDD-as-engine model (link:../bdd/bdd.adoc[BDD-as-engine]) plays the seeding as jGiven
scenarios on an embedded JUnit launcher, inside Felix. Three engines stack, each with a lifecycle,
and each is held TODAY at the grain of the *scenario / test case* — which is acceptable when a test
may fall after each case, and WRONG at runtime where the world must survive the whole seed run.

*Read Figure 1 as three columns, one per stacked engine. The top (blue) cell of each is HOW it is
held today — lexically, per-scenario. The bottom (red) cell is WHERE that grip breaks at runtime.
The three red cells are the same defect three times: a lifetime scoped to the scenario, when the
seed is one long run of many scenarios.*

== The substrate — JUnit carries the lifecycles, nothing home-grown doubles it

*Lead: JUnit already discovers and creates the OSGi framework; it also owns nested scope demarcation.
So it carries the framework, launcher and runbook lifecycles too. A new policy is a contributed JUnit
extension — never a home-grown registry.*

The realisation (2026-07-04): we already make JUnit carry the two hard parts — discovering the
framework's install set and creating the framework in-container. Making it also carry *when* the
framework, launcher and runbook live and die is not new surface — it is the same substrate, one cran
further. This is the dogfooding rule (link:../bdd/bdd.adoc[BDD-as-engine] § "Why embed JUnit +
jGiven at runtime") applied to lifecycle: we extend JUnit, we do not reinvent it beside itself.

*Read Figure 2 as three boxes NESTED one inside the other — session ⊃ class ⊃ method. That nesting IS
the coupling: a resource placed in a scope's `Store` lives exactly as long as that scope and is
closed when it ends, not before. Each scope has an entry hook (`BeforeXxx` — capture / raise) and an
exit hook (`AfterXxx` / `CloseableResource.close()` — release / lower). The socle only fills these
native slots; it adds no registry of its own.*

== The framework lifecycle — held by the connection's scope

*Lead: the framework lives in a JUnit scope's `Store` and is undone when that scope closes. Test vs
runtime is only WHERE the root scope lives; the code is identical. Connecting is an abstraction —
embedded bootstraps and owns the close, remote attaches and closes nothing.*

The framework is not a JVM singleton and not a lexical `try` — it is a closeable resource in the
`Store` of a chosen scope. The same teardown mechanism ("close at the end of the scope") serves both
worlds; only the *location of the root* differs.

*Read Figure 3 top-to-bottom. The top box is the CONNECTION abstraction with its two faces:
`embedded()` (teal, realised — it bootstraps Felix, owns the lifecycle, and its `close()` stops the
world) and `remote()` (green, named-not-built — it attaches to a running world, owns nothing, and its
`close()` merely detaches so the world survives). The two boxes below show the ONLY difference between
a test and a live seed: which scope is the root that holds the embedded connection — the test run, or
the seed run bounded by `pulumi up`. Same `embedded()`, same close-at-scope-end; only the root's
lifetime changes.*

[[the-boot-invariants-one-source]]
=== The boot config the two executors MUST share — one source, or it drifts (2026-07-19)

"Test vs runtime is only WHERE the root scope lives; the code is identical" holds for the lifecycle
mechanism — but the FRAMEWORK PROPERTIES the boot sets are built by two different enclosures (the
live `FrameworkLauncher` from a `LaunchConfig`; the test `OutOfContainerFrameworkExtension` from its
builder), and a property set in one and forgotten in the other is invisible until a live run hits it.
It DID: the live boot shipped without `org.osgi.framework.bootdelegation=sun.misc`, so byte-buddy's
`ClassInjector.UsingReflection` — which jGiven's `beforeEach` drives to generate each stage subclass —
could not reach `sun.misc.Unsafe` in-container, and EVERY scion aborted before its body ran, while the
tests (which had it) stayed green. A JDK-internal package no system-bundle export can serve: it must
be parent-delegated, and both boots play jGiven, so both need it.

The fix is a discipline, not a value: the shared requirements live ONCE, on `LaunchConfig`, and both
executors derive from that source — never a literal spelled twice.

* *`LaunchConfig.SCENARIO_PLAY_BOOT_DELEGATION`* (`= List.of("sun.misc")`) — the boot-delegation
  every jGiven-playing boot needs. `FrameworkLaunch.embedded` sets it via `withBootDelegation(...)`;
  `ScenarioTestkit.felix` sets the same list. One source, so the live↔test drift that caused this
  cannot recur.
* *`LaunchConfig.applyFrameworkInvariants(config)`* — the Felix properties that must be IDENTICAL in
  every boot, stamped by one call both enclosures make. Today one invariant:
  `felix.bootdelegation.implicit=false` (Felix defaults it TRUE — it would guess by stack inspection
  when an outside-a-bundle load falls through to the parent, the silent escape hatch that lets a
  non-wired seam package resolve by accident, so a typed-seam proof could pass for the wrong reason).
  It was already duplicated verbatim in both boots with the same rationale — the exact twin of the
  `sun.misc` drift, closed the same way.

The rule generalises: any framework property both executors need is a can't-drift invariant → it
belongs on `LaunchConfig` (a named constant or `applyFrameworkInvariants`), referenced by both, never
a literal in each enclosure.

==== The framework log-level knob — one currency, one operator knob, two planes (2026-07-19)

When the framework errors at boot (a failed resolve), the ONLY lever that explains WHICH requirement
could not be wired is Felix's own internal log, `felix.log.level`. The operator (the Pulumi actor)
must be able to raise it WITHOUT knowing the framework/bundle distinction — one knob.

* *Currency — `org.osgi.service.log.LogLevel`.* The single vocabulary the whole chain speaks: the
  `@FrameworkLog` test annotation, the `logging:level` operator knob, and the boot all name the OSGi
  standard enum. No second (custom) enum exists. It comes from `osgi.core` in the OSGi realm (which
  bundles the package at v1.5) and from the slim `org.osgi:org.osgi.service.log` spec artifact in the
  host exec realm — never the same classpath (broker-mediated), so no split-package. Felix's system
  bundle does NOT export `org.osgi.service.log`; the type is a boot-CONSTRUCTION parameter consumed
  host-side before Felix exists, never by in-container code, so scenario-engine's bundle imports it
  `resolution:=optional` (the base seam package is host-only — the established optional-import pattern,
  NOT the junit5 anti-pattern of an optional import on an EXPORTED package).
* *The felix-owner primitive — `LaunchConfig.felixLevelOf(LogLevel)`.* The ONE place the OSGi level
  collapses to Felix's proprietary int (1=error … 4=debug; Felix has no AUDIT/TRACE — they pin to the
  nearest step). Reached by BOTH boot paths: the live `FrameworkLauncher.frameworkConfig` (via
  `LaunchConfig.frameworkLogLevel`, threaded by `FrameworkLaunch.embedded(LogLevel)` /
  `OsgiConnection.embedded(LogLevel)`) and the test `OutOfContainerFrameworkExtension` (reading
  `@FrameworkLog`). One mapping, can't drift — the same discipline as `applyFrameworkInvariants`.
* *One knob → two planes.* The operator sets `logging:level` once; the host (`seed-outcluster`) drives:
  ** *Plane A — the framework's own log* (`felix.log.level`, set at construction): the level is sown
     onto the launcher via `LogLevelSeed`, read host-side by `BaseWorldExtension` before it boots
     Felix, and threaded into the `LaunchConfig`. (Threaded, not a sysprop — the value is only knowable
     in `Main`, and the seed is the same session-store channel the other run-facts cross on.)
  ** *Plane B — the logback root* (the application log): the same value maps via
     `LaunchConfig.logbackLevelOf` (the twin of `felixLevelOf`), and `FrameworkLauncher` applies it to
     pax-logging-logback — the ONE logback in the process (pax embeds its own and exports no package,
     so the flat host cannot reach logback directly), reflectively through the `pax-logback-config`
     fragment's `PaxLogbackConfigurer`. Programmatic, not a sysprop the XML reads — logback has already
     initialised by the time the config is knowable, so setting the level on the live context is what
     takes effect.
* *Absent knob ⇒ no override.* `BootstrapConfig.logLevel()` is `Optional`; empty leaves the Felix
  default (a no-op seed) and the `logback.xml` root untouched — the two CLIs, which thread nothing,
  keep the no-arg `embedded()`.

[[the-lever]]
== The lever — the start level, driven by the depth of the JUnit scope

*Lead: the OSGi start level is a SINGLE global cursor. Each JUnit scope targets a level; because the
scopes nest, the cursor moves up on entry and down on teardown, ordered in time — NOT stacked in
parallel. The `BootPlanner` stays the sole role→level authority.*

The `BootPlanner` already assigns each bundle a start level by its ROLE, in named layers
(link:osgi-boot-decomposition-spec.adoc[OSGi boot decomposition]):

[cols="1,2",options="header"]
|===
| Level | Role
| `START_LEVEL_PASSIVE` (1) | DS-API spec jars — resolve only, no activator
| `START_LEVEL_LOGGING` (2) | pax-logging
| `START_LEVEL_FRAMEWORK_RUNTIME` (3) | felix.scr, resolver
| `START_LEVEL_BUNDLES` (4) | model/edge domain bundles — activate LAST
|===

`beginningStartLevel()` is the highest a bundle sits at (4) — the framework climbs to it, so all
installed bundles are active when the boot hands over. The cursor is single and global: the framework
is AT level N, never "at 4 for this scope and 3 for that one". So there is no parallel stack of
levels — what nests is the JUnit scope tree, and it maps to *ordered moves of the one cursor in time*.

*Read Figure 4 as a timeline with three lifelines: the JUnit scopes (who calls), the single global
start-level cursor (what moves), and the domain bundles (what lights up). Follow it down: entering
each scope raises the cursor; `@AfterEach` LOWERS it, and that arrow is the important one — the stop
is transient (autostart untouched) AND asynchronous, so the teardown must WAIT for the level-changed
event before the next scope runs. The final dashed note is why re-ascent needs no explicit restart:
the next `@BeforeEach` re-lights the bundles from their unchanged autostart.*

.Figure 4 — the staircase: scopes move the one cursor, bundles follow; descent is transient + async
[mermaid]
....
sequenceDiagram
  participant J as JUnit scopes
  participant C as start-level cursor (single, global)
  participant B as domain bundles (level 4)
  J->>C: openSession — setStartLevel(0)
  Note over C: 0 · nothing active
  J->>C: @BeforeAll — setStartLevel(3)
  Note over C: 3 · felix.scr, resolver
  J->>C: @BeforeEach — setStartLevel(4)
  C->>B: start (from persistent autostart)
  Note over C,B: 4 · domain bundles active for THIS method
  J->>C: @AfterEach — setStartLevel(3)
  C-->>B: STOP_TRANSIENT (autostart intact)
  Note over C,B: async — WAIT for STARTLEVEL_CHANGED before the next scope
  Note over J,B: the next @BeforeEach re-lights B from autostart (no explicit restart)
  J->>C: @AfterAll — setStartLevel(0)
  J->>C: closeSession
....

NOTE: per the OSGi R8 spec (`osgi.core` 8.0.0, `FrameworkStartLevel.setStartLevel`): lowering the
active level stops bundles above it with `STOP_TRANSIENT` (arrests them without touching persistent
autostart); the call is asynchronous and fires `FrameworkEvent.STARTLEVEL_CHANGED` on completion (so
a teardown that lowers MUST wait, as `BootedFramework.close()` already waits on `waitForStop`);
re-ascending re-lights the transiently-stopped bundles from their unchanged autostart. R8 guarantees
per-level ordering (higher stop before lower) — the dependency-safe order is the level order; it does
not mandate an order *within* a level, which does not bite since the layers separate roles across
levels.

== The two dimensions — depth × domain

*Lead: a scope declares TWO composable things — its DEPTH (start level, the role layer active) and its
DOMAIN (which bundles are installed). They are orthogonal levers, both dimensions of "what I want
active to play".*

[cols="1,2,2",options="header"]
|===
| Dimension | Grain | Lever
| *depth* | role layer (1→4), system-wide | the start level (this spec's lever)
| *domain* | which domain / which bundles installed | `DiscoveryPolicy` (`only` / `onlyMatching(ldap)`
  / fixtures) — link:osgi-boot-decomposition-spec.adoc[boot decomposition]
|===

The start level is COARSE: level 4 activates *all* installed domain bundles together — it cannot say
"doctor but not manifests". Domain selection is the `DiscoveryPolicy`'s job (already a `sealed`
interface with `all`/`allExcept`/`only`/`onlyMatching`). A scope composes both: *"install this domain
subset (policy) AND play at this depth (level)"*. The `BootPlanner` remains the single authority that
maps role→level and computes the install set; the scope only *requests* a level, it reorders nothing.

[[discipline-by-role]]
== The discipline — chosen by role, declared by an rke2lab annotation

*Lead: the mapping scope→level is not fixed — it is a DISCIPLINE the scope's ROLE chooses. A real test
wants isolation (the method scope descends/re-ascends, each case clean); a runtime pipeline wants
stationary (climb once, never descend between pipelines, the world survives). Opposite mappings, one
mechanism.*

*Read Figure 5 as two lanes, each a left-to-right trajectory of the start-level cursor over the run.
The top lane (isolation) SAWTOOTHS: it climbs to 4 for a case, drops back to 3 at `@AfterEach`, climbs
again for the next case — every case re-starts the domain bundles, so every case is clean. The bottom
lane (stationary) is FLAT at 4: it climbs once and holds across every pipeline, the world never torn
down between them. Seeing the two shapes side by side is the argument: a single fixed mapping would
break whichever lane it does not match.*

== The runbook — the deliverable, owned by the operation, contributed by the framework

*Lead: the runbook is the whole POINT (the operator's read-AND-act view). It is owned by the launcher
/ the seed OPERATION, bounded by `pulumi up`. The framework does NOT hold a runbook — it CONTRIBUTES
scenario models to the one the operation owns.*

The runbook (`ReportModel`) is the benefit of all this machinery — miss it and we would have specced
the plumbing without its purpose.

*Read Figure 7 left-to-right around the OWNER (purple): the operation opens ONE report, the scenarios
play and graft their trees into it, and it is rendered at the end of `pulumi up`. The framework (teal)
sits OFF the ownership line: it is consulted across the gateway and returns a serialized scenario
model (the `Document` seam) — a dashed contribution arrow, never a report it holds. That off-line
placement is the whole claim: the framework participates, it is not the repository.*

Scenarios stay distinguishable within one runbook: `ReportModel.scenarios` is a `List<ScenarioModel>`

the OPERATION, not the framework's life; in embedded they coincide (the framework falls with the
operation), but the ownership is the operation's.

[[yagni]]
== What the socle deliberately does NOT do (YAGNI, confirmed by the code)

Each exclusion was checked against the codebase, not assumed:

* *No per-bundle activation model.* Once the framework is connected and injected, a test case
  activates/deactivates ITS bundles with plain JUnit hooks (`@BeforeEach`…) + the `BundleContext` —
  its own affair, with its own knowledge. The socle acts on the FRAMEWORK (the start level), never on
  an individual domain bundle. `START_TRANSIENT`/`STOP_TRANSIENT` per bundle is the test case's
  domain, not the socle's.
* *No scenario-level start level (no level 5).* Cartography: a scenario activates NO bundle of its own
  — what a test case adds is a *fixture*, and a fixture is a FRAGMENT (`Fragment-Host: …`), which has
  no lifecycle (calling `start()` on it throws). A scenario consumes services already active at level
  4 (`awaitService`), it starts nothing. A `START_LEVEL_SCENARIO` above 4 would be empty of meaning.
* *No transaction engine.* The "lease" (bail) is a *lifetime analogy* — begin/hold/release scoped by
  the JUnit tree — NOT an ACID contract. It is bounded to bundle activation; there is no atomicity /
  isolation / resource rollback. The seed is strictly sequential (no concurrent runs), so isolation
  has no referent here. A different name than "transaction" is used on purpose to avoid the ACID
  confusion.
* *No framework-serves-N-operations.* There is no client version of the framework yet. `remote()` is
  a NAMED extension point (the framework *could* survive an operation), but "one long-lived framework
  serving a series of runbooks" is not designed in this socle. It is out of scope until a real client
  case arrives.

== The authority of the lease — bound to the initiator

*Lead: only the scope that INITIATED a mutation of the framework (posed the lease) holds — or
delegates — the authority to keep or undo it. No ambient authority.*

*Read Figure 8 following the solid arrows: the initiating scope holds the authority, and only it (or a
scope it explicitly delegates to) reaches the "keep / undo" outcome. The dashed FORBIDDEN arrow from a
non-initiating scope is barred — that is what "no ambient authority" means: presence in the tree does
not grant the right to undo a mutation you did not pose.*

This is why the discipline is a *choice of the scope*, not a global rule: the role is defined by who
holds the authority at that level. Practically, in this socle the authority is carried by the
extension the annotation pulls — the extension that raised the level at its scope's entry is the one
that lowers it at teardown; a nested scope that wants a different depth declares its own annotation
(its own extension, its own authority, undone at its own teardown).

== Increment boundary — this socle is increment 1

This spec is the foundation the ClusterSeed-vertical migration rests on. It ships as *increment 1*
(the launcher-core extraction + the connection/lifecycle model), integrated BEFORE the ClusterSeed
migration (*increment 2*) consumes it:

* *Increment 1 (this socle):* carve a new runtime module `osgi/runtime/scenario-engine` that OWNS the
  JUnit/jGiven machinery playable at runtime — the two framework envelopes (`InContainerJUnitRunner`
  AND `OutOfContainerFrameworkExtension`, moved out of `junit-testkit`, which is left an attachable
  test bundle holding only the test-only tags) plus the SCR diagnostic; extract the neutral
  `JUnitLauncherCore`; add the `OsgiConnection` abstraction (embedded realised, remote named), the
  start-level lever, and the discipline annotations (isolation / stationary). A committed
  `BulletproofPipeline` played end-to-end proves the socle before ClusterSeed consumes it. Its plan:
  `docs/superpowers/plans/2026-07-05-engine-lifecycle-socle.md`.
* *Increment 2 (ClusterSeed):* the seed as ONE jGiven scenario consuming this socle — the phases become
  `@ScenarioStage`s composed by `@NestedSteps`, the value-DAG (`@Provided/ExpectedScenarioState`)
  replaces `State<I,B>`/`StateBuilder`, and the two live jGiven islands (`SystemdAdapterTopic`,
  `ClusterReadinessTopic`) fold in as phases. A design point settled while planning it: this socle's
  `LaunchedPipelineExchange` is TEST-ONLY — `@SeedRuntime` self-boots (no connection to inject) and
  jGiven's own `ScenarioHolder`/`JGivenExtension` hold the `ReportModel`, so the vertical needs NO
  custom exchange; inbound host-facts ride `ExtensionContext.Store` (the `ConnectionSeeder` pattern),
  outbound is the synchronous harvest return `SeedRun(runbook, outputs)`, and the four OSGi services
  are resolved by the scenario from its connection. It closes with the `SCENARIO_STATE_DAG` staging
  gate. Its design + plan land under `docs/superpowers/`.

== Related — the launcher core it rests on

The launcher is `JUnitLauncherCore`, in the jGiven-FREE `osgi/runtime/junit-launcher` bundle
(with its `DiscoveryStrategy`/`HarvestStrategy` seams + `InContainerJUnitRunner`) — extracted OUT of
`scenario-engine` so a runner-only world installs it alone, without dragging jGiven. `scenario-engine`
depends on it (the runtime owns the runner, the test consumes it — the sound dependency direction,
and the dogfooding promotion of JUnit to runtime scope). It runs a JUnit Platform
`Launcher` inside Felix on a dedicated host-bound thread, engine registered explicitly, the three
OSGi crossings handled; discovery + harvest are injected strategies so both the test envelope
(`*Test` + PASS/FAIL) and the seed (a named scenario + `ReportModel`) reuse one core. Full task
breakdown in the increment-1 plan.
