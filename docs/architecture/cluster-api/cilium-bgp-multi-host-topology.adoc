= Cilium BGP — the multi-host cluster-mesh fabric
:toc: left
:toclevels: 3

== Overview

RKE2 nodes run as Incus containers spread across bare-metal hosts that share one L2 segment
(the physical LAN, `192.168.1.0/24`). Cilium runs in *native routing* mode (no VXLAN/Geneve
encapsulation) and distributes pod routes with BGP: each node advertises its own pod prefix, so a
pod on one host reaches a pod on another directly over the LAN. This document explains that fabric —
Router-ID allocation, the eBGP-to-gateway vs iBGP-mesh choice, and how routing survives
multi-homed nodes.

The concrete *numbers* (per-cluster pod CIDR, BGP `localASN`) are NOT fixed here — they are a
function of cluster identity, owned by link:cluster-addressing-plan.adoc[the Cluster Addressing
Plan]. This doc describes the mechanism; that doc assigns the values.

Each node is *multi-homed*: an internal interface (`vmnet0`, the `10.80.x` InternalIP) and the
physical LAN interface (`lan0`, the `192.168.1.x` address). The two roles are deliberately split —
see <<multihoming>>.

== Router ID — automatic, from InternalIP

Cilium derives each node's BGP Router ID from its Kubernetes *InternalIP* (the `10.80.x`
`vmnet0` address). No manual configuration: uniqueness is guaranteed by distinct node InternalIPs,
and the value is stable as long as the InternalIP is. The Router ID (`10.80.x`) is intentionally
distinct from the *peering address* (`192.168.1.x`, `lan0`) — see <<multihoming>>.

== BGP configuration — two modes

The cilium BGP config is rendered by `CiliumAdvancedManifestsUnit`
(`osgi/domains/manifests/manifests-core/src/main/java/io/seedmatic/rke2lab/manifests/units/networking/CiliumAdvancedManifestsUnit.java`),
which emits the `CiliumBGP*` CRs via cdk8s (an `ApiObject` + `JsonPatch`, a `peerConfigRef` — not a
hand-written config map). It supports two modes; the ASN values come from
link:cluster-addressing-plan.adoc[the addressing plan] (`localASN = 64512 + clusterId`), NOT the
literals shown in older revisions of this doc.

=== eBGP to an external gateway (current)

The cluster peers with the vmnet gateway to integrate cluster routing with the surrounding network.
The rendered shape (values from the addressing plan / `ClusterNetworkBlueprint.GATEWAY_ADDRESS`):

[source,yaml]
----
bgpInstances:
- localASN: <cluster localASN>        # 64512 + clusterId (addressing plan)
  name: control-plane-bgp
  peers:
  - name: gateway-peer
    peerASN: <gateway ASN>            # the fixed fabric gateway AS
    peerAddress: <vmnet gateway>      # ClusterNetworkBlueprint.GATEWAY_ADDRESS
----

=== iBGP mesh across hosts (proposed)

Nodes peer with each other under the *same* AS, exchanging pod routes directly — self-contained
routing across hosts, no external gateway dependency. This variant is *not yet implemented* in
`CiliumAdvancedManifestsUnit` (the rendered config today is the eBGP gateway peer above); it is the
intended shape once cross-host workloads land:

[source,yaml]
----
bgpInstances:
- localASN: <cluster localASN>
  name: control-plane-bgp
  peers:
  - name: cluster-peers
    peerASN: <same localASN>          # same AS = iBGP
    peerSelector:
      matchLabels: { node-role.kubernetes.io/control-plane: "true" }
    transport:
      sourceInterface: lan0           # peer over the LAN, not the InternalIP
----

== How routing survives multi-homed nodes

The split of Router ID (`10.80.x`) from peering address (`192.168.1.x`) is what makes native
routing work across hosts: sessions establish over the *reachable* interface (the shared LAN),
while the Router ID stays a stable per-node identifier independent of any per-host `10.80.x`
isolation.

[mermaid,cilium-bgp-route-flow,svg]
----
flowchart LR
  subgraph A["node A"]
    PA["pod 10.x.0.5"]
  end
  subgraph B["node B"]
    PB["pod 10.y.1.8"]
  end
  PA -->|"1 · dst 10.y.1.0/24"| RA["node A route table<br/>10.y.1.0/24 via 192.168.1.y"]
  RA -->|"2 · over LAN"| LANK["192.168.1.x → 192.168.1.y"]
  LANK -->|"3 · deliver"| PB
----

Each node advertises its own pod `/24` with itself (its `lan0` address) as the next hop; a peer
installs `dst-pod-/24 via <peer lan0>` and forwards over the LAN. Without the LAN interface, peering
would fail whenever the `10.80.x` networks are isolated per host, forcing tunnel-mode encapsulation
— which native routing avoids.

== Prerequisites

* *Kernel modules* on the hypervisor: `ip_set`, `nf_conntrack` (provisioned by ndh —
  `modules/nixos/cilium-kernel-modules.nix`). Their absence was the historical `protocol not
  supported` route-reconciler failure.
* *LAN reachability* between all hosts on `192.168.1.0/24`.
* *Cilium BGP control plane* enabled — `bgpControlPlane.enabled: true` in the cilium
  `HelmChartConfig` (`CiliumConfigManifestsUnit`).

== Verification

[source,bash]
----
# BGP peers (session Up, families exchanged)
kubectl exec -n kube-system <cilium-pod> -- cilium bgp peers

# routes advertised / learned
kubectl exec -n kube-system <cilium-pod> -- cilium bgp routes advertised ipv4 unicast
kubectl exec -n kube-system <cilium-pod> -- cilium bgp routes available  ipv4 unicast
----

== Troubleshooting

[cols="1,2",options="header"]
|===
|Symptom |Check

|Sessions not establishing
|`kubectl get nodes -o wide` — LAN IPs visible/reachable; `ping <peer lan0>`; `kubectl get ciliumnode <node> -o yaml` addresses.
|Routes not advertised
|`kubectl get ciliumbgpclusterconfig -o yaml` / `ciliumbgpadvertisements -o yaml` — nodeSelector/peerSelector match, PodCIDR advertisement configured.
|Packets not routing
|`lsmod \| grep -E 'ip_set\|nf_conntrack'`; `cilium status \| grep Routing` should show `Network: Native`.
|===
