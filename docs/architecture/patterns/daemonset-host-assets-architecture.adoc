= Workload Flox Runtime Delivery (formerly Daemonless Host Assets)
:toc: left
:toclevels: 3

== Overview

Workloads run on the *flox containerd runtime*: an NRI plugin overlays a node's
host `/nix/store` into annotated pods and puts `flox` on their PATH. This document
describes how that runtime — the plugin, its OCI hooks, and the flox *environments*
it injects — is delivered to the node in the *NixOS node-substrate* model.

Delivery splits into two tiers:

* *Foundation (baked, LIVE)* — what is known at image-build time: the NRI plugin
  binary, the OCI hooks, and the host-wide `/etc/flox.toml`. These are nix
  derivations in the `rke2lab-node-base` closure, wired declaratively by
  `nixos/containerd.nix` (`/opt/nri/plugins/10-flox`, `90-nri.toml`) and
  `nixos/flox-runtime.nix` (hooks + `/etc/flox.toml`).
* *Envs (runtime, Flux-delivered)* — the flox environments the plugin injects.
  Each env is a first-class `FloxEnv` CR (a synthesised manifest), reconciled by
  the *flox-controller* (a node-agent DaemonSet) onto each node's own host
  `/nix/store` + GC-roots. Delivering envs as CRs — not baking them — keeps a
  package bump from cold-starting the control node.

[NOTE]
====
*History (dissolved at commit `6e8cd3c28`).* This file used to describe a
*daemonless host-assets subsystem*: a `flox-runtime-installer` DaemonSet that
trampolined pod→host (`DAEMONSET_EXEC_MODE`), materialised verified archive
payloads under `/srv/host/k8s-daemonset.d/…`, and built the shim on the node. The
Java layers that drove it — `FloxContainerdShimLayer`,
`RuntimeDaemonsetScriptPolicyLayer`, `WrapperGoArchiveAssets`, `FloxRuntimeLayer` /
`FloxRuntimeAssets` — and the scripts (`shim-installer.sh`, the
`runtime-daemonset-script-policy` / `flox-runtime-installer-assets` ConfigMaps)
were all *deleted*, along with the `/srv/host` hostPath coupling, when the NixOS
substrate made the shim a baked derivation. That model is gone from the tree; the
current delivery is baked foundation + FloxEnv CRs, below. The general
*host-mutation channel* (a pod that completes durable work on the node) is retained
only as a design for future day-2 host reconfiguration — see
<<retained-extension>>.

The flake inputs are OURS: `flox-nri-plugin` (plugin + hooks) and `flox-controller`
(the `FloxEnv` CRD + the controller); both are baked into the node-base image. The
envs leave the image entirely and become first-class Kubernetes objects.

== The foundation tier (baked)

The runtime *shim* belongs in the node-base closure — every node that runs pods
needs it, so it is not a specialisation:

* `nixos/containerd.nix` resolves `flox-runtime.packages.<system>.flox-nri-plugin`
  and symlinks it to `/opt/nri/plugins/10-flox`; NRI is enabled via `90-nri.toml`;
  the ZFS snapshotter / SystemdCgroup / registries are declarative there too.
* `nixos/flox-runtime.nix` bakes ONLY the flox OCI hooks + the host-wide
  `/etc/flox.toml` policy. The per-env bake (the old `environment.d` envs + their
  GC-roots) is RETIRED — envs are CRs now.

The shim source is a *fork* of flox's containerd plugin, extracted to
`github:seedmatic/flox-nri-plugin` and consumed as the rke2lab flake input
`flox-runtime`; it is built at IMAGE time on the ARM64 build infra
(linux-builder / remote nix-store / cachix), not on the node at runtime. See
link:../nixos-substrate/flox-containerd-runtime.adoc[The flox containerd runtime].

== The envs tier (runtime, FloxEnv CRs)

The `FloxEnv` CRD + the flox-controller are AUTHORITATIVE in their own repo
(`github:seedmatic/flox-controller` → `docs/design.md`); it is pure-k8s and
rke2lab-agnostic. rke2lab only INTEGRATES it:

* *Synthesis* — `FloxEnvManifestsUnit` (in
  `osgi/domains/manifests/manifests-core/.../units/runtime/flox/`) emits the
  workload `FloxEnv` CRs (kdns for networking; the headscale/tailscale/headplane
  mesh family; per debug flavor). Each CR installs its package from the catalog via
  a `floxcatalog:catalog#<output>` ref and declares a `folder` — the GC-root
  category the plugin keys on, typed as the `FloxEnvFolder` enum so the CR folder
  and the consuming pod's annotation prefix cannot diverge.
  `FloxCatalogManifestsUnit` publishes the catalog: a nix flake at the ROOT of the
  dedicated `flox-catalog` git branch, exposed as a Flux `GitRepository` + a
  `FloxCatalog` CR the controller resolves. Flux applies both in an early layer.
* *Delivery* — rke2lab consumes `flox-controller` and `flox-nri-plugin` as flake
  inputs (`…/develop`, green-gated) and bakes their images into the node-base
  image; the controller then reconciles the CRs onto each node.
* *Bumps* — the operator bumps env versions by bumping the flake pins at the ROOT
  of the `flox-catalog` branch, re-locking, and pushing; the controller resolves
  each CR's `floxcatalog:` ref and never re-locks.

The pod-injection annotation keys are a closed vocabulary typed as the
`FloxAnnotation` enum in `manifests-contract` (the single source of the
`flox.seedmatic.io/*` prefixes); the Go readers (the plugin, the controller
webhook) carry their own copies as a cross-repo contract.

== Usage patterns

✅ *DO deliver a workload's flox toolchain as a `FloxEnv` CR.* Add a
`FloxEnvManifestsUnit`-emitted CR (or reuse one) with the right `FloxEnvFolder`,
and annotate the consuming pod with `FloxAnnotation.ENVIRONMENT.forContainer(c)`.
The controller realises it; the plugin injects it.

✅ *DO bump env versions on the `flox-catalog` branch.* Bump the flake pin,
re-lock, push. Nothing rebuilds the node image; the controller re-realises.

❌ *DON'T bake an env into the node image.* That was the interim; a baked env makes
a package bump a cold-start of the control node. Only the shim (plugin + hooks +
`/etc/flox.toml`) is baked.

❌ *DON'T reintroduce a `/srv/host` DaemonSet installer to deliver the shim.* The
shim is a baked derivation. The `/srv/host` hostPath coupling is dissolved.

❌ *DON'T use a string literal for a `flox.seedmatic.io/*` annotation.* Emit
`FloxAnnotation.<CAP>.forContainer(c)` — the enum is the single source shared with
the Go readers.

[[retained-extension]]
== Retained as design — the runtime host-mutation channel

The general pattern this file once documented — a Kubernetes workload that performs
durable mutation ON the node host, post-boot, for things NOT knowable at image-build
time — is RETAINED as a design (not as code) for two remaining needs:

* *day-2 host reconfiguration* (concern-ownership routes "cilium-operator scaling,
  day-2 host reconfig" to a `DaemonSet → Go controller`); and
* *unknown-at-build binaries* — a Flox-injected container that must build a package
  it does not have delegates to the NixOS host's native `nix-daemon` over `ssh-ng`
  (`max-jobs = 0`, never builds locally) — the *remote nix builder* (Part 2 of
  link:flox-store-resolved-runtime-and-builder.adoc[Flox Store-Resolved Runtime]).

Any re-implementation must keep the substrate rules the dissolution established:
no `/srv/host` hostPath, sources resolved from `/nix/store` or the rendered branch
(never copied through a ConfigMap trampoline), and the immutable-code /
mutable-workspace boundary explicit. It is a substrate-compatible successor to the
deleted installer, not a revival of it.

== Troubleshooting

[cols="1,2",options="header"]
|===
| Symptom | Cause / fix

| A flox-annotated pod starts but `flox` is absent / the overlay is empty
| The plugin binary or NRI wiring is missing. Confirm `/opt/nri/plugins/10-flox`
  exists and `90-nri.toml` enables NRI (`nixos/containerd.nix`). Injection is a
  no-op until the plugin is baked.

| The plugin logs "cannot resolve environment `<folder>/<name>`"
| The GC-root `/nix/var/nix/gcroots/flox-runtime/env/<folder>/<name>` is missing —
  the controller has not realised that env on this node. Check the `FloxEnv` CR is
  applied (`kubectl get floxenv`) and the controller's per-node status.

| A folder mismatch — the plugin readlinks a GC-root the controller never wrote
| The CR's `folder` and the pod annotation prefix disagree. Both must derive from
  the `FloxEnvFolder` enum; a string literal on either side is the bug.

| A package bump cold-started the control node
| An env was baked into the image (its version is in the closure, so bumping it
  changes `imageBuildChecksum`). Move it to a `FloxEnv` CR.
|===
