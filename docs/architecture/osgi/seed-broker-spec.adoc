= The seed-broker — a client sows a seed, the crossing is a detail
:toc: left
:toclevels: 3

[NOTE]
====
The design-of-record for the host↔OSGi boundary — the **seed-broker** (module `seed-broker-port`, the
seam; `seed-broker-runtime`, the `DefaultSeedBroker` mechanism; `seed-broker-codec`, the per-realm
codec): a client hands it a seed (a request `Document`) and it sows that seed at the right place, the
host↔OSGi world-crossing being a broker-internal detail the client never sees. This spec describes the
system *as conceived*; the before/after figures show the former shape (BEFORE, N service verbs) versus
the broker shape (AFTER, one door).

*Realised (2026-07):* the seam types, the per-realm codec, the two build-time gates (`REALM_BOUNDARY`,
`SCHEMA_CONCORD`, both `ERROR`); the module rename `world-gateway → seed-broker-port`
(+ `seed-broker-codec`); and the ONE broker door `SeedBroker.sow(Coordinate wanted, Document seed)`
dispatched to `SeedHandler`s by coordinate. Two of the three former verbs are now handlers
(`assess`→`readiness-verdict`, `canonicalize`→`intervention`); `ConsultingService.consult` STAYS a verb
transitionally (its real provider needs `HealthSystem.admit(patient)`, a separate doctor-migration
increment) and folds into the door when that lands — the one item on the broker unification worklist
(§ <<open-extensibility-chantier>>). The host-side migration (§ <<remaining-migration>>) is the other.

*Conceived next (§ <<contribution-and-opacity>>):* the contribution + opacity turn that
makes a domain OWN its vocabulary and renders every `Document` truly opaque to the host. Four moves,
staged: (1) `Coordinate` becomes an *interface* (`slug()`, like `WireEnum`), each domain contributes its
own enum (`DoctorCoordinate implements Coordinate`); (2) `@DocumentContract` binds by `String slug`, not
an enum reference (an interface cannot be an annotation element); (3) the host stops holding domain
wire-record CLASSES — it sows/harvests via the codec's `toMap`/`fromMap` + the broker VOCABULARY, and
when it needs a seed's shape it ASKS the broker (introspection = a `sow` at a meta-coordinate); (4) with
no class crossing, the domain's wire-records leave the seam for a domain bundle. Staged as PALIERS: the
opaque logic is PROVEN at the Pulumi frontier first (§ <<pulumi-frontier-decorrelation>>), then
generalized into the broker — that generalization is what collapses the per-domain seam.
====

== The keystone: crossing worlds is a detail; the client sows a seed

The load-bearing reframe. We are tempted to treat the host↔OSGi seam as *the* subject — classloader
realms, the three natures of a crossing object, seams to system-export. From the CLIENT's view all of
that is broker-internal plumbing. The client does not say "I cross a classloader frontier"; it says
*sow this seed*. Whether the broker sows it by switching into Felix, staying flat, or tomorrow going
HTTP-remote is behind the door — the client has ONE relationship and ONE local signal.

The metaphor names every part: the *seed* = the request `Document`; the *seed-broker* = the exchange
organ (`handle`); *at the right place* = dispatch by `coordinate`; the *terrain* = the provisioned
resources (Pulumi / master); *sows it* = execution, of which the world-crossing is only an internal
detail. This is REST's core promise — the client is blind to the server's implementation — and it is
the remedy to the seam's difficulty: the crossing is HIDDEN behind one door, not made omnipresent.

The five gardening ROLES (commissioner, gardener, soils, tools, cellar) are the model's, defined at
link:gardening-model-spec.adoc[the gardening model] (the design's entry point); the full FR-EN register
lives at link:seed-gardening-lexicon.adoc[the gardening lexicon]. This spec realises ONE of those roles —
the *GARDENER* — so the broker is not a sixth actor but the gardener's incarnation. What that realisation
adds:

* the *GARDENER* is realised as the `SeedBroker` — the one door `sow(coordinate, seed)`, handlers
  collected by Declarative Services (`DefaultSeedBroker`), routing by coordinate, the world-crossing
  hidden behind the door. Transversal know-how, owns no plot; the client requests, the broker acts (REST).
* the other roles are realised ELSEWHERE and only referenced here: the *COMMISSIONER* + *TOOLS* = the host
  (`pulumi-edge`, `seed-master` — wants, launches `pulumi up`, conserves, carries requests speaking only
  gardening); the *SOILS* = the DOMAINS (doctor, cluster — each a `SeedHandler`); the *CELLAR* = the host
  conservation organ (§ <<the-neutral-crud-port-is-a-cellar>>, realised at
  link:host-cellar-realisation-spec.adoc[host Cellar realisation]).

The load-bearing goal of the host migration follows from the roles: *the host speaks only gardening; all
logic that speaks a domain migrates into that domain* (§ <<remaining-migration>>).

=== The germination cascade — why the crossing is NOT symmetric (seed-master)

The client sees one door; the flow BEHIND it is directional, and worth naming because it settles a
tempting-but-wrong idea (that the broker routes freely to a host-side OR an OSGi-side handler,
symmetrically). For seed-master it does not. The seed has ONE origin and germinates in a cascade:

[mermaid]
....

  pulumi(["Pulumi (the driving actor)<br/>sows the FIRST seed"]):::ext
  seedh["host plant<br/>the seed germinates HOST-side<br/>(preflight · bbox · incus — Pulumi-native phases)"]:::host
  newseed["it seeds anew<br/>the host plant produces NEW seeds<br/>(readiness · systemd checkpoints)"]:::host
  osgi["OSGi bloom<br/>those new seeds germinate IN OSGi<br/>(consult the doctor, verify readiness)"]:::osgi
  pulumi -->|"first seed"| seedh
  seedh -->|"germinates, then seeds anew"| newseed
  newseed -->|"cross the seam, bloom"| osgi
  classDef ext fill:#efe6fb,stroke:#8250df;
  classDef host fill:#fde,stroke:#a58;
  classDef osgi fill:#eef,stroke:#88a;
....

*Pulumi sows a seed → it germinates into a plant (host-side) → the plant seeds anew → those new seeds
bloom in the OSGi world.* In the technical model the cascade IS *scenario → sub-scenario*: Pulumi
launches the ROOT scenario (host); it plays its host phases; a phase that needs OSGi *opens a
sub-scenario* (seeding anew) which is *played in-container* and whose `ScenarioModel` grafts back
(`addNestedStep`) — the bloom. "Seed anew" = open a sub-scenario; "bloom in OSGi" = that sub-scenario
played in-container, its model grafted up. Three things this captures that a flat "host, then OSGi"
misses:

* *Single origin.* Pulumi is the first sower — the seed is host-born because the driving actor lives
  host-side (the R4 boot seam, `Pulumi.run`; see the system-context view). The host is not one parcel
  among equals — it is the soil where the first seed germinates.
* *Generation, not transit.* The SAME seed does not cross. The host plant *produces new seeds* — the
  readiness / systemd-adapter checkpoints are born of the host phases, and it is THOSE that cross to
  bloom in OSGi. What crosses the seam is a second generation, engendered host-side.
* *Directional.* Each germination precedes the next sowing; nothing flows back up. So the seam is
  asymmetric BY ORIGIN, which is why the authority asymmetry below (OSGi owns the rich types, the host
  transports) is not a contradiction but the same directionality seen from the type axis: the OSGi
  bloom owns what it grows, the host owns the seed's birth.

So the broker-gardener has, in principle, several parcels (host, OSGi, tomorrow remote) — but for
seed-master the seed is NOT freely routable to either: it is born host-side (Pulumi hands it over) and
only its offspring reach OSGi. Symmetry considered, rejected, and here is why.

== The mental model: REST, in our embedded model

The whole design is one idea: *we do REST, but in our embedded model.* Every decision below is a REST
invariant transposed to an in-process seam — which is why they cohere, and why the design is
forward-compatible with a future remote split (same contract, a different transport).

[cols="1,1",options="header"]
|===
| REST (distributed) | this embedded model

| the API exposes resources/verbs, not the server's internal types | the *ports are services* (verbs), not the records
| the payload is neutral JSON/YAML | the `Document` (a serialized `String` payload)
| the contract is a schema (OpenAPI / JSON Schema), versioned | a *JSON Schema per document type*, semver'd
| the client validates at its edge, blind to server logic | the host validates *structure, not meaning*
| the server is authority over the resource | *OSGi holds the authority*
| an `Accept` / version mismatch surfaces at runtime | a *semver mismatch* surfaces at runtime validation
| *the client discovers HOW to talk by asking the server* (`GET /` index / HATEOAS, `OPTIONS` / OpenAPI) | *the client discovers by asking the broker* — TWO idioms: (a) a coordinate's shape via a `sow` at a meta-coordinate (`OPTIONS`), and (b) HATEOAS — a reaped plant ADVERTISES the coordinates it can be sown at next (§ <<hateoas-the-plant-advertises>>)
| in-process today, on the wire tomorrow — same contract | embedded today, remote tomorrow — forward-compat by construction
|===

The `coordinate` is the path, the `Document` is the body, the schema is the OpenAPI. The day Felix
runs remote, it is the same contract with an HTTP transport instead of a method call.

=== Introspection is the missing REST verb — the server describes itself

This row was the model's missing piece, and its absence is what left the design wobbling. Everything
else said "the client speaks to the broker by one door, the vocabulary stays in the domain" — yet the
client still had to know a document's SHAPE (its fields) from SOMEWHERE. While that shape lived in a
shared compiled type (the seam wire-record), the door was NOT the single source: there was a parallel,
unspoken channel — the class the host compiled against. TWO sources of truth for "how we talk". That is
the wobble.

REST closed this long ago: a client does not compile the server's DTOs — it *asks the server how to
talk*. `GET /` returns the resource index (HATEOAS); `OPTIONS /resource` (or `/openapi.json`) returns
the resource's schema. The server describes ITSELF, over the SAME transport as real requests — not a
compiled contract on the side. Our broker gets the exact same verb, and — the key already established —
it is NOT a new method: it is a META-coordinate. `sow(available, ∅)` reaps the coordinates actually
served (the published handlers — "for real", who has a grower); `sow(shape, {coordinate: X})` reaps
X's projected schema. The broker describes itself through its own single door, exactly as `OPTIONS`
rides the same HTTP transport as `POST`.

This is why introspection is the LOAD-BEARING piece, not a convenience: the paper trial (§
<<contribution-and-opacity>>) showed that de-typing the SOW sites without it would only trade "hold the
class" (compiler-checked) for "hardcode the field names" (silent) — a worse hazard. Introspection is
the CONDITION of opacity, so it removes the parallel channel: the client learns a document's shape FROM
THE DOOR, and the shared wire-record class stops being a source of truth (it can then leave the seam,
§ <<one-seam>>). The schema already exists build-time (`@DocumentContract` + `RecordSchemaProjector`,
consumed by `SCHEMA_CONCORD`); the meta-coordinate is that same projection, offered at runtime through
the door — the OpenAPI endpoint we had described but never served.

=== `@Amendment` — the schema says the SHAPE, the role says WHICH state fills it

Shape answers "what is the FORM of the payload" (a JSON Schema: an `outdir` string, a
`publish` object). It does NOT answer "which of the host's states goes into `outdir`" —
and it cannot: the schema describes the wire-record, it knows nothing of
`BootstrapPaths` and its seventeen roots. That second half is the missing piece a
sower hits the instant it tries to fill a payload from real state.

The answer is the AMONT twin of `@Scion`/`Role`, and it reuses the exact mechanism
already proven aval. Downstream, a domain marks a reaped component with a neutral
horticultural ROLE — `@Scion(Role.FRUIT)` on `consultationReport` — and the host
affixes it by role, never learning the domain's field name. Upstream, a domain marks
an INPUT component with a neutral role of GROWTH-NEED — `@Amendment(Amendment.SOIL)`
on the materialisation-root component — and the host FILLS it by role, from its
provisioning state, never learning the domain's field name. They meet on the role, as
aval they meet on `Role`:

[source,java]
----
@SeedContract("runbook")
public record ManifestsRunbookInput(
    @Amendment(Amendment.FACET)    Facets facets,               // the whole rke2lab:manifests: subtree {publish, debug}, ONE component so the role binds to ONE field
    @Amendment(Amendment.SOIL)     String materializationRoot,  // host fills SOIL from BootstrapPaths
    @Amendment(Amendment.WORKTREE) Optional<Worktree> worktree) {}  // cluster/node identity, the neutral scalars incus reconstructs its topology from

// EACH role fills ONE component, so the fill is uniform — the binder places each value by role:
//   amendment SOIL     <- paths.asStagingView(slot).manifestsRoot()   (SOWN per-consult by incus)
//   amendment WORKTREE <- the cluster/node scalars                    (SOWN per-consult by incus)
//   amendment FACET    <- the rke2lab:manifests: subtree              (CONTRIBUTED by the host, gathered at the door — § the AMEND verb)
----

`Amendment` is a neutral vocabulary of String constants (the twin of `Role`): `SOIL`
(the plot to materialise into), `FACET` (the activation facet — the operator's config),
`WORKTREE` / `IMAGE` (provisioning scalars), more as growth-needs appear. The domain (the
soil) DECLARES its needs by annotating its input record; the amend is filled by role from
whoever OWNS each role's state. A role must name ONE component (the binder rejects an
ambiguous role borne by several — so `FACET` is the single composite `Facets` component
mirroring the yaml subtree, NOT two `publish`/`debug` fields). The `WHICH` — which of the
seventeen roots is `SOIL` — is an explicit host affixation (`manifestsRoot` in staging
view), NOT a name-match derived from the schema: the topology knowledge is the host's,
irreducibly, the same knowledge `IncusResourceBootstrap` carried on main. The schema
VALIDATES the amended payload; the role SELECTS the state.

=== The two natures of a SOIL — intra-world vs CROSSING (the pattern, generalised)

The `@Amendment(SOIL)` above is a soil the host hands DOWN and the scion CONSUMES —
it materialises into the plot and the plot never comes back. Call that an *intra-world
SOIL*: it crosses host→scion once (amont), is spent in-container, nothing returns. Most
soils are this.

But a soil can also be RESOLVED by the scion and read back by the host — a *CROSSING
SOIL*. The incus mounts are the archetype: only the scion knows the container layout
(`HostPathCatalog`, bundle-side) and the staging structure, so it COMPUTES the
mount plan (`{name, source, target}` per mount); the host must read it back to build the
`com.pulumi.incus.Instance.devices(...)`. The host cannot hold the scion's record (a
bundle type does not cross the flat seam — that is the D5 leak), and it must not learn
the domain's field names.

*The pattern: a crossing SOIL rides the AVAL mechanism, not a new contract.* It is
exactly `@Scion`/`@Rootstock` + the domain `SplitReflector` (§ the AVAL split above,
`DoctorSplitReflector`) — the "mechanism the whole opacity turn rests on". The scion
marks its resolved-soil components `@Scion(role)` under a `@Rootstock`; its
`SplitReflector` (OSGi-side, where the record's class lives) decomposes the reaped record
into `{ rootstock → { role → value } }` — FLAT sub-trees (JDK String/Map); the host FETCHES
and NESTS them verbatim, holding no domain class. So:

* *intra-world SOIL* = `@Amendment(SOIL)` — amont, host fills, scion consumes, nothing returns.
* *crossing SOIL* = `@Scion(role)` + `SplitReflector` — aval, scion resolves, host reads flat.

*What the broker KNOWS and VERIFIES.* The broker needs no new machinery to tell the two
apart: the ANNOTATIONS carry it — `@Amendment` marks an amont growth-need, `@Scion`/`@Rootstock`
mark an aval fruit/resolved-soil. A soil that never returns simply bears no aval marker. And
the existing gates already guard it: `RECORD_PURITY`/`CONTRACT_PURITY` keep these wire-records
pure, `REALM_BOUNDARY` forbids a flat class naming a bundle-only type — so a host reading a
scion's record directly (instead of the split flat sub-trees) fails the build. No `CROSSING_SOIL`
gate is needed at N=1; the invariant is already machine-checked by the pair (annotations + REALM_BOUNDARY).

*Corollary for `HostPathCatalog` (and the whole topology).* The realm boundary is a CLASSLOADER
boundary, not a resource one — Felix is embedded in the host JVM, so the scion sees the same
filesystem. So the WHOLE topology is computed OSGi-side, uniformly (it reads better than a host/scion
split): `HostPathCatalog` + `fromLocalWorktree` + the slot + the pure `pathOn` NFS translation all live
bundle-side; the scion produces the resolved mount plan; the host reads it flat via Split and holds no
catalog, no roots. The host keeps only the Pulumi engine (irreducible) + a handful of flat scalars it
hands the scion by `@Amendment` (worktree, cluster, node, automount). No D5 leak, because the
crossing SOIL is flat and `BootstrapConfig` never crosses. See
link:host-cellar-realisation-spec.adoc[host-cellar] § "BootstrapPaths — the WHOLE topology is computed
OSGi-side".

This closes the amont side: Shape gives the form, `@Amendment` gives the mapping, the
sower needs no a-priori knowledge of either the domain's fields or its own state names.

So materializing `shape` is a build in **two pieces**, mirroring the shipped
`SplitCoordinate` trio (coordinate + a domain reflector + broker routing by
`equals`):

. *Foundation, generic.* Add `ShapeCoordinate(domain)` to the `permits` (the
  deliberate one-place edit the sealed interface prescribes), and a
  `RecordSchemaProjector` that emits a JSON Schema from a wire-record's
  `RecordComponents` — the amont twin of `DoctorSplitReflector` (which walks
  `@Scion` components aval). A domain contributes a `@Component SeedHandler` serving
  `new ShapeCoordinate(itsDomain)`, projecting the schema of the wire-record its
  `@SeedContract(slug)` names; the host reaps an opaque JSON-Schema `String`, holding
  no domain class.
+
*Projection engine — victools, wrapped (decided).* The projector does
NOT hand-roll schema generation — we do not re-implement a JSON-Schema generator.
It uses `com.github.victools:jsonschema-generator` (+ `jsonschema-module-jackson`),
which emits Draft 2020-12 and already handles nested wire-records, seam enums,
`Optional` → non-`required`, and constraints. victools ships without a
`Bundle-SymbolicName` (bare MANIFEST, not even an Automatic-Module-Name), so it is
wrapped as its own bundle module on the exact `osgi/runtime/jgiven-wrap` pattern —
`Export-Package: com.github.victools.*`, `Import-Package: *`, embed nothing. Its
transitive tail is already OSGi-ready (`classmate` has a BSN; jackson is already
bundled), so the wrap stamps only the two victools jars and traily nothing. A
hand-rolled projector was weighed and rejected: it would re-cover exactly what
victools does (nested / enum-slug / Optional), for maintenance we would own, to save
a wrap module the repo already builds routinely.
. *Domain, per input.* The runbook needs an INPUT wire-record — the facet of policy
  the scion expects (`@SeedContract("runbook")`, its components the config shape) —
  for the projector to have something to project. This is where the manifests scion's
  activation payload gets a typed home (see
  link:manifests-bdd-spec.adoc[manifests-bdd-spec] § the one config path).

Only piece 1 is broker-generic; piece 2 is what each domain brings. Until piece 1
ships, a sower cannot discover a payload's shape — it must know it a priori, which
is the a-priori coupling the whole introspection turn removes.

==== The AMEND verb — realising the fill-by-role (SHIPPED)

Shape DESCRIBES the input; a third amont verb FILLS it by role, so a sower holds a value under a neutral
role and never names the target's field. `AmendCoordinate(domain)` (in `ValueCoordinate permits`, beside
Shape/Split/Runbook) is the verb; `AmendmentBinder` (module `seed-broker-codec` — its jackson+reflection
home, so an amend reflector needs no schema-generator closure; the twin of `RecordSchemaProjector`, which
stays in `seed-broker-shape` with its victools weight) is the broker-generic role→field bridge, working on
JSON: given a record's
`defaults` and a `{role → value}` map, it binds each offered role onto the `@Amendment` component that role
names (loud on absent/ambiguous). A role borne by MORE than one component is ambiguous to bind by value, so
no wire-record offers one: `FACET` is the single composite `Facets` component (mirroring the yaml subtree),
not two `publish`/`debug` fields. A domain contributes a `@Component` amend reflector
(`ManifestsAmendReflector` serves `AmendCoordinate("manifests")`, binding onto `ManifestsRunbookInput`).

*Amend-filling is MULTI-CONTRIBUTOR — each role filled by whoever OWNS its state, at the same neutral door.*
A role is either PER-CONSULT (derived in-world at the crossing, SOWN by the sower) or AMBIENT (a standing
fact an owner holds, CONTRIBUTED once). incus SOWS the per-consult roles it derives — `SOIL` (the plot it
materialises), `WORKTREE` (the identity it received); the host CONTRIBUTES the ambient `FACET` (the operator
config it read from `rke2lab:manifests:`). The binder already binds a PARTIAL role-map (it rejects only an
undeclared or ambiguous role), so the two fillings MERGE at the door: the sown per-consult roles override
the contributed ambient ones. Two foundation types realise the contribution, both jackson-free port SPIs (a
value is a serialized JSON `String`, per the seam rule):

* `AmendmentContributor` — an owner's standing `{coordinate, {role → value}}`, published as a service.
  Contribution-without-acquaintance, the codebase idiom: OSGi-native owners publish as `@Component`; a
  host-side owner (the root's `FACET`) registers the SAME service through the framework `BundleContext` it
  already holds — the FOURTH `registerService` in `ClusterSeedScenario.Given`, beside the `RunGate` /
  `OpaqueCellar` / `Parcel` it already lays into the world.
* `AmendmentAssembler` — gathers the contributors for a coordinate (`@Reference(MULTIPLE)`, knows none of
  them) and returns their merged `{role → value}` (fail-loud if two contributors claim one role, the broker's
  doubly-served discipline). Its OSGi-side impl lives BESIDE `DefaultSeedBroker`, not
  inside it: the broker's one responsibility is routing coordinates, the assembler's is gathering
  contributions. The contributor reference is DYNAMIC, unlike the broker's STATIC handler roster: the host's
  `FACET` contributor is `registerService`d at RUNTIME from the GIVEN, long after the assembler activated at
  boot — a static reference would capture the boot-time (empty) set and miss it, so the collection is rebound
  live. The amend reflector `@Reference`s the assembler, merges the gathered ambient roles UNDER
  the sown payload, decodes each with its own codec, and binds.

This is where the broker earns its role as the door that RECONCILES two points of view: incus (the first
metier scion→scion) holds a plot under role `soil` and sows `AmendCoordinate("manifests")` then
`RunbookCoordinate("manifests")` — it names no manifests field, offers only the roles it owns, and the door
enriches with the ambient `FACET` it does not. The reconciliation lives at the door, not in the manifests
runbook handler (which receives an already-filled input). The scion input wire-records
carry these amendments: `ManifestsRunbookInput` (its `@Amendment(SOIL) materializationRoot`),
`IncusRunbookInput` (incus's own SOIL, forwarded to manifests), and `BboxRunbookInput` (its
`@Amendment(FACET) Router` — the `{uri, password}` router contact the host joins from `.secrets:lan.bbox`
via `ConfigLoader`'s `secret:` meta and contributes AMBIENT, like the manifests FACET; `BboxAmendReflector`
serves `BboxCoordinate.AMEND` and gathers it at the door onto the input's defaults, so the scion logs into
the Bbox with the real password instead of a hardcoded marker — see cellar-secrets.adoc § bbox transport).
Because bbox carries no per-consult amendment, its crossing opens the amend door via the broker's `serves`
query rather than a non-empty trigger (see § the amend door below). A scion's conserved
harvest is a wire-record too — `BboxHarvest` (the reservation summary bbox stores at the cellar, § the scion
harvests and stores) and `IncusHarvest` (the prep intention incus stores — the image recipe digest + the soil
the tree was cultivated under — that the host fetches to grow the instance, Shape C).

==== Amend integrity — the orphan seam, the loud guard, the phase boundary

The fill-by-role has two mismatch paths, and only ONE is silent. A coordinate reached by a SOW is
routed through the broker, which is LOUD: `DefaultSeedBroker.sow` throws on a coordinate no handler
serves. So a sower's `AmendCoordinate(slug)` typed as a raw literal (incus sowing
`AmendCoordinate("manifests")`) carries NO silent risk — a typo hits the broker and throws; incus
needs no shared slug constant and no dependency on the target's contract. The GATHER path is the
exception: `AmendmentAssembler.gather` matches a contributor's coordinate against the reflector's by
`equals`; a contributor published for a coordinate NO grower serves is silently ORPHANED — its roles
never gather, the amend falls to its defaults, nothing throws. That is the one silent seam.

*BETA — the loud guard closes it generically.* The assembler already fails loud when two contributors
claim one role (the broker's doubly-served discipline); it ALSO cross-checks each bound contributor's
`coordinate()` against the SERVED set — the same `SeedHandler` roster the broker routes on — and
throws on an orphan (`"contributor for a coordinate no grower serves"`). This turns the silent GATHER
path loud for every domain, so a slug divergence is caught at the gather, never swallowed. Consequence:
the slug needs no shared constant to be SAFE — loud divergence replaces compile-time equality. The ALPHA
readability half is `ManifestsCoordinate` — the manifests domain's seed coordinates, declared and owned
in ONE place from one `DOMAIN`, so its growers never diverge as raw literals.

It is an ENUM, like its siblings `BboxCoordinate` / `IncusCoordinate` — the `contract-purity` law admits
only records / enums / sealed ADT / interfaces from a contract module, never a concrete class. But WHAT
the enum holds differs structurally — the coordinate-ownership taxonomy (the two shapes):

* *Enum WITH VALUES — homogeneous value-coordinates* (bbox, incus). A domain that CONSERVES a harvest
  owns the cellar documents it stores — `BBOX_RESERVATIONS`, `INCUS_PREP` — all the SAME kind, differing
  only by slug, and it controls both ends (it serves AND stores them, in-domain). One enum implementing
  `SeedCoordinate`, values by slug, `DOMAIN` private (encapsulated in the values). No magic string.
  A domain that ALSO receives an amended runbook input is a HYBRID: `BboxCoordinate` keeps its
  `BBOX_RESERVATIONS` value AND holds the meta-coordinate CONSTANTS `AMEND` / `RUNBOOK` (below) as
  static fields keyed off the same `DOMAIN` — the reflector serves `AMEND`, the runbook handler serves
  `RUNBOOK`, so the OSGi-side growers never spell the `"bbox"` literal (only the FLAT-realm host does,
  guarded by BETA).
* *EMPTY enum with META-coordinate CONSTANTS — heterogeneous* (manifests). A domain that
  SYNTHESISES-and-GRAFTS — materialises into the soil, stores no harvest (its conservation is delegated
  to the consulter's plot) — owns no value-coordinate, so its enum enumerates NOTHING. It is addressed
  only through the SHARED meta-coordinate types (`AmendCoordinate` / `ShapeCoordinate` / `RunbookCoordinate`),
  which are DIFFERENT record types: an enum cannot hold values of different types, and even forced, enum
  identity-`equals` would not match the RECORD a sower builds (`new AmendCoordinate("manifests")`),
  breaking the broker's `equals`-routing. So the empty enum holds them as typed record CONSTANTS
  (`AMEND` / `SHAPE` / `RUNBOOK`) keyed by one exposed `DOMAIN`. The reflectors serve them, the assembler
  gathers on `AMEND`; a SOWER (incus) and the HOST FACET contributor keep the `"manifests"` literal —
  both run where this bundle-only contract is out of reach (incus does not depend on it; the host is
  FLAT-realm, which the realm-boundary law bars from a bundle package), and BETA guards THAT seam.

The alignment is at the PRINCIPLE (single-source, declare-and-use-in-one-place) and the FORM (both enums);
only what the enum carries differs. ALPHA is a readability win; BETA is the load-bearing guarantee. (When
the unitrepo thesis makes manifest units first-class grown artifacts, manifests gains real
value-coordinates and its enum grows values.)

*Opening the amend door on an unamended crossing.* A scion whose FACET is contributed AMBIENT (bbox's
router, the entry gate) carries NO per-consult amendment, so the host crossing sows an empty trigger.
`Gardening.sow` must still open that scion's AMEND door — else the reflector never runs (no defaults, no
gather) and the runbook decodes from `"{}"`. It decides with `SeedBroker.serves(AmendCoordinate(soil))`:
open the door when the host holds amendments OR a reflector serves the soil; skip it for a soil with no
amend grower (worktree-less domains — a sow there would throw, since `sow` is loud on an unserved
coordinate). This is why `SeedBroker` carries a non-throwing `serves` companion to `sow`: the caller
needs to KNOW a door exists without provoking the throw.

*The phase boundary BETA rests on.* The orphan-check is race-free only if every grower (amend
reflector) is ACTIVE before any contributor binds — so it runs at the GATHER (the consult), not at the
bind. Today the sole contributor is the host's `FACET`, `registerService`d from the GIVEN after
`FrameworkLaunch.embedded().launch()`; the launch drives the framework to its start level (a
`FrameworkEvent.STARTED` await) but does NOT `awaitService` the growers, and SCR activates on its own
thread — so a grower could still be inactive at the instant the contributor binds. The gather, by
contrast, happens deep in the run (after boot, the GIVEN, and DS settling), so both rosters are complete
and the check cannot false-throw. A future OSGi-native (bundle) contributor is NOT launch-sequenced;
it needs a start-level guarantee. `BootPlanner` already pins every bundle to a level BY ROLE (PASSIVE
/ LOGGING / FRAMEWORK_RUNTIME / BUNDLES) — but a grower and a bundle contributor both land at
BUNDLES(4): one layer, no ordering. The rule: when the first bundle contributor lands (a foreseeable
step once Decision 4's artifact-seam lets a contribution read config in-OSGi rather than from Pulumi),
add `START_LEVEL_CONTRIBUTORS = 5` above BUNDLES and route the contributor role there, growers staying
at 4 — the framework then guarantees growers-active-before-contributor-binds. Because *started* (the
framework's start-level unit) is not *activated* (SCR's, on its own thread), this ordering is a
load-bearing OSGi unknown to PROVE, not assume: a `bench` spike — a synthetic grower @4 + contributor
@5 asserting the contributor observes every grower ACTIVE (not merely started) — is its proof ground,
exactly the disposable-Felix remit bench already serves.

[[hateoas-the-plant-advertises]]
=== HATEOAS — the plant advertises what can be sown next (the second discovery idiom)

`OPTIONS` (above) answers *"what is coordinate X's shape"* — but the client must already NAME X. The
REST table lists a SECOND discovery idiom the design had not developed: HATEOAS — the server's response
carries the links the client may follow next, IN the response. Our transposition (settled):
*a reaped plant carries the coordinates it can be sown at next.* The client holds an opaque plant and
learns, FROM IT, what it may re-sow — the exact missing knowledge (*how do I know the coordinate to sow
next?*). Crucially this needs NO new verb: following a link is a `sow` at the advertised coordinate,
exactly as REST HATEOAS follows links with the same `GET`/`POST`, never a new HTTP method per resource.

== The claim

The host world (flat JCL, Pulumi-aware orchestrator) and the OSGi world (bundle classloaders, the
domain models + reasoning) gateway **no data type at all**. They gateway **services** — a port is a
set of verbs — and the data those verbs carry crosses as a **`Document`**, validated by a **JSON
Schema keyed on the document type**. OSGi holds the authority and owns all rich typing; the host
transports. One rule, uniformly applied, closes every boundary leak.

*set of shared service interfaces* (RPC-shaped), conceived as ONE broker door dispatched by
`coordinate`.

[[two-cellars-durable-vs-ephemeral]]
=== Three channels for a crossing fact — decide / persist / render

A fact travelling scion→host takes ONE of THREE channels, each answering a DIFFERENT question, with
zero overlap. Confusing them is what tempts a fact into the wrong carrier (routing a decision through
a tag short-circuits the assessment; routing an ephemeral render path through the Cellar
over-durabilises it).

[cols="1,2,1,1"]
|===
| channel | question it answers | lifetime | carrier

| ASSESSMENT | "must we ACT, and what to materialise?" — the ONLY channel the host acts on | the run's response | verdict / `VerificationResult` → Pulumi
| CELLAR | "where do we START FROM?" | DURABLE, cross-run | `Cellar.store`/`fetch` → a Pulumi resource
| tagMap | "where/how do we RENDER this run?" (non-decisional) | EPHEMERAL, within-run | the graft (ReportModel serialized + rebuilt)
|===

The two lower rows are two CELLARS distinguished by LIFETIME; the `tagMap` IS a cellar SCOPED TO THE
SCENARIO — a `{key → value}` map that rides the ReportModel across the realm. AUDIT:
nothing ephemeral transits the durable `Cellar` today — its uses are all cross-run (doctor
record/ledger, incus/bbox harvests, `CellarStage`'s resume state "where we start from"); the inputs
brought to the soil (the amendments) come from host config / in-world compute, never the Cellar. The
`tagMap` filled a HOLE (the within-run non-decisional fact had no channel), it took nothing from the
other two — which is why the assessment stays the sole DECISION channel.

The choice rule: **a fact reread at a LATER run → the durable `Cellar`; a fact consumed WITHIN this
run → the `tagMap`; a decision the host acts on → the verdict; and a fact crosses AT ALL only if the
host cannot derive it itself.** Routing an ephemeral within-run fact through the `Cellar`
across the realm. The choice rule: **a fact reread at a LATER run → the durable `Cellar`; a fact
consumed WITHIN this run → the `tagMap`; and a fact crosses AT ALL only if the host cannot derive it
itself.** Routing an ephemeral within-run fact through the `Cellar` over-durabilises it (a Pulumi
resource for a value that dies with the run); holding a fact the scion computed on the host
re-derives a convention the scion owns (a single-source-of-truth leak).

The `Cellar` row is itself TRANSACTIONAL (§ the cellar is transactional): `store` accumulates, `commit`
persists at the run boundary. And a fact can be BOTH durable and narrated — the tag then PROJECTS the
Cellar entry (computed from it), never a second capture, so the two renderings cannot diverge. So the
three rows are not exclusive silos: the axis is lifetime + visibility, and a host-tree entry is
committed to the Cellar AND projected as a runbook tag.

Canonical case — `liveRoot` (where the host renders the runbook, § the runbook has a runtime role in
host-cellar-realisation-spec): a WITHIN-RUN path the host consumes right after the graft, whose
`.local.d/<cluster>/<node>` layout convention lives ONLY in incus-core (the whole topology is
OSGi-side) — so the host cannot derive it without re-encoding the convention. → it rides the
`tagMap`, scion→host.

Mechanism (verified, jGiven 2.0.3): a `Tag` serializes with the ReportModel and its value survives
the Writer→rebuild round-trip (keyed in `tagMap` by `type + "-" + value` at model level; the scenario
carries only `tagIds`). BUT `ScenarioGraft.graftUnder` today grafts only the scion's STEPS — for
"take it from the root" to work it must ALSO merge the scion `tagMap` into the host tree (a small,
generic addition; the host then reads `hostTree.getTagMap()` filtered by `type`). The tag stays
NARRATION (it renders in the runbook) — it is not a data smuggler; it carries a within-run meta the
host reads, never a decision input (those are the verdict + the amendment).

The SYMMETRY (deferred): the graft is one-way scion→host. The inverse — the host POSTS on the root
what it brings to the terrain, the scion reads it at sow — is the natural pendant, same map other
direction. But that host→scion sense competes with the `@Amendment` (which has discipline the tag
lacks: a neutral role, a projected schema, the host names no field), NOT with the `Cellar` — so it is
a separate, larger step, not to be improvised alongside the ephemeral read.

[[playing-a-scenario-is-a-sow]]
=== Playing a scion scenario is a `sow` — the runbook handler, not reflection

The host wants a domain's scion PLAYED and its runbook back. The tempting shortcut is for the host to
reach a scenario's execution front-door reflectively — `Class.forName` on the
scion bundle's loader, invoke it, take the JSON. *Rejected:* the host would name a domain type
(a scion scenario class), and reflection lands it inside a world the gardening register has no business
knowing. It also opens a SECOND execution door beside the broker — the one-door invariant broken.

The correct shape needs NO new port type — a `SeedHandler` is already `SeedEnvelope → SeedEnvelope`,
and "play a scenario" is just a `handle()` that PLAYS instead of computes. And it needs NO per-domain
coordinate enum either — a per-domain `RUNBOOK` constant would force the host to name `BboxCoordinate`,
re-corrupting the very decorrelation the broker exists for. Instead, `RunbookCoordinate` is a *value
coordinate* in the foundation seam, the exact twin of `SplitCoordinate`: a record parameterised by a
soil NAME (a `String`), routed by `equals`, so the host names no domain type.

* *the coordinate* — `RunbookCoordinate(String domain)` lives in `seed-broker-port`. The host holds
  only a soil name (`"bbox"`, `"cluster"` — gardening knows a parcel by its soil, never a domain's
  vocabulary) and sows `new RunbookCoordinate(soil)`. This is `SplitCoordinate`'s pattern applied to
  the play-scenario verb: two equal records route to the same handler, the seam names nothing a domain
  owns.
* *the handler* — each scion domain contributes a `@Component SeedHandler` serving `new
  RunbookCoordinate(itsDomain)`, whose `handle(trigger)` plays its OWN scenario in-container (on the
  scenario class's own bundle loader — same loader, legitimate) and returns the serialized
  `RunbookEnvelope` sealed in a `SeedEnvelope`. The handler is now a thin `ScenarioStrategy` over a
  generic body (§ one generic handler, a strategy per domain) — it names only its coordinate, its
  scenario class, and (for an input-bearing scion) how to decode the trigger; the play recipe lives
  once in the engine.

The reflection does not vanish — it MOVES INTO the domain, where selecting its own scenario class on
its own loader is ordinary. The host is left with one door and a soil name:

[listing]
----
  broker.sow(new RunbookCoordinate(soil), trigger)   // one door; soil is a String, no domain type
     → reaps a SeedEnvelope (the runbook as neutral JSON)
     → ScenarioGraft.rebuild(payload) + graftUnder(hostScenario, hostTree, step)   // graft where the runbook is owned
----

So the SOW half of a sow-and-graft caller (link:../bdd/bdd.adoc#clusterseed-scenario-map[the scenario
map]) is `broker.sow` at a neutral `RunbookCoordinate`; the GRAFT half is `ScenarioGraft`, run wherever
the runbook is owned — host-side for the root, in-container for a scion that owns a sub-runbook (the
incus provisioning scion grafts the manifests scion under its own step through the same gesture).
The host never names a scion scenario type (nor its `*RunbookHandler`) nor a `*Coordinate` enum — only
the foundation seam and a soil string. The runbook is the HUMAN-channel output above, now reaped THROUGH the same door as every
verdict.

NOTE: *The host side of the graft is TWO live handles, not one (learnt live).* jGiven
appends the current `ScenarioModel` to its `ReportModel` only when the scenario FINISHES, so mid-run —
inside the WHEN doing the graft — `getModel().getScenarios()` is EMPTY. The scion STEPS therefore
graft into the live current `ScenarioModel` (`getScenario().getScenarioModel()`, the trunk already
carrying the rootstock step), while the scion `tagMap` merges into the `ReportModel`
(`getScenario().getModel()`, whose tag map is live and which the host reads back via `graftedValue`).
Reading the host scenario from `getModel().getScenarios()` mid-run was the "no scenario to graft"
defect — green in every isolated test (they played the host to completion before reading its model),
fatal on the first live run. `ScenarioGraft.graftUnder(hostScenario, hostTree, rootstock, scion)`
takes both handles; `ScenarioGraft` stays report-model-pure, the caller supplies the two.

[[the-scenario-outcome-channel]]
==== How the played model comes back — the `ScenarioOutcome` channel, not a static holder

The handler plays the scenario on `JUnitLauncherCore`, then must reap what the run produced — the
jGiven `ReportModel` (the runbook) and, for a fork-B scenario, the doctor consultations it raised. That
reap crosses a THREAD boundary: the launcher runs the scenario on a dedicated host-bound worker
(§ the three OSGi crossings), and the JUnit engine INSTANTIATES the scenario itself, so neither the
handler nor the front-door holds a reference to the played instance to read its fields.

*The wrong shape it replaces.* Each scenario used to expose its outputs through a pair of `static
AtomicReference` holders — `LAST_RUNBOOK` set at the end of the `@Test`, `LAST_CONSULTATIONS` beside
it — that the front-door read after `launcher.execute`. A cross-membrane static is fragile, and this
one actively MASKED failures: when a scenario threw before reaching the `LAST_RUNBOOK.set(...)` line,
the front-door's `lastRunbook()` NPE'd on the empty holder, hiding the real cause under a "no runbook"
error.

*The channel.* The runbook comes back the SAME way the transaction context goes IN (§ the three
neutral channels): through the launcher session store, the launcher's designed cross-thread channel.
`ScenarioOutcome(ReportModel runbook, List<SeedEnvelope> consultations)` is seeded by
`ScenarioOutcomeExtension` (on `@SeedScenario`, so every scenario wears it) and read back by the
front-door via `ScenarioOutcomeSeed`. The store hop stays IN-REALM — the extension writes and the
harvest reads on the same worker thread, same session, same loader — so the live `ReportModel` is
carried as an object; only the front-door's later `ScenarioJsonWriter` serialisation crosses
scion→host (the realm membrane), exactly as before.

*Harvest-on-failure — the `ReportModel` IS the fail-at-end collector.* The extension reaps the model
in `afterTestExecution`, which fires EVEN when the body failed. jGiven defers a failed step's throw to
scenario-end (a not-ready phase marks its step FAILED and skips the downstream chain, but the `@Test`
still completes), so a FAILED runbook is COMPLETE — every step recorded — and, for fork-B, the
`consultOn*` computation still ran. The masking NPE is structurally impossible now: the runbook is
always seeded. This is why the former `failFast` harvest decorator is DELETED — the front-doors
harvest the FAILED outcome uniformly, and the host driver (`Main`) renders the diagnostic runbook
THEN inspects `getScenariosWithStatus(FAILED, ABORTED)` to fail the Pulumi run: render-then-verify,
never throw-instead-of-render.

* *`ConsultationSource`* — the pull twin of `CellarReceiver`. A fork-B scenario (bbox · cluster ·
  incus-provision · systemd) consults its own doctor and HOLDS the returned envelopes in a field; the
  extension PULLS them (`consultations()`) at the boundary. The other three (root, incus-reconcile
  [designed, not yet wired], manifests) consult no one and do not implement it — the outcome carries an empty list. No push sink,
  no static — the value is read after the body, so a refused row's consultation survives the FAILED
  runbook.
* *`RunbookEnvelope`* — the reap the handler serialises (runbook JSON + consultations) is ONE record
  in the engine's `.container` package (§ one generic handler, a strategy per domain), no longer
  duplicated per domain.
* *A body that never ran surfaces the REAL cause, not a null (hardening).* The outcome
  channel is fail-at-END only for a body that RAN — but a BEFORE-phase failure (test-instance
  post-processing, `@OsgiService` injection, a `beforeAll`) aborts the node before the body, so the
  extension never seeds an outcome. Reading it back then NPE'd on the null, MASKING the true cause
  (this is how a live byte-buddy boot failure first showed only as a downstream NPE). `ScenarioPlayer`
  now registers a failure-capturing `TestExecutionListener` and, on a missing outcome, throws the
  CAPTURED node failure — so the before-phase cause is what the operator sees. `ScenarioOutcomeSeed`
  gained `find` (returns `Optional`, the frontier rule) beside the strict `read`.

[[one-generic-handler-a-strategy-per-domain]]
==== One generic handler, a strategy per domain — the front-door dedup

The shape above left TWO artefacts per domain, near-identical: the `@Component *RunbookHandler`
(cast the cellar, relay the transaction, wrap `InterruptedException`) and a static `*BddScenarios`
front-door (build a `JUnitLauncherCore`, `selectClass`, execute, harvest the `ScenarioOutcome`,
encode a per-domain `RunbookEnvelope`). Five domains × ~115 lines, varying only on THREE axes: the
coordinate, the scenario class, and whether an activation input is decoded from the trigger. The rest
was copy-paste — the classic signal for a generic body parameterised by the variation.

*The collapse.* The play recipe and the handler body move ONCE into the engine's exported
`.container` package (its natural home — it already holds `SeedHandler`, `SeedCodec`,
`TransactionalCellar`, the launcher, jGiven):

* *`ScenarioPlayer`* — the shared play recipe: build the launcher, `selectClass` on the scenario
  class's OWN loader, execute, read the `ScenarioOutcome` back off the session store. It names the
  Jupiter engine (`JupiterTestEngine`) HERE, so the engine bundle owns the launcher machinery — a
  domain no longer carries the `junit-jupiter-engine` dep just to feed a front-door. It returns the
  LIVE `ScenarioOutcome` (the `ReportModel` as an object): the production caller serialises it for
  the realm crossing, an in-container test keeps it live and asserts on the model directly (no JSON
  round-trip — the round-trip was a per-domain `rebuild` the tests now shed).
* *`ScenarioStrategy`* — the three axes a domain varies: `coordinate()`, `scenarioClass()` (bounded
  to `ScenarioPlayer.Playable`, OUR marker every scenario implements — so the bound stays in our
  vocabulary, not jGiven's `ScenarioTestBase`), and `seedFrom(trigger)`. The last FOLDS the input
  fork: a no-input scion leaves the default no-op; an input-bearing scion (manifests,
  incus-provision) overrides it to decode its typed input and route it through the scenario's
  `ScenarioInputSeed` channel.
* *`GenericRunbookHandler`* — `implements SeedHandler, ScenarioStrategy`, abstract. Its `final
  handle()` is the one body: cast to `TransactionalCellar`, compose `seedFrom(trigger)` with the
  `TxIdSeed` + `CellarEntriesSeed` relay, play through `ScenarioPlayer`, serialise the outcome to the
  unified `RunbookEnvelope`.

*Why the domain `@Component` IS the strategy (composition, not a separate injected strategy).* The
scenario class is bundle-private (the founding rule: the host never names a `*BddScenarios` type), so
the naming `@Component` MUST live in the domain bundle regardless. Folding the strategy onto it — the
component `extends GenericRunbookHandler` and answers the three methods on itself — keeps the
piece-count at one irreducible artefact per domain, now carrying ZERO logic, only the three data
answers. There is no multi-strategy per domain, so no `@Reference`-injected strategy earns its keep.

[[the-broker-closes-the-host-osgi-gap]]
=== The broker closes the HOST↔OSGi gap; in-container, a scion resolves by lookup

The broker door exists to close ONE gap: host↔OSGi. The host is flat-classpath and speaks only
gardening, so it cannot resolve an OSGi service or name a domain type — it sows a neutral coordinate
(`RunbookCoordinate(soil)`) and the door reaches the scion. That is the one crossing the broker earns.

Once a scion is playing IN-CONTAINER, it is already in the OSGi world, where naming a domain type and
resolving a service from the registry are ordinary. So a scion resolves ALL its collaborators by
lookup, not by the broker:

[cols="1,2",options="header"]
|===
| the scion needs… | how
| another domain's service (the doctor's `ConsultingService`) | look it up from its own bundle
  registry (`FrameworkUtil`). Domain-to-domain, in-container — NOT a host↔OSGi gap. The consult is a
  service call (`consult(SeedEnvelope) → SeedEnvelope`), not a broker `sow`. Routing a scion→scion
  consult through the broker would be gratuitous — it is not gardening, it is one domain talking to
  another in the world they share.
| the ambient run-condition | look up `RunGate` — a fact of the WHOLE run, published once (its own §
  below).
| the operator-secrets door (read/write `.secrets`) | look up `SecretsGateway` — a host-owned seam the
  GIVEN `registerService`s beside `RunGate`/`Parcel`. The flat host owns `.secrets` (the `ConfigLoader`
  family reads it; `DotSecretsGateway` writes it) and publishes it into the framework it grew, so a
  scion rehydrates an anchor and persists a freshly-established one through a JSON-only door (the ghapp
  registration is its first consumer) without any `.secrets` logic crossing a realm.
| its OWN domain's edge (`BboxReconciler`, `ClusterReadinessContact`, …) | look up the contact from
  the registry — same domain, same world.
|===

So the broker has exactly one job at the scion boundary: the host→scion play (`RunbookCoordinate`).
Everything a scion needs while playing is a lookup. The earlier temptation to route the doctor consult
through the broker was rejected: it is not a host↔OSGi crossing (it is scion→scion, in-container), so
it stays the service verb it always was — consistent with `consult` STAYING a verb (§ the principle
above), not becoming a handler.

[[the-osgi-service-bridge]]
==== The lookup is PUSH-injected, not hand-pulled — the `@OsgiService` bridge

"A scion resolves all its collaborators by lookup" was, at first, a hand-written PULL: every scion
carried a byte-identical triad — `ScenarioRegistry.of(this).require(BboxReconciler.class, "…")`,
`.require(RunGate.class, …)`, `.optional(ConsultingService.class)` — one `resolve*` helper per
collaborator, repeated across all six scions. A service-locator, forced because a scenario is
instantiated by the JUnit engine, NOT by SCR: it cannot carry a DS `@Reference`, so SCR never sees it
to inject.

The bridge closes that gap the DS way, but from the jGiven side: `@OsgiService` marks a scenario
field the `OsgiServiceExtension` (a `TestInstancePostProcessor` on `@SeedScenario`, the twin of the
inbound `ScenarioInputSeed`) INJECTS before the GIVEN, resolving through the same `ScenarioRegistry`
underneath. The scenario now DECLARES its collaborators as fields; the extension fills them. It is the
`@Reference` a Jupiter-instantiated scenario cannot have — the push the engine owns.

* *Uniform `Optional<T>` — the bridge OWNS presence.* Every `@OsgiService` field is an `Optional<T>`,
  initialised to `Optional.empty()`, so NO field is ever null (the null-hygiene discipline holds
  without a `@MonotonicNonNull` guard or a hand-written getter). The field SHAPE is uniform; what
  varies is one attribute.
* *`await` drives resolution, not the field shape.* `@OsgiService` (default `await = true`, the DS
  `@Reference` norm) AWAITS SCR — `require()`, up to the registry timeout — because a delayed DS
  component publishes its service ASYNC to `bundle.start()` (the SCR race a bare `getServiceReference`
  loses); the bridge throws if it never appears, so a required field's `orElseThrow` at the use site
  never fires. `await = false` takes an immediate SNAPSHOT (`optional()`) — the doctor, the
  auth-token edge, empty when a world booted without it. The body unwraps required with `orElseThrow`,
  optional with `map`/`ifPresent`.

Nothing about the RESOLUTION changed — it is still the registry lookup this section describes, still
scion-local, still identical live and in test (only who published the service differs: the live edge,
or a mock the `-bdd-test` registers). What changed is the DIRECTION at the field: pull → push, so the
`resolve*` triad is gone and the scenario reads as a declaration.

== OSGi holds the authority; the host transports (the asymmetry)

The two sides are NOT symmetric. OSGi owns every rich type and all reasoning. The host has *no*
doctor type and *no* doctor mapper — it transports.

[mermaid]
....

  subgraph "HOST transports only"
    cfg["pulumi config to Document"]
    obs["raw probe facts to Document"]
    ctl["reads one control field continue or stop"]
    fwd["forwards DAG Document to pulumi export"]
  end
  subgraph "OSGi authority"

* *Ingress* — the host serializes its host-native facts (Pulumi config, raw probe output) into a
  `Document` and hands it to OSGi. OSGi interprets it into its own records.
* *Verdict* — OSGi answers with a `Document`; the host reads ONE control field, never a typed record.
  The host cannot `== Severity.CRITICAL`, because it holds a string verdict, not a `Severity`.
* *Egress* — OSGi emits its DAG as a `Document`; the host forwards it opaquely to `pulumi.export`.

The asymmetry reaches into the codec too: OSGi owns the `DocumentCodec` as a DS `@Component` (the twin
of `YamlMapper`), the host holds a plain instance (no DS); each realm carries its own jackson and maps
`String` payload ↔ record independently. The rejected symmetric alternative — a rich host-side mapper
rebuilding doctor types — re-creates a doctor vocabulary on the host, the very leak this closes.

[[the-seam-types]]
== The seam types — what actually crosses

The seam module `osgi/foundation/world-gateway` (`type=seam`, system-exported, one shared copy —
renamed `seed-broker` in the conceived form; § <<the-rename>>) holds the entire crossing vocabulary in
package `io.seedmatic.rke2lab.seed.broker.port`:

* *The envelope* — `Document(String domain, String coordinate, String payload)`. The payload is a
  serialized `String`, NOT a `JsonNode` — so jackson never crosses the seam; each realm parses the
  string with its own mapper.
+
[NOTE]
====
`SeedBrokerCatalog` (the `FIELD_CONSULTATION_REPORT`/`FIELD_EXPECTATIONS` constants) was described here
as a single-source-of-truth for shared field names. It is NOT a broker concern — it names PULUMI OUTPUT
KEYS, the storage-frontier leak the § <<pulumi-frontier-decorrelation>> turn removes (the frontier
derives its keys by introspecting the wire-record's components, so no field-name catalog survives in the
seam). Slated for deletion; do not build on it.
====
* *The contributable vocabularies* — seam enums, not loose strings, so the compiler catches drift.
  `Coordinate` is being opened to an *interface* (`slug()`, like `WireEnum`): the six document types
  (`readiness-checkpoint`, `readiness-verdict`, `consultation`, `intervention-request`, `intervention`,
  `visit`) are ALL doctor's today and move to a domain-owned `DoctorCoordinate implements Coordinate`, so
  "publish a handler = publish its coordinates" holds end to end (§ <<contribution-and-opacity>>).
  `Domain`, `Action` (the provisioning control vocabulary the host may name), and `SymptomKind` (the
  routing key, `slug()` ↔ the doctor's `Symptom.id()` in shared kebab-case) each implement the `WireEnum`
  marker (wire form = a kebab-case `slug()`). `WireEnum` is the proof the contributable pattern already
  works — `Coordinate` is the lone type that had not yet followed it.
* *The identity types* — `Checkpoint` (enum: `SYSTEMD_ADAPTER`, `CLUSTER_READINESS`, each carrying its
  slug, derived `resourceName`, and `scenarioTitle`) and `Patient(org, project, stack)` (a stack
  coordinate, not a medical one — `qualifiedName()`). Both worlds hold their own; the checkpoint
  identity is the join key, so the peer verbs pass identity, not payload
  (`reviewDrift(Checkpoint) : void`).
* *The wire-records* — one flat record per `Coordinate`, carrying `@DocumentContract(slug)` (a `String`,
  not an enum reference — an interface `Coordinate` cannot be an annotation element, and foundation must
  not name a domain enum; the `SCHEMA_CONCORD` gate makes a slug that matches no coordinate a RED build,
  so the duplication is gate-guarded, not the silent `clusterApi`-bug hazard). Its `RecordComponents` ARE
  the contract (see the next section). As part of § <<contribution-and-opacity>> these move OUT of the
  seam into a domain-owned `doctor-broker-port`, since the host stops holding their class. The seven:
+

| wire-record | shape / role
| `ReadinessVerdict(Action, reason)` | the verdict; `Action` typed, not a loose slug
| `ReadinessCheckpoint(scenarioId, failed?, override?, recordedAt?, observations)` | the nesting exemplar — holds a `List<ObservationWire>`; two producers (VERDICT + CONSULT) union into it, so every field beyond `scenarioId` is `Optional`/`List`

slot (`Map`/`List`), for which the projection emits an open `object`/`array` — the contract is "this
slot is a structure", its inner shape owned where it is produced. The reader classes that reconstruct
those inner graphs (`ConsultationReportReader`, `ExpectationReader`, `InterventionReader`,
`MedicalRecordReader`) are bundle-internal, OSGi-side.

* *The host READ ports* — the Layer-1 seams the host implements so OSGi reads the stack history
  WITHOUT interpreting it. A `doctor.records` type NEVER crosses — the typed record (`Visit`,
  `InterventionLedger`) is rebuilt OSGi-side FROM the opaque blobs, on the far side of the membrane,

== The contract: a wire-record per coordinate, the schema projected from it

A `Document` payload is untyped text; without a contract we would trade a type leak for silent schema
drift. The contract is the **wire-record per `Coordinate`** — a flat record (scalars, `List`, nested
wire-records, seam enums; no jackson annotations) carrying `@DocumentContract(slug)`. Its
`RecordComponents` ARE the contract: the JSON Schema is a **build-time projection** of them, never
hand-written — no `FIELD_*` string catalog to keep in step. The wire-record *type* never crosses; only
the serialized `String` payload does, mapped record↔`String` by each realm's own `DocumentCodec`. The
codec also exposes `toMap(record)` / `fromMap(map, type)` (record ↔ opaque `Map`) and
`decode(String)→JsonNode` (opaque tree): these are how the HOST reads a plant BY KEY and assembles a
seed WITHOUT the class — the opacity path § <<contribution-and-opacity>> generalizes.

The codec (`osgi/foundation/seed-broker-codec`, package
`io.seedmatic.rke2lab.seed.broker.codec`) registers its jackson modules EXPLICITLY (never
`findAndRegisterModules`, so it stays clear of the `ServiceLoader<Module>` surface): a custom
`WireEnumModule` (maps every `WireEnum` ↔ slug generically, so seam enums carry no jackson
annotation), a `JavaTimeModule` (ISO-8601 `Instant`), and `Jdk8Module` (`Optional<T>` → an absent key,
dropped from `required`). It carries a `withValidation(boolean)` switch, OFF in the embedded build
(see § <<remaining-migration>>).

=== Build-time is the load-bearing contract check (we build on one codebase)

We are *embedded*: the host and the OSGi exec-jar build from the same codebase, in one reactor. So the
contract is enforced where that fact lives — at build time, by the `SCHEMA_CONCORD` staging gate
(alongside record-purity / spec-coverage / instance-discipline / realm-boundary / duplicate-realm).
It asserts every `Coordinate` has a wire-record, that each `<slug>.schema.json` validates against the
JSON-Schema meta-schema, and that the schema's properties concord with the record's components. The
gate lives in both `StagingGate` enums (the annotation module `osgi/foundation/domain-annotations` and
the ASM mirror in `maven-embed-staging-ext/staging-extension`) and is at the locked `ERROR` default.
Because the two worlds ship together, their contract cannot drift in version — the reactor guarantees
the pairing.

=== Runtime validation is designed, but YAGNI until remote

Runtime `Document` validation is *designed* but *deferred (YAGNI)* — it earns its keep only when the
host and the OSGi exec-jar are deployed or versioned **separately** (a remote split), when a semver
mismatch becomes possible. The `DocumentCodec.withValidation(boolean)` switch reserves its shape:

* *OSGi side* — validation carried by a **fragment** that attaches to a domain's bundle and validates
  that domain's `Document`s (the proven fragment-contribution pattern). Absent in the embedded build;
  present when wanted.
* *Host side* — **off by default, on only when OSGi is configured remote**. In the embedded build the
  OSGi mapper that reads the `Document` is the implicit validator (a missing field breaks there). When
  remote, the host validates *structure, not meaning* at its edge — checks fields and types against the
  schema (which travels as data over the wire), never interprets what a value *means*. Validating shape
  is not holding a type; the host stays blind to the vocabulary, exactly as a REST client validates
  JSON without owning the server's logic.

Rejected: contrat-A (opaque Document, no schema — silent drift); contrat-B (a shared `wire` DTO bundle
— re-introduces a shared data type).

== The two units: domain owns the mapper, document type owns the schema

Two instincts ("schema per domain" vs "schema per document type") were each right about a *different*
unit. They form a hierarchy matching `Document(domain, coordinate, payload)`.

[cols="1,2,2",options="header"]
|===
| axis | unit | governs

| ownership / code
| the DOMAIN
| one `DomainDagMapper` `@Component` per domain, collected by `@Reference(cardinality=MULTIPLE)
  List<DomainDagMapper>` (the same DS mechanism as the `List<Specialist>` roster). The domain owns its
  translation.

| contract / validation
| the DOCUMENT TYPE (the `coordinate`)
| one JSON Schema per type, anchored by coordinate (not per-domain), at
  `doctor-core/src/main/resources/schema/<slug>.schema.json`. A domain owns N document types, hence N
  schemas.
|===

So `domain` = ownership, `coordinate` = type = schema key. A new domain plugs in additively: one more
`@Component`, its own schemas, no gateway change.

[[two-kinds-of-coordinate]]
== Two kinds of coordinate — the domain's vocabulary vs the gardener's

The moment a SECOND coordinate turned out to be a record parameterised by a domain string
(`RunbookCoordinate`, joining `SplitCoordinate`), the pattern stopped being a one-off and became a
CATEGORY. There are exactly two kinds of `SeedCoordinate`, and the split is the model's decorrelation
made structural:

[cols="1,1,1,2",options="header"]
|===
| kind | shape | routed by | whose vocabulary
| *domain coordinate* | an enum constant a domain declares (`DoctorCoordinate.CONSULTATION`) | identity
  (the constant) | the DOMAIN's — its own metier verbs; naming one means naming a domain type
| *value coordinate* | a record parameterised by a soil name (`SplitCoordinate(domain)`,
  `RunbookCoordinate(domain)`) | `equals` (two equal records route together) | the GARDENER's — a
  generic verb sown toward ANY soil, the host holding only a soil `String`, naming no domain type
|===

*Why this matters, and why the two sides are ASYMMETRIC by intent:*

* The *value* side is a CLOSED set — it is the gardener's whole vocabulary, and a gardener has finitely
  many generic gestures ("split this", "play this soil's runbook"). So `ValueCoordinate` is a `sealed
  interface … permits SplitCoordinate, RunbookCoordinate`: adding a verb is a deliberate act (extend the
  `permits` list, reviewed in one place), never an accident buried in a domain. Everything the host may
  sow that is NOT a domain's own coordinate is exactly one of these — enumerable, and provably pure
  gardening (the host constructs `new X(soil)`, never a domain type).
* The *domain* side stays OPEN — `SeedCoordinate` is an unsealed root a domain implements freely
  (`DoctorCoordinate implements SeedCoordinate`), because "a domain contributes its coordinates without
  editing the center" (§ <<contribution-and-opacity>>) is the whole extensibility thesis. Sealing the
  root would break it.

So the hierarchy is three levels, one branch closed:

[listing]
----
SeedCoordinate            (interface — the concept: slug() + domain(); OPEN root)
 ├── ValueCoordinate      (sealed — the gardener's vocabulary, routed by equals)
 │    ├── SplitCoordinate(domain)      slug "split"
 │    └── RunbookCoordinate(domain)    slug "runbook"
 ├── CellarCoordinate     (foundation infra enum — the cellar's OWN keys, owned by no domain)
 │    └── RUN_PROVENANCE               slug "run-provenance"  (the fil d'Ariane root)
 └── <domain enums>       (DoctorCoordinate.…, routed by identity — the domain's vocabulary)
----

This is what keeps the frontier pure jardinerie: the host reaches a scion through a value coordinate
(`RunbookCoordinate`) and never names a domain enum; a domain reaches another domain through that
domain's coordinate (`DoctorCoordinate.CONSULTATION`), OSGi-side, where naming a domain type is
ordinary.

[[contribution-and-opacity]]
== Contribution + opacity — a domain owns its vocabulary, the host holds none of it

The shipped broker collects `SeedHandler` `@Component`s by DS and dispatches by coordinate — the domain
already contributes its LOGIC and its own encode/decode (each handler holds a `DocumentCodec` and knows
its own wire-records). Two things are NOT yet contributed, and closing them is what makes a `Document`
truly opaque to the host:

* *the coordinate* — `Coordinate` is a central enum; a domain declares which coordinate it serves but
  cannot DEFINE one. It becomes an *interface* (`slug()`), exactly as `WireEnum` already is; each domain
  ships its own (`DoctorCoordinate implements Coordinate`), and `@DocumentContract` binds by `String
  slug` (§ <<the-seam-types>> / the contract section). Verified safe: no prod code needs the closed set
  (no `values()`/`valueOf`/exhaustive `switch`); only a test used `Coordinate.parse`.
* *the class the host holds* — today the host CONSTRUCTS wire-records to sow (`new ReadinessCheckpoint`,
  `new ObservationWire`, `new InterventionRequest`) and DECODES them to harvest
  (`decode(doc, Consultation.class)`). That is the last tie binding the host to a domain type.

The cure is one mechanism, applied at the client: the host holds only the *vocabulary* (the coordinate
+ the field names), never the class. It sows by assembling a `Map` → `Document` (via `toMap`/the opaque
tree) and harvests by reading the plant BY KEY (`v.path("action")`). The DOMAIN holds the class — inside
its handler, `fromMap(seed)` / `toMap(plant)` — because it contributed the handler.

=== Introspection is asking the broker — a `sow` at a meta-coordinate

Assembling a seed as a raw `Map` would replace "hold the class" (compiler-checked) with "hardcode the
field-name strings" (silent) — a WORSE hazard. The resolution (the keystone of the opacity turn): the
host does not hardcode field names; when it must build or find something in an opaque `Document`, it
ASKS THE BROKER. The domain — which knows the schema, contributed WITH the handler — answers. And since
the door is already `sow(Coordinate wanted, Document seed)` routed by `wanted`, "what can you grow, and
what is the seed's shape?" is ITSELF a `Document` sown at a META-coordinate — *no new interface method*.
The broker becomes self-describing through its own single door.

[mermaid]
....
flowchart TB
  host["HOST — holds no class, no hardcoded keys"]
  broker["SeedBroker.sow(wanted, seed) — the ONE door"]
  meta["meta-coordinate handler (the seed's shape)<br/>knows the schema, contributed with the domain"]
  dom["DOMAIN handler<br/>fromMap(seed) → logic → toMap(plant)"]
  host -->|"sow(shape, {coordinate: 'readiness-checkpoint'})"| broker
  broker -->|route by wanted=shape| meta
  meta -->|"the seed's shape (a Document)"| host
  host -->|"sow(readiness-verdict, the built seed)"| broker
  broker -->|route by wanted| dom
  dom -->|"plant Document (opaque)"| host
  classDef good fill:#d4f4dd,stroke:#2e7d32;

....

This is why the per-domain seam can fall entirely (§ <<one-seam>>): the last thing tying the host to a
domain — knowing a wire-record's fields — becomes a question answered through the door, by the domain
that contributed the handler. The wire-records then leave the seam for a domain bundle
(`doctor-broker-port` becomes a domain API, not a `type=seam`). Open at realization: the meta-coordinate's
name + who serves it (the broker itself, or a foundation handler reflecting each domain's
`@DocumentContract`).

[[pulumi-frontier-decorrelation]]
== The Pulumi-frontier decorrelation — the opacity proof ground

The same opacity logic is PROVEN first at the easiest frontier — host↔Pulumi — because it is already
half-opaque and pulls no new machinery. Today two sites LEAK: `SystemdAdapterResource` decodes a
`Consultation` and re-routes `.consultationReport()`/`.expectations()` to two Pulumi keys (write), and
`StackMedicalRecordJournal` reads those keys back into a `VisitWire` (read). The two leaked names —
`SeedBrokerCatalog.FIELD_*` (foundation) and `ConsultationReport.OUTPUT_KEY`/`Expectation.OUTPUT_KEY`
(doctor-records) — mean the DOMAIN carries the name of Pulumi storage slots. That is the constraint this
turn removes: *Pulumi's storage shape must not transpire into a domain.*

The finding: the "common contract" the frontier needs already EXISTS — it is doctor's own aggregate
model. `Patient(org,project,stack)` = a stack; `Visit(version,when,…)` = a stack update; a
`ConsultationReport` (one per checkpoint) = a resource; a sub-tree the `Visit` aggregates = an output.
The two-key split is not a Pulumi need nor legacy — it is `Visit`'s own two lists (`reports` +
`expectations`). Pulumi merely REALIZES that shape.

So the frontier stops decoding-and-sorting — but it does NOT reflect on the wire-record itself (that
would make it HOLD the seam class, the tie § <<contribution-and-opacity>> removes). Introspection here
is the SAME "ask the broker" mechanism: "split this envelope into its addressable pieces" is a `sow` at a
META-coordinate. The REFLECTION happens OSGi-side, in the meta-handler, where the wire-record's class is
loaded (its own realm) and the markers are declared — the runtime twin of the build-time
`RecordSchemaProjector`.

The markers, settled — TWO role annotations, named for what a component IS, not a verb (an
annotation is a role, like `@Column` not `@Persist`):

* *`@Scion`* (the rename of the former `@Graft`) — marks a wire-record component that is an addressable
  sub-tree to be filed verbatim (the scion grafted onto the stored tree). It supplies the FIELD, so the
  frontier hardcodes none.
* *`@Rootstock`* (its twin) — marks the component that is the RECEIVER's identity (the join key, e.g.
  `scenarioId`). It supplies the RECEIVER, so the frontier hardcodes no resource name either.

Roles, decided deterministically (reflection lives where the class lives): the DOMAIN *declares* `@Scion`
+ `@Rootstock` on its wire-record; the META-HANDLER *reflects* them OSGi-side and returns the scions
grouped under their rootstock (`{rootstock → [scions]}`, opaque Strings); the FRONTIER *asks* (a `sow` at
the `SplitCoordinate` meta-verb — renamed from `GraftCoordinate`, since its role is "split the envelope",
not "give me the grafts") and *executes* — nests each scion under its rootstock resource, transporting the
payload opaque. This satisfies BOTH constraints at once: Pulumi never transpires into the domain (markers
+ reflection are OSGi-side), AND the host holds no wire-record class and hardcodes NO name — not a field
(`@Scion` gives it), not a resource (`@Rootstock` gives it). `SeedBrokerCatalog` + both `OUTPUT_KEY` die.
It is ONE mechanism (ask the broker to split), applied first here (the Pulumi frontier), then generalized
to sowing — no throwaway local reflection. Rejected: the frontier reflecting locally (holds the class);
the convention "a `List` component is a slot" (too implicit — a future non-output list would break it,
against the determinism discipline); putting the markers on `SeedHandler` (re-introduces storage
vocabulary into the domain contract — the handler stays `Document → Document`, backend-blind).

The relation crosses ASYMMETRICALLY (settled): on WRITE the frontier NEEDS it — a Pulumi output is
physically nested under a resource (`registerOutputs` is called on a `ComponentResource`), so the split
returns `{rootstock → [scions]}` and the frontier nests correctly; on READ it does not — `outputsNamed`
collects by coordinate across resources and flattens, and the DOMAIN re-associates by the rootstock VALUE
(`scenarioId`) OSGi-side. And the container FOLLOWS the harvest's nature — a rooted plant → a per-resource
output (a *pot*); a standalone value → a top-level `export` (a *vase*, which "trips on array-valued
outputs", so the nature dictates the legal mechanism); an append-only timeline → stack history (a
*fridge/cellar*). See link:seed-gardening-lexicon.adoc[the gardening lexicon] for the full register.

=== The stack is an envelope store; a stored envelope re-sows; CRUD addresses the SHELL

The frontier's job, stated at the storage level (settled): *the Pulumi stack is a store of
sealed envelopes.* The frontier writes a `SeedEnvelope` verbatim, later re-reads it, and a re-read
envelope is a SEED again — `sow → plant → (stored in the stack) → seed`, the horticultural cycle closed.
This is the SAME "ask the broker for the slot names, transport the payload opaque" mechanism, seen from
the storage axis: the frontier does CRUD on envelopes it never opens.

The precision that keeps it opaque — a `SeedEnvelope(domain, coordinate, payload, trail)` has a SEALED
part and CLEAR parts, and CRUD touches only the clear ones. The SHELL (`domain`, `coordinate` — neutral
`String`s) is what the frontier addresses BY; the `trail` (its fil d'Ariane, see <<fil-d-ariane>>) is a
CLEAR sibling of the shell; the PAYLOAD is sealed, never read. Today's leak is that storage addresses by
a DOMAIN FIELD name (`consultationReport`, via `outputsNamed(key)`); the cure is that the storage key
becomes the COORDINATE (the shell), so the frontier files and finds by shell, never by field.

[mermaid]
....
flowchart TB
  subgraph create["CREATE — file a plant"]
    c["output named = coordinate slug<br/>value = the sealed envelope payload"]
  end
  subgraph read["READ — harvest by coordinate"]
    r["collect by coordinate slug<br/>a list of opaque envelopes<br/>one per rootstock (cross-resource)"]
  end
  subgraph update["UPDATE — append a history entry"]
    u["a new up() files a new envelope<br/>stable resource name<br/>the timeline IS the update log"]
  end

Read the four operations: *CREATE* files one envelope under its coordinate slug, payload verbatim — no
`FIELD_*` split, the write frontier reads the graft coordinates the plant advertises (§
<<hateoas-the-plant-advertises>>) and files each under its own coordinate. *READ* collects by coordinate,
not by field — today's `outputsNamed("consultationReport")` becomes `outputsNamed(<coordinate-slug>)`;
the cross-resource collection (one element per rootstock) is unchanged, returning a list of opaque
envelopes. *UPDATE* is already opaque — a new `up()` appends a history entry under the stable resource
name; the timeline is the update log. *DELETE* is `withdraw` — take one coordinate's case out; it is no
longer there until re-stored (correction: the earlier "DELETE n/a, append-only" was an USAGE —
the doctor's — mistaken for a LAW of the cellar; see § the fridge below). The one mechanical change that
makes CRUD opaque is that `StackSnapshot.outputsNamed` stops being keyed on a domain field and starts
being keyed on a coordinate slug — that single reshape kills both leak names (`SeedBrokerCatalog.FIELD_*`,
the `OUTPUT_KEY` constants). The stored unit is the sealed payload `String` under a slot name the broker
supplied: store the sealed String, return the sealed String, the name comes from the plant.

[[fil-d-ariane]]
==== The fil d'Ariane — a value's lineage rides CLEAR on the envelope

A stored value should be traceable back to the git commit it was cultivated from — and for a SEALED
value, traceable WITHOUT the passphrase (the whole point of secured-value traceability: you audit
*where a secret came from* without reading the secret). So the lineage cannot ride inside the sealed
payload; it rides as a CLEAR sibling on the shell.

*The types (all `seed-broker-port`, seam-owned, flat-composed — no bundle type leaks).*

* `Breadcrumb` — a SEALED interface `{ String domain(); String coordinate(); }`: ONE link of a
  path-to-origin, naming WHERE the link sits. Two shapes descend from it, one mechanism:
** `SourceCrumb(String domain, String coordinate, String sha, boolean dirty)` — the CELLAR crumb: a
   value's source coordinate (the cellar coordinate it was filed under) PLUS the git source it was
   cultivated from. The git fields are RAW strings, deliberately NOT a domain `Provenance` (the seam
   depends on no domain); the worktree soil projects its `Provenance` into a `SourceCrumb` at the seam.
** `Crossing(String domain, String coordinate)` — the SCENARIO crumb: a bare crossing a grafted
   failure grew through, no git provenance (the `ScenarioGraft` prepends one per graft level). The same
   `Trail` mechanism, one level up: the cellar traces a VALUE to its git source, the graft traces a
   FAILURE through its crossings.
* `Trail(List<Breadcrumb> breadcrumbs, Reach reach)` — the CLEAR per-value metadata the frontier reads
  without the passphrase. It carries TWO independent things: the `breadcrumbs` path-to-origin, root-first,
  immutable (`push` appends leaf-ward as the cellar descends, `prepend` roots-ward as a grafted failure
  returns up the chain); and the producer-declared `reach` (below). It is the fourth field of
  `SeedEnvelope`, CLEAR, outside the sealed payload.
* `Reach` — a producer-declared enum `{ OPERATOR_ONLY (default), IN_CLUSTER }` naming WHERE a value is
  consumed, declared *at the seal* by the scion that harvests it (the same "re-declare where born"
  discipline as `Sensitivity`: only the producer knows, at design time, that e.g. the incus identity must
  be readable by the in-cluster render). It is ORTHOGONAL to the breadcrumbs: they say where a value CAME
  FROM (origin lineage), `reach` says where it must GO (destination/audience). It rides on the `Trail` — the
  clear metadata carrier — so a consumer can filter SEALED entries by reach WITHOUT the passphrase. The
  `Trail`'s compact constructor defaults an absent `reach` to `OPERATOR_ONLY`, so durable coquilles filed
  before this field round-trip unchanged; `withReach(Reach)` returns a re-stamped copy.
* The sealed `Breadcrumb` carries NO jackson annotation (the seam has no third-party dependency): the
  polymorphic type-info is configured ONCE in `SeedCodec` (a `@kind` mixin), and the host's
  `PulumiCellar` DELEGATES its trail (de)serialization there rather than to a bare mapper — so every
  realm resolves a crumb back to its concrete shape from the one config. `Reach` is a plain enum on the
  `Trail` record, so it (de)serializes with the trail through the same delegated path, no mixin needed.

*Declaring + consuming `reach` — the SSOT is the producer, the consumer is manifests.* A scion declares
reach through a `Cellar.store(parcel, coordinate, value, sensitivity, reach)` overload (default
`OPERATOR_ONLY`), and `ScenarioCellar.store` folds it into the stamped trail
(`trailFor(...).withReach(reach)`). So the marker is defined ONCE, at the harvest — no central registry of
"which cases go in-cluster" to keep in sync with the reveals. The consumer is the manifests render: at the
grow it reads the durable `OpaqueCellar.fetch(parcel)` (opaque envelopes, trails CLEAR), filters
`env.trail().reach() == IN_CLUSTER`, and extracts those STILL-SEALED envelopes into a branch asset — the
symmetric twin of the `NODE_BOOTSTRAP`-annotation extraction the exploder already does on rendered
documents (see <<in-cluster-cellar-asset>>). The in-cluster render, whose durable cellar is the black-hole
`EphemeralCellar`, reads that asset back through a read-only cellar so its reveals resolve the same sealed
materials the operator sealed — instead of pruning the branch secrets it cannot re-derive.

*The accumulation — the crossing PATH, realised by the EXISTING transactional inheritance.* The
`RUN_PROVENANCE` foundation coordinate carries a `Trail` — the run's provenance PATH — not a lone
`Breadcrumb`. The first crossing (the worktree soil) plants its ROOT: a one-crumb `Trail([git-head])`.
`ScenarioCellar.store` reads that path back from its own overlay and stamps every value's trail
`path.push(here)` — `here` carrying the same git source, so each link is a complete source coordinate.
The path GROWS per crossing: when a scion is sown, `ScenarioCellar.entriesEncoded(sownChild)` appends the
child's crossing crumb (`SourceCrumb(childDomain, "runbook", rootSha, rootDirty)`) to the `RUN_PROVENANCE`
entry as it descends — so a value stored one sow deep carries the FULL route `root → parent → … → here`,
not just `[root, here]`. This rides the EXISTING descent (the entries fold up at the graft and descend to
the next crossing as *inherited* entries) and the SINGLE generic choke-point (`GenericRunbookHandler`,
which knows the sown `coordinate()`), so no per-domain handler changes. A store filed before the root
exists gets a lone self-link with an empty sha, a legitimate pre-provenance root; the `RUN_PROVENANCE`
declaration itself carries no lineage (it IS the root — its path lives in its PAYLOAD, its own trail is
empty).

*Reading it.* `Cellar.trailOf(Parcel, SeedCoordinate)` returns the current value's `Trail` off the
envelope — no decode, no reveal, so a SEALED value's lineage reads without the passphrase. A default
(empty) on `Cellar`, overridden by `ScenarioCellar` (the overlay, with a DURABLE fallback when the
run's write set is silent on the case) and by `CodecCellar` (the durable read path, reading the trail
off the opaque envelope the backend hands back). It is a capability, not a core verb.

[[in-cluster-cellar-asset]]
==== `reach` in practice — the in-cluster cellar asset (the branch-secret prune, closed)

*The problem it closes.* The steady-state manifests render runs IN-CLUSTER, and its durable cellar is the
black-hole `EphemeralCellar` (`seed-bdd`) — stores nothing, reveals nothing. So a reveal of a value the
OPERATOR sealed at the grow (into its `PulumiCellar`) returns empty in-cluster, unless that same run
re-sealed it into the overlay. Two branch secrets are exactly in this trap: `IncusIdentityCase.INCUS_IDENTITY`
and `ClusterPkiCase.WORKLOAD_CLUSTER_CAS` — sealed operator-side (host-world incus creds / the operator sops
key inventory), rendered ON THE BRANCH sops-encrypted (NOT `NODE_BOOTSTRAP`), and referenced by the CAPI CRs'
`secretRef`. A secret-blind in-cluster re-render finds no material, emits no Secret → Flux PRUNES the ones
the operator grow had populated → CAPN loses its `secretRef` and cannot authenticate to incus.

Everything else stays put by DEFAULT: the bootstrap materials (github-app, replicator, admin kubeconfig,
cluster-issuer-CA, sops-age, signing-key, server-manifests) render onto the `NODE_BOOTSTRAP` lane (applied
node-side at the grow, NEVER on the branch), so their `reach` is `OPERATOR_ONLY` — ignored in-cluster by
ABSENCE of the mark, never pruned (they were never branch resources). `OPERATOR_ONLY` is the fail-closed
default: a new sealed secret cannot leak to the branch asset unless a producer deliberately marks it
`IN_CLUSTER`.

*The mechanism (manifests owns it — the seam only carries `reach`).* At the grow the render reads the
durable `OpaqueCellar.fetch(parcel)` (opaque envelopes, trails CLEAR), keeps those with
`env.trail().reach() == IN_CLUSTER`, and writes the STILL-SEALED envelopes into a branch asset (named to
match the `.gitattributes` sops filter so the git-sops clean filter age-encrypts it at commit). This is the
symmetric twin of the `NODE_BOOTSTRAP`-annotation extraction the exploder already does on rendered documents.
In-cluster, the git-sops smudge filter decrypts the asset on checkout, and a READ-ONLY `OpaqueCellar` backed
by it REPLACES the `EphemeralCellar` as the durable read-side: `fetch(parcel, coordinate)` serves the exported
envelopes, so the reveals resolve the same sealed materials the operator sealed. The transactional overlay
still layers on top, so a this-run in-cluster seal (from `.secrets`) still wins over the asset.

❌ Do NOT special-case "ignore bootstrap in-cluster" with a negative test, and do NOT keep a central registry
of in-cluster coordinates alongside the reveals. ✅ The producer declares `reach` at the seal (SSOT per
value); the extraction filters by the mark; absence of the mark IS the ignore. The two `IN_CLUSTER` seals are
`IncusIdentitySealScenario` (`INCUS_IDENTITY`) and `ClusterPkiSealScenario` (`WORKLOAD_CLUSTER_CAS` only — its
sibling `ADMIN_CREDENTIALS`/`CLUSTER_ISSUER_CA`/… stay `OPERATOR_ONLY`).

[[durable-coquille]]
*The durable coquille (integration session, DONE).* The fil d'Ariane is realised at the TRANSACTIONAL
layer (the `Entry` tags carry the full envelope, inheritance propagates it) AND now survives the DURABLE
round-trip. The `PulumiCellar` shell was `(coordinate → payload)`, rebuilding `new SeedEnvelope("",
coordinate, payload)` on fetch — dropping `domain` AND `trail`, and unable to hold a SEALED payload at
all (a `cellar:sealed:v1:…` string is not the JSON `Map` the store parsed). It is now a **five-field
coquille**, a CLEAR shell around the opaque payload:

`{domain, trail[clear], tombstone[clear], mac[clear], payload[sealable]}`

* `domain` + `trail` restore the envelope characterisation the old shell dropped — the fil d'Ariane
  survives the durable round-trip, readable clear.
* `payload` rides as a STRING field, so a SEALED value is just a field value — this dissolves the
  "deserialize expects a Map" blocker and makes durable sealing possible in the same gesture.
* `tombstone` is a first-class shell flag (the withdraw take), replacing the in-band `__cellar_withdrawn__`
  payload marker — the fold reads the state without opening the payload.
* `mac` is an HMAC over the clear characterisation `(domain, coordinate, tombstone, trail, payload)`,
  keyed by the cellar's own passphrase.

*The general MAC (decision A).* Trail (clear) and payload (sealed) are two UNBOUND layers: swap the
payload under the same trail, or edit the trail, and a reveal notices nothing. The `mac` is sops's move
— it BINDS the clear shell to the payload, so any tamper of either fails closed at fetch. It is a
property of the **cellar**, not the seal: present on EVERY coquille (sealed or clear), keyed by the
existing cellar passphrase, so the doctor can trust ANY value's lineage without a per-seal key, and a
seeded side can trust everything it receives (travel-proof). It is cipher-agnostic (a proper MAC, not
AES-GCM's AAD), so it works identically for the passphrase (mono) and the future age (multi) seal. The
host never opens the payload — it MACs and carries the opaque bytes — so the `OpaqueCellar` contract
("never opens a payload") still holds literally. This self-characterised envelope (origin domain, fil
d'Ariane, withdrawn status, integrity binding) is the material for building the CONTEXT of a system
error and aiding its resolution.

NOTE: The trail is the CROSSING path, not a data-flow taint. `path.push(here)` records the route of
SOWS from the root down to the storing crossing — one crumb per crossing traversed (slug {@code
runbook}), the "how did control reach here" a debugger wants. It does NOT track which fetched VALUES fed
a given store (a taint analysis the cellar has no hook for). The rule: the worktree soil (which plants
the root) stamps `[git-root, here]`; a sown crossing X stamps `[git-root, X-crossing, here]`; a scion Y
sub-sown by X stamps `[git-root, X-crossing, Y-crossing, here]`. So a depth-1 store (bbox/incus) already
reads three crumbs (git-root, its own crossing hop, the value), and the incus→manifests sub-sow would
extend to `[git-root, incus, manifests, here]` were manifests ever to store.

[[the-cellar-is-a-fridge]]
==== The cellar is a FRIDGE (put / peek / take), not an append-only journal (correction)

The spec above promoted ONE usage (the doctor's — accumulate visits, never remove) into a LAW of the
cellar ("append-only, DELETE n/a"). The user's real-life intuition debunks it: a fridge is CURRENT STATE
— you PUT something in, you PEEK at what is there, and you TAKE it out to consume it (once taken, it is no
longer there until you put it back). The cellar carries BOTH needs, made EXPLICIT.

Two axes the old model conflated, both realised natively by Pulumi:

* *CURRENT STATE — the fridge (MUTABLE, a Map per coordinate).* `store`(put) / `fetch`(peek) /
  `withdraw`(take). This is the stack's CURRENT state — a resource dropped from the program disappears
  from the state. Addressed by `(Parcel, coordinate)`.
* *HISTORY — the audit (append-only, kept by Pulumi itself).* Every `up()` is a revision: the trace of
  who put/took what. A SEPARATE axis — the `fetch(Parcel)` timeline walk reads this. It is the AUDIT, not
  the live content.

*One primitive, three usages — each names the verbs it needs (the segregation the interface tree gave,
then simplified to one generic `Cellar`):*

[cols="1,2,2",options="header"]
|===
| usage | shape | verbs
| *journal* (doctor) | accumulated timeline | `store` + `fetch`-list ; NEVER `withdraw` (discipline, not a compile guard) — its append-only EMERGES from its usage (distinct coordinate per visit), it is not a law
| *current-state* (live) | one case, last-wins | `store` / `<T> fetch` unitaire
| *ring / pointer* (staging rotation) | bounded position mod N | `fetch` occupancy → `withdraw` the wrapped case + `store` the fresh one
|===

The RING usage is what JUSTIFIES `withdraw` (without it, `withdraw` was a solution seeking a problem). The
bounded staging rotation already exists as `HostSlotSelector` (incus-core, N=3 `ROTATION`, hard-coded — not
yet a Pulumi-config knob): the next slot is `(max present + 1) mod 3`, the wrapped position overwritten by
the fresh replica (the identity is the POSITION, not the age), the `live.syncedFrom` slot PINNED out of
rotation (R1). DECISION: the position's truth MOVES from the filesystem to the cellar —
`HostSlotSelector` consults the cellar (`fetch` the `host-staging` entries → occupancy → `(max+1) mod N`)
instead of `Files.list(nodeRoot)`; its logic (position, wrap, pin) is unchanged, only the source of
occupancy. FS↔cellar reconciliation (an orphan dir with no entry, or the reverse) is EXPLICITLY DEFERRED.

*Two orthogonal selectors — do NOT conflate (the LDAP filter does not restrict the API, it picks the
object):* the TYPE answers "which verbs?" (a compile guarantee); an OSGi LDAP filter
(`@Reference(target="(cellar.kind=durable)")`) answers "which instance?" (runtime, when several instances
of the same type coexist). Today there is ONE impl (`PulumiCellar`, published with no properties), so the
LDAP filter is READY-FOR, not yet needed. It becomes load-bearing when other durable natures arrive — in
the CLUSTER version the durable cellar will be GIT-based, not Pulumi; what makes that substitution possible
without touching a consumer is precisely the FLAT NEUTRAL SEAM (`Cellar` carries only
`SeedEnvelope`/`Parcel`/`SeedCoordinate` — no Pulumi type leaks).

direction is the point: each SIDE projects ONTO the neutral middle; the middle projects onto no one. That

[[the-neutral-crud-port-is-a-cellar]]
=== The neutral CRUD port is a CELLAR (`seed-broker-port`)

The interface that materialises the envelope CRUD must speak ONLY the broker vocabulary — never a doctor
word. A port named `MedicalRecordJournal` means the FRONTIER knows the doctor: the leak moved from the
payload to the interface NAME. But naming matters in a subtler way too (correction): the port
is NOT in the gardening register at all — `pulumi-edge` grows nothing, it is the COMMISSIONER's storage
(the conservation register, adjacent to gardening). So the neutral port is a *`Cellar`* — the
commissioner's addressable store (a FRIDGE: put / peek / take — § the cellar is a fridge below), addressed
by a neutral `Parcel` (the fridge) and a `SeedCoordinate` (the case):

[cols="1,2",options="header"]
|===
| `Cellar` (in `seed-broker-port`) | gesture
| `store(Parcel, SeedEnvelope)` | file a sealed végétal at its coordinate (the case) — the envelope's coordinate IS the address
| `fetch(Parcel) : List<SeedEnvelope>` | open the fridge, list what is there — one opaque envelope per readable case. NOT `harvest`
| `<T> T fetch(Parcel, SeedCoordinate, Class<T>)` | peek ONE precise case (current-state, last-wins) and hand back the decoded type
| `<T> T withdraw(Parcel, SeedCoordinate, Class<T>)` | TAKE a precise case out — consume it: it is no longer there until re-stored (the fridge, not a journal)
| `neighbours(Parcel) : List<Parcel>` | the neighbouring cellars (sibling parcels under the same soil — was `cohort`)
|===

The address is HIERARCHICAL: the `Parcel` is the FRIDGE (the whole furniture — `fetch(Parcel)` opens it
and lists all), the `SeedCoordinate` is the CASE within it (the "carrots" slot — what `withdraw` empties).
You never remove "from the collection of furniture"; you remove from a case addressed by its coordinate.
The coordinate was always in the model (`SeedEnvelope.coordinate`, the output key) but was never exposed
as a REMOVAL address — the missing link the frigo model restores.

Why a cellar and not a garden: a cellar is a NEUTRAL addressable store — it holds crops OR tools, and is
never typed by its contents. This mirrors the envelope's opacity exactly: the cellar never looks inside
(the végétal is sealed — the genus); it knows only the parcel (the fridge), the coordinate (the case), and
the gesture. `harvest` STAYS a gardening verb attached to the grower (in-container), explicitly not a
cellar operation — so the two registers share no word, the decorrelation stated as vocabulary.

[NOTE]
.Two faces: the opaque seam (`OpaqueCellar`) and the typed OSGi view (`Cellar` via `CodecCellar`)
====
The cellar has TWO interfaces, split by realm rather than joined by inheritance (settled):

* `OpaqueCellar` (`seed-broker-port`) — the SEAM: `store` / `fetch(parcel)` / `fetch(parcel,
  coordinate)` / `withdraw(parcel, coordinate)` / `neighbours`, all in sealed `SeedEnvelope`s. The host
  provides and consumes ONLY this (`PulumiCellar implements OpaqueCellar`); it never opens a payload.
* `Cellar` (`seed-broker-port`, OSGi-only) — the TYPED view: the generic `<T>` overloads (`store(coord,
  value)`, `fetch(parcel, Class)`, `fetch/withdraw(parcel, coord, Class)`) plus a codec-neutral
  `neighbours`. It does NOT extend `OpaqueCellar`; its realisation `CodecCellar` (`seed-broker-runtime`,
  a `@Component`) takes an `OpaqueCellar` by `@Reference`, holds a `SeedCodec`, and adds the decode —
  a decorator, so the two faces stay separable.

Why the split, not one interface with `<T>` on the host: the decode reflects on the `Class<T>` a caller
passes (no bundle type is a compile link across the seam — the `Class` carries its own loader), but the
codec must RUN in a realm that holds the type. `CodecCellar` lives OSGi-side, where domain types
(`VisitWire`, `HostLiveEntry`, `IncusCoordinate`) are legal; the host `OpaqueCellar` never decodes. So a
scion says `store(parcel, IncusCoordinate.INCUS_PREP, harvest)` — no `new SeedCodec()`, no magic-string
`new SeedEnvelope("incus", "incus-prep", ...)` — and `fetch(parcel, VisitWire.class)` is fail-at-end
(unreadable entries skipped, the tolerance the `*Reader` classes had). The decode moved OUT of the
per-domain `*Reader` classes INTO `CodecCellar`, where the codec and the types are legal.
====

The three doctor-named host ports (`MedicalRecordJournal.historyOf`/`cohort`, `InterventionJournal.entries`,
`InterventionLedgerWriter.append`) FUSE into this one `Cellar`: `historyOf` and `entries` are the same
`fetch` (the ledger is just a fixed parcel), `cohort` is `neighbours`, `append` is `store`. Host-side the
three classes (`StackMedicalRecordJournal` + `StackInterventionJournal` + `PulumiInterventionLedgerWriter`)
fuse into ONE `Cellar` impl over the Pulumi backend.

The DOCTOR *consumes* the `Cellar` (`@Reference`) and projects its aggregate behind it; the host EDGE
*provides* it. (Nuance vs the port-ownership law "the port is the consumer's": the consumer is still the
doctor, but the port's FACE is neutral by requirement, so it is homed with the vocabulary it speaks — the
middle — not with the consumer's module. The doctor's `historyOf(Patient)`-shaped view sits BEHIND the
neutral port, as its projection: `Patient ↔ Parcel` 1:1.)

[NOTE]
.Open question — the freshness/versioning of what is stored
====
`store`/`fetch` are opaque; the cellar says nothing about whether a `fetch`ed végétal is
still TRUE against the source that grew it. A stored artifact can go stale — so a cellar read is a cache,
and a cache can lie (version skew). This is why material that must be current (e.g. the manifests/flox
synthesis) is a graft *cultivated fresh*, not fetched. When freshness matters, the cellar's contract
needs a versioning/staleness answer — not yet designed, and not required by the current consumers.
====

[[cellar-transactional]]
==== The cellar is TRANSACTIONAL — a UNIVERSAL ScenarioCellar, the ReportModel IS the transaction (converged)

A run must accumulate stores and persist them atomically at a boundary. The design converged over several
turns; the debunked framings are recorded so they are not re-attempted:

* *No transient buffer + read-through CLEAN cache in the service.* A second cache is invisible to the
  consumer and illegitimate — `fetch` reads the durable backend directly (re-hitting it twice a run is
  correct and negligible at our scale). No DIRTY/CLEAN split.
* *No `SeedRunLedger`.* A ledger was posited to index `txId → transaction`. That role dissolved: the cellar
  is INJECTED per scenario, not resolved by key, and the `txId` (a plain UUID) enters no map — so there is
  no index, hence no ledger.
* *No "role encoded by the injected type".* Every scenario — host root AND scion — receives the SAME
  `ScenarioCellar`; it is UNIVERSAL, the SOLE writer of a tag on the `ReportModel`, carrying the common
  logic the scions did by hand (`getScenario().getModel().addTag`, one live site today,
  `IncusProvisionScenario`). Uniformity (CLAUDE.md): one type everywhere.

*The three core decisions.*

. *UNIVERSAL, injected per scenario.* Each scenario (host root AND scion) has its OWN local
  `ScenarioCellar`, backed by its OWN `ReportModel` (`scenario-engine` is DUAL-REALM — depended on by
  `exec/seed-master` and by the domain bundles — so the type lives there, names `ReportModel`, and each
  realm holds its copy; no seam for the cellar). `store` posts the codec-encoded envelope as a `Tag` on the
  model (the within-run write set); `fetch`/`neighbours` delegate to the durable backend directly. The
  cellar is INJECTED by the extension into a scenario field — NOT resolved from the registry (that
  registry-resolution was the source of the identity ambiguity).
. *Tags only, the ROOT drains — pass OR fail.* A fragment never touches the durable backend: it posts tags,
  and the graft folds each scion's tags into the host trunk (`ScenarioGraft`, the `getTagMap` merge —
  already exists). At the boundary only the root drains — a single ordered, batched flush. The batch is
  atomic (it lands in the run's one `up`, § one-history), but it is NOT gated on the run's success: the
  world this cellar mirrors is NON-transactional, so a run that fails part-way leaves real mutations behind
  (the stack, the instance, the sealed CA on disk) and the harvest attesting them must persist too — else
  the cellar lies about the world and the next run re-derives what already exists. A failed run drops only
  the TRANSIENT bus. Isolation (A) between crossings, kept; success-gating, dropped.
+
--
*How the root drains onto the RUN's own stack (§ one-history).* The drain replays the write-set onto the
durable `OpaqueCellar` (`store`/`withdraw` per entry) then calls `conserve(parcel)` once per parcel. For a
SIDE stack (the doctor's ledger) each `store` was an eager out-of-run `up`, and `conserve` is a no-op. For
the RUN's OWN stack — the very stack the outer `pulumi up` is running — a separate nested `up` is impossible
(it would deadlock on the run's lock and be clobbered, since one `up` is authoritative over the whole
resource set). So the run's cellar STAGES each store/withdraw and `conserve` re-declares the full live set
(the coquilles carried forward from the current state, merged with this run's changes) as
`rke2lab:cellar:Entry` resources INTO the running deployment — the harvest folds into the ONE history beside
the infra. Atomicity is then the outer `up` itself (commit all-or-nothing); the drain runs in
`afterTestExecution`, on the worker where the deployment is installed and BEFORE the program returns, so the
registrations are part of that single `up`. This replaces the old separate-`up`-per-entry design, whose
collision with the run's own stack (lock + reading the co-resident incus provider's non-shell outputs) was
the fatal bug (§ host-cellar-realisation-spec, one-history).

*The TRANSIENT tier — the within-run bus.* A store carries a `Persistence` (a seam enum, peer to
`Sensitivity` — lifetime, not secrecy): `DURABLE` is the default drained above; `TRANSIENT` rides the
transactional overlay (read-your-writes) and descends to sown sub-scions (the inheritance) EXACTLY like a
durable entry, but the drain SKIPS it — it never reaches the durable backend, so it never lands as an
`rke2lab:cellar:Entry` in the stack state. It exists for a fact PRODUCED and CONSUMED within one run that
must not be conserved — canonically one whose truth evaporates once the run acts on it (the cold/warm
growth condition, read at grow ENTRY from the prior stack state: the grow then starts the instance, so the
prior state is no longer observable and the fact is frozen on the bus for the rest of the run). The tier is
a capability-default on `Cellar.store(…, Sensitivity, Persistence)` (only `ScenarioCellar` has a drain to
skip and overrides it); the drain still `conserve`s the parcel, so a transient store alongside durable ones
does not suppress their flush.
--
. *The root/fragment role comes from the LAUNCHER, not the type.* A given scenario is a FRAGMENT when
  sown by the host, a ROOT when played alone (`IncusProvisionScenario` in its own in-container test) — so
  the role is not a property of the type; whoever LAUNCHES knows it. A `RunRole` (ROOT|FRAGMENT) is seeded
  into the launcher session store (the same channel as `SessionSeed`/`SeedRun`): `Main` seeds ROOT, the
  sow-graft seeds FRAGMENT — and the extension READS it from the `ExtensionContext`. An isolated
  in-container test plays through `ScenarioPlayer.play` seeding no role, so it defaults to FRAGMENT (its
  read-your-writes assertions read the model's own tags, role-independent). No inference, no realm test
  (`FrameworkUtil.getBundle` would read the REALM and be blind to OSGi→OSGi nesting).
. *`txId` = a UUID minted by the root — for AUDIT correlation (no longer the discriminant).* A
  globally-unique transaction id, stable across serialization (valid remote/P2P). Minted by the root
  (`UUID.randomUUID()`) and propagated to fragments by the sow's `Optional<String>` param. It no longer
  decides root/fragment (the `RunRole` does) — it stays an observability datum, never indexed in a map.

*The TRANSACTION is a PARAMETER of the sow — and it IS the `Cellar`.* Nesting is OSGi→OSGi
REAL (`IncusProvisionScenario` sows `RunbookCoordinate("manifests")`) — so "root" is NOT "host-flat".
Filiation travels PARENT→CHILD through the sow. The transaction qualifies the CROSSING (the act of sowing),
NOT the document (a `SeedEnvelope` also carries REAPED responses that bear no transaction). Earlier this was
a lone `Optional<String> txId`; it GENERALISED (§ the write-set descends) to the whole transaction, and the
transaction is not a new DTO — it is the ambient `Cellar` itself, which already carries the `txId` (its
`transactionId()`) AND the in-flight write-set (its model view). So the sow's shape is
`SeedBroker.sow(SeedCoordinate wanted, Cellar cellar, SeedEnvelope seed)` — read as a sentence: *what I
want, with what (the ambient transaction), the seed* — and `SeedHandler.handle(Cellar cellar, SeedEnvelope
seed)`. The `Cellar` is ALWAYS present: every sow issues from a scenario whose cellar the extension injected
(there is no sowing outside a run), so it is a plain `Cellar` param, never `Optional`, never null — the
optionality lives INSIDE it (`transactionId()` is the `Optional`, empty for a non-transactional play). The
type at the seam is the port interface `Cellar` (module direction: `scenario-engine` → `seed-broker-port`,
so the port cannot name `ScenarioCellar`). The two handler natures stay: the 5 `*RunbookHandler`s
(cluster/systemd/incus/manifests/bbox) LAUNCH an in-container run — they cast the crossed cellar to
`TransactionalCellar` and FLATTEN the transaction at the launcher boundary
(`TxIdSeed.into(transactionId())` + `CellarEntriesSeed.into(entriesEncoded(childCoordinate))`, both flat strings — the
isolation guard-rail); the 5 reflectors (Amend/Shape/Split/Intervention/Readiness) TRANSFORM and IGNORE the
cellar.

*The cast crosses a SEAM, never the realm-library.* A handler receives the neutral `Cellar` and needs the
two transactional accessors (`transactionId()`, `entriesEncoded()`). It must NOT cast to the concrete
`ScenarioCellar`: that class is a dual REALM-LIBRARY (flat host-side, a bundle package in-container), so it
exists as two `Class` objects — casting the crossed cellar to it throws `ClassCastException`, the
DUPLICATE_REALM_CLASS split (surfaced the first time a scion crossing actually ran host→bundle).
The fix: a seam sub-interface `TransactionalCellar extends Cellar` in `seed-broker-port` (system-exported,
ONE copy), carrying exactly the two flat-typed accessors (`Optional<String>`, `List<String>` — seam-eligible,
nothing concrete crosses). `ScenarioCellar implements TransactionalCellar`; the handlers cast to the seam.
It is a SUB-interface, not two methods folded onto `Cellar`, because a durable backend (`PulumiCellar`, the
test doubles) is not transactional. The invariant: a seam type crosses the boundary as an object (one
system-exported copy); a dual realm-library must never cross as an object, only its seam view. The boot is NOT a sow, so no sow precedes the root minting its `txId`.

*The lifecycle — the host adopts `BaseWorldExtension`.* The connection to the shared framework is a WORLD
fact (it lives as long as the framework). `BaseWorldExtension` (already written, used by the scions) opens
`OsgiConnection.embedded()` at `beforeAll`, puts it in the class-`Store` (key `CONNECTION`), and closes it
at `afterAll` (gated by `ownsLifecycle`). `ClusterSeedScenario` ADOPTS it (`@ExtendWith(SeedRuntime)`) and
stops opening the `Gardening` by hand — which fixes a pre-existing leak (the host connection was never
closed) and unifies host and OSGi on ONE lifecycle model. Three ownership layers: WORLD = the connection
(the extension) ; RUN = `OpaqueCellar`/`RunGate`/`Parcel` (the GIVEN `registerService`s them, their source
the already-seeded `SeedRun`) ; SCENARIO = `worktreeScalars`/`preflightGate` (host-local computation, stay
in the GIVEN).

*The extension — `ScenarioCellarExtension` (no ledger).* Dual-loaded (host-flat + one per bundle). Three
gestures; `commit`/`rollback` stay PRIVATE to the extension (the cellar exposes only
store/fetch/neighbours):

* `BeforeTestExecutionCallback` — reads the `RunRole` + the `txId` from the session store. Builds and
  injects the `ScenarioCellar` into a scenario FIELD — the proven `SessionSeed` pattern. NOT a
  `ParameterResolver`: jGiven reads every `@Test` PARAMETER as a narrated scenario argument
  (`ArgumentReflectionUtil.getNamedArgs` → `startScenario`, verified in 2.0.3), so a parameter would be
  narrated and could collide with jGiven's own param-reading; a field puts no parameter on the `@Test`.
* `AfterTestExecutionCallback` — ROLE=ROOT ⇒ DRAIN, whether the run PASSED or FAILED — resolve the
  `OpaqueCellar` from the REGISTRY (via the connection in the class-`Store` `BaseWorldExtension.CONNECTION`,
  the SAME path the scions resolve their collaborators — one resolution route), read the folded
  tag-envelopes off the trunk, re-`store` them opaquely (the host never decodes, a tag-envelope is already
  an encoded `SeedEnvelope`). The drain is NOT gated on success: the world is non-transactional (a failed
  run leaves the stack/instance/filesystem where it stopped), so a harvest filed before the failure point
  is a fact that really happened and must persist — the only thing a failed run drops is the TRANSIENT bus,
  evicted by the drain itself (§ the TRANSIENT tier). FRAGMENT ⇒ no
  drain, but STRIP the inherited entries (`ScenarioCellar.stripInherited`) before the front-door serialises
  the model, so the write-set it inherited from its parent does not fold up into the trunk a SECOND time (§
  the write-set descends).

Timing with `JGivenExtension` is LEVED BY CONSTRUCTION: begin/end touch no `ReportModel`; the drain reads
tags `store` already posted during the body; the verdict comes from JUnit, not jGiven's sealed
`ExecutionStatus`. The cellar reads the model LAZILY (first `store`), so the order between this
`TestInstancePostProcessor` and jGiven's is a non-issue.

===== The three neutral channels the extension reads — role, identity, write-set

The extension lives in `scenario-engine` (runtime); `SeedRun` lives in `exec/seed-master` (the host world,
where `Main` runs). The module direction is `seed-master → scenario-engine`, NEVER the reverse — so the
extension CANNOT read `SeedRun` (it does not know the type, and `SeedRun` is host-flat, it does not cross
the launcher membrane into a scion anyway). That is WHY the transaction context reaches the extension as
THREE NEUTRAL channels (each a flat JDK value in the launcher session store, each with a launcher-side
`into` and an extension-side `read`), never as the host record:

[cols="1,2,1,1",options="header"]
|===
| channel | role | root (Main seeds) | scion (the parent's `*RunbookHandler` relays)
| `TxIdSeed` | the transaction IDENTITY (a UUID) — correlation/narration, one per run | present (the minted UUID) | present (the SAME UUID, relayed unchanged)
| `RunRoleSeed` | the DRAIN discriminant (ROOT drains, FRAGMENT does not) — decides atomicity | `ROOT` | `FRAGMENT`
| `CellarEntriesSeed` | the inherited WRITE-SET (the parent's in-flight stores) — the ALLER sense | empty (the root is the source) | the parent cellar's `entriesEncoded(childCoordinate)`
|===

*Why THREE, not fewer — each answers a distinct question, and none derives from another.*

* `TxIdSeed` is present on BOTH sides with the SAME value, so it CANNOT tell root from scion — identity is
  not a role.
* `RunRoleSeed` cannot be DERIVED from the write-set's contents: at the FIRST sow the root has stored
  nothing yet (its `store` is the closing `the_harvest_is_stored`), so the first scion inherits an EMPTY
  write-set — deducing "empty ⇒ root" would wrongly make it drain mid-run and shatter atomicity. The role
  is a LAUNCHER fact (who launched knows), seeded explicitly, never inferred.
* `CellarEntriesSeed` is the only one that varies by depth; it is the passenger this increment adds.

*Narration vs persistence — the tag PROJECTS the entry (never a second source).* The Cellar persists to the
durable backend, invisible in the runbook; a `tag` is visible in the runbook but not durable. A host-tree
fact that must be BOTH seen and kept is posed as a tag AND drained as an entry — but the tag is a PROJECTION
of the entry ("promoted from staging.N, sha abc, dirty"), never a separately-captured fact. One truth, two
renderings — so the two cannot diverge. `liveRoot` stays a pure tag (a within-run render path, no durable
entry behind it). A durable envelope rides the model as a `Tag` (round-trip verified, narrated), not an
opaque `Attachment`.

===== The write-set descends too — the ALLER sense of the transaction

The design above carried the transaction ONE way: a fragment posts tags, the graft folds them UP into the
trunk (`scion → host`, the RETURN), and the root drains. That is the return sense of the transaction. The
ALLER sense was MISSING: when the root sows a fragment MID-transaction, the fragment opened a FRESH
`ReportModel` whose write-set was empty, so it could not read what an EARLIER crossing of the SAME
transaction had already stored. A crossing that must READ an in-flight store of a sibling crossing — the
reconcile scion reading the staging the provision scion published earlier in the same run (§
host-cellar-realisation, the reconcile cycle) — saw only the DURABLE backend (last run's state), never the
in-flight write. Read-your-transaction's-writes did not hold across crossings.

The correction is the exact twin of the `txId`: whoever SOWS a fragment ALSO hands down the transaction's
accumulated write-set. The `txId` already descends this channel (`TxIdSeed`) — the write-set is its
passenger (`CellarEntriesSeed`, the same session-store idiom). The `ScenarioCellar` is UNCHANGED — it stays a
pure VIEW on the caller's `ReportModel` (`model`, `durableReads`, `txId`), no new field, no `Transaction`
type. What crosses is the VIEW EXTRACTED as flat data: `ScenarioCellar.entriesEncoded(childCoordinate)` returns the
encoded `Entry` strings (the raw `Tag.ENTRY` values) off the trunk — the exact ALLER-sense twin of the
runbook JSON the graft carries the RETURN way. At `BeforeTestExecution` the extension re-posts them onto the
fragment's OWN model via `cellar.inheritEntries(encoded)` (the cellar is the sole tag writer): each becomes
an `Entry(inherited=true)` tag, so `fetch` overlays them uniformly — no third read source, the model stays
the sole carrier. Because they are posted BEFORE the body, they precede the fragment's own stores in tag
order, so a shared coordinate resolves own {@literal >} inherited {@literal >} durable for free.

*The inherited entries live IN the model, marked, then STRIPPED — the anti-duplication.* The parent's
write-set is posed on the fragment's model as ordinary `ScenarioCellar.Entry` tags, so `fetch` reads them
through the SAME overlay path as the fragment's own stores (no third read source — the model is the sole
carrier). But the graft folds a fragment's WHOLE `getTagMap()` up into the trunk; left as-is, the inherited
entries — which the trunk ALREADY holds (crossing A posted them) — would fold up a SECOND time and drain
twice. So each inherited entry carries a flag `inherited=true`, and the extension REMOVES them from the tag
map at `AfterTestExecution`, before the front-door serializes the model. The graft then lifts only the
fragment's OWN tags. Verified on jGiven 2.0.3: a cellar tag is added via `ReportModel.addTag` (the `tagMap`
alone) and is NEVER referenced by a `ScenarioModel.tagIds`, so removing it leaves no dangling id — the strip
is as clean as a tombstone.

`Entry` gains `inherited` as a SECOND flat marker beside `tombstone`, and the two are ORTHOGONAL, not a
single enum: a parent's WITHDRAW must descend too (else the fragment re-reads a durable case the parent
emptied in-flight), so `(tombstone, inherited)` is a real combination — inheritance and emptiness are
independent axes.

*The isolation guard-rail (load-bearing).* `scenario-engine` is DUAL-REALM — host-flat AND one copy per
bundle, SAME version, DIFFERENT classloaders — so a live `ScenarioCellar` or `Entry` object crossing the
launcher membrane would `ClassCastException`/`LinkageError` (the `JsonNode`-payload trap § the seam types).
Nothing of the sort crosses: the write-set descends as the VIEW extracted flat — `entriesEncoded(childCoordinate)` returns
already-encoded `Entry` STRINGS, and the session store carries ONLY those flat JDK types (`TxIdSeed` puts a
`String`, its twin `CellarEntriesSeed` puts ONE `String`, the JSON array of the encoded entries). The child's
cellar re-posts them LOCALLY via `inheritEntries` — decoding each string into an `Entry` in ITS OWN realm,
then re-appending it as a tag on ITS OWN model. Each realm holds its own `Entry` class; none travels. The
rule that keeps it safe: the channel carries FLAT (encoded strings), the typed `Entry` is born downstream of
the read, per realm. Never `store.put(aCellar)` nor put a live `Entry` in the session store.

[[failure-handling]]
===== Failure handling — the crossing verdict, the closing gate, and the harvest

Three coupled decisions govern what happens when a crossing (or a host step) FAILS mid-run. Together
they make a failed bootstrap read HONESTLY (a red runbook, a non-zero `pulumi up`) while KEEPING the
real harvest a partial run produced — the non-transactional mirror.

. *The sow's default THROWS (fail-fast).* `SowAndGraftStage.the_scion_is_sown_and_grafted` grafts the
  scion's verdict into the runbook, then `assertPassed` PROPAGATES a FAILED scion as a throw. A crossing
  whose failure makes the rest meaningless (worktree · bbox · cluster-pki seal · incus-provision;
  incus-reconcile is designed, not yet wired) uses this default — no point growing an instance whose provisioning failed.
. *A tolerating variant lets the SOWER keep the hand.* `…_tolerating_failure` grafts the verdict but does
  NOT throw, so the crossings AFTER it still run and their failures ACCUMULATE in the one runbook (§ the
  graft, ACCUMULATE not first-wins). For the TERMINAL independent crossings a sower wants to report
  together — systemd AND cluster — so an operator sees both causes, not just the first.
. *The root's closing gate BUILDS the verdict (fail-at-end), in the ENGINE — not the driver.* The THEN calls
  `ScenarioGraft.assertNoCrossingFailed(hostScenario, hostTree)`: if any tolerated crossing left an error on
  the host case, it throws an `AssertionError` carrying the accumulated message AND the per-crossing
  `GraftThrowable`s as SUPPRESSED exceptions (from the host tree's GRAFT_FAILURE tags). Because it is thrown
  in the root's THEN, that ONE exception is ROOT-ANCHORED (its stack is `ClusterSeedScenario`), with each
  scion's full cause chain hanging off it. So JUnit's verdict AGREES with the runbook, and — the point — the
  verdict is NOT exe-specific: it is the engine's, so a driver only RE-SURFACES the captured throwable to
  fail its own way (`pulumi up` non-zero), it never reconstructs it. `assertPassed` (the fail-fast default)
  builds the same shape for a single crossing.
. *The reason is captured STRUCTURED at the source, and reconstructed on TWO twin channels.* No live
  `Throwable` crosses the realm — a domain exception (`ClusterNotReadyError` …) is bundle-private, unloadable
  on the flat host loader. The frames must therefore travel as data through the mapper, NOT as a
  printStackTrace dump re-parsed on the far side. So the CALLEE captures itself: `ScenarioPlayer` — the one
  place both the model and the live exception are in hand — builds a `ThrownModel` (type, message, real
  `StackTraceElement`s, and the recursive `cause` chain) DIRECTLY from the `Throwable` and poses it as a
  hidden `SCENARIO_FAILURE` tag (`SeedCodec`-encoded). At graft RECEPTION `graftUnder` reads that structured
  self-report off a failed scion, wraps it in a `GraftFailure` (the WIRE POJO: a crossing `Trail` + the
  `ThrownModel`), and as it returns up a nested graft chain each level PREPENDS its own `Crossing` — so the
  tag accrues the full crossing path (the same path-to-origin mechanism the cellar uses for values, see
  <<fil-d-ariane>>). Both channels rebuild a real `GraftThrowable` from those tags — its frames mapped from
  the structured `Frame`s, its `Caused by:` chain rebuilt as `ReconstructedThrowable` links, so
  `printStackTrace` renders a faithful tree with no line parsed from a string:
** *the runbook* — `ScenarioGraft.foldGraftedReasons`, called by `ScenarioOutcomeExtension` (the universal
   `@SeedScenario` chokepoint, firing after jGiven has overwritten the case `stackTrace` with the scenario's
   own closing-gate/fail-fast throw), rewrites the root case `stackTrace` from the tags — each rebuilt
   `GraftThrowable` rendered per crossing. So EVERY root scenario (the cluster seed, the CLI scenarios)
   renders the crossings that failed, not the gate boilerplate.
** *the console* — the engine's closing gate already attached the `GraftThrowable`s as `Suppressed:` on the
   root-anchored verdict it threw (above); the driver (`Main`) only RE-SURFACES that captured throwable
   (from the launcher summary) to fail the run, so the operator reads one root-anchored Java exception with
   one `Suppressed:` (full cause chain) per failed crossing — no verdict logic in the exe.

And on EVERY exit path — pass, fail-fast, fail-at-end — the root DRAINS (§ cellar-transactional, the drain
is NOT gated on success): the harvest filed before the failure point is real (the world is not
transactional — a failed run leaves the stack, the instance, the sealed CA on disk), so it must persist;
only the `TRANSIENT` bus is evicted. A run that seals the CA then fails at cluster-readiness still persists
the CA — the next run is warm.

[[edge-reaches-osgi]]
=== How the host EDGE reaches an OSGi consumer — registerService, not a handler

The `Cellar` is a host object (it reads the Pulumi backend, so it CANNOT be a Felix bundle), yet its
consumer (`JournalMedicalRecordRegistry`, `@Reference MedicalRecordJournal` → soon `Cellar`) lives OSGi-side.
The channel is the one the preview mock already proved: `registerService(Cellar.class, hostObject)` into
Felix, resolved by the bundle because `Cellar` is a `type=seam` interface (host + bundles share the same
`Class`). Two facts frame it, both load-bearing:

* *The broker never sees the edge, and must not.* `DefaultSeedBroker` collects only `SeedHandler`s (the
  growers, which project a metier onto the neutral) by constructor `@Reference(MULTIPLE)`. The `Cellar` is
  not a handler — it is a COLLABORATOR a handler's dependency (`MedicalRecordRegistry`) `@References`, two
  hops below the broker. The host contributes NO handler (it is outside Felix and cannot be a DS component);
  it only registers a collaborator a bundle consumes.
* *The reference is STATIC + mandatory, so boot ORDER is the whole difficulty.* If the consumer activates
  before the host registers the `Cellar`, the mandatory reference is unsatisfied and the consumer never
  starts. The fix is ordering, not weakening the reference: the host holds the single global start-level
  cursor (`StartLevelLever`, levels assigned per role by `BootPlanner`), so it registers the `Cellar` while
  the consumer bundles sit above the cursor, THEN raises the cursor — the reference binds directly, no
  `greedy`, no rebind, no ranking. Keep the reference static + mandatory: a doctor with no cellar is a
  wiring bug that must fail loud, not be papered over with `OPTIONAL`/`dynamic`.

[[live-preview-rungate]]
=== Live vs preview — the ambient RunGate selects the collaborator at the frontier

Whether a run TOUCHES the world (kubectl, dbus, the Pulumi backend) or only PLANS is a fact of the whole
run, not a property of any seed — so it is published ONCE as a neutral ambient service, `RunGate`, into
Felix at boot. Its VALUE depends on `pulumi-edge` (projected from `RunMode.detect()` → Pulumi's
`isDryRun`), so the HOST publishes it live; a test `registerService`s its own.

[NOTE]
.Sibling ambient service: `ReadinessOverrides` (readiness deadlines, keyed per checkpoint)
====
`ReadinessOverrides` is the `RunGate`'s twin — another fact of the WHOLE run, published ONCE into
Felix at boot (the host projects it from `rke2lab:readiness:`; a test `registerService`s its own or
none). It carries the operator's readiness deadlines at two levels: a global default and a
per-checkpoint map of `ReadinessDeadlineOverride` (two optional durations — `connect`, `ready` —
keyed by the checkpoint slug, e.g. `systemd-adapter` / `cluster-readiness`). A readiness scion
resolves it from its own registry (the same `resolve*` route as `RunGate`), calls
`forCheckpoint(slug)` to fold its per-checkpoint entry over the global, and the
`ReadinessBudgetExtension` folds THAT over the scenario's `@ReadinessDeadlines` annotation default —
so a deadline the operator leaves unset stays the value declared in code. Both types live in this
seam (a single system-exported copy) so the host-flat publisher and the in-container scion share one
class, never a dual-realm split. See `docs/architecture/osgi/cluster-edge-spec.adoc` (§ readiness-await).
====

*The FRONTIER selects; the scenario is mode-blind (reverses "the scion consults it per-step").*
The mode is no longer read inside a scenario. The `@OsgiService` bridge reads the ambient `RunGate` ONCE
and resolves every collaborator with an LDAP filter that picks the right implementation:
`(|(rke2lab.gardening=<mode>)(!(rke2lab.gardening=*)))` — the matching half of a paired collaborator, OR
any un-paired service (which carries no `rke2lab.gardening` property, so the `!(…=*)` clause takes it: the
`RunGate` itself, the doctor, manifests). So a scenario declares `@OsgiService BboxReconciler` and receives
the cultivating or surveying impl transparently; it NO LONGER injects `RunGate` at all. The mode-branch is
aspirated out of the scenario AND the edge, into the one place the mode is known — the frontier.

*Two implementations, not a `dryRun` flag (supersedes the short-circuit-in-one-impl).* A
materialiser's contract DROPS its `dryRun` parameter; it becomes a PAIR, each impl mode-pure:
* `Cultivating…` — the live tool: opens the session, applies, promotes.
* `Surveying…` — the plan tool: it projects the honest plan from the real desired input, contacting the
  world ZERO times (INERT = no contact — a preview login "would hang or lie"). For bbox it returns each
  row's `WOULD_CREATE`, the honest upper bound (a survey cannot read the table, so never a fabricated
  MATCHING). Both are real production code registered with `rke2lab.gardening=cultivating|surveying`;
  the frontier's LDAP filter chooses.

*The criterion — is there an honest plan? (the no-fake law).* Not every collaborator is a pair. A PURE
PROBE (systemd adapter, cluster readiness) has NO honest plan — its output IS the live state — so a
surveying probe would FABRICATE an observation, the forbidden fake. A pure probe therefore does NOT run in
survey: its scenario is survey-inert and every step renders PENDING (E9), touching nothing. A materialiser
HAS a plan → it gets the pair. Manifests (pure FS synthesis) touches nothing live → no pair, runs in both
modes (the staging is wanted at survey).

Two orthogonal axes the earlier "mock pattern" wrongly conflated:

[cols="1,2,2",options="header"]
|===
| axis | governs | lever
| RENDER | how the runbook reads (plan vs result) | `PendingMarkingScenarioExecutor` (E9) — bodies still `proceed()` so the tree builds, `InvocationMode` rewritten `NORMAL → PENDING` as it reaches the model

[[open-extensibility-chantier]]
== Planned evolution — the per-domain roster (required by the distributed peer-to-peer mode)

[NOTE]
====
This is FUTURE, not dead. The per-domain roster ("multiplexor") is an OPEN-extensibility design the
*distributed peer-to-peer mode requires*: while the system is centralized bootstrap (seed-master
orchestrates) the closed form below is fine, but the moment the system becomes a mesh of unitrepo peers
that contribute domains dynamically (as bundles, per new need — the unitrepo thesis), the roster becomes
necessary. It is a PRIORITY chantier right after the behavior-driven pipelines land (cluster, the second
contributing domain, arrives with that migration — the trigger and the slot coincide). The design below
is PRESERVED as the starting point and the DIRECTION; the exact new shape is the chantier's own design
work, done when we get to it — not invented here. (The config `InfraDomain` enum carries the same
closed-vs-open tension, same p2p driver — see the config-restructuring spec.)
====

The shipped records-as-contract won a typed contract-of-form. The § <<contribution-and-opacity>> turn
supplies the OPEN per-domain extensibility on the REQUEST/response axis (coordinate → interface, the
domain owns its enum + wire-records). What THIS chantier still adds is the same openness on the
*data-egress* axis — the egress DAG assembles host-side today, so a new contributing domain still edits
the host builder rather than extending at the edge. Only one domain (doctor) contributes today, so N=1
hides the cost.

The design is not new and not dead: it is the *per-domain roster* we already conceived (the
"multiplexor"), still current — only its BOUNDARY moves. The key correction to the earlier picture:
*inside the OSGi world, working on records is natural* — records ARE the domain model there. The
`Document` is not OSGi's internal currency; it is the currency of the FRONTIER. So the record→`Document`
transposition happens at ONE place, the seam (the host↔OSGi crossing), not inside each mapper. The
multiplexor does not die; its frontier recedes to the edge.

* Each domain publishes a `DomainDagMapper` `@Component` that contributes its part of the DAG **as
  records** (OSGi-natural, Pulumi-blind). A roster collects them by
  `@Reference(cardinality=MULTIPLE) List<DomainDagMapper>` (the same DS mechanism as the
  `List<Specialist>` roster) and assembles the egress DAG **OSGi-side, on records**, dissolving the
  host `OutputBuilder`. A new domain contributes by publishing one `@Component` — touching nothing
  central.
* The record→`Document` transposition sits at the SEAM edge (the egress adapter), a single crossing —
  the assembled DAG becomes `@DocumentContract` `Document`s exactly as it leaves the OSGi world, so
  `SCHEMA_CONCORD` still binds every coordinate to a schema. The typed contract lives at the frontier;
  the roster and its mappers stay record-native behind it.

=== The unification: the broker door subsumes the N verbs AND the roster

The keystone reframe (§ top) resolves a question this roster design left open. The multiplexor was
conceived for the *data-egress* axis (records → DAG → Pulumi, one direction); the N service interfaces
(`ConsultingService`, `ReadinessAuthority`, `InterventionIntake`) carry the *request/response* axis
(`consult`, `assess`) — and were left as RPC, the `ConsultingService` "in-process vs across-runs" knot
explicitly deferred. The Exchange model UNIFIES the two: a `consult` is an Exchange
`readiness-checkpoint → consultation`; a data egress is an Exchange `domain-facts → pulumi-output`.
Same shape — one broker door, dispatched by `coordinate`, is the single organ for both. So the
conceived AFTER is: the broker door subsumes the N service verbs *and* the roster; the door dispatches
each request-coordinate to the domain handler that owns it (whether that handler consults or maps for
egress); the doctor's verbs become internal handlers. This closes the deferred knot — there is no
separate RPC surface left to decide about.

[[the-rename]]
=== The rename: `world-gateway` → `seed-broker` (honest about what the module IS)

The module is named `world-gateway` in code, framed first as a generic organ. The code does not support
"generic": its only consumers are the seeding host + doctor, and the ONE bundle FUSES neutral transport
(`Document`, `Coordinate`, `WireEnum`, `DocumentContract`) with provisioning vocabulary (`Checkpoint`,
`ReadinessCheckpoint`, `ReadinessVerdict`, `Consultation`, `Patient`, `SymptomKind`). It is already a
provisioning broker wearing a generic name. The conceived name is **`seed-broker`** — honest about what
it is: the whole system is `seed-master` (la graine); the broker is the organ that sows.

The two layers are real but NOT split into modules now (rule-of-three; no abstraction at N=1): the
neutral transport (`Document`/`coordinate`/`handle`) and the seed-specific coordinate catalog live in
one `seed-broker` bundle. A future split into a reusable `broker-core` transport is a documented split
point, triggered only by a real second non-seeding consumer. The rename touches ~10 `bnd.bnd` + imports
across the tree (`gateway-document-codec` → `seed-broker-codec`, or folded in); do it in one atomic
pass (delete the old name entirely — no compat shim), ridden on the unification chantier above.

[[one-seam]]
=== One seam only — the `-port`s stop being seams, become domain APIs

If a client speaks only to the broker, nothing else crosses the WORLDS — so the seed-broker is the
ONLY `type=seam`. This is now REALISED: the eight domain `-port`s
(`cluster`/`doctor`/`systemd`/`incus`/`netplan`/`manifests`/`bbox`/`auth`) were de-seamed into
`type=contract` bundles (wired bundle-to-bundle inside OSGi), and `pipeline-port` was dissolved (its
engine relocated INTO `manifests-core` as un-exported internal synthesis). `seed-broker` is the one
retained inter-WORLD seam.

The `-port`s do NOT disappear — they REMAIN, structural, but CHANGE NATURE: from inter-WORLD seams
(shared host↔OSGi, system-exported) to a domain's **external API** — an inter-DOMAIN vocabulary
consumed only inside the OSGi world, how one domain exposes itself to the others. `ClusterReadinessContact`,
`SystemdRuntimeProbe`, a domain's `Specialist` SPI: these are how domains wire to *each other*, never
how the host reaches into OSGi.

.The two natures a `-port` can have
[cols="1,2,2",options="header"]
|===
| | inter-WORLD seam (today) | inter-DOMAIN API (conceived)

| crosses | host ↔ OSGi (system-exported, shared copy) | domain ↔ domain, inside OSGi only
| `type=` | `seam` | a bundle export (not a seam)
| host imports it? | yes (the leak) | NO — the host speaks only to the broker
|===

Why the `-port`s are seams *today* is the LEAK the keystone closes: each is consumed host-side now
(measured: `doctor-port` 9 host files, `manifests-port` 8, `bbox-port` 8, `cluster-port` 6,
`systemd`/`incus` 4, `netplan` 2, `auth` 1) BECAUSE the logic still lives host-side (readiness, consult,
the resource stages). Once the client speaks only to the broker, those host imports vanish and the
`-port` reverts to inter-domain-only.

This gives a NET, verifiable criterion a realization plan tracks per-port: **a `-port` stops being
`type=seam` when zero host files import it** — the host-side count drives to 0, and `REALM_BOUNDARY`
(which already knows realms) confirms it. The end-state the two-worlds architecture was always reaching
for: ONE frontier door (seed-broker), everything else inter-domain wiring that never leaves OSGi.
