= Cross-cluster reach — host routing vs the Tailscale operator
:toc: left
:toclevels: 3
:icons: font
:date: 2026-09-27
:status: SCRATCHPAD — a decision is open, nothing here is implemented

== The question

A management cluster must reach a cluster it birthed. Concretely: CAPI's
`RemoteConnectionProbe`, running in a pod on `bioskop-mgmt`, must reach
`nikopol-mgmt`'s apiserver. Tonight that fails, and `ClusterIntention/nikopol-mgmt`
reads `Degraded` with every pool `Adopted`.

On 2026-09-27 we moved subnet routing *off* the per-cluster `Connector` pod and onto
the bare-metals (rke2lab `acdb4d05`, ndh `34605639`). The stated reason: a route
advertised by a pod dies with its cluster, precisely when it is wanted — while
debugging a half-born cluster.

⚠️ *That reason rests on a premise the operator has since rejected:* waiting for the
VIP to become routable is not a real cost here. With that premise gone, the
`Connector` is back in contention, and this note lays out both shapes so the choice
is made on what each actually provides rather than on the one property that
motivated the removal.

== Why the pod still cannot reach it

[mermaid,reach-pod-failure-sequence,svg]
----
sequenceDiagram
  participant P as CAPI pod<br/>(bioskop-mgmt)
  participant N as k8s node<br/>10.80.0.10
  participant H as bioskop-nixos<br/>subnet router
  participant F as nikopol-nixos<br/>packet filter
  participant V as kube-vip<br/>10.80.23.10

  P->>N: dial 10.80.23.10:6443
  N->>H: via default gw 10.80.0.1 (route correct)
  H->>F: forwarded over tailscale0<br/>src STAYS 10.80.0.10 (no NAT, by invariant)
  F--xH: src is not a tailnet identity<br/>and no grant names it
  Note over P,V: timeout — Accessible=False,<br/>"apiserver not reachable yet"
----

The failure is not routing — every hop has a route. It is *identity*: the fleet
holds a "No NAT anywhere" invariant (source IPs survive end-to-end, the point of the
netflow project), so the packet arrives at nikopol bearing `10.80.0.10`. The
destination admits sources the policy names, and the policy names *tags*. A k8s node
is an incus container, not a tailnet device, so it has no tag to be admitted by.

★ This is the same shape as the corp Mac earlier tonight, which needed its address
named explicitly as a grant `src` (`172.16.24.2`) before it could reach a Service.
The analysis is measured up to the forward (`ip route get` correct from the node,
then timeout); the filter-drop step is inferred from that precedent, not captured.

== What the operator actually offers

Read from the source we build (`k8s-operator/apis/v1alpha1`), not from docs:

[options="header"]
|===
| CR | Field | What it is
| `Connector` | `subnetRouter` | a tailnet DEVICE in the cluster advertising CIDRs *into* the tailnet — INBOUND reach
| `Connector` | `exitNode` | that device as an exit node
| `Connector` | `appConnector` | that device as an app connector (SaaS egress with a predictable IP)
| `Connector` | `replicas` | several devices for HA — the property the removed pod-router lacked
| `ProxyGroup` | `type: egress` | devices that RELAY outbound connections, carrying their own tailnet identity
| `ProxyGroup` | `type: ingress` | devices that expose cluster workloads to the tailnet
| `ProxyGroup` | `type: kube-apiserver` | the apiserver as a first-class tailnet entry
|===

★ The three `Connector` roles are *mutually exclusive*, and all of them are about what
the device does with an identity it always has. Tags default to `tag:k8s`, which the
operator's own OAuth client owns — so `autoApprovers` can approve its routes by tag
with no console step.

⚠️ *Correction to an earlier claim of mine.* I said removing the `Connector` "threw
away the pod's identity". It did not: that `Connector` was a `subnetRouter`, i.e.
INBOUND. Tonight's failure is OUTBOUND from a pod, a path the `Connector` never
served. The outbound relay (`ProxyGroup` type `egress`) was simply never wired.

== What none of them solves: the mesh dataplane

Measured: `cilium-config` has `routing-mode: native` (cluster-id 1,
`bioskop-mgmt`). In native mode cilium does not encapsulate, so clustermesh expects
the *underlay* to carry the remote cluster's POD CIDRs — whole ranges, not one
endpoint. No Service and no proxy expresses that.

So there is a second, independent fork:

* *tunnel* — cilium encapsulates pod↔pod between NODE addresses, and the underlay
  requirement collapses to node reachability, which (A) or (B) already provides.
* *native* — the underlay must route pod CIDRs, which means advertising them into the
  tailnet and solving source identity for them too.

★ Choosing *tunnel* reduces the problem count from two to one. That is the argument
for it — not throughput.

== Before deciding, measure

Three things, none of which should be inferred:

. *Does a `ProxyGroup` egress satisfy CAPI?* The probe dials whatever the render
  wrote into `controlPlaneEndpoint`. An egress proxy offers a *cluster-local*
  address, so this is a change to the rendered CR, not only to infrastructure.
. *Does `kube-apiserver` make the VIP redundant for cross-cluster reach?* If so (C)
  is simpler than (B), and kube-vip stays a cluster-internal concern.
. *What does leaving `native` cost?* The addressing plan derives pod/service CIDRs
  deterministically and disjointly, which is what makes native legitimate. Leaving it
  is a choice, not a repair, and it touches both live clusters.

== Wider move: what belongs in-cluster

The three failures of 2026-09-27 share one shape, and it is not about tailnet at
all: *the host owned something a child it did not know about needed.* The CR-set's
shape (3 nodes, kind `workload`), the `node-<cluster>` profiles (co-located only),
and the domain policy (hardcoded `WRKLD`). Each was repaired by deriving instead of
assuming — but the repair keeps the ownership where it was.

★ *The grow does not have to DO the work. It has to PUBLISH what it knows.* At the
initial grow, `seed-master` holds everything: the blueprint, the ImageState, the
declared targets, the addressing. A controller can then reconcile the objects.

That is already this project's idiom, three times over:

* `network-blueprint.json` — the addressing plan, published so ndh derives from it
  rather than re-declaring it;
* the *image-state ConfigMap* (`ImageStateConfigMapManifestsUnit`) — the grow's
  ImageState handed to the cluster for the Stage A → Stage B handoff;
* `reflections/` — amendments the in-cluster controllers write BACK onto the branch.

So the question is not "can a controller do this" but "which fact does the grow
publish, and which controller consumes it".

=== The test for whether something should move

*Does it concern a cluster the host does not know about?* If yes it is misplaced,
however well it works today. The `node-<cluster>` profile answers yes and is the
first thing to move; a member's own bridge answers no and should stay.

=== Measure before committing to it

. *Can a controller holding the PARENT's `<host>-incus-identity` create a profile
  for a child on the OTHER member?* Profiles are cluster-wide objects, so probably —
  but that is the load-bearing assumption of the whole move, and it is unverified.
. *What does the write right cost?* Moving profiles in-cluster grants the cluster
  the right to create incus resources. That is an authority boundary, the same kind
  as letting a commit birth a cluster — and worth deciding explicitly rather than
  inheriting.

== 2026-09-28 — the VIP flow, measured on the operator we deploy

Everything below is read from the SOURCE at the version we run (tailscale 1.102.3, CAPN v0.9.0),
not from docs. It supersedes the three-candidate framing above where it contradicts it.

=== ★ The VIP has TWO consumers, of different reach — do not conflate them

[options="header"]
|===
| consumer | tailnet member? | path to the VIP | state
| the operator on bioskop (its kubeconfig) | *yes* | host subnet routes | ✅ works since 2026-09-27
| pods in the mgmt cluster (CAPI's probe) | no | the node's IP, which no grant names | ❌ broken
|===

So the requirement is NOT "replace the VIP": it is to make what the in-cluster probes already dial
resolvable and reachable FROM A POD. And `controlPlaneEndpoint` is an IP today
(`https://<vipHostInetAddr>:6443`), so there is nothing to "resolve" — an IP can only be routed.

⚠️ Measured on the operator kubeconfig: THREE context forms already coexist — `bioskop-mgmt`,
`bioskop-mgmt-fabric-name`, and the `-vip` ones. That is the asymmetry of MECHANISM this work should
collapse, not merely a spelling difference.

=== What the operator offers at 1.102.3

`ProxyGroup.spec.type` ∈ `egress` | `ingress` | `kube-apiserver`; `replicas` defaults to *2* (the HA
the removed `Connector` never had). For `kube-apiserver`:

* `kubeAPIServer.hostname` — a DNS label, ≤63 chars, *unique across the whole tailnet*. It is a SPEC
  field, so it is DETERMINISTIC: `<cluster>-apiserver` is knowable before the cluster exists, which
  means the render CAN write it into `controlPlaneEndpoint`. That question is closed.
* `kubeAPIServer.mode` ∈ `auth` | `noauth`, ⚠️ *defaulting to auth*. In `auth` mode requests are
  "additionally impersonated using the sender's tailnet identity" — so with an egress proxy as the
  sender, EVERY pod collapses into one identity. Same shape as the trap already paid on
  `clustermesh-remote-users`, where a shared client cert collapsed all peers into one user and
  nullified the per-peer authorization. It must be set explicitly.
* `status.URL` + `status.Devices[].TailnetIPs` — published after reconcile, hence unusable as a
  render-time contract; the deterministic hostname is what makes the contract writable.

=== ⚠️ The tension that decides the shape

A `kube-apiserver` ProxyGroup is an API-server PROXY: it terminates TLS and re-originates. Our
authorization is a CLIENT CERT from the BYO-CA. The 2026-09-12 design chose `ProxyGroup type: egress`
+ a Service `ExternalName` in L4 pass-through precisely for that — "TLS bout-en-bout, contrairement à
`apiServerProxy`" — and live-probed it.

[options="header"]
|===
| shape | buys | costs
| egress + `kube-apiserver` | policy expressible *tag→tag*, no CIDR in any grant, VIP off the path | TLS terminated at the proxy ⇒ the client-cert model must be revisited
| *egress + the VIP in L4 pass-through* | TLS end-to-end, client certs intact, already probed | grants keep naming the vmnet CIDRs in `dst`
|===

★ Chosen: the second, because the requirement is that EXISTING in-cluster probes keep working, and it
touches no contract. The `kube-apiserver` ProxyGroup stays as a later simplification, once it is known
whether `noauth` preserves a client cert (not the same question as whether it terminates TLS).

=== ⚠️ Correction to the archived record

`claude-preview.archive-2026-09-25` marks the Service `ExternalName <w>-apiserver` with
`tailnet-target-ip` as "✅ EXISTE". *It does not exist in code* — verified 2026-09-28 across rke2lab,
seed-incluster, the flox-catalogue and ndh: zero occurrences of `ExternalName` or
`tailnet-target-ip`. Either it was created out of band for the 2026-09-12 probe, or "exists" meant
"is proven". So this is GREENFIELD, and "the adoption controller owns the VIP Service" is a design
intent, not existing code to extend.

=== The shape to build

. a `ProxyGroup type: egress` in the cluster that PROBES (the parent);
. a Service `ExternalName` per target, annotated `tailnet-target-ip: <target VIP>` — ⚠️ OWNED BY THE
  CONTROLLER, never Flux: the tailscale operator MUTATES `spec.externalName`, so a force-apply SSA
  would make the Service flap. That trap is already documented for the VIP Service;
. the tailnet grant admitting `tag:k8s` → the vmnet segments (one line, in ndh — the proxy carries
  `tag:k8s`, not `tag:headless`, so the grant widened on 2026-09-27 does not cover it);
. LATER, and only then: `controlPlaneEndpoint` names the Service instead of the IP, which is what
  finally STABILISES resolution for the probes from both vantage points.

Steps 1-3 touch no contract and already unblock the probe that holds `nikopol-mgmt` at `Degraded`.

=== Adjacent finding — the tailscaled fork stays

The fork (`github:nxmatic/tailscale`, rebased on release-branch/1.102) carries TWO patches:
CNAME-in-`extra_records` resolver support *and* SSH interception (the port-2222 switch). The CNAME
half is dead — headscale hibernates and the SaaS forbids arbitrary MagicDNS records — but the SSH
half is still needed, so *the fork stays*. Two consequences:

* `flake.nix:111`'s justification names a reason that no longer applies; left uncorrected it misleads
  exactly as `acl.hujson`'s "controller-AGNOSTIC" header did twice in one day;
* ★ `catalog.netplan.tailnet.hosts.<host>.serviceNames` now has NO consumer — it feeds headscale
  `dns.extra_records`, which hibernate. Same shape as the dead `image-state` ConfigMap: a declared
  fact nothing reads, waiting for its delivery (Tailscale Services, or a ProxyGroup hostname). The
  vocabulary is right; only the delivery is missing.

★ And the naming these two threads need is the SAME: whatever gives the apiserver a stable name also
retires the CNAME hack. The cleanup and the VIP work point one way.
