**Chantier ndh (2026-09-17) : `nerd-tart-vm-materialize` sur le Mac corp nikopol-vzhost (hostname `APL-g4xfl7qv06`, compte `stephane.lacoin`) NE crée pas ses gcroots → run wrapper `nerd-nixos.sh -> …run.sh` non protégé, cible GC-ée (« la dernière fois j'ai perdu la cible »).**

Racine : le manifeste nikopol est figé sur `profile_user=nxmatic` + `profile_home=/Volumes/user-home` (venant du `hostProfile` nikopol dans ndh), tous deux **inexistants** sur le Mac corp (pas de compte nxmatic, pas de /Volumes/user-home ; HOME=/Users/stephane.lacoin). La création du gcroot est gatée root + `exec sudo -u <profile_user>` (`ndh/modules/darwin/tart-config.d/activation.sh:1044-1050`) → en stephane.lacoin la branche saute (gcroot sous per-user/nxmatic root-owned jamais écrit) ; en sudo nu `sudo -u nxmatic` échoue. Aggravant : Mac NON-managé (0 config nix-darwin) → l'auto-install du profil bringup-runtime ne tourne jamais, et la closure copiée portait l'installer **aarch64-linux** (bash ELF → « Exec format error »), il faut le **darwin**.

Modèle gcroot : `tart:raw-images:gcroot:materialize` (`activation.sh:532-547`) pose UN symlink `…/gcroots/per-user/<user>/tart-nerd-nixos-materialize` → le **bundle** d'activation, qui garde toute la closure vivante (run.sh + images + runtime nikopol-nixos). Simple symlink dans l'arbre gcroots, pas de `nix-store --add-root`.

Workaround live 2026-09-17 (NON codé) : (1) profil bringup-runtime **darwin** installé main (`sudo …/nerd-bringup-install`, bash Mach-O ✓) ; (2) `ln -sfn <bundle> /nix/var/nix/gcroots/per-user/stephane.lacoin/tart-nerd-nixos-materialize` → run.sh enraciné ; (3) purge gcroots morts + `nix store gc` = 14,8 GiB. ⚠️ le lien manuel épingle CE hash de bundle (re-pointer si re-materialize).

Option tranchée pour débloquer = **override runtime** `sudo env PROFILE_USER=stephane.lacoin PROFILE_HOME=/Users/stephane.lacoin …` (env lues en priorité `activation.sh:974-975`). Fix durable candidat = corriger le hostProfile nikopol OU faire injecter identité+bootstrap-profil par `nerd-tart-nikopol-deploy` (le helper prévu pour ce cas non-managé).

**★★ CORRIGÉ DANS LE CODE (2026-09-18, ndh `8c33cd74`) — l'override PROFILE_USER/PROFILE_HOME n'est plus nécessaire.** Révélé par un symptôme bien pire que le gcroot GC-able : après la bascule du store en EROFS, la VM nikopol **pendait dans l'initrd** sur `/dev/disk/by-label/nix-store` (`lsblk` : vda + vdb…vde, **pas de vdf**). Mécanisme complet : `activation.sh` résolvait déjà le HOME à l'exécution (`tart:runtime:home:resolve`) mais **pas l'utilisateur** → les disques atterrissaient dans le home réel (`/Users/stephane.lacoin/.tart/vms/`, `store.img` bien créé, 2 776 629 248 o) tandis que le gcroot restait gravé sous `per-user/nxmatic/` ; or `run.sh` lit la **liste des disques dans le manifeste du gcroot** → manifeste périmé (bundle de la veille, sans image `store`) → `required_prebuilt_disks` vide → disque jamais attaché. Fix = (1) `tart:runtime:user:resolve`, pendant symétrique du resolve du home (si le compte configuré n'existe pas ici → compte runtime, avec WARN) ; (2) `tart:runtime:gcroot:realign`, qui réécrit le segment `per-user/<configuré>` vers l'utilisateur effectif AVANT l'auto-resolve du manifeste ; (3) `run.sh` essaie le gcroot de l'utilisateur effectif avant le chemin gravé. **+ DURCISSEMENT (même commit) : les replis silencieux sur une liste `tank1/2/3+recover` codée en dur, dans les DEUX scripts, sont désormais FATALS** — ils précédaient le disque de store et l'omettent, donc un jeu de disques deviné ne dégrade plus gracieusement, il fabrique une VM qui ne boote pas, et l'échec n'est visible qu'à la console du guest. Leçon transposable : quand un montage devient `neededForBoot`, tout repli « best effort » en amont devient un piège muet.

**★★★ LA VRAIE CAUSE du blocage nikopol (2026-09-18 soir, ndh `e2c6a302`) — un `~/.config/nerd-tart/<vm>.yaml` PÉRIMÉ battait le gcroot.** Symptôme : VM fraîchement matérialisée qui pend dans l'initrd sur `/dev/disk/by-label/nix-store`, 4 disques attachés au lieu de 5, **alors que tout était correct sur le disque** (bundle `rrh5j25j` avec `role: prebuilt`, `store.img` 2 776 629 248 o + marqueur, wrapper relinké, run.sh à jour). Cause : `run.sh` ordonnait ses candidats de manifeste « du plus spécifique au moins », donc `$XDG_CONFIG_HOME/nerd-tart/nerd-nixos.yaml` — **un symlink posé à la main le 17/09, jamais rafraîchi, pointant sur le run-manifest de la veille et donc sur l'ANCIEN bundle `b7gxsjjp` (sans image store)** — passait AVANT le gcroot que le materializer relinke à chaque exécution. Fix = ordre par **fraîcheur d'autorité** : env var explicite → gcroot de l'utilisateur effectif → chemin gravé → XDG en dernier. Débloqué en écartant le symlink (`mv … nerd-nixos.yaml.stale-20260918`, réversible) → 5 disques dont `store.img:ro`, `Reached target Multi-User System`, `/nix/store` overlay 180G / `/nix/.ro-store` erofs 2,6G. **Méthode : les 3 premières hypothèses (gcroot périmé, run.sh d'ancienne génération, `yq` basé sur jq) étaient toutes FAUSSES — seule la trace `set -x` a tranché, et il faut la prendre en lançant `NDH_BASH_TRAMPOLINED=1 <bash-nix> -x <wrapper>` : le trampoline fait `exec bash <script>`, ce qui perd les flags du shebang, et sauter le trampoline sans donner le bash nix retombe sur le bash 3.2 de macOS et change le comportement.** Gotchas d'accès pour rejouer : `ssh -i ~/.local/share/ndh/ssh-keys/rdp-host stephane.lacoin@nikopol-vzhost` (hostname `APL-g4xfl7qv06`) ; le wrapper exige `socat` ET `yq` dans le PATH (absents d'un ssh non-interactif) ; `tart list` exige `/usr/sbin` (diskutil) ; pas de `timeout` sur macOS ; `ps -eo args=` TRONQUE → utiliser `ps -ww -p <pid> -o command=`. ⚠️ Deux répertoires de VM coexistent : `/Users/stephane.lacoin/.tart/vms/` (le vrai) et `/Volumes/user-home/.tart/vms/` (périmé, vu depuis le guest `nikopol`) — diagnostiquer sur le mauvais fait perdre du temps.

**Why:** identité opérateur gravée dans l'image (nxmatic/@Volumes/user-home) ≠ compte du Mac corp bare-metal (stephane.lacoin) ; sans gcroot le run.sh est GC-able → VM incassable-à-rejouer perdue. Et, depuis l'EROFS, un gcroot périmé ne dégrade plus : il empêche le boot. Leçon générale : dès qu'un montage devient `neededForBoot`, tout repli « best effort » en amont (liste de disques devinée, manifeste posé à la main) devient un piège muet côté hôte, visible seulement à la console du guest.
**How to apply:** matérialiser normalement (le script s'auto-répare depuis `8c33cd74`) ; l'override PROFILE_USER/PROFILE_HOME reste un échappatoire, plus une obligation.
