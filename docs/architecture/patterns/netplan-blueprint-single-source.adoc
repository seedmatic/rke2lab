= Netplan Blueprint as Cross-Repo Single Source of Truth
:toc: left
:toclevels: 3
# :kroki-server-url: https://kroki.io

== Overview

The cluster network underlay — cluster/node IDs, MAC derivation scheme, IP
addressing — is defined once in rke2lab's Java `ClusterNetworkBlueprint` and must
be consumed identically by two parties:

* *rke2lab itself* (the netplan/bootstrap code that provisions guests), and
* *nix-darwin-home* (which configures host routes, dbus, and incus on the NixOS
  hosts that run the guests).

This design re-establishes nix-darwin-home's consumption of that blueprint as a
proper flake edge, so there is a single source of truth. rke2lab's flake builds
and runs the netplan jar to produce the blueprint and exposes it as
`lib.networkBlueprint`; nix-darwin-home adds rke2lab as a flake input and consumes
`deriveMacs` instead of hand-copying the values.

== The synthesis port contract

The `ClusterNetworkBlueprint` above is not reached directly by callers — it is the
`blueprint` field of a `NetplanSynthesisResult`, produced by the `netplan-contract` SPI. That
port is the exported surface of the domain: a request/response pair over the SPI, plus two
strongly-typed value objects the addressing model is built from.

[mermaid]
....
flowchart LR
  req["NetplanSynthesisRequest\nclusterName + nodeName\n+ Optional&lt;Net2PlanEndpoint&gt;"]:::v
  spi["NetplanSynthesisService (SPI)\nproviderId() + synthesize(request)"]:::s
  res["NetplanSynthesisResult\nblueprint"]:::v
  bp["ClusterNetworkBlueprint\n(host/lan/lb/node/vip/…)"]:::s
  cidr["Cidr\nInetAddress + prefixLength"]:::v
  mac["MacAddress\nvalidated 6-octet value"]:::v
  n2p["Net2PlanEndpoint\nbaseUri + networkPlanPath"]:::v

  impl["DefaultNetplanSynthesisService\n@Component (netplan-core)"]:::i

  req -->|input| spi
  spi -->|output| res
  spi -.->|implemented by| impl
  res --> bp
  bp -.->|addressing plans use| cidr
  bp -.->|interface plans use| mac
  req -.->|optional mesh intent| n2p
  classDef s fill:#dae8fc,stroke:#6c8ebf
  classDef v fill:#d5e8d4,stroke:#82b366
  classDef i fill:#d5e8d4,stroke:#82b366
....

[cols="2,3",options="header"]
|===
| Port type | Contract

| `NetplanSynthesisService`
| The SPI: `providerId()` (a stable provider id for diagnostics/policy) and
  `synthesize(NetplanSynthesisRequest)` → `NetplanSynthesisResult`. Canonical netplan synthesis
  behind one seam.

| `DefaultNetplanSynthesisService`
| The OSGi `@Component` (in `netplan-core`) implementing that SPI — the default provider that derives
  the `ClusterNetworkBlueprint` from a request.

| `NetplanSynthesisRequest`
| Request record: `clusterName` + `nodeName` (both required, blank-rejected in the canonical
  constructor) and an `Optional<Net2PlanEndpoint>` mesh-integration intent. Has a `Builder`
  (defaults `bioskop`/`master`) and a two-arg convenience constructor.

| `NetplanSynthesisResult`
| Response record wrapping the single `ClusterNetworkBlueprint` the synthesis derived.

| `Net2PlanEndpoint`
| A lightweight endpoint record (`baseUri` — http/https only — + `networkPlanPath`) letting netplan
  declare Net2Plan mesh-topology integration intent WITHOUT coupling current synthesis to a remote
  planner. Resolvable from the `rke2lab.netplan.net2plan.*` properties / `RK2LAB_NET2PLAN_API_ENDPOINT`.

| `Cidr`
| Strongly-typed IPv4 CIDR value (`InetAddress networkAddress` + `int prefixLength`), parsed and
  validated via the IPAddress library (`Cidr.parse("10.80.0.0/21")`); a missing prefix or non-IPv4
  input is rejected at construction.

| `MacAddress`
| Strongly-typed MAC value: a 6-octet colon-separated string, validated by regex at construction and
  normalized to lowercase canonical form by `MacAddress.parse`.
|===

== Background: how the link broke and why it matters

The reverse edge (nix-darwin-home consuming rke2lab's blueprint) was removed.
nix-darwin-home's `catalog/default.nix` now *hand-inlines* the MAC/IP values
(`mac = "10:66:6a:4c:00:00"`, ...) while its comments still declare
`Source of truth: rke2lab/netplan (ClusterNetworkBlueprint semantics)`. The
intent says "linked"; the mechanism is a manual copy. If the Java blueprint
changes a MAC/IP, the copy silently diverges. rke2lab's `flake.nix`
`lib.networkBlueprint` / `deriveMacs` export — built to feed this link — is
consumed by nobody (orphaned).

[[non-cycle-invariant]]
== The non-cycle invariant

The two repos depend on each other in *different scopes*, so there is no
flake-eval cycle:

* `nix-darwin-home -> rke2lab`: BUILD/eval time (imports the blueprint).
* `rke2lab -> nix-darwin-home`: RUNTIME only (rke2lab's incus instances run on
  the NixOS host nix-darwin-home provisions). This edge is invisible to nix eval.

rke2lab's flake imports only `flake-commons` + its own `flox-runtime` sub-flake —
never nix-darwin-home. A guard comment at rke2lab's `inputs` block records this
invariant so a future edit cannot accidentally close the loop.

[mermaid]
....
flowchart LR
  ndh["nix-darwin-home flake"]:::b -->|build/eval: imports blueprint| rl["rke2lab flake"]:::b
  rl -->|build/eval| fc["flake-commons"]:::b
  rlrun["rke2lab incus instances"]:::r -.->|RUNTIME only: run on| host["bioskop-nixos (provisioned by ndh)"]:::r
  classDef b fill:#dae8fc,stroke:#6c8ebf
  classDef r fill:#ffe6cc,stroke:#d79b00
....

The blue (build) edges form an acyclic graph; the orange (runtime) edge does not
participate in eval.

=== The invariant under pressure — where a per-bare-metal fact would close the loop

The invariant is not merely about flake `inputs`; it constrains *what the blueprint
may be a function of*. Pair it with the pure-output property below (the jar reads
no input file, which is why IFD has no chicken-and-egg) and the rule becomes:

[IMPORTANT]
====
`ClusterNetworkBlueprint.derive()` may depend only on facts rke2lab itself
declares. The moment it needs a value out of ndh's catalog, that catalog feeds the
jar that *generates* that catalog — a real eval cycle, and the end of the
pure-output property. No flake-input guard catches this: the cycle arrives through
a *data* dependency, not an `inputs` entry.
====

This was live, not hypothetical. The decided move of the LAN plane onto each
bare-metal's `172.16.<S>` instance segment needs `<S>` at derivation time, and `<S>`
looked like ndh's property — it is declared in `catalog.netplan.baremetal.<host>`
alongside nnh's DHCP pool and the vz-host `/30`. Taking it from there would have been
exactly the prohibited shape.

*Resolved by derivation, not by choosing an owner.* `<S>` is now a pure function of
`hostId` — the table this blueprint already declares and already uses for the vmnet
plane, the ULA mirror and the MACs. Both repos therefore compute the same value from
a name they each already hold, and *nothing crosses the seam in either direction*.
The arbitrary inverted pair that made this look like an ownership question
(ndh's `nikopol = 6`/`bioskop = 7` against `hostId` 0/1) simply disappears; ndh's
`netCidr` becomes a projection, as its `kind = "rke2"` rows already are. The full plan
is link:../atlas/netplan.adoc#solved-plan[in the netplan atlas], including
link:../atlas/netplan.adoc#eval-cycle[why a hash of the host name is the wrong way to
delete the table] — `hostId()` survives renames and refuses typos, and the file
already carries the proof (`// renamed from alcide, keeping same host id`).

The general form worth remembering: a fact that looks like the *host's* is usually a
fact about a *coordinate we already declare*. Derive it here, or take it on the
runtime edge — never on the eval one.

== Design: the flake runs the jar (IFD), exposes a flat lib

The blueprint is a *pure output* of the Java: it is derived from hardcoded
cluster/node maps and reads no input file. So there is no chicken-and-egg — the jar
takes no blueprint in, it emits one. rke2lab's flake already builds the jar and runs
`yamlExport` to produce the blueprint (`networkBlueprintYaml` -> `networkBlueprintData`);
we keep that and expose `lib.networkBlueprint` for nix-darwin-home to consume.

The generation moved IN-CONTAINER: `ClusterNetworkBlueprint` is a `type=contract`
bundle record that the flat host cannot reference, so `netplan-cli`'s `yamlExport`
drives `NetplanCliScenario`, which sows the `netplan` coordinate through the broker
and grows the `netplan-bdd` scion `NetplanBlueprintScenario` where the blueprint type
is reachable. The scion writes the metadata as JSON; the CLI reads that host-neutral
JSON back and renders it to YAML flat. The command (`netplan.jar yamlExport`) and the
YAML shape are unchanged — only host-neutral JSON crosses the realm boundary (the flat
`BlueprintExportCommand` was retired; see link:../osgi/netplan-bdd-spec.adoc[netplan-bdd-spec]).

[cols="1,3",options="header"]
|===
| Element | Role

| `ClusterNetworkBlueprint` (Java) | the single source of truth
| `netplan.jar yamlExport` | generator: emits the blueprint as YAML (no input)
| rke2lab `flake.nix` (`networkBlueprintYaml` -> `networkBlueprintData`) | builds + runs the jar at eval (IFD), parses the YAML
| `lib.networkBlueprint` (`deriveMacs` + data) | the consumable export
| nix-darwin-home flake input `rke2lab` | consumes `rke2lab.lib.networkBlueprint.deriveMacs`
|===

The YAML carries the full contract (from `NetplanBlueprintScenario`): `clusters`,
`nodes`, `macPatterns`, `nodeTypes`, and per-node `addressing` (macs/ips/leases).
`deriveMacs cluster node` resolves a `{lan, wan}` pair from the cluster/node IDs.

Alongside the per-node addressing the export also carries the cluster-owned
`segments` and the `asns` dictionary (`asn` → AS name). These are the single
source the netflow collector (ndh projects them, `nnh` consumes) derives its
flow→AS labelling from, so it no longer hardcodes the segment→ASN map. The AS
numbering is the `ClusterAsn` enum (`RKE2_CLUSTER` 65010, `GATEWAY` 65020); the
pod/service CIDRs and the gateway address are constants on
`ClusterNetworkBlueprint`, previously scattered as literals across the Cilium
manifests and the node-env. The home AS (65000) is ndh's — it is unioned in on
ndh's side, not owned by rke2lab.

Each segment is `{cidr, name, asn, gateway?, dhcp?, domain?, hosts[]}` — the
*uniform* shape ndh's baremetal segments also expose, so both repos' spans read
the same way. Beyond the attribution triple (`cidr → name → asn`), a segment
carries the managed-network facts *when rke2lab actually runs that network's
gateway/DHCP*:

* `gateway` — the segment gateway address (present only where rke2lab owns it);
* `dhcp` — the DHCP range served (the `ipv4.dhcp.ranges` string);
* `domain` — the dnsmasq DNS zone (absent for the cluster nets, whose Incus
  bridge runs `dns.mode=none`);
* `hosts[]` — the static reservations, each `{name, mac?, ip}`: a `dhcp-host`
  when `mac` is present (the MAC-known cluster nodes) or a `host-record` when it
  is absent (ndh's `vzhost.<host>`, kept uniform).

These optional facts are `Optional<String>` on the record — never nulls — so an
attribution-only span (the `/18` vmnet supernet, the LAN/LB `/27`s, `pod`,
`service`, `gateway`, `ula`) serialises back to just `cidr/name/asn` with an
empty `hosts` list (Jackson's jdk8 module omits an empty Optional's key). The
managed facts land on the *per-cluster vmnet `/21`* segment
(`<cluster>-cluster-net`, e.g. `nikopol-cluster-net` = `10.80.8.0/21`, gateway
`.1`, the WAN DHCP range, and one `dhcp-host` per canonical node) — the same
tuples `GrowNetworkResolver` emits into the Incus bridge's `raw.dnsmasq`,
projected here from the one blueprint source. This mirrors ndh's model exactly:
a broad attribution supernet plus per-owner managed nets carrying gateway + DHCP
+ reservations.

=== The IFD tradeoff (accepted)

Consuming `lib.networkBlueprint` triggers import-from-derivation: nix builds the
netplan jar via Maven-in-nix and runs it during eval. So a `nixos-rebuild` on
bioskop-nixos that touches the catalog will Maven-build rke2lab's netplan module
the first time (then cache).

This cost is *accepted* in favor of simplicity. The alternatives were weighed and
rejected:

* *Committed YAML projection* (commit `yamlExport` output as a lock-like file,
  read it purely, guard against drift): removes the IFD cost but adds a committed
  artifact, a regeneration discipline, and a sync guard. Over-engineered for a
  single-developer lab where the build caches and rebuilds are infrequent.
  IMPORTANT placement note if ever reconsidered: the YAML must NOT live as a
  netplan-module Maven *resource* (`src/main/resources/...`) — that would package
  it into the very jar that generates it, creating a real chicken-and-egg. It
  would have to be a top-level, lock-like file outside the module's input path.
* *Pure-Nix data file*: would require the Java to read the same Nix data (or
  duplicate it), a larger refactor with its own drift surface.

If the IFD cost ever proves painful in practice (cold `nixos-rebuild` latency on
the NixOS hosts), revisit the committed-projection option with the placement
caveat above.

== The blueprint is OS-independent

The blueprint data + `deriveMacs` logic have no genuine system dependency: the
underlying values (cluster/node IDs, MAC patterns, addressing) are pure literals
from the Java, identical on every system. The jar that generates the YAML does
need a build platform (jdk/maven), but the *resulting data* does not.

Practical consequence: `lib.networkBlueprint` is exposed flat and
system-independent, so consumers use `rke2lab.lib.networkBlueprint.deriveMacs`
rather than a per-system `rke2lab.lib.${system}.networkBlueprint...`. The data is
parsed once and surfaced flat; `deriveMacs` uses the system-independent
`nixpkgs.lib` (pure int/string functions).

=== How the flat `lib` is realized (implemented)

A flat `lib` has no `system` in scope, but IFD must still realize the generating
derivation on *some* concrete system. The netplan jar is a portable JDK/Maven
build, so the YAML — and the parsed data — is byte-identical regardless of build
platform. We therefore pin generation to a single system rather than the
consumer's:

* `blueprintSystem = "aarch64-darwin"` — bioskop, the sole build host.
* The jar/YAML/parse derivations are factored into `pkgs`-parameterized helpers
  (`netplanJarFor` / `networkBlueprintYamlFor`); the flat `lib` builds them under
  `nixpkgs.legacyPackages.aarch64-darwin`, parses once, and merges the result at
  the top level via `(eachDefaultSystem ...) // { lib = ...; }`.
* The per-system `packages.${system}.networkBlueprintYaml` still builds locally
  for inspection; only the consumed `lib` copy is pinned.

Because both the darwin config (bioskop) and the NixOS config (bioskop-nixos) are
evaluated *on bioskop*, the pinned `aarch64-darwin` derivation always builds
natively — no linux-builder is involved, and the NixOS side carries only the
parsed MAC strings, not a darwin derivation.

== Implementation plan

*rke2lab side (do first):*

. Keep `networkBlueprintYaml` (the jar-running derivation) and `netplanJar` — they
  produce the blueprint. No committed YAML, no sync guard.
. Surface `lib.networkBlueprint` as flat/system-independent (parse the YAML once,
  expose the data + `deriveMacs` outside the per-system split where practical), so
  consumers don't need `lib.${system}`.
. Keep the no-nix-darwin-home-input guard comment (already added).

*nix-darwin-home side (follow-up):*

. Add `rke2lab` as a flake input (url = the rke2lab repo).
. In `catalog/default.nix`, replace the hand-inlined MAC/IP literals with
  `rke2lab.lib.networkBlueprint.deriveMacs <cluster> <node>` (and the
  IP/addressing fields from the same blueprint).
. The "source of truth: rke2lab" comments become true rather than aspirational.

== Open questions

. *Input pinning*: nix-darwin-home pins rke2lab via flake.lock. Decision: track
  rke2lab `main` and let the operator bump the lock (`nix flake update rke2lab`)
  when they choose to sync — no auto-follow on every rke2lab commit. This keeps
  eval coupling under operator control for a single-developer lab.
. *IFD build*: generation is pinned to `aarch64-darwin` (bioskop, the only build
  host), so both the darwin and the NixOS evals — both run on bioskop — build the
  jar natively. Confirm jdk25 + maven are substitutable/cached so a cold
  `nixos-rebuild`/`darwin-rebuild` isn't a full Maven cold start.
. *The fleet ceiling.* Resolved: the segment is derived from `hostId`, so the
  ownership question is gone (see <<non-cycle-invariant,the invariant under
  pressure>>). What replaces it as *blocking* is how many bare-metals and roles the
  plan admits — because three planes currently give three different answers (pod/
  service `/16`s: 2 bare-metals; vmnet `/18`: 4; the fabric: 16), and the tightest is
  a *live latent defect*: `podCidr` and `serviceCidr` are only 4 apart, so
  `clusterId = 4` — reachable via the declared `test` host — yields a pod CIDR
  identical to `bioskop-mgmt`'s service CIDR. Decide one ceiling, make `clusterId` an
  explicit bit-field, and size every plane from it:
  link:../atlas/netplan.adoc#fleet-ceiling[the fleet ceiling] and
  link:../atlas/netplan.adoc#solved-plan[the solved plan]. Nothing should be coded
  before the ceiling is picked; everything else follows from it arithmetically.
