= Deterministic cluster access — a pre-seeded PKI the operator already trusts
:toc: macro
:toclevels: 3

toc::[]

== Overview — the result we want

[IMPORTANT]
====
Read against the management/workload separation (see the anchor,
link:management-workload-topology.adoc[Management / Workload Topology]). This deterministic pre-seeded
PKI is a *pillar of function-of-git*: because the kubeconfig is a pure function of the deterministic
mDNS name + a pre-seeded root of trust, it is stable across destroy/re-grow — exactly the "deterministic
identities" the function-of-git invariant needs. It applies at both levels: `seed-mgmt` reaches the
*management* cluster it seeds, and the same BYO-CA scheme gives deterministic access to each *workload*
cluster the management cluster greenfields. "The master it bootstrapped" below means the *management
node* `seed-mgmt` seeds; CAPI greenfields the workload clusters' own nodes.
====

The seed-outcluster must reach the live cluster's kube-apiserver to verify readiness. The result this
document fixes as the target: **the operator's machine holds a valid admin kubeconfig for a cluster
the instant that cluster is grown — built entirely on the host, from material the operator already
trusts, and stable across destroy/recreate of the node.** No runtime fetch, no `kubectl` shelling,
no host-mount channel, no per-node CA churn.

Concretely, the end state has three properties, and each is a departure from what came before:

[cols="1,2,2",options="header"]
|===
| Property | What it means | What it replaces
| **Deterministic** | the kubeconfig is a pure function of the node's deterministic mDNS name (`<cluster>-<node>.local`, derived from the blueprint) and the operator's root of trust (the CA) — computable before the node answers | fetching rke2's self-written `rke2.yaml` and rewriting its `server:` at runtime
| **Natively trusted** | the kubeconfig's CA is the ndh `mammoth-skate-tls` root, already installed in every client's system trust store — TLS validates with no custom CA bundle and no `--insecure-skip-tls-verify` | an rke2-generated self-signed CA the operator has to carry and skip-verify around
| **Stable across re-grows** | destroy master, grow it again, the SAME kubeconfig still works — the CA is pre-seeded and constant, not minted fresh on each node's first boot | a new self-signed CA per node → the kubeconfig invalidated on every re-grow
|===

This dissolves two long-standing defects at once: the cluster-readiness probe **shelling `kubectl`**
over a **`/srv/host/kubeconfig` path that died with the `/srv/host` teardown**.

== The one idea — own the root, pre-seed the intermediates

RKE2 generates its own CA hierarchy on first boot. But it also honours a *bring-your-own-CA*: if the
CA set is already present under `/var/lib/rancher/rke2/server/tls/` when the first server starts, rke2
skips generation and issues every leaf (apiserver, kubelet, etcd, service-account) from the provided
CAs. We exploit that to make the operator's existing root the cluster's root.

- **Root of trust: `mammoth-skate-tls`.** The ndh SSH/TLS key inventory (`.ndh-ssh.d/keys.yaml`)
  already carries a dedicated x509 TLS root — `usage: [tls-authority]`, a self-signed `ca_crt` — whose
  certificate the ndh Nix modules install into every client's system trust store. It signs the
  headscale HTTPS leaf today; it becomes the root of the cluster's CA chain tomorrow.
- **rke2's intermediates, rooted on it.** The cluster's `server-ca`, `client-ca`,
  `request-header-ca`, `etcd/{peer,server}-ca` (+ `service.key`) are generated *once per cluster*,
  signed by `mammoth-skate-tls`. The root's private key never leaves the operator's machine; only the
  intermediates travel. Because the chain terminates at a root already in every trust store, anything
  the cluster serves or that we mint from it validates natively.
- **The admin kubeconfig is a pure derivation of the sealed material.** We hold `client-ca`, so the
  seal mints the admin client certificate (the `AdminCredentials`); its endpoint is the node's
  deterministic mDNS name (`<cluster>-<node>.local`, avahi-advertised on the LAN — the lan0 IP is
  router-DHCP and not stable, so the NAME is the stable endpoint); the CA is the trusted root. The
  kubeconfig is a pure function of that material and needs nothing fetched from the node. The host
  runbook renders it today (writing `kubeconfigRef`); the manifests synthesis now ALSO produces it
  as a `local-config` manifest, the path that will retire the host render — see § "Delivery: the
  kubeconfig as a synthesized local-config manifest" below.

Nothing here extends the ndh certificate pipeline (which mints only self-signed *roots* and
end-entity *leaves*, never intermediates): the cluster CA set is produced OSGi-side by the
`cluster-pki` domain — a faithful **BouncyCastle** port of rke2's `generate-custom-ca-certs.sh`
(proven structurally identical cert-by-cert against OpenSSL 3), rooted on our root — and lives
rke2lab-side as a **sops view onto the ndh key material** — encrypted for the operator and for the
cluster age recipient (`age1k0tc4…`, derived from the `rke2-cluster` SSH key), `keys.yaml` itself
untouched. The CA hierarchy is pure Java (no shell); the only external tool contacts are the
`sops-edge` (sealing the bundle the node's sops-nix decrypts) and the ssh-to-age edge (the cluster
age identity), both reused, not reinvented.

The seal's orchestration is `ClusterSeal` (its one-act output a `SealedClusterPki` — the sealed
bundle + the age identity + the operator's `AdminCredentials`, an admin client cert minted from
`client-ca` paired with the server-ca chain); the operator key inventory is read through the ndh
domain's
`NdhKeystoreReader` seam (the single reader of `.ndh-ssh.d/keys.yaml`, shared with manifests so the
keys.yaml navigation is never duplicated).

The sops-encrypted cluster-CA bundle and the admin kubeconfig are *projections* — generated
per-cluster state, not source — and they **never enter the node image**. The image stays a single
homogeneous artifact: it bakes only the sops *declaration* (which secrets exist, their target paths
and modes), while the per-cluster *data* — the encrypted bundle — arrives at runtime. sops-nix carries
exactly this split: `validateSopsFiles = false` lets the declared `sopsFile` be a runtime path
(`/run/rke2lab/cluster-ca-bundle.yaml`, delivered over devlxd beside the age key), and
`sops-install-secrets` decrypts it on the node and places each CA file before `rke2-server`. No PKI is
frozen into an immutable image, and no per-cluster image is built.

The projections still have to *persist* — the CA is stable across re-grows (destroy master, grow it
again, same CA), so the minted bundle is kept, not re-generated. That persistence is the **cellar**:
the `OpaqueCellar` seam the seed already owns (`cellar.store` at harvest, `cellar.fetch` at the next
grow). It is deliberately **not a git branch** — nothing reads the bundle *from* git: not Flux (it is
no manifest), not nix (`validateSopsFiles = false` keeps it out of the eval), not a checkout. The only
consumers are host-side at runtime — the grow (which projects it into the instance's devlxd config)
and the readiness probe (which reads the kubeconfig). So the cellar seam suffices; the gitignored,
per-checkout `.local.d` is retired as a home for anything that must outlive a working tree.

Concretely, three cellar cases carry the PKI under `ClusterPkiCoordinate` (the cluster-pki domain's
dual-realm coordinate — owned by the producing domain, so the incus GROW depends on it, not the
reverse): `ClusterCaBundle` — the sops blob, filed `PLAIN` because it is already sealed for the
node's age recipient; `ClusterAgeKey` — the cluster age identity that decrypts it on the node, filed
`SEALED` (the `CellarCipher`) so its plaintext never rests beside the bundle; and `AdminCredentials`
— the operator's admin client cert + key + server-ca chain, filed `SEALED` (it carries the admin
private key). The seal scion (an OSGi `@SeedScenario` that seals the bundle through the
`SopsEncryptor` edge, derives the identity through ssh-to-age, and mints the admin leaf from
`client-ca`) files all three; the GROW fetches the node cases (revealing the sealed key) and poses
them on the instance's `user.rke2lab.cluster-ca-bundle` / `user.rke2lab.sops-age-key` devlxd keys,
never inside the (PLAIN) `InstanceGrowPlan`. The `AdminCredentials` case is revealed twice today: by
the host runbook (which renders the operator kubeconfig to `kubeconfigRef`, the current sink) and,
for the new synthesis path, by the manifests scion in-container — which hands the record to the
synthesis as it is and renders the kubeconfigs — see the delivery section below.

A fourth case, `ClusterIssuerCa`, carries a dedicated **cluster-issuer CA** — a sixth CA the seal
mints under the SAME intermediate as the five rke2 leaf CAs, so it chains to the mammoth-skate root,
but kept OUT of the node bundle. It is filed `SEALED` (it carries the CA private key). Its purpose is
the two-tier cert-manager convergence: the CA chain + key are delivered in-cluster into `kube-system`
(cert-manager's cluster-resource-namespace) via the durable `NODE_BOOTSTRAP` lane, where a
cert-manager `CA` `ClusterIssuer` (`rke2lab-ca`) signs every in-cluster leaf — the flox webhook
serving cert, the CAPI operator certs, future webhooks — so all chain to our own root instead of a
forest of independent self-signed issuers. Deliberately low-privilege and distinct from the rke2
CAs: cert-manager never receives an rke2 CA private key, so a compromise of the issuer CA mints only
application leaves, never kube/etcd client certs. The manifests scion reveals it in-container and
hands it to the synthesis as it is; the delivering unit stamps only the key Secret onto the
`NODE_BOOTSTRAP` lane, while the `ClusterIssuer` object itself (no secret) renders onto the branch.

The secret channel to the node is the same membrane the per-node *identity* already uses: **devlxd**.
The host poses the cluster age key on the incus instance; the identity oneshot (which already reads
`user.rke2lab.*` over `/dev/incus/sock`) writes it to `/run` so `sops-nix` can decrypt the bundle and
place the CA set — no `/srv/host`, no mount that an out-of-band remote grow can't resolve. `sops-nix`
is wired directly into the node image (it is a plain flake input; the ndh nixos sops *module* is not
imported — that would violate the invariant that nix-darwin-home is never a flake input of rke2lab).

== Anti-patterns this retires

* ❌ **Shelling `kubectl`** from the readiness probe (a `ProcessBuilder` per contact, a CLI on the
  host's PATH) → ✅ a Java kube client (fabric8) reading a real kubeconfig object.
* ❌ **A host-mount kubeconfig channel** (`/srv/host/kubeconfig`, dead since the `/srv/host` teardown)
  → ✅ a host-side derivation that needs nothing mounted from the node.
* ❌ **Fetching + rewriting rke2's runtime kubeconfig** (discover the address, patch `127.0.0.1`,
  carry a self-signed CA, skip-verify) → ✅ the endpoint is the node's deterministic mDNS name, the CA
  is the trusted root, the whole file is deterministic.
* ❌ **A fresh self-signed cluster CA per node** (kubeconfig invalidated on every re-grow) → ✅ one
  pre-seeded CA, constant across the destroy/recreate loop.
* ❌ **`kubeconfig != null` as the "published" check** (always true on a hardcoded path) → ✅ the phase
  checks the file actually exists at the published, config-derived path.
* ❌ **Baking the PKI into the node image** (a secret frozen in an immutable, shared artifact; forces a
  per-cluster image) → ✅ a single homogeneous image bakes only the sops *declaration*; the encrypted
  bundle is delivered at runtime over devlxd (`validateSopsFiles = false`, runtime `sopsFile`).
* ❌ **Projections in the gitignored `.local.d`** (per-checkout, lost on re-checkout) → ✅ they persist
  in the `OpaqueCellar` seam the seed owns (`cellar.store`/`cellar.fetch`) — durable and regenerable,
  and read only host-side, so no git branch is needed.

== Delivery: the kubeconfig as a synthesized local-config manifest

The kubeconfigs ride the ONE synthesis pipeline the rest of the cluster's manifests already ride — a
`kind: Config` is a real (client-side) Kubernetes resource, so cdk8s models it natively and the KRM
`config.kubernetes.io/local-config` annotation is the standard discriminator between "apply into the
cluster" and "materialize, don't apply." No cdk8s extension is needed (this is the lesson of the
retired `systemd-cdk8s`: only genuine k8s resources belong in the synthesis; a kubeconfig qualifies,
a systemd unit did not).

`ClusterKubeconfigManifestsUnit` (cluster-api domain) renders the admin kubeconfig two ways from one
material, discriminated by `local-config`:

* **The operator kubeconfig** — endpoint the node's mDNS name (`<cluster>-<node>.local`), the endpoint
  seed-outcluster reaches the management node it seeded over. Carried in a `local-config` Secret so the
  exploder lands it as a hidden dotfile RKE2 never applies; it is meant for host-side consumption (the
  readiness probe's kubeconfig). Until that sink is wired (below), this dotfile is redundant with the
  host runbook's own render of the same kubeconfig to `kubeconfigRef` — the render the synthesis path
  will retire.
* **The CAPI `<cluster>-kubeconfig` Secret** — endpoint the kube-vip VIP (the stable in-cluster
  endpoint; mDNS does not resolve inside the cluster). The canonical Cluster API kubeconfig Secret
  (data key `value`, type `cluster.x-k8s.io/secret`, `cluster.x-k8s.io/cluster-name` label) that
  CAPI reads in-cluster to seed the OTHER nodes (further control-plane + workers). It lives in the
  cluster's own namespace (`<cluster>`, CAPI's one-namespace-per-managed-cluster convention),
  materialized alongside the (future) `Cluster` CR. seed-outcluster itself seeds only the *management*
  node; CAPI (in the management cluster) greenfield-creates each workload cluster's own nodes
  (master + peers + workers).

The material reaches the synthesis as the owner's record: `AdminCredentials` (cluster-pki) is revealed
from the cellar in-container by the manifests scion, handed to `manifests-core` as it is, and the
kubeconfig unit renders it through `OperatorKubeconfig` — the one renderer, here for one cluster and one
way in. Until 2026-10-10 a manifests-side copy, `OperatorPkiMaterial`, stood in between with a
second, single-endpoint renderer. It existed to satisfy a staging gate (`DUAL_REALM_JUSTIFIED`) that
was retired on 2026-08-09, and domain contracts are how this project's domains wire to each other,
so it went with the four other copies of foreign sealed records; a golden render of the kubeconfig
unit proves the bytes did not move.

The flox-controller webhook's *serving* certificate no longer rides this thread: since 2026-09-06
(`9949119f7`) cert-manager mints and renews it in-cluster from the `rke2lab-ca` `ClusterIssuer`, and
its ca-injector fills the `MutatingWebhookConfiguration` `caBundle`. The seal-minted
`WebhookServingCredentials` and its manifests-side `WebhookServingMaterial`, which this paragraph
used to describe, are gone.

**Additive seal (adding a case to a cluster already sealed).** The seal scion is idempotent on a
cellar hit — an existing `CLUSTER_CA_BUNDLE` means the CA is KEPT, never re-minted (keygen is random;
a re-seal would rotate every cluster cert). But a NEW sealed case introduced later — the webhook
serving leaf is the first — must still land on clusters sealed before it existed, WITHOUT touching the
CA. The seal does this additively: on a cellar hit it mints only the cases the cellar LACKS, from the
CA it already possesses. The CA key is not lost — the sealed `ClusterCaBundle` is encrypted for the
cluster age recipient whose identity the seal itself re-derives (ssh-to-age on the `rke2-cluster`
key), so the seal re-opens the bundle with `SopsDecryptor` (the twin of `SopsEncryptor`, realised by
`sops-edge`), recovers the existing `server-ca`, mints the missing leaf, and files it. No wipe, no
re-seal — the next grow of an existing cluster simply fills `WEBHOOK_SERVING` and the webhook
activates. This is the general mechanism for adding any future sealed case to a live cluster.

The kubeconfig user name is `<cluster>-admin`, unique per cluster: `users`/`clusters`/`contexts` are
global lists merged BY NAME, so a shared user name would collapse across clusters and both contexts
would point at one (wrong) user cert. The cluster + context names are already the cluster name; the
user name follows suit.

NOTE: The `.local.d`-vs-cellar tension in this document is not resolved. The host DOES write
`kubeconfigRef` (`.local.d/kubeconfig.yaml`) — see the next section — while § "The one idea" retires
`.local.d` as a durable home. The write is the live path; the durable home is the open question.

== The operator kubeconfig — every cluster, and every way IN to each

The kubeconfig the host writes to `kubeconfigRef` is not one cluster's file. It is a *document*
spanning every cluster this management plane opened, rendered by the `OperatorKubeconfig` record
(cluster-pki-contract): a list of `ClusterAccess`, each pairing one cluster's `AdminCredentials` with
the `Access` list — `(contextName, server)` — that reaches it.

=== Why a document record, and not a method on `AdminCredentials`

Because a multi-cluster kubeconfig cannot hang off ONE cluster's material. Each cluster has its own
CA hierarchy — a workload cluster's is a *sibling* of the management one (§ "Sibling roots") — so it
has its own `certificate-authority-data` AND its own admin certificate. `AdminCredentials` is
therefore a *component* of a cluster's entry here, and stays what its name says: three PEM blocks, no
rendering.

That is also why `ADMIN_CREDENTIALS` needed a list-shaped twin. It is a single cellar coordinate — the
seal's OWN cluster — where `WORKLOAD_CLUSTER_CAS` was already a list; the management cluster's admin
certificate opens nothing on a workload apiserver. `WorkloadAdminCredentials` closes that asymmetry,
exactly as `MANAGEMENT_CLUSTER_CAS` / `WORKLOAD_CLUSTER_CAS` closes it for the CA sets:

* *Seal.* From each entry of the `WorkloadClusterCas` set just resolved (never from the requested
  names — so a kept CA yields a kept credential and a fresh CA a fresh one, and the two cannot drift
  into an admin cert signed by a CA the cluster no longer has), `ClusterSeal.sealWorkloadAdmins`
  mints an admin leaf off that cluster's own `client-ca` and pairs it with its own `server-ca` chain.
  ADDITIVE, so the operator's kubeconfig does not churn a fresh certificate every run — but the keep
  is GATED on the credentials still matching the cluster: an entry is kept only while its
  `caCertPem` is byte-identical to the cluster's current `serverCa` chain. That check *is* the
  invariant, so no bookkeeping is needed.
* *File.* `ClusterPkiCoordinate.WORKLOAD_ADMIN_CREDENTIALS`, SEALED (admin private keys) and
  **OPERATOR_ONLY** — the one place this pair parts ways with the CA sets. Nothing in-cluster
  consumes it: CAPI mints its own `<cluster>-kubeconfig` Secret for a workload cluster from the
  BYO-CA we handed it. Carrying it onto the branch would be exposure bought for no reader.
* *Read.* The host, and only the host — one context per entry.

=== The contexts, and why each one earns its place

Endpoints are added HOST-side, because which endpoint a consumer can reach is the *consumer's* fact,
not the seal's — which is precisely why the credentials are endpoint-independent. The host reads them
from the netplan's own materialised projection (`network-blueprint.json`), never re-deriving them: it
does not compile against netplan (runtime scope) and must not restate its addressing law.

[cols="1,1,3",options="header"]
|===
| context | endpoint | why it is there, and its limit
| `<mgmt>` (**current**) | the netplan LAN address | 401 in 6.5 ms, and it kept answering straight THROUGH a cold start — when an operator most needs in. Limit: it is ONE node's address.
| `<mgmt>-vip` | the kube-vip VIP | 401 in 39 ms over the tailnet, and it survives the node being replaced. The limit it used to carry — "it needs the cluster healthy enough to run that Connector, so it was mute for minutes after the same cold start" — is GONE since 2026-09-27: the route is advertised by the bare-metal that owns the `vmnet` bridge, not by a pod inside the cluster, so it outlives the cluster it points into.
| `<mgmt>-mdns` | `<cluster>-<node>.local` | last, never current: from the operator's Mac it resolves to the node's GLOBAL IPv6, not the LAN. But it is the only one needing no address at all — what saves it the day the LAN carve moves.
| `<workload>-vip` | that cluster's kube-vip VIP | the ONLY way in to a cattle cluster. Its nodes take an ordinary router lease under a name the provider mints, so neither the projected LAN address nor an mDNS name describes them.
|===

The mDNS context is keyed on the node NAME — admissible HERE and nowhere else: a management node is
an adopted *pet* with a deterministic name, not the CAPI cattle that rule is about.

`vipHost` is a CLUSTER-scoped value the projection deliberately repeats on every node of a cluster,
which is what makes the workload row answerable at all: a workload cluster's real node names are the
provider's cattle names and appear nowhere in the projection, so no node can be named when asking for
its VIP.

Every one of these is in its apiserver's `tls-san` superset, so kubectl needs no
`--insecure-skip-tls-verify` on any of them. Verified live on the workload cluster (2026-09-23): the
served chain is `kube-apiserver` ← `rke2-server-ca` ← `rke2-intermediate-ca` ← `mammoth-skate-tls`,
with the VIP among the SANs — our BYO-CA, not an rke2 self-signed one.

== Rotating the root — breaking "stable across re-grows" on purpose

Everything above makes the CA *stable across re-grows*. Rotating the root — changing
the CA itself, not just re-growing a node — must therefore defeat that stability on
purpose. The seal is **idempotent on a cellar hit**: `ClusterPkiSealScenario` fetches
`ClusterPkiCoordinate.CLUSTER_CA_BUNDLE` and, if present, keeps it rather than
re-minting. So a plain `pulumi up` after changing the root re-grows the node onto the
*old, still-cellared* CA. Rotation is a deliberate three-part ceremony: change the
source, clear the cache, re-grow.

The trigger to date: `mammoth-skate-tls` was minted with step's `root-ca` profile,
which stamps `pathLenConstraint: 1` — at most one intermediate below the root. Our
chain nests two (`rke2-intermediate-ca` -> `server-ca`) before the leaf, so a strict
verifier (OpenSSL / rustls — any kube-rs client, e.g. flux9s) rejects the served chain
with `X509_V_ERR_PATH_LENGTH_EXCEEDED`, while client-go anchors early and passes. The
fix re-mints the root with no `pathLenConstraint`.

. **Re-mint the root in ndh** (the owner of the tree). Same key, so every intermediate
and leaf signed under it stays valid — only the root cert changes:
+
[source,bash]
----
# from the ndh (nix-darwin-home) repo root
nix run .#authority-bootstrap-tls-root -- mammoth-skate-tls --force
----
+
Commit `keys.yaml`, then **sync the subtree down** into rke2lab so the seal reads the
new root from `.ndh-ssh.d/keys.yaml` (procedure:
link:../../../.ndh-ssh.d/README-SUBTREE.md[.ndh-ssh.d/README-SUBTREE.md]). Verify the
synced copy:
+
[source,bash]
----
yq -r '.authorities."mammoth-skate-tls".ca_crt' .ndh-ssh.d/keys.yaml \
  | step certificate inspect - | grep -A1 'Basic Constraints'   # expect CA:TRUE, no pathlen
----

. **Clear the cached PKI** so the next seal re-mints. The three `cluster-pki` cases
(§ "The one idea") persist as cellar `Entry` resources in the Pulumi state:
+
[source,bash]
----
pulumi state delete 'urn:pulumi:dev::rke2lab::rke2lab:cellar:Entry::cluster-ca-bundle' --stack dev
pulumi state delete 'urn:pulumi:dev::rke2lab::rke2lab:cellar:Entry::cluster-age-key'   --stack dev
pulumi state delete 'urn:pulumi:dev::rke2lab::rke2lab:cellar:Entry::admin-credentials' --stack dev
----
+
Delete **all three** — they are minted as a set (the CA, the age key that decrypts it
on the node, and the admin leaf), so a partial delete leaves a mismatched bundle.

. **Re-grow.** A running node reads the bundle only at boot, so delete the master to
force a fresh devlxd fetch, then re-seed:
+
[source,bash]
----
pulumi destroy --target 'urn:pulumi:dev::rke2lab::incus:index/instance:Instance::seed-instance' --stack dev
pulumi up --stack dev
----
+
The seal mints the new CA, the grow poses it over devlxd, and the run re-publishes the
operator kubeconfig at the same mDNS endpoint. Finally refresh the root in the host
trust stores (`nixos-rebuild switch` on the operator hosts) and swap it into any
standing kubeconfig CA bundle (dropping the old root).

[WARNING]
====
Order matters. Sync the new root **before** clearing the cellar and re-seeding. If the
cellar is empty but `.ndh-ssh.d/keys.yaml` still holds the old root, the seal re-mints
the *old* CA and the rotation is silently lost.
====

* ✅ **Same-key re-mint + cellar purge + re-grow** — the root changes, the derived CA
  set is re-minted from it, the node boots onto the new trust chain.
* ❌ **`pulumi up` alone after editing `keys.yaml`** — the cellar hit short-circuits the
  seal; the node re-grows on the old CA and nothing changes.
* ❌ **Deleting only `cluster-ca-bundle`** — leaves a stale age key + admin leaf that no
  longer match the freshly minted CA.

No SSH blast radius: SSH host/user certs chain to the separate `mammoth-skate`
authority (OpenSSH format, no X.509 `pathLen`); rotating `mammoth-skate-tls` touches
only the TLS side.

== Workload clusters — the same root, delivered as CAPRKE2 BYO-CA secrets (C2)

The management node gets its CA as a sops bundle its own `sops-nix` lays under `server/tls/`. A
*workload* cluster is different: `seed-outcluster` never grows its nodes — CAPI/CAPRKE2 greenfield them
in the management cluster. So the workload's deterministic CA is delivered the way CAPRKE2 already
delivers a bring-your-own CA: as four Kubernetes Secrets it looks up *by name* in the cluster's
namespace, whose cert/key it then writes into each node's `server/tls/` through the node's cloud-init
(the same uniform bootstrap channel). If those Secrets are present CAPRKE2 uses them; if absent it
self-generates a random CA. C2 pre-creates them so every workload chains to *our* `mammoth-skate-tls`
root, stable across re-grows.

=== The four secrets — the CAPRKE2 contract

Per workload cluster `<cluster>` (the CAPI `Cluster` name `<host>-<role>`), in its namespace
`rke2lab-<cluster>`, type `cluster.x-k8s.io/secret`, label `cluster.x-k8s.io/cluster-name`, data
`tls.crt`/`tls.key`:

[cols="1,1,2",options="header"]
|===
| Secret | rke2 `server/tls` file | our CA bundle key
| `<cluster>-ca` | `server-ca.{crt,key}` | `server-ca`
| `<cluster>-cca` | `client-ca.{crt,key}` | `client-ca`
| `<cluster>-etcd` | `etcd/server-ca.{crt,key}` | `etcd-server-ca`
| `<cluster>-peer-etcd` | `etcd/peer-ca.{crt,key}` | `etcd-peer-ca`
|===

Each `tls.crt` is the full chain to the root — byte-identical to the mgmt node's `server/tls` files.
CAPRKE2 discovers them by name only; there is no field on `RKE2ControlPlane` to reference them.

=== Sibling roots, not a child of the mgmt CA

Each workload cluster gets its OWN CA hierarchy rooted *directly* on `mammoth-skate-tls` — a
**sibling** of the mgmt CA, with independent keys, so a compromise of one cluster's CA never reaches
another. It is NOT signed by the mgmt CA (that would need the mgmt CA private key at the signing
locus, add chain depth, and — via the low-privilege cluster-issuer CA — break the privilege
boundary). The `ClusterCaGenerator` that mints the mgmt CA is simply called once more per workload
cluster.

=== The seal → reveal → render thread

The workload CA rides the SAME seal→cellar→reveal→render machinery as `ClusterIssuerCa`, plus one
input carrying the workload cluster names:

* *Seal (cluster-pki).* `ClusterSeedScenario` digs the workload cluster names out of the manifests
  facet (`workloadTargets`) and sows the cluster-pki crossing with the neutral `WORKLOAD_TARGETS`
  amendment; the `ClusterPkiSealAmendReflector` binds it onto `ClusterPkiSealInput`. The seal scion
  mints the four CAs per cluster *additively* (a cluster already in the cellar keeps its CA — stable
  across re-grows; a new one is minted; a removed one drops) and files them SEALED under
  `ClusterPkiCoordinate.WORKLOAD_CLUSTER_CAS` as a `WorkloadClusterCas` record.
* *Reveal (manifests).* `ManifestSynthesisScenario` reveals that record at the owner's
  `ClusterPkiCoordinate.WORKLOAD_CLUSTER_CAS` and hands it to the synthesis as it is; a cluster's
  set is looked up with `WorkloadClusterCas.forCluster`.
* *Render.* `ClusterApiWorkloadManifestsUnit` looks up each workload target's entry and renders its
  four Secrets onto the durable `NODE_BOOTSTRAP` lane (a real CA private key — never on the
  Flux-reconciled branch; a secret-blind in-cluster render finds nothing and omits them).

=== The management cluster — the SAME delivery, for adoption

The management cluster is adopted into CAPI in-cluster (see
xref:management-workload-topology.adoc[the topology doc] `[[mgmt-adoption]]`): the
`seed-incluster` creates the CAPI CR-set describing the RUNNING control plane, and CAPRKE2
adopts it only if it finds the four `<mgmt>-{ca,cca,etcd,peer-etcd}` BYO-CA Secrets carrying the
cluster's *LIVE* CA — the very CA the running apiserver issues from, or the minted admin cert is
rejected. That CA is the mgmt cluster's own node bundle (`CLUSTER_CA_BUNDLE`), which is already
minted at seal but stored only as the node's sops blob (decrypted node-side). So a second,
render-usable form is filed alongside it:

* *Seal.* the seal builds a `ManagementClusterCa` record (the four pairs from the same node bundle,
  the LIVE CA) and files it SEALED, reach `IN_CLUSTER`, under
  `ClusterPkiCoordinate.MANAGEMENT_CLUSTER_CAS` — re-filed on a keep so a re-grow converges its
  reach. It is the sibling of `CLUSTER_CA_BUNDLE`: same material, one as the node's sops blob, this
  as the render-usable pairs.
* *Reveal.* `ManifestSynthesisScenario` reveals it at the owner's
  `ClusterPkiCoordinate.MANAGEMENT_CLUSTER_CAS` and hands it to the synthesis as it is.
* *Render.* `ClusterApiManagementManifestsUnit` renders the four BYO-CA Secrets on the branch
  (sops-encrypted — Flux needs them to reconcile the adopted cluster), NAMELESS at the seal: the
  render owns the mgmt cluster name (`bootstrapIdentity`), which the seal does not hold.

=== The CAPN provider identity — a sibling MANDATORY seal

The workload's CA is not the only credential its birth needs: CAPN (the in-cluster incus provider)
must also authenticate to the incus remote to provision the nodes. That credential is the
`<host>-incus-identity` Secret the `LXCCluster.spec.secretRef` names, rendered on the same
NODE_BOOTSTRAP lane by `ClusterApiWorkloadManifestsUnit`. It rides its own pre-provisioning seal,
the twin of the cluster-pki seal: the host offers the host-world creds (the incus remote address and
the bundled capn-provider client cert) as the `INCUS_IDENTITY` amendment carried by
`IncusIdentitySealInput`; the `IncusIdentitySealScenario` reads the remaining one — the client key —
in-container from `.secrets:incus.capn.clientKey` (off the amendment wire, never on the branch),
seals the assembled identity, and `ManifestSynthesisScenario` reveals it.

There used to be a third host-world cred, the operator's server cert from `~/.config/incus`. It is
gone, and the next section is why.

Unlike the replicator secrets, this identity is *MANDATORY* — a workload cannot be grown without it,
so there is no fallback: an absent amendment, an incomplete cred, or a missing client key each raise
an explicit exception rather than silently skipping. The record is always complete (its constructor
rejects a blank field), so an unusable identity cannot even be constructed.

[[capn-trusts-by-ca]]
== CAPN trusts the Incus listener by CA, not by pinning its leaf (📐 2026-10-01)

This section is the same idea as the whole document, applied one layer out. Everything above is about
*owning the root* so a certificate can be reissued without redistributing trust. The CAPN provider
identity was the one place that still pinned a LEAF — and so was the one place where reissuing a
certificate broke something.

=== The defect: a pinned leaf is an unreplaceable certificate

`cluster-api-provider-incus` reads exactly six keys from the identity Secret — `server`,
`server-crt`, `client-crt`, `client-key`, `project`, `insecure-skip-verify`. There is *no* `ca-crt`
key. It passes `server-crt` straight to the incus client's `TLSServerCert`, which is the *pinned
remote certificate*: the client compares the presented leaf against it and logs its fingerprint.

Three consequences followed, and the third is the one that hid:

. Every regeneration of the listener certificate invalidated every pinned copy at once — and a cold
  start does one. The certificate was, in practice, unreplaceable.
. The operator's `~/.config/incus/servercerts/<host>.crt` became a build input: `ClusterSeedScenario`
  read it, the `INCUS_IDENTITY` amendment carried it, the seal filed it.
. *A pin SKIPS name verification.* Measured 2026-10-01: both cluster members serve one certificate —
  `incus cluster update-certificate` installs a single cluster certificate everywhere — and its SAN
  named only `bioskop`. `nixos.nikopol` therefore served a certificate that never named it. Nothing
  complained for as long as the pin was there.

=== The exit, which the incus client documents itself

[quote, incus client/connection.go]
____
Unless the remote server is trusted by the system CA, the remote certificate must be provided
(TLSServerCert).
____

Read the other way, that sentence is the design: make the listener trusted by CA and the pin becomes
unnecessary. Verified in the incus 7.4 source rather than assumed —

* `shared/tls/tls.go` — `GetTLSConfigMem` leaves `RootCAs` nil when the server-cert PEM is empty, so
  Go falls back to the *system pool*;
* `client/util.go` — the transport then runs `VerifyHostname(config.ServerName)`, because
  `insecure-skip-verify` is false. The exact-match path is a separate flag and stays off.

So dropping `server-crt` buys chain verification *and* name verification. Which is why it could not
be dropped alone: it is the change that turns consequence 3 from invisible into fatal.

=== The three preconditions, all measured before the pin came out

[cols="1,3,1"]
|===
|What must hold |Why |Where it lives

|The listener leaf is signed by `mammoth-skate-tls`
|Otherwise no CA we can ship verifies it.
|ndh `mint-incus-listener-cert`

|Its SAN names EVERY member
|One certificate serves the whole cluster, so a per-host SAN leaves half the fleet unverifiable by
 name. Fixed by deriving the SAN as the union over every declared bare-metal.
|ndh `mint-incus-listener-cert`

|`remote.endpoint` is a NAME the SAN carries
|`VerifyHostname` checks the dialled name. `https://nixos.<host>:8443`, which is also what the
 cluster member URL now uses, so the name is the same everywhere.
|`ClusterApiManagementManifestsUnit`, ndh `incus-cluster`
|===

*Why `TlsAuthorityCaMaterial` is DERIVED and not read from the key-store.* The obvious source is
`NdhKeystoreCatalog.TLS_AUTHORITY` through `NdhKeystoreReader`, and it is the wrong one: IN_CLUSTER
the key-store is unreachable, and the in-cluster render is the steady state. A host-only read would
give the operator's render a CA and the cluster's render none — and with `server-crt` empty, "none"
is a provider that trusts nothing we signed. So it is the *last certificate* of
`ClusterIssuerCa.caCertChainPem`, which `ClusterCaGenerator` assembles as
`chainPem(issuerCa, intermediate, root)` with `root` being exactly that key-store entry. That
material is cellar-borne, hence present in both realms, and the derivation states the invariant that
matters: *the CA we ask a pod to trust is the root our own chain ends at.* Two independent reads
could disagree; one derivation cannot.

*Why the volume goes through `configSecret` and the env through `spec.deployment`.* CAPN's own
components file declares `volumes: ${CAPN_VOLUMES:=[]}` and `volumeMounts: ${CAPN_VOLUME_MOUNTS:=[]}`
— a declared extension point the CAPI operator substitutes from the provider's `configSecret`. The
env cannot go there (CAPN declares no variable for it), and `spec.deployment.containers[]` carries
`env` but neither `volumes` nor `volumeMounts`. So each half takes the only seam that can carry it.

* ✅ *Use the provider's declared substitution variables.* They survive an upstream rename of the
  Deployment.
* ❌ *Do not use `spec.patches` for the volume.* A strategic merge keyed on
  `capn-controller-manager` / `manager` goes SILENTLY inert the day either name moves — the failure
  shape this repo keeps getting bitten by (a tool answering "less" instead of "I cannot").
* ✅ *`SSL_CERT_DIR`, colon-separated, naming `/etc/ssl/certs` first.* Go replaces the directory list
  with this value, so naming the image's own store keeps it.
* ❌ *Not `SSL_CERT_FILE`.* It replaces the system bundle outright.
* ⚠️ *The `configSecret` contents are IMMUTABLE to the operator* — changing them means renaming the
  Secret. Affordable only because these two values NAME the CA Secret rather than carrying the CA, so
  rotating the authority changes `rke2lab-tls-authority-ca` and leaves `capn-provider-config` alone.

=== ⚠️ The guard that had to go, and the lane that replaced it (📐 2026-10-01)

`ClusterApiCrRenderer.identitySecret` briefly refused to render an identity when the render carried
no `TlsAuthorityCaMaterial`. The intent was right — without `server-crt` the Secret pins nothing, so
an identity with no anchor verifies nothing — and the PLACE was wrong, expensively:

* an IN-CLUSTER render is blind to host-sealed cellar cases, so it NEVER carries that material;
* the guard therefore failed every in-cluster render, for hours, with a message that read like a
  design violation rather than a realm mismatch.

And softening it would have been worse than the outage. The anchor Secret was on the ORDINARY branch,
so a *successful* in-cluster render would have emitted the branch WITHOUT it and Flux would have
PRUNED the fleet's trust anchor — the reward for a render finally working.

So the fix is the lane, not the guard. Three pieces, by what each needs:

[cols="2,1,3"]
|===
|What |Lane |Why

|`rke2lab-tls-authority-ca` (the CA PEM)
|NODE_BOOTSTRAP
|It is the only piece carrying material. Posed node-side at grow, never on the reconciled branch, so
 a render that cannot see it cannot withdraw it. `ClusterIssuerManifestsUnit`'s CA rides it for the
 same reason — which is the one that generalises, *not* its private key.

|`capn-provider-config` (the substitution variables)
|ordinary
|Static strings: the values NAME the CA Secret, they do not carry the CA. Every realm reproduces them
 byte-for-byte.

|`spec.configSecret` + `spec.deployment`
|ordinary
|A reference and a literal. Gating these is what let a render withdraw a wiring it could not see the
 reason for.
|===

* ✅ *Decide a lane by WHO CAN SEE the material, not by whether it is secret.* That was the actual
  mistake: "it carries no private key, so the ordinary branch is fine" reasons about the wrong
  property.
* ❌ *Do not assert a same-render invariant that only one realm can satisfy.* A guard that cannot hold
  everywhere the code runs is not a guard — it is an outage with a good error message.
* ⚠️ The cost is stated rather than hidden: a CA rotation lands at GROW, not on a reconcile — the same
  cost the cluster-issuer CA already pays. The way out is not the ordinary branch; it is giving the
  authority CA a source an in-cluster render can read, at which point the Secret moves back.

=== Troubleshooting

[cols="2,3"]
|===
|Symptom |Cause

|`x509: certificate signed by unknown authority` in `capn-controller-manager`
|The CA is not in the pod. Check the `rke2lab-tls-authority-ca` Secret exists in `capn-system`, that
 `capn-provider-config` is referenced by `InfrastructureProvider.spec.configSecret`, and that the pod
 actually has `/etc/rke2lab/ca/ca.crt` — the operator substitutes the variables only when it
 re-renders the provider.

|`x509: certificate is valid for <names>, not nixos.<host>`
|The listener certificate's SAN does not name the endpoint being dialled. Re-mint with the fleet-wide
 SAN and re-run `incus cluster update-certificate`. Verify per member, never per fleet:
 `openssl s_client -connect nixos.<host>:8443 -servername nixos.<host> -CAfile <ca> -verify_hostname nixos.<host>`.

|Reconciles succeed but a reissued listener cert breaks them later
|A `server-crt` has come back into the identity Secret. With the leaf present the pin wins, name
 verification is skipped, and the unreplaceable certificate is back.
|===
