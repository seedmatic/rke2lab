Brainstorm design (2026-09-13, whiteboard `.claude/claude-preview.adoc`) pour faire vivre le **cluster workload** par CAPI — déclenché par : (1) au **cold-start du mgmt**, le workload SURVIT (infra incus indépendante, son etcd) → il faut le **RÉ-ADOPTER**, pas le re-provisionner ; (2) conflit single-owner Flux↔CAPI si Flux rend le CR-set complet que CAPI/CAPN mute.

**Inflexion gravée : CAPI = MIROIR d'adoption des clusters qui tournent, PAS un provisionneur.** Control planes bootstrappés + adoptés (décrits par `providerID`, skip bootstrap) ; le cold-start re-décrit, jamais ne re-provisionne.

**Tranché :**
- **2 ressources / 2 rôles** (ne PAS mélanger créer vs adopter) : `ClusterProvision` (NOUVEAU, intention riche, owned par Flux) + `ClusterAdoption` (EXISTANT `adoption.seedmatic.io`, rôle inchangé = miroir, owned+attaché par le contrôleur une fois le CP dispo).
- **Contrôleur = reconcile niveau-déclenché, INVARIANT adopt-first** : chaque reconcile TENTE l'adoption d'abord ; `provision` = le simple fallback du cas « nœuds absents ». Collapse day-0/cold-start/sinistre en UN chemin idempotent. Provision vs adopt = **même CR-set CAPI, 2 modes** (neuf CAPRKE2-bootstrap vs existant par providerID, skip bootstrap).
- **Machine à états** `ClusterProvision.status.phase` (jamais kill/restart) : absent→`Provisioning`→`Adopting` ; présent+sain→`Adopted` (crée la ClusterAdoption) ; **présent+malade→`Degraded` (JAMAIS re-provisionner — détruire un nœud présent = perte)**. Le cold-start WIPE l'etcd mgmt → la ClusterAdoption disparaît (survit : ClusterProvision via Flux + le workload qui tourne) → le contrôleur re-dérive la réalité à chaque reconcile.
- **Watch / contrôleur mince** : le contrôleur `Owns` les CR CAPI qu'il crée (Cluster, RKE2ControlPlane, LXCCluster, Machine, LXCMachine) → leurs events requeue son reconcile → il DÉRIVE son `phase` des conditions que CAPI/CAPN maintiennent déjà (`Cluster.RemoteConnectionProbe`/`ControlPlaneInitialized` = CP sain ? ; statut `LXCMachine` = instance présente ?) — PAS de sonde maison.
- **Renommages** : `ExecutionEnclosure.OPERATOR` → **`STANDALONE`** (face à `IN_CLUSTER` ; `HOST` écarté = collision hôte incus). Contrôleur `rke2-adoption-controller` → **`seed-incluster`** (jumeau in-cluster de seed-master ; `seed-cluster` écarté = collision `ClusterSeedScenario`). **seed-master gardé** (module phare, blast radius).
- **Contrôleur MINCE / intention RICHE** : seed-master (SOT `ClusterNetworkBlueprint`) remplit `ClusterProvision` en valeurs concrètes ; ZÉRO logique d'adressage en Go (sinon on duplique le blueprint Java).

- **Relation + vue opérateur** : chaîne d'ownerRef `ClusterProvision` --> `ClusterAdoption` --> `CAPI Cluster (+CP/infra/Machines)` (cascade ; seul le ClusterProvision survit au cold-start via Git/Flux → re-sème la chaîne ; `kubectl delete clusterprovision` = GC cascade). Opérateur : `kubectl get clusterprovision -A` (colonnes PHASE/ENDPOINT/NODES — pane DURABLE, toujours là) + `kubectl get clusters -A` (vue CAPI standard, gratuite car on miroite dans CAPI).

**ClusterAdoption spec actuel** (déjà riche) : clusterName, clusterNetwork(pod/svc CIDRs), controlPlaneEndpoint(VIP), controlPlaneReplicas, identitySecretName, image.fingerprint, kubeVIPVersion, rke2Version, namespace.

**★ LE CŒUR (ce qui manque à généraliser) : adopter = réconcilier avec un cluster DÉJÀ EXISTANT, idempotemment.** L'`Adopting` matche le cluster en marche par `providerID` déterministe (`lxc:///<cluster>-<node>`, SOT blueprint) → matérialise le CR-set CAPI en **mode adopt** (`providerID` posé + **bootstrap SKIPPÉ** → CAPRKE2/CAPN ne re-bootstrappent/re-créent PAS) → CAPI DÉCRIT l'existant. Idempotent (ré-exécutable chaque reconcile). Raison d'être de seed-incluster (CAPI/CAPRKE2 ne savent pas nativement adopter un rke2-on-incus qui tourne). Prouvé mgmt (self-adoption) → à généraliser workload + idempotence cold-start.

**★ INVARIANT single-adopter (topologie des plans de management)** : un cluster est adopté par EXACTEMENT UN plan de management (single-owner remonté au grain cluster ; 2 seed-incluster sur le même cluster = 2 owners du même ClusterAdoption/CR-set = flap). Donc **seed-incluster ne tourne QUE dans un plan de management** — aujourd'hui le **mgmt seul** (son etcd porte les CR mgmt ET workload ; CR workload rendus sur `manifests/<host>-mgmt`). Le **workload est MANAGÉ** (adopté DEPUIS le mgmt), ne fait PAS tourner seed-incluster (sinon 2e owner). Le mgmt s'auto-adopte in-cluster **parce qu'il est la RACINE** (rien au-dessus ne peut l'adopter, bootstrappé hors-bande par seed-master) ; tout cluster non-racine est adopté par son plan parent, ne s'auto-adopte jamais. **« Un cluster déjà managé par CAPI/CAPN peut-il être adopté in-cluster ? » → NON** (double-owner ; l'adoption a lieu une fois, depuis le plan parent). seed-incluster tourne dans CHAQUE plan (récursif) — voir le bloc FÉDÉRATION ci-dessous : le mid-tier fait tourner seed-incluster pour SES enfants mais est lui-même adopté par son parent (PAS self-adopt) ; seul le root s'auto-adopte ; feuilles jamais.

**★★ FÉDÉRATION = concern de PREMIER ORDRE (user 2026-09-13, « il faut y penser maintenant »).** Le modèle est RÉCURSIF : un plan fait NAÎTRE + adopte ses enfants avec le même contrôleur adopt-first ; un enfant qui est LUI-MÊME un plan refait pareil pour SES enfants. Décisions :
- **Tier-B PRÉFÉRÉ (2 étages) vs A (remote direct).** B = `bioskop-mgmt` manage `nikopol-mgmt`, qui manage `nikopol-wrkld` LOCALEMENT. Seul le hop rare mgmt-of-mgmt traverse le tailnet ; le hot-path workload reste host-local (= la préférence host-local de l'ancre : autonomie par hôte). A (bioskop-mgmt pilote directement le remote incus de nikopol pour le workload) = alternative, couple le hot-path au reach fragile.
- **★ VRAIE fédération : `nikopol-mgmt` n'est PAS bootstrappé STANDALONE par seed-master — il est PROVISIONNÉ IN-CLUSTER par le seed-incluster de bioskop-mgmt** (même funnel provision-puis-adopt ; son unique nœud naît via CAPN sur le remote incus de nikopol, puis adopté). Le chicken-and-egg de l'ancre ne mord QUE le root (créateur=créé). Mapping enclosure EXACT : **STANDALONE = le root SEUL** (seed-master sème bioskop-mgmt hors-bande, fait naître UN cluster point) ; **IN_CLUSTER = tout le reste récursivement** (workloads feuilles ET sous-plans). Turtles-all-the-way-down sur un seul plancher nix.
- **Récursion single-adopter** : root (bioskop-mgmt) s'auto-adopte ; mid-tier (nikopol-mgmt) est PROVISIONNÉ+adopté par son parent (ne s'auto-adopte PAS) MAIS fait tourner son propre seed-incluster pour son enfant ; feuille (nikopol-wrkld) adoptée par nikopol-mgmt, aucun seed-incluster. « Être un plan » ⊥ « qui me fait naître/adopte ».
- **Remote incus = niveau CLUSTER, pas per-nœud** (CAPN natif : `LXCCluster.secretRef` = 1 remote ; tous les LXCMachine du cluster y atterrissent ; fabric partagée BGP exige les nœuds pairs L2/L3 sur 1 bridge/hôte → un cluster ne s'étale jamais sur 2 remotes ; le cross-host est ENTRE clusters). `IncusIdentitySecretManifestsUnit` → per-remote. Le remote ne sert qu'à faire naître le NŒUD unique d'un sous-plan, pas une flotte.
- **4 exigences design NOW** : (1) KIND dans `ClusterProvision.spec` (`workload` feuille vs `management` sous-plan) → sélectionne la saveur de RENDER de l'enfant (un `management` reçoit CAPI-operator + seed-incluster + SES propres ClusterProvision) ; (2) placement CR suit la frontière de tier (un plan possède les CR de SES enfants dans SA branche `manifests/<host>-mgmt`) ; (3) ordering level-triggered outside-in (l'etcd de nikopol-mgmt n'existe qu'après que bioskop-mgmt l'ait fait naître → convergence, zéro orchestration explicite) ; (4) remote cluster-level. Doc : `cluster-seeding-controller.adoc` §Federation.
- **FONDATION adressage DÉJÀ LÀ (vérifié)** : `ClusterNetworkBlueprint.hostOf(clusterName)`→`hostId()` définit DÉJÀ les deux hôtes (`bioskop`=0, `nikopol`=1, TEST=2 ; lignes 291-294), tout span = `f(clusterId=(hostId<<1)|roleId)`. Donc bioskop-mgmt porte DÉJÀ les 2 identités. UNE SSOT (blueprint) → DEUX couches de provisioning : **ndh** provisionne l'HYPERVISEUR (`nikopol-nixos` + son engine incus + fabric, via netplan/dataplan `catalog.datasets`) ; **seed-incluster** provisionne le NŒUD cluster (`nikopol-mgmt-master`) SUR ce remote. Reste = PROJETER (pas définir) : dériver `spec.remote` + Secret identité CAPN per-remote depuis la dimension hôte du blueprint.
- **★ Cross-host trust = WIRING, PAS un canal manquant (correction user : mon 1er framing « pas de canal sécurisé » était BIAISÉ).** rke2lab + ndh PARTAGENT DÉJÀ la clé age (sops) + les filtres git smudge/clean (`git-sops-filter` SSOT ndh) → UN SEUL domaine de confiance sops → le canal existe. + l'essentiel du matériel est PUBLIC (trust incus par fingerprint : ndh n'a besoin que du cert client CAPN public à ajouter au trust ; server-crt public ; clés privées restent chez elles). Transport = git sops partagé + flux dataplan rke2lab→ndh existant. Résidu MINCE. **★ ENCORE réduit (user) : on POSSÈDE la PKI incus** — les server-certs de chaque engine ET le cert client CAPN sont MINTÉS depuis notre root (`mammoth-skate-tls` ndh, même PKI que deterministic-cluster-access / BYO-CA cellier). Donc trust = **CA-based, pas échange runtime** : ndh configure chaque engine à truster notre CA à la provision (server-crt minté du root) → tout cert client du même root accepté par TOUS les engines (appartenance CA) → bioskop/nikopol autorisés à requêter TOUS les remotes du network dès la génération, zéro `incus trust add` par-remote. Résidu = purement BUILD-TIME : dériver server+client certs cohérents avec les identités hôtes du blueprint + semer le trust-CA (ndh) + écrire le Secret per-remote. La clé age partagée ne porte que les clés PRIVÉES (qui ne bougent pas). Local bioskop déjà couvert (`IncusIdentitySecretManifestsUnit`).

**★★ INVARIANT DE SÛRETÉ (user 2026-09-13) — présence = existence, jamais re-provisionner un cluster présent.** Si AU MOINS UNE instance lxc/lxd matche (par providerID `lxc:///<cluster>-<node>`), **quel que soit son état** (même arrêtée/cassée) → le cluster EXISTE → mode ADOPT (décrire) ; CP malade → `Degraded` (surface, ne PAS détruire/re-provisionner). **Provisionner neuf UNIQUEMENT si ZÉRO match.** Raison : greenfield alors qu'un cluster (même mort) existe = split-brain / perte etcd. Détection **status-driven, PAS de sonde incus directe ni parsing d'events** (on ne by-pass pas CAPI/CAPN, on repose dessus) : on crée le CR-set en adopt-attempt (LXCMachine providerID posé) → on LIT les `LXCMachine.status` (`InstanceProvisioned=True`/found = présent — `GetInstance` retourne même une instance arrêtée) → K présents/N pets = présence partielle/complète ; `Cluster.RemoteConnectionProbe` = CP sain. Day-0 (zéro match) : re-créer le LXCMachine au MÊME nom pet avec providerID VIDE → CAPN launch déterministe. Reste à épingler : le reason exact CAPN not-found (`cluster-api-provider-incus/.../lxcmachine/controller_normal.go`).

**★ TAXONOMIE provisioner (user 2026-09-13) — 2 flows décidés par « présence ? »** : `BOOTSTRAP` (zéro match) = provisioner→cluster (greenfield, rien à adopter) ; `RECOVER` (≥1 match) = provisioner→adoption→cluster (décrire les survivants). **Réalisés par UN moteur (ClusterAdoption = builder du CR-set), 2 modes PAR-PET** dérivés du status CAPN : présent → forme-ADOPT (`LXCMachine` providerID posé + bootstrap sentinelle → CAPN adopte) ; absent → forme-PROVISION (`LXCMachine` providerID VIDE + VRAI bootstrap RKE2Config → CAPN launch AU NOM PET). Bootstrap = tous pets en forme-provision ; recover = tout/partie en forme-adopt. **Transition adopt→provision = DELETE + RE-CREATE (pas patch : providerID/spec/bootstrap immuables), PAR NOUS au nom pet** (jamais laisser le RCP greenfield = noms aléatoires → casse l'all-pets). Les 2 flows → cluster aux noms déterministes + owned par ClusterAdoption (cascade). Causalité : recover = adoption AVANT (ré-attache) ; bootstrap = cluster naît puis fait. Reste (day-0 follow-up) : reason not-found exact CAPN + CAPRKE2 accepte-t-il un owned CP Machine pré-créé avec vrai bootstrap.

**Asymétrie racine par rôle** (les 2 CR PAS toujours appariés) : **mgmt** (bootstrap) = racine `ClusterAdoption` SEULE (seed-master le bootstrappe hors-cluster ; seed-incluster tourne dedans, ne peut pas se self-provisionner → adopt-only) ; **workload** = racine `ClusterProvision` → possède une ClusterAdoption. Au cold-start mgmt : les deux → `Adopted` (mgmt self-adopté car le CP est forcément up quand seed-incluster tourne ; workload survécu re-adopté) — rien re-provisionné.

**#4 TRANCHÉ (user validé) : option (B) — PAS de bétail.** TOUS les nœuds (CP + workers) = pets nommés du blueprint (`CANONICAL_NODE_NAMES`, `<cluster>-<node>`), bootstrappés + adoptés par `providerID` ; **CAPI = miroir intégral** ; cold-start ré-adopte *tout* uniformément (même reconcile par nœud). Aucun nœud pré-existant jeté. Donc `ClusterProvision.spec` s'appuie sur la liste de nœuds du blueprint (PAS un pool cattle+replicas MachineDeployment).

**Groupe CRD TRANCHÉ = `cluster.seedmatic.io`** (ex-`adoption.seedmatic.io`) : nommé par le DOMAINE (cluster lifecycle : ClusterProvision+ClusterAdoption+futurs), PAS par le producteur → découplé du nom du contrôleur (qu'on renomme ; un groupe CRD est quasi-immuable), pas de stutter seed…seedmatic, parallèle direct de CAPI `cluster.x-k8s.io` (cohérent avec le rôle miroir). Blast : RBAC `apiGroups` dans Rke2AdoptionControllerManifestsUnit, nom du CRD staged, `groupName` kubebuilder Go, `apiVersion` des CR rendus.

**Détection "CP vivant" TRANCHÉE = dérivée de CAPI/CAPN, PAS de sonde maison** (principe contrôleur mince) : `Cluster.RemoteConnectionProbe`/`ControlPlaneInitialized` = CP sain ; statut `LXCMachine`/`Machine` = instance présente → agrégés dans `phase` via `Owns`/watch. Le garde-fou anti-re-provision lit la présence CAPN, pas une santé mesurée nous-mêmes.
