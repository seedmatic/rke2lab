= Post-Bootstrap In-Cluster Ownership Plan
:toc: left
:toclevels: 3

This note defines who owns what *after* Stage A, under the management/workload separation. It keeps
one canonical owner per concern and records earlier wrong assumptions only as footnotes, not as the
active design.

[IMPORTANT]
====
Rewritten for the *management/workload separation*. Read
link:management-workload-topology.adoc[Management / Workload Topology] (the anchor) first. Under the
old self-managed model, "the management cluster" *was* the seed (`bioskop`), scaled in place, and it
held every in-cluster controller at once. That is gone: the management cluster is dedicated,
single-node, on-demand, and holds *only* CAPI/CAPN/CAPRKE2; the GitOps / workflow / node-local
controllers live *inside each workload cluster*.
====

NOTE: The "no Flux in the management cluster" stance is revised, and now LIVE (validated 2026-08-25):
the management cluster runs its OWN Flux against `manifests/bioskop-mgmt` — GitRepository Ready and all
four layers (crds→foundation→operators→workloads) reconciling on the live cluster, exactly like a
workload. So the "one architecture for every cluster" target is reached for the delivery loop; the
near-term "seed-outcluster consumes the `-mgmt` branch" framing is superseded (seed-outcluster only nix-seeds
the node + bootstrap set; Flux-in-mgmt owns reconciliation thereafter). CAPI/CAPN/CAPRKE2 staying
management-only is unchanged. (Whether Flux runs inside a `gitops` vCluster vs directly in `flux-system`
is a separate packaging question, not yet settled.)

== Current intent

The active plan after Stage A is:

* keep `seed-mgmt` (the host-side Stage A seeder) as the external bootstrap authority for the
  *management* cluster only;
* let CAPI + CAPN + CAPRKE2, running *in the management cluster*, own the machine lifecycle of the
  *separate workload clusters* they greenfield-create — this is Tier 2 in the anchor's operating model;
* let each workload cluster run its own GitOps controller (Flux) that pulls its declarative add-ons
  directly from git — Tier 1, autonomous, no management cluster needed;
* run a workflow/pipeline controller *inside the workload clusters* for build, promotion, and delivery;
* run node-local reconcilers *on the workload nodes* for long-lived host-local runtime mutation.

This means the target control plane is not "one cluster with the Pulumi Operator plus everything
else".footnote:[Earlier planning treated the Pulumi Operator as the likely in-cluster provisioning
brain after bootstrap. That assumption is no longer the active plan because it overlaps too broadly
with the Stage B ownership of CAPI/CAPN/CAPRKE2 for machine lifecycle.] It is a split of specialized
controllers with clearly separated ownership, distributed across *two kinds* of cluster.

== Where each concern lives

The key change from the old model: the concerns no longer all live in one cluster. Machine lifecycle
sits in the management cluster; everything a running application needs sits in the workload clusters.

[cols="1,2,2",options="header"]
|===
| Concern | Canonical owner | Where it runs

| Management-cluster seed + handoff outputs
| `seed-mgmt` (Pulumi, host-side)
| Outside any cluster (Stage A)

| Workload-cluster machine lifecycle (create, scale, replace, rollout, remediation)
| CAPI + CAPN + CAPRKE2
| In the *management* cluster (Tier 2)

| Declarative add-ons / desired cluster services
| GitOps controller (Flux)
| In *each workload* cluster, pull-based (Tier 1)

| Build, promotion, delivery, workflow orchestration
| workflow/pipeline controller
| In *each workload* cluster

| Ongoing host-local runtime mutation and node drift correction
| node-local controller / privileged DaemonSet
| On *each workload node*
|===

The core design rule is unchanged — one canonical owner per concern — but it now reads across the
separation:

* CAPI (in the management cluster) owns *workload* machine lifecycle; it never scales the management
  cluster itself.
* GitOps (in each workload) owns declarative add-ons; it needs neither the management cluster nor the
  other host to reconcile — this is what makes a workload *autonomous* (anchor § _Operating model_).
* The workflow/pipeline controller owns build and delivery workflows, inside the workload where they
  belong.
* Node-local reconcilers own host mutation on already-running workload nodes.

That split is deliberate because CAPI is not the natural owner of ongoing host-local runtime
mutationfootnote:[A second wrong assumption was that CAPI might absorb host-local runtime mutation
expressed through staged systemd services. CAPI can create machines; the active plan treats ongoing
host-runtime reconciliation as a node-local controller concern.] and the workflow/pipeline controller
is not the natural owner of either node lifecycle or host drift correction.footnote:[A third wrong
assumption was that the workflow/pipeline controller might become a general post-bootstrap
orchestrator. The corrected plan keeps it focused on build, promotion, delivery, and workflow
execution.]

== Concrete environment anchors

Two named Darwin bare-metals matter to the plan. The seed is *host-indifferent* (anchor § _Operator
experience_): either can be the Stage A seeding site; the management cluster travels.

* `bioskop` — Darwin bare-metal on the home LAN (`mac-mini m4 pro`)
** runs the NixOS Tart/VZ VM (`bioskop-nixos`) hosting the Incus server;
** hosts the *always-live* `bioskop-wrkld` (and Headscale, the workload mesh plane);
** target placement for the management cluster (`bioskop-mgmt`).
* the Hyland enterprise MacBook Pro (`macos m4 pro`) — a separate Darwin host boundary
** runs the isolated NixOS Tart/VZ guest `nikopol-nixos`;
** hosts `nikopol-wrkld`.
* `nikopol` — the isolated NixOS guest inside the enterprise MacBook Pro
** provides the Incus server for `nikopol-wrkld`;
** reachable from the management cluster over the node mesh plane (`mammoth-skate`).

== Worktree distribution path (substrate source input)

The `rke2lab` git worktree is projected to the *seeding host* as a source input — orthogonal to the
management/workload split, but part of the concrete substrate:

. Darwin host worktree (source checkout)
. NFS-mounted worktree inside the NixOS Tart/VZ guest
. selected worktree folders bind-mounted where a guest process needs them

This matters because the worktree is neither a cluster-owned runtime output nor a daemonset host-asset
root — it is an upstream source input for the seeding host. Under the greenfield model, *workload*
node config is delivered by CAPN cloud-init from the baked `node-base` image, not by bind-mounting the
worktree into workload nodes.

== Canonical ownership split — guardrails

The following guardrails remain strict:

* no overlapping controller ownership for the same concern;
* no backward-compatibility orchestration aliases just to bridge the old self-managed assumptions;
* one canonical owner per lifecycle surface;
* CAPI/CAPN/CAPRKE2 exist *only* in the management cluster; a workload never runs them;
* systemd is a current bootstrap backend, not the long-term architecture concept;
* node-local reconciliation replaces durable host-mutation shell flows once a workload can host that
  control loop.

== C4 dynamic view

[mermaid,post-bootstrap-ownership-dynamic,svg]
----
flowchart TD
    step1[1. Operator commits desired CRs + sops secrets to git]
    step2[2. Operator runs pulumi up via seed-mgmt on EITHER host]
    step3[3. seed-mgmt nix-seeds the single-node management cluster<br/>and installs CAPI + CAPN + CAPRKE2]
    step4[4. seed-mgmt applies the workload CRs from git<br/>to the management cluster]
    step5[5. CAPI/CAPN/CAPRKE2 greenfield-create bioskop-wrkld local<br/>and nikopol-wrkld over the node mesh]
    step6[6. Each workload's Flux pulls its add-ons from git<br/>Tier 1, autonomous]
    step7[7. workflow controllers own build/delivery inside each workload<br/>node-local reconcilers own host mutation]
    step8[8. Management cluster may be stopped when idle<br/>workloads keep running from git]

    step1 --> step2 --> step3 --> step4 --> step5 --> step6 --> step7 --> step8
----

The dynamic view is intentionally simple: seed the management cluster on either host, greenfield the
two workloads (one local, one over the mesh), then let each workload's own pull loop take over. Because
Tier 1 is autonomous, the on-demand management cluster can be stopped once machine lifecycle is
quiescent without touching the running workloads.

== Summary

The real plan is now:

* external `seed-mgmt` for the *management-cluster* seed only;
* CAPI + CAPN + CAPRKE2 in the management cluster for *workload* machine lifecycle (Tier 2);
* GitOps/Flux in *each workload* for declarative add-ons (Tier 1, autonomous);
* workflow/pipeline controller in *each workload* for build/promotion/delivery;
* node-local reconcilers on *each workload node* for host-local runtime mutation.

The earlier one-cluster, Pulumi-operator-centered idea remains only as historical context in
footnotes, not as the active architecture.
