Constat live au cold-start du 2026-09-09 (validation du rename ingress→tailscale + fix funnel-cert namespace-agnostic). Les proxies tailscale montent, **zéro dérive** (FQDN propres `pipelines-webhook`/`flux-webhook` sans suffixe `-N`), MAIS la **réutilisation de cert n'a PAS lieu**.

**Le nœud (conflit de conception, pas un bug ponctuel) :** `TailnetPurgeManifestsUnit` (GC des devices périmés, gate AVANT l'opérateur) et `FunnelCertRestore`/`FunnelStatePersistence` (restaure l'identité device + cert persisté sur PV Retain) poursuivent des buts opposés :
- La **purge** SUPPRIME du tailnet les vieux devices (pour éviter que le nouveau proxy dérive à `pipelines-webhook-N`).
- La **persistence** veut restaurer l'IDENTITÉ device persistée (`_machinekey`/`_profiles`/`device_id`) pour que le même device réutilise son cert LE.
- Mais la purge efface justement le device que la persistence restaure → le proxy se ré-enregistre NEUF → nouvelle identité → **re-fetch ACME dns-01 complet** (log proxy : `no cached certificate for Funnel renewal` → `SetDNS` → `requesting cert` → `got cert`). Le cert restauré (bon `notBefore`, non-expiré) reste **inutilisé** dans le state secret `ts-pipelines-webhook-state` ; un `pipelines-webhook-1.*.crt` résiduel y traîne (trace d'une dérive passée).

**Conséquence :** on obtient le FQDN propre GRÂCE à la purge, mais on RÉÉMET le cert à chaque grow → brûle le budget Let's Encrypt **prod** (5 certs/FQDN/168h) → raison de plus de rester en **staging** pendant l'itération (`useLetsEncryptStagingEnvironment` dans `TailscaleManifestsUnit`).

**Deux directions de résolution (à trancher au prochain cold-start) :**
1. La purge ÉPARGNE les devices dont on persiste l'identité (allowlist par FQDN stable : ne pas GC `pipelines-webhook`/`flux-webhook`, seulement leurs doublons `-N`). Garde l'identité device → vrai reuse.
2. La persistence se passe de la survie du device : réutiliser juste le **cert LE par FQDN** (indépendant de l'identité device tailscale) — le proxy neuf adopte le cert du PV sans avoir à être le même device.

**État annexe (chunk 2 « généraliser la persistence funnel ») :** `flux-webhook` n'a AUCUNE ProxyClass → zéro persistence, purge-only (seul `pipelines-webhook` a `ProxyClass`+state pinné via `PacWebhookFunnel.LEAF`). Autre accroc observé : l'Ingress `pipelines-webhook` tardait à peupler son `status...ADDRESS` (churn `ProxyClass not found` au démarrage, l'Ingress reconcile avant que la ProxyClass existe) — à re-vérifier.

**ProxyGroup ÉCARTÉ DÉFINITIVEMENT (investigation 2026-09-09) — ne pas y revenir.** L'user voulait migrer les funnels vers un `ProxyGroup type: ingress` (identité device stable → reuse cert). VERDICT à la source tailscale : **le ProxyGroup HA-Ingress NE SUPPORTE PAS Funnel**, ni en 1.102.3 ni sur `main` (dernière version). Preuves : `cmd/k8s-operator/ingress-for-pg.go` (HA/ProxyGroup) = ZÉRO ref `funnel`/`AllowFunnel`, serve tailnet-INTERNE only (que `http-endpoint`/`http-redirect`) — vrai en 1.102.3 ET sur main ; `cmd/k8s-operator/ingress.go` (per-Ingress NON-HA) = c'est LÀ que vit le funnel (`AnnotationFunnel` → `sc.AllowFunnel={magic443:true}`) ; changelog = aucune entrée funnel+HA-ingress. Nos funnels (flux-webhook, pipelines-webhook) DOIVENT être publics (webhooks GitHub) → un ProxyGroup les rendrait tailnet-internes = cassé. Donc **option B (upgrade) morte, migration ProxyGroup impossible** — on reste sur le modèle per-Ingress (le SEUL qui expose en Funnel). CRD ProxyGroup en 1.102.3 : `type` enum egress/ingress/kube-apiserver ; secrets par replica `pgStateSecretName=<pg>-<i>` (device identity, `KeyDeviceID`) + `pgConfigSecretName=<pg>-<i>-config` ; cert = 1 Secret PAR DOMAINE (nom = le MagicDNS de l'Ingress, clés `tls.crt`/`tls.key`), émis par `-0`, PARTAGÉ entre replicas (pas entre domaines). (Faits gardés pour mémoire, mais inapplicables au funnel.)

**⇒ FIX = OPTION A (modèle per-Ingress, PAS de ProxyGroup).** La tension : la purge (`--prune-stale-devices --stale-after 1s`) supprime le device canonique (`pipelines-webhook`) offline depuis le grow précédent — pile celui dont on restaure la node key → la key restaurée devient invalide dans le tailnet → le proxy DOIT se ré-enregistrer → nouveau device → re-fetch cert. Deux volets : (1) **la purge doit ÉPARGNER les devices persistés** — ne prune QUE les doublons dérivés `-N` (ou les vrais orphelins), jamais le device canonique à nom nu dont on garde la node key → au restore, le même device revient (tailnet le reconnaît) → même FQDN + cert réutilisé ; (2) **généraliser la persistence à TOUS les funnels** (flux-webhook n'a AUCUNE ProxyClass ni state secret aujourd'hui → se ré-enregistre toujours) : ProxyClass + state secret stable + restore/backup PV paramétrés par funnel (flux + pac), pas seulement PaC.

**✅ VALIDÉ AU COLD-START (2026-09-09) — la transition marche, le re-attach marche.** Fix shippé = option A (per-Ingress) : registre `FunnelLeaf` (pipelines-webhook + flux-webhook), persistence généralisée à TOUS les funnels (ProxyClass + state secret `ts-<leaf>-state` + backup/restore par-leaf sur PV partagé, sous-dossiers `/persist/<leaf>/`), **purge `--keep-host` CONDITIONNELLE** (le purge monte le PV RO et n'épargne QUE les leaves avec `/persist/<leaf>/state.yaml` → un leaf sans état est prune pour un nom propre, le suivant re-attache) + migration one-time du plat `/persist/state.yaml`→sous-dossier pour pipelines (`FunnelLeaf.adoptsLegacyFlatState`). ndh `manage-tailnet --keep-host` (commit `e8f0c267`, poussé develop + flox-catalogue lock bumpé). Résultats live : purge log `sparing pipelines-webhook / not sparing flux-webhook` + pruned controlplane/flux-webhook/operator ; **`device_id` pipelines IDENTIQUE (`noD2NWu4g611CNTRL`) au grow précédent = re-attach confirmé** ; FQDN propres (zéro `-N`) ; cert `notBefore` N'A PAS avancé (LE a redonné le cert existant = dedup, pas de mint prod) ; `ts-flux-webhook-state` créé (flux persisté, re-attach au prochain grow). **Résidu (acceptable, non-bloquant) :** tailscaled log toujours `no cached certificate for Funnel renewal` + `requesting cert` → il ne SERT pas depuis son cache d'état restauré, mais LE dedup → effet net = pas de ré-émission.
