== Why this doc exists (read first)

The session opened with an idea: *introduce a rules engine (Drools-style) to (1) simplify the
pipelines, (2) chain the scenarios automatically in the right order, (3) adapt the Pulumi preview to
real needs.* Brainstorming narrowed the felt pain to one phrase — **"the rule set is open/growing:
adding a specialist / checkpoint / remediation means editing control flow."**

Then a question from the user cracked the problem open: *"Pulumi is already a dependency graph — so
the checkpoints are already walked through it?"* Checking the source showed the answer is **no, and
the inverse of the natural assumption** — and that reframes the whole idea. This doc captures the
grounded map and lays out the three candidate directions as C4 + UML diagrams so the choice can be
made cold.

[#the-keypoint]
== The keypoint — there are TWO graphs, and they are not the same graph

The natural assumption is that a checkpoint is a node in Pulumi's resource DAG, and Pulumi walks the
graph and *triggers* each verification in dependency order. The code does the opposite.

* The verification (`SystemdAdapterStage.launch()`, the JGiven probe, the doctor consult) runs
  *eagerly, in plain sequential Java*, inside the fluent pipeline — *before* any `ComponentResource`
  exists.
* The `ComponentResource` (`SystemdAdapterResource`, `ClusterReadinessResource`) is created
  *afterwards* as a *passive mirror* of the result already computed. `ResourceCreationPipeline`
  says it out loud: _"the resource is a thin graph mirror of the result + the dependsOn edge"_; and
  `ClusterReadinessResource` says _"No verification runs here."_

*Consequence for the idea:* adding a checkpoint as a node in the *Pulumi DAG* verifies nothing —
those nodes are inert. The layer that actually orders, probes, and diagnoses is the **Java/BDD
layer**, and that layer is *not yet a graph* — its dependency knowledge is hand-wired. So the
opportunity a "rules engine / graph" gestures at is real, but it lives one floor down from where the
idea first pointed it.

[#the-propagation-you-already-have]
== The propagation you already have (the case the rules engine has to beat)

Benefit (2) was "chain the scenarios automatically in the right order". A forward-propagation engine
*already runs*: the `@NestedSteps` replay in `ClusterReadinessScenario` walks the upstream
systemd-adapter scenario first, and the fluent chain's fail-fast marks everything downstream of a
broken precondition SKIPPED. Flip the upstream fact, the reachable downstream re-derives. That is
exactly the propagation a RETE engine sells.

[mermaid]

  end

The point: the engine's headline feature is *already built, by hand, with no working memory and no
inference*. What is missing is not propagation — it is a *single declaration of the edge* the
three encodings could derive from.

`Checkpoint` already centralises *identity* and derives the resource name from the slug (guarding the
`clusterApi`/`cluster-api` silent-failure class). It deliberately says: _"ONLY identity, never
topology. The cluster→systemd dependency edge lives on the resource dependsOn, not here."_ The fix
for Redundancy A is therefore a pattern `Checkpoint` already began — just extended to topology.

== The three options

=== Option ① — Checkpoint gains topology (derive the three encodings from one declaration) [DISCARDED]

*Status: DISCARDED for THIS track — but a hard PREREQUISITE for the planner track.* The user chose to
pursue only the specialist track (② + ②′) here, setting the topology track aside. *Redundancy A is
therefore NOT addressed by this subject* — the fact "cluster dependsOn systemd" stays written in three
places (Java call order, nested replay, mirror edge). This is a conscious deferral, not a resolution.

*The divergence to record (two decisions coexist, neither erases the other):* the
link:preview-whatif-replay-exploration.adoc[what-if subject]'s *closed-loop planner* — the generalist
that simulates a remediation, unmasks downstream symptoms, and re-consults along the dependency chain
— *cannot exist without a walkable topology as data*. So ① is *optional* for the specialist track
(de-duplication only) but a *hard prerequisite* for the planner. Discarding it here does not
contradict that: the planner simply raises the bar. Its open sub-question — topology on the
`Checkpoint` enum vs. a companion `CheckpointTopology` — would be the *first concrete decision* of the
planner subject (and of the new agenda-owning consultation flow in `spec.adoc`, whose defer/refer
agenda also needs the diagnostic topology). See <<open-decision,Open decision>>. The design sketch
below is kept for that pickup.

Add the dependency edge to the `Checkpoint` enum (which already owns identity). The Java run order,
the nested replay wiring, and the Pulumi mirror edge all *derive* from that one declaration, instead
of being hand-kept consistent. A tiny DAG over the *two verification checkpoints* — the six action
topics keep their type-state ordering untouched.

  declaration.

=== Option ② — self-declaring specialists, permissive Generalist [DECIDED]

*Status: ADOPTED as the direction.* The decision: the specialist **publishes the set of symptoms it
knows how to treat** (`treats() : Set<Symptom>` — a self-declared capability), and the Generalist
becomes *permissive — it accepts ANY symptom*, no longer pre-filtering through a routing table. It
asks each specialist whether the symptom is in its `treats()` set, collects the prescriptions of
those that say yes, and yields an empty *"symptom seen, no treatment offered"* plan when none do. The
symptom is *always recorded*, treated or not.

*The competence has a single authority — the practitioner.* "Who knows
what it treats" is *always* the specialist itself: it *provides* its set of symptoms. The set never
lives in an external table the Generalist keeps. The specialist's `domain()` gives it a *default
repertoire* — the symptoms of its specialty — which it *inherits*; but the effective list is its own
choice: it *adds* or *removes* from that default. The domain is the *seed*, never a second source
that co-owns the answer. One authority, one `treats()`, with the domain only pre-filling it.

This is stronger than both earlier shapes: the *flat* form (this doc's first cut) dropped the domain
default entirely; the *two-source* reading (composing "the domain says X" with "the specialist
re-says X") would re-create the very synchronization the deleted `switch` had. Neither happens here —
the domain *pre-fills*, the practitioner *owns*. The single-source invariant holds because there is
exactly one owner.

Three mechanical consequences of the decision:

. *The internal symptom guard is deleted, not duplicated.* `DbusTcpSpecialist`'s
  `if (symptom != CONNECTION_REFUSED) return empty` is *lifted* into the specialist's effective
  `treats()`. The Generalist only calls `diagnose` for symptoms a specialist declares, so the guard
  is dead — removed in the same change (the second-source-of-truth elimination; code-hygiene
  discipline).
. *`domain()` is the seed of the default, plus identity — never the routing table.* It still groups
  specialists in the runbook and feeds the future config↔doctor seam, and now it *pre-fills* the
  default repertoire a practitioner inherits. But the routing key is the practitioner's effective
  `treats()`, owned by the specialist. A NETWORK specialist inherits the NETWORK default and may
  *add* (sub-specialize) or *remove* (a procedure it does not perform) — its choice, its authority.
. *The exhaustive `switch` over `Symptom` is gone — a deliberate trade.* Adding a `Symptom` no longer
  forces a Generalist edit (serves the "open set" goal), but the compile-time "did you wire this
  symptom?" nudge is lost. Coherent under the permissive model: an untreated symptom is a *valid*
  case ("seen, no remedy"), not a bug — and a symptom *no* practitioner's `treats()` covers is, by
  definition, the recruitment signal (link:runbook-doctor.adoc[spec.adoc] `[#recruiting-a-specialist]`).

* *Touches:* Redundancy B. *Cost:* small. *Fights project values?* No — kills a
  `ManifestDomainCatalog`-style second-source-of-truth; aligns with instance-passing (the registry of
  specialists is the single instance passed in).
* *Companion (same option, the other half of Redundancy B):* the duplicated
  `new Generalist(List.of(new DbusTcpSpecialist(cfg)))` (BootstrapPipeline systemd + resources topics)
  collapses to one construction site. Not part of the routing decision per se, but the same refactor.
* *Empty-plan behaviour is preserved:* today the switch routes e.g. cluster symptoms to a `CLUSTER`
  domain with no specialist (symptom seen, no treatment). Under the decided model, "no specialist
  treats it" is the natural empty plan — same observable behaviour, without the table.

=== Option ③ — a forward-chaining rules engine (Drools or hand-rolled)

Model dossiers/observations as *facts*; rules fire and derive new facts; the checkpoint order falls
out of fact dependencies; the doctor routing becomes rules. The propagation engine is generic.

* *Touches:* A + B + the what-if. *Cost:* high. *Fights project values?* *Yes* — working memory is
  the hidden mutable state the instance-passing discipline proscribes; inference is what the
  Generalist's doc explicitly rejected (_"a readable, testable rules table — no inference"_).
* *Its one genuine prize* (generic propagation) is the very thing
  <<the-propagation-you-already-have,already built>> via nested replay. At today's scale (2
  checkpoints, 1 edge, 1 active specialist) the engine is a sledgehammer; it earns its keep only if
  the rule set becomes *genuinely dynamic / large*, which is not the case yet.

win and are *not* a rules engine — they finish a pattern `Checkpoint` already started. ③ is YAGNI at
today's scale and collides head-on with two core values, while its headline feature (propagation) is
already in hand. The what-if (benefit 3) rests on ① regardless: a declared edge is what a
counterfactual replay propagates along.

[#open-decision]
== Open decision (named, not resolved)

. *Direction — DECIDED.* ② is *adopted* (self-declaring specialists, permissive Generalist); ③ stays
  *rejected* (substrate) — but ②′ (Drools *contained* behind the `Specialist` seam) is a live future
  option, see link:drools-network-specialist-prototype.adoc[the Drools prototype]. ① is *discarded for
  this track* yet a *hard prerequisite for the planner track* (above).
. *If ① (whenever the planner picks it up):* does topology live on the `Checkpoint` enum itself, or on
  a small companion (keep `Checkpoint` identity-only and add a `CheckpointTopology`)? The enum doc
  currently *forbids* topology on itself — extending it is a deliberate reversal to weigh. This is the
  *first concrete decision* of the planner subject.
. *On ② (resolved):* the routing key is the practitioner's self-declared `treats()`; `domain()`
  survives as the *seed* of the default repertoire (sole authority = the practitioner), not the
  routing table. `treats()` and `domain()` coexist on distinct axes.
. *Relation to the what-if / planner:* ① is the prerequisite for the closed-loop replay propagating
  along a *declared* edge (rather than a hand-wired `@NestedSteps`) AND for the agenda-owning
  consultation flow's defer/refer scheduling (`spec.adoc` `[#consultation-flow]`). Sequencing: the
  planner subject must take ① first.
