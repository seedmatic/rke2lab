== Why this atlas exists — and how to use it

*First gesture when a problem arises: reopen this atlas, locate the problem on it, and start there.*
Not in a spec, not in the code — here. The atlas tells you which subsystem(s) the problem touches,
which value thread it sits on, and whether the answer is already recorded (a decision in one subsystem
often silently answers an open question in another). Starting anywhere else is how you fall back into a
hole already dug and try to fill it again.

The atlas's *function* is to prove the specification models hold together — cross-subsystem, not
subsystem-specific — and, above that, to answer the question you actually lose time on later: *how does
the logic articulate across the system, and what value emerges from the pieces being integrated?* The
ordering (placement) is not tidiness; it is what keeps a solved problem solved.

*The atlas is levelled (C4-style zoom):*

* *L0 — integration + value (this file).* How the subsystems fit into one system, the transverse
  *value threads* that cross several models at once, and the two-spaces / two-vocabularies frame every
  view is read against. *Start here.* This is articulation, not detail.
* *L1 — per-subsystem views (`atlas/*.adoc`).* One file per subsystem (doctor, config, runtime,
  unit-repo, manifests, seed, nixos-substrate, cellar-secrets): the "container" zoom of each model, with its own monotone
  before/after figures. You descend here once L0 has told you where the problem lives.
* *L2 — the figures inside each L1 view.* The additivity proofs themselves.

*The additivity test is MONOTONE before/after.* Draw the model constellation without the new model
(before), then with it (after). Additive means: *no box erased, no arrow rewired, only additions.* If
"after" cannot be drawn without rubbing out a line of "before", the model is not additive — and the
figure says so out loud. A well-integrated spec is itself the proof we are on the right path.

Legend used throughout: thin/blue = IMPLEMENTED (built); thick/green = the model under design;
dashed/amber = EXPLORATION (not built, future); grey = cross-cutting foundation.
== The two spaces — OSGi and host

Every model on this atlas sits in one of two spaces, and the line between them is the application's
deepest seam. This framing is the *purity axis* made structural: it is the backdrop each per-subsystem
view is read against.

* *OSGi space* — pure models that *describe*: the resolution oracle (`UnitResolver`), the
  manifests universe, the doctor record model, the config records. No `com.pulumi`, no `io.grpc`.
* *Host space* — code that *actualises* the description over the Pulumi engine: orchestration, the
  ledger write-side, `ConfigLoader`. This is where the engine imports live.

The only edge that legitimately crosses is the *bundle/host contract*: a bundle declares a need
(`Require osgi.extender`), the host satisfies it (`Provide` + the `SectionReader` SPI for values). A
pure model reaching directly into host code — as `Rke2labConfig → ConfigLoader` does today — is a
crossing in the WRONG direction, a decomposition defect to invert.

[NOTE]
.The dual-realm library — the sanctioned exception, and its intra-domain form (2026-07-17)
====
A `type=contract` bundle is OSGi-only *by seam purity*: the host reads no domain type back typed, it
speaks only to the broker (the `contract-purity` guard fails the build if a contract exports a concrete
class). The one sanctioned exception is a `type=dual-realm` bundle, staged in-framework AND kept flat in
the host uber-jar — TWO copies, each bound to its realm — because it carries NO seam surface: only flat
values cross, each realm holds its own copy. `seed-broker-codec` is the founding case (a foundation:
serves all domains, both worlds).

`incus-ingress-contract` (2026-07-17) is the first `type=dual-realm` of a DOMAIN, and it refines the rule:
the dual-realm here is *intra-domain*. incus must run part of its logic host-flat — the GROW beat,
because `com.pulumi` cannot enter Felix — so the incus SCION (OSGi) and the incus GROW (host) are two
halves of ONE domain that need to share flat value records (the `InstanceGrowPlan`) ACROSS the realm
boundary. That is NOT the leak seam-purity forbids (a domain's vocabulary crossing to ANOTHER domain
typed): producer and consumer are the same domain. The dual-realm-intra-domain is *orthogonal* to seam
purity — incus speaking to incus across the realm frontier the Pulumi engine imposes on it. Discipline
(graved in the module's bnd): FLAT VALUE RECORDS ONLY — no logic method, no `com.pulumi`, no OSGi
service ref, else it becomes the door behind which behaviour leaks host-side. Computation stays OSGi
(scion) or host (GROW); the shared module carries only projected DATA. See
link:osgi/host-cellar-realisation-spec.adoc#the-grow-anatomy[host-cellar § the-grow-anatomy].
====

[NOTE]
.Terminology — `system`, `space`, `world`, `universe`, and where `exec/` fits
====
These words are used precisely throughout the atlas and specs; this is the glossary.

* *system* — THE WHOLE: the two spaces (OSGi + host) joined into one thing that runs. The spaces are
  *parts of the system*; the system is not a third space.
* *space* — a top-level LAYOUT directory, sorted by the purity + nature axes: `osgi/` (pure, describes),
  `host/` (actualises over Pulumi), `exec/` (the *nature* axis — executables). "Two spaces" names the
  PURITY seam (osgi↔host); `exec/` is the orthogonal nature axis, not a third purity space — so the
  two-spaces frame above stays exactly right.
* *world* — a RUNTIME classloader region: the OSGi world (bundle classloaders, no gRPC) vs the HOST
  world (one flat classloader, holds gRPC). Same osgi/host line as the spaces, seen at runtime.
* *`exec/` MATERIALISES the system* — an `exec/` module (`seed-master`) embeds both worlds into one
  launchable artifact: the OSGi bundles (describe) + the host adapters (actualise), composed into a
  self-contained jar that boots Felix inside `Pulumi.run` (the R4 view — link:atlas/runtime.adoc[runtime L1]). That is the role the
  terminology was missing: osgi *describes*, host *actualises*, `exec/` *materialises*.
* *universe* — RESERVED for the resolver sense (`UnitResolver`'s candidate set, `ManifestsUniverse`); it
  is NOT a synonym for "system". Kept distinct on purpose.
====

=== The two vocabularies — one thing, named in each world

The two-spaces seam is also a *vocabulary* seam. The same real-world thing is named differently in
each world, on purpose: the OSGi world speaks the *diagnostic* model, the host world speaks the
*stack* model, and they never share a type. They meet only at a serialized `Document(domain,
coordinate, payload)`. The stage column names where the host pipeline handles each pairing *today*
(read from the code) — a maintenance map for the link:osgi/seed-broker-spec.adoc[seed-broker design].

[NOTE]
====
The seam's CONCEIVED form (link:osgi/seed-broker-spec.adoc[seed-broker design]) reframes this
vocabulary meeting as a broker: a client sows a seed (a request `Document`) and the seed-broker sows it
at the right place, the host↔OSGi world-crossing being a broker-internal detail. Today the crossing is
N shared `Document→Document` service interfaces (`ConsultingService`, `ReadinessAuthority`,
`InterventionIntake`); the conceived form collapses them into ONE broker door dispatched by
`coordinate` (module renamed `world-gateway → seed-broker`). The two-vocabularies invariant is
unchanged — the broker only concentrates the crossing into one door.
====

*The frame (general):* an OSGi-world word names a pure model; its host-world counterpart names the
actualised, Pulumi-typed thing. They never share a type — *the ports speak `SeedEnvelope`, not data*, and
each world maps it to its own types (OSGi decodes with its `SeedCodec` to records, the host adapter maps
to the stack model). (The former `DomainDagMapper`/`DomainDagMultiplexor`/`DomainDagAdapter` mechanism was
NEVER implemented — records-as-contract was built instead; see atlas/doctor.adoc.) *Reserved to the host
world only:* `Pulumi`, `Stack`, `output` —
enforced by `grep -ri pulumi osgi/` == 0. Doctor↔stack is the first (and today only) concrete
pairing; further domains slot in as rows when they acquire a DAG. The refactored stage decomposition
this implies — GROUND / GATEWAY / APPLY — is now designed (world-gateway spec), drawn in Diagram O in the link:atlas/seed.adoc[seed orchestration L1] view.

The right column is *also* a design tool: a stage that touches two unrelated pairings is a
candidate to split; a pairing handled in no stage is dead. The before/after of the pipeline refactor
this design implies is drawn in the link:atlas/doctor.adoc[doctor L1] view.

=== Does it hold? — the seed-broker is additive (a foundation integrating worlds + domains)

The seed-broker (link:osgi/seed-broker-spec.adoc[design]) is a NEW model of the frontier, so the
atlas owes it the additivity test — and it lands HERE, at L0, because the broker is not a subsystem: it
is a `foundation` that INTEGRATES on two axes. (1) Between the two WORLDS — the host↔OSGi inter-space
seam. (2) Between the DOMAINS — it routes by `coordinate`, and the coordinates span doctor + cluster +
systemd (`readiness-checkpoint`, `consultation`, `intervention`, `visit`), so it is also the
inter-domain integrator. That dual role is exactly why it lives in `osgi/foundation/` and belongs to no
domain: a foundation serves ALL domains and BOTH worlds. The test is monotone before/after: draw the
seam without the broker, then with it; additive iff no box is erased and no arrow rewired — only
additions (and named erasures).

*Verdict — additive-with-named-erasure.* The `Document` envelope + the coordinate vocabulary + the
two-vocabularies invariant survive UNCHANGED (the blue box crosses identically; each world still maps
`Document` to its own types). Three things are erased, each named, none silent: the N shared service
interfaces (`ConsultingService`/`ReadinessAuthority`/`InterventionIntake`, collapsed into one
`handle` door), the doctor words shared at the seam (recede to OSGi-internal), and — the same erasure
the "one seam only" rule tracks — the `-port`s' `type=seam` status as their host imports drive to zero.
No box of the two-spaces frame is rubbed out; the seam gains one door and loses N interfaces. It holds.

This is a CONCEIVED model (not built): the verdict certifies the DESIGN is additive against the atlas,
so a realization plan can proceed knowing it does not force rewriting the two-spaces frame. The
build-time proof (the crossing realised as one door) lands when the code does.

== Integration & value threads — how the logic articulates across the system

The L1 views describe each subsystem alone. This section is the reason the atlas is levelled: a *value
thread* is a single line of reasoning that only becomes visible when several models are laid over each
other — and each thread, once drawn here, is a hole we do not have to dig again. A thread earns its
place by answering a question that would otherwise be re-brainstormed from scratch.

[[thread-manifestations]]
=== Thread 1 — one unit-model, several manifestations (bootstrap ↔ detached)

*The question that keeps re-opening:* when seed runs *detached in-cluster* (not the embedded-exec
bootstrap), who plays the roles Pulumi fills at bootstrap — the orchestration engine, the output sink
(the stack), the `Patient`, the storage (medical record)?

*The answer already exists — it is the intersection of four models*, and drawing them together is what
stops the re-derivation:

* link:bdd/bdd.adoc[pipeline (OSGi-owned)] establishes that the reasoning world is *detached
  by design*; embedded exec is the special case, and *the detached OSGi world knows nothing of Pulumi*.
* link:cluster-api/post-bootstrap-in-cluster-ownership-plan.adoc[post-bootstrap ownership]
  names the in-cluster orchestrators (CAPI + GitOps + node-local reconcilers) that replace Pulumi.
* the L1 link:atlas/unit-repo.adoc[unit-repository L1 view] supplies the deep answer: *everything is a unit*
  (a medical record is a unit; the orchestrator itself becomes a unit in the cluster it made), storage
  is a swappable `ContentStore`, and *migration = pull = git clone* of a unit's DAG into another
  substrate. The 3 topologies (embedded JVM · colocated subprocess · in-cluster pod) are one contract.
* the L1 link:atlas/doctor.adoc[doctor L1 view] defines `Patient`/`MedicalRecord` — which the unit-model reframes
  as *units*, dissolving the apparent contradiction below.

*The reverse-mapping, laid out:*

[cols="1,2,2",options="header"]
|===
| Role at bootstrap | Bootstrap manifestation (embedded, Pulumi) | Detached manifestation (in-cluster)
| orchestration engine | Pulumi (`up`/`preview`, drives `RunMode`) | CAPI + GitOps + node-local reconcilers; the orchestrator is itself a unit
| output sink ("the stack") | Pulumi stack state + `registerOutputs` | a `ContentStore` backend (Pulumi is *one* backend, not the only one)
| `Patient` (persistent identity) | the Pulumi stack (`org/project/stack`) | a *unit* in its environment's `ContentStore` — the stack was only the bootstrap incarnation
| storage (medical record) | reconstructed from Pulumi state (layer-3) | the same bottom-up DAG ingest, from a git/`ContentStore` DAG
|===

[IMPORTANT]
.The contradiction this thread dissolves
====
"`Patient` = the Pulumi stack" (doctor glossary) vs "the detached OSGi world knows nothing of Pulumi"
(pipeline spec) *look* contradictory. They are not: `Patient` and `MedicalRecord` are *units*; the
Pulumi stack is the `ContentStore` incarnation *of the bootstrap case only*. Detached, the same units
live in a k8s/git `ContentStore`. The unit-model is the general form; "= Pulumi stack" was the special
case named before the general one was written. Recorded here so the contradiction does not re-surface.
====

*Value that emerges from the integration* (not from any one model): *storage portability* (switch
environment by cloning units, no model change), *self-hosting* (the orchestrator becomes a unit in the
management cluster it seeded — the reflexive bootstrap; the management/workload separation it rides is
the link:cluster-api/management-workload-topology.adoc[Management / Workload Topology] anchor), and
*one source, several packagings*
(bootstrap-exec ↔ cluster-workload from the same unit). None of these is visible in a single
subsystem's spec; all three are the payoff of the four models being additive.

*Monotone check:* drawing this thread adds no box and rewires no arrow in any L1 view — it only overlays
existing boxes (pipeline · unit-repo · doctor · ownership-plan) with the manifestation axis. Additive.
