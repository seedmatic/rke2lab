= CLIs are scions — the host north-adapter and the dual-realm ingress it speaks through
:toc: macro
:toclevels: 3

toc::[]

== Overview

The host runs in the FLAT realm; a domain's live logic runs OSGi-side. The boundary between them
is not a detail a CLI may route around — it is load-bearing, and it dictates HOW a CLI drives work
and WHERE the typed values it holds are allowed to live.

The load-bearing fact: a `type=contract` bundle registers its service with the BUNDLE's copy of the
exported class. A flat host that boots the framework and calls `awaitService(DomainService.class)`
asks for its OWN flat copy of that class — which never matches the bundle-registered service. The
first CLIs were built that way and were STRUCTURALLY broken; the fix was not a tweak but a change of
model. Two laws crystallised out of it — first observed on `manifests-cli` / `netplan-cli`, and
asserted here as general.

== Law 1 — a CLI is a thin north-adapter that sows a root scenario into the OSGi world

A CLI verb does four things and no more: parse argv, seed a small run record, PLAY a host root
scenario on the embedded JUnit launcher (the same BDD-as-engine machinery `seed-outcluster` uses), and
render the reaped runbook. The root scenario opens the gardening and SOWS a coordinate through the
broker — the ONE host↔OSGi membrane (`seed.broker.port`) — and the domain grows its scion
in-container, where the scion's `@OsgiService` collaborators resolve bundle-side against the same
class copies they registered with.

Domain logic NEVER lives host-side. The report/outcome rides IN the runbook (bind the data into the
scenario's steps), which the host renders — never a side-channel the host assembles itself.

[cols="1,1", options="header"]
|===
| ❌ Anti-pattern | ✅ The law

| Boot Felix host-side and `awaitService(DomainService.class)` — the flat class copy never matches
  the bundle-registered service; and it drags domain logic into the host.
| Sow a root scenario through the broker; the scion resolves the service in-container. The host
  names no domain service type.

| A CLI that computes the answer host-side and calls OSGi only for a helper.
| A CLI that is a pure north-adapter: parse → seed → sow → render. The answer is computed OSGi-side
  and travels back as the reaped runbook.
|===

*Worked examples.* `manifests-cli` — `synthesize` sows `manifests` (grows `ManifestSynthesisScenario`),
`versions` sows `manifests-versions` (grows `VersionBumpScenario`). `netplan-cli` — `yamlExport` sows
`netplan`. `seed-outcluster` — the root that sows every provisioning crossing. All four are the same
gesture at different scales; a CLI that is coherent with `seed-outcluster` is one that sows.

== Law 2 — typed values BOTH realms hold live in a dual-realm ingress module

A CLI that stays a north-adapter still often needs to build or read a value TYPED rather than as
opaque JSON — a bump level, a component id, a version pin. When the OSGi world holds the SAME type,
that type must NOT be duplicated host-side, nor threaded across the membrane as a loose String, nor
(the compiler forbids it) referenced from the host as a `type=contract` type. It lives in a
`type=dual-realm` INGRESS module: staged as a bundle in-container AND kept flat host-side, so ONE
typed class legitimately lives in both realms.

That is the ROLE of an ingress module — the domain's dual-realm host face. It is distinct from a
`type=contract` bundle (bundle-wired only, never host-typed) and from a `type=seam` (the boot face,
system-exported). The red line the `REALM_BOUNDARY` gate enforces is "no dependency absent from
either realm", so an ingress type may depend only on the JDK, jspecify, and other both-realm types
(a `type=seam` like `WireEnum`). Make the shared values `WireEnum`s (a kebab/camel `slug()` wire
form) or pure records, so the codec crosses them by slug and the demand-fold keeps the flat copy
only in the assemblies whose flat classes actually reference it.

[cols="1,1", options="header"]
|===
| ❌ Anti-pattern | ✅ The law

| A parallel host-side enum duplicating the domain's set (the drift the `clusterApi` bug came from).
| ONE enum in the dual-realm ingress, referenced by the host AND the scion — the single source of
  truth for that identity.

| Threading `level`/`component` as loose Strings across the membrane and re-validating on both ends.
| A typed `WireEnum` field on the wire record; the codec maps it ↔ slug, the typing lands at decode.
|===

*Worked example.* `manifests-ingress-contract` holds `Component` (the SSOT enum: `slug` +
`defaultVersion` + `Optional<ComponentSource>`), `BumpLevel`, and the resolved `ComponentVersions`.
The `manifests-cli versions` verb builds a TYPED bump facet (a `BumpLevel` and an
`Optional<Component>`) that the in-container `VersionBumpScenario` decodes typed — the same classes
on both sides, because ingress is dual-realm.

== Why the two laws are one boundary

They are the two halves of the same host↔OSGi line. Law 1 says the host reaches domain BEHAVIOUR
only by sowing a scenario (never by resolving a service). Law 2 says the host shares typed VALUES
with the domain only through a dual-realm ingress (never by duplicating or by contract-typing). A CLI
that honours both is a thin, coherent north-adapter; one that breaks either drifts back toward the
structurally-broken boot+awaitService shape the model was built to retire.
