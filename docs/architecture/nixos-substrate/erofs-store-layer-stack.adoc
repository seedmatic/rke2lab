= The EROFS layer stack — one store layer per system generation
:toc: left
:toclevels: 3

[NOTE]
====
`/nix/store` as an ordered stack of read-only EROFS layers, declared by `ndh`.

*Status: the three-layer stack is SHIPPED* — verified end to end on `nikopol-nixos` on
2026-09-20, with the per-host runtime image down from 7.47 GiB to 39 MiB and the pool from
7.90 GiB to 23.7 MB. Its companion link:erofs-store-lower.adoc[the EROFS store lower]
describes the single-layer mechanism this generalises; read that one first for how an EROFS
lower is packed and mounted at all.

Still ahead: automatic activation at boot, layer expiry, and compaction. Each is flagged in
place.

The delta against the codebase is the link:../atlas/nixos-substrate.adoc[atlas view]; the
surrounding substrate vision is link:substrate-model.adoc[the substrate model].
====

== The model in one page

A node's `/nix/store` is not a ZFS dataset. It is an *overlay* whose lower is an EROFS image
delivered as a disk and whose upper is a ZFS dataset. That much is shipped, and both fleet
nodes run on it.

The stack adds three things:

. the lower becomes an *ordered stack* of EROFS layers instead of a single layer frozen at
  bringup;
. the layers follow the *composition chain of the configurations*, so what the fleet has in
  common sits in a shared layer and only the host's residue is private — 77 paths, 39 MiB;
. *`ndh` declares the stack* and computes when a layer is dead. The node has no say.

And one explicit ownership boundary, which is the heart of the design:

[quote]
____
The *instance* owns its *data* (ZFS pools, the overlay upper). *`ndh`* owns the *store
layout*. A reboot may change the layout, provided every generation the instance can still
boot both *finds* its closure in the new stack and is *able to mount* it — that is what
"backward compatible" means here.
____

The second clause of that proviso is not decoration: a generation's initrd bakes in the list
of layers it was built with, so it can only ever mount that many. Both halves are worked out
under <<_the_two_invariants_that_bind_a_layer_to_a_booted_node>>, and one of them was learnt
by breaking a node.

=== Why: determinism, not economy

Today `nixos-rebuild boot --target-host` makes *the node* materialise the runtime closure:
*165 591 file creations*, performed outside any derivation, to produce what the builder would
have produced. That is the same per-file cost class the EROFS lower removed from the image
build, reintroduced on every update.

With one layer per generation that materialisation moves *inside* a derivation:

* reproducible and content-addressed,
* substitutable, therefore shareable across the fleet,
* verifiable — `nix-store --realise --check`, which we exercise,
* and the node builds *nothing*: it mounts.

Pre-computing everything with nix at build time is better *in itself*; the time saved is a
corollary. This is not a new direction either: the commit that retired the `work` profile
(ndh `8d6b6acb`) already stated that "bioskop is the authority and distributes closures to
consumers". Layer-per-generation is that statement carried to its conclusion.

`erofs-store-layers.nix` is the SSOT and every consumer is a projection over it, on the
pattern `zfs-pool-disk-map.nix` already establishes. It is also *self-validating*: it asserts
label uniqueness and the 15-character limit at evaluation time, because both failures would
otherwise surface as a guest that builds fine and then cannot find its store.

`mkFleetRuntimeConfig` is what makes the shared layer possible, and it is deliberately built
from the *literal* host definition rather than the caller's `hostProfile`: every host must
derive the byte-identical closure, or the layer stops deduplicating. `flake.nix` reuses the
same function for the `nerd-runtime` alias so the two cannot drift into two closures.

Two components are still missing — liveness (which makes purging possible) and boot-time
activation (which removes the last manual step).

*The darwin side needs no change.* `run.sh` and `activation.sh` already loop over N prebuilt
images and attach each read-only, and the manifest already emits one `role: prebuilt` entry
per image.

The stack above is the *shipped* one, measured on `nikopol-nixos` on 2026-09-20. The
leftmost `lowerdir` is the top layer — the kernel documents it as "the specified lower
directories will be stacked beginning from the rightmost one and going left" — so the
newest layer goes first and the virtio slot order is irrelevant: every layer is found by
label.

Three invariants read directly off this figure:

* every layer is `neededForBoot`, so its disk must be attached or the guest hangs in the
  initrd;
* the Nix database is the *third* actor, independent of the layers, and it is what makes
  their paths *usable* — without `nix-store --load-db` a `nix copy` would rewrite the whole
  closure into the upper;
* a whiteout in the upper masks *all* layers at once. Whiteouts are the only destructive
  overlay state, which is why purging means removing a disk, never deleting files.

== The two invariants that bind a layer to a booted node

Both were learnt the hard way on `nikopol-nixos` on 2026-09-20, by a node that came up in an
initrd emergency shell after a materialization in which *every individual decision was
defensible*.

=== Depth is part of the ABI: append is safe, replacement is not

A generation's initrd carries its `lowerdir` list *baked in* — it is `fileSystems`, resolved
at build time. The failed boot showed it verbatim:

[source]
----
lowerdir=/sysroot/nix/.ro-store.002:/sysroot/nix/.ro-store
----

Two entries, on a node that had three layer disks attached. `vdg` (layer 003) was attached
and simply never mounted, because the generation being booted had been built when the stack
was two deep.

That cuts cleanly in two:

Appending a layer is safe::
  An older generation neither references the new layer nor mounts it — and does not need to.
  Its closure is wholly inside the layers it was built with. It keeps booting, ignoring the
  addition.

Replacing a layer's content is not::
  An older generation's toplevel can disappear from the stack entirely. That is what
  happened: layer 002 was re-cut from the host runtime closure to the fleet-generic one, so
  generation 2's toplevel existed in no layer, and
  `initrd-find-nixos-closure` failed with `Failed to resolve path …/init in prefix /sysroot`.

[IMPORTANT]
====
This makes the decision recorded below as "we stack, we do not replace" a *condition for
rollback*, not a preference. Rollback survives any number of appended layers and no
replacement at all.
====

=== The ESP and the layers are one unit

An ESP names a system toplevel; the stack has to carry that toplevel. They were decided
independently by the materializer — the root disk had its own preserve/replace gate, the
prebuilt layers had theirs — so a run could legitimately preserve the ESP *and* replace a
layer's content, and nothing compared the two.

The materializer cannot repair that state either: the preserved pools still hold the old Nix
profile and its generations, and only the nested-VM installer ever writes a profile — into
the bundle's own fresh pools, never the live ones. So the gate now *refuses*, naming
`VM_FACTORY_RESET=true` as the operator's way forward (`ndh` `e3451f13`).

== C3c — Generalising: every generation is a layer

Does the model that builds the *bringup* system also serve the *target* system? Yes — and the
code already aimed there. `bringup-zfs-disk-image.nix` carries a `runtimeSystemPath`
parameter, documented "*Production runtime system closure to include in the bringup image
store*".

It is `null` for exactly one reason: embedding one host's closure tags the image per host and
breaks fleet-wide dedup. *The stack resolves precisely that tension* — what is common is
separated from what is specific, instead of everything landing in one image.

=== What it changes — the switch stops writing the store

[cols="2,2,2",options="header"]
|===
| | Today | One layer per generation

| materialising the runtime closure
| `nixos-rebuild` creates *165 591 files* in the upper
| one sequential image, packed on the builder

| cost class of a switch
| the per-file class we removed from the build
| the "bytes" class

| contents of the upper
| the whole runtime (5.3 GiB)
| local writes only

| rollback
| depends on what is left in the upper
| keep the layer
|===

=== The price, and it is structural

. *A switch becomes a reboot.* Tart cannot hot-attach a disk, so delivering a layer means
  stop/start. Accepted: these clusters have no availability constraint and re-grow from git
  anyway. Note that `boot` + reboot is *already* the documented operator practice — an online
  `switch` runs activation scripts before `systemd-tmpfiles`, so the runbook already forbids it.
. *The node no longer builds a generation.* It still *activates* one, locally and from its own
  store — what is lost is building one on the node, not switching to one.
. *It closes the ESP question.* If `ndh` builds the generation and its layer, it installs the
  bootloader entry too. So `ndh` owns the ESP, and the coincidence of image sizes stops
  arbitrating anything.
. *One more layer per generation*, so compaction becomes necessary sooner.

notable part is the tail: reaching the target configuration *transfers nothing and needs no
operator*.

=== What that used to be, and why it is no longer that

The documented practice was a *remote push* from the builder:

[source,bash]
----
TMPDIR=/tmp nixos-rebuild boot --flake .#<host>-nixos --target-host root@nerd-nixos
ssh nerd-nixos reboot
----

That machinery existed for one reason: the runtime closure was not on the node. It now is —
layer 003 carries it and the installer registered the *union* closure in the guest's Nix
database, so both the host runtime and the fleet-generic toplevels read back `VALID` before
activation ever runs. The remote push therefore evaluates the flake on the operator's
machine, delegates the build, opens an SSH session and pushes a closure — in order to
discover there is nothing to send.

The equivalent, entirely local on the guest:

[source,bash]
----
nix-env -p /nix/var/nix/profiles/system --set /nix/store/<host-runtime-toplevel>
/nix/var/nix/profiles/system/bin/switch-to-configuration boot
reboot
----

No flake evaluation, no builder, no SSH key, no transfer. The remote push keeps one role —
deploying a configuration that is in *no* layer — but with the stack that is by definition a
new layer, so it is a rescue path rather than the normal one.

=== Step 5 is automatic: the first-boot handover

`io-seedmatic-ndh-bringup-target-activate.service`
(`modules/nixos/systemd/bringup-target-activate.nix`) performs exactly the three commands
above on the first boot of the bringup, then reboots. So a freshly materialized node reaches
its target configuration with no operator step at all.

The design constraint that shapes it is worth stating, because the obvious implementation is
the broken one. The service must learn *which* system to activate, and it must not learn it
from its own closure: nix records a reference for every store path it finds in an output, so a
bringup toplevel that named the runtime toplevel would drag the entire runtime closure into
the base layer and collapse the stack back to one layer. That is the same trap documented at
`baseClosureInfo`, one level up.

So the target arrives as *data on the target root*: the nested-VM installer writes
`/var/lib/ndh/bringup-target-system`, and the unit reads it. The installer is not part of the
bringup system — it is what installs it — so naming the runtime toplevel there adds no
reference to the bringup closure. Verified: the bringup closure is 661 paths and contains no
`nixos-system-*` other than its own.

Two guards, both deliberate:

`ConditionPathExists` on the declaration file::
  No declared target means the image was not provisioned for one, and a plain bringup must
  stay a bringup. Skipping beats a unit that fails on every boot of every such node.

one attempt, ever::
  The unit records its attempt before rebooting and refuses a second one. Coming back still
  on the bringup means the handover did not take; retrying would reboot-loop the node, which
  is far worse than stopping on a bringup that still answers SSH. The cost is that a
  *deliberate* rollback to the bringup shows a failed unit — visibility was judged worth more
  than that noise.

[WARNING]
====
`modules/nixos/systemd/zfs-nixos-install.{nix,sh}` looks like it should have been the vehicle
for this and is not: it installs into a *separate* `--root` (the pre-EROFS topology where the
bringup ran elsewhere and installed NixOS onto the pool), and it is imported only by a
configuration that is both `bringupMode` and imports `modules/nixos/default.nix` — a
combination no shipped configuration satisfies. It ships in no toplevel. Treat it as dead.
====

== Decisions taken

[cols="3,3",options="header"]
|===
| Decision | Basis

| `/nix/store` = overlay(EROFS packed on the host + ZFS upper)
| the build is operation-bound; `mkfs.erofs` needs no root, so packing stays a pure derivation

| a durable gcroot on the bringup toplevel
| 105 paths lost otherwise; *shipped and applied on both nodes*

| no copy-up before swapping a layer
| 94 491 files — the cost class we just eliminated

| *stack*, never replace
| preserves rollback; purging is removing a disk, not deleting files

| the shared layer is derived *structurally*, not as a set intersection
| an intersection couples every host to every other — adding or changing one rewrites the
  shared layer, hence every node's lower. Deriving it from the neutral host profile
  (`nerd-nixos` evaluated in `full` mode) costs 66 paths / 41.5 MB that no host uses and buys
  full decoupling. Measured against the intersection: +40 MB of dead weight, +6 MB per host,
  i.e. 0.5 % of the shared layer

| `ndh` declares the stack; the instance owns its data
| source-vs-projection; no upward channel is needed

| merging is a rendering choice, deferrable
| no contract with the instance, so it ships later without touching a node

| *every generation is an EROFS layer*
| the bringup model generalises; `runtimeSystemPath` was the hook, the stack lifts the dedup tension

| *the switch becomes `boot` + `reboot`*
| no availability constraint, and it is already the documented practice

| *stack depth is not a new knob*
| it is the number of retained generations, which the operator already controls through nix profiles

| *`ndh` owns the ESP*
| a consequence: if it builds the generation and its layer, it installs the bootloader entry

| *appending a layer is routine; replacing one requires re-provisioning*
| a generation's initrd bakes its `lowerdir` list, so it ignores appended layers but cannot
  survive its own closure being re-cut out of the stack. The materializer refuses the
  combination instead of producing an unbootable node

| *activation is local, from the node's own store*
| the runtime closure is already mounted and already valid in the guest's Nix DB, so a remote
  `nixos-rebuild --target-host` transfers nothing. It stays as a rescue path for a
  configuration that is in no layer

| *one bringup bundle per host*
| the bundle stopped being identity-less when the runtime closure entered the stack: the
  installer bakes the union registration and a GC root on the host runtime toplevel
|===

== What the layer-swap experiment proved

On 2026-09-19 the non-destructive materialization path was exercised end to end on
`nikopol-nixos` (`bioskop-nixos` stays the builder — it is the only aarch64-linux builder, so
losing it blocks repair). The test changed only the EROFS image's *UUID*: a semantically
inert parameter, since the mount is by label, so the bundle and the on-disk marker disagree
while the layer content is identical and the boot cannot break.

Result, on the three branches that had never run:

* the layer was *swapped* — the lower went from UUID `…a62` to `…a63` and the node boots on it;
* the *pools were preserved* — `tank` at 7.90 GiB ONLINE before and after;
* the *root disk was preserved* — generation 2 still current, no reinstall, ESP intact.

So the ownership boundary above is not a wish: `ndh` can change a live instance's store
layout without the instance losing anything it owns.

=== The defect it surfaced, and the rule behind it

The first attempt *destroyed the pools*, and that is what found the real defect: the
preservation branch was *structurally unreachable*, so every materialization that was not a
factory reset destroyed the pools, on any host. Two faults composed:

* `tart:vm:exists` parsed `tart list`'s *first* column as the VM name. That column is
  `Source`, so it compared `local` against the name and could never answer yes.
* `tart` 2.36 fails the *whole* listing when any single VM is running — it stats every VM's
  disk images to report sizes (measured 10/10 on the host where a VM runs permanently; 2.30
  tolerated it).

Both surfaced identically, as "this VM is not registered", and the caller answered that with
`tart create`, which recreates the VM directory and takes the data disks with it.

[IMPORTANT]
====
*A probe whose negative answer authorises destruction must distinguish "absent" from "I could
not look."* Otherwise any introspection failure becomes a deletion order.

Fixed in ndh `47943f0b` and `6213a553`:

* `tart get --format=json <vm>` resolves *one* VM, so another running VM cannot break it, and
  it encodes the answer in its exit code — `0` registered, `2` "does not exist", `1` running.
  That `1` is *positive evidence of existence*: to reach the disk, tart had to resolve the VM.
  Only a formal `2` authorises creation.
* The root-disk gate decides on *content* — a `.source` marker recording the source store
  path, plus an `EFI` partition probe — and no longer on a comparison of virtual sizes, which
  matched only by coincidence (both 600 MiB) and would have silently wiped every node's ESP
  the day the boot image changed size.
* A prebuilt image is read-only and content-addressed, so replacing it is free. A root disk is
  *mutable* and carries the node's generations, so replacing it stays an explicit operator act
  (`VM_FACTORY_RESET`). Two natures, two disciplines.
====

== Troubleshooting

[cols="2,3",options="header"]
|===
| Symptom | Cause and fix

| guest hangs in the initrd on `/dev/disk/by-label/nix-store…`
| a layer's disk is not attached. Almost always a *stale manifest*: the run wrapper resolved
  an older bundle that does not declare the new layer. Check the candidate order in
  `run.sh` — the materializer gcroot must outrank anything under `~/.config/nerd-tart/`.

| paths from a layer disappear after `nix-collect-garbage -d`
| the per-layer gcroot is missing. The loss is *permanent*: the deletions land as whiteouts in
  the upper, which mask the read-only layer underneath.

| `nix copy` rewrites the whole closure into the upper
| the Nix database does not declare the layer's paths valid. The installer must replay the
  registration of the *union* of retained closures (`nix-store --load-db`), not per layer — a
  single layer is not closed on its own.

| the same layer bytes get a different store path per host
| something host-derived leaked into the derivation. The pack fixes `--force-uid/gid=0`, `-T 0`
  and the UUID precisely to keep the output bit-identical; re-check with
  `nix-store --realise --check`.
|===
