= Pattern — passive service, contributors, views, role-owned adapters
:toc: left
:toclevels: 3

*Status:* Pattern — NAMING an idiom already dominant in this codebase, not inventing one. A survey
across `osgi/`, `host/`, `exec/` found Doctor, the seed-broker, the manifests domain channel,
host-asset materialisation, and Pulumi outputs already implement it. This document states its rules,
its shape, its anti-patterns, the conformant exemplars (as proof), and the remaining hold-outs.

== The problem

A piece of state (config, node environment, synthesis inputs) is needed by *many* consumers, and is
fed by *many* contributors. The naive shapes rot:

* a *fat interface* every consumer sees whole, though each uses a slice — the dependency is opaque, a
  reviewer must read the body to learn what a consumer actually needs;
* a *hidden global* (a ThreadLocal `.current()`, a static `getInstance()`) reached sideways — the
  dependency is invisible in the call graph, and any consumer can touch anything;
* a *service that knows its consumers* (enumerates them, builds their views) — a god-node that must
  change every time a consumer is added.

== The four rules

. *One source of truth* — the state is assembled ONCE and is passive; no re-derivation that can drift.
. *Chacun son rôle* — each consuming role OWNS the adapter that restricts the service to that role's
  need. Adaptation is the role's responsibility, not the service's.
. *The DAG rule* — everything a node needs is REACHABLE through the DAG, but the node consumes only
  the VIEWS that concern it, through adapters. Reach-all, consume-narrow — and the narrowing COMPOSES
  down the DAG (each hop hands its children a strictly smaller view).
. *Inversion of control* — the service KNOWS NO ONE. Consumers depend on the service; the service
  enumerates neither its consumers nor (concretely) its contributors.

== The shape — four elements

[cols="1,3",options="header"]
|===
| Element | Definition

| *Service*
| A passive single-source object, "known by all, knows no one." Depends on nothing; enumerates no
  consumer.

| *Contributors*
| Domains contribute DATA through a UNIFORM contract (a `contribute() → fragment` SPI), aggregated in
  a registry with ZERO per-contributor knowledge — the registry sees the abstract contribution, never
  the concrete contributor (*contribution without acquaintance*).

| *Views*
| Narrow, immutable, interface-segregated projections of the service's data. A view stays *navigable
  back to its source* so a role can re-restrict to a sibling view — but navigability takes TWO forms
  by frontier (see <<navigability>>): an in-memory reference *in-process*, or a `SeedCoordinate` (a
  wire value) resolved through the broker *across a frontier*.

| *Adapters*
| Owned by the consuming ROLE. Each role adapts the service down to exactly its view. A collaborator
  is handed the view its parent adapted from the parent's OWN view — never the raw service.
|===

== Contributor resolution — STATIC snapshot vs DYNAMIC roster

Every collector aggregates its contributors through an OSGi Declarative Services `@Reference`, and
that reference has THREE independent axes. Getting them right is what decides whether a contributor
registered *after the collector activates* is seen or silently dropped.

[cols="1,3",options="header"]
|===
| Axis | What it governs

| `cardinality`
| How many, and whether required: `MANDATORY` (1..1), `OPTIONAL` (0..1), `MULTIPLE` (0..n),
  `AT_LEAST_ONE` (1..n). A roster is `MULTIPLE`. Governs component satisfaction (activation).

| `policy`
| What happens when the matching set CHANGES while the collector is active. `STATIC` (default) freezes
  the bindings at activation (constructor/field injection); to change them SCR must DEACTIVATE and
  reactivate. `DYNAMIC` lets bindings change live via `bind`/`unbind` (or a `volatile` collection
  field), no reactivation.

| `policyOption`
| When a NEW bindable service appears while the reference is already satisfied: `RELUCTANT` (default)
  leaves the collector undisturbed; `GREEDY` takes it (rebind if dynamic, *reactivate* if static).
|===

*The decisive rule.* A collector that must accept contributors registered at *runtime* (after it has
activated) needs `policy = DYNAMIC`. A `STATIC` collector snapshots its roster at activation and — with
the default `RELUCTANT` option — never sees a later contributor. And `policyOption` is a *no-op on a
`MULTIPLE`/`DYNAMIC` reference* (a dynamic multiple already tracks the whole set live); it bites only on
STATIC references (where `GREEDY` forces a reactivation to rebuild the set) and on unary references
(where `GREEDY` switches to a higher-`service.ranking` provider). So "add `GREEDY` to make a roster
dynamic" is a category error: the tool for live reactivity is `DYNAMIC`, not `GREEDY`.

This is proven executably, not just asserted, by the `bench-cellar` theses (`osgi/runtime/bench`): the
*additivity* thesis shows a `MULTIPLE`/`DYNAMIC` roster binds a recipient installed at runtime with the
default RELUCTANT option (GREEDY unnecessary), and the *resolution-mode* thesis contrasts a dynamic and
a static clean in one world — the dynamic one seals for the late recipient, the static one stays frozen
on its activation snapshot.

*Migration guidance.* Do NOT blanket-flip the STATIC rosters to GREEDY: on a central collector (the
broker, the health system) a reactivation mid-flight is heavier and riskier than the gap it closes, and
it does not make the collector's code (a constructor snapshot) dynamic-aware. When a contributor
genuinely becomes late-arriving, convert THAT collector to `DYNAMIC` (snapshot → live re-read + a
concurrent collection + `bind`/`unbind`) and earn it a late-arrival test modelled on the bench-cellar
additivity thesis — per real need, never speculatively.

Arrows point FROM roles TO the service. That one-way dependency IS the inversion.

=== The cascade — narrowing composes domain to domain

When domain A collaborates with domain B, A adapts B's view from A's OWN view and injects it — A never
hands B the raw service.

[mermaid]
....
flowchart TB
  svc["service SINGLE SOURCE only the root touches it"]
  a["domain A holds viewA"]
  b["domain B holds viewB"]
  c["domain C holds viewC"]
  svc -->|root adapts| a
  a -->|A adapts its OWN view| b
  b -->|B adapts its OWN view| c
  classDef pass fill:#eef,stroke:#88a,stroke-width:2px;
  classDef neu fill:#dfd,stroke:#2a2,stroke-width:2px;
  class svc pass;
  class a,b,c neu;
....

* *Monotone narrowing* — `viewC ⊆ viewB ⊆ viewA ⊆ service`; each hop can only restrict.
* *Capability-style* — a domain can only delegate a subset of what it holds; it cannot grant access it
  does not have. Robust and locally checkable.
* *The reviewer's win* — because A narrows its own view down to exactly B's at the call site, the
  injection point IS the dependency contract: a reviewer sees, right there, what B really needs — no
  reading B's body, no hidden reach. The minimal adapted view cannot lie (B cannot touch what A did
  not hand it).

== Navigability — two tiers by frontier

Rule 3 says a view is navigable back to its source. HOW it navigates depends on whether the hop stays
inside a realm or crosses a frontier — an in-memory reference cannot survive a process boundary, but a
coordinate can. So navigability has two tiers, and the seam between them is a granularity decision.

[cols="1,2,2",options="header"]
|===
| Tier | Navigation | The "back-reference"

| *In-process* (within a realm) — fine, per-access, compile-typed
| The view holds an in-memory reference to its source; a role re-restricts to a sibling view by a plain
  method call. Cheap, typed. (`BootstrapPaths.asStagingView` / `asAutomountView` were the exemplar, both
  since deleted: a view returning sibling views of the same source.)
| an object pointer

| *Cross-frontier* (host↔OSGi today, remote tomorrow) — coarse, once-per-scope, wire-typed
| The view is *named* by a `SeedCoordinate` (a wire value: `slug()` + `domain()`); navigate =
  `broker.sow(coordinate, cellar, seed)`, reaping a value. Location-transparent — "same JVM today,
  remote tomorrow, a broker detail the client never sees."
| a `SeedCoordinate` (relocated into the broker)
|===

=== The broker IS the cross-frontier projection substrate

The seed-broker is not merely a contributor-aggregator (its row in the exemplars table) — it is a
*coordinate-addressed directory that returns a RESULT, never a reference*. That distinction is what
lets it cross a frontier: unlike the OSGi service registry (which hands back the object for you to
call, in-process only), the broker makes the call FOR you and hands back the reaped `SeedEnvelope`
value, so the consumer never holds a remote pointer.

[cols="1,1,1,1",options="header"]
|===
| Directory | Scope | Addressed by | Returns

| OSGi registry (`@Reference`) | in-process | Java type | the *object* (you call it)
| `SeedBroker` | cross-frontier | coordinate (a value) | the *result* (it calls)
|===

Coordinate→projection is *already live in production*: `ShapeCoordinate` → a domain reflector projects
a coordinate's JSON Schema on demand. Navigability across the frontier is not a future mechanism to
build — it exists; a domain that must be reachable across the frontier *contributes its coordinate +
handler* to the existing broker.

=== Reaching another domain's view — a C4 walk

How domain A navigates to domain B's view *across a frontier*: it never holds B, nor B's source — it
holds a coordinate, and the broker resolves it to a value.

*Container — two realms, one door.* A and B may sit in different realms (host today, OSGi/remote
tomorrow). Both depend on the ONE broker; neither depends on the other.

=== The granularity seam (guardrail)

The broker is COARSE — a serialize→sow→deserialize envelope round-trip. Right for a *realm boundary*
crossed *once per scope* with a *cohesive view* (one `BootstrapIdentity`, one runbook, one schema).
Sowing an envelope per accessor (`context.clusterCidr()`, one field, one path) would serialize JSON on
every read and degrade everything to `String` — a misuse. Fine narrowing stays plain value-records /
in-memory navigable views, cheap and typed, *inside* a realm. Rule of thumb: *broker = cross-realm,
coarse, wire-typed, once* — the coordinate is the relocated back-reference; *value-record / navigable
`View` = in-realm, fine, compile-typed, per-access* — the reference is in memory. A view that must
cross is delivered coarse *once* by the broker, then narrowed fine in-process.

== Anti-patterns this replaces

* *Fat interface consumed narrowly* — one wide type passed whole; invert to segregated views.
* *Hidden global* — `.current()` ThreadLocal / static `getInstance()` reached sideways; invert to an
  injected narrow view.
* *Service that knows its consumers* — a root that builds every view; invert so each role owns its
  adapter.

== Conformant exemplars (the pattern is already this system's idiom)

Proof that the pattern holds in production — do NOT re-invert these:

[cols="1,2,2",options="header"]
|===
| Subsystem | Where | How it conforms

| Doctor
| `DefaultHealthSystem` (doctor core)
| Passive `@Component(service=HealthSystem.class)`; `Specialist` contributors by
  `@Reference(MULTIPLE)` routed on `Specialty domain()`; `ClinicalAccess`/`MedicalRecord`/`Patient` are
  the narrow views; `admit(Patient)` the seam. Zero per-specialist knowledge.

| Seed broker
| `DefaultSeedBroker` (`host/`)
| Aggregates `SeedHandler` via `@Reference(MULTIPLE)`; passive, knows no handler. *Also* the
  cross-frontier projection substrate (see <<navigability>>) — a coordinate-addressed directory
  returning a reaped value, not a reference.

| Manifests domain channel
| `ManifestsDomainRegistrar` → `ManifestsDomainRegistry`
| `domain(policy)` SPI aggregated by `@Reference(MULTIPLE)`; no static registration.

| Pulumi outputs
| `PulumiOutputContributor` → `PulumiOutputRegistry`
| `add()`/`assemble()` contributor aggregation.

| Config (Stage A)
| `InfraDomain` → sealed `InfraConfigFragment` → `InfraConfigRegistry`
| The canonical contribution-without-acquaintance: fragments aggregated by id, zero per-domain
  knowledge. See link:../config/config-restructuring-spec.adoc[the config-restructuring spec].
|===

== Remaining hold-outs (application targets)

`NodeEnvContext` was the FIRST realized application: its fat interface is now a thin composite of
interface-segregated views — `BootstrapIdentity` and `NetworkTopology` (carrying the host MACs) —
with every consumer re-typed onto the view that concerns it. It is the working in-process `View`
exemplar the generalization section draws from.

The synthesis side still carries the anti-patterns elsewhere. Bringing them into conformance is the
remaining work:

[cols="1,1,3",options="header"]
|===
| Hold-out | Payoff | Note

| `ManifestSynthesisContext`
| large
| The one true hidden-global-plus-fat-interface: a ThreadLocal `.current()` consumed narrowly by ~28
  call sites, each taking ONE slice. The views already exist (`BootstrapIdentity`, `NetworkTopology`,
  `ComponentVersions`, `ImageState`, `IncusIdentityMaterial`, `FloxDebugPolicy`, `SopsAgeMaterial`).
  Invert to injected narrow views; delete the ThreadLocal.
|===

== Composition root & delivery — the jGiven scenario-state

The driving stack here is `junit → jgiven → steps → domains`, with JUnit as the entry point — so the
SCENARIO is the composition root, and jGiven's scenario-state is the concrete carrier of the common
context. (Legitimate only because the project deliberately made BDD the engine — jGiven-in-OSGi, the
boot is a scenario's first step; elsewhere this would be test-coupling.)

* the root PROVIDES the service at the top (`@ProvidedScenarioState`);
* each step CONSUMES only the view types that concern it (`@ExpectedScenarioState`, matched by type) —
  provide-at-top + consume-narrow, enforced by the framework, no `.current()` reach;
* below the step layer (step → synthesis service → units) it is no longer jGiven but the CASCADE: the
  step injects the narrowed views into the domains it drives.

*Discipline:* `@ScenarioState` is a type-matched shared bag — it stays narrow ONLY if each step
declares its segregated VIEW types, never a fat context. The pattern's view-segregation is what keeps
the jGiven vehicle honest; the mechanism alone does not enforce it.

== Generalization / foundation enrichment (future)

The pattern is proven in 5+ subsystems, so the temptation is a generic foundation. An exemplar survey
under the frontier lens (see <<navigability>>) refuted that: *the honest foundation is mostly what
already exists — ship ZERO new foundation types now.* Adaptation is not a config concern; it is the
general act of a rich source crossing a role boundary, and the machinery for that already differs by
tier:

* *Already generic — do not reinvent.* Contributor AGGREGATION is OSGi DS `@Reference(MULTIPLE)`. SCR
  is the runtime's contribution foundation; lean on it.
* *Do NOT abstract the registries.* They diverge exactly where abstraction is hard —
  `ManifestsDomainRegistry` (homogeneous units + DAG resolve) vs `InfraConfigRegistry` (heterogeneous
  sealed fragments + id↔type) vs Doctor (specialty routing). Forcing a generic registry leaks — this
  is the recorded deferral in link:../config/config-restructuring-spec.adoc[the config-restructuring
  spec] (`refactor/domain-registry-abstraction`).
* *Cross-frontier projection — NO new type; the broker already IS it.* Navigation across a frontier is
  `broker.sow(coordinate, cellar, seed)`; the substrate (`SeedCoordinate`, `SeedHandler`,
  `SeedEnvelope`, the sealed `ValueCoordinate`, the reflectors) is built and proven. A domain that must
  be reachable across the frontier *contributes* its coordinate + handler — it does not extract an
  abstraction. This is where Doctor's coarse `consult` crossing, manifests' `RunbookCoordinate`, and
  the config value channel already converge.
* *In-process projection — a navigable `View`, deferred by design.* The only genuinely new type worth
  extracting: a `View` holding an in-memory reference to its source, a role-owned adapter, monotone
  narrowing. Draw it FROM working code — after the first application (`NodeEnvContext`), not before —
  then confirm against a second. `BootstrapPaths.asStagingView` is the working seed to generalise from.
* *A standalone `Projection<S,V>` alias is SUBSUMED — do not add it.* Cross-frontier, projection already
  IS `SeedHandler.handle`; in-process it already IS the adapter method (`asStagingView`,
  `viewFor(domain, context)`). A `Projection extends Function` adds nothing over either concrete
  mechanism and would be the speculative abstraction this project forbids.

The litmus still holds: a candidate foundation must serve Doctor, the broker, and config alike. It does
— because for the cross-frontier tier they already share the broker, and the in-process tier is one
small `View` drawn from the first real application.
