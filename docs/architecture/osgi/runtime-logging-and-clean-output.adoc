= Runtime logging & clean exec output
:toc: left
:toclevels: 3

_How the embedded-OSGi execs keep their logging in ONE logback context, configured in
Java rather than inlined XML, and keep their stdout the PRODUCT (a CLI's YAML) — nothing
of the boot's noise leaking onto it._

== Overview

Every exec (`seed-outcluster`, `manifests-cli`, `netplan-cli`) boots an embedded Felix and drains
all logging — host JUL, Felix's own trace, the OSGi `LogService` — into ONE logback context
that `pax-logging-logback` owns. Two problems shape this file:

. *The logback config must be Java-coded, not an inlined XML string.* pax's only external-config
  channel is a Joran XML FILE, and its default is a `ConsoleAppender` whose native stdout write
  wedges the boot under a remote debugger. We want the noise-suppression POLICY (which trees are
  quieted, the root level) expressed in the codebase as Java, XML reduced to the bare plumbing.
. *A CLI's stdout IS its product.* `netplan-cli yamlExport` writes a blueprint YAML to stdout; the
  boot's pax-logging init lines and jGiven's plain-text scenario report must NOT corrupt it.

The mechanisms: a *fragment* carrying the logback policy in Java (`pax-logback-config`), a *launcher
trigger* that applies it across the realm seam, and a *`ConsoleReportExtension`* that brackets
jGiven's report. All three are OWNER-based — no `System.setOut` redirect, no helper.

== The logging convergence (recap)

JUL is the one channel that crosses the OSGi classloader boundary (pax embeds its own private
logback). Host slf4j binds to `slf4j-jdk14`; native emitters (io.grpc, the JDK) already speak JUL;
`FelixJulLogger` hands Felix's internal output into JUL via `felix.log.logger`. pax-logging-api's
`JdkHandler` then drains that JUL bus into `pax-logging-logback`, the single sink. So there is ONE
logback context in the process, and configuring it configures everything.

== The logback policy, coded in Java (the `pax-logback-config` fragment)

=== Why a fragment is mandatory

`pax-logging-logback`'s manifest carries *no `Export-Package`* — it embeds logback (and its own
internals) as private packages. A normal bundle therefore cannot reach the live `LoggerContext`: it
would bind its OWN logback copy, a different context than the one pax logs through. Only a
*fragment* — attached by `Fragment-Host: org.ops4j.pax.logging.pax-logging-logback`, sharing the
host classloader — links against pax's embedded logback and sees the real context.

The fragment is `osgi/runtime/pax-logback-config` (embed `type=dual-realm` is wrong here — it
exports nothing; `type=model` classifies + stages it like any carrier). It is installed but never
`start()`ed (a fragment has no lifecycle); it merges into pax when pax resolves.

=== The split: minimal bootstrap XML + Java policy

[cols="1,3"]
|===
| Bootstrap XML (`FrameworkLauncher.writePaxLogbackConfig`) | Java policy (`PaxLogbackConfigurer`)

| The PLUMBING, minimal: a FILE appender to `LaunchConfig.logFile` + root at the configured level.
  It exists only so pax configures from a file (via `StaticLogbackFile`) instead of its
  ConsoleAppender default during the boot window, before the policy runs.
| The POLICY, in Java: per-tree levels (io.netty / io.grpc.netty / org.apache.http … quieted so an
  INFO root never drowns the file) + the root level from `LaunchConfig.frameworkLogLevel`. The
  single source that WAS the old inlined `logback.xml`.
|===

=== The trigger: a reflective call across the realm seam

The flat host cannot reference the fragment's class (it lives in pax's realm). So `FrameworkLauncher`,
right after `framework.start()` returns (pax ACTIVE, bootstrap applied), loads the configurer THROUGH
the pax bundle's own classloader and invokes it reflectively:

[source,java]
----
bundle.loadClass("io.seedmatic.rke2lab.osgi.runtime.logback.PaxLogbackConfigurer")
      .getMethod("configure", Bundle.class, String.class)
      .invoke(null, bundle, rootLevel);   // rootLevel from LaunchConfig — values flow from the host
----

Nothing reconfigures the context afterwards, so the Java policy is the last word. A failure degrades
to a `LOG.warn` (to the file), never fells the boot.

=== Reaching the live `LoggerContext`

pax holds the context in `PaxLoggingServiceImpl.m_logbackContext` (a fresh `new LoggerContext()`
unless `StaticLogbackContext` is set). But the object registered under `PaxLoggingService` is not the
impl — it is its local wrapper `PaxLoggingServiceImpl$1ManagedPaxLoggingService`. The configurer scans
pax's registered services and unwraps the wrapper's synthetic enclosing reference (`this$0`) to reach
the impl and its field. This handles both context modes.

=== Config Admin was ruled out

Installing `felix.configadmin` and pushing the PID `org.ops4j.pax.logging` looks OSGi-native, but pax's
Config Admin channel only changes the *path of the XML file* (`…logback.config.file`) — it does not
accept an inline, Java-built config. It would add a bundle + a reconfiguration race for ZERO gain on
the "eliminate the XML" goal. The fragment reaches the context directly instead.

== Clean CLI stdout

Two sinks would otherwise reach the console; both are closed at their OWNER, not by redirecting
`System.out`:

* *pax's fallback logger* echoes logback's Joran status to the console at INFO ("Initializing
  Logback…"). Raised to ERROR via the framework property `org.ops4j.pax.logging.DefaultServiceLog.level`
  in `FrameworkLauncher` — only genuine boot failures reach the console; the file appender still
  carries INFO.
* *jGiven's plain-text scenario report* is printed from `JGivenExtension.afterAll`, gated on
  `Config.config().textReport()`. `ConsoleReportExtension` (registered FIRST in `@SeedScenario`, so its
  `beforeAll` runs first and its `afterAll` runs LAST) disables the text report in `beforeAll` via
  jGiven's Java `Config` API and restores the prior value in `afterAll` — after jGiven has already
  emitted (and thus suppressed) the report. A clean bracket, no system-property poking left behind.

The CLI then writes only its product (the blueprint YAML) to stdout.

== Anti-patterns

* ❌ *Inlining the logback config as an XML string in Java.* No advantage over a checked-in resource,
  and it hides the policy in a heredoc. ✅ Express the policy with the logback Java API in the fragment;
  keep only a minimal bootstrap XML for the boot window.
* ❌ *A normal bundle (or the flat host) casting `LoggerFactory.getILoggerFactory()` to `LoggerContext`.*
  pax-logging-api exports `org.slf4j`, so that returns pax's `PaxLoggerFactory` in every realm — the
  cast fails by TYPE. ✅ Reach the context through pax's internal `m_logbackContext`, from a fragment.
* ❌ *A DS `@Component` in the fragment as the trigger.* felix.scr reads `Service-Component` off the
  HOST bundle's own manifest, and pax declares none — a fragment-contributed component is invisible.
  ✅ Trigger from the launcher via `paxBundle.loadClass(...)`.
* ❌ *`System.setOut(System.err)` to hide noise.* jGiven caches the original `System.out`, so its report
  leaks anyway; and it is a blunt global side effect. ✅ Close each sink at its owner (the pax knob + the
  jGiven `Config` bracket).
