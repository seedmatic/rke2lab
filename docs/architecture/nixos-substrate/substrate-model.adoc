= NixOS node substrate — the model
:toc: left
:toclevels: 3

[NOTE]
====
The *vision* of the node substrate — the converged target shape, not a migration plan. The
alternatives explored and discarded on the way (Talos as node OS, running master bare on the NixOS
host, per-node hand-rolled cloud-init) are deliberately absent. Its companions carve out the
specifics: link:concern-ownership.adoc[where each concern lives],
link:flox-containerd-runtime.adoc[the flox containerd runtime], and

codebase↔vision before/after delta is the link:../atlas/nixos-substrate.adoc[atlas view].
====

== The vision in one paragraph

Every RKE2 node runs the *same NixOS substrate*, delivered as an immutable Incus image built from the
`lxc-container` NixOS profile (`config.system.build.{squashfs,metadata}`) and imported into the Incus
image store. A node's *role* is config, not OS:
control-plane vs worker is an RKE2 setting, master vs peer is a bootstrap-order handled by CAPRKE2 —
none of it forks the OS. The imperative `cloud-init`/`distrobuilder` provisioning collapses:
everything a node needs *before it joins* is baked declaratively into the image; everything *after it
joins* leaves the host — cluster-level delivery (manifests, secrets, ordering) becomes Flux GitOps,
and the residual host-mutating work (the flox containerd runtime, day-2 reconfiguration) is a
DaemonSet today and a Kubernetes controller (Go) tomorrow. Workloads run on the *flox containerd
runtime*, baked into the base image as a nix derivation. `bioskop-nixos` is the Incus hypervisor
host; master is seeded imperatively (Pulumi); peers and workers are grown by CAPI/CAPN from the same
images. Each concern sits in its own realm — *chacun son rôle*.

== Founding principle — chacun son rôle

The whole design is one separation of concerns. Every provisioning responsibility has exactly one
home, chosen by *when* it must happen and *what* it mutates.

[cols="1,2,2",options="header"]
|===
| Realm | Owns | Nature

| *OS image* (NixOS `lxc-container` build → Incus)
| the immutable homogeneous substrate + everything needed *before cluster join*
| declarative, baked, reproducible

| *Bootstrap config* (CAPRKE2 for peers/workers; seed for master)
| RKE2 role (server/agent), cluster-init vs join, per-node identity, join token, labels/taints
| per-node, generated at provisioning

| *Cluster delivery* (Flux GitOps — already in the stack)
| manifests, secrets, readiness/ordering gates, layer activation
| post-join, cluster-only, no host mutation

| *Host mutation* (DaemonSet → Go controller)
| flox containerd runtime shim, day-2 host reconfiguration
| post-join, mutates the node host

| *Provisioning engine* (Pulumi + Incus provider, host-side)
| the VM/instance graph: Project·Network·Profile·Image·Instance for master; CAPN for the rest
| imperative for master, declarative CAPI for peers/workers
|===

The rule that decides the boundary: *a responsibility that must exist before the kubelet runs cannot
live in Kubernetes* — it belongs to the image. A responsibility that only mutates cluster objects
belongs to Flux. A responsibility that mutates the host *after* the node has joined belongs to the
DaemonSet/controller. The full redistribution table — old responsibility → new home — is
link:concern-ownership.adoc[its own spec].

== The node model — three types, two roles, one substrate

There are three node *types* but they collapse onto two differentiation axes, and only one of those
axes touches the OS.

[cols="1,2,2",options="header"]
|===
| Axis | master vs peers | control-plane vs workers

| Nature
| same role (control-plane); master is the *first* node (cluster-init), peers *join*
| RKE2 `role`: *server* vs *agent*

| Level
| bootstrap-order — CAPRKE2 handles it (first replica inits, others join)
| config — `services.rke2.role` + taints/labels

| Impact on OS image
| *none* — master ≡ peer at the OS level
| *the only real functional split*
|===

Consequences:

* *master and peers are the same OS.* What makes master "master" — being first, hosting the CAPI
  operators and Flux — is bootstrap-order and cluster-level (pods), never the image.
* the image split follows the *RKE2 role* (server/agent), not the master/peer distinction.

=== Image factoring

* `rke2lab-node-base` — a NixOS *module* (not an image): the shared substrate — Nix, Flox, ZFS,
  containerd + the flox runtime, networking, the `systemd.services.*` that replace the old
  materialised units. See the `nixos/` directory (`default.nix` aggregates the per-concern modules).
* `rke2lab-control-node` — image = base + control-plane module (RKE2 server, kube-vip, etcd). Run by
  *both* master and peers.
* `rke2lab-worker-node` — image = base + worker module (RKE2 agent).
* future specialised workers — `rke2lab-worker-gpu-node`, `rke2lab-worker-storage-node`, … — each =
  base + its specialisation module. Homogeneity lives at the *base*; specialisation is *additive*.

Because NixOS shares the store across closures (cachix dedup), a derived image is only a thin delta
over the base — "based on the base" literally, and cheap.

[mermaid]
----
flowchart TB
  base["rke2lab-node-base<br/>(shared module: nix, flox, zfs,<br/>containerd + flox runtime, networking)"]
  ctrl["rke2lab-control-node<br/>(+ rke2 server, kube-vip, etcd)"]
  work["rke2lab-worker-node<br/>(+ rke2 agent)"]
  gpu["rke2lab-worker-gpu-node<br/>(+ drivers, accel shim)"]
  base --> ctrl
  base --> work
  work --> gpu
  ctrl -. "master (seed) + peers (CAPN)" .-> use1["instances"]
  work -. "workers (CAPN)" .-> use1
----

== The maturation arc

The post-join host mutation follows one arc, deliberately staged:

. *scripting via DaemonSet* (today) — host-asset materializer, shell.
. *baked declaratively* where stable — into `rke2lab-node-base` (the flox runtime, the networking,
  the containerd config).
. *Go controller* for what stays dynamic — a reconciler over a CRD, with a DaemonSet agent as its
  hands. Replaces the residual scripting with typed, reconciled code.

The controller never crosses the pre-join floor either: bootstrap-critical config is always the
image.

== Open refinements (not blockers)

* *master OS delta — light or heavy?* If master's OS-level specifics are light (a `hostname`-gated
  dbus-TCP drop-in, a few sysctls), they live as `lib.mkIf (hostName == "master")` inside
  `rke2lab-control-node` → *two images total*. Only a *heavy* OS delta (daemons/packages the fleet
  must not carry) justifies a distinct `rke2lab-master-node` → three images. To settle: inventory
  master's real OS delta.
* *shim build locus.* runtime build during dev vs baked at image time when stable — the switch point
  per shim (see link:flox-containerd-runtime.adoc[the runtime spec]).

Per-node injection is *settled*: hostname + RKE2 role + join token + ZFS dataset reach each instance
over *devlxd* (the Incus guest API), read back at boot by `nixos/identity.nix` — one image serves
many nodes. The node-side bootstrap objects (CNI + Flux) reach the node the same way; see
link:node-bootstrap-delivery.adoc[node-bootstrap delivery].
