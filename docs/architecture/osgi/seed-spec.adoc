= The seed — orchestration architecture (host↔OSGi ownership, the embedded seam)
:toc: left
:toclevels: 3

[NOTE]
====
The design of the SEED subsystem — the orchestration that provisions the management cluster (the
`seed-outcluster` program, whose `controlplane` package is being redistributed into sub-modules). This spec
carries the seed's ARCHITECTURE in prose: who owns what across the host↔OSGi seam, why the OSGi world is
detached-by-design with the embedded exec as a special case, and the migration roadmap. Its sibling
documents: link:../bdd/bdd.adoc[the BDD-as-engine pattern] (the engine the seed is expressed on — a
transverse pattern, not seed-specific) and link:../atlas/seed.adoc[the seed atlas L1 view] (the
figures + verdicts). This file is the seed's *design*; those are the *pattern* and the *view*.
====

== Ownership and the seam — OSGi reasons, the host feeds and renders

*Lead: OSGi owns the scenarios + engine + reasoning (they already live there); the host injects the
`RunMode` fact + Pulumi context and renders/writes back. The cross-world edge crosses as a serialized
`ScenarioModel`, grafted into the host runbook — the live jGiven object never crosses.*

The pipeline is *owned by the OSGi world*; the host is a consumer. Two facts of the code already put it
there: jGiven is already an OSGi bundle (`jgiven-wrap`, with an in-container testkit), and the JUnit
launcher already runs inside embedded Felix (`InContainerJUnitRunner` drives `LauncherFactory` under
the testkit). The bootstrap reasoning — the scenarios, the doctor consult, the readiness verification,
the runbook — is *target-state OSGi*; it is only *stranded* in `exec/seed-outcluster` today.

[cols="1,2,2",options="header"]
|===
| | *OSGi world* (owner) | *host* (`exec/seed-outcluster` + `pulumi-edge`, consumer)
| role | the brain — reasons about the bootstrap | thin launcher + the Pulumi edge
| holds | the scenarios, the jGiven session + engine, the launcher, the doctor, readiness, the
  `ReportModel` runbook | framework boot (already OSGi via `BootPipeline`), the *source* of `RunMode`,
  the stack *sink*
| jGiven engine + launcher | *here* (`jgiven-wrap` + `junit-testkit`) | —
| the seam | *produces* the runbook + the output contributions | *injects* `RunMode` + Pulumi context,
  *renders* the runbook, *assembles + writes* the stack
|===

The seam keeps the discipline this spec is built on: *a domain never reaches for the global flag.*
`RunMode` (which only the host can know — it derives from `Deployment.isDryRun()`) is *injected* into
the OSGi world as a value; the OSGi world reasons; the host renders and writes. The founding constraint
travels intact: probes-as-steps and the runbook are produced OSGi-side; the host only renders/exports.

*The cross-world edge = a grafted scenario — SHIPPED as `ScenarioGraft`.* A `@NestedSteps` composes
within ONE world (one jGiven engine, one `ReportModel`). A dependency that crosses the world boundary
cannot be a nested step — two engines, two `ReportModel`s, and a live jGiven object would
`ClassCastException` on the flat host loader. So it is a graft, in one horticultural register: the
scenario played in the other world grows there into a *scion*, serializes to a JSON String (the only
thing that crosses — no live jackson type), and the host `rebuild`s a model of its own realm and
`graftUnder`s the scion's steps onto its *rootstock* step (the host step executing the crossing)
→ the operator reads ONE continuous tree, from the seed down to the scion's root cause. The verdict
travels IN the model: if the scion is FAILED, the graft marks the rootstock step FAILED, and the sow's
default throws on it, so jGiven skips the host's downstream steps (the local fail-fast, reproduced
across the frontier). *One serialized
scenario suffices* — it carries both the narration (steps → the sub-tree) and the verdict
(`executionStatus` → the propagation). The mechanism is DISSOCIATED from the worlds it grafts across:
`ScenarioGraft` (`osgi/runtime/scenario-engine`) speaks only jGiven's report model, so the same graft
serves any scion — OSGi in-container today, HTTP-remote tomorrow. Its execution twin — one broker door
instead of N service verbs — is link:seed-broker-spec.adoc[the seed-broker design].

=== The horticultural register — the two twins, one cycle

The crossing has ONE register, played by two twins. A client sows a *seed* (the request `Document`);
it germinates into a *plant* (what grew — the response `Document`). The two twins see that same grown
thing differently:

[cols="1,2,2",options="header"]
|===
| | *execution twin* (the broker) | *observability twin* (the graft)

| what grew | the *plant* — the response `Document` `sow` returns | the *scion* — the played scenario's `ScenarioModel` (a plant, narrated)
| the verb on it | *harvest* (récolter) — read it, opaque, by key | *graft* — `graftUnder` its steps onto the *rootstock* step
| currency | a `Document` (opaque JSON payload) | a jGiven `ReportModel` (agnostic narration)
|===

So *plant* and *scion* are the SAME object seen by the two twins — one harvested (data, the machine
channel), one grafted (narration, the human channel). The full cycles: execution = *seed → sow → plant
→ harvest*; observability = *seed → sow → scion → graft/rootstock*. The harvest is opaque: the host
reads the plant BY KEY (never by holding a domain class) — when it needs to know the seed's or plant's
shape, it ASKS the broker (introspection is itself a `sow` at a meta-coordinate; see
link:seed-broker-spec.adoc[the seed-broker design]).

== The OSGi world is detached by design — embedded exec is a special case

*Lead: the general case is a detached OSGi world (remote); seed-outcluster's embedded exec merely folds the
seam in-process. The launcher is one more consumer of the R4 boot seam. Pulumi belongs to the
embedded/bootstrap host only, not the world.*

The general case is a standalone OSGi world running as a service — it *amorces itself*, and the host is
a *remote client* that connects, injects `RunMode` + the Pulumi context, and pulls back the runbook and
the output contributions across the remote frontier. The embedded exec (`FrameworkLaunch.
embedded()`) is *one particular case* — the degenerate one where the host co-locates and boots OSGi
in-process. The chicken-and-egg amorce ("what starts OSGi cannot run inside OSGi") is *real only in the
embedded case*; detached, the OSGi world has its own internal amorce.

*This does NOT bar the boot from being a jGiven step* (see link:../bdd/bdd.adoc#the-model[the model]).
The thing that "starts OSGi" is the JUnit launcher + its `main()`, which run on the HOST flat classpath,
OUTSIDE Felix — so they do not run *inside* OSGi, and the paradox does not touch them. The launcher
plays the seed scenario whose *first step* is the boot effect (launch Felix); every later step reasons
within the framework that first step opened. "What starts OSGi" (host launcher) and "what runs inside
OSGi" (the reasoning steps) are different threads/classpaths — the frontier is exactly the seam the
broker crosses and the graft narrates (Figure 2).

The launcher does not change this — it is one more consumer of the R4 boot seam (Felix in `Pulumi.run`).
`InContainerJUnitRunner` already drives a JUnit launcher *inside* Felix; `JGivenTestkit.felix()` proves
the jGiven runtime (byte-buddy proxy, `ScenarioExecutor`, `ValueInjector`) boots in-container — the
coupling that gives the state-DAG + the execution nesting. The live boot seam is in production:
`Main` (inside the `Pulumi.run` lambda) drives `JUnitLauncherCore` on the host flat classpath, playing
`ClusterSeedScenario`, whose first jGiven step launches embedded Felix (`FrameworkLaunch` via
`OsgiConnection.embedded()`).

*Which use case is which* (two real seed use cases, not a theoretical symmetry):

[cols="1,2,2",options="header"]
|===
| | *seed-outcluster (bootstrap)* | *seed in-cluster (other uses)*
| mode | *embedded exec* — boots OSGi in-process | *detached workloads* — OSGi as a separate workload, remote
| why this mode | it *precedes* the cluster: there is no cluster yet to deploy a workload into, so it
  must embed and amorce OSGi itself — *this* is why it owns the amorce paradox | the cluster already
  exists; the OSGi world runs as a workload, accessed remotely — nothing needs to amorce it in-process
| Pulumi edge (`RunMode`, stack sink) | *yes* — seed-outcluster *creates* the infra via Pulumi, so
  `Deployment.isDryRun()` is a fact only here | *no* — a workload runs *inside* the already-created
  cluster; it has no `RunMode`
|===

This lands the Pulumi coupling precisely: it is *not* a property of the OSGi world — it is a property
of the *bootstrap's embedded host*. The detached OSGi world knows nothing of Pulumi. Which confirms, by
a second route, that the preview trigger and the stack sink live at the *host edge* (`pulumi-edge`),
never in the OSGi reasoning.

The concern was that `context.export` is synchronous on the `Pulumi.run` lambda thread while the test
harness runs the launcher on a dedicated TCCL thread. It conflated the harness with the production
path: host-world scenarios run on the lambda thread (no OSGi realm → launcher inline, export
synchronous); OSGi-world scenarios run inside Felix on ITS own thread — the host never drives that
thread, it `sow`s via the broker and `graftUnder`s the returned scion runbook. *The thread/TCCL
frontier IS the seam* — no live jGiven object ever sits on the export thread.

[[migration]]
== Migration — the unit is a DOMAIN, not a pipeline

*The method (revised 2026-07-09): the migration unit is a DOMAIN, not a pipeline. The old
"one-pipeline-at-a-time, fold its phases into seed-outcluster" plan was written before the seed-broker
realization; two scans (controlplane + manifests-core) invalidated its hypotheses — the destination is
the DOMAINS, not seed-outcluster, and the seed's host pipeline does not fold, it DISSOLVES into a cascade
of broker `sow` calls into per-domain sub-scenarios.*

=== Why the unit changed

The controlplane scan found seed-outcluster holds ~10 classes of pure domain reasoning stranded host-side,
whose real home is a domain's OSGi `-core` (e.g. `ClusterBootstrapReadinessVerifier`→cluster,
`SeedSystemdAdapterEndpointGate`→systemd, `BboxReconciliationOrchestrator`→bbox). So "migrate a
pipeline" is the wrong verb: there is nothing to re-host into seed-outcluster. Per domain, the migration is
a triptych:

. *Re-dispatch* — its host-stranded reasoning descends to its `-core` (Pulumi-blind, so legal in OSGi).
. *Scenario* — its scenario lives in its `-bdd`, played IN-CONTAINER (the bloom).
. *Host* — seed-outcluster keeps ONLY the Pulumi-irreducible (`*Resource`, the edge) + a broker `sow` and a
  graft. The host stage becomes a *sowing post* toward the domain bloom, not a place the logic lives.

The seed's root scenario stays host (Pulumi sows the first seed = launches it); its phases that need a
domain OPEN a sub-scenario played in-container, whose `ScenarioModel` grafts back — the germination
cascade (see link:seed-broker-spec.adoc[the seed-broker], § the cascade). E1 ("a `-port` sheds
`type=seam` when 0 host files import it") is now a MEASURABLE CONSEQUENCE of the re-dispatch: each
class moved host→OSGi drops one `-port`'s host-import count toward 0.

=== What is shipped

. *Engine-lifecycle socle — SHIPPED (2026-07-05).* Launcher, connection, lever, disciplines in
  `osgi/runtime/scenario-engine`; see link:engine-lifecycle-spec.adoc[engine-lifecycle-spec].
. *The seed-broker door — SHIPPED (2026-07).* One `SeedBroker.sow(Coordinate, Document)` dispatched to
  `SeedHandler`s subsumes the former N crossing verbs; see link:seed-broker-spec.adoc[the seed-broker].
. *The cross-world graft — SHIPPED (2026-07).* `ScenarioGraft` (`osgi/runtime/scenario-engine`, host
  side) is the generic mechanism `rebuild(runbookJson)→ReportModel` + `graftUnder(hostScenario,
  hostTree, soil, scion)` under the executing step, FAILED propagated. Horticultural register, one throughout: the host sows a
  seed, it grows into a `scion` (played in-container), the scion is grafted onto the host tree at its
  `rootstock` step (the step that stands for the crossing). Proven in `ScenarioGraftTest` (was only the
  pinned `CrossWorldGraftSpikeTest`). It is a FOUNDATION every per-domain migration reuses, not a
  cluster detail — the observability twin of the broker.

=== The per-domain worklist

. *cluster FIRST* — its `-bdd` already exists (`cluster-bdd`, the in-container readiness scenario).
  Re-dispatch `ClusterBootstrapReadinessVerifier`→`cluster-core`; the host `ClusterReadinessStage`
  becomes a sowing post: `sow` the checkpoint, `graftUnder` the returned bloom. This is where the
  graft's PROD wiring lands (the mechanism is generic; cluster is its first caller).
. *the other domains* — systemd, bbox, incus, doctor, manifests-reasoning — each the same triptych,
  each dropping its `-port`'s host-import count. Vocabulary hygiene (a domain scene stops importing the
  envelope machinery) falls out per domain.
. *`consult` folds into the broker* — its real provider needs `HealthSystem.admit(patient)` host-side
  (a doctor-migration increment); until then it stays a `ConsultingService` verb (2 seams, not 1).
. *`pipeline-port` dissolved* — DONE. Its scenario natures `Topic.Checkpoint`/`Pipeline` were removed
  first (2026-07-09: 0 prod implementors after the seed moved its scenarios to the broker), leaving
  `Topic.Execution` alone — pure value-threading, jGiven-free. With the seed's fluent `during/then`
  gone, the grammar's only surviving OSGi consumer was manifests-core, so the shared seam had no
  reason to stand: the engine relocated INTO manifests-core as
  `io.seedmatic.rke2lab.manifests.internal.synthesis` (`Phase`/`PhaseRunner`/`PhaseFailure`, un-exported),
  the unit `Topic`→`Phase` (neither the pipeline word nor jGiven's `Stage`). The boot ceased to be a
  `Topic` too: `FrameworkLaunch.embedded().launch()` is invoked as a scenario's first jGiven step, not
  a pipeline verb. `PipelineContext` died with the host. The gate `PIPELINE_PATTERN` became
  `SYNTHESIS_PATTERN`.

The mechanisms not yet productionised (the `PendingMarkingScenarioExecutor`, the `SCENARIO_STATE_DAG` gate) have their
reference sketch pinned at tag `spike/bdd-pipeline-poc`: `DagGateSpikeTest` (the topological gate),
`PollUntilReadyExtension` (adaptive poll — live form `SeedSystemdAdapterEndpointGate`). The graft
shipped; the rest shipped with the socle.
