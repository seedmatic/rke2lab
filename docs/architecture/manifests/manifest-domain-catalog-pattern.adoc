= ManifestDomainCatalog: Single Source of Truth for Domain IDs
:toc: left
:toclevels: 2

**Status**: ✅ Enforced (as of 2026-05-31)

== Overview

`ManifestDomainCatalog` is the *canonical registry* for all manifest domain identifiers. It prevents identifier mismatches by providing typed accessor methods instead of magic strings.

**What it solves**: The `clusterApi: false` bug (May 2026) where hardcoded string `"clusterApi"` didn't match the catalog's actual ID `"cluster-api"`, causing policy values to silently default to `false` instead of using the configured `true` value.

== Architecture

=== Catalog as Single Source

A domain string is spelled exactly once — in a `public static final String` constant on the record. Two faces read those constants, and each face has one consumer shape. The figure below traces the `cluster-api` string from its single definition to both faces.

[mermaid]
....

    subgraph ssot["ManifestDomainCatalog (contract record)"]
        Const["CLUSTER_API = &quot;cluster-api&quot;<br/><i>public static final String</i>"]
        Acc["clusterApi()<br/><i>instance accessor</i>"]
        Const -.->|returned by| Acc
    end

    subgraph regface["Registrar face — direct constant"]
        Reg["ClusterApiDomainRegistrar<br/>new ManifestsDomain(CLUSTER_API, …)"]
    end

    subgraph polface["Policy face — via accessor"]

        Role["ClusterRole.domainPolicy<br/>enableOnly(enabledDomainIds(catalog))"]
        Role -->|drives| Pol
    end

    Const -->|referenced by| Reg

**Key principle**: Domain IDs are *data*, not code — defined once, referenced everywhere. Registrars reference the *constants* directly (they compose `"<domain>/<leaf>"` unit IDs at static-init time, which the accessors cannot). The *instance accessors* live one level down, inside the `ManifestDomainPolicy.Builder` setters, so the scion drives the policy with type-safe per-domain methods rather than strings. Both faces resolve to the same constant, so a mismatch is impossible.

=== Domain ID Formats

[cols="1,2,2,2", options="header"]
|===
| Domain | Constant (SSOT) | Instance Accessor | Actual ID String
| Cluster API | `CLUSTER_API` | `catalog.clusterApi()` | `"cluster-api"` (kebab-case)
| High Availability | `HIGH_AVAILABILITY` | `catalog.highAvailability()` | `"high-availability"` (kebab-case)
| Networking | `NETWORKING` | `catalog.networking()` | `"networking"` (single word)
| All others | UPPER_SNAKE constant | camelCase accessor | lowercase string
|===

**Critical**: Multi-word domains use *kebab-case* strings but *camelCase* accessors (and *UPPER_SNAKE* constants). Hardcoding the string directly — in any casing — causes mismatches. The accessor merely returns its constant, so the two are always in lock-step.

== Usage Patterns

=== ✅ Registrar face: reference the constants

A `ManifestsDomainRegistrar` declares its domain ID and its dependency IDs from the constants — no `policy` parameter, units built with plain `new`. See `GitopsDomainRegistrar` / `ClusterApiDomainRegistrar`. The teaching shape:

[source,java]
----
return new ManifestsDomain(
    ManifestDomainCatalog.GITOPS,                 // ✅ single source
    List.of(ManifestDomainCatalog.PLATFORM),      // ✅ dependency ID from the same constant
    List.of(new FluxOperatorManifestsUnit(), new FluxInstanceManifestsUnit(), …));
----

The constants (not the accessors) are used here because a manifest unit composes its `"<domain>/<leaf>"` ID from `CLUSTER_API + "/operator"` at static-initialization time — a `static final String` can do that, a built-catalog accessor cannot.

=== ✅ Policy face: drive the typed setters

The scion never touches strings either. `ManifestDomainPolicy.Builder` exposes one boolean setter per domain (`clusterApi(b)`, `gitops(b)`, …), each of which stores `put(catalog.clusterApi(), b)` internally — that is the *only* place the instance accessors are consumed. `ClusterRole` is what drives them, from the cluster's own identity:

[source,java]
----
// ClusterRole.domainPolicy — the domain set is a FUNCTION of the role parsed from
// the `<host>-<role>` clusterName, not an operator toggle (see f51ba1d10: PublishFacet
// removed, membership is structural and replays from the identity on every render).
ManifestDomainPolicy.builder()
    .domainCatalog(catalog)
    .enableOnly(enabledDomainIds(catalog))   // catalog accessors, never literals
    .build();
----

The discipline is unchanged by that move, and is the whole point of this document: whichever face
drives the policy, the domain IDs come from the catalog's accessors. `enableOnly` takes the same
`catalog.gitops()` / `catalog.clusterApi()` values the per-domain setters would have stored.

=== ❌ Wrong: hardcoded strings

Any string literal for a domain ID re-derives what the catalog already owns and can drift from it:

[source,java]
----
new ManifestsDomain("gitops", List.of("platform"), units);  // ❌ duplicates the catalog
----

== The Bug We Fixed

In May 2026 `clusterApi` showed `false` in `MANIFEST.yaml` even though Pulumi reported it enabled: the serialization code carried the literal `"clusterApi"`, which is *not* a catalog ID — the real ID is `"cluster-api"` (kebab-case) — so the lookup silently fell through to the default `false`. The lesson survives even though the offending call site (a host-side `HostSlotManifest` policy map) is no longer in the exec path: a domain string written by hand, in any casing, is a mismatch waiting to happen. Route every reference through the constant or its accessor and the compiler guarantees the match.

== Enforcement Rules

=== Rule 1: Never Hardcode Domain ID Strings

**What**: Domain IDs like `"cluster-api"`, `"gitops"`, `"networking"` must NEVER appear as string literals in domain-related code.

**Where it applies**:
- `ManifestsDomainRegistrar` implementations (in the `domain/` package) — reference the *constants* (`ManifestDomainCatalog.GITOPS`).
- Manifest-unit ID composition — build `"<domain>/<leaf>"` from a constant.
- Policy derivation in the manifests scion (`ManifestSynthesisScenario.the_policy_is_derived_from_the_facet`) — use the typed `ManifestDomainPolicy.Builder` setters, which reference the *accessors* internally.

**Exceptions**:
- The catalog's own constants and default-domain lists (`addDefaultDomains()` — the one place the literals are declared).
- Test fixtures where IDs are explicitly being tested.

**Violation vs correct**:
[source,java]
----
new ManifestsDomain("gitops", …)                 // ❌ hardcoded
new ManifestsDomain(ManifestDomainCatalog.GITOPS, …)  // ✅ constant
----

=== Rule 2: Initialize Catalog as Static Final Where a Built Instance Is Needed

Registrars need only the constants, so most do not hold a catalog instance. The scion, which drives the policy builder, keeps one immutable instance:

[source,java]
----
private static final ManifestDomainCatalog CATALOG =
    ManifestDomainCatalog.builder()
        .addDefaultDomains()
        .addDefaultStageALinkableDomains()  // publishable facet domains
        .build();
----

**Why**: the catalog is immutable once built — share one instance, and let `build()` validate that every Stage-A-linkable domain is registered.

=== Rule 3: Grep for Violations in CI

Add to the CI pipeline (example):

[source,bash]
----
# Fail if any registrar constructs a domain from a string literal
! grep -rn 'new ManifestsDomain("' osgi/domains/manifests/
----

== Adding a New Domain

**Steps**:

1. Add the constant, then its accessor, to `ManifestDomainCatalog`:
+
[source,java]
----
public static final String MY_NEW_DOMAIN = "my-new-domain";  // kebab-case for multi-word

public String myNewDomain() {
  return MY_NEW_DOMAIN;
}
----

2. Add the constant to `Builder.addDefaultDomains()` (and to `addDefaultStageALinkableDomains()` if the operator toggles it):
+
[source,java]
----
return addAllDomains(List.of(CLUSTER, STORAGE, …, MY_NEW_DOMAIN));
----

3. Add the typed boolean setter to `ManifestDomainPolicy.Builder`, delegating to the accessor:
+
[source,java]
----
public Builder myNewDomain(boolean enabled) {
  put(domainCatalog.myNewDomain(), enabled);
  return this;
}
----

4. Build the domain registrar from the constant:
+
[source,java]
----
return new ManifestsDomain(ManifestDomainCatalog.MY_NEW_DOMAIN, …);
----

5. Wire the new setter to the publish facet in the scion's policy derivation (`ManifestSynthesisScenario.the_policy_is_derived_from_the_facet`):
+
[source,java]
----
.myNewDomain(publish.myNewDomain())
----

**That's it!** All existing consumers reference the same constant, so they stay in lock-step.

== Troubleshooting

**Q: Policy shows `true` in Pulumi outputs but `false` in MANIFEST.yaml**

A: Domain ID mismatch. Check if the serialization code uses hardcoded strings instead of catalog methods.

Debugging steps:
1. Add debug logging to see raw vs parsed values
2. Grep for hardcoded domain strings: `grep -r '"your-domain"' src/`
3. Verify catalog method returns expected ID: `System.err.println(catalog.yourDomain())`

**Q: New domain doesn't appear in policy**

A: Check these locations:
1. `ManifestDomainCatalog` - accessor method exists?
2. `Builder.addDefaultDomains()` - ID in the list?
3. `ManifestSynthesisScenario` (the scion) - policy derivation from the facet added?
4. `ManifestDomainPolicy.Builder` - setter method exists?

**Q: Can I use domain ID strings in tests?**

A: Yes, but prefer catalog methods even in tests for consistency. Only use strings when explicitly testing ID matching logic itself.
