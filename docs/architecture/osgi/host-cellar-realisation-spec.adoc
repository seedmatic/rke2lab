[NOTE]
.The cellar SPLIT into three faces (shipped) — this doc was written around ONE `Cellar`, read it through the split
====
This doc was drafted around a SINGLE `Cellar` interface the host implements and `registerService`s. The
shipped shape is a *split by realm*, and every mention of "the host `Cellar` impl" below should be read as
`PulumiCellar implements OpaqueCellar`:

* `OpaqueCellar` (`seed-broker-port`, `type=seam`) — the HOST-implemented face: opaque `SeedEnvelope`
  verbs only (`store` / `fetch(parcel)` / `fetch(parcel, coordinate)` / `withdraw(parcel, coordinate)` /
  `neighbours` / `conserve`). The host provides and consumes ONLY this; it never opens a payload.
  `PulumiCellar` implements it; the tests use `EphemeralCellar` / `InMemoryCellar` / `RefusingCellar`.
* `Cellar` (`seed-broker-port`, OSGi-only) — the TYPED view: the generic `<T>` overloads, each carrying a
  `Sensitivity {PLAIN, SEALED}` and (a capability-default) a `Persistence {DURABLE, TRANSIENT}` +
  `trailOf`. It does NOT extend `OpaqueCellar`. Its `@Component` realisation `CodecCellar`
  (`seed-broker-runtime`) is a DECORATOR: it takes an `OpaqueCellar` by `@Reference`, holds a `SeedCodec`
  (`seed-broker-codec`) and a `CellarCipher`, and adds the decode + the seal/reveal.
* `ScenarioCellar` (`scenario-engine`, `implements TransactionalCellar extends Cellar`) — the UNIVERSAL
  transactional cellar EVERY scenario is INJECTED (host root AND in-container scion), and the SOLE writer
  of a tag on the run's `ReportModel`. `store` tags (the within-run write set); only the ROOT drains the
  folded tags to the durable `OpaqueCellar` at the run boundary (§ seed-broker-spec, cellar-transactional).
  `TransactionalCellar` + `TxIdSeed` are the shipped transactional overlay — they SUPERSEDE the originally
  designed `SeedRunLedger`/`SeedRunLedgerExtension` (never built under those names).

Sensitivity is honoured OSGi-side (`CodecCellar`/`ScenarioCellar` seal a `SEALED` value through the
`CellarCipher` — `PassphraseCellarCipher` mono stand-in, or `AgeCellarCipher` in `cellar-cipher-age` when
provisioned — BEFORE the payload crosses), so `PulumiCellar` persists only the opaque, MAC-bound coquille.
See link:../atlas/cellar-secrets.adoc[cellar-secrets] for the clean/smudge vision.

The implementation plan at the end (§ <<plan>>) is the HISTORICAL record of how this shipped; the fusion
map + open questions there are closed.

== Why this is the first step (how we got here)

Attacking the host top-down (`Main` → `ApplicationPipeline` → …) the build stops BELOW seed-outcluster, in
`pulumi-edge`, on `package io.seedmatic.rke2lab.doctor.port does not exist` /
`io.seedmatic.rke2lab.doctor.records does not exist`. Those packages were de-seamed into
`doctor.contract` (records fused, the `-port` seam dissolved). Three `pulumi-edge` classes still import
them:

* `StackMedicalRecordJournal` (implements the old `MedicalRecordJournal` READ port)
* `StackInterventionJournal` (implements the old `InterventionJournal` READ port)
* `PulumiInterventionLedgerWriter` (implements the old `InterventionLedgerWriter` WRITE port)

The seed-broker spec already prescribes their fate: *the three fuse into ONE `Cellar` impl over the
Pulumi backend.* Everything OSGi-side is already shipped (see § <<already-shipped>>); the ONLY missing
link is this host impl. Realising it unblocks the whole host compilation and is prerequisite to the
domain-by-domain BDD migration above it.

== The model — confirmed from the design, corrected against my own conflation

Two facts the reading settled, both load-bearing and both places I had it wrong first:

. *This is the realisation of the CELLAR role — one of the five gardening roles, defined at
  link:gardening-model-spec.adoc[the gardening model].* The model states, and this doc does NOT re-derive:
  the cellar is the COMMISSIONER's conservation organ (not a third actor, not the gardener's); one
  gardening = one cellar; the végétal is opaque, addressed by a neutral `Parcel`, never read. What THIS
  realisation adds — the *how* over the Pulumi backend:
  ** the verbs are pure Pulumi-backend gestures: `store`/`fetch` = write/read a `végétal` as a stack
     OUTPUT keyed by coordinate slug, `withdraw` = drop that output from the current state (§ the fridge),
     `neighbours` = enumerate the sibling stacks under the same soil. `Parcel(project, stack)` IS a Pulumi
     stack reference said in gardening words.
  ** *Two soils, one verb (§ one-history).* A `Parcel` is either the RUN's OWN stack — the live Pulumi
     deployment installed on this thread targets it (`PulumiDeploymentSeed.targets`) — or a SIDE stack (the
     doctor's ledger, its own project `intervention-ledger`, no live deployment). The run's own stack CANNOT
     take a separate `createOrSelectStack(...).up()`: that stack is the very one the outer `pulumi up` is
     running, so a nested `up` deadlocks on its lock AND is clobbered by the outer program (one `up` is
     authoritative over the whole resource set). So the run's cellar STAGES its stores and, at the drain,
     `conserve` re-declares the whole live set as `rke2lab:cellar:Entry` resources INTO that same running
     deployment — the harvest folds into the ONE history beside the infra (incus, cluster). A side stack has
     no live deployment, so it keeps the eager out-of-run `up()` (a stable resource name per coordinate makes
     each append a history entry). `fetch` is FILTERED to the `rke2lab:cellar:Entry` type so the resources the
     run's stack co-hosts (the incus provider, the root `Stack`) are never mistaken for coquilles. The
     discriminant differs by VERB: a WRITE asks the thread-local deployment (`targets` — staging into the one
     live deployment needs it on THIS thread), but a READ asks the run stack's IDENTITY
     (`PulumiDeploymentSeed.runStack`, captured host-side at construction). A scion plays on its OWN worker
     with no deployment installed, so a thread-local read would fork it to the side-stack history-walk and
     RESURRECT a coquille a prior reap dropped — a run-stack delete is a tombstone-less omission the history
     fold cannot honour (the seal read a destroyed CA the grow could not: the seal-vs-grow divergence).
     Deciding the read by identity makes every thread read the run stack's current state alike.

== The two contracts (a FRIDGE — put / peek / take) — the OPAQUE seam + the TYPED OSGi face

The cellar is CURRENT STATE (put / peek / take), not an append-only journal — the "append-only" the older
draft named was the DOCTOR's usage mistaken for a law (correction 2026-07-15, § seed-broker-spec "the
cellar is a fridge"). The `Parcel` is the fridge (the whole furniture), the `SeedCoordinate` the case
within it. The contract SPLITS by realm: the host implements only the OPAQUE seam, the typed `<T>` face
is an OSGi-only decorator over it.

*`OpaqueCellar` (`seed-broker-port`, `type=seam`) — the HOST-implemented face, opaque only:*

[cols="1,2",options="header"]
|===
| verb | gesture
| `store(Parcel, SeedEnvelope)` | file the sealed envelope at its coordinate (the case); never reads the payload
| `fetch(Parcel) : List<SeedEnvelope>` | open the fridge, list what is there — one opaque envelope per readable case
| `fetch(Parcel, SeedCoordinate) : Optional<SeedEnvelope>` | peek ONE case OPAQUE (last-wins)
| `withdraw(Parcel, SeedCoordinate) : Optional<SeedEnvelope>` | TAKE one case out OPAQUE — gone until re-stored (the ring usage justifies this)
| `neighbours(Parcel) : List<Parcel>` | the sibling parcels under the same backend soil (the parcel's own first)
| `conserve(Parcel)` | the end-of-drain flush (default no-op; the run's own stack re-declares its live set)
|===

*`Cellar` (`seed-broker-port`, OSGi-only) — the TYPED decorator face, `<T>` + sensitivity:*

[cols="1,2",options="header"]
|===
| verb | gesture
| `<T> store(Parcel, SeedCoordinate, T, Sensitivity[, Persistence])` | encode + (SEALED) seal via `CellarCipher`, then file — the scion DECLARES the sensitivity/tier
| `<T> List<T> fetch(Parcel, Class<T>)` | the whole timeline DECODED, fail-at-end (unreadable entries skipped)
| `<T> Optional<T> fetch(Parcel, SeedCoordinate, Class<T>)` | peek ONE case DECODED (last-wins)
| `<T> Optional<T> withdraw(Parcel, SeedCoordinate, Class<T>)` | TAKE one case out DECODED
| `List<Parcel> neighbours(Parcel)` | codec-neutral, delegated verbatim to the `OpaqueCellar`
| `Optional<Trail> trailOf(Parcel, SeedCoordinate)` | the value's fil d'Ariane, read CLEAR off the envelope (no decode)
|===

`SeedEnvelope(domain, coordinate, payload, trail)` — the shell (`domain`, `coordinate`: neutral
`String`s; `trail`: the CLEAR fil d'Ariane) is what the frontier addresses BY; the `payload` (a JSON
`String`, possibly SEALED) is never read by the host. Each world uses its OWN jackson; no jackson type
crosses.

NOTE: `PulumiCellar` is a HOST object and implements ONLY `OpaqueCellar` — it never sees the generic
`<T>` (it cannot materialise a bundle type — the `LinkageError` the seam prevents). The typed decode
happens OSGi-side in `CodecCellar` (a `@Component(service = Cellar.class)` decorator holding a
`SeedCodec` + `CellarCipher`, taking the `OpaqueCellar` by `@Reference`), and the transactional
`ScenarioCellar` overlays the run's write set before the drain reaches the opaque backend. The three
usages — journal (doctor: `store`+`fetch`-list, never `withdraw`), current-state (live: `<T> fetch`),
ring (staging rotation: `fetch`→`withdraw`+`store`) — share this one primitive; only the ring needs
`withdraw` (and `HostSlotSelector`'s position truth would move FS→cellar, § seed-broker-spec —
DESIGNED, not wired, § the reconcile cycle).

[[every-scion-contributes]]
== Every scion contributes — the cellar IS the resource producer (the `ResourceManager` dissolution)

The doctor is the cellar's FIRST consumer, not its only one. The general law: *every scion contributes its
harvest to the cellar, and — on the Pulumi realisation — `store` PRODUCES the Pulumi resource.* This is where
the host's old `ResourceManager` dissolves.

[NOTE]
.The `store` is TRANSACTIONAL — the scion TAGS, the ROOT drains (2026-07-16)
====
The law below (*every scion harvests AND stores, `store` PRODUCES the resource*) holds at the API level, but
the store is now TRANSACTIONAL: a scion's `store` posts a TAG on its `ReportModel` (it does NOT touch the
durable backend), the graft folds those tags into the host trunk, and only the ROOT drains them to the
durable `OpaqueCellar` (`PulumiCellar`) at the run boundary — a single all-or-nothing flush. So "on Pulumi
`store` PRODUCES the resource" is the DRAIN's act at the root, not an immediate per-scion `up()`. The scion
is handed a UNIVERSAL `ScenarioCellar` (injected, not resolved from the registry) whose `store` tags; the
durable resolution is the root extension's, via the registry. Full design: §
link:seed-broker-spec.adoc#cellar-transactional[seed-broker-spec — cellar transactional]. The paragraphs
below describe the API contract (what a scion calls); read them with this deferral in mind.
====

*The SCION harvests AND stores — it does not return its harvest to the host.* The host lays the durable
backend into Felix at boot (`registerService(OpaqueCellar.class, …)`); a scion does NOT resolve that
opaque backend itself — it is INJECTED the UNIVERSAL transactional `ScenarioCellar` (the typed `Cellar`
view, § the store is TRANSACTIONAL above), whose `store` tags the run's write set and whose reads overlay
it on the durable fallback. When it harvests, it `store`s — the grower reaps AND puts away (the lexicon law: *the grower draws on the cellar, the
gardener merely ROUTES*). There is NO harvest field on the `RunbookEnvelope` and no host re-store: routing a
harvest back out only to call `store` from the host would be an absurd round-trip. The envelope keeps carrying
`(runbook, consultations)` — the doctor's consultations cross because the host GRAFTS them into the runbook
(narration); the harvest does not cross because its destination is the cellar, not the runbook (two
destinations, two channels — do not conflate them, the mistake the doctor's consultation channel invites).

*What the scion needs to store.* Two ambient facts of the run, both resolved from the registry: the `Cellar`
(the neutral furniture) and the `Parcel` currently being cultivated. The `Parcel` is published into Felix as an
AMBIENT fact — the twin of `RunGate` — because the run cultivates ONE parcel (the master stack) and only the
host knows its identity at the GIVEN. The `Cellar` stays NEUTRAL and addressed FROM OUTSIDE (`store(Parcel,
…)`): it must not hold "the current parcel" as state — the doctor addresses N parcels (one per patient), so a
mono-parcel or sentinel-resolving cellar would break it. The current parcel lives BESIDE the cellar (an ambient
fact), never inside it.

*The dissolution.* On the former host bootstrap, a `ResourceManager` ran `ResourceCreationPipeline` and, per
scion, built a "thin graph mirror of the result + a `dependsOn` edge" (`SystemdAdapterResource`,
`SeedImageBuildResource`, `SeedManifestSynthResource`, `ClusterReadinessResource`). That is EXACTLY what
`PulumiCellar.store` already does: an out-of-run `up()` registers a `CellarEntry` (`ComponentResource`) whose
payload rides `registerOutputs` under the coordinate slug. So there is no `ResourceManager` to re-create in the
new system — producing a resource per scion IS the scion's `Cellar.store`; the Pulumi realisation turns each
stored case into a resource.

=== Two Pulumi natures: RESOURCES (the graph) vs OUTPUTS (top-level exports)

* *Resources* — the graph nodes carrying identity + the `dependsOn` edge. Produced by `store`.
* *Outputs* — the top-level `ctx.export(name, value)` the commissioner reads. They are a PROJECTION of the
  resources (the former `OutputBuilder` merely republished the resources' URNs/summaries flat). The cellar
  already files as outputs-OF-a-resource, *bypassing* top-level `ctx.export` — the top-level is a READ FAÇADE,
  never the append-only store.

*The read façade stays HOST, carries no métier.* `ctx.export` is the twin of `Cellar.fetch`: the commissioner
re-reads the façade of the stored cases. The façade is host (like the gRPC mount — the commissioner reads it),
and holds NO decision — it lifts, it does not decide.

=== The cellar consults the RunGate — two spaces: CONSERVED (`up`) vs PRE-RESERVE (`preview`)

A harvest must not be LOST in dry-run — but preview must touch nothing conserved. The cellar reconciles this
because it is a system tool: like every tool it consults the ambient `RunGate` and ADAPTS, so the scion holds
ONE verb (`store(Parcel, harvest)`) and never chooses the mode.

[cols="1,1,1",options="header"]
|===
| gate | Pulumi gesture | space
| open (cultivating) | `stack.up()` | the CONSERVED state — the real resources, the history fold
| closed (surveying) | `stack.preview()` | the PRE-RESERVE — the plan of what WOULD be produced this run
|===

This is NOT "fabricate a fake harvest" (the lexicon's red line): `preview()` mutates nothing and invents no
green — it is the REAL tool computing the plan honestly, which IS the act of surveying (lexicon: *the gardener
plans without cultivating, nothing is touched*). So a dry-run does not lose the harvest: it lands in the
pre-reserve (the plan), rendered PENDING in the runbook via E9; a live run folds it into the conserved state.

*The pre-reserve is EPHEMERAL — the plan of THIS run, never an inter-run history.* A preview plan conserved and
re-read next run would be exactly the cache-that-can-lie the model forbids; `pulumi preview` is ephemeral by
nature (no `--save-plan`), so this holds. The RunGate decision lives IN the cellar (the `PulumiCellar` reads the
ambient gate and routes `up`/`preview`) — the twin of every other tool consulting the gate, not a new
orchestrator.

*Why the runbook alone does not carry the harvest (the trap avoided).* jGiven's `ReportModel` captures STEP
ARGUMENTS (the `@Quoted` values), NOT the `@ProvidedScenarioState`/`@ExpectedScenarioState` — so a scion's
harvest held in scenario state is NOT recoverable from the runbook. The runbook carries the narration/plan
(steps, PENDING, quoted counts), the cellar carries the data (conserved or pre-reserved). Two channels, two
destinations — never conflate "the plan is in the runbook" with "the data is in the runbook".

=== A harvest is FETCHED from the cellar, never pushed as an input (amont ≠ récolte)

Now that harvests are conserved at the cellar, a scion that needs ANOTHER scion's harvest FETCHES it from the
cellar — it is never pushed into an input/amendment. The SOIL (and any amendment) carries only the *where* / the
*policy facet* — a plot path, a boolean posture — NEVER a cultivated value (a fingerprint, a urn, a checksum).
Those are harvests; they live at the cellar and are re-read by address.

The trap this forbids (a vestige of the former host bootstrap): `ManifestSynthesisRequest` still has an
`imageState` field (carrying `imageFingerprint`, a Stage-A image harvest). In the scion world it is NOT wired
into `ManifestsRunbookInput` — the synthesis scion defaults it to `ImageState.unknown()`. It must STAY unwired:
when the synthesis genuinely needs the fingerprint, the manifests scion FETCHES the image scion's harvest from
the cellar (`Cellar.fetch`), it does not receive it amended. So incus, consulting manifests, forwards the SOIL
(the plot) — never the fingerprint. The ordering that makes this sound is the causal `dependsOn` below: the
image is cultivated and stored BEFORE the synthesis that fetches it.

=== The `dependsOn` edge is CAUSAL — the amendment graph, not the runbook position

The persisted Pulumi DAG must mirror real causality, not narration order. The edge is read from the AMENDMENT
graph (amont) AND the fetch graph: if scion incus FETCHED the image scion's harvest from the cellar (or was
amended from provisioning state that depends on it), then `incus.resource dependsOn image.resource` falls out of
that consumption. NOT from the scion declaring "I depend on systemd" (that would re-couple the scion to sibling
soils — forbidden), and NOT merely from the step's position in the runbook tree (that reads a POSITION, not a
CAUSE). The runbook nesting and the causal graph converge, but the causal graph (what a scion fetched / was
amended with) is the correct source.

=== The scion — not the façade — decides what has output value

Who knows a harvest field is worth surfacing? The SCION, never the host façade (a façade that "picks the
fingerprint" would re-take métier knowledge host-side — forbidden). The scion marks its harvest by the neutral
role it already uses: `@Scion(Role.FRUIT)` = conservable value, `@Scion(Role.SOWING)` = internal expectations.
The split files each part in its case; the host façade then MECHANICALLY lifts whatever is marked `FRUIT`,
knowing nothing of its meaning (it never names `seedImageFingerprint`). Sovereignty: *the scion decides the
value, the host executes the projection.*

*Granularity (current vs planned).* Today the marked grain is the WHOLE FRUIT part — the fruit case becomes one
output (`stack output <domain>.fruit` → the JSON blob), reusing the existing role, inventing no split
vocabulary. A FINER grain — the scion marking WHICH fields are flat top-level scalars (recovering
`seedImageFingerprint = "abc123"` as a named string) — enriches the split vocabulary (a `flat` facet or a
dedicated role) and is a PLANNED EVOLUTION, expected to land during the top-down migration when a concrete
`stack output X` flat-scalar need appears. Not deferred-and-forgotten: the migration WILL hit it.

[[host-tree-provisioning]]
== The host tree the instance mounts — publish / validate / mount (2026-07-14)

The scions conserve harvests at the cellar (above). This section is the twin question on the OTHER
matter a run produces: the FILESYSTEM TREE the incus instance mounts (the former `host/` — its
`rke2-manifests.d` / `k8s-daemonset.d` / `systemd.d`, the cloud-config, the env-overlay). It is a
DISTINCT concern from a conserved harvest — a harvest is a value in the cellar; this is bytes on the
host filesystem the instance binds. The former host (`main`) solved it with an FS slot-rotation
(replica slots synced into the live `host/`). That FS mechanism is KEPT — but with `jsync`
(pure-Java, `setDelete(true)`, no `rsync` binary), and the rotation/ring is now realised by
`HostSlotSelector` reading the cellar (§ the reconcile cycle); what the scion/cellar idiom adds is
WHERE the contract and validation live (below), not a replacement of the sync.

=== The invariants (the result, non-negotiable)

* *R1 — never lose what a live instance mounts.* A live instance binds physical host paths (the mount
  DIRECTORIES `rke2-manifests.d` / `k8s-daemonset.d` / `systemd.d` under `host/`). Those DIRECTORIES
  are never destroyed — only their CONTENT is synced. `rsync -av --delete` from the chosen replica into
  the live `host/` is exactly the tool: it lazily creates missing dirs and syncs file content, but a
  mount directory present on BOTH sides (it is in every replica) is never deleted. So the bind never
  points at a vanished inode.
* *R2 — a cache of the produced host trees,* to compare and validate evolutions/corrections.
* *R3 — a host tree IS the root that materialises the instance's assets* (and MAY later carry the
  run's narration: the runbook rendered `adoc` for the operator, `json` for the runtime).
* *R4 — at LIVE provisioning, reconcile the live `host/` with the replica produced this run* (rsync);
  at PREVIEW, produce the replica but do NOT touch `host/`.

=== The model — the three fixed places + the CONTRACT in the cellar

Three FIXED filesystem places, a pipeline, not variable modes:

  host.N.staging.d  →  host.live.d  →  host.N.drift
    (produced,        (deployed)     (drift measured at reconcile:
     carries `change`)                live ↔ host.{live.syncedFrom}.staging.d)

* *`host.N.staging.d`* — where a run MATERIALISES its replica (the synthesis writes here). A bounded
  rotation over THREE increments (0/1/2); each `host.N.staging.d` is IMMUTABLE once written (the cache,
  R2). The rotation recycles positions — a new run overwrites the oldest position with a fresh replica —
  EXCEPT the slot the live currently mirrors (`live.syncedFrom`), which is PINNED out of the rotation as
  long as the live reflects it. Pinning it guarantees the deltas' pivot TREE is always present (both
  `change` and `drift` diff against `host.{live.syncedFrom}.staging.d`, and a line-level diff needs the actual
  bytes, not just the manifest's checksum), and it is the FS face of R1 (never lose what the live
  mounts). So the effective rotation may hold fewer than 3 free slots while a pinned staging waits.
  It also CARRIES its `change` — the delta `staging.N ↔ host.{live.syncedFrom}.staging.d` (the run's INTENDED
  change vs the staging the live currently mirrors), a report rendered beside the runbook (§ the two
  deltas), computed whether the run is preview or live.
* *`host.live.d`* — the PHYSICAL directory (not a symlink), the STABLE bind-mount target of the instance.
  Singular (one mounted tree at a time). It is INTENDED as a faithful replica of the `host.N.staging.d`
  it was `rsync -av --delete`d from — but it can DRIFT: the live instance, a corruption, or a tampering
  may modify files after the rsync, and that drift is written into NO staging (stagings are immutable).
  At LIVE the chosen staging is rsynced in (content synced, mount dirs preserved — R1); at PREVIEW
  `host.live.d` is NOT touched (the RunGate closes the rsync, the twin of how it closes the cellar `up()`).
* *`host.N.drift`* — NOT a `--backup-dir` of evicted bytes (the sync uses `jsync`, which has no
  backup-dir, and the rollback never needs the evicted bytes — see below). It is the DRIFT REPORT: the
  delta `host.live.d ↔ host.{live.syncedFrom}.staging.d` (the staging the live mirrored), measured BEFORE the
  sync overwrites it — the live's out-of-band deviation, the one delta no staging captures. A bounded
  rotation of 3 (the last 3 drift reports).

*ONE manifest for the whole collection, living at the cellar.* There is a SINGLE host-manifest — the
index of the replica collection, one entry per replica present on the FS (`staging.0/1/2`, `drift.0/1/2`,
`live`), and it is CONSERVED AT THE CELLAR (a `Cellar.store`), not a file the host keeps on the side.
Two natures of entry, both referencing a `host.{SN}.staging.d` (one kind of referent everywhere — never
an invented live-identity):

  host.{SN}.staging.d  → its CONTRACT: checksums + provenance + `change` (delta vs syncedFrom)  (IMMUTABLE)
  host.live.d          → host.{SN}.staging.d it currently mirrors                          (the ONLY mutable entry)
  host.{DN}.drift    → host.{SN}.staging.d the live drifted from (the drift report)       (IMMUTABLE until DN recycled)

The collection is almost entirely IMMUTABLE — the staging and drift entries never change once written
(until their slot is recycled by the bounded rotation). The SOLE moving part is the `host.live.d` entry:
it is overwritten `→ host.{SN}.staging.d` on each live provisioning. PREVIEW-vs-PROMOTED is DEDUCED from
it (a staging is preview-only while `host.live.d` does not name it; promoted once it does — no flag, the
relation is the reality). A `host.{DN}.drift` records the staging the live had drifted from (the
`live.syncedFrom` it mirrored, against which the drift was measured) and stays frozen on it until the DN
rotation recycles the slot; so over successive provisionings `host.live.d` moves and the drift entries stay
fixed.

[NOTE]
.Superseded in part by the FRIDGE model (2026-07-15) — two axes, not one append-only store
====
The passage below describes the staging rotation as an APPEND-ONLY store with a HEAD read = a fold
last-wins. The fridge correction (§ seed-broker-spec "the cellar is a fridge") splits this into TWO axes:
the CURRENT STATE (mutable — the ring pointer + the live case, reached by `<T> fetch`/`withdraw`) and the
HISTORY (append-only — Pulumi's own revision log, the AUDIT). The ring's position truth MOVES FS→cellar:
`HostSlotSelector` will `fetch` the `host-staging` occupancy and `withdraw` the wrapped case rather than
fold an infinite timeline. The "HEAD = fold" reading below still holds as the AUDIT view; the CURRENT
state is now the mutable fridge. FS↔cellar reconciliation is DEFERRED. Read the below as the audit axis.
====

*Because the manifest lives at the cellar, the history of live promotions is FREE.* The cellar's HISTORY
axis (Pulumi's revision log) is append-only, versioned by its stack history (`fetch` walks the timeline).
Each mutation of the `host.live.d` entry is a new `Cellar.store` → a new history version → the timeline of
"which staging was live when" falls out of the cellar, no separate transition log. R2's sliding cache IS
that timeline.

*And because each staging entry carries CHECKSUMS, the cellar describes the FS in full — without ever
holding a byte of it.* The manifest is the complete, authoritative description of what each replica
must contain; the FS is merely a VERIFIABLE materialisation of it. This is the strong reading at its
limit: the cellar is the AUTHORITY over the host FS state while remaining pure storage of FACETS
(checksums + paths, never files — fetch-not-push, the twin of `IncusHarvest.soil`). What it buys, all
free: validation (§ below) is FS-vs-manifest-checksums; drift is detectable (a supposedly-immutable
staging whose bytes no longer match its checksums has been tampered with); comparing evolutions (R2) is
a checksum diff between two manifest versions in the history, never a re-read of the FS; and a lost
replica can be re-materialised from its description + the deterministic SOIL synthesis.

R2: the cache is the collection of `host.N.staging.d` (the last 3 produced) PLUS the `host.N.drift` (the
last 3 drift reports — the live-deviation history), INDEXED by the cellar's host-manifests. Comparing two
versions is a diff of conserved CHECKSUMS, not a re-read of two arbres; the no-op check (was main's
byte-for-byte replica-vs-`host/`) becomes a checksum diff.

*Who reads and writes it — two reads, two writers, all on the neutral cellar (the audit axis).* The manifest is
NOT one document mutated in place: it is ENTRIES PER REPLICA, each an append-only `Cellar.store`; the
logical manifest is the FOLD of the parcel's timeline at read. Two writers, never in conflict (append):

* each *SCION* PUBLISHES its own staging entry — `store(parcel, {host.{SN}.staging.d, checksums,
  provenance})` — it knows only its own morceau (an availability).
* the *HOST at grow* PROMOTES — and ONLY it, because promoting is `rsync staging → host.live.d`: BEFORE
  the sync it measures the drift (`host.live.d ↔ host.{live.syncedFrom}.staging.d`) into `host.{DN}.drift`, then
  once the sync SUCCEEDS it appends ONE promotion envelope carrying both linked mutations `{host.live.d →
  SN, host.{DN}.drift → the prior syncedFrom}` (the switch is a single atomic fact). Stored only
  post-sync-success, so the manifest never lies about the FS.

Two reads, both derived from `fetch` (the whole timeline) — no new port verb, the cellar stays neutral
at three verbs:

* the *HEAD* (current state: where `host.live.d` points, which stagings exist) — a FOLD of the timeline,
  last-wins per key. The host (to promote) and incus (to validate) read the head. It is a convenience
  fold on the reader side (the doctor already folds its timeline the same way), NOT a new contract.
* the *TIMELINE* (all versions) — `fetch` verbatim, for R2 (comparing evolutions, the live-promotion
  history — free from the append-only store, § above).

*What is new vs `main` (the FS mechanism is NOT).* The `--delete` sync into a physical `host.live.d`, the
staging rotation — kept from `main`. What CHANGES: the sync is `jsync` (pure-Java, no `rsync` binary),
and `main`'s `gc` (a `--backup-dir` of evicted bytes) becomes `host.N.drift`, a DRIFT REPORT (no bytes —
the rollback re-syncs the immutable staging, never the evicted bytes). What the scion/cellar idiom ADDS:
the CONTRACT moves to the cellar as host-manifests (not `main`'s slot ConfigMap), PUBLISHED by each scion,
VALIDATED by the incus prep before the rsync. The ownership of the contract and the validation is the new
idiom.

*A slot's IDENTITY is its POSITION* (`host.N.staging.d`), NOT its content hash — so there is no "no-op for
free by the name"; the no-op check stays an explicit checksum diff. The content hash lives INSIDE the
host-manifest (a comparison discriminant, correspondence hash→slot possible) but is NOT a key: the same
hash may map to SEVERAL slots (identical content re-materialised across the rotation), so the hash
discriminates, the position identifies.

=== Publish (each scion) vs VALIDATE (incus prep) vs mount (host grow)

The three roles do not overlap:

* *Each scion PUBLISHES what it makes available* — it materialises its own content under the SOIL and
  stores its host-manifest (pointer + checksums) at the cellar. It publishes an availability; it
  validates nothing beyond its own morceau (it only knows its own). Concretely the manifests scion
  (the sole scion that materialises an FS tree — the instance mounts chiefly the synthesis tree)
  checksums its staging replica with `HostTreeChecksummer` (relpath → SHA-256) and stores a
  `HostStagingEntry` (`@SeedContract("host-staging")`: the staging root, the checksums, the
  provenance) under the current parcel, keyed by `IncusCoordinate.HOST_STAGING` (the typed store —
  no magic string). It is one of THREE natures of the host-manifest family, all in `incus-contract`
  (the host tree belongs to incus, § the I6 correction): `HostStagingEntry` (published by the scion),
  `HostLiveEntry` (`IncusCoordinate.HOST_LIVE` — which staging the live mirrors, the sole mutable
  entry, written at the grow), and `HostDriftEntry` (`IncusCoordinate.HOST_DRIFT` — the drift report
  written at the grow). The reader-side fold of the three is `HostTreeHead`.
* *The incus PREP VALIDATES the content made available to the instance.* incus is already the prep
  (it consults manifests, assembles what the instance mounts) — validating that content is the natural
  conclusion of preparing, and only incus sees the WHOLE of what the instance will mount, so only it
  can validate global coherence. It fetches the published host-manifests and confronts the replica slot
  against the published checksums. A mismatch (corruption, partial write, an interrupted run) is caught
  BEFORE the rsync into `host/`, not discovered inside the instance — it becomes a symptom on incus's
  already-wired doctor channel (the `IMAGE_BUILD_FAILED` twin — a `CONTENT_MISMATCH` kind), fork B.
+
NOTE: *the re-check is DEFERRED — it earns nothing WITHIN a run.* In the same run, manifests just
synthesised the tree AND checksummed it (the publish step above); re-verifying those same checksums
in incus's prep immediately after proves nothing — nothing can have drifted between synthesis and
validation in one run. The check EARNS its keep only ACROSS runs: reading a staging produced by an
EARLIER run, or reconciling `host.live.d`, where corruption/tampering could have happened since. So the
publish (the checksums at the cellar) SHIPS now; the incus-side re-check is built when a cross-run
read actually consumes it. This also keeps incus decoupled from manifests (no `manifests-core`/algo
dependency) until the need is real — the FS access + `HostStagingEntry` decode are wired only then.
* *The host GROW reconciles then mounts already-validated content* (Shape C, `com.pulumi`): it fetches,
  MEASURES the drift (`host.live.d ↔ host.{live.syncedFrom}.staging.d` → `host.{DN}.drift`) so nothing is
  overwritten blind,
  then `jsync` (`setDelete(true)`) syncs the validated slot into the physical `host/` (mount dirs
  preserved — R1), and binds `host/` into the instance. It does NOT re-validate — re-validating
  host-side would duplicate metier logic outside the OSGi world (forbidden ownership leak); it trusts
  the prep.

*Filesystem access is not an obstacle (settled):* the incus scion runs in the SAME place as the host,
over the same FS — reading/checksumming `host.N` from the scion is free. `BootstrapPaths` already
offers place-dependent VIEWS (host / node) and new views can be added, so resolving `host.N` is a view,
not new plumbing.

[[the-grow-anatomy]]

The grow was `IncusResourceBootstrap.apply(ControlplanePolicy)` (3789 lines, deleted at `342b7c327`),

==== The scion-projects / host-actualises rule + `InstanceGrowPlan` (2026-07-17)

The GROW runs HOST-FLAT (the `ClusterSeedScenario` and its WHENs run on the launcher's flat classpath,
outside Felix; only the sowed scions run in-container). So the GROW cannot read an OSGi-only

provider invokes). The host derives NOTHING of the domain — it actualises a description.

*The channel — `InstanceGrowPlan`, one immutable record, one fetch, one consumer.* The GROW is the SOLE

fail-fast `ReadinessOverrides`, `COLD` keeps the patient config-derived one), but the transient bus

=== Live vs preview

There is NO separate preview directory: a preview run materialises `host.N.staging.d` (the SAME place a
live run does) and its host-manifest, but the gate does NOT fire the rsync into `host.live.d` — so
`live.syncedFrom` never comes to name this staging, and PREVIEW-vs-PROMOTED is exactly that deduced
distinction (§ the model). `host.live.d` is left untouched (the live instance is unaffected). This is the
same RunGate axis as the cellar's `up`/`preview` (§ *the cellar consults the RunGate*), realised on the
host tree instead of the cellar store — one axis, two realisations: the gate closes the rsync exactly
as it closes the cellar `up()`. A preview is thus TRACEABLE from the cellar (a produced staging its
host-manifest records, that live never adopted), with no mode-directory polluting the FS.

=== The two deltas (java-diff-utils OBSERVES) + the sync (jsync ACTS) — I6

The reconcile is TWO gestures with distinct roles: OBSERVE (compute the deltas, decide) then ACT (sync).
Both pivot on `host.{live.syncedFrom}.staging.d` — the staging the live CURRENTLY MIRRORS, read from the
`host.live.d` manifest entry — which is the common reference. It is NOT the arithmetic `N-1` (the previous
slot): previews materialise a staging without promoting (§ Live vs preview), so a preview staging can sit
at `N-1` while the live still mirrors an earlier promoted one. Comparing against the arithmetic
predecessor would diff against a tree that never touched the live — a false report. `live.syncedFrom` is
already materialised in the cellar (no recompute), and deterministic under interleaved previews:

* *`change` = `staging.N ↔ host.{live.syncedFrom}.staging.d`* — the run's INTENDED change (what THIS run decides
  to change vs what is live). Computed ALWAYS (preview AND live), because both stagings are immutable
  materialisations that exist regardless of the gate. In preview it IS the value report: "here is what
  this run would change." It travels inside `host.N.staging.d` (beside the runbook, I5), a facet of the
  staging entry.
* *`drift` = `host.live.d ↔ host.{live.syncedFrom}.staging.d`* — the live's out-of-band DEVIATION (what the live
  instance / corruption / tampering modified since the last sync). Computed LIVE ONLY, before the sync —
  in preview `host.live.d` is not touched, so there is nothing to reconcile and no drift to measure. It is
  `host.N.drift`.

Pivoting BOTH on `live.syncedFrom` is what keeps them PURE: the live was synced FROM that staging, so
`live ↔ syncedFrom` is drift alone; N and `syncedFrom` are two immutable stagings, so `N ↔ syncedFrom` is
intended change alone. Comparing the live to N (the new staging) instead would BLEND the two.

*Why compute `drift` at all — the live can drift, and a blind `--delete` would erase it unseen.* The
drift is the one delta NO staging captures (stagings are immutable; the live's deviation is written
nowhere else). Measuring it BEFORE the sync lets the grow decide (preserve / report / alert) rather
than overwrite blind. We do NOT restore the drift (it is an anomaly, not a desired state); the rollback
"go back" is simply re-syncing a still-present immutable staging (any slot in the rotation) — never
applying an inverse patch, never the evicted bytes. That is why `host.N.drift` is a REPORT, not a
`--backup-dir` of bytes.

*The tooling — two bricks, matched to the two roles:*

* *OBSERVE — `java-diff-utils` (`io.github.java-diff-utils:java-diff-utils:4.17`).* A pure-Java tree
  walk (`Files.walk` → `Map<relPath, {size, mtime, hash}>`) yields the per-file status
  `ADDED / REMOVED / MODIFIED`; for a MODIFIED TEXT file (the `host/` tree is chiefly generated
  YAML/JSON/adoc) java-diff-utils produces the line-level unified diff. The tree walk pairs + statuses;
  java-diff-utils only diffs INSIDE a text file. Dogfooding: each delta IS a `ReportModel`, rendered
  `json` (runtime) + `adoc` (operator), exactly like the runbook (`RunbookRenderer`, I5).
* *ACT — `jsync` (`com.fizzed:jsync-engine:1.5.0`, Apache-2.0, JDK 8→25).* After the deltas are computed
  and (live) the gate is open, `jsync` with `setDelete(true)` / `setForce(true)` syncs
  `host.N.staging.d → host.live.d`. Diff-based, so R1 holds naturally: a mount directory present on both
  sides is never destroyed, only its content is synced (to be VERIFIED by a test before trusting live
  mounts). No `rsync` binary on the host; testable/mockable (the instance-passing discipline).

*Packaging — CORRECTED 2026-07-15 (the reconcile is a SCION, not host-side).* The earlier note said the
GROW/reconcile runs host-side, so both libs were plain host Maven deps. That was WRONG: the reconcile is
an INCUS SCION (played in-container), and its promoter lives in `incus-core` (a `type=model` bundle) —
the host tree is incus's, and putting the promoter host-side would re-open the realm leak §1-§3 closed.
*Survey/cultivate (2026-07-19):* the promoter is now a CONTRACT (`HostTreePromoter` in `incus-contract`,
returning a home `Promotion`) realised by a mode-pure PAIR in incus-core — `CultivatingHostTreePromoter`
(observes drift + syncs) and `SurveyingHostTreePromoter` (touches nothing, reports `notPromoted()`) —
tagged `rke2lab.gardening=cultivating|surveying`, the frontier picks one. The jsync ACT is factored into
`HostTreeSync` (a reusable core helper both would-be callers share, no duplication). So the tooling is
IN-CONTAINER: `java-diff-utils` carries a BSN
(`io.github.java-diff-utils`), a first-class bundle incus-core imports normally; `jsync-engine` +
`jsync-vfs` (1.5.0) ship WITHOUT a BSN (nu manifests), so a bundle cannot import them — they are EMBEDDED
in incus-core's `Bundle-ClassPath` (`-includeresource: jsync-*.jar;lib:=true`, the manifests-cdk8s
pattern), their packages NOT imported. One consumer (incus-core) → Bundle-ClassPath embed, NOT a `*-wrap`
module (the settled rule: wrap only at the third genuine reuse). The victools/BSN closure trap DOES apply
here (in-container) — the embed avoids it (the jars are internal to the bundle, never a resolution edge).

*The reconcile scenario — the cycle: fetch the cellar, decide on checksums, commit only if promoted.*
The reconcile is a DISTINCT incus scion (the planned `IncusScenario.RECONCILE` soil), not a beat of `prepare` — prepare
answers "is the material ready?" (image + manifests), reconcile answers "must the live flip, and onto
what?". Its GIVEN FETCHES the cellar and folds `HostTreeHead` → the `pivot` (`liveSyncedFrom`) and the
`source` (the staging to promote, determined FROM the folded entries, never guessed). Prepare must have
published a `HostStagingEntry(stagingRoot, checksums)` for the source to exist — that publish is
prepare's own new Then (`HostTreeChecksummer.checksum(staging)` → `cellar.store`). The WHEN decides on
ONE comparison — `change = diff(pivot, source)` (checksum maps, no FS touch to decide): empty → NO-OP
(`Promotion.notPromoted()`); else → `promoter.promote(source, live, pivot, driftBase)`, MODE-BLIND. The
scion injects no `RunGate`: the frontier hands it the cultivating impl (drift-observe + sync) or the
surveying impl (touches nothing) and every step renders PENDING via E9 under a survey. The drift
(`live ↔ pivot`) is OBSERVED and reported inside the cultivating impl, NEVER a decision gate — if the
source changed we promote (the staging is authoritative, the drift is overwritten); the report is its
only role. The THEN commits `HostLiveEntry(syncedFrom=source)` to the cellar ONLY when the returned
`Promotion.promoted()` is true — the cellar is the committed truth, written once when the flip is
actually done; the PROMOTED tag follows the same `promoted()` fact, so the mode never leaks into the
scion. The jsync ACT is `HostTreeSync`: no no-op-detect (the WHEN already decided by checksums), it only
syncs — `jsync.setDelete(true).addIgnore(".flox").sync(source, live, MERGE)`, skip-flox native here.
Ordering: the reconcile's sow-and-graft WHEN sits in `ClusterSeedScenario` BEFORE the grow (the live must
be current before the VM mounts it).

*How the `source` is VISIBLE — the in-flight write-set descends (2026-07-16).* The `source` is the staging
the PROVISION crossing published EARLIER in the same run — an IN-FLIGHT store, not yet drained (the root
drains at its own boundary, AFTER reconcile). Reconcile plays in its own fresh `ReportModel`, so without
help its overlay would see only the durable backend (last run's stagings), never this run's fresh one. The
transaction's ALLER sense closes it: the root hands the accumulated write-set DOWN the sow (the twin of the
`txId`, § link:seed-broker-spec.adoc#the-cellar-is-transactional[seed-broker-spec, write-set descends]), the
extension posts it as `Entry(inherited=true)` on reconcile's model, and `fetch(HostStagingEntry)` overlays
it — so reconcile reads the just-published staging as its `source`. The `pivot` (`liveSyncedFrom`) is a
PRIOR-run committed fact, so it resolves from the durable fallback; only the `source` needs the in-flight
overlay. The inherited entries are STRIPPED before reconcile's graft, so they do not fold up a second time
(they are already in the trunk from the provision crossing).

*`HostSlotSelector` reads the cellar, not the FS (2026-07-16).* The slot rotation's occupancy no longer
comes from `Files.list(nodeRoot)`; the selector `fetch`es the `host-staging` entries (the occupancy) and the
`host-live` entry (the pinned `liveSyncedFrom` pivot) from the cellar it is handed, and the same overlay
makes this run's fresh staging visible. incus-core already depends on `seed-broker-port` + `-codec` (via
`HostTreeHead`), so this adds no new dependency category; the selector is tested against a mock cellar (the
scions' existing gesture). BOTH callers migrate together — provision and reconcile — no transitional
FS-reading variant (uniformity). The position/wrap/pin arithmetic is unchanged; only the occupancy source
moves.

*Rejected (why not):* Apache VFS is a file-ACCESS layer, not a reconciler (one would rewrite the whole
diff/delete over it); Ant `SyncTask` does delete + `<preserveintarget>` but drags Ant as a runtime dep
and wants `Project`/`Task` piloting — heavy inside a jGiven `Stage`; a reversible binary patch (jbsdiff)
is moot — rollback is a re-sync of the immutable staging, and the reconcile is LOCAL (no bytes-on-the-wire

*First run (no `live.syncedFrom` yet):* `change` is all-ADDED (vs the empty tree), and there is no

=== CORRECTION (2026-07-14): the host-tree belongs to INCUS, and its CRUD is OSGi-side — NOT host-flat

The publish/validate/mount split above (and the "two reads, two writers" § earlier) said the HOST at
grow reads the head and writes `HostLiveEntry`/`HostDriftEntry`, with `HostTreeHead` folding the
timeline *host-side*. Playing the first preview PROVED that wrong: `HostTreeHead` lived flat in
`seed-outcluster` and decoded `HostStagingEntry`/`HostLiveEntry`/`HostDriftEntry` — types in
`manifests-contract`, a `type=contract` bundle (staged, NOT flat). A flat class touching a bundle-only
contract type is a REALM leak; at runtime it is a `NoClassDefFoundError`. It is the SAME anti-pattern
as the former host-flat `EntryGatePolicyEnforcer → ManifestUpdateGate` leak (since removed) — host-flat
code reading a domain's typed contract.

*Who OWNS the host tree — incus, not manifests.* The first reflex was to give the host-tree CRUD to
manifests (that is where `Host*Entry` sat). WRONG. The HOST TREE (`host.N.staging.d` entire —
`rke2-manifests.d` + `k8s-daemonset.d` + `systemd.d` + cloud-config + env-overlay …) is what the INCUS
INSTANCE MOUNTS. incus owns the mount, picks the rotation slot, triggers the grow, measures the drift
of the WHOLE tree; `rke2-manifests.d` is just ONE folder among many — manifests CONTRIBUTES content,
it does not own the tree. This is the same reasoning already stated on the validate side ("only incus
sees the WHOLE of what the instance will mount, so only it can validate global coherence"): the tree's
CRUD/fold/rotation/drift is incus's, exactly as its validation is.

*The correction (the CRUD moves OSGi-side, into incus).* The whole host-entry CRUD — publish the
staging entry, fold the timeline into the head, choose the rotation slot (`HostSlotSelector`), compute
the two deltas (`HostTreeDiffer`), promote (live + drift) — runs INSIDE the OSGi world, in incus, never
host-flat. incus already runs over the same FS as the host, so reading/checksumming `host.N` from the
scion is free (§ *Filesystem access is not an obstacle*). The logic lives in a new `incus-core`
(`type=model`, uniform with the six other domains' `-core`); the `Host*Entry` records move to
`incus-contract` (host-tree vocabulary is incus's) — leaving `manifests-contract` to the synthesis
vocabulary alone, and no host-flat reader to leak.

*The flow INVERTS — incus chooses the slot, then hands the SOIL.* Before, the host-flat GIVEN chose the
slot (`HostSlotSelector(nodeRoot)`) then handed `manifestsRoot` to incus. After, INCUS chooses the slot
(it owns the tree), creates `host.N.staging.d`, then hands the subfolder `rke2-manifests.d` as the SOIL
to manifests. The host only passes `nodeRoot` to incus.

*INCUS publishes ALL the host-entries — manifests never touches the cellar host-tree.* manifests
produces only ONE folder, so it cannot publish `HostStagingEntry` (a whole-tree contract); it only
materialises content into the SOIL. incus publishes — after grafting, when the tree is complete. And
the tree IS complete at the graft: `DefaultManifestSynthesisService` writes the WHOLE tree under one

*The ordering — promotion BEFORE the instance grows.* "grow" conflated two gestures: the host-tree grow

host-entries are published in the incus `prepare` scenario, upstream of the instance grow:
`HostStagingEntry` right after the graft, then `HostDriftEntry` + `HostLiveEntry` at the promotion; the
instance grow (`com.pulumi`) is the SEPARATE, LATER gesture that mounts an already-current `host.live.d`.

CRUD over the host tree incus owns. incus carries DEDICATED scenarios (routed via the `IncusScenario`
enum + `IncusRunbookHandler` on the shared `ScenarioPlayer`, a domain hosts N scenarios like doctor): a `prepare` scenario grafts → publishes `HostStagingEntry` → folds →
promotes (the twin structure of `IncusProvisionScenario`'s graft → harvest → store today). `prepare` and
the instance grow stay DISTINCT — `prepare` will gain its own steps (cross-run validation, multi-scion

==== BootstrapPaths — the WHOLE topology is computed OSGi-side (the realm criterion, not the resource one)

The inversion ("incus chooses the slot, then hands the SOIL") forces a decision on `BootstrapPaths`
(the 17-root provisioning topology, `seed-outcluster`). An earlier draft split it BY ROLE (layout → incus,
host-view stays), on the belief that `fromLocalWorktree` (the DARWIN-local view, where the Mac writes)
and `pathOn` (the NFS DARWIN→NIXOS translation) were host-IRREDUCIBLE. *That belief used the wrong
criterion.* The host↔OSGi boundary is a CLASSLOADER REALM (which TYPES you may name), NOT a resource
boundary: Felix is embedded IN the host JVM (on the Mac), so the incus scion sees the SAME filesystem
and system resources through the same `java.nio.file` API (the spec already says as much — § *Filesystem
access is not an obstacle*). Nothing about touching the Mac FS, resolving the local view, or applying
the NFS prefix is beyond the scion.

*So the whole topology is computed OSGi-side, uniformly — it reads better than a host/scion split.*
`incus-core` holds `HostPathCatalog` (the container targets), `fromLocalWorktree` (the DARWIN-local
view), `HostSlotSelector` + `asStagingView` (the slot), AND `pathOn` **extracted as a pure function**
(the NFS `/net/` · `/private/` · `netPrefix` translation, formerly a `BootstrapConfig` method). From
these the scion produces the three PREPARE outputs in-container:

. the staging slot — `HostSlotSelector(nodeRoot).nextStaging()`, `nodeRoot` = `.local.d/<cluster>/<node>`;
. the SOIL `rke2-manifests.d` — the slot + the `MANIFESTS` catalog name, handed to manifests by coordinate;
. the mount plan — `{name, source (NIXOS-translated via the pure `pathOn`), target (`HostPathCatalog.path()`)}`
  per mount, the crossing SOIL (§ seed-broker-spec, the two natures of a SOIL).

*The host keeps only TWO gestures.* (a) the Pulumi engine (`com.pulumi.incus`, the sole host-irreducible
— the control flow cannot enter Felix, shape B); (b) extracting a HANDFUL of FLAT SCALARS from
`BootstrapConfig` — `worktreeRoot`, `clusterName`, `nodeName`, `automount` (netPrefix derives from
cluster) — and handing them to the scion by `@Amendment`. `BootstrapConfig` itself NEVER crosses
(consistent with "the flat host fills it from BootstrapConfig", the SystemdProbeRequest pattern). The
host reads the resolved mount plan back (flat, via Split) to build the `InstanceDeviceArgs`.

*The SOIL crosses by COORDINATE, never a typed field.* `IncusProvisionScenario.the_manifests_are_cultivated`
already sows `broker.sow(new AmendCoordinate("manifests"), …)` (the reflector maps the SOIL role onto
`ManifestsRunbookInput.materializationRoot`) then `broker.sow(new RunbookCoordinate("manifests"), …)`. So
the computed `rke2-manifests.d` is handed through that SAME amend-by-coordinate — neutral JSON, ZERO
added typed cross-domain dependency. That is what keeps the boundary clean.

*The automount translation, and WHY it survives.* `BootstrapPaths.asAutomountView(automount, netPrefix)`
(the pure `automountPath` helper, ex-`BootstrapConfig.pathOn`, extracted into incus-core 2026-07-15)
rewrites a DARWIN path into its automount NIXOS view (`/private/x` → `/net/<cluster>.local/private/x`)
because provisioning is BI-MACHINE: the Mac WRITES the assets (Felix runs there), the remote NIXOS host
MOUNTS them over NFS to grow the instance. It is dormant in the feature branch (its only caller,
`seedInstanceDevices`, was deleted with the grow) but NOT dead — it returns with the mount plan. As a
pure method on the record (fed `automount` + `netPrefix`) the scion applies it without naming
`BootstrapConfig`, which never crosses.

*The true consumer of the 17 roots is the GROW, not the two phantom reads.* Today's scenario reads only
`clusterNodeRoot()` (feed the slot) and `manifestsRoot()` (the SOIL) — vestiges. The real client is
`seedInstanceDevices` (the deleted grow body, `342b7c327`): it pairs EACH host-view root
(`hostPaths.systemdRoot()`, …) with a `HostPathCatalog.path()` (the container mount). The cut is drawn
against that grow returning (I6e). But the grow no longer needs the host to hold BOTH halves: the scion
computes both (target from the catalog, source from the pure `pathOn`) and hands the resolved
`{source, target}` pairs across flat. The host names neither the roots nor the catalog — it reads the
mount plan and builds `InstanceDeviceArgs`. The vestigial reads dissolve with the inversion.

=== The runbook `json` has a RUNTIME role INSIDE the node (not only operator narration)

R3 says a replica slot MAY carry the run's narration; the `json` rendering is more than a consultable
artefact — it earns a runtime job in the node. Because a live instance is never restarted when the
mounted content changes (R1: we rsync fresh content into `host/`, we do not reboot), a content change
must be reconciled by REFRESHING the affected services in the node (a targeted reload/restart), not a
reboot. The runbook `json` is what tells WHICH: it carries the mapping *changed content → services
to refresh*. It pairs exactly with the content validation: the incus prep validates THAT the content
is conform; the runbook `json` says WHAT to do when it changed — and the files it names are exactly the
`change` delta (`staging.N ↔ host.{live.syncedFrom}.staging.d`, § the two deltas), which the runbook maps to the services to
reload. So the `json` lives in `host.live.d` for the node's own refresh logic, while the `adoc` is the
operator's read. WHERE it is rendered (CORRECTED 2026-07-15): NOT inside a staging slot, and NOT
promoted. The runbook is rendered from the COMPLETE played `ReportModel`, which only exists AFTER the
whole scenario (all WHENs) has run — i.e. AFTER the promotion, which is a mid-scenario beat of the
incus scion. So it cannot travel through the promotion. The host writes it into `host.live.d`
DIRECTLY, post-run — a LIVE mutation, the twin of the instance mutating its own mounted content at
runtime. At the next rotation the `drift` delta (`host.live.d ↔ the staging it was synced from`) sees
the runbook as drift versus the static staging tree — expected, not an anomaly. The live root is a
fixed path off the worktree scalars the host already holds (`BootstrapPaths.liveRoot()`), so the host
need not learn back the slot the scion chose. (Concrete shape — the change→service map, who consumes it in the node — is downstream
work.)

*Dogfooding — ONE model, two renderings.* Both artefacts ARE the run's jGiven `ReportModel`: the
`adoc` is `AsciiDocReportGenerator` over the model (the operator narration); the `json` is
`ScenarioJsonWriter(model)` — the model's raw serialisation, the SAME format the scions already cross
the realm boundary with today, round-tripped by `ScenarioJsonReader`. The `json` runbook is therefore
NOT a bespoke artefact — it is the `ReportModel` itself, so the node reads it with machinery we
already have. This is the dogfooding: the jGiven model serves as narration AND as runtime artifact.

*The hard consequence.* A `ReportModel` captures only the `@Quoted` STEP ARGUMENTS (+ step names and
statuses), NOT `@ProvidedScenarioState`/`@ExpectedScenarioState` (§ the two channels — the runbook is
narration, the cellar is data). So for the node to read WHAT to refresh out of the `json`, that fact
must be NARRATED — exposed as a `@Quoted` step argument, not held in scenario state. A scion touching
content must SAY so in its step (e.g. "… refreshing `foo.service`"), so the affected service survives
into the serialised model. Healthy pressure: it forces the narration to be complete rather than
letting load-bearing facts hide in unrendered state.

== Open questions (2 of 4 resolved 2026-07-12; #2 + #3 remain)

. *`Parcel` arity — RESOLVED (2026-07-12): keep `Parcel(project, stack)` as shipped.* Since the Cellar
  is the Pulumi-backend frontier (§ <<the-model>> claim #1), `Parcel` IS a Pulumi stack reference; the
  `org` in the figure text is the Pulumi org — a host/doctor-side constant applied when projecting, not
  a field the neutral seam forces the host to invent. The figure text was loose; the shipped
  `(project, stack)` record stands.

. *What coordinate does `fetch` stamp? — RESOLVED (2026-07-12): NONE. Collect-all-neutral, capability
  as a service.* The guiding principle (the user's): the cellar is the LEAST-capable realisation — the
  host knows nothing of the doctor. So we do not ask it to be clever. If the OSGi side can already
  RENDER a service (interpret, assemble), it OFFERS it; it is up to the cellar to CONSUME that service or
  not, per what it can do. This is REST/HATEOAS turned toward storage: the neutral store returns
  everything neutral, and the interpretation CAPABILITY is a service the domain offers, never a
  requirement on the store. Concretely: `fetch(parcel)` returns `{version, when, + every present output
  by its NEUTRAL name}` (the `Role.*` cases) — NO doctor coordinate stamped, no doctor type. The OSGi
  reader — which asked for THIS parcel — knows what to assemble. The "which coordinate / which assembly"
  lives entirely on the capable side.
+
*The neutral shelf is Pulumi's NATIVE addressing, not an invented label (realisation detail).* The
cellar need not mint any coordinate: the Pulumi checkpoint already carries each resource's native
identity — the `type` token (e.g. `rke2lab:controlplane:SystemdAdapter`), the `urn`, the logical name —
alongside its `outputs` (see `StackSnapshot`, iterating `deployment.resources[]`). That native identity
IS the neutral shelf: the cellar addresses by what the SOIL already gives it, no doctor word. A different
furniture (a git store) would have its own native discriminant (path, blob sha) — the principle is the
same, the medium differs. So `fetch` hands back resources addressed by their Pulumi-native meta + neutral
outputs; the capable OSGi side filters/assembles by what it asked for.

. *`store` for the medical-record parcel vs the ledger parcel.* Today only the ledger is written
  (`append`); the medical record is written elsewhere (`SystemdAdapterResource` nests
  `FIELD_CONSULTATION_REPORT`/`FIELD_EXPECTATIONS` — the leak). The Cellar's `store` must become the
  ONE write path, keyed by coordinate slug. Whether `SystemdAdapterResource`'s write folds into
  `Cellar.store` now or in the domain-migration step is a scope call for the plan.

. *How the host registers the Cellar into Felix — RESOLVED (2026-07-12): `registerService(Cellar.class,
  hostImpl)`, NOT via the broker.* Confirmed against `DefaultSeedBroker` + seed-broker-spec
  § `edge-reaches-osgi`. The host publishes the Cellar ACTIVELY into Felix, but the target is the bare
  service registry, not the `SeedBroker`. Two load-bearing facts:
  ** *The broker never sees the Cellar, and must not.* `DefaultSeedBroker` collects ONLY `SeedHandler`s
     (growers projecting a metier onto the neutral) by constructor `@Reference(MULTIPLE)`. The host is
     outside Felix, cannot be a DS component, so contributes no handler. The Cellar is not a grower — it
     is a COLLABORATOR a handler's dependency (`MedicalRecordRegistry`) `@References`, two hops below the
     broker: `SeedBroker → SeedHandler → MedicalRecordRegistry → @Reference Cellar`.
  ** *The reference is STATIC + mandatory, so boot ORDER is the whole difficulty.* The host holds the
     single global start-level cursor (`StartLevelLever`, levels per role from `BootPlanner`), registers
     the Cellar while consumer bundles sit ABOVE the cursor, THEN raises it — the reference binds
     directly, no `greedy`/`dynamic`/`OPTIONAL`. A doctor with no cellar is a wiring bug that must fail
     loud.
  +
  This is STEP 2 territory (boot wiring), not the impl itself — sequenced by the plan, but the mechanism
  is now settled.
