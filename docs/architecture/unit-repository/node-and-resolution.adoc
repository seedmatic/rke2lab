= unitrepo — node & resolution
:toc: left
:toclevels: 2
# :kroki-server-url: https://kroki.io
:kroki-fetch-diagram:

NOTE: This is a *design* document folded into rke2lab. It describes the
full node-and-resolution model as a self-sufficient federated peer. Only a
slice is *shipped* today (the OSGi resolution model, run as an injected
service inside the booted Felix framework); the federation machinery (node
actor, peer discovery, closure puller, re-wire/prune, reflog, anchors,
serve-own-DAG, and the live re-resolution loop) remains design. Each section
below marks SHIPPED vs DESIGN where the distinction matters.

What a unit-node *does*. A unit-node is self-sufficient on its own
content-addressed store, resolves its requirements against reachable peers,
pulls the closure (and becomes an owner), and serves only what it holds. This
document holds the container view, the federation component view, and the live
re-resolution loop that is the system's heartbeat.

== Container view (C4 L2)

Six containers. The kernel is the only thing that is NOT a unit; everything
above it is loaded from the store.

In rke2lab the *kernel level-0* maps onto the host/exec *actualiser* — the boot
seam (`SeedRuntime`) that boots an embedded Felix inside seed-outcluster's
`Pulumi.run` callback. That actualiser is the level-0 that is not itself a unit:
it mounts the store-equivalent (the local `ManifestsDomainRegistry`), starts the
framework, and lets everything above it run as bundles. The bridge is explicit:
the design's "kernel that boots OSGi and is not a unit" *is* rke2lab's host-side
boot seam.

The **kernel boundary is non-deferrable**: because running modules are
resolved/loaded from the store at runtime, there must be a tiny level-0 kernel
(here, the host boot seam that mounts the store and boots Felix) that is *not*
itself a unit. Everything above the kernel is a unit. SHIPPED: the framework
genuinely boots in production (R4 boot seam, proven by `pulumi preview`).

DESIGN. Every box traces to a resolved fork. The serve endpoint serves only this
node's own DAG — no proxying.

The resolution **model** is reused from the OSGi generic
capability/requirement stack: the generic model (Core ch.6 Resource API),
custom namespaces (Core §3.3), the Resolver (Core ch.58, Apache Felix
Resolver), Repository XML (Compendium ch.132), and `uses:`/class-space
consistency (Core §3.7.6). The original design imagined this model running
standalone, without a running framework; in rke2lab that is now only half-true.
The framework boots in production, and the resolver runs as an
SCR-*injected* `org.osgi.service.resolver.Resolver` service *inside* that
booted framework. SHIPPED: `UnitResolver` consumes the injected `Resolver`
and resolves against a `ManifestsUniverse`. The resolver's job, reframed for the
federated design, is to **assemble the Repository view from reachable peers'
capability-manifest units, then resolve the requirement against it** — but
today the universe is built from the *local* `ManifestsDomainRegistry`, NOT
from peers yet.

The hand-rolled `dependsOn…` walker that the resolver superseded is **retired**
— it has been deleted. The resolution model is now the sole path; there is no
walker feeding resolver input.

== Resolving a coordinate — three stages across two name-spaces

Resolving "which unit, which bytes" is NOT one lookup. It crosses the two
orthogonal name-spaces (see link:jgit-transposition.adoc[the JGit transposition]):
a requirement is a NAME, the bytes are reached by a HASH. The resolver bridges
them, and an optional ref layer sits between for human version control.

[mermaid]
....
flowchart LR
  need["a need — Require type=doctor version>=2.0<br/>schema-name, logical, a RANGE"]
  resolver["UnitResolver<br/>which unit provides it"]
  ref["optional ref — tag, branch<br/>name maps to a root hash, git-native"]
  hash["a root hash<br/>content-hash, exact, immutable"]
  subtree["subtree reachability<br/>walk the closure, serve the bytes"]
  bytes["the unit closure — data plus code"]
  need -->|stage 1 logical| resolver
  resolver -->|stage 2 pin| ref
  ref -->|stage 3 reach| hash
  hash --> subtree
  subtree --> bytes
  classDef ship fill:#dfd,stroke:#2a2,stroke-width:2px;
  classDef des fill:#ffd,stroke:#aa2,stroke-width:1px,stroke-dasharray:4 3;
  class need,resolver ship;
  class ref,hash,subtree,bytes des;
....

The three stages, each in its name-space:

* *Stage 1 — logical, schema-name (SHIPPED).* The coordinate is a NAME plus a
  version RANGE, e.g. `Require unitrepo.type=doctor; version>=2.0`. The
  `UnitResolver` decides which unit satisfies it. This half — the hard half git
  has no equivalent for — is what is already in production. The range expresses
  *policy* (what is acceptable), not a fixed pick.
* *Stage 2 — ref, content-hash, OPTIONAL (DESIGN).* Among the versions stage 1
  accepts, a git-native ref (tag, branch) pins WHICH one: a mutable name that
  maps to a root hash. This is the human version-control layer — the registry
  between the loose range and the frozen hash. It refines the resolution, it
  never replaces it: resolve the range first, then a ref constrains the choice.
  Discipline: the `ContentStore` exposes refs as name-maps-to-hash, never a raw
  JGit `Ref` or `ObjectId` (it speaks hash, bytes, unit).
* *Stage 3 — hash, content-hash (DESIGN).* The result is a root hash — an exact,
  immutable coordinate covering the whole closure by Merkle. From there subtree
  reachability serves the bytes; git does this natively. A lockfile-DAG is
  exactly a frozen set of stage-3 hashes — reproducible byte-exact.

So a coordinate resolves logically first (name plus range), is optionally pinned
by a ref, and lands on a hash whose subtree yields the closure — data and the
code bundles required to consult it. Stage 1 is shipped; stages 2 and 3 ride with
the `ContentStore`.

== Live re-resolution loop — the heartbeat

DESIGN. This is the strictly larger reactive horizon. rke2lab's *shipped*
resolution is **one-shot at synthesis**: `CoherentManifestsDomainRegistry`
resolves once and the result feeds manifest synthesis. The loop below — the
continuous re-resolution and re-wiring driven by a heartbeat — is the design
target that subsumes that one-shot pass.

A unit-node's running configuration is a function of what its neighbours
currently offer. Two sources of dynamism trigger re-resolution and re-wiring:
**topology mutates** (neighbours appear/disappear) and **the application
mutates** (its own needs change as it specializes). The doctor's
recruit-a-specialist path is this same loop with a domain-specific trigger.

Ordering note (validation item): **re-wire before prune** — move to the new
coherent closure, then shed what is no longer required.

== Durability — the pull-own regime + demand-driven pruning

DESIGN. Once a unit-node resolves its requirements it **pulls and becomes an
owner** (the pull-own regime: pull = own, content-addressed, local). A provider
disappearing does **not** un-run the node — already-owned units keep running;
availability only gates *discovery of new requirements* and *updates*. A
resolved node survives partition.

Ownership is **not accretive** (a divergence from git): in resolving, a node
may replace old units with current ones and **prune its own history**,
demand-driven, at resolution time. Invariant: **once you own a resolved closure
you are always safe in THAT state**; moving to a new state is what sheds the
old.

Emergent federation property: a version exists in the federation **iff at least
one node currently requires it** — retention = the union of all nodes' live
requirement-closures, no central policy (= git GC with "reachable" = "required
by some live closure", distributed). Storage self-balances: popular docs widely
replicated, abandoned docs evaporate.

The hazard: rollback is not local. After v1.0→v2.0 + prune v1.0, reverting
needs a re-fetch, which only works if someone still requires v1.0. That lands
exactly on the doctor: a bad prescription whose revert path evaporated. Hence
retention.

== Retention — reflog + opt-in anchors

DESIGN.

. **Local reflog** — each node keeps a bounded generational tail of pruned
  units in its own store before true GC. Cheap, universal,
  federation-independent; guarantees rollback of recent moves (the doctor can
  always undo its last prescription). Pure git-reflog semantics.
. **Opt-in anchors** — anchoring is a **role** a node chooses, not a system
  tier. A node curating domain X declares a requirement on "all versions" of X;
  the emergent rule (alive-iff-required) then keeps that history alive through
  ordinary mechanics — no special retention code. Any node can anchor, several
  can anchor redundantly → **no mandatory center**. An anchor vanishing degrades
  deep-history recoverability gracefully and never un-runs anyone (the pull-own
  regime).

"Hold all history of X" is just a requirement closure that happens to be wide —
it rides the same pull=own / alive-iff-required machinery as everything else.

== Discovery + serve-own-DAG

DESIGN. Discovery splits into two symmetric layers, both derived from the
homogeneity axiom (any external index would be a special node, forbidden):

* **Layer 2 — capability index = capability-manifest units IN the DAG.** A
  node's advertisement IS a small content-addressed unit; learning what a peer
  offers = pulling its manifest; the Repository the resolver sees = the merged
  manifests of reachable peers.
* **Layer 1 — peer presence = mDNS, used symmetrically** (every node both
  publishes and browses). Presence is an interface (`PeerSource`) so gossip can
  layer on later for WAN reach without touching resolution. DHT / central
  registry are ruled out — privileged roles.

**A unit-node serves only its own DAG; it never proxies/forwards.**
Reachability is transitive through **ownership replication** (each needing node
pulls and becomes a real holder), never through relay. ⇒ discovery may be
multi-hop; **acquisition is always first-party**. The federation gets units
everywhere by replication of ownership (= git's "popular objects end up
everywhere", no node a router).
