= Dataplan as Cross-Repo Single Source of Truth
:toc: left
:toclevels: 3

== Overview

The cluster's ZFS *dataset layout* — the tree a node needs so that a cluster can
be grown on it (the ephemeral per-node datasets that back containerd + the
openebs-zfs `pvc-*` volumes, and the *persist* datasets that must outlive a
cold-start) — is defined once in rke2lab's `seed-master` and consumed identically
by *three* parties:

* *nix-darwin-home* (ndh), which materialises the datasets on the host `tank` pool
  via `disko`, *before* the cluster exists;
* rke2lab's *manifests* — the `openebs-zfs` StorageClass pool and the statically
  provisioned *persist* PV both name datasets from the layout;
* rke2lab's *node substrate* (`nixos/containerd.nix`), which mounts the per-node
  containerd dataset.

This is the storage twin of
link:netplan-blueprint-single-source.adoc[the netplan blueprint]: rke2lab is the
source of truth for a cluster-scoped fact, ndh pulls it over a flake edge and
merges it into its catalog. Where the netplan owns *addressing*, the *dataplan*
owns the *dataset layout*.

The name is deliberate. `dataplan` : `netplan` :: dataset layout : network layout.

== Why a single source is load-bearing here

Two independent forces make a hand-copied dataset tree a latent bug:

. *etcd is wiped at every cold-start.* A re-grow deletes+recreates the instance;
  node-local etcd is gone, so every PVC→PV→`ZFSVolume` binding vanishes. Dynamic
  openebs-zfs provisioning therefore *cannot* persist across grows — a fresh
  cluster mints a new random `pvc-<uid>` and the surviving dataset is re-orphaned.
  Anything that must survive (the Tailscale funnel Let's Encrypt cert, the render
  Maven cache) needs a *stable dataset handle* declared out-of-band of etcd. That
  handle is a dataplan entry.
. *The same path is named in three places.* `tank/rke2lab/persist/...` and
  `tank/rke2lab/control-nodes/<node>` appear in ndh's `disko` config, in the
  `openebs-zfs` StorageClass `poolname`, and (for persist) in the static PV's
  `volumeHandle`. A literal in each drifts silently — the exact failure mode the
  link:manifest-domain-catalog-pattern.adoc[ManifestDomainCatalog] discipline
  exists to prevent, applied to dataset paths.

== The two natures of a dataplan entry

[cols="1,3",options="header"]
|===
| Nature | Meaning

| *ephemeral*
| Wiped on grow: `tank/rke2lab/<role>/ephemeral/*`. Two owners, one parent each —
  `nodes/<node>/containerd` (created by the node) and `volumes/pvc-*` (created by
  openebs-zfs, whose `poolname` is the `volumes` parent). Reclaim is `Delete`; the
  whole subtree is wiped by ndh at instance renewal (see
  link:../nixos-substrate/concern-ownership.adoc[concern ownership]).

| *persist*
| Cross-grow, retained: `tank/rke2lab/<role>/persist/*` (the funnel cert state
  today). A *sibling* of `ephemeral` inside the cluster root — that topological
  placement *is* the exemption mechanism: `zfs destroy -r
  tank/rke2lab/<role>/ephemeral` never touches it. Reclaim is `Retain`; bound in
  the cluster by a *static* PV with a stable handle. The funnel-cert use is
  INDIRECT: the Tailscale proxy cannot mount a PVC (its ProxyClass exposes no
  volume), so a helper Job mirrors the proxy's state Secret to/from this dataset —
  persisting the funnel *identity* only (NOT etcd, which would break a clean
  cold-start). See
  link:../cluster-api/pac-in-cluster-render-spec.adoc#funnel-durability[Durable
  funnel identity].
|===

Both natures are keyed per CLUSTER, by its role — see <<per-cluster-pools,the
layout>> for the shape and for why the discriminator is the role and not the
cluster name.

== Ownership split (rke2lab vs ndh)

Mirrors the netplan split-ownership exactly — each repo owns the fact that is
*its* concern:

[cols="2,3",options="header"]
|===
| Fact | Owner

| The `tank` zpool geometry (raidz1, `rootFsOptions`) and the host `nerd/*` trees
  (root/nix/var/`persist` impermanence)
| *ndh* — physical + host concern. Note ndh's host `nerd/persist -> /persist`
  (NixOS impermanence) is distinct from the cluster `tank/rke2lab/persist`.

| The materialisation *law* — the `addDatasetOptions` / `addPostMountHook` /
  `datasetsWithHooks` helpers
| *ndh* — how any declared dataset is normalised (`canmount=noauto`, snapshot
  props, post-mount hooks).

| The cluster dataset *layout* under `tank/rke2lab/*` (ephemeral + persist)
| *rke2lab seed-master* — a cluster need, provided to ndh like the netplan.
|===

== The root rename: `rke2` -> `rke2lab`

The layout root moves from `tank/rke2/*` to `tank/rke2lab/*`. `rke2` names the
Kubernetes distro; the datasets belong to *rke2lab* (the project that owns the
layout), so the root must name the owner, not the technology — the same reasoning
that makes seed-master the SSOT. This is a greenfield rename: because etcd is
wiped and the tree is re-grown each cold-start, and because the *persist* tier
does not exist yet, there is nothing precious under the old `tank/rke2`. The
cutover is a one-off `zfs destroy -r tank/rke2` at the first grow on the new root.

Most of the change *collapses into the SSOT*: once the root lives in the dataplan,
the StorageClass pool, the disko materialisation, the containerd mount and the
persist PV all pick it up from one place. Two by-hand stragglers remain: ndh's
`zfs.d/zpool-init.sh` iterator (`zfs list -r tank/rke2`) and doc/comment mentions.

`"rke2"` used elsewhere as a *node kind* (the tailnet/host `kind = "rke2"`) is the
distro identifier, NOT a dataset path — it does not change.

== The dataplan entry shape

The twin of the netplan *segment* shape. Each entry is:

[source]
----
{ path, type, mountpoint, options }
----

* `path` — dataset path relative to the pool root, e.g.
  `rke2lab/wrkld/ephemeral/volumes`, `rke2lab/mgmt/persist/funnel-cert`. Only
  PARENTS appear; the datasets their owners create at runtime do not (see
  <<per-cluster-pools,who declares, who creates>>).
* `type` — `zfs_fs` (the disko dataset type).
* `mountpoint` — e.g. `legacy` for the containerd child (mounted by the kubelet /
  containerd, not auto).
* `options` — the ZFS property map, carried verbatim so the extraction from ndh's
  current static literal is *behaviour-preserving*.

== The committed projection (anti-IFD)

The dataplan is consumed as a *checked-in* `dataplan.json`, read purely
(`builtins.fromJSON (builtins.readFile ./dataplan.json)`) and surfaced as a flat,
system-independent `lib.dataplan`. seed-master regenerates it via `nix build
.#dataplanJson`.

This is the *committed-projection* option that
link:netplan-blueprint-single-source.adoc[the netplan doc] weighed and — in
practice — the netplan blueprint later adopted (`network-blueprint.json` is read
purely today). The dataplan starts there: it keeps `nixos-rebuild` on the host off
the Java/Maven hot-path, which matters because ndh materialises the datasets at
*host provisioning time*, before any cluster exists to run the jar.

IMPORTANT placement caveat (inherited from the netplan doc): `dataplan.json` must
NOT live as a Maven *resource* of the module that generates it — that packages the
output into the very jar that emits it (a real chicken-and-egg). It is a
top-level, lock-like file outside the generating module's input path.

== Usage — do / don't

❌ *Don't* hardcode a dataset path, and — the subtler one — don't name a cluster by
a NODE that happens to be in it:

[source,java]
----
private static final String ZFS_POOL = "tank/rke2/control-nodes/master";   // drifts
final String pool = layout.controlNodePool("master");  // a pet standing in for a CLUSTER
----

That second line is the shape of the live bug: one hardcoded pet as the pool for
every cluster on the host. A literal is usually the admission of an implicit
owner — ask *who owns this* before parameterising it.

✅ *Do* ask the dataplan for THIS cluster's view, so the StorageClass pools, the
persist PV handle, the containerd mount and ndh's disko materialisation all agree
by construction:

[source,java]
----
// one accessor per cluster; the role keying is internal to the layout
final var dataplan = DataplanLayout.forCluster(clusterName);   // bioskop-wrkld
dataplan.ephemeralPool();                    // tank/rke2lab/wrkld/ephemeral/volumes
dataplan.persistPool();                      // tank/rke2lab/wrkld/persist
dataplan.persistDataset(FUNNEL_CERT);        // tank/rke2lab/wrkld/persist/funnel-cert
----

❌ *Don't* put a pet in a path — see <<pet-not-in-the-path,the rule>>: the pet
names what must survive, the node name names what must not.

== Implementation plan

*rke2lab side (do first):*

. Author the dataplan SSOT in `seed-master` (a typed layout model — NOT in the
  netplan/network domain; a dataset is a storage concern, decompose by nature).
. Add `nix build .#dataplanJson` -> checked-in `dataplan.json` -> flat
  `lib.dataplan` (mirror `networkBlueprintJson` / `lib.networkBlueprint`).
. Rename the root to `tank/rke2lab`; point `OpenebsZfsManifestsUnit`,
  `nixos/containerd.nix`, and the new persist PV at the SSOT.

*ndh side (follow-up):*

. Add a `catalog.datasets` dimension in `catalog/default.nix` with the
  `mergeByKey`/`checkMerge` law copied from the `segments` block (key = dataset
  path), unioning `lib.dataplan` in.
. Materialise `catalog.datasets` in `modules/nixos/zfs-disko-config.nix` — the
  static `tank/rke2/*` subtree is deleted and replaced by the merged layout;
  pass `catalog` through `modules/nixos/disko.nix`.
. Update `zfs.d/zpool-init.sh` to the new root.

== A ROOT per cluster — the layout the one-cluster era could not have

The layout was declared when there was one cluster, so it was keyed by NODE NAME with the cluster
implicit. Two clusters on one host broke that in three ways at once, and the live tree showed all three
on 2026-09-21:

[source]
----
tank/rke2lab/control-nodes/
├── master/                              2.00G
│   ├── containerd
│   ├── pvc-3698166d…  1.57G
│   ├── pvc-b72ef9b3…   436M
│   └── pvc-e13b83da…   128K             ← ★ bound in the WORKLOAD cluster
├── bioskop-wrkld-control-plane-v9fhz/
│   └── containerd                       ← the node made this; it is in no declaration
└── peer{1,2,3}/containerd               ← declared pets that never existed: empty shells
tank/rke2lab/persist/funnel-cert         149K   ← ONE cert dataset for the whole host
----

*1. Both pools were shared across clusters, by a literal.* `OpenebsZfsManifestsUnit` named the
ephemeral StorageClasses from `layout.controlNodePool("master")` — one hardcoded pet. `poolname` is a
single StorageClass parameter, so every node of every cluster resolved the same host path and all
dynamic PVCs landed in the MANAGEMENT node's dataset: `pvc-e13b83da…` above is bound *in the workload
cluster*. The persist tier had the same fault, and there it is not untidy but destructive — see
link:../cluster-api/pac-in-cluster-render-spec.adoc#funnel-per-cluster[the funnel decomposition],
where sharing one dataset destroys the Let's Encrypt budget of both clusters at once.

*2. The declared node roster only ever made sense for HOST-GROWN nodes.* `CONTROL_NODES` was a roster
of PETS (`master`, `peer1..3`), deterministic because the host names those instances. A
CAPI-provisioned node's name is random, so the real workload node appears in the tree and in no
declaration, while three declared pets sit there empty.

*3. Three writers shared one parent.* `control-nodes/master/` was filled by the node (`containerd`),
by openebs (`pvc-*`) and by the declaration (the pet dataset itself) — the single-owner fault, in the
tree's own shape.

=== The shape

[source]
----
tank/rke2lab/
├── mgmt/
│   ├── ephemeral/                  ← declared. THE WIPE ROOT: one command per cluster
│   │   ├── nodes/                  ← declared parent only
│   │   │   └── <node>/containerd   ← the NODE creates it (zfs create -p)
│   │   └── volumes/                ← declared. openebs EPHEMERAL poolname
│   │       └── pvc-<uid>           ← openebs creates it, names it
│   └── persist/                    ← declared. openebs PERSIST poolname, Retain
│       └── funnel-cert             ← declared. the static PV ADOPTS it
└── wrkld/                          ← identical, disjoint
----

Three properties earn the three levels:

*The cluster root* (`<role>/`) makes each cluster's storage one subtree — a well-defined root for
inventory and accounting, and the thing the shared-`poolname` bug could not have.

*The nature level* (`ephemeral` vs `persist`) is the load-bearing one, because the wipe is the
dangerous operation. It keeps the invariant "the ephemeral wipe never reaches persist" expressed at a
SINGLE level, per cluster: the wipe is `zfs destroy -r tank/rke2lab/<role>/ephemeral`, and no retained
dataset can ever be under that path by construction.

WARNING: for the same reason the cluster root is *not* a destroy target. `zfs destroy -r
tank/rke2lab/<role>` would take `persist` with it. Destroying a cluster's storage means destroying its
`ephemeral` subtree; the persist subtree outlives the cluster on purpose.

*The owner level* (`nodes` vs `volumes`) gives each writer its own parent, so no two parties ever
create siblings in one dataset. `control-nodes` also loses its role word: workers will land under the
same parent, and the level is about nodes, not about control nodes.

=== Why the role, and not the cluster name

The projection ndh consumes is ONE checked-in `dataplan.json`, materialised on EVERY host — so it
cannot name hosts. A fleet cluster roster declared here would be a second owner of a fact
link:netplan-blueprint-single-source.adoc[the network blueprint] already derives
(`clustersOnSameHost()`). The ROLE suffices, because a host carries exactly one cluster per
`ClusterRole` — so `wrkld` is unambiguous on any host, and `DataplanLayout.canonical()` stays
argument-free.

IMPORTANT: the layout therefore now *depends* on "one cluster per role per host". That was already the
fleet law, but nothing in the dataplan leaned on it before. Two workload clusters on one host would
require the real cluster roster, and with it a way to make a host-specific projection.

=== Who declares, who creates

Only the PARENTS are declared, because openebs does not create its `poolname` — it must exist for the
CSI to create volume datasets under it. Everything below a parent is created by the party that owns its
content.

[#pet-not-in-the-path]
=== A pet label cannot place a dataset — the ephemeral is keyed on the NODE NAME

link:../cluster-api/pac-in-cluster-render-spec.adoc#pet-label[The pet label] gives a managed node its
role back (`master`, `peer1`), which invites an obvious idea: key the dataset on the pet, so the path is
stable across greenfield cycles. It does not work, for two independent reasons.

*It arrives far too late.* `rke2lab-zfs-containerd` is ordered `before=rke2-server.service` — the
dataset is mounted before rke2 starts, so before the node joins, so before any `Node` object exists to
carry a label. The pet becomes readable only after CAPI propagates it from the `Machine`.

[mermaid]
....
sequenceDiagram
  autonumber
  participant M as rke2lab-zfs-containerd
  participant R as rke2-server
  participant A as this cluster's apiserver
  participant C as CAPI (management cluster)

  M->>M: dataset = ephemeral/nodes/$node/containerd
  Note over M: no Node object exists yet —<br/>nothing carries a pet label
  M->>R: mounted (before=rke2-server.service)
  R->>A: the node registers
  C->>A: Machine label propagates (pet=master)
  Note over A: the pet is readable only HERE,<br/>long after the path was chosen
....

And the asymmetry would be exactly the one this decomposition removes: a HOST-grown node does know its
pet at boot (`InstanceGrow` writes `RKE2LAB_NODE_NAME=master` into `node.env`), a managed one does not,
because CAPRKE2's `spec.files` is one set for every replica. A pet in the path would work for the
management cluster and not for the workload.

*And a pet is RECYCLED.* Remediating `master` gives the replacement machine the same pet. A dataset at
`nodes/master/containerd` would then hand the new node the previous node's snapshotter state —
container state belonging to a different node identity. A node name is unique and disposable; that is
what ephemeral state needs.

****
*The rule.* The pet names what must SURVIVE. The node name names what must NOT.

So the pet is the right key for ELECTING the owner of a persist volume — and a better one than sorting
by `creationTimestamp`, because when the role moves the label moves with it — while every ephemeral
dataset stays keyed on the node name. No pet appears anywhere in a path.
****

NOTE: electing by label still does not free the controller from resolving a node NAME:
`ZFSVolume.ownerNodeID` must equal the `ZFSNode` object's name. The label serves the choice and the
scheduling half only.

=== Migrating the live tree — the ephemeral cannot move

[cols="1,3",options="header"]
|===
| Subtree | Gesture

| `persist/funnel-cert`
| *A `zfs rename` into `mgmt/persist/funnel-cert`, and it is mandatory.* This dataset holds the
  management cluster's funnel identity and cert. Letting a fresh one be created instead re-issues, and
  burns one of the 5 certs / FQDN / 168h budget the whole mechanism exists to protect.

| `control-nodes/*/pvc-*`
| *Cannot be moved.* openebs records the pool in the PV's `volumeAttributes.openebs.io/poolname` at
  PROVISIONING time, so the bound PVs keep pointing at the old path; renaming would break a running
  cluster. The old subtree survives as a graveyard until the next cold start re-creates every dynamic
  PVC under the new pool — and THAT is when it is destroyed.

| `control-nodes/<node>/containerd`
| No gesture needed: the node re-creates it under the new path (`zfs create -p`). The cost is
  re-pulling images once.

| `control-nodes/peer{1,2,3}`
| Destroy. They are the declared pets that never existed.
|===

== Open questions

. *Producer emit mechanism*: how seed-master emits `dataplan.json` — a CLI verb
  (like the netplan `yamlExport`, which drives an in-container scion), or a
  simpler host-flat export since the layout is *declared*, not derived from a
  bundle-only contract type. To settle at implementation.
. *openebs-zfs adoption*: the adopt path WORKS in practice — the management
  cluster's `funnel-cert` PVC is bound against the pre-created dataset today. Still
  to confirm from the source: that the `ZFSVolume` delete-finalizer does not `zfs
  destroy` the persist dataset on teardown (cluster-destroy bypasses the CSI, so it
  should not), and whether the plugin CREATES a missing dataset or requires the
  parent only (the layout assumes the parent only, which is why parents are
  declared and volume datasets are not).
. *Ephemeral wipe owner*: the wipe is ndh's (host layer, at instance renewal),
  diverging from the tailnet prune (in-cluster). Confirm the wipe hook's exact
  placement in ndh's instance-renewal path — and that it now targets
  `<role>/ephemeral` per cluster rather than one `control-nodes` tree.
. *The graveyard's end condition*: the old `tank/rke2lab/control-nodes` subtree
  cannot be migrated (bound PVs record the old pool) and is destroyed at the first
  cold start after the cutover. Nothing enforces that today — it is an operator
  gesture waiting for a GC that knows the difference between the old shape and the
  new.

== Contract types (the `dataplan-contract` bundle)

The dataplan vocabulary is realised as an OSGi `type=contract` bundle
(`io.seedmatic.rke2lab.dataplan.contract`), exported bundle-side and wired
bundle-to-bundle — the host speaks only to the broker, never to a dataplan type.
Its exported types:

* `DataplanLayout` — the canonical cluster-ZFS layout: the pool roots + their
  `Dataset` entries (path, tier, reclaim), the SSOT both the NixOS substrate and
  the in-cluster openebs-zfs storage classes project from.
* `DataplanCoordinate` — the domain's seed coordinates (the runbook + the sealed
  layout case), the slugs the handlers speak through the broker.
* `DataplanRunbookInput` — the runbook-input wire-record the front-door seeds the
  dataplan scion through.

A consumer imports the package in-container — `OpenebsZfsManifestsUnit` reads the
layout to render the storage classes, `FunnelStatePersistenceManifestsUnit`
adopts the pre-declared persist dataset. Without the bundle exporting this package
(the bnd `Export-Package` + `io.seedmatic.rke2lab.embed;type=contract`
capability), `manifests-core` cannot resolve its `dataplan.contract` import in any
closure.
