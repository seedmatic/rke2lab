= Worktree component spec (the worktree as an OSGi domain)
:toc: macro
:toclevels: 3

Status: the domain *as built* is ✅ Complete (committed `eb50886f` + `079ce552`); the realm
refinement in <<refinement>> is fully ✅ landed — Q1 (self-contained grow plan), Q2 (entry gate
OSGi-side), AND the final fold of `worktree-contract-host` into an OSGi-only `worktree-contract`.

This spec discharges the `SPEC_COVERAGE` obligation of the worktree contract packages by naming every

`Provenance`, `WorkingState`, `GitIdentity`, `GitBotIdentities`, `LinkedWorktrees`, `LinkedWorktree`.

toc::[]

== Overview — the worktree KNOWS its own git facts

The seed process runs *inside* the git worktree it cultivates. Worktree access used to be a static
helper (`Worktree.locatedFrom/at/openRepository`) that leaked a jgit `Repository` to its callers —
and jgit had begun to *spread*: a `GitProvenanceReader` in incus-core, the entry gate, and a
flake-lock policy each reached for git directly, duplicating the same walk for zero benefit. It is
now a proper OSGi domain that mirrors `incus` exactly: one `@Component` that self-locates its root
(walking up to `.git`) and answers the facts that root carries — *jgit sealed behind it, never
exposed*, so a consumer couples to the worktree's facts, not to a git library. It is *the one place*
the "is the worktree clean?" and "what did we provision from?" knowledge lives.

The domain has three modules:

[cols="1,3",options="header"]
|===
| Module | Role

| `worktree-contract` (`type=contract`, pkg `io.seedmatic.rke2lab.worktree`)
| The jgit-free `Worktree` service interface (OSGi consumers `@Reference` it — the incus scion), the
`LinkedWorktrees` factory + its `LinkedWorktree` handle (the rendered-branch delivery seam), the
entry-gate wire types `GatePolicy` and `WorktreeRunbookInput` (`@SeedContract("runbook")`), AND the
cellar-harvested wire types folded in from the former `worktree-contract-host` (see <<refinement>>):
`WorktreeFacts`, `WorktreeCoordinate`, `Provenance`, `WorkingState`. OSGi-only.

| `worktree-core` (pkg `io.seedmatic.rke2lab.worktree.internal`)
| `JgitWorktree` and `JgitLinkedWorktrees` `@Component`s, composing the jgit-holder `JgitCheckout` (all
git facts + write verbs + the network operations for one worktree path), the `GitCli` (the sole
`git` shell, local operations only), the
`JgitLinkedWorktree` handle, and the `SshCommitSigner`. jgit lives only here.

| `worktree-bdd`
| `WorktreeScenario` — the worktree SOIL (harvest + entry-gate THEN), `WorktreeRunbookHandler`
(extends `GenericRunbookHandler`, decodes the trigger), and `WorktreeAmendReflector` (the `worktree`
amend door that binds the injected `GatePolicy` FACET — the twin of `IncusAmendReflector`).
|===

== The exported types

* **`Worktree`** (contract) — the service: `root()` (the absolute, normalised anchor every
  provisioning path derives from), `provenance()`, `workingState()`, and `flakeLockCoherent()` (the
  `HEAD~1..HEAD` check — a `flake.nix` inputs change without its `flake.lock`). jgit-free — only JDK
  types and the `worktree` records cross it.
* **`GatePolicy`** (contract) — the entry-gate POLICY, injected into the worktree crossing as the
  `FACET` amendment. Two sub-gates, each toggled: `cleanWorktreeRequired` (+ the `toleratedPaths`
  allowed to be uncommitted) and `flakeLockRequired` (default OFF). Its `enforce(WorktreeFacts)`
  throws when an armed sub-gate is violated. The worktree domain enforces its OWN ground against a
  caller-supplied policy — it hardcodes no path, so no manifests/host vocabulary leaks in (the gate
  moved OSGi-side here; the host holds no gate).
* **`WorktreeRunbookInput`** (`@SeedContract("runbook")`) — the activation trigger the host amends,
  carrying the `@Amendment(FACET)` `GatePolicy`. The host names no worktree type: it contributes the
  gate as opaque JSON on the `FACET` role (a `FacetContributor(AmendCoordinate("worktree"), …)`),
  decoded here OSGi-side at the `WorktreeAmendReflector` door — the twin of `IncusRunbookInput`.
* **`WorktreeFacts`** (`@SeedContract("worktree-facts")`) — the snapshot the soil harvests into the
  cellar: `root` (as a String path; the reader re-hydrates a `Path`), the HEAD `Provenance`, the
  `WorkingState`, and `flakeLockCoherent` (the flake-lock fact the gate consumes when armed). No jgit
  type and no service reference crosses the seam — only the serialized payload, decoded per realm
  into its own copy.
* **`WorktreeCoordinate`** — the cellar coordinate (`FACTS`, slug `worktree-facts`, domain
  `worktree`). A `SeedCoordinate` enum. The `Cellar` keys on the slug/domain *strings*, not object
  identity, so it works across the seam exactly as `IncusGrowCoordinate.INSTANCE_GROW_PLAN` does.
* **`Provenance`** — the HEAD provenance: the commit `sha` (the key; the rest is recoverable via
  `git show`) and whether it is `dirty` (the one bit the sha cannot carry). An empty sha is a
  legitimate first run.
* **`WorkingState`** — `clean` plus `uncommittedPaths` when it is not. *The worktree owns the fact;
  the gate owns the policy (which paths matter)* — a neutral facts record with no consumer-specific
  knowledge.
* **`GitIdentity`** — the author/committer a `commit` stamps onto an automated change: a bot identity
  (name + email), so a machine-made commit is attributable to the tool, never the ambient
  `user.name`/`user.email` of whoever ran it. Domain-neutral — the worktree carries no specific
  identity; the caller supplies one.
* **`GitBotIdentities`** — mints that identity: `rke2lab:<tool>` / `rke2lab+<tool>@<authorityDomain>`,
  the base OWNED here and the tool supplying only its own discriminator (guarded to a bare suffix, so
  a tool can add provenance but never replace the base). An INSTANCE holding the one thing that varies
  by deployment, the tailnet authority domain, read from the ndh key-store rather than re-typed.
  It moved here from `manifests-bdd` on 2026-10-10, when the fabric delivery became a second automated
  committer: its javadoc calls itself "the single source of trust for the bot identity", and a single
  source only ONE domain can reach is not one — fabric would have minted a second convention. It sits
  beside `GitIdentity` because the identity of a git commit belongs to the domain that owns the git
  mechanism. Users: the manifests render, the manifests version bumper, the fabric delivery.

The `Worktree` service also carries TWO write verbs — the first the domain gained (survey stayed
read-only until a consumer needed to cultivate the tree), jgit still sealed behind the implementation
so only JDK types cross:

* **`stage(List<Path>)`** — stage additions/modifications for paths that exist, removals for paths
  that no longer do; each path absolute or worktree-relative, resolved against `root()`.
* **`commit(String message, GitIdentity identity, Optional<String> sshSigningKey)`** — commit the
  staged changes authored AND committed as `identity`, optionally SSH-signed with the caller's OpenSSH
  private key (git SSHSIG, `git` namespace, via an injected `ssh-keygen` signer since jgit ships
  none), returning the new commit sha. LOCAL to the seed's OWN worktree — pushing a rendered branch is
  the separate `LinkedWorktrees` service below.

=== The rendered-branch delivery — `LinkedWorktrees` / `LinkedWorktree`

Where `Worktree` is "the worktree the seed IS" (it self-locates and reports its own facts),
`LinkedWorktrees` is "a worktree the seed MAKES": the delivery seam that carries a rendered tree to a
`manifests/<host>-<role>` branch (see
link:../cluster-api/manifests-rendered-branches.adoc[Manifests Rendered Branches]). It is the socle
that replaces the old host-staging rotation/promotion (`host.N.staging.d` → `host.live.d`) with a
render-then-force-push of a git branch.

* **`LinkedWorktrees`** (contract) — the factory: `prepare(Path worktreePath, String branch,
  Optional<String> fetchToken)`. It releases any worktree holding the branch, FETCHES the branch from
  `origin` so the render accretes on its pushed history, then adds the linked worktree on it — or, the
  first time, on a new branch seeded with a null-commit base — and empties the tree, so the rendered
  branch carries only the rendered YAML, never the source, one commit per render on top of the last.
  `git worktree` is shelled (jgit exposes no worktree porcelain — verified against 7.7.x, which can
  OPEN a linked worktree but not CREATE one); the fetch is jgit's, authenticated as `x-access-token`
  with `fetchToken` (the App's reader token, or the pipeline's in-cluster) and otherwise anonymous —
  never through a credential helper the machine's git config names. No origin, or no such branch
  there, is the first render; any other fetch failure throws rather than orphaning the base.
  Domain-neutral like `Worktree`/`GatePolicy`:
  the caller supplies the branch name (`manifests/<host>-<role>`) and the path
  (`.local.d/worktrees/manifests/<host>-<role>/`), so no consumer vocabulary leaks in. Published as an
  `@Component(service = LinkedWorktrees.class)` that `@Reference`s `Worktree` to learn the repo root
  (instance-passing — the root flows in, it is not re-located).
* **`LinkedWorktree`** (contract) — the `AutoCloseable` handle `prepare` returns: `path()` (the render
  target), `branch()`, `stage(List<Path>)` and `commit(…)` (the same signed-commit mechanism as
  `Worktree`, against THIS worktree), `push(String token)` (push `branch()` to `origin` over HTTPS
  as `x-access-token`:`token`, a FAST-FORWARD — the branch accretes, a divergence is rejected, not
  clobbered; the token is a short-lived GitHub token the caller reveals, held only in jgit's
  in-memory credential provider), and `close()` (`git worktree remove --force`). jgit and `git`
  stay sealed behind `worktree-core`'s `JgitCheckout` (the sole jgit-holder instance both worktrees
  compose, which owns every network operation) and `GitCli` (the sole `git` shell, local operations
  only); only JDK types cross.

== The soil crossing — harvest, not push

`WorktreeScenario` (`@SeedScenario`, an OSGi bundle) is the worktree SOIL, played in-container by the
seeding engine like every other crossing, via a seam `RunbookCoordinate("worktree")` (broker routing
needs a shared value-coordinate). Its whole job: read the `Worktree` `@Component` (injected by the
`@OsgiService` bridge) and *harvest* a `WorktreeFacts` into the cellar at `WorktreeCoordinate.FACTS`
(WHEN fabricates, THEN seals). It is *not* survey-inert — reading git facts is a pure deterministic
read (no live system contacted), so the harvest runs in preview too, exactly as the incus grow plan
is projected in both modes.

The consumers read the harvest *from the cellar* (fetch-not-push), the same discipline the incus
`InstanceGrowPlan` rides — a domain-owned coordinate keyed by its wire slug crosses the realm through
the cellar, without the broker ever routing a domain enum.

== Realm model — as built (Q1+Q2 + fold landed)

The worktree domain is now OSGi-only: the former dual-realm `worktree-contract-host` has been FOLDED
into `worktree-contract` (`type=contract`) and DELETED. Two Q1+Q2 changes had removed both host
consumers first: the entry gate moved INTO the worktree crossing (an OSGi THEN that enforces an
injected `GatePolicy` against the just-harvested `WorkingState`), and the host GROW actualises the
self-contained `InstanceGrowPlan` ALONE (the incus scion projects the 13 disk mounts as
`GrowMountView`s — no worktree fetch). With no host reader left, `WorktreeFacts` /`WorktreeCoordinate`
/`Provenance`/`WorkingState` are consumed *only* OSGi-side, so the dual-realm face had no reason to
exist — it folded (see <<refinement>> for the principle, and the symmetric `REALM_BOUNDARY` rule that
now makes this class of drift a build ERROR).

== Realm refinement — the fold (✅ landed)

=== The principle it rests on

*A domain needs a dual-realm `-host` library iff the host ACTUALISES its harvest.* `incus` is
host-actualised (the host runs `pulumi up` to create the instance), so `incus-ingress-contract` is
legitimately dual-realm. The worktree is *not* actualised by the host — the worktree already exists;
the domain only reads facts off it. So once nothing host-side consumes those facts, the worktree
contract is OSGi-only, and `worktree-contract-host` folds into `worktree-contract`.

=== What removed the two host consumers (Q1+Q2 — ✅ landed)

Two changes removed both host-side reads, and with them the reason for the dual-realm face:

. **The grow plan became self-contained (Q1 — ✅).** The `InstanceGrowPlan` (`incus-ingress-contract`)
  now carries the resolved disk mounts as `GrowMountView`s: the incus scion (which `@Reference`s
  `Worktree`) computes the live + automount `BootstrapPaths` view OSGi-side and projects the 13
  source↔target pairs into the plan, so the host GROW actualises the plan ALONE — no separate
  `WorktreeCoordinate.FACTS` fetch for `root()`.
. **The entry gate moved OSGi-side (Q2 — ✅).** The host-flat `EntryGatePolicyEnforcer` (with its
  hardcoded manifests-path predicate) is DELETED. The gate is now a `GatePolicy`
  (`cleanWorktreeRequired` + injected `toleratedPaths`, its `enforce(WorkingState)`) carried as the
  `@Amendment(FACET)` of `WorktreeRunbookInput`: the host contributes it as opaque JSON at the
  `worktree` amend door (`WorktreeAmendReflector`), and `WorktreeScenario` enforces it in a THEN
  against the `WorkingState` it just harvested — the worktree domain gates its OWN ground under a
  caller-supplied policy, no host worktree fetch.

=== The consequence — the fold (✅ landed)

With both host reads gone, `WorktreeFacts`/`WorktreeCoordinate`/`WorkingState`/`Provenance` are
consumed *only* OSGi-side, so `worktree-contract-host` FOLDED into the OSGi-only `worktree-contract`
(`type=contract`) and the module was deleted. The worktree root still reaches the host, but *inside
the incus `InstanceGrowPlan`* (the `GrowMountView` sources, an incus dual-realm type), never as a
worktree type. The `SPEC_COVERAGE` obligation on these exports travelled with them into
`worktree-contract` (the default `ERROR`, covered by this spec).

[NOTE]
====
The forcing function DESIGNED for this class of drift (📋 enforcement pending, lands test-first as its
own step): a SYMMETRIC `REALM_BOUNDARY` rule — a `type=dual-realm` module must be referenced from BOTH
realms, and the gate ERRORs when EITHER realm has zero importers, naming the empty one. Had it been in
force, once Q1+Q2 emptied the host realm's references to `worktree-contract-host` it would have failed
the build until the fold — dual staging is earned only when both realms genuinely consume the carrier.
The fold here was done by hand ahead of the rule.
====

== Open questions (from the working session)

* **Naming `worktree` vs `row`** — resolved: keep `worktree` (concrete, truthful). `ROW`/planche is
  the gardening *role* (the SOIL), which applies at the role level without renaming the domain;
  introduce `row` as an abstraction only if a second soil appears (YAGNI today).
* **Entry-gate placement** — resolved: OSGi-side with an *injected* path policy (see <<refinement>>);
  keeping the manifests literal out of the worktree domain was the real constraint, and injection
  satisfies it.
* **flake-lock gate** — ✅ resurrected (Q1+Q2). The old `enforceFlakeLockCoherence` short-circuited
  with `if (true) return`; its intent is a real, *distinct* check: over the latest commit (a
  `HEAD~1` tree-diff) it fails when a `flake.nix` inputs block changed without a matching
  `flake.lock` change — a coherence a clean worktree does NOT catch (a clean tree can still commit
  an incoherent lock). It landed in three clean parts, NOT a revival of the old host code (the logic
  re-expressed, none of the six helper classes ported): the *check* is `JgitWorktree.flakeLockCoherent()`
  (the jgit `HEAD~1` diff + inputs-block compare, sealed behind the component), surfaced on
  `Worktree` and harvested into `WorktreeFacts.flakeLockCoherent`; the *enforcement* is
  `GatePolicy`'s flake-lock sub-gate (in `enforce(WorktreeFacts)`); the *enable/disable* is the
  `flakeLockRequired` toggle (`entryGate.flakeLock.required`, default OFF — like `bbox.failOnError`).
