= GitHub Credential Model — one org-owned GitHub App
:toc: left
:toclevels: 3

[NOTE]
====
*Status:* 🟡 Model frozen; domain built (2026-08-13). Freezes the credential model for the
rendered-branch GitOps flow. Every GitHub access — push of a render, Flux pull, in-cluster CI —
derives from a *single GitHub App owned by the `seedmatic` organization*, never from a personal
account's tokens. The realising domain (`ghapp`) is built — see
link:../osgi/ghapp-domain-spec.adoc[The ghapp domain] for the contract / edge / scenario *how*; this
doc is the *why* and the cross-cutting shape.
====

== Why this — escape the personal-token fragility

GitHub access is a *critical, cross-cutting* seam: `seed-outcluster` pushes each rendered branch
(`manifests/<host>-<role>` — see link:manifests-rendered-branches.adoc[Manifests Rendered Branches]),
every cluster's Flux pulls it, and in-cluster CI (Tekton) touches the repo. The question this doc
freezes is: *what identity carries that access, and where does its trust come from.*

The wrong answer — and what the codebase does today — is *personal PATs* (`gho_…` tokens tied to the
`nxmatic` user, `gh auth token`). That is fragile on two axes:

* *Governance* — the personal account is subject to a corporate organization's policies (SSO, PAT
  rotation, forced deletion). A credential the system depends on can be rotated or revoked *out of the
  operator's control*, breaking provisioning.
* *Coupling* — the automation borrows a human's identity and rights, so its blast radius is the
  human's, and its audit trail is the human's.

The fix is to give the automation its *own* identity, owned in a namespace the operator fully
controls: a *GitHub App owned by the `seedmatic` organization*. `seedmatic` owns the repos it
provisions (`seedmatic/rke2lab`, `seedmatic/ndh`, and their dependencies) and the App and its keys.
An App's keys are the *App's* — not personal PATs — so corporate PAT policies do not touch them, and
the App acts as itself (`seedmatic-rke2lab[bot]`), not as a person.

== The one App — an org-owned automation identity

A *single* GitHub App, `seedmatic-rke2lab`, owned by the `seedmatic` org, installed on the repos it
provisions. Every GitHub usage mints a token from it. There is no second identity, no PAT, no personal
deploy key.

The App's *union* of permissions (declared in its manifest):

[cols="1,1,2",options="header"]
|===
|Permission |Level |Serves

|`contents` |`write` |writer push; also covers every reader (a `read` token is a subset)
|`statuses` |`write` |Tekton — commit status checks
|`pull_requests` |`write` |Tekton — open/update PRs
|`checks` |`write` |Tekton — check runs
|`metadata` |`read` |mandatory baseline
|===

=== Per-token least privilege — one identity, scoped tokens

The App holding a broad *union* of permissions does NOT mean every token is broad. An installation
token is *scoped down at mint time*: the mint call requests a *subset* of the App's permissions (and
optionally a subset of repos). So from the one App:

* the *writer* mints a `contents:write` token,
* *Flux* mints a `contents:read` token,
* *Tekton* mints a `statuses:write` + `pull_requests:write` + `checks:write` token.

Each usage gets exactly what it needs — least privilege *per token*, from a *single* identity. Adding
a usage is a new scoped mint, not a new credential to provision.

=== One private key, operator-minted short-lived tokens

The App has *one* private key, full stop — *no per-cluster keys*. (Generating additional App keys is
GitHub-UI-only — there is no API — so per-cluster keys would mean N manual key generations for a gain
that token-scoping already delivers.) Isolation comes entirely from *scoping each token* (a reader
never mints write) and their *short lifetime* (≈1 h); if ever compromised, the remedy is
suspend-the-App or rotate-the-one-key. Every consumer mints scoped tokens from that one key at runtime,
rather than holding a static credential:

* *Flux* mints its `contents:read` pull token *natively* — the Flux Operator's GitHub App auth: a
  `githubapp` Secret carrying the App id + installation id + the private key, referenced by
  `pullSecret`; Flux self-mints and self-refreshes (see link:https://fluxcd.io/blog/2025/04/flux-operator-github-app-bootstrap/[the Flux blog]). This *replaces* deploy keys and PATs for the pull.
* *other in-cluster actors* (Tekton) mint their scoped tokens through a `github-app-operator`
  controller (link:https://github.com/samirtahir91/github-app-operator[`samirtahir91/github-app-operator`])
  that refreshes a token Secret from the same App key — an existing upstream controller, *not* a
  bespoke minter.
* *the writer* (`seed-outcluster`, OPERATOR) mints its `contents:write` token *on demand, at the point of
  the push* — never sealed (§ <<Where minting happens>>, § <<Token delivery by enclosure (C4)>>). The
  in-cluster render uses PaC's per-PipelineRun token instead, from a mounted Secret.

The one key rides each cluster's sops-sealed lane. Simpler than per-cluster keys, and no per-cluster
key ceremony.

=== Defining the App — a pre-filled form + one grow-sown scenario

The App's *shape* — permissions, name, homepage — is expressed as *URL query parameters* on GitHub's
"New GitHub App" page, held as `REGISTRATION_URL` in `GithubAppScenario`:

----
https://github.com/organizations/seedmatic/settings/apps/new
  ?name=seedmatic-rke2lab
  &url=https://github.com/seedmatic/rke2lab
  &webhook_active=false
  &contents=write&statuses=write&pull_requests=write&checks=write&metadata=read
----

*Why a pre-filled form and not an auto-POSTed manifest:* GitHub gates App creation behind `SameSite`
session cookies (`user_session` Lax + `__Host-user_session_same_site` Strict), which a browser
*strips on a cross-site POST*. A loopback endpoint auto-submitting a manifest to `github.com` arrives
*anonymous* — GitHub answers `"url" wasn't supplied` even for a perfect manifest (proven from a HAR:
zero session cookies on the POST). A *top-level GET navigation* to the pre-filled form DOES carry the
Lax session, so the operator lands authenticated and the final "Create" click is same-site. See
link:../osgi/ghapp-domain-spec.adoc[the ghapp domain] § "Why registration cannot be a loopback POST".

What is versioned vs. intrinsically out-of-band (GitHub's rules, not our wiring):

[cols="1,2",options="header"]
|===
|Concern |Where it lives

|App *shape* (permissions) |*committed* — the `REGISTRATION_URL` above
|Creation *procedure* |*committed* — the host-side `ghapp` CLI (a `seed-outcluster` subcommand): `ghapp create` opens the pre-filled form, `ghapp install` opens the install page, `ghapp seed <appId>` resolves the installation id and writes `.secrets`. It is kept OUT of the grow because `seed-outcluster` runs under `pulumi up`, whose gRPC engine captures the console and makes a mid-run browser/prompt unusable; the grow-sown `GithubAppScenario` only *rehydrates* the sealed credentials. No loopback endpoint, no in-container browser.
|`installation` intent (which repos) |*committed* — declared data
|App ID + installation ID |*declared config* — non-secret; `ghapp seed` resolves the installation id from `GET /app/installations` after the operator installs the App
|App *creation* |*out-of-band, once* — GitHub gates creation + key generation + installation behind three browser clicks (even Terraform cannot create an App). The irreducible manual atom; the `ghapp` CLI opens the browser at the pre-filled form on the real console.
|The private key |*sealed (sops-governed)* — a GitHub-generated secret output, never re-derivable, committed only sops-encrypted. Our single source of trust for the automation. *One key*, sealed once at `GhAppCoordinate.GITHUB_APP`.
|===

This is the same shape as every root of trust here (the `rke2-cluster` SSH key, the age recipients,
the sops config): the *shape and policy* are declared in code; the *establishment* of the anchor (key
material + the human authorization) is an out-of-band act producing sealed outputs. A predictable
system has known, declared sources of trust; it does not bootstrap its own root from nothing.

== Predictability invariants (govern everything below)

The overriding goal is a *predictable* system: fully declarative, with an always-known source of
trust, and *no uncertain logic* — no fallback chains, no silent soft-skips, nothing that can leave the
system in an unknown state.

. *One declared source of trust — the App.* Every GitHub token is minted from the `seedmatic-rke2lab`
  App key; there is no "env var, else CLI, else PAT" precedence (the current `LaunchSecretsWriter`
  env→CLI precedence is disallowed and removed). The personal `gho_` PATs and `gh auth token` are
  retired.
. *A required credential's absence is a HARD fail, declared per run mode — never a silent skip.* A run
  DECLARES whether a mint is required: required ⇒ a mint failure is a loud failure; not-required
  (preview / survey / ephemeral test) ⇒ an *explicit, declared* skip, never inferred from "the App key
  happened to be absent".
. *Keys are declared artefacts, not lazily generated.* Private keys are GitHub-generated at App
  creation / key-add, sealed in `.secrets`, and referenced — never a `if missing, generate` runtime
  branch.
. *One usage, one scoped mint.* A usage never "tries token A, else token B"; its scope is declared and
  fixed at the mint call.

=== Where minting happens

* *Writer* — the manifests-synthesis scenario reveals the durable `GithubAppCredentials` and mints a
  `contents:write` token *on demand, at the point of the push* through the auth `GithubWriterTokenMint`
  port (which delegates to `GithubAppMinter`: sign a JWT, `POST /app/installations/{id}/access_tokens`
  scoped to `contents:write`). The token is *never sealed* — it is ephemeral (≈1 h, a lifetime GitHub
  chooses) and minting it seconds before use is what keeps it from going stale between a mint and a
  much later reveal (the trap a durable seal fell into: minted before provisioning, dead by push).
  In-container mint (the minter is bundle-wired, unreachable to the flat host); mint failure is a hard
  fail. The IN_CLUSTER render skips the port and reads Pipelines-as-Code's `RKE2LAB_PUSH_TOKEN` env.
* *Flux reader (in-cluster)* — Flux v2 authenticates to a `GitRepository` as a GitHub App natively: a
  `githubapp` Secret carrying `githubAppID`, `githubAppInstallationID`, and the App's private key; Flux
  mints and self-refreshes `contents:read` tokens. No host dependency ⇒ Tier-1 autonomy preserved.
* *Tekton (in-cluster)* — Tekton has no native App auth, so
  link:https://github.com/samirtahir91/github-app-operator[`github-app-operator`] (an existing upstream
  controller) reads the App key Secret and refreshes Tekton's git-auth Secret with a freshly minted,
  scoped token. No bespoke minter to build.

== The token consumers — the delegation map (blast radius)

Retiring the personal `gh auth token` is NOT a one-line swap: the token has *four* host-side touch
points. `auth` does NOT disappear — it stays as the GitHub *mint seam*: the `GithubWriterTokenMint`
port, realised by an `auth-edge` `@Component` that delegates to `ghapp`'s `GithubAppMinter`, and
`GithubAppTokens`, the one revealer every consumer asks for a token — it reads the App from its owner
(`GhAppCoordinate.GITHUB_APP`) and hands the mint the owner's `GithubAppCredentials`. The port used to
take three plain strings so that a consumer mirroring the App material would not be dragged onto
`ghapp-contract`; since 2026-10-10 no consumer calls the mint itself, so that reason is gone.
There is no longer a sealed-token coordinate — the token is minted at the point of use, never filed.
`auth` keeps a second, orthogonal job — the *FloxHub* token (`flox auth token`), which `ghapp` does not
cover and must survive.

[cols="2,2,2,3",options="header"]
|===
|Consumer |Source today |Purpose |Target

|`ManifestSynthesisScenario`
|sealed token (auth-seal, durable → staleable)
|push `manifests/<host>-<role>` → origin (write)
|`GithubWriterTokenMint` — a FRESH WRITER token minted on demand at the push

|`VersionBumpScenario` + `manifests-cli`
|`AuthTokenContact` edge (`gh auth token`)
|list upstream releases (read, rate-limit)
|`GithubWriterTokenMint` on demand (or stay anonymous)

|`LaunchSecretsWriter` — github
|`AuthTokenContact` edge
|deliver a github token into the guest `.secrets`
|*DROPPED* — the guest gets the `githubapp` Secret; Flux self-mints

|`LaunchSecretsWriter` — flox

|deliver the flox token into the guest `.secrets`

*The delegation, proven*: `auth` owns "the git-push credential" (the `GithubToken` seam); `ghapp` owns
"the App identity + minting". `auth` re-sources its GitHub branch from `ghapp` (delegation) and drops
its own `gh auth token` edge for GitHub, while its FloxHub branch keeps that edge. The push seam is
untouched, so `ManifestSynthesisScenario` never changes.

== Token delivery by enclosure (C4)

The one App key is the source of truth, but *how a container gets a token differs by enclosure*, and
that difference is the invariant: *in-cluster, the token comes from a Kubernetes Secret — the
sops-encrypted `.secrets` is NEVER read/decrypted inside a container*. On the host (OPERATOR), where
no in-cluster token operator applies (it is the bootstrap, before/outside the cluster), the token is
minted from the host-smudged (plaintext) `.secrets`. The nix wrapper keys off `GH_TOKEN`: empty ⇒
OPERATOR, mint from `.secrets`; already set ⇒ in-cluster, use the mounted Secret and skip `.secrets`.

[[writer-isolation]]
== Writer isolation — by token scope, not by key

With *one* key, there is no host-vs-cluster key separation to lean on: the same key mints the writer's
`contents:write` token and is rendered into each cluster's `githubapp` Secret. Isolation is therefore
*by token scope*, and it must stay that way by construction:

* the *writer* mint requests `WRITER` (`contents:write`) and nothing else; the token is short-lived and
  used for the single push;
* a *reader* (Flux) mints `READER` (`contents:read`) — it *cannot* mint write, because the scope is
  fixed at the mint call, not by which key it holds.

The checkable invariant shifts accordingly: every mint call declares a `TokenScope`, and no consumer
ever mints a scope broader than its role. The key itself is uniform; the *tokens* carry the privilege
boundary.

== Bootstrap ordering — the cluster App key is a LOCAL-ONLY seed

The cluster's App-auth material bootstraps the pull, so it cannot live only inside the branch it
fetches (chicken-and-egg). It belongs to the *local-only bootstrap seed* — the node's RKE2 auto-deploy
`server-manifests` dir, written by `seed-outcluster` at nix-seed (the `delivery=local-only` facet in
link:manifests-rendered-branches.adoc[Rendered Branches]) — alongside cert-manager, the Flux operator /
instance, `FluxRoot`, and the `sops-age` Secret.

The `sops-age` Secret already rides this lane (see `SopsAgeSecretManifestsUnit`); the App-auth Secret
*joins it* as its twin — the new `GithubAppSecretManifestsUnit` renders the `githubapp` Secret
(`githubAppID` / `githubAppInstallationID` / `githubAppPrivateKey`) from a `GithubAppMaterial` handed
to synthesis on `ManifestSynthesisContext`. That material is the manifests-side MIRROR of the sealed
`ghapp` `GithubAppCredentials` (the exact treatment `OperatorPkiMaterial` gives cluster-pki's
`AdminCredentials`): `ManifestSynthesisScenario` reveals the sealed credentials from the cellar by
the neutral `github-app` wire slug and translates them into `GithubAppMaterial`, so no `ghapp-contract`
flat copy is dragged into the standalone `manifests-cli` assembly. Resolved upstream in-container,
sealed, rendered into a Secret, applied at bootstrap. Once Flux is up WITH the App key (to mint the
pull token) AND the age key (to decrypt), it reconciles the rest of `manifests/<host>-<role>` from git.

== FluxRoot — HTTPS + App-auth secretRef

`FluxRootManifestsUnit` is rewritten to the target: a `GitRepository` on the rendered branch,
authenticating as the App.

* `url: https://github.com/seedmatic/rke2lab.git` (HTTPS — App auth, not SSH).
* `ref.branch: manifests/<host>-<role>`, `spec.ref` on the rendered branch; the root Kustomization
  `path: ./`, `prune: true`, `decryption: { provider: sops, secretRef: sops-age }`.
* `spec.secretRef` → the `githubapp` Secret (`githubAppID`, `githubAppInstallationID`, and the App's
  one `githubAppPrivateKey`).

The stale placeholders — `url: https://…nxmatic/rke2lab.git` anonymous, `ref.branch: main`, `path:
./gitops/clusters/<cluster>` — are deleted in the same change; no dead paths.

== `.secrets` — App identity material, no PATs

All personal `gho_` PATs are retired from `.secrets` (`github.token`, `tekton.git.password`). In their
place, the App identity material, sops-sealed:

* `githubApp.appId`, `githubApp.installationId` — non-secret, declared.
* `githubApp.privateKeyPem` — the *one* App private key (PEM), sealed. No per-cluster keys.

The one key is used by the writer mint (in-container) and rendered into each cluster's `githubapp`
Secret (local-only seed), where Flux and `github-app-operator` mint their scoped tokens. The
`kubernetes.secrets`-replicator entries for the old shared PATs are removed.

== Caveats (documented, not solved here)

* *The one App key lives in each cluster* (Flux/`github-app-operator` self-mint). Contained by: a
  *single-repo* App (a leaked key mints tokens for *one repo* — blast ≈ a repo write key, not a whole
  org); and *sops-sealed at rest* (the key rides the `sops-age` decryption lane, never in the clear in
  git or on disk). The trade-off of one key: a leak from *any* cluster is a leak of *the* key — accepted
  in exchange for no per-cluster key ceremony, and mitigated by suspend-the-App / rotate-the-key.
* *Runtime minting + refresh.* Tokens are short-lived (≈1 h) and minted at runtime — a live GitHub API
  dependency for refresh, handled *inside* the cluster (Flux native; `github-app-operator` for Tekton).
  Standard, battle-tested; a GitHub outage pauses refresh but an in-flight token stays valid ≈1 h.
* *No branch-scoped read.* GitHub cannot scope read to a single BRANCH; a `contents:read` token can read
  other branches. The branch-per-cluster model gives WRITE isolation; true per-branch READ isolation
  would need one repo per cluster (deferred).
* *The App creation is one human approval* (GitHub-gated), and the App/repo ownership is `seedmatic` —
  as robust as the org the operator controls. Installing the App (to resolve the installation id) is a
  second click in the same ceremony.
