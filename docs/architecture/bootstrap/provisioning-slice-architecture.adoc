== The founding rule of the migration — two black-box frontiers

The seeding sits between two frontiers, and the whole migration obeys one rule:
**our internal restructuring must be invisible at both edges.**

* **Upward — the Pulumi frontier (the commissioner).** `seed-outcluster` crosses it to
  hand Pulumi the resources and the checksums; that we keep. But the Pulumi engine
  must never see that we reorganised the inside (host/OSGi split, scions,
  gardening). It sees its resources + a checksum string, nothing more. It is
  *indifferent to who wrote the files* — host component or in-container scion, same
  thing: the only channel that tells it "the provisioning files changed" is a value
  planted in one of its resources. The realm boundary does not exist for it.

* **Downward — the master frontier (the provisioned node).** The master must not
  see the new version either. Its consumers — cloud-init, the systemd daemon, the
  rke2 manifest watch, and the contacts the incus/systemd/cluster scions probe
  (ssh/incus exec, dbus-on-TCP, kube API) — must observe the same materialized
  files and the same endpoints, whether host or OSGi produces/probes them.

Both frontiers are black boxes: the refactoring changes the inside, never the
observable surface at either edge. This invariant is what justifies delta #7 (the
checksum stays the files→commissioner channel regardless of who computes it) and
what keeps the whole restoration honest — we may reorganise everything within, so
long as these two surfaces do not move.

**Corollary (the verification method):** the truth of "invisible at both edges" is
checked by *comparison with the base the master was provisioned from* (`main`).
The outputs — the materialized files, the Pulumi outputs, the instance config —
must match byte-for-byte. Any divergence is a migration defect, not a new feature.
We already suspect drift; the comparison below measures it.

== Overview

Seeding a master is two distinct gestures, fused for a long time in a single
host class (`IncusResourceBootstrap`) and now being split along the realm
boundary the gardening model draws:

* **The Pulumi provisioning** — the `com.pulumi.incus` resources that bring the VM
  itself into being: `Project · Network · Profile · Image · Instance`. The Java
  code declares these as a *resource graph* (their dependencies: Instance needs
  Image + Profile, Profile references Network, all under Project); the **Pulumi
  engine** resolves that graph topologically and talks **gRPC** to the Incus
  *resource provider* (a separate plugin process) which makes the real Incus API
  calls. This whole machine — engine, gRPC channel, provider processes — lives
  *around* the program, host-side: `Main` itself runs *inside* `Pulumi.run(...)`.
  It therefore **stays host** (it cannot enter Felix — a scion in the OSGi
  container has no engine around it). It is the commissioner's own gesture, kept
  in `seed-outcluster`.

* **The materialization** — writing onto the master the files its downstream
  consumers read (cloud-init seed, systemd units, k8s manifests, rke2 config, the
  env-config overlay). This is *metier*: it reasons over domains, catalogs, layer
  contributions. In the gardening model it is a **scion played in-container**
  (`broker.sow`), fed a host-neutral activation payload — never a host class that
  names `manifests.contract`.

This document is the map of both gestures: what each materialized target writes,
who reads it downstream, and its reload protocol — the load-bearing knowledge that
must survive the transposition. It closes with the *current gap*: what the
top-down demolition removed ahead of its replacement, so the work-list is explicit.

== The checksum→reload mechanism — the glue between the two gestures

The reload column above is not documentation; it is *driven*. It is the nerve that
joins the materialized targets (metier) to the Pulumi Instance (host), and it
decides — per change — whether the master is *renewed* or *hot-reloaded*. Losing
it means: even with the graph and the scions restored, a re-synthesis has no way to
reconcile.

=== Figure 2 — how a change decides renew vs hot-reload

[mermaid]
----
flowchart TB
  change["a target's materialized files change<br/>→ its checksum changes"]
  policy{"target's<br/>TargetReloadPolicy?"}

  change --> policy
  policy -->|STATIC| cfg["write checksum into instance config<br/>user.rke2lab.provisioning.slice.*"]
  policy -->|DYNAMIC| out["store checksum in Pulumi outputs"]

  cfg --> diff["Pulumi sees a config.* diff<br/>(replaceOnChanges: config, config.*)"]
  diff --> renew["INSTANCE RENEWED<br/>(delete-before-create)"]

  out --> nodiff["Pulumi sees no config diff"]
  nodiff --> recon["reconciler reads new checksum<br/>→ HOT-RELOAD the component"]

  classDef s fill:#fee,stroke:#a22,stroke-width:2px;
  classDef d fill:#dfd,stroke:#2a2,stroke-width:2px;
  class cfg,diff,renew s;
  class out,nodiff,recon d;
----

The mechanism, as it stood:

* Each target declares a `TargetReloadPolicy`: **STATIC** (consumed once, at
  boot — e.g. cloud-init, which defines the instance) or **DYNAMIC** (re-watched
  and re-applied on change — systemd, k8s, rke2-config, rke2lab-env).
* A checksum is computed per target over its materialized roots (with foreign-
  descendant scoping so a file owned by another target does not perturb the digest).
* **STATIC** checksums are written into the Incus instance config under
  `user.rke2lab.provisioning.slice.*`. The Pulumi `Instance` is configured with
  `replaceOnChanges(["config", "config.*"])`, so a STATIC checksum change makes
  Pulumi see a `config.*` diff and **replace the instance** (delete-before-create).
* **DYNAMIC** checksums are stored in Pulumi outputs (not instance config). Pulumi
  sees no config diff → no replacement; a reconciler reads the new checksum from
  outputs and **hot-reloads** the component.

The key insight the old design captured: we do not duplicate checksums, we control
*which* checksums appear in instance config, to leverage Pulumi's existing
`replaceOnChanges` — the Incus SDK is a pass-through to the Incus API, it has no
checksum logic of its own.

This straddles the realm boundary: the checksum *computation* reads materialized
paths (metier, in-container with the scion), but the *partition* into instance
config vs outputs and the `replaceOnChanges` wiring live on the Pulumi `Instance`
(host). The target vision must place each half on its side and define how the
per-target checksums cross from the scion to the host graph.

== The activation payload — how "which layers" reaches the master

The `RKE2LAB_MANIFESTS_PUBLISH_*` variables in the env-config overlay are the master's
copy of the operator's per-domain activation choice (mesh on/off, cluster-api
on/off, …). Their journey is the crux of the realm split:

. The operator's choice lives in the Pulumi config (`manifests.publish.*`).
. It must reach the `rke2lab-env` materialization as *seed variables* the
  synthesis folds into the overlay ConfigMap.
. The synthesis (the manifests domain) knows the vocabulary — the
  `ManifestDomainCatalog`, the `RKE2LAB_MANIFESTS_PUBLISH_<X>_ENABLED` naming, the
  `ManifestDomainPolicy` that filters which domains are synthesized at all.

**Target shape:** the host `sow`s a host-neutral activation payload (raw booleans,
`mesh: false`) — naming no domain type — and the in-container manifests scion
translates it into both the `ManifestDomainPolicy` (synth-time: which domains are
built) and the `seedVariables` (publish-time: the `RKE2LAB_MANIFESTS_PUBLISH_*` written into
the overlay). The translation that used to live host-side (the former
`ManifestLinkPolicy`/`ControlplanePolicy`, now dissolved) lives in the scion, which alone may name its own catalog.
The former env-overlay SINK (`writeControlplaneOverlay` / `NodeEnvOverlayService`) is GONE — the NixOS
substrate bakes the node env via the `nixos/` modules, so there is no `/srv/host` overlay to write.

=== Delta #7 resolved — the DYNAMIC half dissolves, only cloud-init survives

The checksum→reload glue looked like the subtlest hole (what decides renew-vs-hot-reload
after a re-synthesis?). Reading main against the I6 model resolves it, and it is SMALLER
than it looked. main had **exactly one STATIC target — `cloud-init`** ("Cloud-init reads
it once at first boot, so the only STATIC target"); the other four (`k8s`, `rke2-config`,
`systemd`, `rke2lab-env`) are DYNAMIC.

* *The DYNAMIC half is DISSOLVED by I6, not restored.* R1 (host-cellar) already states a
  live instance is **never restarted when mounted content changes** — a change is
  reconciled by REFRESHING the affected services, driven by the runbook `json` runtime
  role (the `change` delta → services-to-reload map). That IS main's hot-reload, in the
  I6 vocabulary. So the DYNAMIC targets need no `TargetReloadPolicy`/outputs machinery;
  the promotion (delta #9) + the `json` refresh map replace it whole.
* *Only the STATIC target survives as a real replace-trigger.* cloud-init reads its seed
  ONCE at first boot; if `user-data` changes, a running instance never re-reads it → the
  instance MUST be recreated. This is the sole case where a content change forces an
  instance-replace, and it is exactly the nocloud material (delta #8 mount + the transcode
  step). So the surviving glue is narrow: a change to the promoted `cloud.d/` (equivalently,
  a `HostDriftEntry` touching the nocloud paths) must flip `replaceOnChanges` on the host
  `Instance`. The per-file checksums to detect it already live in `HostStagingEntry`
  (incus-contract) — the DATA exists; only the wiring "nocloud drift → instance-replace"
  is to build, host-side, when the grow (delta #1/#8) is restored.

*What this deletes from the restore list.* `TargetChecksumPipeline`, `TargetReloadPolicy`,
the STATIC/DYNAMIC partition, `user.rke2lab.provisioning.slice.*` — NOT restored (the
5-target registry was main's way to route hot-reload-vs-renew; I6 routes it by drift-entry
+ `json` refresh instead). The four `*Metadata` records + `HostSlotManifest` +
`GitMetadataExtractor` — their PROVENANCE role (git commit, policy, flox envs) folds into
the `Host*Entry` provenance field, not restored as standalone types. Only the single
nocloud→replace wire is a genuine host residue.

The synthesis is driven as a scion. `manifests-bdd` and `netplan-bdd` exist; the
manifests crossing runs inside `ClusterSeedScenario`, and the CLIs are sowers —
`manifests-cli` drives `ManifestsCliScenario` (sows the `manifests` coordinate),
`netplan-cli`'s `yamlExport` drives `NetplanCliScenario` (sows `netplan`). Each names
no domain type: it sows a coordinate through `seed.broker.port` and the domain plays
its scion in-container, sealing the result — only JSON crosses the frontier.

This is why a flat host cannot `awaitService` a `type=contract` domain service: the
service registers with the bundle's class copy, so a flat host copy never matches
(and `java -jar manifests-cli-exec.jar` naming a contract type flat throws
`NoClassDefFoundError` — the frontier working, not a packaging bug). The host does
not reach into the registry for domain logic, **it sows**. The materialization a
fresh seed must reproduce (the `99-…` overlay, the `RKE2LAB_MANIFESTS_PUBLISH_*`
vars) is produced by the manifests scion — the "graft cultivated fresh" the bdd map
names. See link:../osgi/manifests-bdd-spec.adoc[manifests-bdd-spec] +
link:../osgi/netplan-bdd-spec.adoc[netplan-bdd-spec].

== Target vision — how the seven deltas are restored

The deltas are not seven independent chantiers; they group by nature and realm,
with a dependency order.

=== Three families

**Family 1 — the Pulumi graph (delta #1), pure host.** The `com.pulumi.incus`
resources return, host-side, as the provisioning body of the "the instance is
provisioned" WHEN. Code that exists in `342b7c327~1` and should not have left.

**Family 2 — the five materializations (deltas #2–6), metier → scion.** The synthesis
machinery (`ManifestSynthesisService`, the env-config contributors, explode) is intact
OSGi-side, but two things were dropped: nothing plays it as a scion, and main's
`materializeAssets()` step that wrote the synthesised content INTO the staging roots
(before the mounts) is gone — only nocloud's writer was re-added. The settled
replacement is an IoC service (§ _The host-asset materialization service_ below): the
providers, in manifests, own the content; a driver in incus writes them where the
instance needs them. One pattern covers env, systemd-bundle and cloud-config at once.

**Family 3 — the checksum→reload glue (delta #7), straddling.** The cloud-init
checksum is COMPUTED in-container (the scion already carries it: `host.live.d =
jsync(syncedFrom)`, so the nocloud checksum IS the `syncedFrom` `HostStagingEntry`'s
per-file value — no recompute) and PROJECTED into the `InstanceGrowPlan`; the host
only POSES it on `replaceOnChanges`'s `user.rke2lab.provisioning.slice.cloud-init`
key (with `buildChecksum`, likewise scion-computed). It *depends* on both other
families (a graph to wire `replaceOnChanges` onto, materializations to checksum), so
it comes last. The straddle is now clean: compute+project OSGi-side, pose host-side.

**Family 4 — the host-tree promotion + bind (deltas #8–11), scion-then-host.** The
materialisation (Family 2) writes a staging slot; the PROMOTION (delta #9,
`HostTreePromoter`, incus-core) then `jsync`s it onto `host.live.d`, publishing the
live/drift entries; only THEN does the host GROW bind the 13 mounts (delta #8) onto
that already-current tree. `HostMountSourceVerifier` (#11) guards the sources before
the bind; the secrets write (#10) is a host-only sidecar. This family is what
surfaced the ordering correction below — it did not exist when the "either first"
order was written.

*Order (corrected 2026-07-15, was "Family 1 and Family 2 are independent, either
first").* The naive "either first" is WRONG once the promotion (Family 4) is in the
picture. The instance MOUNTS `host.live.d`; so the tree must be materialised (F2)
AND promoted (F4) BEFORE the host graph (F1) starts the VM with `running=true`, or
it mounts stale/empty content (first run). The hard sequence:

  F2 (materialise the slot) → F4-promote (jsync → host.live.d) → F1 (grow the VM,
  bind the mounts) → F4-verify (probe) ; F3 (checksum glue) wires across F2+F1.

This is the I6 correction (link:../osgi/host-cellar-realisation-spec.adoc[host-cellar]
§ CORRECTION) folded in: the SCION prepares+promotes first, the HOST grows last. It
does NOT reverse shape (A) — shape (A) settled WHO (the host owns the Pulumi graph,
a scion cannot; see the crux below); I6 settles WHEN (after the promotion). The two
compose: two beats, *ordered by the mount*, not two free beats.

=== The crux — the "instance provisioned" WHEN, and its resolution

The ClusterSeed map (link:../bdd/bdd.adoc#clusterseed-scenario-map[bdd.adoc]) says
the incus scion is "image + instance". Reality contradicts it: the scion
(`IncusProvisionScenario`) builds the image and probes reachability, and states
itself that "the actual instance provisioning stays host-side". The provisioning
that *brings the instance into being* is host: the Pulumi engine resolves the
resource graph and drives the Incus provider over gRPC — a control flow that runs
around `Main`, outside Felix. So the WHEN has two parts in two realms, and the
map's "image + instance = the scion" conflates them.

**Decision (settled): shape (A) — host provisions, then sows the scion to verify.**

The alternative — (B) *the scion drives, the host provides the graph as a service*
— is ruled out on a hard constraint, not a preference: it would have the scion
*direct* the provisioning, i.e. Pulumi's control flow crossing the seam INTO
Felix. But it is the engine that resolves the graph and drives the provider; a
scion has no engine around it. Pulumi crosses the frontier and directs the
operations, never the reverse. (B) inverts the direction of control and is
physically impossible.

So the WHEN is THREE-beat (was drafted as two; the promotion, Family 4, forces a
prepare beat in front — corrected 2026-07-15):

. **(sow-and-graft beat) the instance is PREPARED** — the host sows the incus scion,
  which in-container: builds/caches the image, grafts the manifests material into the
  staging slot (incl. the nocloud transcode), publishes `HostStagingEntry`, then
  PROMOTES (`jsync staging → host.live.d`, Family 4 delta #9) and publishes the
  live/drift entries. It produces `IncusHarvest` (recipe digest + soil) — the request
  the host fetches. No VM yet.
. **(pure-host beat) the instance GROWS** — the host fetches ONE immutable
  `InstanceGrowPlan` (network view + image view + cloudInitChecksum — assembled and
  stored by the scion at PREPARE's end, in the `incus-ingress-contract` `type=dual-realm`
  module), declares the resource graph (Project/Network/Profile/Image/Instance) and the
  Pulumi engine drives the Incus provider over gRPC to create the VM with `running=true`,
  binding the 13 mounts (delta #8) onto the already-promoted `host.live.d`. Pure-host
  register, like `Cellar.fetch` — no metier, no sow. The host does ONLY `com.pulumi` +
  provider invokes (reuse-lookup, import-lookup); it COMPUTES nothing of the domain — the
  scion projected every value (blueprint-derived NIC/dnsmasq, buildChecksum, checksums)
  into the plan (§ link:../osgi/host-cellar-realisation-spec.adoc#the-grow-anatomy[host-cellar,
  the scion-projects/host-actualises rule]). MUST come after PREPARE (the mount rule).
. **(sow-and-graft beat) the instance is VERIFIED** — the host sow-and-grafts the incus
  scion, which probes reachability in-container (the VM now runs) and grafts its verdict.

This keeps the map's regularity honest: every root step is *pure-host gardening* OR a
*sow-and-graft caller*. PREPARE and VERIFY are sow-and-graft; GROW is pure-host. The
map's current single "the instance is provisioned (incus) — sow-and-graft" line splits
into these THREE, ordered by the mount (prepare+promote → grow → verify) — not into two
free beats. It does trade "one domain = one root line" for correctness; incus is now two
sow-and-graft callers bracketing one pure-host beat.

NOTE: *verify is a DISTINCT root beat after grow, not the tail of prepare* — the
reachability probe needs the VM running, which only happens in the grow beat. The scion
today (`IncusProvisionScenario`) fuses prepare-material + probe in one scenario; the
split pulls the probe out to run post-grow.

== The host-asset materialization service (SUPERSEDED by the NixOS substrate)

[WARNING]
====
*This section is design rationale, NOT the shipped shape.* None of the types below —
`BootstrapHostAssetMaterializer`, `HostAssetProvider`, `HostAssetContribution`, `HostAssetSlot`,
`HostAssetEntry`, `HostAssetDeliveryKind`, the `CloudConfig`/`EnvConfig`/`SystemdBundle` providers —
exist in the code. The declarative NixOS substrate dissolved the whole materialise-into-`/srv/host`
apparatus (see the top-of-doc re-baseline and the paragraph at the end of this section). Kept as the
record of the design the substrate replaced.
====

[NOTE]
====
*Terminology — "host" is overloaded (a known naming debt).* It carries three senses in this
codebase: (1) the *host world* — the machine running Pulumi, the realm OUTSIDE Felix (the
host↔OSGi membrane, `InstanceGrow`'s "pure-host GROW"); (2) the *control node* — the RKE2
node being provisioned; (3) `/srv/host` — that node's base filesystem (vs its containers),
whence `HostPathCatalog`, `host-tree`, `BootstrapPaths`. The `HostAsset*` types here mean
sense (3): assets materialised into the node's `/srv/host` tree — aligned with the existing
`HostPathCatalog` convention. The collision is chiefly (1) vs (3): the materializer RUNS in the
host world yet WRITES to the node's `/srv/host`. A codebase-wide disambiguation is a separate
pass; the name `HostAsset*` is kept to stay consistent with `HostPathCatalog`/`host-tree`.
====

Family 2's materializations share ONE dropped mechanism: main's
`IncusResourceBootstrap.materializeAssets()` populated the staging roots BEFORE the
mounts; the migration to `InstanceGrow` (mounts-only) re-added only nocloud's writer.
The settled replacement makes the formerly IMPLICIT incus↔manifests coupling — manifests
wrote files by convention, incus read them back blind through a generic YAML parse — an
EXPLICIT, typed, enumerable *contribution*: a missing asset is now a missing provider, not
a silent gap. It is a contribution, NOT a manifests _policy_ (a policy activates a common
logic across units, e.g. `ManifestDomainPolicy`; this is manifests contributing resources
to incus). Split by realm:

* *incus DRIVES* — `BootstrapHostAssetMaterializer` (an SCR `@Component` in `incus-core`)
  realises a requirement of provisioning the instance: it `@Reference(MULTIPLE)` the
  providers, maps each `HostAssetSlot` to the `BootstrapPaths` root it owns, and applies
  the transform-and-place strategy. The instance's boot format (the NoCloud seed
  filenames) lives HERE — incus knows the instance's need. This is the FIRST explicit
  incus→`manifests-contract` type coupling (the content still crosses as raw bytes; no
  manifests IMPL coupling).
* *manifests PROVIDES* — `HostAssetProvider` (SPI in `manifests-contract`) reads its own
  synthesised slice under the manifests root (`manifests` owns the `runtime/…` sub-layout,
  incus owns the mount-root name) and returns a list of `HostAssetContribution`: each a
  `HostAssetSlot` + a `HostAssetDeliveryKind` + a list of `HostAssetEntry` (relativePath +
  RAW content) + a per-contribution `executable` flag the DOMAIN declares (a systemd script
  must run, a unit file must not — incus never infers it from the slot) + a `targetFile`
  naming the single output of the fan-in kind. A provider may yield several — the systemd
  bundle contributes one per slot.

`HostAssetDeliveryKind` names the transform incus applies (every host asset is a synthesised
ConfigMap the materializer extracts — no raw files in the tree): `SEED_DIR` strips the
ConfigMap/Secret envelope and writes the NoCloud files (absorbing the former
`NocloudSeedWriter`); `SHELL_ENV_FILE` extracts the env vars and emits ONE `set -a`…`set +a`
shell file the boot sources — closing the env read-gap (the sections synthesise as hidden
dotfiles the loader's visible-`*.yml` glob missed); `CONFIGMAP_FILES` extracts each ConfigMap
`data` key back to its own file under the slot root (executable when the contribution
declares it) — the systemd bundle.

The bootstrap host-asset providers that once delivered `/srv/host` assets — CloudConfig, EnvConfig,
and the systemd bundle (units + scripts carried as local-config ConfigMap dotfiles, materialised
disk-to-disk on the node) — were *dissolved* when the node moved to a declarative NixOS substrate:
its config, systemd units and scripts are baked by the `nixos/` modules
(link:../nixos-substrate/substrate-model.adoc[target vision]), not synthesised and materialised as
host assets. The DAEMONSET path
(link:../patterns/daemonset-host-assets-architecture.adoc[daemonset-host-assets],
`daemonset-host-asset-materializer.sh`, flox) survives — it brings the flox runtime to the host VIA
THE CLUSTER, an entirely separate in-cluster delivery channel.
