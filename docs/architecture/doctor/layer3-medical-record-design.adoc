[NOTE]
.OSGi re-baseline — read the write-side mechanism through this
====
The *guiding principle* below is unchanged and correct: Pulumi is the authority on what it already
knows (the graph in stack state, the when/git/config in the update history); the medical record
persists ONLY the diagnostic delta Pulumi ignores (`Symptom` / `Observation` / `RemediationPlan`),
per checkpoint. What migrated is *where the delta is filed*:

* As-built, the per-node diagnostic layer is filed into the *host `Cellar` / journal* as a neutral
  `visit` blob (`SeedCodec.toMap`), NOT as a design-time `registerOutputs` output on a Pulumi
  `ComponentResource`. It is read back OSGi-side, codec-based, by `doctor-core`'s
  `MedicalRecordReader` (`SeedCodec.fromMap`). `Observation` / `ConsultationReport` are
  `doctor-contract` records with no `toOutputMap()`.
* The `Checkpoint` enum (the join key, identity-only) shipped in `doctor-contract`.
* The pre-OSGi types this doc names — `OutputBuilder`, `VerificationResult`, `ClusterReadinessResource`
  / `SystemdAdapterResource`, `ResourceCreationPipeline` — do NOT exist in the OSGi build; the readiness
  verdict is `ReadinessVerdict` folded by `DefaultReadinessAuthority`, and the host Pulumi bind lives in
  `pulumi-edge`. The seed-outcluster source links below are pre-OSGi and no longer resolve.
====

== The problem, as previously framed

Layer 3 makes the *medical record* (one per patient-stack) OUR aggregate and the SOURCE; the runbook
and `VerificationResult` become VIEWS. The locked decision was to *serialize the WHOLE record —
plans included — into the stack outputs* for "100% faithful reconstruction from state alone", behind
a new additive top-level `medicalRecord` output key.

That framing carried a *hard problem*: the *phantom diff*. `OutputBuilder` deliberately omits
`timestamp` (link:../../../seed-outcluster/src/main/java/io/seedmatic/rke2lab/controlplane/pipeline/OutputBuilder.java[OutputBuilder.java]
lines 37-46) because "it would change every run and produce phantom output diffs on no-op pulumi
up". A full record carries admission (timestamp, git) → re-introduces exactly that phantom diff. The
parade (exclude the timestamp) tensions with "100% faithful".

== The recadrage — Pulumi already holds most of the record

The phantom-diff-vs-100%-faithful dilemma was a *false dilemma*. It assumed "serialize everything".
Pulumi already maintains two authoritative memories, and the record must duplicate *neither*:

[cols="1,2,2",options="header"]
|===
|Dimension |Pulumi's authoritative memory |Therefore the record…
|Dependency graph (`dependencies`, `parent`) |*State* (`pulumi stack export`) — reconstructible offline |never serializes edges
|The "when" + git commit + run config |*Update history* (one timestamped entry per `up`) |never serializes timestamp/git
|Diagnostic semantics (`Symptom`, `Observation`, `RemediationPlan`) |*Pulumi knows nothing of these* |serializes ONLY this
|===

*Guiding principle:* **Pulumi is the authority on everything Pulumi already knows; the medical
record persists only what Pulumi ignores — the diagnostic layer, grafted per node.**

Consequences, each answering a tension:

. *Phantom diff → dissolved.* No `timestamp` in our outputs (it lives in the update history). The
  diagnostic data is *deterministic at constant state* → a no-op `up` shows no output diff.
. *Drift → dissolved.* We copy neither the graph nor the history. Post-hoc reconstruction reads the
  Pulumi state and *grafts* our layer onto it.
. *"100% faithful" → redefined.* Fidelity = `Pulumi state (graph + history) ⋈ diagnostic layer`. It
  comes from the *join*, not from a self-sufficient blob.

=== A note on `pulumi refresh`

`refresh` reconciles the *body of the patient* (provisioned resources — it runs each provider's
`Read` against the real world). It does NOT reconcile the *consultation* (symptoms/observation/plan):
those are *events* produced by running a probe at an instant, not a current external state to
re-read. Re-observing is a `pulumi up` (the probes re-run), not a `refresh`. This is the same reason
Option B (provider-backed `CustomResource`) was rejected (commit a949f3bb): there is no managed
external state for a provider `Read` to reconstruct. So the medical record is *append-only* (visits
are added), never refresh-reconciled.

== The single-source edge

The "state holds the graph" principle is only tenable if the business edge *is actually in the
state*. Today it is NOT:

* The two checkpoint resources are *siblings* under a common parent — both receive
  `bootstrapResult.readinessDependency()` as their `dependsOn`
  (link:../../../seed-outcluster/src/main/java/io/seedmatic/rke2lab/controlplane/resources/ResourceCreationPipeline.java[ResourceCreationPipeline.java]
  lines 120, 131). The cluster resource does NOT depend on the systemd-adapter resource.
* The cluster→systemd-adapter edge lives only in the *BDD nesting* (`@NestedSteps` /
  `.depending_on_systemd_adapter(...)`).

⇒ the resource graph and the runbook graph are *not the same graph*. The edge is declared in the
wrong place (a render view), and absent from the authority (the state).

*Correction (validated):* `ClusterReadinessResource` must really `dependsOn` `SystemdAdapterResource`.
The only wiring change is in `withReadiness()`: pass `this.systemdAdapter` instead of
`bootstrapResult.readinessDependency()`. *Verified safe* — the eager scenario play is ordered by the
builder (`withSystemdAdapter()` precedes `withReadiness()`), NOT by `dependsOn`; the edge affects
only the persisted graph. The `@NestedSteps` nesting then becomes a *render view*, no longer the
*source* of the edge. The edge is declared *once*, in the resource, and read back from the state by
BOTH the runbook and the medical record.

== The join key — a `Checkpoint` enum

Two vocabularies are implicitly aligned today, with nothing guaranteeing the correspondence:

[cols="1,1,1",options="header"]
|===
|Side |Identifier |Value
|Diagnostic (BDD) |`ConsultationReport.checkpointId` ← `SCENARIO_ID` |`"cluster-readiness"`
|Pulumi (→ URN) |the `name` ctor arg |`"seed-cluster-readiness"`
|===

`"cluster-readiness"` ↔ `"seed-cluster-readiness"` is a hand-maintained alignment — exactly the
`clusterApi`/`cluster-api` silent-failure pattern the project CLAUDE.md documents at length. We apply
the project's "single source of truth for identifiers" discipline, *as an enum* (the set of
checkpoints is finite and closed → closing it at compile time is the invariant we want; same idiom as
the config `InfraDomain` enum). The enum's shape is in the UML class diagram below.

One source — the `slug`; the resource name is *derived* from it (`"seed-" + slug`), so the
correspondence is *structural*, not hand-maintained. Both sides consume the enum: the stage's
scenario id becomes the enum's `slug()`; the resource wiring's literal becomes its `resourceName()`.

*The enum carries identity, NEVER topology.* It does NOT encode `CLUSTER_READINESS dependsOn
SYSTEMD_ADAPTER` — that edge lives in the resource's `dependsOn` (the single source, read from
state). Putting it in the enum too would recreate the very duplication we are removing. (Rule-of-three
note: the enum has 2 entries today; its justification is *invariant correctness* — the join key must
be guaranteed, not hand-aligned — not "3 cases".)

== The serialization — per-node, strict

*Placement — per node, on the existing `registerOutputs` (not a top-level blob).* A top-level
aggregated `medicalRecord` key would itself be a *copy of the structure* (it aggregates nodes +
order) → the drift we just removed. Instead, per Option A (the resolved Pulumi fork), each checkpoint
`ComponentResource` registers an *additive* output carrying ITS own consultation report:

* `ClusterReadinessResource` today receives only the `VerificationResult`; it ALSO receives the
  `Optional<ConsultationReport>`, registered as an additive output via `toOutputMap()`.
* same for `SystemdAdapterResource`.

*Effect on the guard:* the stack's *top-level* outputs (what `OutputBuilder` builds) stay
*literally unchanged* — the Stage-B contract is not touched at all. The diagnostic data lives *under*
the checkpoint's `ComponentResource` in the state, indexed by `Checkpoint.slug()`. This is the
*per-node strict* choice (validated) — no top-level aggregate, no structure copy.

*What is serialized — the diagnostic layer only.* `ConsultationReport(checkpointId, observations, plan)`:
`Observation` already has `toOutputMap()`; `Symptom` is an enum (`name()`); only `RemediationPlan` /
`Prescription` need a serialized form (a concrete sub-task, no blocker). A healthy checkpoint raises
no symptom → the output is absent/empty → deterministic at constant state → no phantom diff, no
timestamp anywhere.

== Reconstruction — the join

. `pulumi stack export` → read the resources of our type tokens
  (`rke2lab:controlplane:ClusterReadiness`, `:SystemdAdapter`).
. Build the DAG from their `dependencies` array (the cluster→systemd edge is *really there* now,
  thanks to the single-source edge).
. Graft each node's `consultationReport` output, joined by `Checkpoint.slug()`.
. Render the runbook from this reconstructed model.

== Runtime vs post-hoc — the two moments

* *Runtime* (during `up`): the state is not yet written and checkpoints play eager → the runbook
  renders from the *in-memory model* (the already-wired `ConsultationLog` + the graph the code knows,
  having just declared it). Unchanged from today.
* *Post-hoc* (after the run): reconstruction from the state (above).
* *Correctness criterion:* both paths produce *the same view*. That equality is the test proving
  there is no drift.

== Scope — what this increment does NOT do

* `VerificationResult` stays as-is (the always-present Stage-B handoff projection; already in the
  guard's "unchanged" list). It is NOT merged with the consultation report — layer 2 proved they are
  two distinct aggregates.
* The full "our model = source" renderer rewrite: the TDD entry point is flipping
  `RunbookRenderingTest`'s assertion ("no Diagnosis/Mitigation before the doctor exists"). Noted; we
  do NOT rewrite the JGiven renderer wholesale here.
* Opening `Symptom`/`Specialty`/routing into contributed data (the module-extraction
  chantier) — unchanged from the spec's deferral.

== What this changes vs the locked decisions (spec Increment E)

[cols="1,2,2",options="header"]
|===
|Decision |Previously locked |Recadred here
|Serialization target |WHOLE record, top-level `medicalRecord` key |diagnostic layer ONLY, per-node on each `registerOutputs`
|Edges |part of the serialized record |NOT serialized — read from the resource `dependsOn` in state
|Admission (timestamp/git) |serialized for 100% fidelity |NOT serialized — read from Pulumi update history
|Phantom diff |"hard problem to solve first" |dissolved (nothing varying is serialized)
|Top-level guard |renegotiated (new additive key) |*untouched* — top-level outputs literally unchanged
|Join key |implicit |explicit `Checkpoint` enum (identity only)
|===

== Open / deferred (unchanged from spec)

T2 (stateless doctor vs panel), T3 (routing contributed), T4 (context = visit vs patient) remain
deferred until a first working doctor version is in place. The renderer-route fork is folded into the
"our model = source" direction (JGiven as one backend).
