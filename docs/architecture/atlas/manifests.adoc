== Manifests subsystem — per-subsystem view

The fifth subsystem to adopt the ritual, and the FIRST brought in by the design-state coverage pass
(2026-06-21). The four views above are the OSGi-centric heart of the system; this pass folds in the
rest of the design, subsystem by subsystem, manifests first as the exemplar. Unlike unitrepo, manifests
is almost entirely SHIPPED — it is the CDK8s synthesis layer that has run in production for months. Its
design state is therefore an all-blue base — the unit-lifecycle cleanup (the last green target) has since shipped too. The
full design is link:../manifests/manifests-architecture.adoc[the manifests architecture]; this view holds
the inventory, the additivity proof, the capability map, and the scenario map.

The load-bearing seam this view makes explicit: manifests does NOT own a resolver — it is the first and
shipped CONSUMER of the same Felix `UnitResolver` the unitrepo view owns. The `ManifestsUniverse` /
`CoherentManifestsDomainRegistry` boxes appear in both views; here they are read as "manifests resolves
its units", there as "the resolution oracle generalises to any unit". One box, two readings — the
convergence unitrepo's verdict already named (a `ManifestsUnit` is the first concrete unit).

| ✅ Shipped (blue)

=== Verdict — does it hold?

. *Monotone: yes.* No box from the four prior views is erased or rewired. The shared `UnitResolver` /
  `ManifestsUniverse` / `CoherentManifestsDomainRegistry` boxes are read here as "manifests resolves its
  units" without changing them — the same boxes the unitrepo view reads as the general oracle. The
  manifests-specific boxes are additions.

. *All blue.* Unlike the other views, manifests is shipped-in-bulk: all nine boxes are blue — the
  unit-lifecycle cleanup (plain objects + `doSynthesize`) has since shipped, closing the last design
  target. There is no amber — manifests has no exploration horizon, it is a settled subsystem.

. *Two shared boxes are named, not redrawn.* `ManifestSynthesisContext` (identity threading) is the same
  box the bootstrap view's identity provider will read; the `UnitResolver` trio is the unitrepo view's.
  Naming them shared — rather than drawing manifests-local copies — is what keeps the merge monotone.

. *The convergence is earned.* unitrepo's verdict already claimed "a `ManifestsUnit` is the first concrete
  unit"; this view is the other end of that claim, reached from the manifests side. The resolver was built
  FOR manifests and generalised INTO unitrepo — the shared boxes are the proof, not an assertion.

Conclusion: the constellation holds; manifests is additive, and now entirely blue.

=== Design scenarios — the nine capabilities as DSL sentences

The third movement (see <<the-scenario-map>>). All nine playable-and-blue (the shipped synthesis layer —
the richest playable surface after the runtime view).

. *Manifests synthesise from typed units, not hand-written YAML* — `[playable]` blue +
.. GIVEN raw Kubernetes YAML hand-authored per resource
.. WHEN `ManifestsUnit` + CDK8s `Chart` express each resource as typed Java
.. THEN manifests synthesise from typed units — AND the YAML is generated, never hand-edited.


. *Units resolve into a coherent visit-order in one gate* — `[playable]` blue +
.. GIVEN units with inter-unit and cross-domain dependencies
.. WHEN `ManifestsUniverse` expresses them as `UnitResource`s and the `UnitResolver` resolves them
.. THEN units resolve into a topological visit-order — producer-before-consumer, cycles rejected, missing
   deps reported, cross-domain rules enforced — in ONE coherence gate (`resolve()`) — AND this is the same
   resolver box the unitrepo view owns, shared not duplicated.

. *Domain IDs come from one catalog, no magic strings* — `[playable]` blue +
.. GIVEN domain IDs hardcoded as string literals (the kebab/camel mismatch bug class)
.. WHEN `ManifestDomainCatalog` accessors become the only source
.. THEN domain IDs come from one catalog — AND a typo is a compile error, not a silent policy miss.

. *Optional units are included by policy at synthesis* — `[playable]` blue +
.. GIVEN a fixed set of units always synthesised
.. WHEN the manifests domain policy (derived by the scion from its facet) gates optional units/layers at synthesis time
.. THEN optional units are included by policy — AND ephemeral runs skip synthesis via the
   `BootstrapIdentity.UNKNOWN` guard, nothing else rewired.

. *Output explodes per-domain and applies with no kubectl* — `[playable]` blue +
.. GIVEN one consolidated YAML stream
.. WHEN `ManifestExploder` splits it per-domain by annotation and RKE2 auto-deploy applies it
.. THEN output explodes per-domain and applies with no kubectl — AND `local-config` excludes the
   non-deployed resources.

. *Synthesis defers to the provider to read runtime Outputs* — `[playable]` blue +
.. GIVEN synthesis running before Pulumi Outputs resolve
.. WHEN it defers to the provider stage via `Output.applyValue`
.. THEN synthesis reads runtime Outputs (image fingerprints) — AND this is the seam the cluster-api
   staged-post-cluster pattern extends, additive.

. *Synthesis reads identity by context, not constructor params* — `[playable]` blue +
.. GIVEN units that would need cluster/node identity passed through every constructor
.. WHEN `ManifestSynthesisContext` threads it via ThreadLocal
.. THEN synthesis reads identity by context — AND the same context box the bootstrap identity provider
   owns is read here, shared not copied.

. *A unit binds its scope at synthesis, no `lazy()` factory* — `[playable]` blue +
.. GIVEN units wrapped in a `lazy()` factory to defer CDK8s scope binding
.. WHEN the unit-lifecycle cleanup makes units plain objects with `apply(ManifestsUnitContext)` over a `doSynthesize(Construct, ManifestsUnitContext)` hook
.. THEN a unit binds its scope at synthesis with no `lazy()` workaround, group-markers emitted uniformly
   from the base hook — AND the change is internal to the unit model, the synthesis seam unchanged.

*Coverage of this view:* 9 capabilities, 9 scenarios — complete per <<scenario-completeness>>. All nine
playable-and-blue (the shipped synthesis layer, the lifecycle cleanup now landed).

=== Diagram N — the contribution seam: how a domain feeds the synthesis

The nine capabilities above are what the synthesis DOES. This is what feeds it: a domain never writes
into the synthesis directly — it publishes a CONTRIBUTION (a set of CDK8s constructs) and the synthesis
aggregates. There were once THREE typed channels (manifest units, node-env env sections, host-assets);
the node-env and host-asset channels were *dissolved* into the declarative NixOS node substrate,
leaving the unit channel. Full detail:
link:../manifests/manifests-contribution-channels.adoc[the contribution channels spec].

  classDef neu fill:#dfd,stroke:#2a2,stroke-width:2px;

*The completed migration.* The unit channel was once the static laggard — a hand-maintained
`register(new XxxRegistrar())` chain. It has since been aligned on the SCR contribution *shape* the
node-env and host-asset channels pioneered before they were dissolved: `ManifestsDomainRegistrar` is an
SCR `@Component` keyed by `domainId`, collected by `DefaultManifestSynthesisService` via
`@Reference(MULTIPLE)`, and the static chain is erased. The shape outlived the two channels that first
carried it.

=== Diagram O — additivity: the delivery loop closes (grow → publish → PaC)

Diagrams M/N are what the synthesis produces + how it is fed. This is what carries the OUTPUT to the
cluster, and how it re-renders itself. The render+push OPERATION is one thing (the OSGi
`ghapp`→`auth`→`manifests` scion graph); what changes is the HOST that sows it. Monotone: the grow
lane is the shipped base (blue), the standalone `publish` verb is shipped (blue), the in-cluster PaC
lane is the target (green). Full detail:
link:../cluster-api/pac-in-cluster-render-spec.adoc[the PaC in-cluster render spec].

*What holds.* The operation is realm-neutral (it never knows its host) — the same coordinates sown
under a Pulumi grow, a standalone CLI, or a PaC PipelineRun. The push identity is uniform (the baked
GitHub App) across all three; only the token's provenance is host-specific, resolved by the
`ExecutionEnvironment` instance from the `ExecutionEnclosure` FACT (OPERATOR mints via `.secrets`;
IN_CLUSTER consumes PaC's `git_auth`).
The render is now secret-FULL in-cluster (the git-sops chantier). Both pipeline containers run on the
flox-carrier runtime (`prodImage()`, no stock image) and opt into the `toolchains/git-sops` flox env
(`environment.step-clone` + `environment.step-render`); the env makes the checkout secret-full by two
mechanisms from one annotation — its `[hook.on-activate]` wires the ndh `sops-yaml` git filter GLOBALLY
(so the clone smudges `.secrets` at checkout, in-cluster as on the host), and its `spec.inject`
contributes `SOPS_AGE_KEY` from the replicated cluster age key (the flox-controller webhook adds it, no
hand-wired Task env). So the `SecretsGateway` is a `DotSecretsGateway` over the smudged `.secrets` (the
`EmptySecretsGateway` was removed). Real-data secrets ride the branch sops-encrypted (Flux decrypts on
reconcile); the durable-minted materials not in `.secrets` (incus-identity, workload CAs) ride a sops
branch cellar asset the render rehydrates. See
link:../patterns/flox-store-resolved-runtime-and-builder.adoc#flox-runtime-universal-base[the
flox-runtime base + `spec.inject` capability].

The render *configuration* is uniform the same way, and recorded in the branch. The facet (which
layers publish, `delivery`) has one authoring source — the Pulumi stack, read at the grow — and the
render writes it back as a native-YAML `manifest.yaml` doc at the ROOT of `manifests/<cluster>`
(carrying `source:{sha,dirty}` provenance + the effective `facet:`, NOT a ConfigMap — it sits outside
every Flux Kustomization path so nothing applies it, and deterministic serialisation keeps the
empty-commit guard's fixpoint). The in-cluster lane READS that manifest at branch HEAD (the wrapper's
`git show manifests/<cluster>:manifest.yaml | yq .facet`), so it renders exactly what the last grow
decided (not a hardcoded CLI default that would diverge — e.g. drop
`mesh`), and the branch is self-describing. The grow
is the authority; the in-cluster render is its faithful continuation; the Pipeline stays generic (a
`facet` param overrides only to intentionally drift). See
link:../cluster-api/pac-in-cluster-render-spec.adoc#render-config[the facet-follows-the-grow section].
