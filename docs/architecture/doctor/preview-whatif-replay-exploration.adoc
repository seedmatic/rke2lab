[#the-solution]
== ★ THE SOLUTION — the self-referential medical-record accumulator (the landing)

[IMPORTANT]
====
The whole thread converged here, and this is *simpler* than every intermediate option (the two-jar
wrapper, the FIFO handoff, the inception read — all superseded). The patient record is *carried
forward in a top-level stack output*: each run *pre-initializes its output with the previous record*
(read via a self-`StackReference`), *appends* this run's consultations, and *re-exports* it. No
wrapper on the normal path, no lock problem, one process. It is an *exploration conclusion*, not a
spec.
====

*The one-line idea (the user's):* `ctx.export("medicalRecord", previous ⊕ this-run)`. The output
*is* the patient record; it persists itself and re-seeds the next run.

*The mechanism — read your own last output, append, re-export.*

. *Recover the previous record.* A *self-`StackReference`* (the stack referencing itself) reads
  `output("medicalRecord")` — the record exported by the last `up`. This is a *native Read handled by
  the Pulumi engine*, NOT a self-`exportStack` shelled under the run's own lock — so there is *no lock
  problem*, and (proven by the throwaway-stack test) it resolves to *known values in preview as well
  as up*.
. *Pre-initialize the new output with it.* The run's `medicalRecord` *starts* as the previous one.
. *Append this run's consultations* (the in-memory `ConsultationLog`, produced by the diagnostic
  sweep), and *summarize the old ones* beyond a window (retention; see below).
. *Re-export.* `ctx.export("medicalRecord", accumulated)` persists it into this run's state — which
  becomes the *previous* the next run reads. The export is *both ends of the cycle*: it recovers (the
  next run's `StackReference` reads it) and it persists (this run writes it).

*Why this is the landing:*

* *Lock — gone, not "solved".* The recovery read is a native engine `StackReference` Read, not a
  shelled `exportStack`; nothing contends the lock. (This is why it beats the wrapper — no second
  process, no off-lock choreography.)
* *Patient record — delivered as a first-class output.* It is *top-level*, so a self-`StackReference`
  can read it back (verified: `StackReference.outputs()` returns the full top-level map,
  `output(name)` keys into it; see <<read-mechanics>>). It is *longitudinal* because each run carries
  the previous record forward — the time axis lives *in the output*, not in fragile history/checkpoint
  reconstruction (history keeps only ~5 full checkpoints; this does not depend on that).
* *Placement — RESOLVED by design, not renegotiated.* The record is top-level *on purpose*
  (`ctx.export`), because that is the only channel `StackReference` reads. The per-node
  `consultationReport` (shipped recadrage) is *untouched* — it stays the runbook read-side source; the
  top-level `medicalRecord` is *additive*, a different role.
* *Mono-process, seed-outcluster only.* No wrapper, no FIFO, no config-mode handoff. All inside the
  existing program.

*Working state vs. archive — two cycles, flush at the end (the user's refinement).* The run's
*in-flight* consultations are NOT the archive. They live as *working state*: the in-memory
`ConsultationLog` and its parallel per-node `consultationReport` (`registerOutputs`) — *not*
`ctx.export`-ed (proven: the per-node persists without export, and is invisible to `StackReference`).
The *archive* — the top-level `medicalRecord` — is written *once, at the end*, by *flushing* the run's
log into it. This is not merely cleaner, it is the *only* shape Pulumi allows: `ctx.export` is
*declarative* (one final value per output, no incremental append) — so "accumulate in the export" is
mechanically impossible; collect in memory, flush once. The flush reads its inputs from the in-memory
log ⊕ the previous record (self-`StackReference`), *never* from the program's own per-node (a program
cannot read its own per-node mid-run — proven `<null>`). The per-node stays a parallel mirror (runbook
read-side + diff), not the flush input. The flush is also *the curation point*: append + summarize
happens here.

*Retention — append + summarize (the user's choice).* Unbounded append would grow the output without
limit. Policy: keep the last N visits verbatim, and *summarize* older ones (e.g. "symptom X recurred
5× between t1–t2") — applied *at the flush*. This bounds the state AND feeds the longitudinal-pattern
need — the very case-history a rules-backed specialist wants (see <<rules-engine-correlation>>).

*Honest note on diffs.* The `medicalRecord` output changes whenever a new consultation is recorded —
but that is a *real, meaningful* change (a genuine new visit), NOT the phantom diff `OutputBuilder`
avoids (a `timestamp` that churns for nothing). A no-symptom run records no new consultation → no
change → no diff. Bounded by the retention summary.

*The wrapper / `exportStack` — DEMOTED to a recovery script.* The Automation-API path
(`LocalWorkspace.exportStack()` reading the per-node `consultationReport`s + `getHistory()`) is *no
longer the normal path*. It survives only as an *offline recovery tool*: if the top-level
`medicalRecord` is ever lost, rebuild it from the per-node state + history. Verified available
(`com.pulumi:pulumi` 1.28.0, see <<read-mechanics>> NOTE) — kept for that fallback, not the cycle.

*Grounded references:* `StackReference.outputs() : Output<Map<String,Object>>` and `output(String) :
Output<?>` (top-level map, keyed by output name — verified on source L98/L118); `Context.export(name,
value)` (top-level export); the self-reference-resolves-in-preview test (<<read-mechanics>>); the
in-memory `ConsultationLog` as the append source (`RunbookRenderer` already consumes it in the
caller-owned `finally`).

== What the system does TODAY (grounded in the code)

* *The checkpoint plays a JGiven scenario.* `SystemdAdapterStage.launch()` /
  `ClusterReadinessStage.launch()` create a `Scenario`, run Given/When/Then, `finished()`. The same
  scenario runs offline (tests) and live (the stage).
* *The `When` does NOT probe inline — it calls an injected `probe`.* The stage already injects
  *different* probe implementations:
+
[cols="2,2,3",options="header"]
|===
|Probe source |When |What the `When` reads
|`ProductionClusterReadinessProbe` |apply (`up`) |the *live* infra
|`SimulatedSystemdAdapterProbe` |preview + ordered incident |a *canned* failure
|_(body skipped — dry-run)_ |normal preview |*nothing* → `deferred-preview`
|===
* *Normal preview renders an empty shell.* In preview the stage sets `jgiven.report.dry-run=true`,
  which skips step *bodies* but still plays the scenario so the *shell* renders. No probe runs → no
  observation → `deferredPreview`.
* *The dependency edge is a gated nested replay.* `ClusterReadinessScenario` replays the
  systemd-adapter Given/When/Then via `@NestedSteps`; the nested probe re-emits the *already-captured*
  systemd-adapter dossier, and the step `the_systemd_adapter_dependency_is_satisfied` is the *gate*.
  When the upstream is down, that step throws and the downstream cluster phases are SKIPPED
  (fail-fast along the edge) — "downstream unobservable if upstream fails".
* *`simulate` already bends dry-run in one direction.* A preview-only `policy.preview.simulate` map
  *closes* a gate: it injects an upstream *failure* (a typed symptom) so the incident renders without
  touching infra; downstream goes SKIPPED. The what-if is the *mirror* of this (see <<mirror>>).
* *Today's graph is 2 linear nodes.* `Checkpoint` = `SYSTEMD_ADAPTER → CLUSTER_READINESS`. The
  checkpoints are played in a *hard-coded order* by the pipeline; topology lives in the resources'
  `dependsOn` edges (single source since commit `13bb7715`), *not* read as data by the orchestrator.
  Linear order == topological order *by accident* (see <<dag-tension>>).

[#patient-record]
== The model — observation vs. consultation vs. patient record

The user's terminology correction exposes a naming collision worth naming.

* *`Dossier` is NOT the patient record.* Its own javadoc calls it "the captured snapshot a readiness
  probe produces" — the *day's clinical observations / reason for consultation*: `status`, `symptom`
  (typed, never parsed), `summary`, `details`. Produced by the probe.
* *`ConsultationReport` is one visit's record:* the dossiers raised + the `RemediationPlan` (the
  diagnosed `Symptom` + the `Prescription`s + a generalist summary). Produced only on a raised
  symptom.
* *The patient record (the layer-3 medical record) is the longitudinal whole:* observations ⊕
  diagnosis ⊕ prescriptions-and-why, accumulated per patient across visits. The *runbook* is its
  materialization.

[cols="1,2,2",options="header"]
|===
|Concept |Code object today |What it holds
|Reason for consultation |`Dossier` |status, symptom, summary, details (observed)
|One visit |`ConsultationReport` |dossiers + diagnosis + prescriptions
|Patient record (longitudinal) |`ConsultationLog` → runbook |all visits, observed ⊕ diagnosed ⊕ prescribed
|===

*Consequence for the what-if.* The patient record the operator wants to read is *not* the raw
snapshot — it is observations ⊕ diagnosis ⊕ prescriptions. That is exactly what makes the
*prescription carry its own expected-state* (see <<closed-loop>>): a prescription that predicts its
success condition is what makes it *simulable*, and "the record includes the prescriptions and why".

The first session's blocker assumed the what-if must *read back* a previously-persisted diagnostic

[#mirror]
== The what-if is the mirror of `simulate`

The mechanism is not new code so much as the *inverse* of one that ships. `simulate` *closes* a gate
(inject failure); the what-if *opens* one (inject the prescription's expected success-state). The
user's framing: do not *predict* downstream — *reopen the gate and let dry-run walk the path it
already knows how to walk, and see where it leads.* Reachability is therefore not a chosen policy; it
is what dry-run *naturally* yields (it walks structure, it does not probe results) — honest by
construction.

[cols="1,2,2",options="header"]
|===
|Aspect |`simulate` (ships) |what-if (new)
|Injects upstream |a *failure* (typed symptom) |a *success* (the expected-state)
|Effect on the gate |*closes* it |*opens* it
|Downstream in dry-run |SKIPPED (fail-fast) |WALKABLE (made reachable)
|Scope |preview-only |preview-only
|Severity |can abort the apply (CRITICAL) |*never* aborts anything (it is an opening)
|===

[#closed-loop]
== The generalist as a closed-loop planner (the second session's keystone)

The user's keystone idea: the specialist addresses its prescription *to the generalist*; the
generalist *runs a simulation of the remediation*, which *unmasks new downstream symptoms*, and it
*re-consults the other specialists* on those. The generalist stops being a one-shot *router* and
becomes a forward-reasoning *planner*.

This reveals *two loops*, cleanly separated:

* *Inner loop — diagnostic, one preview, zero side effects.* observe → consult specialist →
  prescription (+ expected-state) → generalist *simulates* (opens the gate) → unmask downstream
  symptom → re-consult → … → complete multi-step plan.
* *Outer loop — execution, across visits (already in spec.adoc).* plan → operator administers → next
  `up` re-observes the *real* → back to observe. The CLAUDE.md "propose, don't execute" boundary holds
  structurally: the inner loop only *plans*.

.The two loops — inner plans (fast, speculative), outer validates against reality (slow, grounded)

The `expected-state` field added to `Prescription` is the hinge between the loops: it is what makes a
prescription *simulable*. The inner loop terminates because the graph is a *DAG* — a single
topological sweep opening gates as it goes, bounded by node count, not an unbounded fixpoint.

[#sweep]
== The sweep semantics (what the user's last three turns fixed)

The correction the user made: when a node fails for real, re-probing its *dependents* is pointless
(they would fail *because of* the root, not on their own merit). So that *downstream subtree* switches
to dry-run (reachability only). *But* independent *siblings* — other branches that do not depend on
the failing node — must still be probed *for real*, because the root's failure says nothing about
them. This is exactly the semantics of a real `pulumi up`: a failed resource blocks only its
*descendants*, never its *siblings*.

[cols="2,2,3",options="header"]
|===
|Node situation |Treatment |What it produces
|healthy |probed live, ok |nothing to remediate
|*fault root* (real failure) |probed live |symptom + prescription (+ expected-state)
|*descendant* of a fault root |*dry-run* (gate opened by hypothesis) |reachability — "unblocked once the root is fixed"; invents no symptom
|*sibling* (independent branch) |*probed live normally* |its own symptom + prescription, *in the same pass*
|===

.A branched DAG: descendants dry-run, siblings are still probed for real

....

Precise wording, to avoid a re-litigation: "reachable *from* the failing node" means its *descendants*
(follow outgoing edges), *not* "all remaining nodes". Siblings are not reachable from the failing node;
they are probed normally. A *single pass* over a branched DAG therefore yields a *complete* diagnosis —
fault roots with prescriptions, their descendants marked reachable-if-fixed, and independent branches
fully diagnosed — instead of fix-A → re-run → discover-B → fix → re-run.

[#treats]
== The specialist declares what it treats (inverted routing)

Today the symptom→specialist knowledge is *duplicated*: the generalist holds a hard-coded `switch`
(`routeBySymptom`: `CONNECTION_REFUSED → SYSTEMD, NETWORK`) *and* the specialist holds a guard
(`DbusTcpSpecialist`: `if symptom != CONNECTION_REFUSED return empty`). Two places encode "dbus treats
connection-refused" — exactly the single-source-of-truth violation CLAUDE.md forbids.

The user's inversion: the *specialist declares the symptoms it treats*; the generalist routes by
*asking* the specialists, not by consulting a table.

*Single authority — the practitioner (the user's refinement, aligned with the rules-engine doc's
clarification).* The competence has exactly *one owner*: the specialist itself *provides*
its set of symptoms. The `domain()` only *seeds* a *default repertoire* — the symptoms a specialist of
that specialty *can* treat — which the practitioner *inherits*; but the effective list is always the
practitioner's own, *adding* (sub-specialization) or *removing* (a procedure it does not perform). The
domain is the *seed, never a second source* that co-owns the answer. Exactly real medicine: the
specialty says what is treatable in the field; the individual practitioner declares what *they* treat.

[cols="2,3",options="header"]
|===
|Role |What it is
|`SpecialistDomain` (the specialty) |the *seed* — the default repertoire a practitioner of the domain inherits; *pre-fills*, never co-owns
|`Specialist` (the practitioner) |the *sole authority* — *provides* its own `treats()`, inheriting the default then adding / removing
|`treats()` |the set *the practitioner provides* — one owner, the routing key the Generalist asks
|===

*Why this is not "two sources".* It is stronger than both earlier readings. The *flat* form (this
doc's first cut) dropped the domain default entirely. The *two-source / computed* reading — composing
"the domain says X" with "the specialist re-says X" — would re-create the very synchronization the
deleted `switch` had. Neither happens: the domain *pre-fills*, the practitioner *owns*. The
single-source invariant holds because there is exactly *one owner* — not because a merge is "computed".

Three benefits chain into the rest of the model:

. *Single source of truth* — the competence lives where the treatment lives; the `switch` is deleted;
  the domain seeds a default, it does not co-own a second copy.
. *Recruitment trigger* (link:runbook-doctor.adoc[spec.adoc] `[#recruiting-a-specialist]`, memory
  `doctor-remediation-model`) — a symptom *no* practitioner's `treats()` covers is, by definition, the
  recruitment signal. The seed/owner split still refines *what* to recruit: a symptom no domain *can*
  treat = a *specialty gap* (recruit a new domain); a symptom the domain can treat but every
  practitioner *removed* = a *practitioner gap* (assign another specialist of that domain).
. *Closed-loop routing* — when the inner-loop simulation unmasks a downstream symptom, "which
  specialist?" resolves by asking each practitioner's `treats()`, not a table re-synced per node.

[#dag-tension]
== The one real architectural tension (DAG as data)

Everything above assumes *someone can walk the DAG as data* — decide "descendant or sibling?",
orchestrate the sweep, open the right gates. Today that is not possible:

* topology lives in the `dependsOn` edges of the Pulumi *ComponentResources* (single source since
  `13bb7715`);
* but checkpoints are played in a *hard-coded order* by the pipeline (`SystemdAdapterStage` *then*
  `ClusterReadinessStage`), *not* by walking a graph.

The 2-node linear graph has always masked this — hard-coded order happens to equal topological order.
The planner model *requires* topology to be data the orchestrator (the generalist, or a layer above it)
can traverse. This is *the* real work of the *planner*; the *placement* question turned out not to be a
blocker against the Automation API (it reads per-node directly — <<read-mechanics>>), though *where*
the doctor reads from (inception vs. external orchestrator) is its own open decision
(<<patient-record-longitudinal>>). DAG-as-data also rejoins memory `domain-registry-abstraction` (unify
the registry pairs once the rule-of-three is met). Not a blocker; the actual architecture to design.

This *is* the rules-engine doc's *Option ① (give `Checkpoint` topology)* — which that agent
*discarded* (pursuing only the specialist track). For a one-off refactor, discarding ① is defensible;
but the closed-loop planner *cannot exist* without a walkable topology, so ① is a hard *prerequisite*
here, not a nice-to-have. That is a sequencing fact for whoever picks up the planner — not a contradiction
of their choice (their choice was scoped to de-duplication, which ① is optional for; the planner raises
the bar). Their open sub-question — topology on the `Checkpoint` enum vs. a companion `CheckpointTopology`
— would be the *first* concrete decision of the planner subject too.

[#patient-record-longitudinal]
== The patient record is longitudinal — and it is an ESSENTIAL element (the session-3 reframe)

The user's definition, verbatim in intent: *the patient record is the grouping of ALL consultations a
patient has had, regardless of which practitioner conducted them.* Two consequences follow, and the
second is the one that was missing.

. *Grouped by patient, across practitioners.* `ConsultationReport` is already indexed by
  `checkpointId` (the patient), not by practitioner — so "all consultations of this patient" is the
  natural grouping. (The dual, practitioner-centric view the Drools prototype wants — "all patients
  that consulted specialist X" — additionally needs the missing patient↔specialist edge; the *patient
  record* defined here does not.)
. *Across time — the state must carry consultations, then history is walked.* During planning, the
  `up` *must persist this run's consultations into the state* (it already does — per-node). Then the
  longitudinal record is built by *walking the stack's history* (the time axis). This is the essential
  element: without persisted-then-replayed consultations, the doctor has only the present run and the
  "doctor sees the records" premise of layer 3 is hollow.

=== The architectural choice — RESOLVED toward the external wrapper

The Automation API drives Pulumi *from the outside*, whereas today *seed-outcluster IS the Pulumi program*
(launched *by* `pulumi`). Two ways to read the longitudinal record were on the table:

* *Inception (self-inspection)* — the running program inspects its *own* stack mid-run. *Rejected:* the
  `up` holds the lock, so a self-`exportStack` is at best fragile, at worst blocked. (The lock kills it.)
* *External orchestrator* — an Automation-API driver wraps the lifecycle, reading *off-lock* before and
  after the up. *Chosen* — this is <<the-solution,THE SOLUTION>>: the two-jar wrapper via
  `createOrSelectStack` local-source.

So "where does the doctor read the record" is resolved: *the wrapper builds it off-lock and hands it to
seed-outcluster as input* (config-driven stream/file). Adjacent to
link:pulumi-doctor-integration.adoc[pulumi-doctor-integration] (where the doctor sits relative to the
Pulumi lifecycle) — the wrapper is now that answer too.

== Open tensions (named, not resolved)

. *`StackDeployment` opacity* — "no strongly typed model for the contents yet": navigate the raw
  `Map<String,Object>` (`resources[]`, filter by URN/type, read `outputs`) by hand. A small parse layer.
. *DAG as data* (<<dag-tension>>) — the planner needs a walkable topology (the rules-engine doc's
  discarded Option ①).
. *Master reachability* — re-probe-live makes the preview depend on the master being reachable; defer
  remains the honest *fallback* when it is not. The default when reachable is re-probe.
. *COUNTERFACTUAL rendering* — the walked-downstream view is a simulation ("if the remediation works
  AND the dependency model is correct, then reachable"), not a guarantee. Must be marked clearly in the
  runbook. Risk: the operator reads reachability as a promise.
. *Expected-state shape* — a boolean flip ("dbus → ok") vs. a rich hypothetical `Dossier`. Open. It
  must live on the `Prescription` (the closed-loop hinge).
. *Inner-loop termination on richer graphs* — a DAG bounds a single sweep; a future cyclic or
  diamond-shaped dependency set would need an explicit visited-set / topological guard.

== Correlation with the rules-engine subject (for that agent)

NOTE: This section was first written correlating the planner to the rules-engine doc's *Option ③
(Drools as substrate)*. That was wrong: the parallel agent *rejected* ③ and adopted *Option ②′ —
Drools CONTAINED behind the `Specialist` seam* (one bounded `NetworkSpecialist`), per
link:drools-network-specialist-prototype.adoc[the Drools prototype]. The section below is corrected to
that actual decision. The synthesis is *not* mine to make — these are correlations for you and that

=== The decisions are largely ORTHOGONAL (their verdict, confirmed)

The Drools prototype states it plainly: _"preview-whatif — orthogonal; the what-if propagates along the
*checkpoint* edge, not inside a specialist. No interaction."_ That holds, and it is the right reading:

* *Their ②′ lives BELOW the seam* — a `KieSession` born and disposed inside one `NetworkSpecialist.
  diagnose()`. It changes *how one specialist reasons*, nothing above it.
* *The planner lives ABOVE the seam* — it orchestrates *which* checkpoints to probe, *which* gates to
  open, *who* to re-consult. It treats every `Specialist` as an opaque `diagnose(symptom, dossier)`,
  Drools-backed or plain-Java alike.

So the two compose without conflict: the planner can route an unmasked downstream symptom to a
Drools-backed specialist exactly as to a plain one. *The seam is what keeps them orthogonal* — the same
seam the prototype leans on. No correlation forces a change on either side. The points below are the
*only* genuine intersections, and both are small.

=== Intersection 1 — `treats()` shape: CONVERGED (domain seeds, practitioner owns)

Both subjects adopt "the specialist declares what it treats" (their Option ②, this doc's <<treats>>),
and — after the clarification — *both landed on the same shape*: the `domain()` *seeds* a
default repertoire the practitioner inherits, but the practitioner is the *sole authority* that
provides its effective `treats()` (adding / removing). Not "flat" (which dropped the domain default),
not "computed two-source" (which would re-create the synchronization the `switch` had) — one owner, the
domain pre-fills. This was the one place the two docs briefly diverged; they no longer do.

The practical note that remains: **a `NetworkSpecialist` that treats `{TIMEOUT, CONNECTION_REFUSED,
API_NOT_READY}` is a good first exercise of the seed/owner split** — those are exactly the symptoms the
old `routeBySymptom` mapped to `NETWORK`, so the `NETWORK` domain seeds them and the specialist
inherits-then-owns, rather than hand-listing from scratch. Low stakes; no decision pending.

=== Intersection 2 — the layer-3 read path: now CLOSED for them too (updated)

The Drools prototype's fact base is the specialist's *longitudinal case history* — all past dossiers of
patients that consulted it (cross-node, cross-time). An earlier cut of this section said that read path
stayed *"fully open for them"* and pointed at a *missing patient↔specialist edge*. *Both halves are now
out of date* — superseded by this doc's own landing and by reframings on both sides:

* *The persisted longitudinal store now EXISTS — it is <<the-solution,THE SOLUTION>>.* The
  self-referential `medicalRecord` accumulator (top-level, carried forward, append + *summarize old*) is
  precisely a persisted, queryable case history across runs. The retention summary ("symptom X recurred
  5× between t1–t2") is the longitudinal-pattern material a rules-backed specialist consumes. So the
  what-if does *not* "sidestep the store" anymore — its solution *is* the store.
* *The patient↔specialist edge is no longer "missing".* Their doc dropped it (now
  link:drools-network-specialist-prototype.adoc#no-authored-by[`#no-authored-by`] — the record is
  *patient-centric*, the edge is not needed for the patient record). And the doctor-model enrichment
  (memory `doctor-remediation-model`, the `Referral`/`ReferralReply` round-trip) *traces* the addressing
  end-to-end anyway — so the gap is closed from both directions, not open.

Net: the case-history store the prototype wanted is delivered by the accumulator; the missing-edge
concern is resolved (patient-centric on their side, referral-traced on the doctor-model side). This
section no longer flags an open dependency — it flags a *convergence*.

=== A weaker, optional resonance (not a dependency)

If one ever *wanted* a rules-engine framing for the orchestration layer (not the plan today), the
closed-loop planner happens to *be* a forward chainer without the substrate costs ③ was rejected for:
explicit instance-passed dossiers as the fact base (not hidden working memory), typed `diagnose()`
methods as rules (no inference), a bounded DAG sweep as propagation (no RETE network). This is a
*resonance worth noting*, not a proposal — the planner does not need an engine, and ③ stays rejected.
