= Pulumi entity model & the Doctor's Pulumi integration
:toc: left
:toclevels: 3

> *Workshop:* lives in `wip/` on `feature/runbook-doctor` alongside link:runbook-doctor.adoc[spec.adoc]
> (which references this from Increment E). Durable substance migrates to `docs/architecture/`
> before merge. This doc exists because the question "the doctor needs a Pulumi specialization —
> how do we implement it in Pulumi?" cannot be answered without first laying out *what entities a
> Pulumi application manipulates* vs *what entities a Pulumi provider manipulates*. The medical
> record = the stack state (see spec), so the doctor's relationship to Pulumi is structural, not
> an afterthought.

== Why this matters

The doctor core is a *generic module* (reused in config and elsewhere), yet the *medical record is
the Pulumi state* and "each medical record's DAG must be reconstructable from the states". Those
reconcile only if the Pulumi-ness lives in a *specialization*, never in the core. To choose the
shape of that specialization we must be precise about Pulumi's two entity worlds — the
*application* world (what our seed-outcluster code touches) and the *provider* world (what a plugin
touches). The fork at the end (ComponentResource vs Provider) hangs entirely on this distinction.

        APP["The application<br/>registers Resources,<br/>builds Outputs"]
    end

    subgraph PROV["Provider plugin(s) — gRPC ResourceProvider"]
        CRUD["Check / Diff /<br/>Create / Read / Update / Delete /<br/>Construct / Invoke"]
    end

    STATE[("State backend — checkpoint/snapshot:<br/>per-resource inputs+outputs<br/>+ dependsOn edges")]
    WORLD([Real infrastructure<br/>AWS, Incus, k8s…])

    OP -->|pulumi up / preview| ENGINE
    ENGINE -->|starts, asks to run| HOST
    APP -->|RegisterResource… via gRPC| RM
    RM --> DEP
    DEP -->|CRUD over gRPC| PROV
    PROV -->|talks to the real world| WORLD
    DEP -->|writes / reads| STATE
----

*The load-bearing fact:* our code (seed-outcluster) runs *inside the Language Host*. It *never writes
state directly* — it *declares* resources to the Resource Monitor; the *engine* writes state; the
*providers* talk to the real world. So "persist into the state" has exactly two routes: a
*ComponentResource* (`registerOutputs`) or a *CustomResource backed by a provider* (CRUD).

----

    class ResourceOptions {
        +dependsOn : Resource[]

    }
    class ResourceArgs {
        +Input fields (desired state)
    }
    class Deployment {
        +isDryRun()
        +stackName / projectName / org
    }
    class Context {
        +export(name, Output)
    }
    class Config {
        +get / getObject (stack config)
    }

    Resource <|-- ComponentResource
    Resource <|-- CustomResource
    CustomResource <|-- ProviderResource
    Resource o-- ResourceOptions
    ResourceOptions o-- Resource : dependsOn
    CustomResource ..> ResourceArgs : created from
    Resource ..> Output : exposes
    Context ..> Output : exports
----

Notes:

* `ComponentResource` = a *logical grouping*; NO provider, NO CRUD lifecycle. It is re-registered
  every run. `registerOutputs(...)` writes its outputs to state; `dependsOn` records edges. This is
  what `SystemdAdapterResource` and `ClusterReadinessResource` are today.
* `CustomResource` = backed by a provider; has a physical `id` and a CRUD lifecycle.
* `Config` = the stack config = the *call parameters* = the "admission context" of a visit
  (incl. `policy.preview.simulate.<scenario>`). `Deployment.isDryRun()` = preview vs up.
* `Output` carries `dependencies` — the data-flow edges Pulumi tracks automatically.

----

*Why this world does NOT fit the doctor.* A provider has `Read` = "reconstruct the actual state from
the world" (`pulumi refresh`) and `Diff` = "has it changed?" — for *external state the provider
manages*. Our observations are not managed external state; the probes recompute them from scratch
each run. A `ComponentResource` has none of `Read`/`Diff` and doesn't need them. So this provider
world is the wrong tool — see the resolved verdict in §4.

== The decision — RESOLVED (2026-06-07): Option A; the doctor is NOT a resource

The fork is closed by a design argument, which also removes the open facts-to-confirm.

*Resources are PROVISIONED by Pulumi, not USED by it.* A resource is a *target of reconciliation*
toward a desired state (Create/Update/Delete) — not a service the engine invokes. So modelling the
*doctor* (or the *patient*) as a resource is the wrong branch:

* *The doctor has no desired state.* It is behaviour — it reads observations and produces a
  diagnosis. "Provision a doctor toward a desired config" is meaningless; you'd invent a fake
  lifecycle to fit the mould. That is "walking on Pulumi's toes": re-implementing an actor/object
  model on top of a desired-state reconciler.
* *The patient is already the stack.* Modelling "patient" as a resource *inside* the stack would
  model the stack as a resource of itself — circular. Once the doctor is a resource, the whole
  medical ontology must become resources, duplicating the entity Pulumi already manages.
* *"Interacting with them" is illusory.* Interacting with a resource = `pulumi up`/`refresh`/
  `destroy`. You don't `pulumi up` a doctor. The interaction we actually want is *the operator
  reading the runbook* — a rendering/reading concern, not a resource interaction.

*This also kills Option B (provider-backed CustomResource).* B was attractive because `Read`/refresh
= "re-observe the patient". But re-observation *already happens in the program*: the probes re-run
every `pulumi up` and observe the live world. A provider's `Read` reconstructs *external state a
provider manages*; our observations are not a managed external object — they are *recomputed from
scratch* each run. So B adds almost nothing and costs a heavy Java gRPC plugin. (Therefore the old
"does pulumi-java support inline providers?" question is now *moot* — we never need a provider.)

*What survives — Option A, with the precise nuance.* A `ComponentResource` is the one resource kind
that is *NOT provisioned toward an external target* — it is a *logical grouping that carries outputs
into the state* via `registerOutputs`, and records `dependsOn` edges. So:

* The *doctor stays application logic* in the Language Host — a module, never a resource.
* Only the *consultation report* (the data/result) lands in the state, as `registerOutputs` on the
  checkpoint's existing `ComponentResource`. This is *not* "modelling the doctor as a resource" — it
  is *recording the result of an observation as an output*. The ComponentResource is an
  *output-carrier / anchor point in the state*, not a provisioned actor. That distinction is the
  whole reason A is legitimate where B and "doctor-as-resource" fail.
* "Medical record = reconstructable state" never needed B: reconstruct by re-reading the
  checkpoint's outputs + `dependsOn`; the "re-observe" cycle = the program re-running, not a
  provider `Read`.

[cols="1,3,3",options="header"]
|===
|Shape |Verdict |Why
|*doctor/patient as resources* |REJECTED |resources are provisioned toward a desired state; a doctor is behaviour, the patient is the stack — circular, walks on Pulumi's toes
|*B — CustomResource + provider* |REJECTED |re-observation already happens in-program; provider `Read` reconstructs managed external state we don't have; heavy Java plugin for ~no gain
|*A — ComponentResource* |CHOSEN |the report is carried as outputs (+ `dependsOn` edges) on the checkpoint's existing component resource; doctor stays application logic; DAG reconstructable from outputs+edges
|===

*Still distinct (not part of this verdict):* a *Pulumi-domain Specialist* — a diagnosis expert that
reads Pulumi engine errors/state to diagnose — is a business expert, orthogonal to the persistence
question above. It may exist later as just another `Specialist`; it does not make the doctor a
resource.

*Remaining design checkpoint (layer 3, not blocked by this verdict):* confirm that a
`ComponentResource`'s checkpoint outputs + `dependsOn` are sufficient to reconstruct the DAG
off-line — a verification when layer 3 is built, not a fork.
