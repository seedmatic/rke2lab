= bbox-edge — the router-reconciliation contact, put in its place
:toc: left
:toclevels: 3

[IMPORTANT]
====
*Status:* ⚠️ *RETIRED 2026-09-24* (`e020654a1`). The `bbox` domain is *gone from this codebase* —
no `bbox-contract`, no `bbox-edge`, no `bbox-bdd` scion. Nothing below describes code you can read
here; it is kept because six sibling specs cite it as the *library-backed edge shape* they mirror,
and that shape is still the reference.

*Why it went, in the excision's own words:* it "existed to reconcile reservations on the home
router; with no rke2lab span left on that network it has no subject, and leaving it compiled would
imply rke2lab still plays bbox logic." The same commit moved each cluster onto a `/24` in its
bare-metal's fabric slice, so a node's reservation is served by that bare-metal's dnsmasq — which
answers the NAME too, ending the split where DHCP came from the bbox and mDNS from avahi. The
excision took `java-bbox-api-client` with it (BOM, `settings.xml`, build-parent, flake) plus the
`rke2lab:bbox` stack section, and `.secrets` dropped its `.lan` subtree. Verified then: the
projection emits ZERO `192.168.*` segments.

*Where the contact lives now:* ndh, as `bbox-reconcile` — deliberately, because "the fabric's incus
door is Pulumi, host-side and declarative, while the edge played in-container", so the survey half
belongs beside the write. ★ And since 2026-09-27 it no longer dials the router over a routed
`192.168.0.0/24` at all: the bbox is a *Tailscale Service* (`svc:bbox`), reached by a virtual IP that
needs no subnet route. See ndh `docs/network-topology-c4.adoc#authorisation`.

Read on ONLY for the edge pattern. For a live example of the same shape, see
link:incus-edge-spec.adoc[incus-edge] or link:auth-edge-spec.adoc[auth-edge].
====

== The contact today — inlined, duplicated, library types on the host

The bbox contact (open a session to the Bouygues Bbox router, diff+apply DHCP reservations) lived in
`seed-outcluster`, duplicated across two paths: `BboxReconcilerComponent.reconcileStandalone` and the
Pulumi `BboxReservationsResource`. Both did `BboxApiClient.open` + `ReservationReconciler.apply(row,
mode)`. Five host files imported `io.seedmatic.bbox.*` — the library's `Action`/`RowOutcome`/
`DesiredReservation` types were spread across the host, including into the Pulumi resource graph
(`BboxReservationResource` built its `Output`s from a library `RowOutcome`).

== Resolution — a `bbox-edge` `@Component` and a home-vocabulary `bbox-contract`

* *java-bbox-api-client* becomes an OSGi bundle (bnd manifest, `0.2.1`): `Bundle-SymbolicName
  io.seedmatic.bbox.api.client`, exports its two API packages, imports `com.google.gson` (itself a
  bundle). No embedding — the edge imports it, and the staging closure stages it (and gson) as
  carriers because an edge imports their packages.
* *bbox-contract* (`type=contract`): `BboxReconciler` — `reconcile(baseUri, password,
  List<BboxReservationRequest>) → List<BboxRowOutcome>` — over a HOME vocabulary
  (`BboxReservationRequest`, `BboxRowOutcome`, `BboxAction` mirroring the library enum). NO `dryRun`
  parameter: the mode is chosen at the frontier, never passed in. No `io.seedmatic.bbox.*` type crosses.
* *bbox-edge* (`type=edge`, a PAIR of `@Component`s, each tagged `rke2lab.gardening` so the
  `@OsgiService` frontier picks one under the ambient RunGate):
  ** `CultivatingBboxReconciler` (`rke2lab.gardening=cultivating`) opens the session, rebuilds the
     library `DesiredReservation` from each request, applies, and maps `RowOutcome`/`Action` back to
     the home records. The single live door.
  ** `SurveyingBboxReconciler` (`rke2lab.gardening=surveying`) contacts the router ZERO times: it
     projects each request's `WOULD_CREATE` — the honest upper bound (a survey cannot read the live
     table, so never a fabricated MATCHING). Real production code, not a fake.
* *seed-outcluster* (host): purified off `io.seedmatic.bbox.*` — it builds `BboxReservationRequest`s from
  the blueprint, calls the reconciler resolved from the registry, and projects `BboxRowOutcome`s into
  its counts and Pulumi resource graph. The library types no longer live host-side.

== The bbox SCION scenario (shipped — the metier definition)

In the ClusterSeed vision (link:../bdd/bdd.adoc#clusterseed-scenario-map[the scenario map]) bbox is a
graft-caller: the host step "the network reservations are settled" sows THIS scenario in-container and
grafts its scion. The host speaks gardening; this scenario speaks the bbox metier (reservation · diff ·
outcome). It is the `bbox-bdd` bundle (first extraction of the two host-side scions, 2026-07-11), on the
`cluster-bdd` reference shape: a `BboxReconciliationScenario` (jGiven `Given/When/Then`), a `BboxRunbookHandler` (a
`@Component service=SeedHandler` extending the shared `GenericRunbookHandler`, supplying
`scenarioClass()`) the shared `ScenarioPlayer` plays in-container, a `BboxAmendReflector`, and a
`BboxReconciliationScenarioInContainerTest` (`@OsgiWorld`) that boots Felix and registers the mock
collaborators. `BlueprintRowEnumerator` (pure — `bbox-core` + `netplan-contract`, zero Pulumi) lives in
`bbox-core` (its home vocabulary), consumed by the scion. The host `BboxStage` +
`BboxReconciliationOrchestrator` are the DEFERRED "avant", deleted when the host runbook grafts this scion.

[listing]
----
SCENARIO: the desired reservations are reconciled against the router
  GIVEN the desired (mac, ip, hostname) reservations for the run
    AND the BboxReconciler contact resolved from the registry — mode-blind, the frontier picks
        cultivating or surveying
  WHEN the reconciler is driven once over the desired rows
    AND it diffs each row against the router table (cultivating) or projects WOULD_CREATE (surveying)
  THEN every desired row has a BboxRowOutcome — present-already / created / corrected (BboxAction)
    AND a row that could not be reconciled is SURFACED, never silently dropped
----

*Preview inertness — the FRONTIER selects, the scion is mode-blind.* The scenario injects
`@OsgiService BboxReconciler` and NO `RunGate`; the bridge reads the ambient gate once and resolves the
`CultivatingBboxReconciler` or the `SurveyingBboxReconciler` by LDAP filter on `rke2lab.gardening`
(`(|(rke2lab.gardening=<mode>)(!(rke2lab.gardening=*)))`). The scenario body is identical either way —
it just drives the reconciler. Under survey it gets the surveying impl (WOULD_CREATE, zero contact);
under cultivate, the live one. No `dryRun` flag, no per-step gate. *On a refused row* the domain MAY
consult the doctor itself (a symptom), the same transversal-consult pattern as systemd/cluster — the
host never sees it.

The scion grafts back under the host step; its `@Scion("fruit")`/`@Scion("sowing")` roles (if it consults)
project through the neutral port exactly as the doctor's do (see
link:seed-broker-spec.adoc[the seed-broker spec]).
