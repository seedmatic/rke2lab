= Node image lifecycle — the realised artifact as a resource
:toc: left
:toclevels: 3
:icons: font

== Overview — what, why, the problem it solves

The nix-built node-base image is ONE artifact. Until the `NodeImage` CR it had no
owning object, and its identity was *shredded* across the CRs that consumed
pieces of it:

[options="header"]
|===
| `ImageState` field | Where it landed | Consumer
| `imageFingerprint` | embedded inside each pool's spec | the `LXCMachineTemplate` image pin
| `rke2Version` | a sibling scalar beside it | `RKE2ControlPlane.spec.version`
| `incusProject` | inside the CAPN identity Secret | CAPN
| `imageAlias` | a `<cluster>-image-state` ConfigMap | *nothing*
| `imageBuildChecksum` | idem | *nothing*
| `incusRemoteAddress` | idem | *nothing*
|===

Three of six fields existed only to fill a ConfigMap **no component ever read** —
a fossil of the "Stage A → Stage B / seed-peers" era, superseded by the intention
CRs which carry the fingerprint directly. The unit that rendered it is deleted.

★ The cost was not the dead ConfigMap. It is that *because no object owned the
image, the runtime contract of that image had nowhere to live* — so it was stated
twice, once on rke2lab's host-side `node-base` incus profile and once inline in
the in-cluster controller, and the two DIVERGED. The in-cluster copy carried nine
kernel modules where the profile carried sixteen, missing exactly the entries each
established by loading it and watching the cilium agent:

* without `xfrm_user`, the agent's route reconciler opens a netlink socket for
  every family, the XFRM one returns `EPROTONOSUPPORT`, and the start hook dies
  with "protocol not supported" — the agent never runs;
* without `nft_compat` + `xt_mark`/`xt_CT`/`xt_TPROXY`/`xt_comment`/`xt_conntrack`,
  only 10 of its 34 iptables rules land; the missing ones stamp `MARK_MAGIC_HOST`
  on host-originated traffic, so every host→pod packet reads as `world-ipv4` and
  any pod carrying a policy denies the kubelet's health probes.

⚠️ And the diverged copy is the one that WINS: the controller poses the contract on
`LXCMachine.spec.config`, i.e. at INSTANCE level, which overrides both CAPN's
embedded instance profile and our own profiles.

One owner for the artifact makes that divergence structurally impossible rather
than merely corrected.

== The resource — `NodeImage`

A published FACT, not an intention: the image exists on the source remote before
the object is written, so there is no reconcile loop and no status — nothing is
converged toward.

The spec is modelled on the incus keys it becomes, not as an opaque map, so a
missing field is a schema error rather than a silent default:

[source,yaml]
----
kind: NodeImage
spec:
  alias: control-node
  fingerprint: <sha256(metadata.tar.xz ++ rootfs.squashfs)>
  buildChecksum: <sha256 of the build INPUTS>
  rke2Version: v1.34.1+rke2r1        # normalised ONCE, by the producer
  source:
    endpoint: https://nixos.bioskop:8443   # the FABRIC FQDN — read from a pod
    project: rke2lab                       # images are listed PER PROJECT
  runtime:
    kernelModules: [ip_vs, …, xfrm_user, nft_compat, xt_mark, xt_CT, xt_TPROXY]
    rawLXC: |
      lxc.mount.auto = proc:rw sys:rw cgroup:rw
      …
    security:
      privileged: true
      nesting: true
      interceptBPF: true
      interceptBPFDevices: true
----

ONE per cluster namespace: every cluster receives the description of the resources
it depends on — the same reason `PoolIntention` duplicates its cluster-level facts
rather than reaching for a shared object.

=== Why the security flags are emitted even when false

Instance config is what OVERRIDES CAPN's embedded profile, so a declared `false`
has to be SENT to win over that profile's `true`. An omitted key silently inherits
it.

== Why a reference, not an embedded fingerprint

`ImageRef` was always *called* a reference while embedding the fingerprint.

[source,go]
----
// ❌ the pool embeds the artifact's hash — the artifact itself has no name
type ImageRef struct { Fingerprint string }

// ✅ the pool NAMES the NodeImage that describes the artifact
type ImageRef struct { Name string }
----

The decisive argument is the upgrade: with an embedded fingerprint there is no
name for the *old* artifact and no way to express "both exist, this one is in
use". A reference makes the generation addressable, so rolling a pool becomes
changing one reference instead of mutating an inner value.

And the controller now derives BOTH the image pin AND the runtime contract from
the one object it resolved — they cannot disagree.

== Three names, three audiences

[options="header"]
|===
| Name | Audience | Rule
| *fingerprint* | provisioning | THE pin. `LXCMachineTemplate` pins this so a pool launches from the exact image that was built.
| *generation alias* | the CR model | identity — addressable, so two generations can coexist as two objects.
| *floating alias* | humans, CLI, observability | convenience only.
|===

❌ *Anti-pattern* — feeding the floating alias into provisioning:

[source,yaml]
----
# NEVER: this silently restores "launch from whatever latest points at today"
image:
  alias: control-node     # floating
----

✅ Provisioning pins the fingerprint; the floating alias exists for
`incus launch rke2lab:control-node` and for a human reading the image list.

== The structured producer — a pilot

`NodeImage` is the first of our own CRs rendered from a RECORD (`NodeImageCr`)
rather than a hand-rolled `Map.of`. The record is the model; `toSpec()` flattens
to maps only at the cdk8s edge — structured inside, flat at the boundary.

What it buys: the field set becomes the compiler's business on the producing side,
and the shape has one readable definition.

⚠️ What it does NOT buy: proof of agreement with the deployed CRD schema. The
component names still match the Go struct tags by CONVENTION. Proving it needs
POJOs generated from the CRD — the graved target (fabric8 `java-generator` over
the CRDs this build already stages into `target/generated-resources/crds`). This is
the structured *producer*, not the generated contract.

Adopting the pattern on a NEW object is deliberate: it seeds the target pattern
without leaving the existing CR set half-migrated.

== Future need — generations and upgrade campaigns

NOT BUILT. Graved here because the alias is now load-bearing (it names the CR), so
the shape of the future need constrains the present model.

=== The need

A node upgrade campaign rolls one node at a time, so old and new images must
coexist in incus for the duration. That calls for a generation increment on the
alias plus a floating alias for humans.

★ *A bump is a TRANSIENT STATE of the cluster* — which settles the ownership:
`seed-master` PRODUCES images and never decides who runs them; the campaign is
PLAYED in-cluster.

[mermaid,node-image-generation-ownership,svg]
----
flowchart TB
  CELLAR["cellar (host)<br/>the ledger of what was PRODUCED<br/>generation ordinal ↔ checksum"]
  FACET["branch facet<br/>the TARGET generation per cluster<br/>EDIT changes it · UPDATE preserves it"]
  ROLL["in-cluster rollout<br/>PLAYS the roll — one node at a time,<br/>health gate, rollback<br/>writes effective state as a reflection"]

  CELLAR -->|"publishes a generation"| FACET
  FACET -->|"declares a desire"| ROLL
  ROLL -.->|"reflection"| FACET

  classDef host fill:#FFCDD2,stroke:#B71C1C
  classDef seam fill:#FFF9C4,stroke:#333
  classDef incl fill:#C8E6C9,stroke:#333
  class CELLAR host
  class FACET seam
  class ROLL incl
----

The host publishes a *desire*, the cluster owns the *execution*. So the render
legitimately owns the TARGET while the cluster owns the EFFECTIVE state — no
two-owners conflict on one field.

=== The generation is content-derived; the cellar keeps the ordinal

`alias = <base>-<buildChecksum[0..8]>`. A counter alone is state someone must own
and is ambiguous across two hosts; a checksum is already computed, idempotent
(rebuilding identical inputs yields the same alias, so the grow does not churn),
and matches the existing precedent — the fingerprint itself is content-derived.

The cellar keeps the *ordinal* (generation 7 = checksum `abc`): the checksum is the
identity, the cellar is the history, and it is what a future incus image pruner
would consult.

⚠️ The alias becomes the CR object name, so it must be DNS-1123 — the rke2 version
(`1.34.1+rke2r1`) cannot go in raw.

=== ⚠️ Two measured obstacles

*1. No seam holds an in-cluster decision today — on EITHER side.*

On the CR side, `poolintention_controller.go` reconciles the mirror with
`CreateOrUpdate` and assigns `adoption.Spec = specFromPoolIntention(pi)` **wholesale
on every pass**. The `PoolAdoption` is therefore a COPY, not an ownership boundary: a
campaign writing it is reverted within seconds, and one writing the `PoolIntention`
is reverted by the next Flux sync. This is the same two-owners-one-field trap
already paid on the tailscale-owned `Service.spec.externalName`.

On the branch side there IS durable state — the branch root records a render
context `{source, facet, image}`, so the whole `ImageState` already survives there
and a steady-state render replays it rather than emptying the CR set (the incus
scion runs only at the grow). Read → decode → re-serialise is a fixpoint, so
replaying causes no commit churn.

⚠️ But its precedence is "a live seeded image (a GROW) wins; else replay HEAD". So
the branch holds an in-cluster decision only against in-cluster renders
(`UPDATE` = HEAD wins) — **the next host grow re-asserts it**. The rule that falls
out is general and worth stating once:

[quote]
A cluster-owned decision cannot live in a place the grow re-asserts.

So the target generation belongs neither in the recorded `ImageState` (the grow
overwrites it) nor in the copied mirror (the reconcile overwrites it). It needs a
home whose owner is the cluster — which is why a campaign wants its own object.

*2. The pruning render, not incus, is what makes images hard to keep.* Every render
directory carries `prune: true`, so a generation-stamped alias changes the object
name on each rebuild and Flux DELETES the previous generation's `NodeImage`.

✅ *Bounded answer* — the render emits the `NodeImage` of the target generation AND
the previous one. A window of two, because a roll happens precisely between two
generations. Coexistence becomes bounded by construction rather than by a garbage
collector nobody wrote.

=== Costs to price before starting

* `ScenarioCellar` / `SeedRunLedger` is design-converged, *code not started* — this
  path leans on a foundation that does not exist yet.
* `RenderMode.overrides` is `Map<String, Boolean>`, deliberately boolean-only "so
  the contract stays jackson-free", and its paths reach `debug` / `delivery` /
  `workloadTargets` — the `Facets` sub-map, NOT the recorded `image` beside it. A
  generation is neither a boolean nor reachable by those paths, so using `EDIT` as
  the bump trigger means widening it on both axes.
* A campaign is a STATE, not a field — ordering, one node at a time, a health gate
  between nodes, rollback. That is an object with a status, not a copied scalar.

Which generations are live is a CLUSTER fact (who is using what), not a producer
fact. The producer publishes one generation; the cluster accumulates and decides.

== Where the image identity SHOULD come from — the unwired seam

NOT BUILT, and it contradicts part of what is built. Graved because it decides the shape
of everything above.

`host-cellar-realisation-spec.adoc` is explicit: the image fingerprint is a HARVEST
conserved at the cellar and re-read by address, never a value handed around.

[quote]
when the synthesis genuinely needs the fingerprint, the manifests scion FETCHES the
image scion's harvest from the cellar (`Cellar.fetch`), it does not receive it amended

The same spec names `imageState` as a vestige of the former host bootstrap and says it
"must STAY unwired". ⚠️ It has since been wired: `ManifestsRunbookInput` carries
`@Amendment(IMAGE_STATE) Optional<ImageState>`, and the `NodeImage` CR described above is
rendered FROM that amendment. So this document's own increment deepened the vestige
rather than avoiding it.

The spec's discriminator is what makes the target shape clear — amendments carry the
*where* and the *posture*, never a CULTIVATED value (a fingerprint, a urn, a checksum):

[options="header"]
|===
| Fact | Nature | Belongs on
| `fingerprint`, `alias`, `buildChecksum` | CULTIVATED — produced by a build | the cellar, fetched by address
| `source.endpoint`, `source.project` | where | may travel as an amendment
| `runtime` (modules, `raw.lxc`, `security.*`) | a DECLARED CONSTANT of the recipe, not cultivated | may travel — but not nested inside the cultivated record
|===

So the target is not "delete the amendment": it is to split the two natures that
`ImageState` currently fuses. The runtime contract is a constant and may be amended; the
identity is a harvest and must be fetched. Today they ride together, which is why the one
that must not travel does.

=== The three sources of an image identity

An absent artefact set is NOT an absent image, and the difference is what makes a survey
honest:

. *mint* — the live grow builds it;
. *the cellar* — the previous run's harvest, read by address. The DESIGNED path, unwired
  from the host grow today;
. *the daemon* — the `node-base` alias a completed grow posed, which is why
  `poseNodeBaseAliasAndGcImages` exists. Wired (`IncusImportLookup.nodeBaseFingerprint`),
  and what makes a preview work on a fresh worktree: a new worktree empties the Pulumi
  stack, not the daemon.

Only when all three are silent is it an error — and then it must BE an error.

=== The rule that governs both repairs

Two defects here were the same shape, and the project had already named it
(`destructive-gate-needs-three-valued-probe`, graved after the tart/diskutil incident):

[quote]
Under `prune: true`, emitting nothing IS AN ACT. So "I do not know" must fail, and only
"there is nothing" may emit nothing.

A read failure must never be allowed to become a delete, nor a guess.

== The same rule on the BAKED OCI images

The governing rule — *an artefact's identity must move with its content* — is not specific to
the node image. Three baked container images were breaking it, and silently.

=== Why a static tag is a silent no-op deploy

These images reach a node through the air-gap path: the `.tar.gz` is baked into the
node-base image, rke2 auto-imports it into local containerd at boot, and pods reference it
with `imagePullPolicy: IfNotPresent` — there is no registry to pull from, so that policy is
structural, not a choice.

⚠️ `IfNotPresent` means a node already holding a RepoTag NEVER replaces it. With a static
tag, a rebuilt binary therefore shipped *inside* the node image while every pod kept running
the old one, and **nothing reported it**. "I deployed and nothing changed, with no error" is
the worst class of failure: it does not even announce itself.

=== What each image does now

[options="header"]
|===
| Image | Delivery | Identity
| `flox-controller` | baked OCI — it CANNOT use a flox env, being the thing that *realises*
  flox envs (an env delivering it would have to run to realise itself) | tag omitted ⇒
  dockerTools derives it from the OUTPUT HASH
| `flox-carrier` | baked OCI — the minimal base every flox-injected pod runs | idem
| `seed-incluster` | the flox env `cluster-api/seed-incluster` installs the binary; the pod
  runs the carrier with it on PATH | DELETED — the env's lock pins a store path, so it is
  content-addressed by construction
|===

★ So the two shapes are not equivalent, and the choice is forced rather than stylistic: a
flox env is content-addressed for free, and only what *cannot* use one needs a
content-derived tag. The `seed-incluster` OCI output was removed rather than fixed, because
it had no consumer left and was the worse shape of the two.

=== A derived tag cannot be written down — which is the point

Both tags used to be Java literals on `FloxDebugPolicy` (`rke2lab/flox-carrier:0.1.0`,
`io.seedmatic.flox-controller:0.0.0-develop`) under a javadoc pleading that they "MUST match
the RepoTag the nix image is tagged with". The plea *was* the design: nothing enforced it,
and one of the two lived in another repository's `VERSION` file.

Now the flake PUBLISHES each ref and stages it onto the synthesis classpath at
`/image-refs/` — the same mechanism, pom wiring and `mvn clean` hygiene as `/crds/` and
`/rbac/` — and the synthesis READS it through `ContainerImageRefs`, reached from
`ManifestSynthesisContext.containerImages()`.

[source,java]
----
// ❌ a literal that a rebuild silently invalidates
container.put("image", "io.seedmatic.flox-controller:0.0.0-develop");

// ✅ read what the build staged
container.put("image",
    ManifestSynthesisContext.current().containerImages().floxController());
----

Two properties worth keeping:

* the carrier's ref is computed from the NODE's pkgs
  (`nixosConfigurations.rke2-node-base.pkgs`, via the leaf both the module and the flake
  import), so the tag rendered and the image baked cannot disagree. A separately imported
  nixpkgs would agree only BY COINCIDENCE — there are no overlays on the node today — and a
  coincidence is the fragility being removed;
* a missing staged ref fails AT THE POINT OF USE, naming the step that produces it. It is
  never defaulted: a guessed tag would name an image no node holds.

★ And it makes a guard unnecessary rather than needed. The alternative was a build-time
concord check (the pattern `flake.nix`'s `node-label-concord` already uses for a Java
constant the nix side must match) — but that only catches a typo, never "same tag, new
content". Deriving the tag removes the literal, so there is nothing left to keep in step.

== The node's devices — inline, from one definition

A node is an Incus container, so something must say which disk, which passthroughs and which bridges
it gets. That used to be two Incus PROFILES the HOST grow created as Pulumi resources — `node-base`
(fleet-wide) and `node-<cluster>` (per cluster). Both are gone; `NodeDeviceSet` is the one definition,
posed INLINE by each consumer.

=== Why the profiles went

Three defects, and only the third is about tidiness:

* ⚠️ *They collided on every cold start.* A fresh Pulumi stack meets a daemon that still holds them,
  and `Profile` was the one resource here with neither `importId` nor adopt-by-omission — so the grow
  died on "The profile already exists" while `seed-project` (which imports) was adopted. `pulumi
  refresh` cannot help: it reconciles resources already IN the state and never discovers ones absent
  from it.
* ⚠️ *Their devices could be created but never corrected.* The provider models `devices` as an ordered
  list that churns, so it is ignored — meaning a change to a NIC's parent or name reached an existing
  profile only if an operator deleted it by hand. It bit twice on 2026-09-24.
* *They needed a name on both sides of the language boundary* — `node-<cluster>` in Java,
  `nodeProfileName` in Go: two derivations of one convention.

★ And inlining them needs NO new authority over Incus, which is what made it the right move on a
branch about giving each part its role: there is no profile left to create, and CAPN already creates
the instances. Adopting the profiles by omission instead would have made their config write-once —
the defect that once hid six kernel modules cilium needs.

=== What CAPN already provides, measured in its source

`internal/instances/kubeadm.go` applies `static.DefaultKubeadmProfile(...)` itself —
`opts.WithConfig(profile.Config).WithDevices(profile.Devices)` — so the `incus profile create kubeadm`
its docs describe is for people launching containers BY HAND, not a prerequisite for the provider.

The build order in `controller_util_launch.go` is what makes our contract decide:

. CAPN's own kubeadm profile (config + devices, including `/dev/kmsg`)
. `WithProfiles(spec.Profiles)` — additive, and now empty
. `WithDevices(spec.Devices)`
. `WithConfig(spec.Config)`, then CAPN's cluster metadata

So our `spec.config` lands AFTER the built-in profile. That is why the kernel-module list is asserted
there and why it wins — and it must be the WHOLE list, since `linux.kernel_modules` is a single
comma-string that replaces rather than merges.

=== ⚠️ The full device set, including `root`

With no profile named, nothing else supplies a disk. Incus's own `default` profile carries one, but it
is not applied when the profile list is empty, and OUR base profile is precisely what is being
removed. Measured on the live daemon on 2026-09-28: `node-base` declared `root`, `kmsg.dev`,
`zfs.dev` and `fabric0`, and both live instances referenced it.

`kmsg.dev` duplicates what CAPN already gives; it is declared anyway, at an identical value, so the two
delivery paths stay symmetric — the standalone master gets NO CAPN base, being created by the Pulumi
provider directly, so it needs the full set regardless.

=== Who publishes what

The vmnet bridge follows the cluster's ROLE, so the blueprint derives it. The fabric bridge does not:
it is an operator declaration in the host's `rke2lab:network:` concern, which reaches the render as its
own amendment role (`NETWORK_FACET`) — contributed verbatim, exactly as `rke2lab:manifests:` is. The
render then composes the set and publishes it on `PoolIntention.spec.devices`; the controller poses it
and derives nothing.

⚠️ Ordering when this lands: an Incus profile cannot be deleted while an instance references it, so
the instances are recreated first and the orphaned profiles removed after — which a cold start does
anyway.

== Troubleshooting

The grow fails with "no node-base image can be identified"::
Neither source answered: no built artefacts (a surveying run builds none) and the daemon
holds no `node-base` alias in the project. Mint one with a live grow. This is deliberate —
it used to compute a fingerprint from whatever files happened to be on disk, which is why
it appeared to work until the first run from a fresh worktree.

The render fails with "HEAD records an image this build cannot decode"::
The branch's recorded render context predates a field the current `ImageState` requires.
A grow re-records it. The refusal is the point: emptying the render instead would prune
the cluster's `ClusterIntention` / `PoolIntention`.

`PoolAdoption` stays `MaterialReady=False` with reason `ImageMissing`::
The reconciler is waiting for Flux to apply the `NodeImage` named by
`spec.image.name` in the pool's namespace. Check the render actually emitted it
(the units no-op when no `ImageState` is bound — a bare survey or a secret-blind
in-cluster render) and that Flux has synced the branch. The wait is deliberate:
without the object the contract would have to be guessed, which is how the two
copies diverged.

A node comes up but cilium's agent never runs ("protocol not supported")::
The instance is missing `xfrm_user`. Check
`incus config get <instance> linux.kernel_modules` against
`NodeImage.spec.runtime.kernelModules` — instance config wins over the profile, so
the instance value is the one that decides.

Flux keeps deleting a `NodeImage`::
Expected while the render emits only one generation and the object name changes
(see the pruning obstacle above). Coexistence needs the two-generation window.
