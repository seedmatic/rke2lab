= Atlas L1 — Fabric control-plane view (from keys and SaaS to our own tailnets)
:toc: left
:toclevels: 3

_Level-1 (per-subsystem) view of the link:../integration-atlas.adoc[integration atlas] (L0)._
_L0 shows how this subsystem integrates with the others and the value that emerges; this file is the detail._

The access plane of the infrastructure — how a machine of the fabric is reached, by whom, and with what
— migrating from today's shape (one SaaS tailnet for everything, an SSH authority whose private sits
on every host, keys rotated at every activation) to the target specified in ndh
`docs/fabric-control-plane-spec.adoc`: **one self-managed headscale tailnet per bare-metal** for the
infrastructure nodes, the clusters staying on the SaaS, and access granted by policy.

Everything marked *measured* was read on 2026-10-06 in ndh, rke2lab, the Tailscale source or the
headscale source. The corporate bare-metal is named by its role and its alias `vzhost.nikopol`.

== The thesis — access stops being key material

Each figure carries its own before/after in one frame (atlas convention). The red `BEFORE` block is
what the transition deletes; the green `AFTER` block is the target.

The motive is a measured incident, not tidiness. On 2026-08-27 a misrouted sops rule published the
whole key registry in this public repository: eight private keys, including the SSH authority every
host trusted, where this repository reads four items. Renewing the keys closed that leak, not the next
one, because the shape that caused it stayed: **a registry that carries privates everywhere eventually
leaks everywhere.** The target removes the shape: access becomes a grant, a key becomes an exception,
and an exception is generated by the machine that uses it.

=== Diagram B — Bootstrap: BEFORE vs AFTER

Reads: the BEFORE bootstraps a guest through keys baked into the bringup image (`linux-builder` and
`rdp-host` authorised for root) and an ssh session for every activation; a stale image is a locked
door once those keys are revoked. The AFTER needs no key at all: the operator reaches the guest's
serial console from its bare-metal, and the control plane by `incus exec`.

=== Diagram C — Keys: BEFORE vs AFTER

Reads: in the BEFORE, a key rotated at every activation is never recorded, so it can be neither revoked
nor evicted — and the principals command grants every principal to every account, so one
certificate opens root everywhere. In the AFTER, every key is static, generated by its owner, and
authorised for one flow.

*Measured:* `cert::identity` derives the Key ID from the key name and usage only, so every generation

*current* files, so a regenerated keypair is never evicted; `ssh-keys-renew` has no revocation step.

=== Diagram E — Crossing bare-metals: BEFORE vs AFTER

Reads: in the BEFORE, one tailnet makes every node a peer of every other, and the NixOS guests
announce the `vmnet` cluster segments into it. In the AFTER, two tailnets meet at their gateways
through a dedicated WireGuard bridge; traffic between them targets segment addresses, and the
announcement of the `vmnet` segments into the SaaS must move to the cluster nodes before the guests
leave it.

== The migration sequence

Each step leaves every connection working, and the old path goes only once the new one is
*measured*. The invariant across all of them: an operator always has a path to the machine being
changed — the serial console, `incus exec`, or the emergency screen.

| Step | Content | Precondition / measured fact

| 0 — rke2lab prerequisites
| ✅ *DONE on develop, measured 2026-10-06.* `DefaultNdhKeystoreReader` resolves the presented
generation (`newestSlot`, with the oldest for an authority) and raises on a v1 flat entry;
`NdhKeystoreCatalog` gained `SIGNING_KEY("github-signing")`, which `SigningKeyMaterialResolver` now
reads instead of its literal — all in `7a0d6d79e`. `.ndh-ssh.d/keys.yaml` is the v2 slots shape
(`4a13478b6`), and `nch-relay-tls-server` exists in **both** trees, upstreamed to ndh
| it had to land first: the retired `github-signing` public is gone from GitHub, so a stale copy made
the bump bot's commits Unverified, and a plain subtree pull would have deleted the relay leaf

| 1 — headscale ≥ 0.29
| ✅ *DONE in ndh, measured 2026-10-06* (`04e83f35` + the re-lock `a8d463ca`). Not an overlay — a
**re-aim of the existing version band** in `modules/.common.d/headscale-pkg.nix`, from
`>= 0.28, < 0.29` to `>= 0.29, < 0.30`, because `nixpkgs-unstable` already carries the version we
want. `0.30` is the right ceiling: it moves the admin surface to `/api/v2` + OAuth, which we do not
need while the clusters stay on the SaaS
| grants arrive in 0.29.0 (2026-06-17); unstable carries 0.29.4 (2026-09-23). ⛔ *Two defects the
bump uncovered, both fixed in the same change:* the band was a **tripwire that had already tripped**
— unstable was past it, so `pinned` fell back to `pkgs.headscale` silently, harmless only by luck
(stable happened to sit inside the band it aimed at); the fallback now warns at eval time and names
both versions. And `ndh.headscalePkg` called itself the single source of truth while **only darwin
honoured it** — `modules/nixos/headscale-daemon.nix` took `pkgs.headscale` directly, so the re-aim
alone would have moved darwin and left NixOS on stable, on the very platform the control plane is
about to run on

| 2 — bioskop control plane
| `headscale-daemon` moves from the guest's host system into an Incus container; `server_url` = a
private fabric name, reached locally by the tailnet's members; the bbox `tcp/41841` forward closed
| headscale FAQ: running it on a tailnet member *"is not supported"*. The control traffic never
crosses the public network, so no ACME and no public name are needed — the control URL's TLS leaf is
signed on a seat from the shared `mammoth-skate-tls` root, which every member already trusts
(`security.pki.certificates` on NixOS, the System keychain on darwin). *Measured:* Apple's 398-day
ceiling does not apply to an administrator-added root, so the leaf can be long-lived

| 3 — per-tailnet policy
| **The carve landed** (ndh `0e727c3a`): `netplan.tailnet` became `netplan.tailnets`, keyed
`saas` / `bioskop` / `nikopol`, each a control plane's *domain of authority*. The vendor entry is
`allocation = "vendor"` with its `/10` as an opaque **given**; ours are `allocation = "ours"`,
`magicDns = false`, no `domain`, with `v4 = 100.{127 - hostId}.0.0/16` and
`v6 = fd7a:115c:a1e0:{hostId + 1}::/64` — and `assert hostId < 9`, because the v6 carve spells the
index as a **hextet** and only 1–9 agree in decimal and hex. `netplan.segments` went 33 → 38: the
hard-coded `100.64.0.0/10` pair is gone, replaced by six **derived** entries `tailnet-{saas,bioskop,nikopol}`,
so nnh's attribution now tells the tailnets apart instead of collapsing every address into one
`tailnet` label. ⬜ *Remaining:* `manage-tailnet` rendering one policy per tailnet and applying it
through headscale's own tooling
| `config-example.yaml`: *"Using a SUBSET of these ranges is supported"*. ⚠️ *The carve is for
legibility — nothing may depend on it:* no machine is ever on two tailnets (clusters on the vendor's,
infra on ours, one `tailscaled` each), so a collision is never resolved on a host, and cross-tailnet
traffic targets **segment** addresses because `tailscaled`'s `ts-forward` hard-codes
`-s 100.64.0.0/10 -j DROP`. What it buys is that an address says which tailnet it belongs to.
*Measured:* the SaaS is not a carve participant — its 13 live addresses are scattered 100.65 → 100.120
across the whole `/10` and we do not control its allocator; the asymmetry is in the type so nobody
later "fixes" the vendor entry by carving it

| 4 — vmnet announcement
| each cluster's nodes announce their own `/21` into the SaaS
| open in `management-workload-topology.adoc`; must land BEFORE step 5, or CAPI loses the workload VIPs

| 5 — bioskop infra nodes
| bioskop and bioskop-nixos register to their tailnet and leave the SaaS
| layer 0 measured first: the serial console and `incus exec` answer. ⚠️ *A consequence of the ssh
repair in step 9:* the guest's tailnet FQDN pattern is derived from `netplan.tailnets.saas.domain`,
the only tailnet with a MagicDNS domain — so the moment a guest leaves the SaaS, that `Host` pattern
stops describing it. It matches nothing rather than mis-matching, so nothing breaks; but the pattern
must follow the guest to its new tailnet, and our tailnets form no FQDN at all

| 6 — nikopol control plane
| same as 2–5, with a private `server_url` reached over the segment
| nikopol is itinerant and has no inbound door; all its members are local

| 7 — the bridge
| WireGuard between the gateways; nikopol initiates with a keepalive
| one static keypair per gateway — the accepted exception

| 8 — screens
| routes + grants replace `svc:rdp-*`; `tailscale-vnc-forward` and its `0.0.0.0:5901` removed
| headscale has no Services

| 9 — keys
| the `mammoth-skate` SSH authority, the signing in `ssh-enrich-keys-yaml.sh`, `renew: on-activation`
and the principals command removed; `vz-nudge` becomes `tart exec`; **no emergency SSH key replaces
them** — the emergency path is a bbox VNC forward to bioskop's screen, its credential from the password
store, so `tcp/2222` and the `rdp.mammoth-skate` ssh tunnel are superseded;
`ssh-keys-renew --retire` writes `revoked` with the slot removal. ✅ *One piece landed early as a
repair, not a removal* (ndh `42c1035c`): both ssh modules read `netplan.tailnet ? name`, a key the
catalog **has never had**, so `tailnetName` was permanently null and the two
`lib.optional (tailnetFqdn != null)` guards could never contribute — the guest's tailnet FQDN reached
no ssh config at all, silently, despite `includeTailnet` defaulting to true. The correct form is the
two-part `<guest><domain>`: `<host>.<name>.<domain>` would have rendered
`bioskop-nixos.mammoth-skate..mammoth-skate.ts.net`, because `name` had been absorbed by `domain`
and nobody removed the guards
| `tart exec` is unmeasured — `tart list` failed on a locked `disk.img`. ⚠️ The ssh repair **changes
rendered ssh config, additively**: the guest stanza now reads
`Host bioskop-nixos bioskop-nixos.local bioskop-nixos.mammoth-skate.ts.net`, where the third pattern
was absent — so reaching a guest by its tailnet FQDN now picks up the intended identity and host-key
policy instead of falling through. Verified at the rendered-file level, not at eval

| 10 — projections
| per-role projections of `keys.yaml`, each encrypted whole for its own recipients. Each GUEST
**generates its own age identity in place** and sends only its PUBLIC up to a seat, which re-encrypts
that guest's projection — so nothing is delivered inbound and the virtiofs share becomes unnecessary.
The operator identity stays between SEATS: operator → bioskop by hand, bioskop → nikopol by authorized
replication
| today every guest receives the operator identity, which opens every sops file. ⛔ *No reprovisioning:*
nikopol already plays its role, so a guest gains its own identity by generating a key in place and
having its projection re-encrypted for it — never by a reset. An alternative route (the age key held
GPG-encrypted in a GitHub repo, unlocked with `gh` from the shared screen, so the bare-metal carries
nothing) is parked

| 11 — dead code and ownership
| `MeshDomainRegistrar` and its units; the `remoteFetch` fallback; the uncalled orchestrator
`ssh-enrich-split-runtime-keys.sh`; the two platform enrichment modules folded into one shared
implementation. **Plus the password-store ownership split** (see below) — the last piece of this
migration
| the orchestrator is bundled by both modules and called by neither — measured. Also to re-examine
when the GPG-rooted bootstrap lands: `modules/nixos/enable-gpg-false.nix` forwards the darwin
gpg-agent into the guests over SSH (the guests sign nothing with GPG, and whether forwarding survives
Tailscale SSH is unverified), and the commented-out `importGpgKeys` activation in
`modules/home-manager/gpg.nix` reads a `gpg.d/keys.yaml` that fits no current model

| 12 — later, and **not decided**
| ⛔ *An earlier revision of this row said "the clusters move to headscale by flipping
`OPERATOR_LOGIN_SERVER`". That was wrong in kind, not merely optimistic* — it presented an
arbitration as a flag flip. The **Funnel cannot move at all**, and two upstream constraints have to
be answered before the step can be designed.
| The scope, the cost and the open arbitrations are a document of their own:
xref:headscale-scope-and-switch-cost.adoc[Headscale — Scope and the Cost of Switching]. Read it
before planning this step; nothing here is executable today, because **headscale 0.30 is not
released**.
|===

=== The password-store ownership split — the cleanup that closes the migration

The store is the bootstrap root (ndh `docs/fabric-control-plane-spec.adoc` § *The initiating
gesture*), so who owns what about it stops being cosmetic. *Measured 2026-10-06:*

[cols="1,2,2",options="header"]
|===
| Holder | What it does today | What it should own

| **ndh** `modules/home-manager/password-store.nix`
| installs `pass` + its extensions, sets `PASSWORD_STORE_DIR`
| the **package and its configuration** — one declaration of the variable, and nothing else

| **zdotdir** `lib/xdg.d/xdg-pass-store`
| sets `PASSWORD_STORE_DIR` — a single line, and it is **syntactically broken**:
`${PASSWORD_STORE_DIR:${XDG_DATA_HOME}/password-store` misses the `-` of `:-` and its closing brace
| nothing — the variable belongs to ndh. The breakage is masked today precisely because ndh sets it

| **zdothome** `.config/zsh/lib/xdg.d/xdg-pass-store`
| the **same line, duplicated**
| nothing

| the **operator**
| clones the store by hand
| the clone — deliberately, as the initiating gesture
|===

⛔ *And a stale second clone.* `~/Gits/nxmatic/store` is a second clone of the same repository, 19
months behind: `cc8b9dc` (2025-02-27, **303** entries) against `cbfb9dd` (2026-09-28, **396**) at the
live `~/.local/share/password-store`. Both working trees are clean, so this is a forgotten copy, not
work in progress — and a bootstrap root with a stale twin is the kind of thing that gets opened by
mistake. To delete once confirmed.

== What the transition deletes

* every SSH key an operator would use to reach the fabric — none is introduced to replace them;
* the `rdp.mammoth-skate` ssh tunnel and the `tcp/2222` forward it needed;
* the `mammoth-skate` SSH authority, the certificates, and the `KnownHostsCommand` / `TrustedUserCAKeys`
  machinery that consumes them;
* every key regenerated at activation, and the eviction logic that could never catch them;
* the principals command that granted every principal to every account;
* the whole-registry subtree in this repository — replaced by its projection;
* the Tailscale Services for the screens, and the ssh tunnel on the screen path;
* the in-cluster mesh domain (`MeshDomainRegistrar`);
* the `remoteFetch` ssh fallback and the uncalled enrichment orchestrator.

== Verdict — does it hold?

[cols="1,3",options="header"]
|===
| Question | Answer

| Is the move monotone?
| Yes, by ordering: every step adds the new path before it removes the old, and steps 4 → 5 are the one
hard dependency — the vmnet announcement must move before any guest leaves the SaaS.

| Does any step risk a lockout?
| Only if layer 0 is not measured first. The serial console and `incus exec` depend on nothing the
migration changes; step 5 starts by proving them.

| What stays out of reach?
| The clusters' move, gated on headscale 0.30.0; and addressing the other tailnet's `100.x` directly,
gated on the fork patch.

| What is still open?
| the vmnet announcement owner, the CGNAT sub-prefix values, the leaf's validity period, the console login of the
runtime guests, sftp and `nix-daemon --stdio` over Tailscale SSH, `tart exec` for the nudge.
|===
